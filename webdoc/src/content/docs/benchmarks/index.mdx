Three runs of Queen MQ 2.0 on a three-node cluster: a throughput ceiling on one queue, a
partition-count stress, and a soak through restarts. Every figure carries its conditions.
**None of them measures `POST /api/v1/transaction`:** they push, pop and ack.

## The rig

- **Brokers:** three DigitalOcean droplets, 16 vCPU and 31 GB RAM each, in one VPC, as one raft
  cluster of three nodes. Every write is replicated before it is answered.
- **Load:** three loader droplets running goload in open loop, so the offered rate does not slow
  down when the broker does, and latency includes any queueing.
- **Messages:** 256-byte JSON payloads, pushed in batches of 100, deduplication on.
- **Consumers:** long-polling pops in batches, explicit acks sent asynchronously. e2e latency is
  measured by goload from push to delivery.
- **CPU:** the droplets do not all have the same CPU model. Each run started with the leader on a
  node with the newer CPU, because the leader's CPU sets the ceiling.

## 1,000,000 msg/s on one queue

One queue of 500,000 partitions, created by a prefill before the timed run, nine goloads (three per
loader). The cluster sustained 1.00M msg/s pushed and consumed, e2e p99 ~270 ms, in 90 s runs
(2026-09-29, raft at `e3456a48`, `benchmark-queen/2026-09-29-1m-3node/README.md`). Later that day
an 8-minute soak of the same shape averaged 990.7k msg/s, ramp included, past the point where
retention starts deleting completed messages; it set `QUEEN_RAFT_PIPELINE=8` and
`QUEEN_RAFT_RT_THREADS=4`, which are the defaults now (`harness-sz-latest/run-0929q.sh` in the
same folder).

- **It shows** that one raft group carries a million replicated messages a second, in and out,
  with half a million partitions in one queue.
- **It does not show** hours at that rate (the longest run was 8 minutes), many queues, larger
  payloads, or transactions.

## 10,000,000 partitions in one queue

One queue of 10,000,000 partitions, prefilled, with 1M msg/s offered. The cluster ran at 913k msg/s
in and 905k out, e2e p99 4.7 s, in a 60 s run (2026-09-29 grid, scripts in
`benchmark-queen/2026-09-29-1m-3node/harness-sz-latest/`).

- **It shows** that the partition count is not a cliff: ten million partitions in one queue,
  every one ordered, on three nodes.
- **It does not show** a latency you would run at (a 4.7 s p99 means messages waited in the
  queue), more than a minute of load, or the same total spread over many queues: in the same grid,
  throughput fell as the queue count rose.

## 500,000 msg/s for hours, through restarts

1,000 queues of 1,000 partitions (a million partitions, prefilled), 500k msg/s offered by nine
goloads, pop sizing left to the SDK defaults, completed-message retention of 300 s. A fault every
90 minutes, the first 10 minutes in: kill -9 of the leader, SIGTERM of the leader, kill -9 of a
follower, in turn. In steady windows, e2e p50 was ~19 ms and p99 ~80-90 ms (the night of
2026-09-30, the builds committed as `7a2a1711`, 2.0.0-beta.1,
`benchmark-queen/2026-09-30-stage03-3node/`).

- **It shows** latency at half the ceiling with retention running, and a cluster that keeps
  serving through kill -9 and rolling restarts of its leader.
- **It does not show** the minutes after each fault, when throughput dips while the restarted node
  catches up, or runs of days.

## What none of these show

- **Transaction throughput.** No published run measures `POST /api/v1/transaction`. Do not read
  these rates as transaction rates.
- **Your workload.** One tenant, one raft group, three nodes, 256-byte payloads, one rig. Five-node
  clusters, larger payloads and other hardware are unmeasured.
- **The current build.** Each run names its commit, and the engine has changed since. Treat the
  figures as what those builds did on this rig.

## Reproduce

Each folder holds the scripts and the goload source that ran. In `2026-09-29-1m-3node/harness/`,
`setup.sh <b1 b2 b3 l1 l2 l3>` provisions the droplets, then
`env SECS=90 NL=3 AVOID=3 CONS=33 PARTS=500000 PREFILL=1 LANES=8 ./sz9.sh <tag> 1000000` runs the
1M shape; in `2026-09-30-stage03-3node/`, `setup30.sh` provisions and `soak.sh <tag>` runs the
soak, read with `soak-status.sh <tag>`.

Results measured on Queen 1.x, whose storage was PostgreSQL, stay in the git history of this site.
They are not 2.0 numbers. For what the cluster guarantees under faults, see
[guarantees](/concepts/guarantees/).
