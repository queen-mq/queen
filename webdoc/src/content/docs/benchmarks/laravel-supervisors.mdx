This qualification asks whether Queen can replace the **process control plane** of Laravel
Horizon for Queen-backed Laravel queues. Queen does not replace `queue:work`: both Queen engines
start ordinary Laravel workers, while the Queen broker remains outside process supervision.

The performance results on this page are **diagnostic**, and the feature and fault results are
**diagnostic smoke tests**. They were produced on Docker Desktop on an Arm Mac, not on a dedicated
Linux benchmark host. The protocol was written by the Queen team and is not an independent
certification.

## What was compared

| Lane | Queue backend | Orchestrator | Worker command |
| --- | --- | --- | --- |
| Horizon | Redis | Horizon PHP master and supervisor | `artisan horizon:work` |
| Queen PHP | Queen broker plus PostgreSQL | Resident Laravel/PHP master | `artisan queue:work queen` |
| Queen Rust | Queen broker plus PostgreSQL | `queen-supervisor` Rust master | `artisan queue:work queen` |

The Queen PHP engine is the reference implementation. The Rust engine resolves the same Laravel
configuration once, then leaves Rust and the ordinary PHP workers resident. Both Queen engines
use the same worker limits and resolved supervisor contract.

The fixture pinned PHP 8.3 semantics, Laravel 12.68.0 and Horizon 5.48.3. Every lane ran the same
Laravel application, serialized job, JSONL result sink and worker limits. Redis and Queen plus
PostgreSQL are not equivalent in topology or durability, so whole-stack figures describe the
declared product-shaped configurations. They are not a broker microbenchmark.

## Final diagnostic cell

The final confirmation measured commit `a79db4de9bc9d59cdc6facf42a475bbb7a3dd7a1` with:

- macOS 26.5 on Arm, Docker Desktop Engine 29.7.2 and LinuxKit containers;
- cgroup v2, 10 exposed CPUs and 8,214,851,584 bytes of exposed memory;
- a fixed pool of four workers in every lane;
- 2,000 jobs per lane, each with 10 ms of simulated work;
- Queen prefetch 4 and ACK batch 1, with lease renewal disabled;
- three repetitions per engine, nine runs in total.

All nine runs completed the exact job set, reached queue quiescence and passed container
isolation. Values below are medians.

| Metric | Horizon | Queen PHP | Queen Rust |
| --- | ---: | ---: | ---: |
| Completion jobs/s | 294.30 | 300.08 | 307.67 |
| End-to-end p95 | 6,019.54 ms | 5,478.43 ms | 5,266.49 ms |
| Orchestrator PSS | 65.0 MiB | 35.1 MiB | 2.9 MiB |
| Measured stack CPU | 3.750 s | 4.148 s | 3.938 s |
| Measured stack memory | 198.1 MiB | 295.1 MiB | 265.3 MiB |

Control-plane PSS excludes queue workers and backends. Measured stack memory includes the
application container and its complete backend, Redis for Horizon and the Queen broker plus
PostgreSQL for Queen.

## Paired ratios

Each entry is candidate divided by Horizon for matched repetitions. A throughput ratio above one
favours the candidate. A latency or resource ratio below one favours the candidate. Parentheses
contain the deterministic paired-bootstrap 95% descriptive interval where the report provides
one.

| Candidate | Throughput | End-to-end p95 | Orchestrator PSS | Stack CPU | Stack memory |
| --- | ---: | ---: | ---: | ---: | ---: |
| Queen PHP | 1.018 (0.937 to 1.041) | 0.924 (0.874 to 0.933) | 0.541 | 1.061 (1.018 to 1.110) | 1.488 |
| Queen Rust | 1.046 (1.044 to 1.064) | 0.888 (0.850 to 0.898) | 0.044 | 1.031 (0.950 to 1.060) | 1.341 |

Within this cell, Queen Rust completed 4.6% more jobs per second, reduced p95 by 11.2% and used
95.6% less orchestrator PSS than Horizon. Its stack CPU result is inconclusive because the
descriptive interval crosses one. Its measured whole-stack memory was 34.1% higher. Queen PHP
used 45.9% less master PSS, but its throughput result is inconclusive, its measured stack CPU was
higher and its whole-stack memory was 48.8% higher.

Only three pairs contribute to each final ratio. These intervals describe variation among runs on
this host; they do not remove host, workload or topology bias and are not population guarantees.
The results do not support a universal claim that one supervisor is faster or cheaper for every
Laravel workload.

## Method and anti-bias controls

The qualification protocol was frozen before the final campaign. The runner then applied these
controls:

- one lane at a time, with a fresh backend and result volume for every sample;
- matched workload, worker settings, cgroup budgets and application code;
- rotated Horizon, Queen PHP and Queen Rust execution order;
- exact job-set and settled queue-state gates before a run became comparable;
- no post-hoc outlier removal;
- per-run values, medians, quartiles and deterministic paired bootstrap ratios;
- container inventory snapshots plus a continuous Docker start-event watcher;
- fail-closed handling for a dirty checkout, image or configuration mismatch, foreign or replaced
  containers, unexpected restart or OOM, incomplete sampling and a non-empty final queue;
- retention of failed-run evidence rather than silently dropping it.

The fail-closed dirty-tree gate was exercised in practice. An otherwise valid campaign was
excluded because an unrelated local file made the checkout dirty, then repeated on the same clean
commit without an override.

## Reliability smoke tests

The feature-parity harness used fresh backends. Every engine completed exactly 24 of 24 jobs over
two queues, left both queues empty and retained the expected worker identities. Queen PHP and
Queen Rust also exercised the Queen-specific synchronized failed-job path: a terminal failure
appeared in both Laravel's failed repository and Queen's DLQ, `queue:retry` succeeded, and both
indexes were empty afterwards. The harness did not run that Queen-specific synchronization test
for Horizon, which is not evidence that Horizon lacks its own failed-job lifecycle.

The worker fault smoke killed one worker during user code:

| Engine | Observed respawn | Unique jobs | Missing | Effects | Retry observed | Queue empty | At-least-once | Strict execution |
| --- | ---: | ---: | ---: | ---: | --- | --- | --- | --- |
| Horizon | 997.5 ms | 24/24 | 0 | 24 | yes | yes | pass | fail |
| Queen PHP | 1,509.5 ms | 24/24 | 0 | 24 | yes | yes | pass | fail |
| Queen Rust | 1,442.8 ms | 24/24 | 0 | 24 | yes | yes | pass | fail |

Strict execution fails because the interrupted attempt is retried. The fixture's SQLite ledger
keeps one idempotent effect for each job, but it is not atomic with a queue ACK or with an external
database or service. These results support at-least-once recovery for this injected fault, not
exactly-once delivery or a failure-probability estimate.

## The prefetch and renewal caveat

The final performance cell used prefetch 4 and ACK batch 1 without the lease-renewal helper. That
combination is now classified as diagnostic only. Laravel can retain a prefetched leased tail for
an unbounded period during maintenance mode, `queue:pause` or a `Looping` listener.

A no-helper profile is supported with prefetch 1 only when the worst-case runtime of one job plus
margin remains below `retry_after`. Every Queen supervisor profile with prefetch greater than one
requires lease renewal. The helper has passed focused and end-to-end smoke tests, including a job
that outlived its original lease and a renewal failure that fenced the worker before retry, but its
cost was not present in the final table.

The production performance candidate is therefore prefetch 4, ACK batch 1, renewal enabled. The
[Raft campaign below](#horizon-against-queen-on-raft-2026-10-01) measures it, still as a diagnostic
result. ACK batches greater than one remain separate fault-oriented experiments because they widen
the duplicate and recovery window.

## Supervisor features, 2026-09-30

Three opt-in features of supervisor 0.4.0 were measured after the qualification: prefork workers,
coordinated replicas and fast scale-up. One Apple Silicon host with Docker Desktop, Queen 1.6.0 and
PostgreSQL 16 ran every case, with the same Laravel application as above. The results show what
each feature changes; they are diagnostic, not a release performance claim. Scripts, raw samples and
limits are in `benchmark-queen/2026-09-30-laravel-supervisor-features/`.

### Prefork memory

Inside a Linux container with PHP 8.4, N workers were started one by one (`spawned`) or forked from
one booted Laravel (`forked`, the fork server included). The proportional set size (PSS) of every
process was summed 15 seconds after the start, or after a burst of 600 jobs. PSS divides a shared
page among the processes that share it, so the sum is the physical memory the workers hold together.

| Case | Opcache | Spawned | Forked | Saving |
| --- | --- | --- | --- | --- |
| 4 idle workers | off | 146 MiB | 91 MiB | 38% |
| 4 idle workers | on | 167 MiB | 69 MiB | 59% |
| 8 workers after 600 jobs | off | 272 MiB | 142 MiB | 48% |
| 8 workers after 600 jobs | on | 336 MiB | 85 MiB | 75% |

Medians of three runs; the runs differed by at most 1 MiB. With opcache on, every spawned worker
compiles its own copy of the framework, which forking shares. The resident set size barely moves
(203 against 202 MiB for four idle workers) because it counts a shared page once in every process.
A worker that runs for hours writes to more of the shared pages than one measured after 15 seconds,
so the saving in production is lower than this table.

### Coordinated replicas

Two Rust supervisors served one queue and consumer group, as two pods would, each with
`max_processes` 8, the `size` strategy and 10 jobs per worker, against a backlog of 150 jobs of three
seconds. Both status documents were sampled every second for thirty seconds. The fleet target is
what one pool of 16 would size for the sampled backlog: `ceil(depth / 10)`, at most 16.

Without coordination, each pod sized the whole backlog on its own. The two ran above the fleet target
in all 30 samples, and twice it once the target fell under 8: 12 workers for a target of 6. With
coordination, the two shares added up to the target in all 30 samples. The uncoordinated run
drained its backlog sooner because it ran more workers than configured; coordination keeps the
fleet to the configured target, so raise `max_processes` or the replica count to go faster.

### Fast scale-up

One Rust supervisor with `max_processes` 20, `balance_max_shift` 1 and a one-second poll and
cooldown received 600 jobs of five seconds while running its minimum of one worker. Its running
workers were sampled every half second. Stepping by one worker per cycle, it reached 20 workers after
18.1 seconds; with `fast_scale_up`, which closes half of the remaining gap per cycle, after 3.6
seconds. The production defaults are a three-second poll and cooldown, which multiply both times by
about three.

### Event-driven scaling

One Rust supervisor at the production cadence, a three-second poll and cooldown, with
`fast_scale_up`, `max_processes` 20 and `balance_max_shift` 1, idled at one worker on an existing
queue. Then 600 jobs of five seconds were dispatched, and the running workers were sampled about
every third of a second from the start of the dispatch. Three runs polled; three were woken by the
broker with `event_driven`.

| Mode | First extra worker | Twenty workers |
| --- | --- | --- |
| Polling | 1.6 s | 13.9 s |
| `event_driven` | 0.5 s | 5.6 s |

Medians of three runs. With polling, the first step depends on where the burst falls in the
three-second cycle, and every later step waits for the cooldown. Woken by the broker, the pool took
its first step as the first jobs arrived and then one step per second. The dispatch clock includes
the Laravel boot of `bench:dispatch`, which is the same in both modes.

## Horizon against Queen on Raft, 2026-10-01

This campaign compares Horizon with the Queen supervisor on the Queen **Raft** broker, and measures
the worker-side changes of this release one at a time:
[lease renewal in the master](/use/laravel/supervisors#lease-renewal-in-the-master),
[asynchronous acknowledgements](/use/laravel#asynchronous-acknowledgements) and
[popping the next batch ahead](/use/laravel#pop-the-next-batch-ahead). It is the paired campaign for
prefetch 4 with renewal enabled that the section above asked for. Scripts, one row per run and limits
are in `benchmark-queen/2026-10-01-laravel-horizon-raft/`.

- One Apple Silicon host with Docker Desktop, cgroup v2, and the same Laravel application as above.
- Horizon on Redis 7.4 with AOF. The strict cells use `appendfsync always`, so Redis and the Raft
  log both fsync every acknowledged write; the relaxed cell uses `everysec` for Redis, while Raft
  keeps fsyncing every write. Redis and the broker each had 2 CPUs and 2 GiB.
- Queen with the Rust supervisor, prefork workers and the command-line opcache, one Raft node on a
  local data directory, prefetch 4 with lease renewal unless a row says otherwise.
- One fixed pool of 8 workers, jobs of 10 ms, dispatched with `Queue::bulk()` at the start of each
  run, 5 runs per engine and lane on a fresh backend. All 165 runs completed the exact job set, with
  no duplicate and no failure.

Values are medians of 5 runs.

| Lane | Horizon | Queen | Queen against Horizon |
| --- | ---: | ---: | ---: |
| 10 ms jobs, fsync every write | 417 jobs/s | 643 jobs/s | 1.54x |
| 10 ms jobs, Redis `everysec`, Raft fsync every write | 548 jobs/s | 635 jobs/s | 1.16x |
| Empty jobs | 670 jobs/s | 1,585 jobs/s | 2.37x |
| CPU-bound jobs of about 20 ms | 389 jobs/s | 401 jobs/s | 1.03x |
| Prefetch 1 | 410 jobs/s | 628 jobs/s | 1.53x |
| Burst, autoscaling from 1 to 16 workers | 451 jobs/s | 709 jobs/s | 1.57x |
| Workers at the peak of that burst, and time to reach it | 10 after 7.3 s | 15 after 4.3 s | |
| 300 jobs/s arriving one by one, end-to-end p95 | 90 to 105 ms | 19 to 20 ms | 0.18x to 0.22x |
| 100 jobs/s arriving one by one, end-to-end p95 | 19 ms | 21 ms | 1.11x |
| PSS of master and 8 workers | 310 MiB | 70 MiB | 0.23x |

Throughput depends on how long a worker waits between two jobs. Every Raft write, a pop or an ACK,
waits for a group-commit fsync of about 5 ms on this host. A Horizon worker makes two fsynced Redis
writes per job. Queen now keeps both of its writes off the worker's critical path: the ACK of a job
travels while the next job runs, and the pop for the next batch travels while the last job of the
current one runs. The CPU-bound lane shows where that stops mattering: when the job itself dominates,
both systems are equal.

Memory is where the supervisor-side change counts. A lease helper per worker cost 99 MiB for 8
workers; serving renewal from the Rust master removes all of it. With prefork, the whole Queen
application, master and workers, used 70 MiB against Horizon's 310 MiB. The backends are separate:
the Raft broker used 23 to 37 MiB and Redis 20 to 57 MiB, depending on the lane.

The backlog lanes enqueue every job at once, so their latency measures the length of the queue. The
paced lanes dispatch one job at a time at a fixed rate below capacity and measure how soon a job
runs. At 100 jobs/s the two systems are equal. At 300 jobs/s, Horizon's workers queue behind Redis's
fsync on every write, and its p95 grows to 90 to 105 ms; Queen's stays at 19 to 21 ms, with prefetch
1 or 4 and with or without the pop ahead.

Queen spends more CPU in the workers in most lanes. With 10 ms jobs and fsync on every write, the
Queen application used 7.8 CPU seconds for 5,000 jobs, against Horizon's 3.1; with empty jobs the two
were equal, 5.8 against 6.0 seconds for 10,000 jobs. The HTTP client costs more per request than
phpredis. At 100 paced jobs/s the Raft broker also used 4.7 CPU seconds against Redis's 1.1. Size
worker CPU from your own jobs.

The PHP client's [cURL transport](/reference/sdk/php#transport) was measured afterwards in
Queen-only lanes, against the Guzzle transport on identical images. With 10 ms jobs and fsync on every
write the application used 6.3 to 6.8 CPU seconds for 5,000 jobs against 7.4 to 7.7, at 660 to 665
against 649 to 652 jobs/s. With empty jobs and prefork it used more, 6.5 to 6.9 against 5.6 to 6.3
seconds for 10,000 jobs, and the broker's CPU rose by about a third; without prefork the two were
within noise. That case is not explained on Docker Desktop; on the Linux server below, cURL was
faster and cheaper with empty jobs too.

Seven of these lanes ran again on the final commit, after the last review fixes: throughput and
latency moved by at most 3%, and the time to the burst's peak became 5.3 s for Queen against 6.3 s
for Horizon. Those runs are in `raw/runs-final.csv`.

Two fault-recovery runs on the same broker checked the new paths under failure. With 24 jobs of
2 s on 2 workers, a worker killed with SIGKILL during a job was back after 1.0 s under Horizon and
1.4 s under Queen, and both ran all 24 jobs with no duplicate effect; the killed job ran again, as
at-least-once delivery allows. In the second run, 16 jobs of 8 s with prefetch 4 and a 30 s lease,
the last job of a prefetched batch ended 32.1 s after its pop on its first attempt, because the
master renewed the lease; again all 16 jobs ran with no duplicate effect.

These results are diagnostic. Docker Desktop's virtual disk sets the fsync cost, a single Raft node
adds no replication round trip, and the protocol was written by the Queen team. The next section
repeats them on a dedicated Linux server; a Raft cluster is still to come.

## Horizon against Queen on a Linux server, 2026-10-01

The same comparison on a dedicated Linux virtual machine, with 16 to 64 workers, up to 360,000 jobs
per run and a 15-minute soak. Scripts, one row per run, the broker profile and limits are in
`benchmark-queen/2026-10-01-linux-vm-horizon-raft/`.

- A DigitalOcean droplet with 16 vCPUs (Intel Xeon Gold 6548N), 31 GiB and a virtual disk, Ubuntu
  24.04, Docker 29. Nothing else ran on it.
- The application had 8 CPUs and 8 GiB; the broker and Redis 4 CPUs and 4 GiB each.
- Horizon on Redis 7.4 with AOF, `appendfsync always` unless a lane says otherwise. Queen on one Raft
  node, server `2.0.0-beta.2`, which fsyncs every acknowledged write in every lane, with the Rust
  supervisor, prefork, lease renewal in the supervisor, `ack_async`, `pop_ahead`, prefetch 4 and the
  cURL transport.
- Jobs of 10 ms unless a lane says empty, 3 runs per engine and lane, engines alternating, each run
  on a fresh backend. All 119 runs completed the exact job set, with no duplicate and no failure.

When all jobs are dispatched in one burst, Horizon's rate is its producer's. For every job it
dispatches, Horizon writes its monitoring records to Redis, and with `appendfsync always` one
producer sends about 860 jobs/s. The drain lanes take the producer out: every worker is held until
the whole batch is enqueued (`run.sh --backlog-first 1`), and in none of their 24 runs did a job run
before the release.

| Lane | Horizon | Queen |
| --- | ---: | ---: |
| 50,000 jobs, 32 workers | 1.83 and 0.37 ms | 0.91 and 0.23 ms |

Under load the Raft broker spends less CPU per job than Redis; at a low, steady rate it spends more.
A profile of the broker at 500 jobs/s found the reason: each job is its own Raft entry, and about half
of the broker's CPU goes to handing work between threads (waking them, system calls and scheduling),
not to the queue's work; the fsync itself is about 3%. Under a bulk load one entry carries about 12 jobs and the cost is shared.
`raw/broker-profile.md` has the breakdown. The profile also found that `pop_ahead` sent a pop with
every job at a low rate, which came back empty; it now pops ahead only after a full batch. On the
server that halved the pops at 500 jobs/s and took 12% off the broker's CPU and 8% off the
application's, with the same latency and no change under load.

The worker-side changes, one at a time, with 50,000 jobs and 32 workers: 1,890 jobs/s with prefork
alone and 417 MiB for the application, 1,879 jobs/s and 116 MiB with lease renewal in the
supervisor, 2,270 with `ack_async` and 2,794 with `pop_ahead`. The cURL transport against Guzzle,
with 100,000 empty jobs: 6,030 against 5,441 jobs/s, and 1.03 against 1.41 ms of application CPU per
job.

The limits stay: one virtual machine and its disk, one Raft node, and a protocol written by the Queen
team. A Raft cluster and other hosts must repeat it before it becomes a release performance claim.

## Failures, replicas, a soak and Laravel features, 2026-10-02

The same Laravel application ran on Horizon, the Queen PHP supervisor and the Queen Rust supervisor
through the failures that a production deployment meets, then through ordinary Laravel queue
features. Each job writes its attempts to a log on the lane's volume, so every check reads what the
jobs did, not what an engine reports. Scripts, every lane's result and the tables are in
`benchmark-queen/2026-10-02-laravel-failure-matrix/`.

- The Linux server of 2026-10-01. The application had 4 CPUs and 1 GiB, the broker and Redis 2 CPUs
  and 2 GiB each, every lane on a fresh backend.
- Horizon on Redis 7.4 with `appendfsync always`. Queen on one Raft node, server `2.0.0-beta.3`,
  with the PHP client and supervisors of this release.
- Queen with its production-like settings: prefetch 1, synchronous ACKs, lease renewal, prefork
  workers. A fourth column runs the Rust engine with prefetch 4, `ack_async` and `pop_ahead`.
- Every lane: 2 workers unless it says otherwise, a pool `timeout` of 20 s, `retry_after` 30 s and
  `shutdown_grace` 35 s.

### What the failure lanes found

**Three defects in the Queen PHP client and supervisors, fixed in this release.** With prefetch
above 1, a graceful stop handed the unstarted jobs of a batch back with a retry ACK, which the
broker counts as a delivery, so jobs reached `failed_jobs` before running `tries` times. With
`ack_async`, the ACK of a finished job could stay unwritten until the next job ended, so a worker
killed during that job ran the finished job again. And both supervisors counted a worker that
Laravel killed after a job timeout as a crash: after five of them, the crash circuit cut the pool
to one worker for 30 s. The table above is the run with the fixes; the first run, with the client
of 2026-10-01, found these:

| Lane, Rust engine with prefetch 4 | Before the fixes | After |
| --- | --- | --- |
| `job-timeout` | 3 of 4 jobs reached `failed_jobs` after one run | Pass |
| `memory-limit` | 1 of 6 jobs failed instead of completing | Pass |
| `stop-long` | 1 of 2 jobs completed twice | Pass |
| `stop-long-batch` | The job done before the deploy ran again | Pass |
| `memory-fatal` | Both jobs failed after one run | 1 of 2 jobs failed without running; passed with the crash hand-back below |

With the supervisor fix, the four jobs of `job-timeout` reached `failed_jobs` after 44 s on both Queen
engines, against 126 to 147 s before, while the crash circuit held the pool back. An audit of the
PHP client and both supervisors during the same night fixed ten more defects, each with a test that
failed before its fix; the changelog lists them.

- **The prefetched-batch lane is the proof of the ACK fix.** One worker runs two 60 s jobs of one
  prefetched batch, and a deploy kills it during the second. With the client before the fix, the
  first job, finished before the deploy, ran again; with the fix it ran once, on all three Queen
  profiles.
- **A crash charged an attempt to a prefetched job; the lease renewer now hands those jobs back.**
  When a worker died without a shutdown (SIGKILL, a PHP fatal error), the unstarted jobs of its
  batch returned when the lease expired, and each counted one delivery. In `memory-fatal` with
  prefetch 4 and `tries` 2, a job that never ran reached `failed_jobs` because the job before it
  crashed the worker twice, and in `worker-kill` the jobs the killed worker had not started ran 31 s
  later as their second attempt. With the
  [crash hand-back](/use/laravel/concepts#prefetch-ack_async-and-pop_ahead), the Rust master or the
  PHP lease helper sends what the dead worker journaled. A rerun of five lanes on Docker Desktop,
  on both engines with prefetch 1 and with prefetch 4, passed all twenty: in `worker-kill` those
  jobs ran a few seconds after the kill as their first attempt, and in `memory-fatal` both jobs ran
  twice. A lost node, a crash that takes the lease helper with the worker, and a batch popped ahead
  and not read yet still charge the attempt.
- **Horizon ran 2 of 300 jobs twice after a Redis restart.** They finished while Redis restarted.
  The worker could not remove them from Redis's reserved set, so their reservation expired after
  `retry_after`, and they ran again 30 s later. Both stacks deliver at least once. The Queen client
  retries a failed request three times, 1 s and then 2 s apart, so the ACKs sent during the broker's
  restart went through when it came back.

## What remains before GA

The current evidence supports a Unix release candidate within the tested single-master scope. A
general-availability claim still requires:

1. fixed, automatic and scaling campaigns on dedicated native Linux amd64 hosts;
2. equivalent native Linux arm64 campaigns before publishing an arm64 performance claim;
3. the paired campaign for prefetch 4, ACK batch 1 and renewal enabled, run above on one Docker
   Desktop host and one dedicated Linux virtual machine, repeated on more hosts and a Raft cluster;
4. the 1, 2, 4 and 8 worker matrix, three queues, and the declared partition and pop-fusion cells;
5. a 24-hour Laravel soak for each engine with a durable ledger and memory-slope analysis;
6. the failure lanes of 2026-10-02, run above on one Raft node, repeated on PostgreSQL storage and
   a Raft cluster, with network, packet-loss, latency and full-storage faults;
7. native installer, process-tree and provenance verification for every release target;
8. macOS Developer ID signing and notarization before general macOS availability;
9. a native Windows process backend and Windows end-to-end tests before any Windows asset;
10. web actions to forget, flush and prune failed jobs, or an explicit revision of that dashboard
    gate; retry already has one, on the failed-job detail page.

The historical Queen broker result near one million accepted pushes per second used Go loaders,
200 partitions and 600 consumers on dedicated infrastructure. It did not execute Laravel jobs or
exercise either supervisor, so it is not evidence for Laravel supervisor throughput.
