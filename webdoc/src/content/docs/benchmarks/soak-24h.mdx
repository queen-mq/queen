**In 24 hours, one broker against one PostgreSQL moved 86,369,975,300 messages (about 1,000,000
per second in each direction) with leased pops, explicit acknowledgement, deduplication and
retention all on, zero restarts, and resident memory flat at roughly 4.1 GB.** The broker host was a
32 vCPU / 62 GiB machine and the broker was Queen **1.0.0**. Artifacts are in
`benchmark-queen/2026-08-11-soak24-1M/`, and each loader's own stdout is under `raw/loader-0*/g.out`.

This is the reference run for production semantics, and the only one long enough to distinguish
"fast" from "stays fast".

## Configuration

The load was offered by three loader hosts against one broker, 333,334 and 333,333 and 333,333
messages per second, so that the generator could never be the limit. Each loader printed its own
configuration, which is what makes this quotable:

```text
goload -mode openloop -> queue=segbench partitions=200 consumers=200 manualAck=true ackAsync=true ackInflight=256
  offered: rate=333334 msg/s | push-batch=100 -> 3333.3 req/s across 64 pacer workers | max-inflight=20000 | payload=256B
[configure] queue=segbench completedRetentionSeconds=300
```

| Parameter | Value | Why it matters |
| --- | --- | --- |
| Delivery semantics | leased pops with explicit acks (`manualAck=true`) | The cursor moves only on an ack, which is the at-least-once path real work uses. Server-side auto-ack would remove one round trip and one transaction per batch |
| Ack dispatch | asynchronous, 256 in flight (`ackAsync=true`) | Each batch's ack is dispatched on its own task so a consumer does not hold a partition's lease blocked on its own ack round trip. An ack is never shed; when the semaphore is full the consumer blocks |
| Offered rate | 1,000,000 msg/s, open loop | Fixed schedule across three loader hosts, 10,000 push requests per second in total |
| Push batch | 100 messages | Amortises per-transaction cost. Batch 1 is a different measurement |
| Pop batch | 1,000 messages | The serve size a consumer asks for |
| Payload | 256 bytes | One size, one shape |
| Partitions | 200 | Consumption parallelism per group is bounded by partition count |
| Consumers | 600 closed-loop drainers, 200 per loader | Consumers pull; consumer count changes the answer |
| Deduplication | on, 60-second window | Every push probes the transaction-id sidecar under the partition lock before offsets are allocated. This is part of the measured path |
| Retention | on, completed messages after 300 s, pending after 3,600 s | The reason the database plateaus instead of growing |
| Duration | 86,400 s after a 60 s ramp, reported every 30 s | 2,880 interval lines per loader in the archived stdout |

<Aside type="note">
Three loader hosts rather than one is a property of the rig, not of the broker. Generating and
consuming this shape costs about 20 microcores per message operation, so a million per second in
each direction needs roughly 40 cores of load generator before the broker is even reached. A
single 48-core loader tops out near 950,000 on the pop side and becomes the measurement.
</Aside>

| Messages popped | 86,369,532,700 |
| Messages acked | 86,369,517,700 |
| Failed push requests | 4 |
| Failed pop requests | 0 |
| Failed acks | 600 |

| Restarts, incidents | **0, 0** |

Average accepted throughput is 86,369,975,300 over 86,400 s, or 999,652 msg/s including the ramp.

Popped falls short of pushed by 442,600 messages, or 0.0005%. That is the residue still in flight
when the clock ran out, not loss: the loaders stop offering at 86,400 s and their in-flight leases
are cut with them.

### Latency, across the whole run

Each loader reports its percentiles every 30 seconds. Over 8,643 such reports:

| Reported percentile | Median | p90 | p99 | Worst single interval |
| --- | --- | --- | --- | --- |
| p50 | 92.7 ms | 106.0 ms | 117.2 ms | **160.8 ms** |
| p99 | 288.8 ms | 325.6 ms | 358.4 ms | **593.9 ms** |
| p99.9 | 383.0 ms | 432.1 ms | 489.5 ms | **856.1 ms** |

No 30-second interval, on any of the three loaders, reported a p99 above one second in 24 hours.

Broker memory is the number this run exists to produce. A leak at this rate would be obvious: at a
million messages per second, a per-message overhead of even tens of bytes is gigabytes per hour.
Across 24 hours the samples span a 4.10 GB mean and a 4.37 GB maximum, with no trend.

The database plateau is retention working. Completed messages leave after 300 s, so steady-state
size is set by the retention window and the rate rather than by the run length. Sampled every
three hours the size reads 29.8, 29.6, 30.2, 30.0, 29.9, 31.4, 30.4 and 31.2 GB.

## Errors

Every error counter over the whole run, on 86,369,975,300 accepted messages:

| Counter | Value | Unit |
| --- | --- | --- |
| Failed push requests | 4 | requests, each carrying 100 messages |
| Failed pop requests | 0 | requests |
| Failed acks | 600 | messages |
| Shed | 0 | messages |

Push and pop errors count failed **requests**; ack errors count **messages**. The message-level
statement is therefore that 1,000 messages were touched by an error of any kind, and that 41,800
of 86,370,017,100 offered messages were never accepted, which is 0.000048%, with nothing shed.

## What this run establishes

- **No memory leak on the hot path at scale.** 24 hours at a million messages per second per side
  with resident memory flat at 4.1 GB. Short runs cannot show this.
- **Retention reaches a steady state.** The database plateaued at about 30 GB instead of growing,
  and the plateau is set by the retention window rather than by the run length.
- **Explicit acknowledgement is affordable at this rate.** Leases plus an offset commit per batch
  sustained a million per second per side at about 11 cores of broker CPU and 12 of PostgreSQL, on
  a 32-core host.
- **The rate is steady, not an average.** Twenty-three consecutive hours inside a 0.02% band, and
  no 30-second interval above a one-second p99.

## What it does not establish

- **Not a per-message completeness proof.** The open-loop loader counts aggregates: offered,
  accepted, popped, acked. It does not assign a sequence number per message and check the set on
  arrival, so "zero loss" is not one of this run's findings. The run that does per-message
  accounting is [the ordered pipeline](/benchmarks/ordered-pipeline), and the run that does
  per-tenant bitmaps is [the multi-tenant cell](/benchmarks/multitenant-cell).
- **Not an ordering proof.** No verifier ran. Ordering was verified separately.
- **Nothing about high availability.** One broker, no mesh, no peer.
- **Nothing about failure.** No PostgreSQL restart, no failover, no broker kill, no consumer
  churn. The disk spool was never exercised.
- **Nothing about the proxy, tenancy, quotas or rate limits.** The loaders spoke to the broker
  directly.
- **One workload shape.** 256-byte payloads, push batch 100, 200 partitions, one queue, one
  consumer group. Batch 1, large payloads and wildcard consumption are all materially different
  measurements.
- **A compressible payload.** The loader's body is a repeated character, which the write path
  compresses to almost nothing: 83 MB/s of WAL at a million messages per second is 83 bytes per
  message, envelope included. A payload of real, high-entropy data would write several times that,
  and this run does not measure it.
- **Fast storage.** About 70 µs per `fdatasync` on the broker host. This figure is not disk-bound.
