A million messages a second is worth nothing if one of them can go missing. We check that with
Jepsen: five nodes, clients driving the native API as hard as they can, a nemesis that kills,
pauses, partitions, skews clocks and cuts power, and checkers that read the whole history
afterwards looking for a message lost, delivered twice, acked twice or seen out of order. The
latest full campaign ran 257 tests on the code of 2.6.0, on 2026-10-21 and 22, a standby cluster's
failover and pushes of several messages at once among them: all 257 came back valid, 255 at their
first run, one in four reruns after its first run's final drain ran out of time, and one once its
history was checked again with the checker's other search. That is
evidence, not proof. Jepsen finds bugs and cannot show there are
none, and further down is every bug it found in Queen 2.

## How a test runs

Each test starts a fresh five-node cluster, which needs three nodes for a quorum. It runs one
workload for 300 seconds at 100 to 200 operations a second while the nemesis injects one class of
fault (a few tests combine two), then heals everything, lets the clients finish (drain the queues,
read every partition) and hands the full history to the workload's checkers. A test is valid only
when every checker is. The failover workload is the exception in its shape: it starts two
clusters of three nodes, one following the other, and the faults run on both. The harness is in
`test/jepsen/` (Clojure, Jepsen 0.3.14), and `run-campaign.sh` runs a list of tests and writes
one verdict line per test. The checkers judge the history, and three nodes of five can carry a
history while the other two are down, so after each test the script also reads every node's log:
a node that refused to start or panicked turns the line into `REFUSED`, whatever the checkers
said. The tests that damage a node's files on purpose are left out of that, because there a
refusal is the right answer. The panic checker inside each test, which looks for a panic, a
poisoned lock or `NA-QLOG-I1` in every node's log, leaves out the same refusals since 2.5.0: an
`NA-QLOG-I1` line the nemesis recorded as its victim's reason to refuse a boot.

<Figure id="benchmarks/jepsen-test" />

```bash
cd test/jepsen
RUNS=/root/runs BIN=/root/bin/queen ./run-campaign.sh matrix-p11.txt
```

One test on its own, against nodes `n1` to `n5` reachable over SSH:

```bash
lein run test --nodes n1,n2,n3,n4,n5 --username root --bin /root/bin/queen \
  --concurrency 2n --workload queue --nemesis kill --time-limit 300 --rate 200
```

## What each workload checks

| Workload | What the clients do | What the checker rejects |
|---|---|---|
| W1 `log` | push, and read partitions by offset; with `--txn`, pushes to several partitions in one transaction; with `--batch-sends N`, pushes of up to N messages of one partition | an acknowledged record lost or duplicated, two orders of one partition, a gap in the offsets, a transaction partly visible |
| W2 `queue` | push, leased pop, one batch ack carrying the lease | an acknowledged message lost, a message acked twice, a redelivery after a successful ack, two unexpired leases on one message, order skipped within a partition |
| W3 `register`, W3b `counter`, W3c `claim` | KV get, put and compare-and-set; increments; `putIfAbsent` | a history that is not linearizable; an increment lost or doubled; two winners of one claim |
| W4 `elle` | KV calls that write and read several keys | any history that is not strict serializable, as Elle finds it: G0, G1, G-single, G2 and their real-time forms |
| W5 `pipeline` | pop one message, then one `/api/v1/transaction` that acks it with its lease, pushes its output and increments a KV counter | an input lost, an input committed twice, output from a transaction that rolled back |
| W6 `dedup` | pushes that reuse `transactionId`s, an unanswered one re-sent once to another node; with `--batch-sends N`, pushes of 2 to N ids of one partition | two records for one id, an answer naming an offset that does not hold its record |
| W7 `dlq` | acks that fail messages under a retry budget, or send them to the DLQ at once | a message neither completed nor dead-lettered, a dead letter that was never failed, a dead letter without its payload |
| W8 `retention` | W2 with completed messages deleted 2 s after their push | a message deleted before its ack |
| W9 `streams` | stream cycles: pop a batch, read the partition's state, one cycle that acks it, writes output and updates the state | a batch counted twice or never, state that disagrees with the output |
| W10 `timers` | schedule, reschedule and cancel timers, and consume what fires | a timer that fires twice or early, a cancelled timer that fires, fires and cancels that do not add up to the timers created |
| W11 `locks`, W11b `semaphore` | take a lock, or one permit of a semaphore, for 2 to 4 seconds; commit transactions that carry its guard and push to the partition it protects; renew it, release it and read its holders. No client watches a clock, so each goes on using a token whose lease ran out | a guarded transaction that commits after its permit moved on, a token with two owners, a record of a transaction that rolled back, a grant whose token is not above the one before it, a permit handed to another owner before its lease could have ended |
| W12 `failover` | two clusters of three nodes, one [following the other](/manage/standby/): push to the source, one record or a transaction over several partitions, and keep sending writes to the standby, which must refuse them; then the source stops (a crash, a crash while the standby is 10 s behind, or a planned switch that waits for the standby), the standby is promoted, and the clients write to it | a write a standby took before its promotion; a promoted log that is not the source's, record for record, up to where it ends; a transaction there in part; a planned switch that lost a write; after a crash, an acknowledged write missing while a later one is there; a write of the promoted cluster lost; a write refused as a standby's and found in the log |

## The faults

- kill -9 of nodes, restarted after a while; with `lazyfs`, a kill also loses every write the node
  had not fsynced, as a power cut does, and a slow-disk variant makes two nodes fsync 300 ms late
- SIGSTOP pauses
- network partitions: one node, a minority, a majority, a ring of overlapping majorities, and a
  bridge where one node sees both halves
- a deaf leader, whose followers receive its appends while their answers never reach it
- clock jumps and strobes on any node, the leader included
- graceful restarts (SIGTERM) of one node, or of every node in turn
- membership changes through the admin API: a voter removed, wiped and added back, or two at once,
  also while snapshots are being installed
- a file bit-flipped or truncated on one node, which must refuse or repair the damage and never
  serve it

The unknown of 2026-10-02 is W9 under bridge partitions. After the last heal, a follower's pops
kept timing out for about 90 seconds although it had caught up, so the final reads did not finish
within the test's time limit and the checker had no end state to judge. It was a liveness
problem, and its cause was not found. The same test was valid in the 2.1.0 campaign, on
2026-10-09, whose build has the fix for a leader that stops planning while it leads
(`5d48aef94`): such a leader's requests time out the same way, and whether it was the cause that
day is not known. P8 to P10 are archived with every history in
`benchmark-queen/2026-09-27-jepsen-archive/`.

The 2.1.0 campaign started on the build as it was merged (`e2f7236bd`) and was stopped after 48
tests, 47 of them valid. The other had found a five-node cluster whose leader led on for two
minutes and answered nothing (the row for `5d48aef94` below), and the fix was ready. The campaign
then ran from its first test on the build with the four fixes, on two sets of five nodes that
shared the list. In 51 of its tests a leader was handed an entry when no quorum had acknowledged
it for 2 s or more, 116 times in all: each is a write that raft refused before the fix, and each
waited until a quorum answered or that leadership ended. The one test judged invalid, a semaphore
test under a deaf leader, ran on nodes whose clocks were 0.55 s apart, and is among our own
faults below. The verdicts of both runs are in `benchmark-queen/2026-10-08-jepsen-full/`.

The failover campaign started on the build as it was merged and found three bugs in its first
two hours, listed below; a fourth came from the standby's own tests the same evening. On the build
with the four fixes, the sources acknowledged 446,016 writes over 37 tests. No standby took a
write before its promotion, no promoted log differed from its source's, and the ten planned
switches lost nothing. A crash of the source lost what the standby had not read: nothing in 19
of 23 runs, the writes of the last 3 to 20 seconds in the other four, where the standby's own
leader was cut off or dead at that moment, and about 10 seconds of writes in the four runs that
cut the two clusters apart for 10 seconds first. Every standby was promoted, in 9 ms at the
median, and took its first write 10 ms later. The one test that did not end valid was a planned
switch during which the harness killed two nodes of each cluster and then waited two minutes
for a standby it had left without a quorum; the ten planned tests ran again on a harness that
heals before it waits, all valid. The verdicts and counts are in
`benchmark-queen/2026-10-08-jepsen-failover/`.

The locks campaign counted what the fence did. In its 29 lock and semaphore tests 373,312 guarded
transactions committed, permits changed hands 18,456 times, and the guard refused 3,245
transactions that carried a token its permit no longer had. No token went back, and no record came
from a transaction that rolled back. One thing the checker reports and does not judge: under clock
strobes, one semaphore test read the same owner in two slots 51 times, 12 pairs of permits in all.
In the one traced, the owner's permit looked expired while a clock was ahead, its next acquire was
given another slot, and the first permit was live again a moment later. No semaphore gave out more
permits than its limit. Every test's verdict and counts are in
`benchmark-queen/2026-10-08-jepsen-locks/`.

The 2.2.0 campaign tests what that release changes: a push's row leaves the store when its
queue's dedup window has passed, and a consumer behind that reads from the queue log. Its first
pass ran the consumption workloads with rows that live two seconds, on log files of 256 KiB
that are sealed after ten seconds, where the defaults are 64 MiB and ten minutes, so that every
test seals, reclaims and removes log files while its faults run. Four of its 41 tests were not
valid, each with nodes that had refused to start: the two rows below. Both bugs are in 2.1.0 too,
where a five-minute test does not reach them.

The campaign then ran for sixteen hours on two sets of nodes, and on five builds, because fixes
landed while it ran: each test that had run on an older build ran again on the newer one, 352
runs in all, and all 244 tests ran on the last build, `3b1a6d9bb`. One run on the first build was
judged valid while two of its five nodes had refused to start: three nodes carried the history.
It was the second bug again, in a place the first fix had missed, and it is among our own faults
below, because the harness should have said so. Every node's log of both sets was read at the
end, the tests that damage a node's files on purpose left out, and no other run has a refusal or
a panic. Eleven of the tests then ran on the final code, `8f5342d29`, and all were valid. The
verdicts, the builds and the node logs' scan are in `benchmark-queen/2026-10-09-jepsen-220/`.

The 2.3.0 campaign ran the same 244 tests on what that release changes: the consumption engine
(its scan of idle partitions in turns, and a checkpoint taken as soon as an answer waits for one),
when a command's recorded outcome is retired, retention spread over its interval, the planner's
tables of partition names, a durable point every 250 ms written out in steps, and the dedup filter
of busy partitions. It ran on one set of six nodes, `n1` to `n5` for 213 tests and all six for the
31 failovers, from 2026-10-13 11:58 to 2026-10-14 11:50 UTC. Three tests of the log workload first
came back unknown: the checker of their histories ran out of memory on a control of 4 GB, and the
other checkers had found nothing. Their stored histories were checked again with 8 GB, and all
three are valid, with no anomaly, no duplicate and no torn read. One failover test crashed in the
harness before any load ran, for the reason the 2.2.0 campaign met on its sixth node, and it ran
again valid. The binary wire forms that 2.3.0 adds were not part of it, as its clients speak JSON.
The verdicts are in `benchmark-queen/2026-10-13-jepsen-230/`.

The 2.4.0 campaign ran the same 244 tests on what that release changes, the bytes a message costs
on disk: a push's outcome written as runs, the checkpoint's index rows without their hashes and the
boot that puts them back, and entry records without the hashes their message records hold, all
from cluster version 7. Every test of those 244 pushes one message at a time, and a one-message push
keeps the older outcome, so 13 more tests push up to eight messages of one partition at once
(`--batch-sends`): the log workload under kills, partitions, pauses, power loss, a deaf leader,
graceful restarts, forced snapshots, clock jumps and rows that live two seconds, and the dedup
workload under kills, partitions, restarts and power loss. It ran on one set of six nodes from
2026-10-15 13:20 to 2026-10-16 13:33 UTC, after a rolling upgrade from 2.3.0 on three of them, and
every test was valid at its first run; lazyfs was built on every node before the first power
loss. The encryption fix that 2.4.0 also carries was not part of it, as no test runs with an
encryption key. The verdicts and the upgrade are in `benchmark-queen/2026-10-15-jepsen-24/`.

The 2.5.0 campaign ran the same 257 tests on what that release changes: openraft
0.10.0-alpha.37 in place of a git revision, a hook in the batcher, the path every push takes, for
the Kafka facade's ordered pushes, and the end of a windowBuffer hold. It ran on one set of six
nodes from 2026-10-17 15:05 to 2026-10-18 15:27 UTC, then a rolling upgrade from 2.4.0 to 2.5.0
and back on three of them, at cluster version 7 throughout. 256 tests were valid at their first
run. The 257th, `p11-w1-corrupt-all`, damages one node's files on purpose and checks that the node
refuses them. In both of its runs every checker passed but the panic checker, which failed on
`NA-QLOG-I1` lines that were that node's refusals to boot, each within a second of the nemesis
cutting one of its queue logs short. Those refusals are the right answer, so the checker now leaves
out exactly the lines the nemesis recorded as its victim's reason to refuse. Both stored runs are
valid under it, and taking the nemesis's records out of their histories makes them fail again.
The Kafka facade, which 2.5.0 changes the most, is outside these tests, as their clients use the
native API. The verdicts and the upgrade are in `benchmark-queen/2026-10-17-jepsen-25/`.

The 2.6.0 campaign ran the same 257 tests on what that release changes: a member that comes back
recovers from the leader's log or from a delta snapshot, a boot reads hash sidecars instead of its
queue logs, and the raft port is listened on late. It ran on seven GCP VMs from 2026-10-21 07:48
to 2026-10-22 10:00 UTC, then a rolling upgrade from 2.5.0 to 2.6.0 and back on three of them, at
cluster version 7 throughout. Tests 1 to 91 of the main list ran 2.6.0-beta.1 (`d3809f2e5`), and
the rest of the campaign 2.6.0-beta.6 (`229a4c3ea`), the server code of 2.6.0. 255 tests were valid
at their first run. `p11-w5-slow-lz-kill`, the pipeline under kills with two nodes fsyncing late
through lazyfs, failed its checker once, on beta.1: its throughput collapsed under the kills (3,798
inputs, where the reruns took 15,500 to 21,000), and the final drain, which the harness caps at 120
seconds, ended with 1,323 acknowledged inputs still waiting, which its checker counts as lost. 1,633
transactions committed after the final reads, and nothing was written twice or without its input.
It was valid in four reruns on beta.6, one of them with a ten-minute drain. `p11-w3-lead-deaf`, the
KV register under a leader that stops answering, came back undecided: knossos' linear search ran out
of memory on two of its 117 keys, and stalled again with a 56 GB heap. Its WGL search, which decides
the same question, found the stored history linearizable on every key in two seconds. The Kafka
facade, which 2.6.0 rewrote, is outside these tests, as their clients use the native API. The
verdicts, the upgrade and both checks are in `benchmark-queen/2026-10-21-jepsen-26/`.

Two of P8's failures were our own. The claim workload lost ids when a call timed out, and Elle
reported version cycles that did not exist, because a set union in its `bifurcan` dependency
modified its inputs. The W4 checker runs with that union replaced (`edc699b6`), until Elle ships on
a fixed `bifurcan`.

The night of 2026-10-08 had two of our own as well. A planned switch ended unknown because the
failover's steps let the kill nemesis in between them: it killed two nodes of each cluster, and
the harness then waited for a standby it had left without a quorum (`7bf42d5ac`). And a
semaphore test was judged invalid because the nodes' clocks had drifted 0.55 s apart. The
harness turns the nodes' time daemon off for the clock faults, only a clock test set the clocks
again, and the last one on those nodes was three hours old; a lease survives a leader change
only while the clocks agree within 500 ms. Every test now starts with its nodes' clocks set
(`c4525140e`).

The 2.2.0 campaign had two more. A run was judged valid while two of its nodes had refused to
start: the checkers judge the history, and nothing looked at the nodes. `run-campaign.sh` reads
every node's log after each test since, and such a run is `REFUSED`. And a failover test crashed
in the harness, the first one that needed lazyfs on six nodes: the sixth had never built it, and
the build took longer than a node's setup may. It ran again valid.

The 2.3.0 campaign had two as well. Its control had 4 GB, where the earlier controls had 31: the
log workload's checker ran out of memory on three histories, which were checked again once the
control had 16 GB. And its sixth node met the lazyfs build of the 2.2.0 campaign again, since the
harness still builds lazyfs during a test's setup the first time a node needs it.

## Limits

This is testing. A valid run shows that these histories, under these faults, broke no rule a
checker knows, and every campaign ran one raft group with one tenant over the native HTTP API:
several raft groups, several tenants, the Kafka facade, the embedded proxy and the binary wire
forms of 2.3.0 (binary push, compressed groups, framed pops, the binary transaction body) were not
part of any.
Lease exclusivity across a leader change needs the nodes' clocks within
`QUEEN_RAFT_MAX_CLOCK_SKEW_MS` (500 ms) of each other. Losing a majority of the disks for good can
lose acknowledged writes, since raft survives the loss of a minority. The full campaign last ran
on the binary of `229a4c3ea`, 2.6.0-beta.6 (its first 91 tests on 2.6.0-beta.1); the server code of
2.6.0 adds its version line and nothing else. No test sets a completed retention above its queue's dedup window, so
none of them checks the rule of 2.2.0 by which a queue's completed retention no longer extends how
long a push keeps its row. A standby's failover
has its own workload since 2026-10-08, on a standby that starts empty beside its source: a seeded
standby, one that follows across a version upgrade, and two clusters in different places were not
part of it.
