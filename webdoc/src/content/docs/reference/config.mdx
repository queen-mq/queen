The broker has no configuration file and no command-line flags. Every knob is an
environment variable, read once during boot, before the HTTP listener binds.
There is no reload: changing a variable means restarting the process.

## Which variables actually matter

Most knobs are tuning that should be left alone. In practice a node sets
variables from these groups only.

| Purpose | Variables |
| --- | --- |
| Keep the node's state | `QUEEN_RAFT_DIR` (default `/var/lib/queen/raft`). Mount a persistent volume there. See [the data directory](#the-data-directory) |
| Run a cluster | `QUEEN_RAFT_REPLICATOR=openraft`, `QUEEN_RAFT_NODE_ID`, `QUEEN_RAFT_PEERS`, `QUEEN_RAFT_TOKEN`. See [the cluster set](#the-cluster-set) |
| Stop writes before the disk fills | `QUEEN_RAFT_DISK_HIGH_PCT`, `QUEEN_RAFT_DISK_LOW_PCT`. See [the disk gate](#the-disk-gate) |
| Fsync fewer files when a node holds many queues | `QUEEN_QLOG_SHARDS`, fixed when the data directory is created. See [queue-log layout](#queue-log-layout) |
| Serve on a different port or interface | `PORT` (default `6632`), `QUEEN_BIND_ADDR` |
| Turn on authentication | `JWT_ENABLED`, `JWT_ALGORITHM`, then `JWT_SECRET` or `JWT_PUBLIC_KEY` or `JWT_JWKS_URL` |
| Run the multi-tenant proxy in the same process | `QUEEN_PROXY_EMBEDDED`, `QUEEN_PROXY_PORT`, and the proxy's own `QUEEN_PROXY_*` settings. See [the proxy](/deploy/proxy/) |
| Serve the Kafka wire protocol | `QUEEN_KAFKA_EMBEDDED`, `QUEEN_KAFKA_ADVERTISED_ADDR`. See [Kafka](/reference/kafka/) |
| Change the maintenance cadence | `RETENTION_INTERVAL` |
| Accept larger request bodies | `QUEEN_MAX_BODY_BYTES` |
| Encrypt payloads at rest | `QUEEN_ENCRYPTION_KEY`, the same value on every node |
| Shape the logs | `LOG_LEVEL`, `QUEEN_LOG_JSON` |
| Scope queues by tenant behind a proxy | `QUEEN_TENANCY_HEADER`, with `QUEEN_KV_TRUSTED_PROXY`. See [Self-hosting](/deploy/) |
| Shape the KV and timer surfaces | Nothing turns them on: every broker serves them. Their knobs are ceilings and cadences that should be left alone, and pausing a live surface is a runtime call (`POST /api/v1/system/kv-timers`) rather than a variable; in a cluster it takes effect at once only on the node that served it. The one variable that stops timers from firing is `QUEEN_RAFT_TIMER_TICK_MS=0`, on every node. See [kv](/reference/http/kv), [timers](/reference/http/timers) and [KV and timers](/deploy/state) |

`LOG_LEVEL` accepts the full `EnvFilter` syntax, not just a bare level:
`info,rsm=debug` works. `RUST_LOG` takes precedence over it, and an
unparseable filter falls back to `info`.

## The data directory

`QUEEN_RAFT_DIR` (default `/var/lib/queen/raft`) is the only place a node keeps
state. It holds the queue logs (`qlog/`), the ordered store (`store/`), the raft
state when the node is part of a cluster (`raft/`), and `dash.db`, the node's
dashboard history. There is no external database and no disk spool. Mount a
persistent volume there: a node that loses the directory loses its copy of the
data.

The boot refuses an empty `QUEEN_RAFT_DIR` and creates the directory when it is
missing. A data directory belongs to the replicator that created it: a directory
written by the `openraft` replicator is refused by the `local` one, and the other
way round.

`QUEEN_RAFT_READY_LAG_MS` (default `2000`) is the apply lag under which
`GET /health` answers `200`; above it, or with no leader known, `/health` answers
`503` with `"status":"settling"`.

## The cluster set

A single node needs none of these: the default `local` replicator has no network
and no consensus. A cluster runs 3 or 5 voters, because raft needs a majority: 3
tolerate one failure, 5 tolerate two. These variables are read by the replicator,
not by `config.rs`; the generated table below lists them as well, from the files
that read them.

| Variable | Default | Meaning |
| --- | --- | --- |
| `QUEEN_RAFT_REPLICATOR` | `local` | `local`, or `openraft` (also spelled `raft`) for a cluster. Any other value fails the boot. |
| `QUEEN_RAFT_NODE_ID` | `1` | This node's id: a number from 1, or `ordinal`, which takes the trailing number of `HOSTNAME` plus one, so StatefulSet pod `queen-0` is node 1. |
| `QUEEN_RAFT_PEERS` | unset | Every voter of the initial membership, this node included: `id=raft_host:raft_port/http_host:http_port,...`. Raft RPCs go to the first address; a follower forwards client requests to the leader's second one. Setting it with the `local` replicator fails the boot. |
| `QUEEN_RAFT_TOKEN` | unset | The shared secret every raft RPC carries (header `x-queen-raft-token`). Without it, any host that reaches the raft port can send votes and appends. Set the same value on every node, for example from `openssl rand -hex 32`. |
| `QUEEN_RAFT_LISTEN` | `0.0.0.0:<this node's raft port>` | The address the raft RPC listener binds. |
| `QUEEN_RAFT_JOIN` | off | For a node joining a cluster that already exists: it does not initialize a cluster of its own, and it answers `503` until the leader adds it as a learner. |
| `QUEEN_RAFT_GROUPS` | `1` | Raft groups per process, at most 64, the same value on every node. A tenant lives in exactly one group, and group `g` uses the node's raft port plus `g`. |

For example, node 2 of three:

```bash
QUEEN_RAFT_REPLICATOR=openraft
QUEEN_RAFT_NODE_ID=2
QUEEN_RAFT_PEERS=1=<host1>:7400/<host1>:6632,2=<host2>:7400/<host2>:6632,3=<host3>:7400/<host3>:6632
QUEEN_RAFT_TOKEN=<same secret on all three>
```

Port 7400 is the raft port the Helm chart uses, not a code default: the raft
port is whatever `QUEEN_RAFT_PEERS` says. The peer list is written into the raft
membership at first boot. After that, the environment only supplies this node's
own listen address and the token, and membership changes go through
`/api/v1/system/raft/membership`. The walkthrough is in
[High availability](/deploy/ha/).

## The disk gate

Writes that grow storage (pushes, transactions carrying pushes, KV puts, timer
schedules, traces) are refused with `507` `storage_full` once the filesystem
holding the data directory is `QUEEN_RAFT_DISK_HIGH_PCT` percent used (default
`85`). They are accepted again once it is back under `QUEEN_RAFT_DISK_LOW_PCT`
(default `80`). A value that does not parse, or lies outside 1 to 100, keeps the
default. Pops, acks and deletes are not gated, so consumers can drain. The same
gate closes at 85 percent of the store's memory map and reopens under 80 percent;
those two numbers are fixed. `queen_raft_storage_full` on
[`/metrics/prometheus`](/reference/prometheus) is `1` while the gate is closed.

## Queue-log layout

`QUEEN_QLOG_SHARDS` (default `0`) sets how many shared queue logs a **new** data
directory gets. `0` means one log per queue. A value `K` from 1 to 4096 routes
every queue's records to shared log `queue_id % K`, so one commit fsyncs at most
`K` logs however many queues it touches; larger values are capped at 4096. The
count is written into the data directory when it is created, and an existing
directory keeps its layout: a different value later only logs a warning.

## The proxy and the Kafka facade

`QUEEN_PROXY_EMBEDDED=true` runs the multi-tenant proxy inside the broker
process. Without `QUEEN_PROXY_PORT`, the proxy serves `PORT` and the broker
router has no socket of its own, so every client needs an API key or a session.
With `QUEEN_PROXY_PORT` set to another port, the proxy serves that port and
`PORT` serves the broker router directly, with its own JWT and tenancy settings:
an internal port for clients inside the network, scrapers and probes, never
internet-facing. The proxy's own settings (`QUEEN_PROXY_*`) are described in
[the proxy](/deploy/proxy/).

`QUEEN_KAFKA_EMBEDDED=true` runs the Kafka wire facade inside the broker
process. `QUEEN_KAFKA_ADVERTISED_ADDR`, the `host:port` Kafka clients are told to
connect to, has no default: without it the boot fails naming the variable. The
listener binds `QUEEN_KAFKA_ADDR` (default `0.0.0.0:9092`). The rest is in
[Kafka](/reference/kafka/).

## Names kept from 1.x

These variables kept their names because the raft node reads them with the same
meaning. They are in the generated table below as well:

| Variable | Default | On a raft node |
| --- | --- | --- |
| `RETENTION_INTERVAL` | `5000` ms | How often the leader plans a maintenance pass (retention, partition cleanup). |
| `RETENTION_BATCH_SIZE` | `1000` | The most rows one maintenance entry considers. |
| `PARTITION_CLEANUP_DAYS` | `30` | An empty partition with no write, lease or new consumer group for this many days, and no dead letters, is deleted. |
| `QUEEN_PARTITION_CLEANUP_ENABLED` | on | `0`, `false`, `off` or `no` keeps idle empty partitions forever. |
| `METRICS_FLUSH_MS` | `60000` | How often the dashboard collector writes the node's counters to `dash.db`. A value under 1000 keeps the default. |
| `QUEEN_SWEEPER_BACKOFF_MIN_MS` | `1000` | Backoff after a timer fire fails permanently: `min(min * 2^attempts, max)`. |
| `QUEEN_SWEEPER_BACKOFF_MAX_MS` | `60000` | The ceiling of that backoff. |
| `QUEEN_SWEEPER_TRANSIENT_BACKOFF_MS` | `1000` | Backoff after a transient fire failure, which spends no attempt. |
| `QUEEN_SWEEPER_MAX_ATTEMPTS` | `5` | Permanent failures after which a timer is dead-lettered into its destination queue's DLQ. |

`QUEEN_STMT_TIMEOUT_MS`, `DEFAULT_TIMEOUT` (with its alias
`POP_DEFAULT_TIMEOUT_MS`) and `DEFAULT_SUBSCRIPTION_MODE` are read by
`config.rs` and appear in the table. On a raft node `QUEEN_STMT_TIMEOUT_MS` is the
deadline of an ack, a transaction and a lease extension, capped at 60 seconds.

### Variables that no longer exist

The 1.x PostgreSQL connection, pool and TLS settings (`PG_*`, `DB_POOL_SIZE`,
`PG_USE_SSL`, `PG_SSL_REJECT_UNAUTHORIZED`, `PG_SSL_ROOT_CERT`), the disk spool
(`FILE_BUFFER_*`), the mesh (`QUEEN_MESH_*`, `QUEEN_UDP_*`, `QUEEN_SYNC_*`), the
hot-list, fusion, ack-fusion, pop-fusion, admission and pop-autopilot knobs
(`QUEEN_HOTLIST_*`, `QUEEN_V2_FUSION_*`, `QUEEN_ACK_FUSION_*`,
`QUEEN_POP_FUSION_*`, `QUEEN_ADMISSION_*`, `QUEEN_POP_AUTOPILOT*`),
`QUEEN_APPLY_SCHEMA`, `RETENTION_PARALLELISM`, the stats refresh intervals,
`QUEEN_STORAGE`, `QUEEN_SQS_*`, `QUEEN_S3_*` and `PXDB_*` no longer exist and are
ignored. A 2.0 node has no database to reach and one storage class, so there is
nothing for them to configure.

## How booleans parse

Every boolean read by `config.rs` goes through one parser, so `=on`, `=1` and
`=true` mean the same thing there. The accepted spellings are `true/false`,
`1/0`, `yes/no`, `on/off`, case-insensitive, surrounding whitespace trimmed.

Three outcomes, and only three:

- **Recognised value**: used.
- **Unset, or present but empty or whitespace-only**: the documented default.
  `JWT_ENABLED=` in a Compose file means "leave it alone", not `false`.
- **Anything else**: a **fatal boot error**. The process logs
  `FATAL: JWT_ENABLED="maybe" is not a boolean (expected true/false, 1/0, yes/no, on/off)`
  and exits 1.

That last rule exists because the alternative failed in both directions: a
strict parser with a silent fallback turned `JWT_ENABLED=1` into a broker
running with authentication off and nothing in the log. `QUEEN_LOG_JSON`, which
is read before logging starts, is validated at the same moment.

A few switches are read where they are used, with their own rule and no boot
error. `QUEEN_PROXY_EMBEDDED` and `QUEEN_RAFT_JOIN` are on for `1`, `true`,
`yes` or `on` (any case) and off for anything else. `QUEEN_RAFT_METRICS` and
`QUEEN_PARTITION_CLEANUP_ENABLED` are on unless set to `0`, `false`, `off` or
`no`.

<Aside type="caution">
Numbers are **not** strict. An unparseable integer silently resolves to the
default: `QUEEN_RAFT_READY_LAG_MS=2OOO` (letter O) yields 2000, not an error.
The protection against that is the boot block below, not the parser.
</Aside>

## The effective configuration is printed at boot

After the JWT configuration is validated, the broker logs one `boot` line per
subsystem, headed `config: server`, `config: storage`, `config: auth` and so on,
carrying the values it actually resolved. The data directory and the disk gate
are in `config: storage`, and the `listening` line repeats the version, the
address and the data directory. A misspelled variable or a defaulted knob is
visible there instead of having to be inferred from behaviour. Read those lines
first when a setting appears not to have taken effect.

Secrets are masked, never printed: `JWT_SECRET`, `JWT_PUBLIC_KEY` and
`QUEEN_ENCRYPTION_KEY` render as `<unset>` or `<set:32 chars>`. That is enough to
tell "I forgot to mount the secret" from "I mounted the wrong one" without
putting key material into a log shipper.

## What kills the boot

The broker prefers to die at startup over serving in a state you did not ask
for. All of these exit 1:

- an unparseable boolean read by `config.rs`, as above;
- `JWT_ENABLED=true` with no usable key material for the configured algorithm,
  or an algorithm outside `HS256`, `HS384`, `HS512`, `RS256`, `RS384`, `RS512`,
  `EdDSA`, `auto`;
- `QUEEN_TENANCY_HEADER=1` with no `QUEEN_KV_TRUSTED_PROXY=1`;
- an empty `QUEEN_RAFT_DIR`, or a data directory the state machine cannot open,
  including one written by the other replicator;
- a cluster set that does not hold together: an unknown `QUEEN_RAFT_REPLICATOR`,
  a `QUEEN_RAFT_PEERS` that does not parse or does not list
  `QUEEN_RAFT_NODE_ID`, or `QUEEN_RAFT_PEERS` with the `local` replicator;
- `QUEEN_KAFKA_EMBEDDED=true` without a usable `QUEEN_KAFKA_ADVERTISED_ADDR`;
- failure to bind `$PORT` on `$QUEEN_BIND_ADDR`, including a `QUEEN_BIND_ADDR`
  that carries a port of its own instead of a bare host or IP, or failure to bind
  `QUEEN_PROXY_PORT`.

The tenancy interlock is a safety rule rather than a validation. The tenant
header is opaque and validated against nothing, so the trust boundary is the
network in front of the broker. That is tolerable for queues, where an ack still
has an ownership gate on an id the caller cannot guess, and it is not tolerable
for key/value state, which is addressed purely by name: the only gate is the
tenant, and the tenant comes from the header. Setting `QUEEN_KV_TRUSTED_PROXY=1`
is the operator asserting that a proxy supplies that header and strips the
client's. There is no flag that switches the KV off to make an unvalidated tenant
header safe; an operator who has to take the KV down on a running node wants the
runtime kill switch instead. See [KV and timers](/deploy/state).

One important omission from that list: a malformed `QUEEN_ENCRYPTION_KEY` (not
64 hex characters, or not hex) logs a single warning and **disables
encryption**. Queues flagged `encryptionEnabled` then store plaintext and the
pushes succeed. Grep the boot `config: security` line for
`encryption_key=<set:64 chars>` before trusting at-rest encryption. Set the
same key on every node and check the line on each: any node can serve a push or
a pop.

## The variables

Defaults below are the ones the code applies, extracted at build time from
`config.rs` and, for the variables read at their own call site (the cluster set,
`QUEEN_QLOG_SHARDS`, the names kept from 1.x, the proxy and Kafka switches), from
the file that reads each one. The proxy's own `QUEEN_PROXY_*` settings and the
facade's `QUEEN_KAFKA_*` settings are on [the proxy](/deploy/proxy/) and
[Kafka](/deploy/kafka/) pages. Where a variable has an alias, both names read
the same setting and the newer name wins.

A few rows carry a **derivation** rather than a literal, because that is what
the code applies: `QUEEN_KV_REQUIRE_GRANT` and `QUEEN_EPHEMERAL_REQUIRE_GRANT`
take the value of `QUEEN_TENANCY_HEADER`, and `DEFAULT_TIMEOUT` falls back to
`POP_DEFAULT_TIMEOUT_MS`, then to 30000.

### Node identity

`QUEEN_SERVER_ID` names this node on the dashboard's cell pages and in
`/auth/me`. Unset, the broker uses `HOSTNAME`; with neither, it generates
`queen-<8 hex>`. The value is cosmetic: nothing routes on it. The raft node id is
`QUEEN_RAFT_NODE_ID`, above.
