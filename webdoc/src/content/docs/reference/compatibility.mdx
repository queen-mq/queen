Queen 2.0 is one binary: the broker, and optionally the multi-tenant proxy and the
Kafka facade, in one process. The JavaScript, Python, Go and Rust clients,
`queen-protocol` and the Go command-line client are at 1.3.0 and talk to a 2.0
broker over the same HTTP API; the PHP/Laravel source has no tagged Packagist
release yet, and the C++ header is consumed at a repository revision. The broker
reports its version on `GET /health` and in its boot log; the value is compiled in
from a single file, so the binary, the container tag and the health document can
never disagree.

## The HTTP API is the compatibility surface

The contract is the HTTP API: the paths under `/api/v1` and `/streams/v1`, their
methods, their JSON field names, and the status-code behaviour described in
[Status codes and error bodies](/reference/errors). An SDK is a convenience over
that surface, not a separate contract: anything an SDK can do, a plain HTTP call
can do.

Everything else is an implementation detail and changes without notice:

- the data directory's on-disk format (the queue logs, the store, the raft state);
- the raft RPC protocol between the nodes of a cluster, on the raft port;
- the embedded dashboard bundle;
- the boot log's field names.

Fields are added, not renamed: a client must ignore fields it does not know.

Every 1.x route is still served by 2.0 except one:
`GET /api/v1/analytics/postgres-stats`, which described a database 2.0 does not
have. `POST /api/v1/stats/refresh` still answers `200`, as
`{"success":true,"refreshed":false,"engine":"raft"}`: counters are maintained as
entries apply, so there is nothing to refresh. Two things a 2.0 broker answers
differently are covered on [Status codes and error bodies](/reference/errors): a
node that cannot take a write answers `503` with `Retry-After` instead of
spooling it, and a push never reports `buffered`.

## The embedded Rust API is beta

Since 1.0.0 the broker crate also ships a library target: `queen-engine` on
crates.io, importing as `queen`, whose [engine API](/reference/engine) runs the
broker in-process. That Rust surface is a second contract and it is explicitly
**beta**: the types can change between releases while it hardens, and it does
not follow the HTTP surface's stability promise yet. In 2.0 it boots with
`BrokerConfig::new().raft(dir)`: the PostgreSQL connection, pool, schema and spool
settings of the 1.x builder are gone. What does carry over is the wire
vocabulary, because the engine's requests and responses are the `queen-protocol`
types, the same crate the Rust client compiles against. Build against the engine
expecting to read release notes; build against HTTP expecting not to.

## There is no schema and no migration step

A 2.0 node keeps everything in its data directory, `QUEEN_RAFT_DIR` (default
`/var/lib/queen/raft`). There is no external database, so there is no schema to
apply at boot, no migration step, no version table, no database privileges to
grant and no PostgreSQL version to meet.

A new node starts from an empty data directory. A restart reopens the directory
it finds and replays what was committed after its last checkpoint. Two choices
are fixed when a directory is created and cannot be changed on it afterwards:

- **the replicator.** A directory written by the `openraft` replicator is refused
  by the `local` one, and the other way round;
- **the queue-log layout.** `QUEEN_QLOG_SHARDS` is written into the directory at
  creation; a different value later only logs a warning.

Roll a cluster one node at a time. On `SIGTERM` a leader first hands its
leadership to a caught-up voter and only then drains, so a rolling restart costs
one transfer rather than an election timeout.

## Coming from 1.x

A 1.x deployment kept its data in PostgreSQL. 2.0 has no PostgreSQL client and
reads nothing from a 1.x database: messages, queue configurations,
consumer-group positions, key/value state and timers stay where they are. There
is no in-place upgrade and no migration tool. The same holds for the retired
0.16 broker.

The move is therefore a cutover at the application level:

1. Stand up the 2.0 broker (see [Self-hosting](/deploy/)) and configure its
   queues.
2. Point producers at the new host.
3. Let the 1.x consumers drain the 1.x broker.
4. Point the consumers at the new host. The HTTP API is the same, so a client
   moves by changing the host it talks to.

What 2.0 no longer has, so a 1.x configuration can be cleaned up: every
PostgreSQL, spool and mesh variable (see
[Environment variables](/reference/config)), the SQS facade and the S3 sink.
