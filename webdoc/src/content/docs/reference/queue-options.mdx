`POST /api/v1/configure` creates or updates a queue's configuration. An update
**merges**: an option the body does not mention keeps the value the queue
already has.

Four rules cover every option on this page:

| In the body | What the queue ends up with |
| --- | --- |
| the key is absent | the value the queue already had |
| the key is present with a value | that value |
| the key is present with `null` | refused with `400` (`"<key> must be an integer"`, or `boolean`) for a numeric or boolean option, and nothing is written; `""` for `namespace` and `task` |
| top-level `"mode": "replace"` | every option rebuilt from defaults, so anything the body omits goes back to its default |

<Aside type="caution">
Every call used to replace, which is why so much of this site used to tell you
to send the complete option set. That advice is now the opposite of the truth for
an edit, and it is still exactly right for a manifest: a declarative source means
the whole configuration, so `queenctl apply -f` sends `"mode": "replace"` and
anything the file leaves out goes back to the default. Pick the mode from what the
caller is: a nudge merges, a desired-state document replaces.
</Aside>

Two consequences worth holding on to. Restoring one option's default means
sending its default value, or a replacing call with the whole configuration: a
`null` does not do it. And a create is the same call in either mode, because a
queue that does not exist yet has nothing to keep.

A queue does not need to be configured at all: the first push creates it, with
every option at its default except `namespace` and `task`, which are derived
from the queue name. `/configure` is how you move off those defaults, and a
partial `/configure` keeps the derived labels.

## Sending it

The body carries the queue name and the options, which may be nested or
top-level:

```json
{"queue":"orders.shipped","options":{"leaseTime":120,"retryLimit":5}}
```

Only `queue` is required, and it must be a string. `namespace` and `task` are
read from the options object, and are also accepted at the top level. Anything
else at the top level is treated as an option when no `options` object is
present, apart from `mode`, which is routing rather than configuration: it is
`"merge"` (the default) or `"replace"`, and any other value is a `400` that
writes nothing. A numeric option that is not an integer, or a boolean option that
is not a boolean, is a `400` that writes nothing.

The response is HTTP 200 with `configured: true`, the queue id (`partitionId` is
always `null`: configuring creates no partition, the first push does), the queue
name, its namespace and task, and an `options` object echoing the **effective**
configuration: every option as it now stands, whether the request carried three
of them or all of them. So a merging edit reports back the whole configuration
without a second read, and a clamped value is reported as what the queue now
holds. To read a queue's configuration without writing to it, use
`GET /api/v1/resources/queues/:queue`.

## Where the values live

A queue's options are one record in the replicated store. `/configure` writes it
as one entry of the log, and the first push to a new queue creates it with the
defaults. The pop reads it for the lease time and the visibility rules, the ack
for the retry budget and dead-lettering, the push for the deduplication window
and encryption, and maintenance for the retention cutoffs. Each reads the
current record, so a change applies to the next operation that reads it.

The one asymmetry left is the lease default: a queue created implicitly by a
push gets **60**, while `/configure` writes an explicit **300** when `leaseTime`
is omitted on a create or on a replacing call. A merging edit keeps whatever the
queue holds, so a push-created queue that is nudged through `/configure` stays at
60. That is why the lease in effect depends on how the queue was created.

## Declared, not enforced

Five options `/configure` accepts are stored, echoed back, and enforced by
nothing:

| Option | Type | Default | What reads it |
| --- | --- | --- | --- |
| `priority` | integer | `0` | Echoes only. Nothing on the push, pop, ack or maintenance path reads a priority, so nothing is served ahead of anything else because of it. |
| `ttl` | integer (s) | `3600` | Echoes only. It expires nothing: age eviction is `maxWaitTimeSeconds`, and deletion is retention. |
| `maxSize` | integer | `0` | Nothing. There is no queue-depth cap and no push back pressure behind this number. |
| `retryDelay` | integer (ms) | `1000` | Echoes only. A failed ack redelivers on the next pop of the partition; nothing waits this long first. |
| `minPopWaitTime` | integer (ms) | `0` | Echoes only, clamped to 0–60000 when stored. A 2.0 pop does not hold an under-full batch back for it. |

They are kept because they are on the wire and every SDK's option type carries
them. Setting one changes a stored value and nothing else, which is worth
knowing before you reach for `maxSize` expecting back pressure, or for
`priority` expecting one queue to be drained ahead of another.

| Option | Type | Default | Enforced by |

| `dlqAfterMaxRetries` | boolean | `true` | Ack, combined with the previous flag by `OR` |
| `delayedProcessing` | integer (s) | `0` | Pop, always |
| `windowBuffer` | integer (s) | `0` | Pop, always |

| `completedRetentionSeconds` | integer (s) | `0` | Maintenance, rule 2 |

## namespace

**Type** string. **Default** `""`.

A grouping label. Its only functional role is the discovery pop
(`GET /api/v1/pop?namespace=…`), which matches it for **exact equality** across
every queue of the tenant, and the namespace listing endpoints. For a queue
created implicitly by a push, it is derived from the queue name: the part before
the first `.`.

Changing it moves nothing. Messages stay where they are; the queue simply starts
matching a different discovery pop from the next call onwards. A consumer group
that was discovering the old namespace stops seeing the queue, keeping its cursor
exactly where it was.

## task

**Type** string. **Default** `""`.

The second discovery dimension, matched the same way, and derived for a
push-created queue from the name between the first and second `.` (empty when the
name has no dot). Same change semantics as `namespace`.

## leaseTime: the visibility timeout

**Type** integer, seconds. **Default** `300` from `/configure`; **60** for a queue
created by a push.

How long a leased batch stays invisible to other consumers in the same group. A
pop resolves its lease as: the request's `leaseSeconds` when positive, else this
value, else 60 when the queue has no configuration yet.

Changing it affects **new** pops only. Leases already issued keep the expiry they
were given. The queue detail endpoint and the pop read the same stored value, so
what the display shows is what pops lease with.

Set it longer than your slowest realistic message handler. A lease that expires
while a consumer is still working means the batch is redelivered to someone else,
and because the retry budget is only charged by explicit `failed` acks, lease
expiry can redeliver indefinitely without ever dead-lettering.

## retryLimit: the retry budget before dead-lettering

**Type** integer. **Default** `3`.

The number of explicit `failed` acks a leased batch may accumulate before the
broker dead-letters or drops the failing message. The counter lives on the
consumer group's cursor of the partition and is reset when the failing message is
dead-lettered or dropped.

Only an explicit `failed` charges it. A `retry` status releases the lease without
charging, and a lease expiry does not charge either, so this is a budget for
*reported* failures, not for delivery attempts.

Changing it takes effect on the next `failed` ack, and existing counters are
**not** reset. Lowering the limit below a partition's current counter means the
next `failed` ack on that partition dead-letters immediately.

## deadLetterQueue

**Type** boolean. **Default** `true`.

Whether a message that exhausts the retry budget is written to the dead-letter
queue. `true` for an unconfigured queue, so dead-lettering is the default
behaviour.

Changing it affects only future budget exhaustions. Dead letters already filed
stay. Nothing purges them, including retention.

## dlqAfterMaxRetries

**Type** boolean. **Default** `true`.

A second flag with the same meaning, kept for compatibility. The ack path
combines the two with `OR`.

<Aside type="caution">
Because the two flags are OR-ed, setting `deadLetterQueue: false` alone does
nothing. Both must be `false` to disable dead-lettering, and when they are, a
message that exhausts its retry budget is **dropped**: the cursor advances past
it and nothing in the ack response marks it. That is silent data loss, chosen
deliberately over an unbounded redelivery loop.
</Aside>

## delayedProcessing: delayed (deferred) delivery

**Type** integer, seconds. **Default** `0` (off).

A visibility delay. A pop delivers only messages stored at least this long ago,
so a message becomes available `delayedProcessing` seconds after it was stored.
The pop applies the rule every time; nothing bypasses it.

Because a partition's timestamps are monotone, the delay cuts a contiguous recent
tail, and the pop stops at the batch budget before ever reaching it.

Changing it applies to existing messages at once: raising it hides messages that
were visible a moment ago, and lowering it exposes them.

## windowBuffer: quiet-period debounce (batching window)

**Type** integer, seconds. **Default** `0` (off).

A quiet-period debounce, evaluated per partition: while the partition has
received a write within the last `windowBuffer` seconds, a pop delivers
**nothing** from it. The intent is to batch a bursty writer into fewer, fatter
deliveries.

<Aside type="caution">
A partition written to more often than every `windowBuffer` seconds is not
delivered at all until the writes pause: each pop finds a write inside the quiet
window and returns empty. There is no early release once a batch has
accumulated. Keep the window shorter than the gaps your producer actually leaves.
</Aside>

Changing it does not touch stored data, and the next pop uses the new value.

## retentionEnabled

**Type** boolean. **Default** `false`.

The master switch for the two time-based retention rules. Retention is opt-in:
without this flag, and without a positive window, maintenance does no deletion
work for the queue at all, and a queue grows until you delete it.

Turning it on with a window already configured makes the next maintenance pass
start deleting eligible records, at most `RETENTION_INTERVAL` (5 s) away.
Turning it off stops future deletion; it does not bring anything back.

## retentionSeconds: age-based retention

**Type** integer, seconds. **Default** `0`. **Requires** `retentionEnabled` and a
positive value.

Deletes stored records older than `now - retentionSeconds`, **regardless of
whether anything consumed them**. This is the explicit "drop unconsumed data after
N seconds" knob, and it will delete a backlog a consumer never read.

Deletion is by whole stored record, oldest first: a partition's start moves
forward past every record older than the cutoff. Consumers whose cursor was inside
the deleted range resume at the next existing offset, so they silently skip the
deleted messages rather than erroring.

Lowering the value takes effect on the next pass and can delete a large backlog,
in bounded passes of at most `RETENTION_BATCH_SIZE` rows each.

## completedRetentionSeconds: retention behind the consumers

**Type** integer, seconds. **Default** `0`. **Requires** `retentionEnabled` and a
positive value.

Deletes records older than `now - completedRetentionSeconds`, but only up to what
has actually been consumed: the boundary is capped at the *slowest* consumer
group's cursor on the partition. Unconsumed backlog is never lost to this rule.

A partition with no consumer group has consumed nothing, so this rule contributes
nothing there: old-but-unconsumed records survive. That is the intended asymmetry
with `retentionSeconds`: use this one to reclaim space behind your consumers, and
that one to enforce a hard age limit.

One side effect is worth knowing: this value also sets how long transaction ids
stay resolvable, described under `dedupWindowSeconds`.

## maxWaitTimeSeconds: message TTL (age eviction)

**Type** integer, seconds. **Default** `0` (off).

**Deletes stored records older than the cutoff for every consumer group,
including in-flight leased batches.** That is data loss by design. It does not
dead-letter, does not notify, and does not wait for a consumer.

It is the one deletion rule that ignores `retentionEnabled`: a queue configured
with only `maxWaitTimeSeconds` still gets swept. Mechanically it is the same
boundary walk as `retentionSeconds` with a different cutoff source, and consumers
left behind the new start resume at the next existing offset.

Use it when stale data is worse than lost data: a live telemetry lane where a
message older than the window has no value. Do not use it as a retention policy
for anything you would want to audit.

## encryptionEnabled: encryption at rest

**Type** boolean. **Default** `false`.

Stores payloads pushed to this queue as an AES-256-GCM envelope instead of
plaintext. It requires `QUEEN_ENCRYPTION_KEY` to be a valid 64-hex-character key.

<Aside type="danger">
With no key, or a malformed one, the broker logs a warning and disables
encryption: pushes to a queue flagged `encryptionEnabled` then succeed and store
**plaintext**. Nothing in the response says so. Verify the key in the boot log of
every node before relying on this flag.
</Aside>

Changing it is not retroactive in either direction. Existing messages are not
re-encrypted when you turn it on, and not rewritten when you turn it off.
Whether a message is decrypted is decided per stored message, not by the queue's
current flag, so a queue can hold both forms and both read back correctly. A flip
applies to the pushes that follow it. Configure encryption before you start
producing, not while.

## dedupWindowSeconds: the deduplication window

**Type** integer, seconds. **Default** `3600`. Stored with the queue like every
other option, and echoed in the `/configure` response.

The window within which a repeated `transactionId` is recognised as a duplicate
for the same partition. Deduplication is **on by default**; only an explicit `0`
turns it off. The push checks the window *before* an offset is allocated, so a
duplicate writes nothing at all and the push reports `status: "duplicate"` with
the original message's id and offset.

This option also controls **how long an ack can be resolved.** Acks arrive
addressed by `transactionId`, and a transaction id stays resolvable for the
largest of `dedupWindowSeconds`, `completedRetentionSeconds` and 900 s
(`QUEEN_RAFT_TXN_WINDOW_MIN_S`). Shrinking the deduplication window can therefore
also shorten the period in which a late ack can still be matched. Past it, the
ack is reported with `success: false` rather than silently succeeding. If the
batch is still leased, the message redelivers.

Changing the value applies to the next push. Setting it to `0` is a real choice
with a real cost: a client retry after a lost response duplicates the message. Do
that only where the consumer is idempotent.
