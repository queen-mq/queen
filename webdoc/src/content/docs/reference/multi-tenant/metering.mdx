Usage is counted **after** the response, from what the broker actually did, not from
what the request asked for. That single decision is what makes the numbers defensible:
a duplicate that stored nothing is not billed, a transaction that rolled back is not
billed, and a batch of 1000 items where 400 were rejected is billed for 600.

## The unit

One accumulator per `(cluster, op class, minute)`, held in a 16-way sharded map keyed by
cluster id, carrying four counters:

| Field | Meaning |
| --- | --- |
| `reqs` | Requests, one per proxied call |
| `msgs` | Billable messages, per the rules below |
| `bytes_in` | Buffered request bytes. Non-zero only for the requests the proxy buffers: produce, `/configure`, the ephemeral push and the streams cycle |
| `bytes_out` | Buffered response bytes, or the upstream `Content-Length` when the response streams through |

Recording is deliberately silent: no log line on the per-request path. Rates and sizes
belong in aggregated blocks, not per-message lines.

Every node runs its own proxy and keeps its own accumulators, for the requests that node
served.

## Op classes

The op class is one of five values:

| Class | Which requests |
| --- | --- |
| `push` | `POST /api/v1/push`, the accepted sink messages of a streams cycle, and a dead-letter replay that moved a message (the last two as messages only, on a second sample; see below) |
| `txn` | `POST /api/v1/transaction` |
| `delivery` | Pop routes (`/api/v1/pop/queue/…`) |
| `configure` | The queue-admin class: `/configure`, deletes, seeks, subscription changes |
| `read` | Everything else that is metered: reads, gated surfaces, operator surfaces, and the consume routes that are not pops (ack, lease extension) |

Ack and lease-extension calls metering as `read` is worth knowing when you read the
figures: `delivery` counts deliveries, not acknowledgements.

## What counts as a billable message

<AccordionGroup>
<Accordion>
<AccordionTrigger>Push: from the per-item statuses</AccordionTrigger>
<AccordionContent>

A `201` response body is a top-level array of per-item results. Each item's `status`
decides:

- `queued` → billed.
- `duplicate` → **not** billed. Deduplication stored nothing.
- `error` → **not** billed.

The parser also knows `buffered` (billed like `queued`) and `failed` (not billed). The 2.0
broker returns neither: it answers each item `queued` with its offset, `duplicate` with the
original's, or `error`.

A response that will not parse bills `msgs = 0` with a warning. Under-billing something
unrecognised beats billing something that did not happen.

</AccordionContent>
</Accordion>

<Accordion>
<AccordionTrigger>Transaction: only when it committed</AccordionTrigger>
<AccordionContent>

The push operations are counted on the way **in**, when the body is parsed for the size
caps and the message bucket. What decides whether they are billed is the response body,
not the status line: the broker answers `200` on a rollback too, with
`{transactionId, success:false, reason, error, results:[]}`.

- `success: true` → bill the counted push operations, minus any that came back
  `duplicate: true` (first-wins deduplication inside the batch stored nothing new).
- `success: false` → bill zero. The transaction is one entry in the replicated log and
  applies whole or not at all, so nothing was stored whatever the request contained.
- A shape the proxy cannot read → bill zero, with a warning.

</AccordionContent>
</Accordion>

<Accordion>
<AccordionTrigger>Pop: delivered messages, and a bucket debit</AccordionTrigger>
<AccordionContent>

A `200` response is buffered and the `messages` array counted. That count is both
metered as `delivery` messages **and** debited from the cluster's message token bucket,
the post-completion debit described in
[Quotas and rate limits](/reference/multi-tenant/quotas/).

A `204` (nothing available, or the queue is paused) is `reqs = 1`, `msgs = 0`, and the
body is not buffered at all.

</AccordionContent>
</Accordion>

<Accordion>
<AccordionTrigger>Streams cycle: sink emits billed as push</AccordionTrigger>
<AccordionContent>

`POST /streams/v1/cycle` is always buffered, both ways. The request itself books one
`read` sample (`reqs = 1`, `msgs = 0`, bytes both directions), like every gated
surface. Its sink `push_items` are the part that bills: on a 2xx whose body says
`success: true`, every request sink group whose matching `(queue, partition)` entry
in `push_results` came back `queued` bills its item count as `push` messages, on a
second sample with `reqs = 0` so the request is never double-counted. That is what
puts stream output in the same `usage_days` rows as ordinary pushes and under the
monthly message quota.

Not billed: `duplicate` groups (deduplication stored nothing, same rule as push), a
cycle whose body says `success: false` (the cycle is one entry in the replicated log and
rolled back whole, sink writes included), and a response the proxy cannot parse
(`msgs = 0` with a warning).

Nothing else in a cycle is a billable message. The source pop was already metered as
`delivery` on its own request, and the ack advances a cursor, keeping the reqs-only
posture `/api/v1/ack` has. An idle-flush or state-only cycle therefore meters as one
`read` request and nothing more.

</AccordionContent>
</Accordion>

<Accordion>
<AccordionTrigger>Dead-letter replay: one message when it moved</AccordionTrigger>
<AccordionContent>

The two replay routes, `POST /api/v1/dlq/:id/replay` and the address-keyed
`POST /api/v1/messages/:partitionId/:transactionId/retry`, are `queue admin`, so the
request itself books one `configure` sample (`reqs = 1`, `msgs = 0`). A replay also
writes a frame into a live partition, and that message bills as `push` on a second
sample with `reqs = 0`, exactly like a cycle's sink emits: it is stored, retained and
rolled up like any pushed message, so it belongs in the same `usage_days` row and under
the same monthly quota.

The response decides. A 2xx whose body says `result: "moved"` wrote a frame and bills one
message. Not billed: `result: "duplicate"` (the destination's dedup window already held
the deterministic transaction id, so nothing was stored), a body saying `success: false`,
a verdict word the proxy does not recognise, and a response it cannot parse (`msgs = 0`
with a warning). A `404` on a row that was already replayed or purged never reaches this
path at all.

Request bytes are small but real on the row-id route: its body is buffered on the way
in, because a `{queue, partition}` override provisions a destination and has to pass the
same registry admission `/configure` does. The address-keyed route reads no body and
buffers none, so its `bytes_in` stays `0`. The message payload itself is the broker's own
dead-letter snapshot and never crosses the proxy in either direction, so the in-flight
storage estimate learns about a replay only at the next retained-bytes computation.

</AccordionContent>
</Accordion>

<Accordion>
<AccordionTrigger>Errors: recorded, never billed</AccordionTrigger>
<AccordionContent>

- **Upstream 5xx**: `reqs = 1`, `msgs = 0`, logged separately, body streamed straight
  through with no buffering. On the 2.0 broker that includes the `503` a node answers
  while it has no leader and the `507` it answers when its data disk is full.
- **Upstream timeout** (the proxy's own `504`): the request is recorded with `msgs = 0`
  and a log line saying it was not billed.
- **Refused at the proxy** (`401`, `403`, `413`, `429`, `421`) is not metered at all.
  Those responses return before the metering step, so `usage_minutes` reflects work the
  cell was actually asked to do.

</AccordionContent>
</Accordion>
</AccordionGroup>

Responses that need parsing are buffered with a 64 MiB ceiling, matching the broker's
own default body cap, so a legitimate pop batch of large messages still relays. A
response above it answers `502` rather than being silently truncated or mis-billed.

## From memory to the store

Usage lives in the proxy's state in the replicated key/value store, in two sets of
documents: `usage_minutes` and `usage_days`.

Every `QUEEN_PROXY_METER_FLUSH_MS` (default 15000) the flush task writes every
accumulator that holds usage not yet written, the open minute included, so the console
and the monthly quota see current traffic. Each node writes only its own rows, one per
`(cluster, minute, op class, node)`, and every reader sums the nodes. The node is named
by `QUEEN_SERVER_ID`, else `HOSTNAME`, else `node-<QUEEN_RAFT_NODE_ID>`. Two processes
that share a name overwrite each other's minutes, so keep it unique per node and stable
across restarts.

A write sets the node's cumulative total for that minute rather than adding to it. A
retry after a lost answer therefore writes the same value again, and no two nodes ever
update one row.

A flush that fails (no leader, a timeout) keeps its usage in memory, and the next tick
retries it. Only when more than 50,000 closed `(cluster, op class, minute)` keys are
waiting does a node move them to the disk spool, so a leader election does not cost a
trip to the disk.

At shutdown the drain writes everything still in memory, including the open minute, and
spools what the store did not take. It is bounded by `QUEEN_PROXY_SHUTDOWN_DRAIN_MS`
(default 5000), so a store without a leader cannot turn a deploy into a hang.

## The disk spool

Usage a node could not write for too long, and usage the shutdown drain could not write,
is appended as JSONL to `QUEEN_PROXY_SPOOL_DIR` (default `./queen-proxy-spool`). Every
spooled row is usage to add.

| Property | Behaviour |
| --- | --- |
| File name | `meter-<epoch_ms>-<seq>.buf`, so lexical order is FIFO order |
| Rotation | Size-based at 5 MB |
| Durability | `flush`, not `fsync` per line: best-effort, because a lost tail of usage on an unclean crash is acceptable where a lost message would not be |
| Recovery | Once, at process start, before the first flush. A file is added onto this node's rows a chunk at a time, and a `<file>.done` sidecar records how many rows are applied, so a file that fails halfway resumes after its applied prefix on the next start |
| Circuit breaker | After 3 consecutive recovery failures, sleep 30 s before the next file, so a startup recovery against a store that still does not answer does not hammer it |

Recovery is at-least-once: a chunk whose write landed but whose answer was lost is added
again on the next start. That is the deliberate trade: usage that can be over-counted
once is recoverable, usage that is dropped is gone. The days a replay wrote to are rolled
up again on the next roll-up pass, even when they are behind its usual window.

If `QUEEN_PROXY_SPOOL_DIR` cannot be created, the proxy warns at construction and keeps
running. Usage is then lost whenever it would have been spooled. The default is relative
to the working directory and is not writable on a read-only root filesystem, so put the
spool on the data volume, for example `/var/lib/queen/raft/proxy-spool`.

## Roll-up and retention

The roll-up task ticks every `QUEEN_PROXY_ROLLUP_MS` (default hourly, first tick
immediately) on every node.

It folds **closed** days out of `usage_minutes` into `usage_days`, aggregated by
`(cluster, day, op_class)` and summed over the nodes. The day is the UTC calendar day,
pinned to UTC rather than the server's timezone so a roll-up produces the same rows on any
node and month boundaries are stable. It recomputes each day rather than adding to it, and
writes only the rows that differ, so it is idempotent: extra runs, or a second node
running the same pass, cost an aggregate pass and change nothing. That is why hourly is
fine. Each pass recomputes from the day before the last rolled-up day through yesterday.

Minute rows are not pruned by a task: each one carries a TTL. A minute of UTC day `D`
expires at the start of day `D + QUEEN_PROXY_USAGE_KEEP_DAYS + 2` (default 90 days, at
least 1), so every minute of a day expires at the same instant and a day is never half
gone. The roll-up never recomputes a day within one day of that instant, and a day whose
minutes have expired keeps its figure.

Minutes are the evidence behind a billing dispute, which is why the retention window is
generous. `usage_days` is kept indefinitely either way.

## The warn and block chain

The same tick evaluates the monthly allowance. One pass reads, for every cluster with an
allowance (from its plan or a cluster override) that is not being deleted, its
calendar-month message count and the month itself, both from one clock reading, so month
and count cannot disagree across a boundary. The count is, for each UTC day of the month,
the larger of the rolled-up figure and the live minute rows, so it includes today's
traffic up to each node's last flush.

| Level | Condition | Outbox event | Effect |
| --- | --- | --- | --- |
| Warn | `msgs ≥ quota × 80%` (`QUEEN_PROXY_QUOTA_WARN_PERCENT`) | `cluster_monthly_quota_warning` | None. The point is that a human can raise the plan before the tenant is stopped |
| Over | `msgs ≥ quota` | `cluster_monthly_quota_blocked` | Pushes blocked until the next calendar month |

Each level is announced once per cluster per month, and only upward. A repeat announces
nothing, and a count that wobbles back down announces nothing. Two things enforce that:
in-process state for the common case, and a lookup against the outbox for an existing
`(kind, cluster_id, month)` event, which is needed because a restart mid-month, or another
node running the same pass, would otherwise re-announce every cluster already over the
line. That lookup is best-effort: if it fails the event is emitted anyway, because a
duplicate control-plane event beats a swallowed one.

Every node runs this pass and holds its own block flags. A block is released when the
count falls back under, when the quota is lifted, when a new month starts the count near
zero, or when the cluster stops being listed at all. A failed read releases nothing:
having no evidence is not evidence that a block should be lifted.

The outbox is part of the proxy's state. The proxy writes events to it, and no route of the
proxy reads them back: draining it (sending the email, opening the ticket, calling the
billing system) is a job for something else.

## Reading usage

The cluster console exposes it per cluster, human sessions only: `GET /api/console/usage`
returns per-minute rows for up to 168 hours, summed over the nodes, and
`GET /api/console/overview` carries the month-to-date count. The control plane returns the
last hour of a cluster's minutes, summed over the nodes, on the control-plane token:

```bash
curl -s http://127.0.0.1:6711/api/cp/clusters/$CLUSTER_ID/usage \
  -H "x-queen-cp-token: $CP_TOKEN"
```

No route returns the daily rows.

## What metering is not

- **Not a storage measure.** Retained bytes come from the broker's own per-queue stats
  through the registry reconciler, on a separate path, and are not in `usage_minutes`.
  See [Quotas and rate limits](/reference/multi-tenant/quotas/).
- **Not a per-queue breakdown.** The finest grain is `(cluster, minute, op class)`.
- **Not exactly-once.** The periodic write is idempotent, but a spool replay can
  over-count a batch once. Design any invoice on top of these figures with that in mind.
- **Not a substitute for the broker's own metrics.** These numbers describe traffic
  through the gateway, not what the storage engine did with it.
