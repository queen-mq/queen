The broker can scope queue identity to a tenant itself, on every operation. One
variable turns it on, a second says the header is somebody's to set, and one header drives
it:

```bash
QUEEN_TENANCY_HEADER=true
QUEEN_KV_TRUSTED_PROXY=true
```

```http
x-queen-tenant: 7f1a9c2e-4b3d-4f8a-9e10-2c5b6d7a8f90
```

This is an **operator** feature. The header is unauthenticated by design, so it is
meaningful only when the broker is unreachable except through something that sets it.
Everything below follows from that.

## Two broker routers

Where the two variables apply depends on the embedded proxy.

- **Behind the embedded proxy** (`QUEEN_PROXY_EMBEDDED=true`), the broker router the proxy
  hands requests to is built with tenancy on and the broker's own JWT off, whatever
  `QUEEN_TENANCY_HEADER` says, and it is bound to no socket: the proxy is the only way in.
- **On `PORT` without the proxy in front**, the broker router resolves the header only when
  `QUEEN_TENANCY_HEADER=true`. That is a node without the embedded proxy, or the internal
  port when `QUEEN_PROXY_PORT` gives the proxy a port of its own.

## What the flag does

With `QUEEN_TENANCY_HEADER=false` (the default), a middleware stamps the default tenant
into every request without reading any header at all, and the broker behaves exactly as a
broker with no notion of tenants: every queue, partition, cursor and KV row belongs to the
default tenant.

With it on, one middleware resolves the header once per request and stamps a tenant into
the request extensions. Every handler reads it and passes it with its command to the
state machine, where queues, partitions, cursors, KV rows and timers are keyed by tenant.

The boot log's `config: security` line reports the value as `tenancy_header`.

## Header semantics

| Header | Resolved tenant |
| --- | --- |
| Absent | `00000000-0000-0000-0000-000000000001`, the default tenant |
| Present but empty or whitespace | The default tenant |
| A canonical 8-4-4-4-12 hex UUID | That UUID, lowercased |
| Anything else (wrong length, missing dashes, non-hex, non-ASCII) | `400 {"error":"invalid x-queen-tenant header (must be a UUID)"}` |

The value is **opaque**. It is checked for shape and for nothing else: there is no
registry of tenants inside the broker, no list to be a member of, no signature.

The default tenant constant is shared with the proxy, which uses the same literal.

## What changes when it is on

- **Queue identity becomes `(tenant, name)`.** Two tenants can each own `orders`; they
  are different queues with different partitions, offsets and consumer-group cursors.
- **Pid-addressed operations are gated.** An ack, a message read, a message delete or a
  trace lookup that names a partition id verifies that the partition belongs to the
  request's tenant before it acts. See
  [Isolation](/reference/multi-tenant/isolation/) for the gate's properties.
- **In-process state is keyed by tenant**: long-poll wake gates by `(tenant, queue,
  group)`, per-queue metric counters and parked gauges by `(tenant, queue)`.
- **Deletes are keyed by tenant.** A queue delete removes that tenant's queue and nothing
  that only shares its name.

What does **not** change: the JWT access levels. Authentication and tenancy are
orthogonal mechanisms. A token's role decides which routes it may call; the header
decides which tenant's data those calls touch. Nothing binds a token to a tenant.

## The header is unauthenticated by design

Put plainly: **any client that can open a TCP connection to a tenancy-enabled broker
router can set `x-queen-tenant` to any UUID and operate as that tenant.** If JWT is on it
still needs a token with the right access level, but that token is not tied to a tenant,
so an admin token plus an arbitrary header value is full access to an arbitrary tenant's
data.

This is not a defect to be fixed at the broker. The trust boundary is drawn one hop out:

- The proxy sets the header from the cluster it resolved, using the cluster's
  `broker_tenant_uuid`, a value the tenant never sees and cannot influence. It drops any
  `x-queen-tenant` the client sent first.
- The proxy strips the client's `Authorization` header, and the broker router behind it
  runs with its own JWT off, so the credential a tenant holds has no meaning to the broker.
- That broker router has no socket. The only broker router with one is `PORT` when the
  proxy is not on it, and that port must stay off every network a tenant can reach.

<Aside type="danger">
A tenancy-enabled broker router must never be reachable by a tenant, by a tenant's
application, or from any network a tenant can reach. There is no configuration that makes
direct exposure safe: validating the header would require the broker to hold an identity
registry it deliberately does not have.
</Aside>

The same reasoning is why this header is absent from the client documentation. No SDK
sets it, no client-facing page mentions it, and a client that sends it to a proxy has it
dropped.

### One combination the broker refuses to boot with

`QUEEN_TENANCY_HEADER=1` **exits 1** unless `QUEEN_KV_TRUSTED_PROXY=1` is also set. It is
the only place where the reasoning above is turned into an interlock rather than a
warning, and the reason is that key/value state is the one surface with no opaque
identifier anywhere in it.

For queues the forged header is bad and bounded: a caller still has to name a queue, and
an ack still carries a lease id the broker minted and the caller cannot guess. For
[key/value state](/reference/http/kv) there is no such id. The only gate is the tenant the
KV rows are keyed by, and the tenant comes from the header, so a forged one reads and
writes another tenant's state **knowing only its name**. Setting the second variable is
the operator asserting that a proxy supplies the header and strips the client's, which is
exactly the trust boundary this section describes. An interlock that defaulted to
permissive would not be one.

The requirement is **unconditional**. The KV is part of the engine on every node, so
choosing the header mode is by itself the assertion that something in front sets it. A
deployment that cannot make that assertion is not one missing a feature, it is one with
an open door.

The eight [kv](/reference/http/kv) and [timer](/reference/http/timers) routes are
tenant-scoped in the generated route table, and every broker registers them.

## How the proxy uses it

`QUEEN_PROXY_TENANT_HEADER` defaults to `true`, so the proxy sets the header unless you
turn it off. Two paths send it:

- The data plane, on every request it hands to the broker, with the resolved cluster's
  `broker_tenant_uuid`.
- The registry reconciler, when it reads `GET /api/v1/resources/queues` for each cluster,
  in-process, to count queues and sum retained bytes. Otherwise it would read the default
  tenant's inventory for every cluster.

`GET /healthz` on the proxy reports the live value of the switch as `tenant_header`, so
a check can assert on the running process rather than on a boot log that outlives it.

Behind the embedded proxy the broker router always resolves the header, so this switch
alone decides the namespace. With `QUEEN_PROXY_TENANT_HEADER=false` the proxy still drops
any header a client sends and sets none of its own, so every cluster shares the default
tenant's namespace. That is the single-tenant front door
([Proxy](/deploy/proxy#the-single-tenant-front-door)); on a multi-tenant cell it is no
isolation at all. Verify the switch on the running processes.

## Enabling it on a broker that already holds data

Data written with the flag off belongs to the default tenant, the same constant the
middleware uses when the header is absent. Turning the flag on does not hide or move it.

What it does mean is that a cluster whose `broker_tenant_uuid` is a freshly generated
UUID, which is what cluster creation produces, sees an empty broker. No route changes a
cluster's `broker_tenant_uuid`, so bringing existing single-tenant data under a proxy
cluster leaves two choices:

- Keep every cluster on the default tenant with `QUEEN_PROXY_TENANT_HEADER=false`. That
  is right only while the cell has a single tenant.
- Or re-push the data under the new tenant. There is no in-broker facility for
  re-tenanting existing data.

Decide this before you create the cluster. After traffic has arrived on both UUIDs you
have two namespaces and no tool that merges them.

## Surfaces the header does not reach

Some broker responses describe the cell rather than a tenant and ignore the header
entirely: `GET /api/v1/status`, the system analytics, and the Prometheus exposition
(whose per-queue series sum across tenants). The proxy classifies each of them as
operator or blocked for exactly that reason. The raft membership routes under
`/api/v1/system/raft/` go further and refuse a request that names a tenant with `403`.
The streams routes resolve the header like every other tenant surface
([Isolation](/reference/multi-tenant/isolation/#streams-are-tenant-scoped)).

[Isolation](/reference/multi-tenant/isolation/) lists them with what each one would
expose.

## Checklist

<Steps>

1. On a multi-tenant cell, set `QUEEN_PROXY_EMBEDDED=true` on every node. The broker
   router behind the proxy then resolves the header, with its own JWT off and no socket.

2. Leave `QUEEN_PROXY_TENANT_HEADER` at its default and confirm `GET /healthz` on the
   proxy reports `"tenant_header": true` on every node.

3. If `QUEEN_PROXY_PORT` gives the proxy a port of its own, `PORT` serves the broker
   router directly with its own settings. Keep it off every network a tenant can reach.
   If it runs `QUEEN_TENANCY_HEADER=true`, it also needs `QUEEN_KV_TRUSTED_PROXY=true`
   ([that interlock](#one-combination-the-broker-refuses-to-boot-with) is the reason),
   and `JWT_ENABLED=true`: tenancy is not authentication.

4. Keep the raft port reachable by the cell's own nodes only, with the same
   `QUEEN_RAFT_TOKEN` on each. See [Trust boundaries](/deploy/security/).

5. Test the boundary before you trust it: push with one cluster's API key, then try to
   read it back with another's. The second call must see nothing.

</Steps>
