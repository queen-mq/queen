Everything the proxy needs to route, authorize, limit and bill a request lives in the
broker's own replicated key/value store, under a system tenant reserved for the proxy that
no cluster is ever given. There is no separate database: the proxy's writes go through the
same raft log as the messages, and every node of a cell reads the same state. The proxy
reads it through a 30-second cache. Writes go through the proxy's own store functions,
which validate their input and write the change, its audit row and its cache invalidation
in one atomic batch, so neither the audit trail nor the invalidation is optional.

## The documents

Each table of the model is one key/value namespace holding one JSON document per row. A
unique column (a slug, an email, a key hash) is an index of its own, claimed in the same
atomic batch as the row, so two nodes can never both win the same value.

| Documents | Holds | Lifecycle |
| --- | --- | --- |
| `tenants` | The organisation. `slug` (DNS-label shaped, unique), `name`, `status` | `status`. `DELETE /api/cp/tenants/:slug` deletes it with everything under it |
| `users` | Login identity, scoped to one tenant. Non-unique optional display `name`, globally unique `email`, optional bcrypt `password_hash`, last login time, `is_operator` | Deleted only with their tenant |
| `identities` | One per linked provider (`local`, `google`, `github`) per user, with `verified` | Written by the OAuth sign-in path |
| `plans` | The limit catalog. `code`, `cell_class`, eleven limit fields, `monthly_msgs_quota`, `features` JSON | Seeded at first boot |
| `cells` | One Queen deployment. `slug`, `region`, `base_url`, `class`, `cell_secret`, `status`, `capacity_slots`, `used_slots` | Seeded at first boot |
| `clusters` | The tenant-visible Queen. `slug` (the subdomain, globally unique), `cell_id`, `plan_id`, `broker_tenant_uuid`, `status`, `limit_overrides` JSON | `status` |
| `cluster_roles` | `(user, cluster) → role` for `admin`, `producer`, `consumer`, `viewer` | One per pair |
| `api_keys` | Cluster-scoped credentials, stored as a sha256 hash, with a scope list | `revoked_at` |
| `queues` | A **cache** of `(cluster, queue name, partitions_count)` for cap admission | Soft-deleted by the reconciler |
| `s3_sinks` | One per cluster: its [S3 sink](#a-clusters-s3-sink). The cluster's `broker_tenant` (copied when written), `enabled`, the sink's settings as `config` JSON (never a secret), the S3 secret sealed with the cell's `QUEEN_ENCRYPTION_KEY`, and `updated_at`, which every write moves | Set and removed through `/api/cp/clusters/:slug/s3`; removed by the tenant's purge and with the tenant |
| `usage_minutes`, `usage_days` | Metered usage per `(cluster, period, op class)`; minutes are written per node | Minutes expire ([metering](/reference/multi-tenant/metering/)); days are kept |
| `operations` | Append-only audit. Every change the store makes writes a row for it | Kept |
| `revoked_tokens` | Session `jti` deny-list with the token's own expiry | Expires with the token |
| `outbox` | Control-plane-bound events. The proxy writes them; something else drains | `consumed_at` |

`queues` deserves the emphasis on *cache*. The broker owns queue existence; these documents
exist so the proxy can answer "how many queues does this cluster have" without a
round trip per push. They store a partition **count**, never partition names (neither
this cache nor the broker's own queue listing exposes them), which is why the proxy keeps
the exact pairs it admitted in memory and treats the stored count as a floor after a
restart.

## Status, and how two statuses combine

The store refuses any status outside the lists below.

| `tenants.status` | `clusters.status` | Effect the proxy applies |
| --- | --- | --- |
| `active` | `active` | Everything allowed |
| `grace` | n/a | Pushes blocked, consumes allowed |
| n/a | `push_blocked` | Pushes blocked, consumes allowed |
| `suspended` | `suspended` | Whole data plane `403 cluster_suspended` |
| `deleting` | `deleting` | Same as suspended |

The two are merged **worst-wins**: a tenant in `grace` puts every one of its clusters
into the push-blocked state without touching their documents. An unrecognised status value
is treated as at least as restrictive as `suspended`, so a future state cannot fail
open.

`grace` mapping to push-blocked rather than a full suspend is a deliberate choice: a
payment problem should stop new data arriving, not strand data the tenant has already
paid to store.

A cluster's status is set with `PUT /api/cp/clusters/:id/status`, a tenant's with
`PUT /api/cp/tenants/:slug/status`.

## Plans and per-cluster overrides

Four plans are seeded at first boot, idempotently on every node. Every value is a hard cap
the proxy enforces, `null` meaning unlimited:

| | `free` | `dev` | `pro` | `dedicated-s` |
| --- | --- | --- | --- | --- |
| `cell_class` | shared | shared | shared | dedicated |
| `max_req_per_sec` / `req_burst` | 5 / 25 | 10 / 50 | 50 / 200 | 200 / 800 |
| `max_msgs_per_sec` / `msgs_burst` | 20 / 100 | 40 / 200 | 200 / 800 | 600 / 2000 |
| `max_queues` | 20 | 50 | 200 | 1000 |
| `max_partitions_per_queue` | 8 | 16 | 32 | 64 |
| `max_parked_pops` | 50 | 150 | 1000 | 5000 |
| `max_payload_bytes` | 256 KiB | 512 KiB | 1 MiB | 4 MiB |
| `max_batch_items` | 1000 | 2000 | 5000 | 10000 |
| `max_retained_bytes` | 1 GiB | 3 GiB | 20 GiB | 200 GiB |
| `max_retention_seconds` | 7 days | 14 days | 30 days | 90 days |
| `features` | kv, timers, ephemeral | kv, timers, ephemeral | kv, timers, ephemeral, streams, traces | kv, timers, ephemeral, streams, traces |
| `monthly_msgs_quota` | `null` | `null` | `null` | `null` |

These are the seeds, not a recommendation. No route adds, edits or reassigns a plan: a
cluster gets its plan when it is created (`plan` on `POST /api/cp/bootstrap` and
`POST /api/cp/clusters`, default `free`; required on `POST /api/cp/provision`;
`QUEEN_PROXY_BOOTSTRAP_PLAN`, default `dev`), and a change for one cluster goes through its
overrides.

`monthly_msgs_quota` is `null` on **every** seeded plan. Nothing monthly is enforced
until you set one, which on a seeded plan means a cluster override. The mechanism exists
and is described in [Usage metering](/reference/multi-tenant/metering/); it simply has no
value to compare against out of the box.

`features.streams` opens the routes but is not the whole grant: the broker refuses a
non-default tenant's **new** query registrations until it holds an enabled streams grant
for that cluster's `broker_tenant_uuid`, with an optional `maxQueries` cap (absent is
unlimited). The grant is a broker write, not a proxy one, and the proxy blocks
`/api/v1/system/*` for every principal, so it is made on the broker router itself: the
internal port when `QUEEN_PROXY_PORT` gives the proxy a port of its own, with an `admin`
token when that port runs `JWT_ENABLED=true`. `GET /api/cp/clusters/:slug` returns the
`broker_tenant_uuid`:

```bash
curl -s -X POST http://127.0.0.1:6632/api/v1/system/quota \
  -H 'Content-Type: application/json' \
  -d '{"tenant":"<broker_tenant_uuid>","kind":"streams","maxQueries":100}'
```

Absence is a denial by design, because the tenant header is opaque and a fail-open default
would hand query space to any invented id.
[Isolation](/reference/multi-tenant/isolation/#streams-are-tenant-scoped) covers what
the streams family guarantees once granted.

Per-cluster deltas live in the cluster's `limit_overrides`, a JSON object whose keys are
the plan's limit names. The merge has exactly three cases:

| Key in `limit_overrides` | Effective value |
| --- | --- |
| Absent | The plan's value |
| Present as JSON `null` | Unlimited. This *overrides* a plan cap, it does not fall back to it |
| Present as a number | That number |
| Present as something else | The plan's value (a non-numeric override is ignored, never a silent zero) |

```bash
curl -s -X PUT http://127.0.0.1:6711/api/cp/clusters/$CLUSTER_ID/overrides \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d '{"max_queues": 500, "max_retained_bytes": null}'
```

The route takes the cluster's id: `GET /api/cp/clusters/acme-prod` returns it (`acme-prod`
is the cluster provisioned in the next section). A body of `null` or `{}` clears every
override. Raising one limit for one customer is therefore one call, not a forked plan.

The document is the whole override set, and it is checked before it is stored: its keys are
the plan's eleven limit names and `monthly_msgs_quota`, each a non-negative integer or
`null`. Any other key or value is `400 {"code":"invalid"}`, here and on
`POST /api/cp/provision`, so the last row of the table only describes a document written
some other way.

## Provisioning

Provisioning goes through the control plane, `/api/cp/*` on the proxy's port, guarded by
`QUEEN_PROXY_CP_TOKEN` in the `x-queen-cp-token` header. With no token configured every
route answers `404`, and a wrong token is `401`. Each write calls a store function that
validates its input and writes the change, its audit row and, when a cluster is involved,
an invalidation mark, in one atomic batch. Every node polls that invalidation feed
(`QUEEN_PROXY_INVAL_POLL_MS`, default 1000 ms) and drops that cluster's cached entries at
its next poll.

| Route | Does |
| --- | --- |
| `POST /api/cp/bootstrap` | A tenant, its cluster, an admin and a first API key, in one write |
| `POST /api/cp/provision` | A tenancy whose ids and key a control plane chose: tenant, cluster, user, role, key and overrides, in one write |
| `POST /api/cp/tenants` | A tenant, from `{slug, name?}` |
| `PUT /api/cp/tenants/:slug/status` | `{status}`: `active`, `grace`, `suspended` or `deleting`, for every cluster of the tenant |
| `POST /api/cp/tenants/:slug/purge` | The tenant's S3 sinks removed, then the broker's own purge, for every cluster of a `deleting` tenant |
| `DELETE /api/cp/tenants/:slug` | Deletes a `deleting` tenant and everything under it (`?force=true` skips the status check) |
| `GET /api/cp/clusters` | Every cluster; `?plan=<code>` keeps one plan's |
| `POST /api/cp/clusters` | Ensures a cluster exists, from `{tenant_slug, tenant_name?, slug, plan?, cell_id?}`, creating the tenant when needed |
| `GET /api/cp/clusters/:slug` | One cluster: its ids, plan, statuses and overrides |
| `GET /api/cp/clusters/:slug/queues` | The broker's queue listing for the cluster |
| `POST /api/cp/clusters/:slug/configure` | The broker's `configure` for one of the cluster's queues |
| `PUT /api/cp/clusters/:slug/s3` | The cluster's S3 sink: its settings, checked by the broker, `secretKey`, stored sealed, and `enabled` |
| `GET /api/cp/clusters/:slug/s3` | The cluster's S3 sink, without its secret |
| `DELETE /api/cp/clusters/:slug/s3` | Removes the cluster's S3 sink |
| `PUT /api/cp/clusters/:id/overrides` | The cluster's limit overrides (`null` clears them) |
| `PUT /api/cp/clusters/:id/status` | `{status}`: `active`, `push_blocked`, `suspended` or `deleting` |
| `GET /api/cp/clusters/:id/usage` | The last hour of metered minutes, summed over the nodes |
| `POST /api/cp/activity` | When each named cluster last had traffic, and how much it stores |
| `POST /api/cp/keys` | An API key from `{cluster_id, name, key_hash, scopes}`: the plaintext never reaches the proxy |
| `DELETE /api/cp/keys/:id` | Revokes a key |

Every route is safe to retry: a call that already took effect answers success again with
the same ids, so a control plane that delivers its commands at least once needs no
bookkeeping of its own for them. A refused input answers `400 {"code":"invalid"}`, a
unique value that is already taken `409 {"code":"conflict"}`, and a store that did not
answer `503 {"code":"unavailable"}`. The sections below name the other codes.

The token is checked from the request's head before any of its body is read, and a body
over 1 MiB is `413 {"code":"payload_too_large"}`. Every slug is read one way: trimmed,
lowercased, and then it must be a DNS label (`a-z`, `0-9` and `-`, at most 63 characters),
or the call is `400` before anything is looked up. Tenant and key names are at most 200
characters and emails at most 254 bytes.

### One call to onboard

```bash
curl -s -X POST http://127.0.0.1:6711/api/cp/bootstrap \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d '{"tenant_slug":"acme","tenant_name":"Acme Inc","cluster_slug":"acme-prod","plan":"free","admin_email":"ops@acme.example","password":"initial-password","key_name":"default"}'
```

It returns `{tenant_id, cluster_id, user_id, api_key, password_set, can_login}` and is one
atomic write: there is no half-created tenant. The `api_key` field is the **plaintext key,
shown exactly once**, with all four scopes; only its sha256 hash is stored.
`cluster_slug` defaults to the tenant slug, `plan` to `free` and `key_name` to `default`.
Leave `password` out for an OAuth-only admin.

It is idempotent on the slugs: a re-run returns the existing ids with `api_key` set to
`null`, because the plaintext cannot be recovered. It still re-asserts the admin role.
Two collisions are refusals rather than repeats: a cluster slug owned by another
tenant, and an email that already belongs to another tenant. Both are globally unique.

A password passed here is bcrypt-hashed at cost 10 before it is stored, in the form the
login path accepts.

The first tenant of a cell can come from the environment instead, at every boot, on every
node, idempotently: `QUEEN_PROXY_BOOTSTRAP_TENANT` and its companions
([the bootstrap tenant](/deploy/proxy#the-bootstrap-tenant)).

### A tenancy from a control plane

`POST /api/cp/provision` is for a control plane that owns the identities. It chooses the
user's id (the `sub` of the sessions it signs) and mints the API key itself, sending only
the key's sha256:

```bash
curl -s -X POST http://127.0.0.1:6711/api/cp/provision \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  --data @- <<'EOF'
{"tenant_slug": "acme", "tenant_name": "Acme Inc", "cluster_slug": "acme", "plan": "free",
 "user_id": "6f2c1d64-8a3e-4a57-9d1b-2f0c5e7a9b10", "email": "ops@acme.example", "role": "admin",
 "key_name": "signup", "key_hash": "<sha256 of the key, 64 lowercase hex>",
 "scopes": ["produce", "consume", "read", "admin"],
 "overrides": {"max_req_per_sec": 10, "max_retained_bytes": 1073741824}}
EOF
```

It ensures, in one atomic write:

- the tenant, by slug, created with `tenant_name` (the slug when absent);
- the cluster, by slug, created on `plan`. An existing cluster keeps its plan, and a
  cluster slug that belongs to another tenant is `409`;
- the user under `user_id`, created, or its email moved to `email` (lowercased). An email
  that belongs to another user, or a `user_id` of another tenant, is `409`;
- `role` on the cluster: `admin`, `producer`, `consumer` or `viewer`;
- the key. A live key of this cluster holding `key_hash` is the one an earlier attempt
  created, and is kept whatever its name. A hash held by a revoked key or by another
  cluster's key is `409`;
- `overrides` as the cluster's whole override document, replacing the old one (`null` or
  absent is `{}`). Its keys are the plan's eleven limit names and `monthly_msgs_quota`,
  each a non-negative integer or `null`.

An unknown `plan`, a `key_hash` that is not 64 lowercase hex characters, or any other
refused field is `400`, and a node that has not seeded its state yet answers `503`. A
tenant being wiped (status `deleting`) is `409 {"code":"deleting"}`, also when the wipe
begins while the call runs: the write carries the version of the tenant it read. The
answer carries `tenant_id`, `cluster_id`, `broker_tenant_uuid`, `user_id`, `key_id`,
`plan_code`, `overrides` and `created: {tenant, cluster, user, key}`. `plan_code` is the
cluster's own plan, and each `created` flag says whether this call made that row. A repeat
answers the same ids with every flag `false` and writes nothing.

### Reading clusters back

`GET /api/cp/clusters/:slug`, and every row of `GET /api/cp/clusters`, carries `id`,
`slug`, `tenant_id`, `tenant_slug`, `broker_tenant_uuid`, `plan_code`, `status`,
`tenant_status` and `overrides`. `status` is the cluster's own and `tenant_status` the
tenant's; the two combine worst-wins, as above. The list is in slug order, and
`?plan=free` keeps the clusters on that plan. An unknown slug is
`404 {"code":"cluster_unknown"}`.

### Retiring a tenant

Three calls, in this order, each safe to repeat:

1. `PUT /api/cp/tenants/:slug/status` with `{"status":"deleting"}`. Every cluster of the
   tenant refuses its data plane (`403 cluster_suspended`) from each node's next cache
   refresh. The answer is `{ok: true, tenant_id, clusters}`, each cluster as
   `{id, slug, broker_tenant_uuid}`, and an unknown slug is
   `404 {"code":"tenant_unknown"}`. Setting the status a tenant already has writes nothing.
2. `POST /api/cp/tenants/:slug/purge`. It first removes the S3 sinks of the tenant's
   clusters, on every pass. Every broker node has stopped them, or does within 5 seconds,
   the interval at which it reads the statuses again: a `deleting` tenant's sink does not
   run. What the sinks wrote stays in their buckets, because neither the purge nor a sink
   deletes an object. Then, for every cluster, the proxy runs the broker's own
   tenant purge (`DELETE /api/v1/resources/tenant`, which no tenant credential can reach)
   in-process, for that cluster's `broker_tenant_uuid`: its queues and messages, KV rows,
   timers, traces and stream queries. It refuses a tenant that is not `deleting`
   (`409 {"code":"not_deleting"}`) and answers `{existed, done, clusters}`, each cluster as
   `{slug, broker_tenant_uuid, done, partitions_deleted}`. A cluster is `done` only on a
   pass the broker confirms that found nothing left to delete, so the pass that deletes
   answers `done: false` and the next one proves it: repeat the call until `done` is
   `true`. An answer the broker did not confirm carries an `error`. A cluster the tenant
   lists whose document is gone keeps the whole call at `done: false`, its id under
   `missing_clusters`: its broker tenant is unknown. An unknown slug answers
   `{existed: false, done: true, clusters: []}`.
3. `DELETE /api/cp/tenants/:slug`. Deletes the tenant and everything the proxy keeps for
   it: its clusters, users and their identities, roles, API keys, queue rows, S3 sink rows,
   usage and audit rows. It refuses a tenant that is not `deleting` (`409 {"code":"not_deleting"}`),
   and one whose clusters' broker tenants still list a queue
   (`409 {"code":"not_purged"}`, or `503` when the broker's listing cannot be read);
   `?force=true` skips both. It answers `{existed: true, clusters}`, each cluster as
   `{cluster_id, slug, broker_tenant_uuid}`, and `{existed: false, clusters: []}` once the
   tenant is gone.

The delete does not touch the broker, and the purge touches none of the proxy's documents
but the tenant's S3 sink rows, which it removes without an audit row of their own: a tenant
deleted without its purge leaves its broker data behind, under a `broker_tenant_uuid` the
delete's answer is the last place to find.

### Activity

`POST /api/cp/activity` with `{"clusters": ["acme", ...]}`, at most 256 slugs, answers
`{clusters: [...]}` with one entry per slug, in the order asked:

| Field | Meaning |
| --- | --- |
| `slug` | The slug as asked |
| `found` | Whether a cluster has that slug. Every field below is `null` when none does |
| `cluster_id` | The cluster's id |
| `last_activity_at` | The newest minute with traffic of op class `push`, `delivery`, `txn` or `read`, from every node. A rolled-up day whose minutes are already gone counts as its last second |
| `first_push_at` | The oldest minute still kept with pushed messages |
| `last_key_used_at` | The newest use of any of the cluster's keys, revoked ones included, recorded at most once a minute per key |
| `retained_bytes` | The total the storage quota last measured for the cluster on this node |

Times are RFC 3339 in UTC, to the second (`2026-10-01T07:15:00Z`). Missing data is `null`,
never `0`: a cluster without traffic has no `last_activity_at`, and `retained_bytes` stays
`null` until the registry has measured the cluster since the node started. A slug that is
not a DNS label is answered `found: false` like any other unknown one.

### The broker, for one cluster

`GET /api/cp/clusters/:slug/queues` and `POST /api/cp/clusters/:slug/configure` hand their
request to the broker in-process, with the cluster's `broker_tenant_uuid` as the tenant, and
pass the broker's answer back as it is: the queue listing (`GET /api/v1/resources/queues`,
query string included) and a queue's configuration (`POST /api/v1/configure`, the body
`{queue, options}` unchanged). An unknown slug is `404 {"code":"cluster_unknown"}`: neither
route creates a cluster. While the cluster or its tenant is `deleting`, `configure` is
`409 {"code":"deleting"}`, so nothing writes a queue back during a wipe; the listing still
answers.

Every route that acts on the broker (these two, the purge and the delete's purge check)
refuses with
`409 {"code":"system_tenant"}` a cluster bound to the broker's default tenant or to the
proxy's own, and refuses every cluster while `QUEEN_PROXY_TENANT_HEADER` is off, because
the clusters' data is then the default tenant's. A tenant a request names is never used:
the tenant is always the cluster's own.

### A cluster's S3 sink

`PUT /api/cp/clusters/:slug/s3` gives the cluster's broker tenant an S3 sink of its own,
writing to its own bucket; `GET` reads it back and `DELETE` removes it. The three routes
exist only where the node runs the S3 sink (`QUEEN_S3_EMBEDDED=true`), and answer
`404 {"code":"s3_unavailable"}` elsewhere.

```bash
curl -s -X PUT http://127.0.0.1:6711/api/cp/clusters/acme-prod/s3 \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d '{"endpoint":"https://s3.eu-west-1.amazonaws.com","region":"eu-west-1","bucket":"acme-lake","accessKey":"AKIA...","secretKey":"...","queues":"*"}'
```

- The body is the sink's settings, plus `secretKey` and `enabled`. The settings are a JSON
  object of at most 32 KiB with no key named like a secret, and the broker checks them by
  the sink's own rules: `endpoint`, `region`, `bucket`, `accessKey` and `queues` are
  required, the optional ones are listed on
  [the S3 sink page](/deploy/s3#per-tenant-settings), and an unknown field, a node-wide
  one or a value the sink refuses is `400 {"code":"invalid"}` with the sink's sentence.
- `secretKey` is required while the cluster has no sink, at most 4096 bytes, and omitted
  or `null` keeps the stored one. It is stored only sealed with the cell's
  `QUEEN_ENCRYPTION_KEY`, so a cell without the key answers
  `409 {"code":"encryption_required"}`, and no answer or error carries it, sealed or not.
- `enabled` defaults to `true`. `false` keeps the row and its secret, and the sink does not
  run.

A PUT and a GET answer the row without its secret:
`{cluster, tenant, enabled, config, secretKeySet, updatedAt}`, `tenant` being the cluster's
broker tenant and `updatedAt` the time of the last write, to the second. A GET of a cluster
with no sink is `404 {"code":"s3_unset"}`. A DELETE answers `{cluster, removed}`, with
`removed: false` when there was nothing to remove. A PUT that carries `secretKey` always
writes and moves `updatedAt`, because a new secret cannot be told from a repeated one, and
that is what makes every node rebuild the sink with it; a PUT without one that changes
nothing writes nothing. Each write appends its audit row: `s3_sink_set`, with
`{enabled, secret}` and `secret` `set` or `kept`, or `s3_sink_removed`.

A PUT is refused for a cluster or tenant being deleted (`409 {"code":"deleting"}`), and, like
the routes above, for a cluster bound to a system tenant or any cluster while
`QUEEN_PROXY_TENANT_HEADER` is off (`409 {"code":"system_tenant"}`). An unknown slug is
`404 {"code":"cluster_unknown"}` on all three. Every broker node reads the rows again every 5
seconds and starts, rebuilds or stops the tenant's sink to match. A sink runs while its row is
enabled and the cluster's combined status is `active` or `push_blocked`; how it runs, and what
it writes, is [the S3 sink page](/deploy/s3#a-tenants-sink-from-the-control-plane).

### Keys, retried

`POST /api/cp/keys` answers `201 {id, existed: false}` for a new key. A hash the cluster
already holds on a live key answers `200 {id, existed: true}` with that key, whatever its
name and scopes. A hash held by a revoked key or by another cluster's key is `409`.
`DELETE /api/cp/keys/:id` answers `{ok: true, already_revoked}`, `true` when the key was
revoked before, and an unknown id is `404 {"code":"key_unknown"}`.

cluster admin could escalate to reading (and pausing) every other tenant on the cell.

## API keys

The format is `qk_<env>_<43 base64url characters>`, generated from 32 bytes of the OS
CSPRNG. Only `sha256(key)` in lowercase hex is stored, and the store refuses any other
shape. A key the proxy generates exists in plaintext once, in the response of the call
that created it; a key issued through `POST /api/cp/keys` arrives as its hash, so the
proxy never sees its plaintext.

The `<env>` segment (`live`, `test`, whatever you choose) is **informational**.
Authentication routes on the `qk_` prefix and then matches on the hash alone; nothing
parses the environment out.

Scopes are a non-empty subset of `produce`, `consume`, `admin`, `read`. What each scope
opens is in [Credentials and authorization](/reference/multi-tenant/auth/).

A key is bound to the cluster it was issued on, for its whole life. Presenting it on
another cluster's hostname is `403`, and the `x-queen-act-cluster` header is refused
for API keys outright.

## Cells

A cell is one Queen deployment: a single node, or one raft cluster of nodes. The single
binary seeds exactly one cell at first boot, `local`, with `base_url` `inprocess://self`
and no `cell_secret`: the data plane hands each request to the broker router in the same
process, which runs with its own JWT off, so there is no secret to present. No route
creates another cell. `POST /api/cp/clusters` takes an optional `cell_id`, which defaults
to that cell, and `POST /api/cp/provision` always places a new cluster there.

### Placement and groups

Every node of a cell serves every cluster on it: the proxy's state is replicated, and a
node hands a request for any cluster to its own broker. Within a node,
`QUEEN_RAFT_GROUPS` (default 1, at most 64, the same value on every node) splits the state
machine into that many raft groups, each with its own log and leader. A broker tenant,
which for a proxy cluster is its `broker_tenant_uuid`, lives in exactly one group: the one
a stable hash of the tenant picks, or the one an entry of
`QUEEN_TENANT_GROUPS=tenant=group,...` names for a tenant that has not written yet. A
tenant's group does not change while it has data.

There is no cluster migration path. Moving a cluster to another cell means moving its
data, and nothing here does that. Size a cell with enough headroom that you are never
forced to move a cluster in a hurry.

## The audit trail

`operations` is append-only, stored newest first per tenant, with a second index per
cluster. Every change above writes a row for itself, except the purge's removal of a
tenant's S3 sinks, with an `actor` of `user`,
`api_key`, `control_plane` or `system`. The control-plane store functions write
`control_plane`. The console and the sign-in path write rows with actor `user` and the
signed-in user's id,
so a console action that also runs a store function leaves two rows: the function's own
`control_plane` row and a second, user-attributed one. That is deliberate, and it is why
a `user` actor in the audit trail means a human acted rather than an automation did. The
console's second row is best-effort: a failed write does not fail the action it was
recording.

No route reads the audit trail back. A tenant's rows go with the tenant
(`DELETE /api/cp/tenants/:slug`); the outbox keeps one `tenant_deleted` event with the
counts, and no copy of the admin's email.
