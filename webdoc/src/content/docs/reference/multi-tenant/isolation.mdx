Tenant isolation in Queen is split across two processes on purpose. The broker scopes
everything that is queue-shaped, natively, in SQL, on every read and every write. The
proxy is what makes the header that drives that scoping trustworthy, and what refuses
the surfaces the broker does not scope because they describe the cell rather than a
tenant.

Neither half is sufficient alone. A broker reachable directly by a tenant has no
isolation at all, because the scoping key arrives in an unauthenticated header. A proxy
in front of a broker with tenancy off would route every tenant into the same namespace.

## What the broker scopes natively

With `QUEEN_TENANCY_HEADER=true`, `queen.queues` carries a `tenant_id` and queue
identity becomes `(tenant, name)` rather than `name`. Two tenants can both own a queue
called `orders` and they are different queues, with different partitions, different
offsets, and different consumer-group cursors.

Queue identity is one table: `queen.queues(id)` is both the configuration row and the
identity every data row hangs off, and `queen.log_partitions.queue_id` is a foreign key
to it. There is no name-based bridge between configuration and data anywhere in the
schema, so a whole class of cross-tenant hazard (a join on queue *name* that matches
another tenant's same-named queue) is structurally unrepresentable, not merely
guarded against. The retention work list, the analytics readers and the ownership gate
below all join by id.

Forty-three of the broker's sixty registered handlers resolve a tenant from the request
and thread it into the SQL name-resolution functions. That covers the whole queue-shaped
surface: push, pop, ack, transactions, configure, seeks, subscriptions, queue and
namespace listings, per-queue analytics, consumer groups, message and DLQ reads, trace
reads, and the three streams routes (registration, state reads and the cycle). The
[route table in the reference](/reference) marks each one.

## The ownership gate

Some operations do not name a queue. They name a **partition id** (an ack, a message
read, a message delete, a trace lookup, a stream state read, a stream cycle), and the
stored procedures behind them address rows by partition UUID alone. Scoping by name
cannot help there.

So the handler checks ownership first, before the procedure runs:

```sql
SELECT EXISTS(
  SELECT 1 FROM queen.log_partitions p
  JOIN queen.queues q ON q.id = p.queue_id
  WHERE p.id = $1::text::uuid AND q.tenant_id = $2::text::uuid
)
```

One indexed lookup on the partitions primary key. A partition id belonging to another
tenant is rejected rather than acted on. Four properties make the gate trustworthy:

- **Deny by default.** A pool checkout failure or a query error is treated as *not*
  owned. A transient database problem cannot open a cross-tenant hole.
- **It never consults the pid-to-queue memo.** That cache is populated by pop traffic,
  and ownership must not trust a cache an attacker's traffic can fill.
- **Only positives are cached.** A confirmed `(pid, tenant)` pair is remembered: a
  partition's tenant is immutable, and UUIDs are not reused, so a positive is valid
  forever. Negatives are never cached, which means a forged or foreign pid pays the
  full check every single time and cannot be used to grow the map.
- **The cache is bounded** at 500,000 entries and cleared wholesale on overflow;
  correctness is unaffected because ownership is re-derived from the database.

With tenancy off the gate short-circuits to "owned" with no database round trip, since
a single-tenant broker has only default-tenant queues. That is what keeps the
open-source path byte-identical.

## Tenant-keyed in-process state

Isolation would leak through caches if any of them were keyed by queue name alone. They
are keyed by a `(tenant, queue)` composite instead:

| State | Why the key matters |
| --- | --- |
| Lease-time cache | Two tenants' same-named queues can have different lease times |
| Encryption-flag cache | A flag lookup must not be poisoned by another tenant's same-named queue |
| Hot-list rings and long-poll wake gates | A wake for one tenant's `orders` must not wake another's |
| Per-queue metric counters | Otherwise two tenants' counters would merge |
| Parked-consumer gauges | Same |

Cross-broker mesh frames carry the tenant, so an invalidation removes exactly one
entry. A frame that arrives without a tenant (the pre-tenancy frame shape is still
parsed) is fanned out to every tenant holding that queue name. That is an over-invalidation
and an over-wake, both harmless; attributing it to the default tenant instead would
silently drop the signal for every other tenant.

Shared-cell memory is bounded by an idle sweep that drops per-`(tenant, queue)` rings
and gates once they go quiet, so a tenant cannot pin unbounded per-name state by
touching many queue names.

## The surfaces that are not tenant-scoped

These exist, they are useful, and they describe the **cell**. None of them can be
scoped to a tenant, which is why the proxy classifies them as operator or blocked and
answers `404` to everything else. Read this list as the reason the gateway exists, not
as a set of holes.

| Surface | What it exposes |
| --- | --- |
| `GET /api/v1/status`, `GET /api/v1/status/buffers` | Cell-wide broker state and buffer counts across every tenant |
| `GET /api/v1/analytics/system-metrics` | Host CPU and memory of the machine the cell runs on |
| `GET /api/v1/analytics/worker-metrics` | Process lifetime counters |
| `GET /api/v1/analytics/postgres-stats` | PostgreSQL internals for the shared database |
| `GET /metrics/prometheus` | Per-queue series labelled by queue name with **no tenant label** |
| `POST /api/v1/system/maintenance` | A switch that changes the behaviour of the whole cell |
| `/internal/*` | The broker-to-broker surface |

One of those deserves the detail.

### Prometheus sums across tenants

The exposition format keeps one line per queue name, so the parked-long-poll gauge is
explicitly aggregated across tenants before it is written, and the database-backed
per-queue families (depth, pending, pop lag, acks per minute, DLQ depth) carry a
`queue` label and nothing else.

On a shared cell that endpoint therefore reveals every tenant's queue names and volumes.
It is also classified `public` by the broker's own access-level table, so enabling JWT
does not close it. Restrict it at the network layer and scrape it from the operator
side only. Never proxy it to a tenant.

## Streams are tenant-scoped

The streaming engine used to be the one name-addressed surface the tenant header did
not reach: query names were global, the cycle resolved its sink queues on the default
tenant, and stream state answered to anyone holding the right UUIDs. All of that is
gone, and the family now carries the same guarantees as the queue surface:

- **A query belongs to one tenant.** `queen_streams.queries` carries a `tenant_id` and
  its `name` is unique per tenant, so two tenants can both register
  `orders.per_customer_per_min` and neither can observe, update or reset the other's.
  The 409 a `config_hash` conflict returns can only ever name the caller's own query.
- **State reads and cycles pass the ownership gate.** Both routes address a partition
  by raw UUID, so they take the same pre-gate as acks and message reads (a foreign
  partition gets the same 404 a missing one gets), and the stored procedures check the
  query's owner again before touching a state row. A foreign `query_id` reads as empty
  rows, never as an error that would confirm it exists.
- **Sink emits stay home.** Every sink queue the cycle resolves or lazily creates is
  the caller's own: auto-created queues are stamped with the request tenant, exactly
  like push auto-create.
- **Registration is granted, not assumed.** With tenancy on, a tenant registers a new
  query only if the cell database holds an enabled `queen_streams.quota` row for it,
  and `max_queries` (when set) is an exact cap. Absence is a denial, the same posture
  as the KV grant: provisioning a streams-enabled tenant means writing that row.
  Re-registering an existing query is never gate-checked, so revoking the grant stops
  new queries without stranding a Runner that is still draining.
- **The tenant wipe covers it.** `queen.delete_tenant_data_v1` purges the tenant's
  queries, its quota row and its state, and every state row is attributable through
  the query foreign key even after its partition is gone.

The default tenant is exempt from the grant and the cap, which is what keeps a
single-tenant broker with tenancy off byte-identical to the pre-tenancy engine.

<Aside type="caution">
The scoping lives in the current broker. On a shared cell, enable the `streams`
feature only once every broker in the cell runs a version that scopes streams: during
a mixed-version window an older broker resolves the family on the default tenant,
which is the pre-tenancy behaviour, not a crash, but it is not isolation either. And a
tenant on a plan with `features.streams = true` still needs its `queen_streams.quota`
row on the cell database, or every new registration answers 403.
</Aside>

## Where the proxy is the boundary

Every isolation property above depends on the tenant header being right, and on the
broker being unreachable except through the thing that sets it:

<Steps>

1. **The client's credential never reaches the broker.** The proxy strips
   `Authorization` and substitutes the cell secret.

2. **The tenant header is set by the proxy**, from the cluster resolved out of the
   `Host` label (from `clusters.broker_tenant_uuid`, a value the tenant never sees and
   cannot choose).

3. **Blocked and operator classes never forward.** An unknown API-shaped path is `404`,
   not a pass-through, so a new broker route cannot become reachable by accident.

4. **The operator capability is gated per cell.** With
   `QUEEN_PROXY_OPERATOR_ENABLED=false`, the cell-wide routes have no code path at all,
   a structural guarantee rather than a permission check.

5. **The broker's network policy admits only the proxy.** This is the assumption all
   four points above rest on.

</Steps>

## How these claims are tested

Every property on this page is asserted by a suite that plays one tenant against
another, on a running stack, rather than by reading the code.

`test/runners/tenancy/tenancy-check.sh` drives the two-broker mesh pair directly
with the trusted `x-queen-tenant` header and no proxy in the picture. Every
scenario gives two tenants the **same queue name, the same partition name and the
same consumer-group name**, and splits the traffic across both brokers so the mesh
frames and both brokers' caches are in play. It asserts that queue identity and
configuration are per-tenant when read back on either broker, that no message
crosses, that a foreign `partitionId` cannot advance another tenant's cursor,
that deduplication keys are per-tenant while within-tenant deduplication still
fires, that a shared consumer-group name keeps independent cursors, and that one
tenant's claim-and-ack traffic can neither hide nor delay the other's pending
message. That last one carries a latency budget rather than a bare delivery
assertion, because a shared ring would still deliver eventually through the
reseed floor and a delivery-only assertion would pass on the broken shape. It
runs on the `ha-tenanted` topology: `test/run.sh --suite tenancy`.

`proxy/scripts/isolation-smoke.sh` asks the same question end to end through the
proxy, against a dev cell with a second cluster as the adversary. It asserts
scoped listings and aggregates on **content** rather than on HTTP 200, foreign
partition-id rejection on every mutating route, trace-name isolation, cross-tenant
retention, api-key scopes, key and session revocation, key-to-cluster binding, the
blocked operator surfaces, the storage quota and the meters. Under shadow mode the
three enforcement checks are reported as counted skips and never as silent passes,
so the printed tally means the same thing whether `QUEEN_PROXY_ENFORCE` is on or
off.

`server/tests/streams_tenant_isolation.rs` plays the same adversarial shape against
the streaming engine specifically: two tenants and the default tenant all holding the
same query name and the same sink queue name, on one booted broker. It asserts both
halves of every claim in the streams section above, denial for the foreigner and no
side effect for the owner, including that a cycle aimed at a foreign shard writes
nothing and that a sink emit touches only the caller's same-named queue. It runs
`--ignored` against a disposable PostgreSQL, like the other `server/tests` suites.

A third gate covers the case nobody thinks to test: the tenancy flag changing
behaviour for a client that sends no header at all. `test/run.sh` runs each of its
client suites (`js`, `go`, `py`, `cli`, `cpp`, `rust-client`) against a flag-off
broker and again against a broker started with `QUEEN_TENANCY_HEADER=true` and no
header on the wire, and requires the same verdict from both. It compares exit
codes, and, where a suite prints a machine-readable tally, the pass counts too. A
divergence fails the run **even when the flag-on side is the green one**, because
a behaviour change in either direction is a regression.

[Running the suites](/internals/contributing/testing/) covers the topologies, the
runners and how to reproduce any of this locally.

## What isolation does not mean

Four things sit outside the guarantee, so nothing here is over-read:

- **Not resource isolation.** Tenants on a shared cell share one broker process and one
  PostgreSQL. The quotas bound each tenant's demand; they do not partition CPU, memory
  or disk. A cell is sized for its tenants, and a tenant that needs a guarantee needs a
  dedicated cell.
- **Not isolation from the operator.** A live operator is admin on every cluster on the
  cell, and anyone with pxdb access holds the cell secret. Isolation is between tenants,
  not between a tenant and whoever runs the fleet.
- **Not encryption between tenants.** Payload encryption is per queue with one key per
  broker process, so it protects against database access, not against another tenant,
  who cannot read those rows anyway.
- **Not a substitute for the header discipline.** `x-queen-tenant` is unauthenticated by
  design: [Broker-native tenancy](/reference/multi-tenant/broker-tenancy/) is the page
  that spells out what follows from that.
