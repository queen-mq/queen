Tenant isolation in Queen is split across two layers of the same process on purpose. The
broker scopes everything that is queue-shaped, natively, in its state machine, on every read
and every write. The embedded proxy is what makes the header that drives that scoping
trustworthy, and what refuses the surfaces the broker does not scope because they describe
the cell rather than a tenant.

Neither half is sufficient alone. A broker router reachable directly by a tenant has no
isolation at all, because the scoping key arrives in an unauthenticated header. A proxy
that sets no tenant header (`QUEEN_PROXY_TENANT_HEADER=false`) routes every tenant into the
same namespace.

## What the broker scopes natively

With tenancy on (`QUEEN_TENANCY_HEADER=true` on a broker router, and always on the router
behind the embedded proxy), queue identity becomes `(tenant, name)` rather than `name`. Two
tenants can both own a queue called `orders` and they are different queues, with different
partitions, different offsets, and different consumer-group cursors.

Queue reads take the tenant together with the name: a queue's configuration is keyed by
`(tenant, queue)` in the replicated store, and every partition row carries its tenant.

Every queue-shaped route passes the request's tenant to the state machine with its command.
That covers the whole queue-shaped surface: push, pop, ack, transactions, configure, seeks,
subscriptions, queue and namespace listings, per-queue analytics, consumer groups, message
and DLQ reads, trace reads, and the three streams routes (registration, state reads and the
cycle). The [route table in the reference](/reference) marks each one.

## The partition owner check

Some operations do not name a queue. They name a **partition id** (an ack, a message read,
a message delete, a trace lookup, a stream state read, a stream cycle). Scoping by name
cannot help there.

So the partition row itself decides. Every partition row in the replicated store carries
its tenant, and an operation that names a partition id resolves it only when that row's
tenant is the request's tenant:

- An ack item for another tenant's partition fails on its own with
  `partition <id> not owned by this tenant`; a transaction that contains one fails whole.
- A message read, a message delete or a trace lookup that names another tenant's partition
  finds nothing, the same answer a partition that does not exist gets.
- A stream state read or cycle aimed at another tenant's partition answers the same `404` a
  missing one gets.

With tenancy off every request is the default tenant, and every partition belongs to it.

## Tenant-keyed in-process state

Isolation would leak through in-process state if any of it were keyed by queue name alone.
It is keyed by tenant instead:

| State | Why the key matters |
| --- | --- |
| Long-poll wake gates, keyed by `(tenant, queue, group)` | A wake for one tenant's `orders` must not wake another's |
| Per-queue metric counters, keyed by `(tenant, queue)` | Otherwise two tenants' counters would merge |
| Parked-consumer gauges, keyed by `(tenant, queue)` | Same |

Every node applies the same committed log, so a tenant's queues, partitions and cursors are
the same on every node, and each node keys its own in-process state the same way.

## The surfaces that are not tenant-scoped

These exist, they are useful, and they describe the **cell**. None of them can be
scoped to a tenant, which is why the proxy classifies them as operator or blocked and
answers `404` to everything else. Read this list as the reason the gateway exists, not
as a set of holes.

| Surface | What it exposes |
| --- | --- |
| `GET /api/v1/status` | Cell-wide broker state across every tenant |
| `GET /api/v1/analytics/system-metrics` | Host CPU and memory of the machine the node runs on |
| `GET /api/v1/analytics/worker-metrics` | Process lifetime counters |
| `GET /metrics/prometheus` | Per-queue series labelled by queue name with **no tenant label** |
| `/api/v1/system/raft/membership` and the routes under it | The cell's raft membership. The broker also refuses a request that names a tenant with `403` |

One of those deserves the detail.

### Prometheus sums across tenants

The exposition format keeps one line per queue name, so the parked-long-poll gauge
(`queen_parked_long_polls`) is explicitly aggregated across tenants before it is written,
with a `queue` label and nothing else.

On a shared cell that endpoint therefore reveals every tenant's queue names. On the
embedded proxy's port, `/metrics` and `/metrics/prometheus` answer `404` unless the request
carries the control-plane token (`QUEEN_PROXY_CP_TOKEN`, in `x-queen-cp-token` or as
`Authorization: Bearer`). On a broker router, the internal port included, they are
classified `public` by the broker's own access-level table, so enabling JWT does not close
them. Scrape from the operator side only. Never expose them to a tenant.

## Streams are tenant-scoped

The streaming engine carries the same guarantees as the queue surface:

- **A query belongs to one tenant.** Queries are stored per tenant and a `name` is unique
  per tenant, so two tenants can both register `orders.per_customer_per_min` and neither
  can observe, update or reset the other's. The 409 a `config_hash` conflict returns can
  only ever name the caller's own query.
- **State reads and cycles pass the owner check.** Both routes address a partition by id,
  so they take the same check as acks and message reads: a foreign partition gets the same
  404 a missing one gets, and a foreign `query_id` reads as not found, never as an error
  that would confirm it exists.
- **Sink emits stay home.** Every sink queue the cycle resolves or lazily creates is the
  caller's own: the cycle's pushes carry the request tenant, exactly like push auto-create.
- **Registration is granted, not assumed.** With tenancy on, a tenant registers a new query
  only if the broker holds an enabled streams grant for it, and `maxQueries` (when set) is
  an exact cap. Absence is a denial: provisioning a streams-enabled tenant means writing
  that grant ([tenants, clusters and cells](/reference/multi-tenant/tenants/)).
  Re-registering an existing query is never gate-checked, so revoking the grant stops new
  queries without stranding a Runner that is still draining.
- **The tenant wipe covers it.** `DELETE /api/v1/resources/tenant` removes the tenant's
  queries, their state and its streams grant together with its queues, KV rows, timers and
  traces.

The default tenant is exempt from the grant and the cap, which is what keeps a
single-tenant broker with tenancy off working with no grant at all.

<Aside type="caution">
A tenant on a plan with `features.streams = true` still needs its streams grant on the
broker, or every new registration answers 403.
</Aside>

## Where the proxy is the boundary

Every isolation property above depends on the tenant header being right, and on the
broker being unreachable except through the thing that sets it:

<Steps>

1. **The client's credential never reaches the broker.** The proxy strips
   `Authorization`, and the broker router behind it runs with its own JWT off.

2. **The tenant header is set by the proxy**, from the cluster resolved out of the
   `Host` label (the cluster's `broker_tenant_uuid`, a value the tenant never sees and
   cannot choose). Any `x-queen-tenant` the client sent is dropped first.

3. **Blocked and operator classes never forward.** An unknown API-shaped path is `404`,
   not a pass-through, so a new broker route cannot become reachable by accident.

4. **The operator capability is gated per cell.** With
   `QUEEN_PROXY_OPERATOR_ENABLED=false`, the cell-wide routes have no code path at all,
   a structural guarantee rather than a permission check.

5. **The broker router is reachable only through the proxy.** With the embedded proxy on
   `PORT` it has no socket. With `QUEEN_PROXY_PORT` set to another port, `PORT` serves it
   directly and must stay off every network a tenant can reach. This is the assumption all
   four points above rest on.

</Steps>

## How these claims are tested

Every property on this page is asserted by a suite that plays one tenant against
another, on a running stack, rather than by reading the code.

`test/runners/tenancy/tenancy-check.sh` drives the brokers directly with the trusted
`x-queen-tenant` header and no proxy in the picture. Every scenario gives two tenants
the **same queue name, the same partition name and the same consumer-group name**, and
splits the traffic across two URLs: on the `tenanted` topology both are the single node,
on `ha-tenanted` they are two nodes of a three-node raft cluster, so the traffic crosses
nodes. It asserts that queue identity and configuration are per-tenant when read back
through either URL, that no message crosses, that a foreign `partitionId` cannot advance
another tenant's cursor, that deduplication keys are per-tenant while within-tenant
deduplication still fires, that listings are scoped, that a shared consumer-group name
keeps independent cursors, that one tenant's claim-and-ack traffic can neither hide nor
delay the other's pending message, and that a parked long-poll delivers nothing a foreign
tenant pushes. The claim-and-ack check carries a latency budget (3 seconds) rather than a
bare delivery assertion, because shared pop state could still deliver eventually through a
periodic rescan and a delivery-only assertion would pass on the broken shape.
`test/run.sh --suite tenancy` runs it on `tenanted`, and `test/run.sh --suite tenancy
--topo ha` on `ha-tenanted`.

`proxy/scripts/isolation-smoke.sh` asks the same question end to end through the
proxy, against a node with `QUEEN_PROXY_EMBEDDED=true`, provisioning a second cluster as
the adversary through the control plane. It asserts scoped listings and aggregates on
**content** rather than on HTTP 200, foreign partition-id rejection on every mutating
route, trace-name isolation, cross-tenant retention, api-key scopes, key and session
revocation, key-to-cluster binding, the blocked operator surfaces, the storage quota and
the meters. Under shadow mode the three enforcement checks are reported as counted skips
and never as silent passes, so the printed tally means the same thing whether
`QUEEN_PROXY_ENFORCE` is on or off.

A third gate covers the case nobody thinks to test: the tenancy flag changing
behaviour for a client that sends no header at all. `test/run.sh` runs each of its
client suites (`js`, `go`, `py`, `cli`, `cpp`, `laravel`, `rust-client`) against a flag-off
broker and again against a broker started with `QUEEN_TENANCY_HEADER=true` and no
header on the wire, and requires the same verdict from both. It compares exit
codes, and, where a suite prints a machine-readable tally, the pass counts too. A
divergence fails the run **even when the flag-on side is the green one**, because
a behaviour change in either direction is a regression.

[Running the suites](/internals/contributing/testing/) covers the topologies, the
runners and how to reproduce any of this locally.

## What isolation does not mean

Four things sit outside the guarantee, so nothing here is over-read:

- **Not resource isolation.** Tenants on a shared cell share the same broker processes and
  the same disks. The quotas bound each tenant's demand; they do not partition CPU, memory
  or disk. `QUEEN_RAFT_GROUPS` splits each node into several raft groups, each with its own
  log and leader, and a tenant lives in exactly one of them: that spreads the load, it does
  not reserve capacity. A cell is sized for its tenants, and a tenant that needs a
  guarantee needs a dedicated cell.
- **Not isolation from the operator.** A live operator is admin on every cluster on the
  cell, and whoever holds `QUEEN_PROXY_CP_TOKEN` can create tenants, clusters and API keys
  through the control plane. Isolation is between tenants, not between a tenant and
  whoever runs the fleet.
- **Not encryption between tenants.** Payload encryption is per queue with one key per
  broker process, so it protects the stored payloads, not against another tenant, who
  cannot read those messages anyway.
- **Not a substitute for the header discipline.** `x-queen-tenant` is unauthenticated by
  design: [Broker-native tenancy](/reference/multi-tenant/broker-tenancy/) is the page
  that spells out what follows from that.
