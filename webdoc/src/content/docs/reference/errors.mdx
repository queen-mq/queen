Broker failures come in two shapes. An error raised by the replicated state
machine carries a machine-readable `code` next to the message:

```json
{"error":"no leader is known; retry after","code":"no_leader"}
```

An error minted at the HTTP edge, before a command reaches the state machine
(authentication, the tenancy header, some request validation), is one JSON
object with one key:

```json
{"error":"invalid x-queen-tenant header (must be a UUID)"}
```

Content type is `application/json` in both cases. The message is JSON-escaped
while the structural quotes are preserved, so the body always parses. There is
no request id. Branch on the status code and, where it is present, on `code`;
treat `error` as text for a human or a log. The proxy adds a `code` to every
error it generates itself, described at the end of this page.

## 204 carries no body at all

A `204 No Content` response (an empty pop) is built with **no body at all**,
and the handler discards the body it would otherwise have sent. This is
deliberate. Announcing a content length on a body that the HTTP layer then
elides made strict HTTP/1.1 clients (Node's undici and llhttp) treat the
connection as poisoned and drop it, which under empty-poll load snowballed into
`ECONNRESET` storms.

Consequence for a client: branch on the status before parsing. A pop that
returns 204 has no `{"messages":[]}` to read.

## Status codes

| Code | When |
| --- | --- |
| `200` | Every successful read and management call; also acks, lease extension and completed transactions, including ones that rolled back (see below). |
| `201` | `POST /api/v1/push` (even for an empty item list, which returns `[]`) and a recorded trace. |
| `204` | A pop with no messages. |
| `400` | A body that is not valid JSON; a missing required field; a discovery pop with neither `namespace` nor `task`; a malformed `x-queen-tenant` header when tenancy is on; a request the state machine refuses as a client error, with the refusal's own `code` (for example `bad_request` or `bad_body`). |
| `401` | Authentication is enabled and the token is absent, unparseable, badly signed, expired, not yet valid, issued in the future, or carries a rejected issuer, audience, algorithm or key id. |
| `403` | A valid token whose roles do not satisfy the route's required level; a streams registration by a non-default tenant with no enabled streams grant or at its `max_queries` cap; a raft membership call that names a tenant. |
| `404` | Any unmatched path under `/api/` or `/streams/`, and any non-`GET`/`HEAD` request that reaches the dashboard fallback; a message, queue or trace that does not exist. |
| `409` | `POST /streams/v1/queries` with a `config_hash` that does not match the registered query, and no `reset`; a raft membership change the cluster refuses (the body's `code` says why). |
| `413` | A request body larger than `QUEEN_MAX_BODY_BYTES` (64 MiB by default); a queue, partition or consumer-group name too long for the store key (`name_too_long`). |
| `429` | A push or transaction that waited the whole admission hold without room (`overloaded`). See below. |
| `500` | An internal failure of the state machine (`internal`); a JWT configuration fault discovered per request, such as an `HS256` token with no configured secret or an unparseable public-key PEM. |
| `503` | No leader is known (`no_leader`); this node is not the leader and could not hand the request over (`retry`); the request deadline elapsed (`timeout`); `GET /health` while the node has no leader. |
| `504` | A raft membership change whose `timeoutMs` passed before it committed. It may still complete: read the membership before repeating it. |
| `507` | A write that would grow storage while the node's data directory is over the disk gate (`storage_full`). See below. |

### 503: retry it

A node answers `503` with `Retry-After: 1` when it cannot place a command in
the replicated log right now: an election is in progress, the cluster has lost
its quorum, the leader did not answer a forwarded request, or the request's
deadline passed. The body carries the `code` (`no_leader`, `retry`,
`timeout`), and a `retry` may carry a `leader` hint. Any node serves clients: a
write that reaches a follower is handed to the leader, so a client does not have
to find the leader itself. There is no local spooling: a request refused this way
was not accepted, and the client retries it, so a successful push always means
the message is in the log.

### 429: the push admission budget

A push or a transaction takes room from a byte budget at the HTTP edge, sized by
its `Content-Length`, before its body is read. When the budget is spent, a new
request **waits** for room, so a producer that sends faster than the node
commits slows down. Only a request that waited the whole hold is refused, with
`429`, `code` `overloaded` and a `Retry-After` between 1 and 5 seconds. The hold
is `QUEEN_RAFT_ADMIT_HOLD_MS` (default 15000 ms, jittered by 25 percent either
way) and the budget is `QUEEN_RAFT_ADMIT_MAX_MB` (default 64; `0` turns the
gate off). Pops and acks never take room from this budget. Per-tenant rate
limiting is the proxy's job, described below.

### 507: the disk gate

Writes that grow storage (pushes, transactions carrying pushes, KV puts and
increments, timer schedules, traces) are refused with `507` and `code`
`storage_full` once the filesystem holding the data directory is
`QUEEN_RAFT_DISK_HIGH_PCT` percent used (default 85). They are accepted again
once it is back under `QUEEN_RAFT_DISK_LOW_PCT` (default 80). Pops, acks and
deletes are still accepted, so consumers can drain. Size the volume for the
retention you configure.

## Responses that are not the generic envelope

<Aside type="caution">
A 2xx does not mean the operation succeeded. Push, ack and transaction all report
their real outcome inside the body of a 200 or a 201.
</Aside>

**Push** returns `201` with one object per submitted item:

```json
[{"index":0,"message_id":"019...","transaction_id":"t-1","queueName":"orders","status":"queued","offset":42}]
```

`status` is `queued` for an accepted message, with its `offset`; `duplicate`
when deduplication matched, and `message_id` and `offset` are then the original
message's; and `error` when the state machine refused that item's partition.
The 2.0 broker never answers `buffered` or `failed`: those meant a disk spool,
and there is none. A push that cannot be committed at all is not a `201`: it is
one of the `503`, `429` or `507` answers above.

**Ack** and **ack batch** always return `200` with one object per
acknowledgement:

```json
[{"index":0,"transactionId":"t-1","success":true,"error":null,"leaseReleased":true,"dlq":false,"noop":false}]
```

An ack that resolved to nothing is *reported*, not silently accepted:
`noop:true` for a duplicate commit, and `success:false` with an explanatory
`error` for one that is unresolvable, already committed or stale, or whose lease
is invalid or expired. See [Use Queen](/use) for what those mean for a consumer.

**Transaction** failures use their own envelope and arrive at HTTP `200`:

```json
{"transactionId":"019...","success":false,"reason":"kv_precondition","error":"...","results":[]}
```

A transaction is one entry in the replicated log: it applies whole or not at
all. `reason` is a machine-readable code, and it is the thing to branch on.

| `reason` | What rolled the bundle back |
| --- | --- |
| `bad_request` | The body was malformed, an operation was neither a push nor an ack, or no operation or rider was given. |
| `duplicate` | A pushed message was a duplicate. |
| `rejected_ack` | An ack in the bundle could not be applied: its message is not leased by this worker, was already acked, or could not be resolved. |
| `kv_precondition` | A `required` key/value gate lost. |

A validation failure of a rider carries that rider's own code instead (for
example `kv_bad_request`, `too_large` or `name_too_long`). `kv_precondition` is
the one to design around. A lost gate is the expected outcome of every
legitimate redelivery, which is the idempotency marker doing its job, so it
arrives at `200` and belongs in neither a retry policy nor an error metric. The
body carries `failedIndex`, `kvReason`, `version` and `value` alongside the
code, so the caller can see who won without a second round trip. See
[KV state](/use/kv/).

A transaction that cannot be committed at all (no leader, overload, disk gate)
is not a `200`: it gets the status and envelope of that failure.

**Lease extension** always returns `200`. A lease that does not exist, has
expired, or belongs to another tenant is reported as `{"renewed":0,...}` with
`success:false`. An unknown lease and a foreign lease are deliberately
indistinguishable.

**Queue deletion** returns `200` even when nothing was deleted, with
`deleted:false` and a `message` field saying the queue was not found. `DELETE`
is idempotent here because the SDKs use delete-before-create as a cleanup idiom.

**Health** returns its own document at both `200` and `503`:
`{"status":"healthy","engine":"raft","version":"…","raft":{...}}` while a leader
is known, `"status":"settling"` with `503` otherwise. There is no `error` key to
read.

**Unknown API routes** return `404` with `"code":"no_such_route"`. This exists
because the dashboard fallback matches any method, so a call to an endpoint that
does not exist used to come back as `200 text/html`, which every JSON client
reads as success.

**413** for an oversized body is produced by the body-limit layer before any
handler runs, so it does not pass through the helper that builds every other
error body. Do not expect the `{"error":...}` shape there.

## Authentication and authorization errors

With `JWT_ENABLED=false` (the default) the middleware is a pass-through and
neither code occurs from it. The streams registration denial below is the one 403
minted outside the middleware for a tenant, so it exists with authentication off
too, though only for a non-default tenant, which in practice means behind a
proxy.

`401` bodies carry a fixed short message: `Authentication required`,
`Bad token header`, `Invalid token signature`, `Token has expired`,
`Token not yet valid`, `Token issued in the future`, `Invalid token issuer`,
`Invalid token audience`, `Unsupported token algorithm`, `Unknown key ID`.

A role-check `403` is always `{"error":"Insufficient permissions"}`. The route's
required level is compared against the token's role *set*, not a numeric ladder, and
`WriteOnly` is not below `ReadOnly`: a write-only role passes `POST /api/v1/push`
and is rejected with 403 on every read and consume route, including pop and ack.
The streams registration denial carries `denied: true` and an error naming the
missing grant or the cap ([streams routes](/reference/http/streams)).

Three endpoints can never return either code: `/health`, `/metrics` and
`/metrics/prometheus` are `public` in the route table, and the level check
short-circuits before any token is examined. The dashboard's own root and asset
paths are public for the same reason.

## Behind the proxy

The proxy (embedded in the broker process with `QUEEN_PROXY_EMBEDDED=true`)
wraps the same routes and adds a machine-readable `code` to every error it
generates itself:

```json
{"error":"request rate limit exceeded","code":"rate_limited"}
```

The codes are a stable contract that clients switch on: `unauthorized`,
`forbidden`, `rate_limited`, `quota_exceeded`, `storage_quota_exceeded`,
`cluster_suspended`, `push_blocked`, `feature_gated`, `route_blocked`,
`cluster_unknown`, `scope_unknown`, `payload_too_large`, `invalid_request`,
`bad_gateway`, `upstream_timeout`.

### The 429 contract

A `429` from the proxy always carries a `Retry-After` header in **seconds**. On
the data plane it has one of three causes:

| Cause | `code` | `Retry-After` |
| --- | --- | --- |
| Request rate limit (per-cluster token bucket) | `rate_limited` | Time to refill the deficit, computed from the plan's sustained rate, clamped to 1–60 s |
| Message rate limit (push and transaction items) | `rate_limited` | Same computation |
| Too many parked consumers (a `wait=true` pop over the cell or cluster cap) | `rate_limited` | 5 s |

A denied request never debits the bucket, so a client that backs off correctly is
not punished for having been throttled.

`403` with `quota_exceeded`, `storage_quota_exceeded` or `push_blocked` is the
other family a producer must handle: those are not retryable on a timescale that
backoff can fix. Note that those three reach the two dead-letter replay routes as
well, because a replay writes a message. `404` with `route_blocked` means the
route is not exposed to tenant credentials at all, and `400` with
`invalid_request` is the proxy refusing a body it read and understood: today the
one data-plane case is a replay whose destination names one half of a
`(queue, partition)` pair, where the message names the half to add. See
[the endpoints a tenant can reach](/reference/multi-tenant/endpoints/).

### What the clients do with a 429

Every SDK retries `429` in place, against the same backend and never via
failover (a 429 is a quota signal, not a health signal), and treats no other
status as retryable at that layer. That covers the proxy's `429` and the
broker's own `overloaded` alike:

- ordinary requests: up to **10 attempts**;
- long-poll pops: **unbounded** by default, because the loop is meant to keep
  waiting through transient throttling;
- delay: `Retry-After` when present, otherwise exponential backoff from 500 ms
  capped at 30 s;
- either way jittered ±20 % so a fleet does not resynchronise into a herd.

Each SDK exposes a `retry429` option carrying `maxAttempts`, `baseMs` and
`capMs` (spelled per language convention) that overrides all of it, and setting
`maxAttempts` explicitly applies it to pops too. Setting `maxAttempts` to `1`
disables retrying and surfaces the 429 to your code, which is what a load
generator wants and an application usually does not.
