The crates.io package is `queen-engine`; the library imports as `queen`. The public surface
is `queen::Broker`, `queen::BrokerConfig`, the two error enums, `queen::DeleteQueueResult`
(the one response type not in the protocol crate), the `queen::VERSION` const, and
`queen::protocol` (a re-export of `queen-protocol`, so every other request and response
type below is the same type the Rust client uses). Everything else in the crate is private
and carries no stability promise. The whole surface is **beta**: the HTTP API is the stable
contract, this one can still change between releases.

Every operation calls the same handler function the HTTP router dispatches to and parses
the rendered response back into the protocol types, so semantics match the
[HTTP reference](/reference/http) route by route. Where an HTTP status carried the meaning,
the mapping is stated in the notes below.

## BrokerConfig

<Render file="snippets/embedded-start" />

The embedded broker runs the replicated state machine on a single node, durable in the
data directory it is given. There is no database to connect to. Unset fields fall back to
the same environment variables the binary reads, so an embedded broker in a container
behaves like the image; a set field wins over env.

| Builder | Env fallback | Default | Meaning |
| --- | --- | --- | --- |
| `raft(dir)` | `QUEEN_RAFT_DIR` | none: one of the two is required | The data directory. The binary's default, `/var/lib/queen/raft`, is not used implicitly, because two embedded applications on one host must never share a directory. Never open one data directory from two brokers at once. With neither set, `Broker::start` returns `StartError::Config`. |
| `raft_disk_pct(high, low)` | `QUEEN_RAFT_DISK_HIGH_PCT`, `QUEEN_RAFT_DISK_LOW_PCT` | 85, 80 | The disk gate: writes that grow storage are refused (HTTP 507) once the data directory's filesystem is `high` percent used, and accepted again below `low`. A value outside 1 to 100 is a `StartError::Config`, not a silent default, because a fraction such as `0.85` would refuse every write. |
| `stmt_timeout_ms(ms)` | `QUEEN_STMT_TIMEOUT_MS` | 30000 | The deadline of an ack, a transaction and a lease extension. |

`QUEEN_*` tuning knobs are honoured like the binary's, with the HTTP-only ones inert.
Two are deliberately ignored and log a warning if set: `QUEEN_TENANCY_HEADER` (embedded is
single-tenant by construction) and `JWT_ENABLED` (there is no HTTP surface; the in-process
caller is trusted). `QUEEN_MAX_BODY_BYTES` has no embedded equivalent: there is no request
body to cap. A malformed boolean env value makes the binary exit; `Broker::start` returns
`StartError::Config` instead.

`Broker::start` must run inside a Tokio runtime: the engine spawns its background work on
the ambient runtime. It installs a panic hook, chained to the host's, that aborts the
process when one of the engine's core threads panics (planner, log writer, apply,
checkpoint, openraft); the data directory is replayed on the next start. Every other panic,
including the host's own, unwinds as before. Logging goes through `tracing`: install your
own subscriber, the library never does.

## Broker

`Broker` is `Clone` (one shared engine per clone). All operations take `&self`. Types named
below live in `queen::protocol`, except `DeleteQueueResult`, which the crate defines itself.

### Data plane

| Method | Returns | Notes |
| --- | --- | --- |
| `push(Vec<PushItem>)` | `Vec<PushResult>` | Per-item outcomes in request order (`queued`, `duplicate` or `error`); a partial failure is not an `Err`. |
| `pop(queue, &PopParams)` | `PopResponse` | Wildcard pop. An empty claim (HTTP 204) is an empty response, not an error. `wait: true` parks on the in-process waker up to `timeout_millis`. |
| `pop_partition(queue, partition, &PopParams)` | `PopResponse` | One named partition. |
| `pop_discover(&PopParams)` | `PopResponse` | Namespace or task discovery; at least one of `namespace` and `task` is required, else `Error::InvalidRequest`. |
| `ack(&AckRequest)` | `AckResult` | A rejected ack (expired lease, unknown message) is `Ok` with `success: false`, as over HTTP. `Err` means the request was malformed. |
| `ack_batch(&AckBatchRequest)` | `Vec<AckResult>` | One consumer group per batch; per-item outcomes in order. |
| `renew_lease(lease_id, seconds)` | `RenewLeaseResponse` | Best effort: an unknown or expired lease is `success: false`, not an `Err`. |
| `transaction(&TransactionRequest)` | `TransactionResponse` | Atomic ack plus push, with the request's `kv` and `timers` riders in the same entry of the log. A rollback is `Ok` with `success: false`, its code in `reason` and the text in `error`. |

### Queues and DLQ

| Method | Returns | Notes |
| --- | --- | --- |
| `configure(&ConfigureRequest)` | `ConfigureResponse` | Create or reconfigure a queue. Merges by default: an option the request does not carry keeps the queue's stored value. `ConfigureRequest::replace(true)` sends `mode: "replace"` and resets everything the request omits. An in-body error is promoted to `Err`. |
| `delete_queue(name)` | `DeleteQueueResult` | Idempotent: a missing queue is `existed: false`, not an error. |
| `dlq(&DlqParams)` | `DlqResponse` | Dead-lettered messages, filtered by queue, group, limit, offset. |
| `dlq_replay(dlq_id, Option<queue>, Option<partition>)` | `serde_json::Value` | The preferred replay: **moves** the dead-letter row named by its `id` back into the log, the push and the row's deletion in one entry, optionally to a different destination. Read `result`: `moved` wrote the message and removed the row, `duplicate` wrote nothing and kept it. |
| `retry_message(partition_id, transaction_id)` | `serde_json::Value` | The same move addressed by `(partitionId, transactionId)`. An address can carry one dead-letter row per consumer group, so prefer `dlq_replay`, whose row id names exactly one record. |
| `delete_message(partition_id, transaction_id)` | `serde_json::Value` | Deletes the dead-letter rows at that address. It cannot remove a live message from the log. |

### Ephemeral queues

`ephemeral_push`, `ephemeral_pop`, `ephemeral_ack`, `ephemeral_configure`,
`ephemeral_reset`, `ephemeral_delete`, `ephemeral_queues` and `ephemeral_depth` call the
`/api/v1/ephemeral/*` handlers. They take and return `serde_json::Value`, with the
request and response bodies of the [ephemeral routes](/reference/http/ephemeral).

### Observability and lifecycle

| Method | Returns | Notes |
| --- | --- | --- |
| `metrics()` | `serde_json::Value` | The `/metrics` document: uptime, request and message counts, resident memory, `"engine": "raft"` and the `raft` block. |
| `prometheus()` | `String` | The `/metrics/prometheus` exposition, including the `queen_raft_*` families. |
| `health()` | `serde_json::Value` | The `/health` document. `status` is `healthy` (HTTP 200) while a leader is known and the apply lag is under `QUEEN_RAFT_READY_LAG_MS`, and `settling` (HTTP 503) otherwise. Both parse: read `status` from the document. |

`shutdown()` hands leadership off (a no-op on a single node) and aborts the loops the
handle owns. It returns nothing.

## Errors

```rust
pub enum StartError { Config(String) }

pub enum Error {
    InvalidRequest(String),
    NotFound(String),
    Broker { status: Option<u16>, message: String },
    Decode(String),
}
```

`StartError::Config` is what `Broker::start` returns for a configuration it refuses: no
data directory, a malformed boolean env value, or a disk percentage outside 1 to 100.

`Error::status()` exposes the HTTP code behind the mapping. `InvalidRequest` and `NotFound`
are terminal; a `Broker` error with a 5xx status is usually transient (overload, no leader
yet) and worth a retry with backoff, while a `Broker` error with `status: None` is a
semantic failure reported inside a 200 body (a failed pop, a configure error). `Decode`
means the broker's rendered bytes did not parse into the protocol type, which the
conformance and end-to-end tests exist to prevent; treat it as a bug.

## Not present

Consumer-group administration (list, details, lagging, seek, delete), queue and message
listings, traces, the streams runner endpoints and the standalone identity routes have no
embedded equivalent in the beta. Nor do the key/value
and timer routes: there is no `kv` method and no `timers` method, only the `kv` and
`timers` riders on `TransactionRequest`, which commit in the same log entry as the bundle.
The dashboard is not served (build with `default-features = false`; the `server` feature
exists for the binary).
