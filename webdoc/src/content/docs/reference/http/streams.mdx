The whole streaming engine is three JSON POSTs. `/streams/v1` sits inside the versioned contract
alongside `/api/v1` (see [compatibility](/reference/compatibility)), so these routes are a public
protocol rather than an SDK's private wire: a language with no Queen streams SDK can run a complete
streaming worker by registering a query, reading its state, and committing cycles.

| Route | Access level | What it does |
| --- | --- | --- |
| `POST /streams/v1/queries` | read-write | Registers or re-registers a query by name, returns its `query_id` |
| `POST /streams/v1/state/get` | read-only | Reads the state rows for one query and one partition |
| `POST /streams/v1/cycle` | read-write | Commits state writes, sink pushes and the source ack as one entry in the replicated log |

All three are tenant-scoped. A query `name` is unique per tenant, not global, so the same name
under two tenants is two independent queries; state reads and cycles answer `404` for a partition
or query that is not the caller's, and the cycle resolves and auto-creates its sink queues under the
request tenant. On a broker with tenancy off everything lands on the default tenant and none of
this is observable. See [the model](/use/streams) for what a worker does between these calls, and
[Isolation](/reference/multi-tenant/isolation/#streams-are-tenant-scoped) for the guarantees.

## POST /streams/v1/queries

Registration is idempotent on `name`, and it is where a changed operator chain is caught. The node
answers after a read barrier, so it sees every registration the cluster had committed when the call
began.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `name` | string | yes | The query's identity within the tenant. This is the SDK's `queryId` |
| `source_queue` | string | yes | The queue the worker pops from |
| `sink_queue` | string | no | The queue closed windows are pushed to, stored as sent |
| `config_hash` | string | yes | A hash the client computes over the operator chain |
| `reset` | boolean | no, default `false` | Delete every state row for this query when `config_hash` has changed |

A missing or empty `name`, `source_queue` or `config_hash` answers **400** with code
`bad_request`, and nothing is written.

Four outcomes:

- **The name is new.** The query is registered and the response carries `fresh: true`.
- **The name is new but the tenant may not register it.** A tenant other than the default one
  needs an enabled streams grant: a quota of kind `streams`, written with
  `POST /api/v1/system/quota`, whose `maxQueries`, when set, is an exact cap on the tenant's
  registered queries. No grant, a disabled one, or a full cap is **HTTP 403** with `success: false`,
  `denied: true` and an error that says whether the tenant is not granted or at its cap. Nothing is
  written. This is distinct from the 409 below
  on purpose: retrying a 409 with `reset: true` is the documented fix, and retrying a 403 that way
  fixes nothing. The gate applies to **new names only**: re-registering an existing query, hash
  match or `reset` alike, always passes, so revoking a grant stops new queries without stranding a
  Runner that is still draining. The default tenant needs no grant.
- **The name exists and `config_hash` matches.** `source_queue` and `sink_queue` are updated to the
  supplied values and the accumulators are kept. `fresh` is `false`, and so is `reset`, even when
  the request sent `reset: true`.
- **The name exists and `config_hash` differs.** With `reset` absent or `false` this is **HTTP
  409**, with `success: false`, the `query_id` and an error naming the mismatch. With `reset: true`
  the broker deletes every state row of the query and stores the new registration in one entry of
  the replicated log, and answers 200 with `reset: true`. Names are per-tenant, so the query this
  resolves, and the `query_id` the 409 reveals, can only ever be the caller's own.

A 200 body carries the identity every later call uses. `query_id` is that value; the name never
appears on the wire again.

```json
{
  "success": true,
  "query_id": "0193f0c4-1a2b-7c3d-8e4f-5a6b7c8d9e0f",
  "name": "orders.per_minute",
  "config_hash": "9f2c…",
  "fresh": false,
  "reset": false
}
```

<Aside type="caution">
`reset: true` on a changed hash deletes the accumulators, not just the registration. Every open
window for that query is gone, and the next cycle starts folding from an empty state while the
source cursor stays where it was. It is the right answer to the 409 and the wrong answer to a
transient startup failure.
</Aside>

The 409 exists because old accumulators and a new fold shape do not mix: a chain that used to sum
and now averages would read the old value as if it meant the new thing. See
[status codes](/reference/errors) for the other statuses the broker emits.

## POST /streams/v1/state/get

Read-only, and the only way to see a window before it closes. Closed windows are ordinary messages
on the sink queue and need nothing from this route. The node answers after a read barrier, so it
sees every cycle the cluster had committed when the read began.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `query_id` | uuid string | yes | From registration |
| `partition_id` | uuid string | yes | The source partition whose state shard you want |
| `keys` | string array | no | Exact keys. Absent, `null` or `[]` all mean no key filter |
| `key_prefix` | string | no | Returns keys beginning with this string. An empty string is treated as absent |
| `ripe_at_or_before` | integer | no | Epoch milliseconds. Returns only rows whose `value.windowEnd` is an integer at or before it |

The filters are ANDed, so `keys` and `key_prefix` together mean both must hold. The response is
`{"success": true, "rows": [{"key": "…", "value": {…}, "updated_at": "…"}]}`, ordered by `key` in
byte order. **A key that does not exist is absent from `rows`, not present with a null value.**

`ripe_at_or_before` is what an idle-flush timer uses: ask for the windows that are already due on a
partition that has stopped receiving, emit them, and delete their rows in the same cycle. A state
row whose `value` has no integer `windowEnd` can never match that filter.

A missing `query_id` or `partition_id`, or a `query_id` that is not a UUID, answers **400** with
code `bad_request`. A `query_id` or `partition_id` that does not exist, or belongs to another
tenant, answers **404** `{"error":"not found"}`: the same answer either way, so neither address can
be probed for another tenant's existence.

<Aside type="note">
No SDK exposes the full filter set. `getState` is an internal module in JavaScript and Rust, and
Go's `runtime.GetState` takes explicit keys only. Prefix and ripeness reads are available over HTTP
and nowhere else, which is the practical reason to treat this as a route rather than a client
feature.
</Aside>

## POST /streams/v1/cycle

One call, one entry in the replicated log: the state writes, the sink pushes and the source ack
commit together or not at all. This is the route the [exactly-once argument](/use/streams) rests on.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `query_id` | uuid string | yes | 400 if absent or not a UUID |
| `partition_id` | uuid string | yes | The source partition. 400 if absent or empty |
| `consumer_group` | string | no | Defaults to `__QUEUE_MODE__` when absent or empty. The SDKs send `streams.<queryId>` |
| `state_ops` | array | no, default `[]` | Applied in order, scoped to this query and partition |
| `push_items` | array | no, default `[]` | Sink messages |
| `ack` | object or `null` | no | The source ack. `null` is an idle-flush cycle: state ops and sink pushes only, no cursor movement |
| `release_lease` | boolean | no, default `true` | `false` retains the source lease on the un-acked tail |

The two arrays and the ack have fixed element shapes. A state `key` is an opaque string to this
route; the SDKs compose it from the operator tag, the window key and the user key joined by
`U+001F`, which is what makes a `key_prefix` read return exactly one operator's windows.

```json
{
  "state_ops": [
    {"type": "upsert", "key": "tumb:60\u001f2026-08-17T10:01:00.000Z\u001facme", "value": {"acc": 41}},
    {"type": "delete", "key": "tumb:60\u001f2026-08-17T10:00:00.000Z\u001facme"}
  ],
  "push_items": [
    {"queue": "orders.per_minute", "partition": "Default", "payload": {"count": 41}}
  ],
  "ack": {"leaseId": "…", "status": "completed", "count": 50}
}
```

A state op whose `type` is `delete` deletes its key; any other `type`, or none, writes its `value`
under its key. An op without a string `key` is skipped. `state_ops_applied` in the response counts
the ops that had a key.

In a `push_items` element, `partition` defaults to `Default` and `payload` may also be sent as
`data`. An item with an empty `queue` is skipped rather than rejected. You may supply `messageId`
and `transactionId`, and the broker mints a UUIDv7 message id and reuses it as the transaction id
when you do not. Sink queues resolve within the request tenant, and one that does not exist yet is
auto-created under it, exactly like push auto-create. A sink item whose `transactionId` is already
in the sink partition's deduplication window refuses the whole cycle (`reason: "duplicate"`).

`leaseId` is the worker id the pop returned, and it is the exactly-once guard: with it, the cycle is
refused whole when the source lease is held by another worker or has expired (`reason:
"bad_lease"`), which rolls the sink pushes and the state ops back with it. Without a `leaseId` the
lease is not checked. `status` counts as success for `completed`, `success`, `acked`, `ok` and for
an absent field, in any letter case; **anything else, including a misspelling, is a nack** and
redelivers the batch.

### What the ack does to the cursor

| `status` | `release_lease` | Effect |
| --- | --- | --- |
| ok | `true` | The committed position jumps to the end of the leased batch, the lease and the retry state are cleared, and the consumed total grows by `count`. Identical to an ordinary ack of the whole leased batch |
| ok | `false` | The committed position advances by exactly `count` offsets from the first un-acked offset of the leased batch, never past its end, and the lease is **retained**. This is the gate partial ack |
| not ok | either | The lease is released and the cursor is untouched, so the whole batch redelivers. The reported `count` is 0 |
| `ack: null` | either | The lease block is skipped entirely |

An ok ack refuses the cycle (`reason: "no_batch"`) when the group's cursor on the partition holds
no leased batch. A group that has never popped the partition has no cursor there, and its ack does
nothing while the rest of the cycle commits.

### The response

A cycle that reaches the state machine answers **HTTP 200** whether it committed or was refused,
so a client must read the body rather than the status line.

```json
{
  "success": true,
  "query_id": "0193f0c4-...",
  "partition_id": "0193f0c5-...",
  "queueName": "orders",
  "state_ops_applied": 2,
  "push_results": [
    {"queueName": "orders.per_minute", "messageId": "0193f0c6-...", "transactionId": "0193f0c6-...", "status": "created"}
  ],
  "ack_result": {"success": true, "count": 50, "lease_released": true, "dlq": false}
}
```

`push_results` has one element per sink item that was not skipped. `ack_result` is `null` for an
idle-flush cycle.

A refused cycle comes back as `{"success": false, "error": "…", "reason": "…"}`, and nothing in it
was written: no state op, no sink message, no cursor movement. The `reason` values above
(`bad_lease`, `no_batch`, `duplicate`) are the ones a worker meets in normal operation.

A status other than 200 means the cycle did not reach a verdict: `400` for a malformed request,
`404` `{"success": false, "error": "query or partition not found"}` for a query or partition that
is not the caller's, `413` `name_too_long` for a sink queue or partition name the store cannot
hold, and the broker's common `503` (with `Retry-After: 1`) and `507` answers, described in
[HTTP API conventions](/reference/http/). After a `503` with code `timeout` the outcome is
unknown: the entry may have committed.

<Aside type="caution">
`"success": false` arrives with a 200. A client that checks only the status code will treat a
rolled-back cycle as a committed one, re-pop the same batch after the lease expires, and never
notice it is looping.
</Aside>

## What the broker adds on this route

Each sink item is framed and hashed by the broker and planned by the same push planner
[`POST /api/v1/push`](/reference/http/push) uses, inside the cycle's entry, so offsets,
deduplication and queue auto-creation behave as they do for a push. Stream output is not a second
class of message: a consumer of the sink queue pops it like any pushed message, and a consumer
parked on that queue is woken by it.

Sink payloads are not encrypted: a 2.0 broker stores them in cleartext even when the sink queue has
`encryptionEnabled`. See [payload encryption](/reference/security/encryption/).
