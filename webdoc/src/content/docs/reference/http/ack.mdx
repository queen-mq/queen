An acknowledgement is not a per-message delete. Consumption state is one cursor per
`(partition, consumer group)`, and an ack **commits that cursor**. Acking message N therefore
implicitly completes every earlier unacked message in the same partition for the same group:
"ack the last message of the batch" completes the batch. There is no per-message delivery state
to store, clean up or leak.

On the wire an ack is addressed by `transactionId`, which the broker resolves to an offset
through the partition's transaction index. Both routes have access level **read-write** and both
answer a processed call with `200` and a top-level array, one element per request item, in
request order.

## Request

### Single

`POST /api/v1/ack`

```json
{
  "transactionId": "order-8891-created",
  "partitionId": "17",
  "consumerGroup": "billing",
  "leaseId": "0198f2c1-9a7b-7d20-8e31-4c5d6e7f8a90",
  "status": "completed"
}
```

| Field | Type | Required | Default |
| --- | --- | --- | --- |
| `transactionId` | string | in practice yes | empty string, which resolves to nothing |
| `partitionId` | string | yes | empty string, which fails as `partitionId is not a partition id` |
| `status` | string | no | `completed` |
| `consumerGroup` | string | no | `__QUEUE_MODE__` |
| `leaseId` | string | no | empty, meaning a lease-less ack |
| `error` | string | no | absent |

`partitionId` is the value the pop returned with the message: the partition's numeric id written
as a decimal string, not a UUID. Send it back exactly as you received it.

### Batch

`POST /api/v1/ack/batch`

```json
{
  "consumerGroup": "billing",
  "acknowledgments": [
    { "transactionId": "order-8891-created", "partitionId": "17", "status": "completed", "leaseId": "0198…8a90" },
    { "transactionId": "order-8892-created", "partitionId": "17", "status": "failed", "leaseId": "0198…8a90", "error": "downstream 502" }
  ]
}
```

The array key is `acknowledgments` (American spelling, no `e` after the `g`). `consumerGroup` is
top-level only; per-item `consumerGroup` is not read. Each item carries its own `partitionId`,
`status`, `leaseId` and `error`. Both routes read both shapes: a body whose `acknowledgments`
array is not empty is a batch, and anything else is read as a single ack.

`error` is the failure reason. It is not stored for a plain nack; it is recorded on the
dead-letter record if this nack is the one that dead-letters the message. When several nacks in
one `(partition, lease)` group carry reasons, the one whose `transactionId` matches the poison
message wins, then the first available reason, then the default `Retries exhausted`.

### Status values

The broker lowercases `status` and then matches it:

| You send | Treated as |
| --- | --- |
| absent or `null` | `completed` |
| `failed`, in any case | `failed` |
| `retry`, in any case | `retry` |
| `dlq`, in any case | `dlq` |
| **anything else**, including `completed`, `success`, `acked`, `ok`, `""`, `nack` | `completed` |

There is no validation error for an unrecognised status. It silently becomes a completion,
which commits the message and everything before it: a handler that means to reject a message
must send `failed`, `retry` or `dlq`, never `nack`.

<Aside type="caution">
A 1.x broker read an unrecognised `status` as `failed`. The 2.0 broker reads it as `completed`.
Code that nacks with any spelling other than `failed`, `retry` or `dlq` completes the message on
2.0.
</Aside>

### Leases are optional, and that has teeth

- With a `leaseId`, the ack is validated against the live lease: a mismatched, expired or
  already-released lease is refused with `invalid or expired lease` for every item of that
  `(partition, lease)` group, and the cursor does not move.
- Without a `leaseId`, validation is skipped and the cursor advances anyway. That is what makes a
  post-expiry ack succeed, and it also means a lease-less ack can advance a cursor while another
  worker holds the batch. Send the `leaseId` you popped with unless you specifically want the
  unvalidated behaviour.

Items are grouped by `(partitionId, leaseId)`, and each group is judged on its own: a refused
group does not affect the others. All groups of one call travel to the leader as one command.

## Response

`200 OK`, a top-level array:

```json
[
  {
    "index": 0,
    "transactionId": "order-8891-created",
    "success": true,
    "error": null,
    "leaseReleased": true,
    "dlq": false,
    "noop": false
  }
]
```

| Field | Type | Meaning |
| --- | --- | --- |
| `index` | integer | the item's position in the request |
| `transactionId` | string | echoed back, so you can map results without relying on order alone |
| `success` | boolean | the broker **carried out the instruction you sent** (see below) |
| `error` | string or `null` | why this item was refused |
| `leaseReleased` | boolean | this ack ended the lease on that `(partition, group)`; the partition is claimable again |
| `dlq` | boolean | this item carried `failed` or `dlq`, and its `(partition, lease)` group filed a dead-letter record |
| `noop` | boolean | the ack was a harmless duplicate: it resolved at or below the committed cursor and changed nothing |

<Aside type="caution">
`success: true` means "instruction executed", not "message completed". A `failed` nack that was
processed correctly returns `success: true` with `leaseReleased: true`. The broker did exactly
what you asked, which was to *not* complete the message. Read `status` from your own request to
know what the outcome was, and `dlq` to know whether it was dead-lettered.
</Aside>

The response does not carry the new cursor value, the remaining retry budget, or how many
messages were implicitly completed.

## What each status does

Assume a batch was delivered as offsets 10–19 with the cursor at 9.

### completed

The cursor advances to the highest completed offset in the call, and every unacked offset below
it is completed too. If the cursor reaches the leased batch's end, the lease is released and the
retry state is reset (`leaseReleased: true`); if it does not, the lease is **kept** so you can
ack the rest of the batch.

### failed

An explicit failure. The cursor is clamped below the failed offset, so the failed message
and everything after it in the batch redelivers. Then:

| Retry budget | Queue's DLQ setting | Outcome |
| --- | --- | --- |
| remaining | any | the counter is charged once, the lease is released, and the tail redelivers |
| exhausted | DLQ enabled (**the default**) | the message is dead-lettered: a record is filed with your `error` as the reason, the cursor moves past it, the lease is released (`dlq: true`) |
| exhausted | DLQ disabled | the poison message is **dropped**: the cursor advances past it, the counter resets, the lease is released, and `dlq` stays `false`. The message is gone and nothing recorded it |

Dead-lettering is disabled only when **both** `deadLetterQueue` and `dlqAfterMaxRetries` are
explicitly `false` on the queue; either one left at its default keeps it on. An unconfigured
queue dead-letters.

The budget is `retryLimit`, default **3**, counted per `(partition, group)` and reset when a
batch completes. With the default of 3, three `failed` acks each release the batch to
redeliver, and the fourth dead-letters the message. The budget is charged **only** by an
explicit `failed` ack. A lease that merely expires redelivers without consuming any of it, so a
crash-looping consumer never exhausts a budget by crashing, only by nacking.

### retry

A budget-free retry. The lease is released, the cursor sits at the completed prefix, the retry
counter is **untouched**, and the tail redelivers. Use it for "not my turn yet" conditions
(a missing dependency, a rate-limited downstream) that should not count against the message's
life.

### dlq

Immediate dead-letter, bypassing whatever budget is left. The cursor advances over the completed
prefix, the poison message's id and payload are filed as a dead-letter record in the same log
entry, the cursor then moves past it and the lease is released. `dlq: true`.

`failed`, `retry` and `dlq` act on the group's leased batch on that partition. A lease-less
signal sent while no batch is leased there (after an ack or a nack released it) has nothing to
act on; the table under [Acks that cannot do anything](#acks-that-cannot-do-anything) says what
comes back.

### Explicit signals are never skipped

In one ack call:

- The cursor is clamped at the **lowest** explicit `failed`/`retry`/`dlq` position, even when a
  *later* offset in the same call was acked `completed`. Those later completed messages
  redeliver. At-least-once duplicates are acceptable; a silently swallowed nack is not.
- At the same offset the precedence is `dlq` > `failed` > `retry`.
- Only *silent gaps* (offsets you did not mention at all, below the highest completed one) are
  implicitly completed.

So a handler that acks messages individually and then fails one does not need to withdraw the
earlier acks: the failure wins from its own offset onward.

## Acks that cannot do anything

An ack can arrive too late or address something the broker cannot resolve:

| Situation | Result |
| --- | --- |
| `completed` ack that resolves at or below the cursor | `success: true`, `noop: true` (a duplicate commit, harmless) |
| `failed`, `retry` or `dlq` that resolves at or below the cursor | `success: false`, `error: "transaction is unresolvable, already committed, or acknowledgment is stale"`. The signal can no longer be honoured, and pretending otherwise would lose the nack |
| a `transactionId` that resolves nowhere: never pushed to that partition, or its index entry has been removed | `success: false`, the same error |
| a `transactionId` that exists in the partition but sits **above the leased batch's end** | `success: false`, the same error. While the group holds a leased batch on the partition, resolution is bounded to that batch |
| a `leaseId` that is not the live lease | `success: false`, `error: "invalid or expired lease"`, for every item of that `(partition, lease)` group |
| a lease-less `failed`, `retry` or `dlq` that resolves above the cursor while the group holds no leased batch on that partition | `success: true`, and the signal changes nothing: it acts only on a leased batch. The message is delivered again by the next pop |

The three rows that share one error string are the ones to design against: the string does not
say which mistake it was.

The index-removal case is a retention question. The index that resolves a `transactionId`
outlives its message: an entry is removed only once retention has removed the message and the
message is older than the larger of the queue's `dedupWindowSeconds`, its
`completedRetentionSeconds` and 900 seconds. An ack that arrives after that finds nothing to
resolve and changes nothing, and if it was a nack it charged nothing and dead-lettered nothing.
Ack while your lease is alive, extending it if you need to.

The out-of-batch case is an addressing problem. A pop hands out the inclusive span
`(committed, batch_end]`, and while the group holds a leased batch on the partition the broker
resolves acked ids only within that span, whether or not the ack carries a `leaseId`. A
`transactionId` for an offset above the batch is therefore reported as unresolvable rather than
accepted, which is what acking a message your lease did not deliver looks like: an id kept from
an earlier batch, or one that belongs to another worker's batch. With no batch leased on the
partition, resolution runs up to the partition's tail. That bounded scan, and how a
`transactionId` becomes an offset at all, are in [Ack internals](/internals/ack-internals).

### Error strings you can encounter

| `error` | Meaning |
| --- | --- |
| `invalid or expired lease` | a `leaseId` was supplied and it is not the live lease, including when the group has no cursor on that partition |
| `transaction is unresolvable, already committed, or acknowledgment is stale` | see the table above; also every item of a lease-less ack from a group that never popped from that partition |
| `partitionId is not a partition id` | the `partitionId` is missing, or is not a decimal partition id |
| `no partition <id>` | no partition with that id exists; in a cluster the node first catches up with what the cluster committed and looks again |
| `partition <id> not owned by this tenant` | multi-tenant deployments only: the `partitionId` belongs to another tenant |

### Status codes

| Code | When |
| --- | --- |
| `200` | the call was processed, whatever the per-item outcomes |
| `400` | the body is not JSON, or a field has the wrong type: `{"error":"bad ack body: …","code":"bad_body"}` |
| `403` | authentication is on and the token has no `read-write` role |
| `413` | code `name_too_long`: the tenant and consumer group names together exceed 447 bytes |
| `503` | code `no_leader`, `retry` or `timeout`, with `Retry-After: 1` |
| `500` | code `internal`: a broker fault |

There is no 404 for an unknown `transactionId` and no 409 for a stale lease: both are per-item
outcomes inside a 200.

## Acknowledging in a transaction

If the next thing your handler does is write another message, do the ack and the push in one
transaction instead of two calls: both commit in one entry of the replicated log. See
[`POST /api/v1/transaction`](/reference/http/transaction). That is how a multi-stage pipeline
hands work forward without a window in which the ack landed and the next message did not.
