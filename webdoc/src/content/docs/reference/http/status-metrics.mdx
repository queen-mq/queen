Several different things are called "status" on this broker, and they answer different
questions. `/health` asks whether this node can serve: whether it knows a leader. `/status`
asks whether the process is up. `/api/v1/status` is the dashboard's aggregate view, and
`/api/v1/status/queues` the per-queue view. The `/api/v1/raft/*` views describe the Raft
cluster as the node you asked sees it.

## GET /health

Public: no token required, even with JWT enabled. Answered by the node you reached, never
forwarded. It reads node-local state only.

```json
{
  "status": "healthy",
  "engine": "raft",
  "version": "2.0.0",
  "raft": {
    "role": "leader",
    "leader": true,
    "term": 3,
    "applied": 18342,
    "commit": 18342,
    "lag": 0,
    "storageReady": true
  }
}
```

It answers **200** `healthy` when the node knows a leader and its apply lag is under
`QUEEN_RAFT_READY_LAG_MS` (default `2000`). Otherwise it answers **503** with
`"status":"settling"` and the same `raft` object: an election is running, or the cluster has
no quorum.

| Field | Meaning |
| --- | --- |
| `raft.role` | `leader`, `follower`, `candidate`, `learner` or `stopped` |
| `raft.leader` | whether this node knows a leader |
| `raft.term` | the current Raft term |
| `raft.applied`, `raft.commit` | the last applied and the last committed log index |
| `raft.lag` | apply lag in ms. Reported as `0` today |
| `raft.storageReady` | `false` once the replicator has stopped |
| `raft.apply` | only with the openraft replicator: the entries this node stepped over (`skipped`) and the entry that stopped apply here (`failure`, or `null`) |

<Aside type="danger">
Use `/health` as a **readiness** probe, not a liveness probe. A node without a leader must not
be restarted for that: restarting it does not bring a leader back, and in a cluster it takes one
more voter away. For liveness, probe TCP on the HTTP port: the port opens only after the store
and the replicator have opened. Because `raft.lag` is reported as `0`, a follower that is still
catching up already answers `200`: readiness does not mean caught up.
</Aside>

## GET /status

Access level `read-only`, deliberately not public, so an unauthenticated caller
cannot enumerate broker facts.

```json
{ "status": "ok", "engine": "segments-rust" }
```

It touches neither the state machine nor the disk, so it answers as long as the HTTP server
is scheduling requests. When the in-process Kafka facade is on (`QUEEN_KAFKA_EMBEDDED=true`),
the body adds a `kafka` object with the facade's state (`mode`, `phase`, `listen`,
`advertised`, `clustered`, `restarts` and more).

## GET /api/v1/status

Access level `read-only`. The dashboard's aggregate view, with two halves that are scoped
differently:

- the **queue half** (`queues`, `messages.pending`, `messages.processing`, `leases`, and
  `deadLetterQueue.currentMessages`, `affectedPartitions` and `topErrors`) is read from the
  replicated state for the caller's tenant;
- the **node half** (`throughput` without a queue filter, `workers`, `errors`, and the other
  `messages` and `deadLetterQueue` figures) is built from the metric rows of every node,
  across every tenant. On a shared cell, treat this route as an operator route.

Filters: `from` (default one hour before now), `to` (default now), `queue`, `namespace`,
`task`.

| Field | Meaning |
| --- | --- |
| `timeRange` | The window actually used. |
| `bucketMinutes` | Bucket width chosen from the window length: 1 up to 60 min, 5 up to 6 h, 15 up to 24 h, 60 up to 7 days, else 360. |
| `pointCount` | Number of buckets returned. |
| `throughput[]` | Per bucket, newest first: pushed, acked and popped counts and their per-second rates, pop lag, event-loop lag, CPU and RSS. `dbPoolActive`, `dbPoolIdle`, `dbPoolSize` and `minFreeSlots` are always `null`. |
| `queues` | The tenant's queues that hold messages. |
| `messages` | `pending` and `processing` are live; `total`, `completed`, `failed`, `deadLetter`, `requests` and `batchEfficiency` are sums over the node rows the nodes still keep. |
| `leases`, `deadLetterQueue` | Live leases and dead letters of the tenant; `leases.totalAcked` is always `0`. |
| `workers[]` | One entry per node that wrote a row in the last 2 minutes. |
| `errors` | `dbErrors` (always `0`: nothing records it), `ackFailed`, `dlqMessages`. |
| `statsAge` | Seconds since the newest node row, or `-1` when there is none. |
| `engine` | `"raft"`. |
| `nodesMissing` | Present only when some nodes did not answer the gather: their ids. Their rows are missing from the response. |

When a `queue`, `namespace` or `task` filter is set, throughput comes from the selected
queues' per-queue rows and the node signals (event-loop lag, CPU, RSS) are attached by bucket,
so you can read "this queue's throughput against the cell's health" in one response.

## GET /api/v1/status/queues

Access level `read-only`, tenant-scoped. Every queue of the tenant, newest first, computed per
request from the replicated state:

```json
{
  "queues": [
    {
      "id": "0198...",
      "name": "orders",
      "queue": "orders",
      "namespace": "billing",
      "task": "invoice",
      "storage": "segments",
      "partitions": 8,
      "segments": { "segments": 9, "messages": 12904 },
      "messages": { "total": 12904, "pending": 286, "processing": 24, "completed": 12594, "deadLetter": 0 },
      "retainedBytes": 1824113,
      "options": {},
      "createdAt": "2026-07-30T09:12:44.011Z"
    }
  ]
}
```

`messages.pending` excludes what is leased, which `processing` counts. The route takes no
filters and no paging: `queue`, `namespace`, `task`, `from`, `to`, `limit` and `offset` are
ignored and there is no `pagination` object. The [queues page](/reference/http/queues)
documents the `options` object.

## GET /api/v1/status/queues/:queue

Access level `read-only`, tenant-scoped. The per-queue detail the dashboard's queue page
renders, computed per request from the replicated state: a `queue` object with its identity,
`priority` and `config`, one entry per partition (`messages`, `stats`, `cursor`,
`lastActivity`, `oldestMessage`, `newestMessage`, `retainedBytes`), and `totals`. Four shape
notes:

- `pending` is measured against the lowest committed cursor across the queue's consumer
  groups (the queue-mode cursor when there is no group), so one lagging group holds the number
  up for the whole partition.
- `failed` is `null`, never `0`: there is no per-partition failure counter, and a literal `0`
  next to a live ack-failure chart would read as "no failures".
- `cursor.batchesConsumed` is always `0`; `cursor.totalConsumed` is the sum over the
  partition's cursors.
- `lastActivity` is the latest time a lease was taken on the partition.

A queue that does not exist for the tenant answers `404` with `{"error":"Queue not found"}`.

## GET /api/v1/status/analytics

Access level `read-only`, tenant-scoped. On 2.0 this is not a time series: it answers one data
point, the sum of `messages.total` over the tenant's queues at the time of the request, with
`interval` `"hour"` and a window of the last 24 hours. Its filters are ignored.

```json
{
  "dataPoints": [ { "timestamp": "2026-07-30T11:00:00.000Z", "messages": 12904 } ],
  "interval": "hour",
  "from": "2026-07-29T11:00:00.000Z",
  "to": "2026-07-30T11:00:00.000Z"
}
```

For message volume over time, use `GET /api/v1/analytics/queue-ops` on
[Analytics](/reference/http/analytics).

## The Raft views

Three `GET` routes describe the cluster. Each is answered by the node you reached, never
forwarded, so a follower reports itself rather than the leader. Their access level is
`read-write` (the access table has no arm for them), and none is tenant-scoped. On a single node
with the `local` replicator, `status` and `members` describe that one node.

### GET /api/v1/raft/status

This node's block plus the cluster's identity: `nodeId`, `hostname` (`QUEEN_SERVER_ID`, else
`HOSTNAME`, else `node-<id>`), `raftAddr`, `httpAddr`, `role` (`voter` or `learner`), `state`
(`leader`, `follower`, `candidate`, `learner` or `shutdown`), `leaderId`, `term`,
`lastLogIndex`, `committedIndex`, `appliedIndex`, `durableIndex`, `inflight`, `proposals`,
`log` (`files`, `bytes`), `store` (`mapBytes`, `usedBytes`, `mapUsedPct`, `readersInUse`,
`maxReaders`), `version`, `uptimeSeconds` and, on the leader, `replication` (each follower's
`matchIndex` and `heartbeatAgeMs`). Added to it: `engine`, `clusterId`, `self`, `voters` and
`singleNode`.

`clusterId` is `QUEEN_CELL_ID` when set, else `raft-` and eight hex digits of a hash of the
voters' ids and Raft addresses, so every node of one cluster answers the same id.

### GET /api/v1/raft/members

`{engine, clusterId, leaderId, term, self, voters, members}`. `members` holds every member's
own block, the peers' gathered over the Raft RPC port. A peer that does not answer within
1.5 s is listed with `"state":"unreachable"`, `"reachable":false` and the `error`. Each member
also carries the leader's view of it: `matchIndex`, `heartbeatAgeMs` and `lagEntries`.

### GET /api/v1/raft/liveness

How long ago the leader last heard from each member, as the leader sees it:
`{engine, nodeId, leaderId, term, viewAgeMs, viewLeaderId, members}`, each member with
`nodeId`, `role`, `state`, `http`, `raft`, `lastAckMs`, `matchIndex` and `local`. A follower
serves the copy of the leader's view it last received, `viewAgeMs` old, and adds that age to
`lastAckMs`.

## GET /metrics

Public. Returns **JSON**, not Prometheus text, and describes the node that answered.

```json
{
  "uptime": 8412,
  "requests": { "total": 91002, "rate": 0 },
  "messages": { "total": 402881, "rate": 0 },
  "memory": { "rss": 6612574208, "heapTotal": 0, "heapUsed": 0, "external": 0, "arrayBuffers": 0 },
  "cpu": { "user": 0, "system": 0 },
  "engine": "raft",
  "raft": { "role": "leader", "leader": true, "term": 3, "applied": 18342, "commit": 18342, "lag": 0, "storageReady": true }
}
```

The zeros are literal, not measurements: `requests.rate`, `messages.rate`, every `heap*` field
and both `cpu` fields are fixed values kept for shape compatibility. The 1.x `database` block is
gone.
Only `uptime`, the two `total` counters, `memory.rss` and the `raft` block carry real values,
and the totals are process-lifetime sums since this node started. For anything you intend to
graph, use `/metrics/prometheus`.

## GET /metrics/prometheus

Public. `Content-Type: text/plain; version=0.0.4`. Every family carries `HELP` and `TYPE`, and
every one describes the node that answered: there is no family read back from a shared store.

The body is assembled in three parts:

1. **In-process families**: `queen_uptime_seconds`, `queen_process_*`, the parked long-poll
   and scheduler-lag gauges and the other counters of this process.
2. **Pipeline timing**: the `queen_raft_*` histograms and counters of the pipeline stages
   (planning, proposal to commit, log fsync, apply, checkpoint). They are emitted while
   `QUEEN_RAFT_METRICS` is on (the default) and left out entirely when it is `0`, `false`,
   `off` or `no`.
3. **State-machine families**: `queen_raft_store_operations_total`,
   `queen_raft_store_map_bytes` (`kind` `capacity`, `used`), `queen_raft_store_ram_rows`,
   `queen_raft_store_readers`, `queen_raft_index` (`kind` `log`, `committed`, `applied`,
   `durable`), `queen_raft_inflight`, `queen_raft_proposals_total`, `queen_raft_log_storage`
   (`kind` `files`, `bytes`) and `queen_raft_storage_full`, which is `1` while the disk gate
   refuses writes.

The complete family list, generated from the source, is in the [reference section](/reference).
In a cluster, scrape every node: each reports only itself.

<Aside type="danger">
Never expose `/metrics/prometheus` (or `/metrics`) to a tenant. Both are public and neither is
tenant-scoped. On a multi-tenant cell, bind them to an operator-only network path. On the port
the embedded proxy serves, both need the control-plane token (`x-queen-cp-token`) and answer
`404` without it.
</Aside>

## Where the numbers come from

Three sources, each with its own freshness:

| Source | Fresh as of | Read by |
| --- | --- | --- |
| The replicated state (partition offsets, cursors, leases, the dead-letter rows and the counters apply maintains) | the request: computed per call | `/api/v1/status/queues`, `/api/v1/status/queues/:queue`, `/api/v1/status/analytics`, the queue half of `/api/v1/status`, the `/api/v1/resources/*` listings |
| Each node's metric rows: one worker row and one system row per flush, and one row per queue with activity | the last collector flush, every `METRICS_FLUSH_MS` (default `60000` ms) on every node | the node half of `/api/v1/status`, the `/api/v1/analytics/*` series |
| The process itself | the scrape | `/health`, `/metrics`, `/metrics/prometheus`, the Raft views |

Each node keeps its own metric rows in `dash.db` in its data directory, so a restart keeps its
history. Node rows are kept `QUEEN_DASH_NODE_RETENTION_H` hours (default `168`), per-queue rows
`QUEEN_DASH_QUEUE_RETENTION_H` hours (default `24`, at most `QUEEN_DASH_MAX_QUEUE_ROWS` rows,
default `500000`). A read gathers the rows of every node over the Raft RPC port; a node that
does not answer within 1.5 s is left out.

Two consequences to plan around. First, a new node reports nothing on the metric routes until
its first flush, one `METRICS_FLUSH_MS` after it starts. Second, `statsAge` is the honest
freshness signal on `/api/v1/status`: a large value means no node has flushed a row recently,
not that traffic stopped.
