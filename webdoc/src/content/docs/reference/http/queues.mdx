A queue does not have to be created before it is used. The first push to a queue
name creates the queue and the partition the push names (`Default` when it names
none) with the implicit defaults. They match the `/configure` defaults listed below,
except for two options: `leaseTime` is 60 seconds instead of 300, and
`retentionSinkHoldMaxSeconds` is `0` instead of 604800. The push also derives
`namespace` and `task` from the name: the first dotted component is the namespace and
the second is the task. `billing.invoice` becomes namespace `billing`, task `invoice`;
an undotted `orders` becomes namespace `orders` with an empty task. A push-only queue
is therefore still visible to namespace and task discovery pops.

A **pop can create the queue too**: `GET /api/v1/pop/queue/:queue` on a name that does
not exist creates it with the same implicit defaults, because a consumer group may
legitimately register before the first push. The practical consequence is that a
consumer-side typo creates an empty queue rather than nothing. The partition-pinned pop
and the namespace/task discovery pop create nothing. A timer that fires into a missing
queue, and a dead-letter replay to a destination that does not exist, create it the
same way.

`POST /api/v1/configure` exists to set options that differ from the defaults, and to
create a queue so a consumer can attach before any producer runs.

Two routes change queue state: `POST /api/v1/configure` (read-write) and
`DELETE /api/v1/resources/queues/:queue` (**admin**). Each is a command the leader
turns into entries of the replicated log; it takes effect on every node when those
entries apply. Everything else on this page is a read at the `read-only` access level.

## POST /api/v1/configure

`queue` is the only required field, a string. An empty string is a valid queue name. A
missing or non-string `queue` is a `400`.

Options are read from the `options` object when the body has one, and from the top
level of the body otherwise; the two places are not combined. A top-level `namespace`
or `task` that is a non-empty string is folded into the options when `options` does not
already carry that key. Two other top-level keys are routing, not configuration:
`options` itself, and `mode`, which decides whether the call merges or replaces.

```json
{
  "queue": "orders",
  "namespace": "billing",
  "task": "invoice",
  "options": {
    "leaseTime": 120,
    "retryLimit": 5,
    "dedupWindowSeconds": 600
  }
}
```

The broker reads the queue's current configuration, applies the body to it, and writes
the whole resulting configuration as one log entry.

### Configure merges, unless you ask it to replace

An edit to an existing queue keeps every option the body does not mention:

| In the body | What the queue ends up with |
| --- | --- |
| the key is absent | the value the queue already had |
| the key is present with a value of its type | that value |
| `namespace`, `task` or `retentionSinkHold` with `null` or any non-string value | `""`, which is their default |
| any other option with `null`, or a value of the wrong type | no change: the call is a `400` naming the key (`leaseTime must be an integer`, `retentionEnabled must be a boolean`) |
| top-level `"mode": "replace"` | every option starts from the `/configure` defaults, so anything the body omits goes back to its default |

Integer options take JSON integers that fit in 32 bits, and boolean options take JSON
booleans. A string such as `"60"` is a `400`, not a number.

A queue that does not exist yet is created from the `/configure` defaults whichever
mode you send: there is nothing to keep. So on a create the two modes are the same
call, and on an edit they are opposites. A replace keeps the queue's id and creation
time.

<Aside type="note">
`mode` is the only spelling of this decision on the wire. It is `"merge"`
(the default when the key is absent or `null`) or `"replace"`; anything else,
including `"Replace"`, `""`, `true` and `1`, is a `400`
`{"error":"mode must be \"merge\" or \"replace\", got ..."}` and nothing is
written. A `replace` or `mode` key inside `options` is not an option and is ignored.
</Aside>

Merge is the default because every client sends only the options its caller set.
`"mode": "replace"` is for a caller that states the whole configuration, and it is what
`queenctl apply -f` sends: a manifest means the whole configuration, and anything it
leaves out should go back to the default.

Concurrent edits of one queue are not merged with each other. Each call reads the
current configuration, applies its keys, and writes the whole configuration back, so
when two merging edits race, the one applied second wins and the keys only the first
one set are lost. Serialize edits to one queue on the caller's side when that matters.

<Aside type="caution">
What the merge rule means for a given SDK depends on what it puts on the wire. Go,
Rust and `queenctl queue configure` send only the options the caller set, so their
partial calls keep all the rest. JavaScript, Python and PHP merge a nine-option
client-side default bag into every `.config()` call (`leaseTime`, `retryLimit`,
`priority`, `delayedProcessing`, `windowBuffer`, `maxSize`, `retentionSeconds`,
`completedRetentionSeconds`, `encryptionEnabled`), so those nine are always sent and
always land on the client's default when the caller does not name them, in either mode;
the other options survive a partial call.
</Aside>

### Enforced options

These are the options something on the broker reads. Each row names what reads it, so
you can predict the behaviour change from setting it.

| Option | Default | What reads it |
| --- | --- | --- |
| `namespace` | `""` | Stored on the queue. Selects queues for the namespace discovery pop and for the `namespace` filter of `GET /api/v1/messages`, and groups `GET /api/v1/resources/namespaces`. |
| `task` | `""` | Same as `namespace`, on the `task` axis. |
| `leaseTime` | `300` (seconds) | The lease a pop on `/api/v1/pop/queue/:queue`, or its partition-pinned form, takes when the request sends no `leaseSeconds`. A namespace/task discovery pop does not read it: it leases for 60 seconds unless the request sends `leaseSeconds`. |
| `retryLimit` | `3` | The retry budget per (partition, consumer group), charged by an explicit `failed` ack. Below the limit the lease is released and the failed message is delivered again; at the limit it is dead-lettered or dropped. |
| `deadLetterQueue` | `true` | With `dlqAfterMaxRetries`, decides whether an exhausted retry budget files a dead-letter row. |
| `dlqAfterMaxRetries` | `true` | See the note below: the two flags are OR-ed. |
| `delayedProcessing` | `0` (seconds) | Pop visibility: only messages at least this old are delivered. |
| `windowBuffer` | `0` (seconds) | Pop visibility: if the partition received a write within this window, the pop delivers **nothing** from that partition. Trades latency for larger batches. |
| `retentionEnabled` | `false` | Switch for the two age-based retention rules. Without it, `retentionSeconds` and `completedRetentionSeconds` do nothing. |
| `retentionSeconds` | `0` | Rule 1: messages older than this are removed from the head of each partition. Active only when `retentionEnabled` is true and the value is positive. |
| `completedRetentionSeconds` | `0` | Rule 2: the same, for messages every cursor on the partition has passed. A partition no group has a cursor on is not trimmed by this rule. Also sets how long transaction-id hashes are kept: the largest of `dedupWindowSeconds`, `completedRetentionSeconds` and 900 seconds. |
| `maxWaitTimeSeconds` | `0` | **Removes messages older than the cutoff for every consumer group, leased ones included.** Independent of `retentionEnabled`. See below. |
| `encryptionEnabled` | `false` | Read at push time. With `QUEEN_ENCRYPTION_KEY` set, the queue's payloads are stored encrypted; without a key they are stored as plaintext. |
| `dedupWindowSeconds` | `3600` (seconds) | The push path looks for each message's transaction id among the partition's messages written within this window, and answers `duplicate` with the original's offset instead of writing it. `0` disables the lookup. |

Retention removes messages from the head of a partition in the batches they were pushed
in: messages pushed together in one request are removed together.

Values are stored as given. The broker does not check ranges, apart from clamping
`minPopWaitTime` to `[0, 60000]`, flooring `dedupWindowSeconds` at `0`, and the two
sink-hold checks below, which are **rejected** rather than clamped.

Fourteen rows for twenty-one keys. Two more, `retentionSinkHold` and
`retentionSinkHoldMaxSeconds`, are read by retention and described below. The other
five are stored, echoed back and read by nothing: `priority` (default `0`, echoed by
`GET /api/v1/messages` as `queuePriority`), `ttl` (`3600`), `maxSize` (`0`, echoed a
second time as `maxQueueSize`), `retryDelay` (`1000`) and `minPopWaitTime` (`0` ms).
No push, pop, ack or retention path reads any of them. See
[Queue options](/reference/queue-options).

<Aside type="note">
The effective `leaseTime` depends on how the queue came to exist. A queue created
implicitly by a push or a pop gets **60 seconds**. A queue created by `/configure`, or
reconfigured with `"mode": "replace"`, gets the option's default, **300 seconds**, when
`leaseTime` is omitted. A pop overrides either with `?leaseSeconds=`. The value the
queue detail route displays is the value queue-scoped pops lease with.
</Aside>

#### Disabling the dead-letter queue takes both flags

The ack path computes the switch as `deadLetterQueue OR dlqAfterMaxRetries`. Setting
only one of them to `false` leaves dead-lettering on. Send both as `false` to turn it
off, at which point an exhausted retry budget drops the failed message (the cursor
moves past it) instead of filing it. An ack with status `dlq` files a dead letter
whatever the two flags say.

#### maxWaitTimeSeconds deletes messages

`maxWaitTimeSeconds` is not a delivery deadline and it does not dead-letter. The
retention pass removes messages older than the cutoff from the head of every partition
of the queue, for every consumer group, including messages a group holds a live lease
on. This is data loss by design. A cursor left below the new start of the log resumes at
the first message still there. Use it only where dropping stale work is the intent.

#### retentionSinkHold and retentionSinkHoldMaxSeconds

These two options were the retention hold of the S3 sink, which 2.0 does not ship. The
broker still validates and stores them, and the retention pass still reads them:

- `retentionSinkHold` must match `[A-Za-z0-9._-]{0,64}` and `retentionSinkHoldMaxSeconds`
  must be between 60 and 31,536,000. Outside either, the call is a `400` (code
  `bad_request`) and **the queue keeps the configuration it had**; nothing partial is
  written. The check applies to the value the queue ends up with, not only to a value
  the body sends. A queue created implicitly stores `retentionSinkHoldMaxSeconds: 0`,
  so a merging edit of such a queue answers `400`
  (`retentionSinkHoldMaxSeconds must be between 60 and 31536000`) unless the body sets
  `retentionSinkHoldMaxSeconds` or sends `"mode": "replace"`.
- With a non-empty `retentionSinkHold`, rules 1 and 2 remove nothing younger than
  `retentionSinkHoldMaxSeconds`: the hold waits for a sink commit pointer that nothing in
  2.0 writes. `maxWaitTimeSeconds` is not held.

Leave `retentionSinkHold` empty.

#### How retention runs

The leader evaluates rules 1 and 2 and `maxWaitTimeSeconds` every `RETENTION_INTERVAL`
milliseconds (default 5000) and writes the result as log entries that move each
partition's start forward, so every node drops the same messages. Each pass is bounded
by `RETENTION_BATCH_SIZE` (default 1000); what does not fit waits for the next pass.

The same pass removes a partition that holds no messages (never written, or emptied by
retention), is older than `PARTITION_CLEANUP_DAYS` days (default 30) and has seen no
write, no lease and no new cursor in that time, provided it has no dead letters and no
streams state.
`QUEEN_PARTITION_CLEANUP_ENABLED=false` turns that cleanup off.

### Response

`200` with the resulting configuration:

```json
{
  "configured": true,
  "queueId": "0198...",
  "partitionId": null,
  "queue": "orders",
  "namespace": "billing",
  "task": "invoice",
  "storage": "segments",
  "options": { "leaseTime": 120, "retryLimit": 5, "dedupWindowSeconds": 600 }
}
```

The example abbreviates `options`. It echoes the **resulting configuration**, not the
request: twenty keys, every option except `namespace` and `task`, plus `maxQueueSize`,
a second spelling of `maxSize` that `/configure` does not read. A caller that sent three
options gets the whole set back and needs no second read to render the queue's
configuration, which is what makes a merging edit safe to build a form on. `namespace`
and `task` stay top level. There is no `mode` or `replace` key anywhere in the response:
the flag is a directive of the request, read once and never stored.

`storage` and `partitionId` are constants kept so the response shape does not change:
`storage` is always `"segments"`, and `partitionId` is always `null`, because
configuring a queue creates no partition. Partitions are created by the first push that
names one.

Every failure writes nothing:

- a body that is not JSON: `400`, code `bad_body`;
- a missing or non-string `queue`: `400` `{"error":"queue is required","code":"bad_request"}`;
- an unrecognised `mode`: `400`, described above;
- an option of the wrong type, or `null` for a numeric or boolean option: `400`, code
  `bad_request`;
- a sink-hold option out of range: `400`, code `bad_request`, described above;
- a queue name too long for the store: `413`, code `name_too_long`.

A write the cluster cannot take (no leader, an election, a timeout) answers `503` with
`Retry-After: 1`, as every write does. See [Errors](/reference/errors).

## GET /api/v1/resources/queues

Lists the tenant's queues, newest first.

```json
{
  "queues": [
    {
      "id": "0198...",
      "name": "orders",
      "queue": "orders",
      "namespace": "billing",
      "task": "invoice",
      "storage": "segments",
      "partitions": 8,
      "segments": { "segments": 41, "messages": 12904 },
      "messages": { "total": 12904, "pending": 286, "processing": 24, "completed": 12594, "deadLetter": 0 },
      "retainedBytes": 194883,
      "options": { "leaseTime": 120, "retryLimit": 5, "dedupWindowSeconds": 600 },
      "createdAt": "2026-07-30T09:12:44.011000Z"
    }
  ],
  "kvRows": 12,
  "kvBytes": 4096,
  "timerRows": 0,
  "timerBytes": 0
}
```

Every number is computed from the node's state when the request arrives. There is no
stats table and no refresh cycle behind it; `POST /api/v1/stats/refresh` answers `200`
and does nothing on 2.0. The cost of the call grows with the tenant's partition and
cursor count.

- `partitions` is the queue's partition count.
- `messages.total` counts **retained** messages, not the backlog.
- `messages.pending` counts the messages the slowest cursor has not passed,
  **excluding** those inside a live lease, which are `messages.processing`. Per
  partition, the slowest cursor is the lowest committed offset among the named consumer
  groups; the queue-mode cursor counts only when no named group has a cursor there; with
  no cursor at all, every retained message is pending.
- `messages.completed` is `total` minus pending (leased included) minus `deadLetter`.
- `messages.deadLetter` counts the queue's dead-letter rows.
- `segments.segments` counts each partition's sealed payload files, plus one for the open
  tail of each non-empty partition. Treat it as a size indicator; `segments.messages`
  repeats `messages.total`.
- `retainedBytes` is the payload bytes the queue retains.
- `options` is the object the detail route returns (abbreviated above).
- `kvRows` and `kvBytes` are the tenant's KV rows and their key-plus-value bytes.
  `timerRows` and `timerBytes` are always `0`.

`?stats=lanes` answers only each queue's `id`, `name`, `queue`, `partitions` and
`createdAt`, with `"stats": "lanes"` at the top level, from an index walk instead of
every partition's cursors and files. Use it when you only need to know which queues
exist and how many partitions each has. Any other `stats` value, `cached` included,
returns the full list.

<Aside type="caution">
`namespace` and `task` query parameters are accepted and **ignored**. `stats` is the
only query parameter this route reads: it always serves the full list for the tenant.
`GET /api/v1/status/queues` applies no filter either. Filter client-side. See
[Status and metrics](/reference/http/status-metrics).
</Aside>

## GET /api/v1/resources/queues/:queue

One queue in detail: identity, its whole configuration, per-partition figures, and
totals.

```json
{
  "id": "0198...",
  "name": "orders",
  "namespace": "billing",
  "task": "invoice",
  "createdAt": "2026-07-30T09:12:44.011000Z",
  "options": {
    "priority": 0,
    "leaseTime": 120,
    "retryLimit": 5,
    "retryDelay": 1000,
    "maxSize": 0,
    "maxQueueSize": 0,
    "ttl": 3600,
    "deadLetterQueue": true,
    "dlqAfterMaxRetries": true,
    "delayedProcessing": 0,
    "windowBuffer": 0,
    "retentionSeconds": 0,
    "completedRetentionSeconds": 0,
    "retentionEnabled": false,
    "encryptionEnabled": false,
    "maxWaitTimeSeconds": 0,
    "minPopWaitTime": 0,
    "dedupWindowSeconds": 600,
    "retentionSinkHold": "",
    "retentionSinkHoldMaxSeconds": 604800
  },
  "partitions": [
    {
      "id": "0198...",
      "name": "Default",
      "createdAt": "2026-07-30T09:12:44.031000Z",
      "messages": {
        "total": 1600, "pending": 40, "processing": 8,
        "completed": 1560, "failed": null, "deadLetter": 0
      },
      "stats": {
        "total": 1600, "pending": 40, "processing": 8,
        "completed": 1560, "failed": null, "deadLetter": 0
      },
      "cursor": { "totalConsumed": 1560, "batchesConsumed": 0 },
      "lastActivity": "2026-07-30T10:44:01.120000Z",
      "oldestMessage": "2026-07-30T09:12:45.100000Z",
      "newestMessage": "2026-07-30T10:44:02.900000Z",
      "retainedBytes": 24160
    }
  ],
  "segments": { "segments": 41, "messages": 12904 },
  "totals": { "total": 12904, "pending": 310, "processing": 24, "completed": 12594, "failed": null, "deadLetter": 0 },
  "retainedBytes": 194883
}
```

`options` carries twenty keys: every option `/configure` accepts except `namespace` and
`task`, spelled exactly as `/configure` reads them, plus `maxQueueSize`. Post it back as
`options`, with `namespace` and `task` at the top level, and a `GET`, an edit and a
`POST` round-trip without a mapping table. This is the read an editor prefills from, and
it is the whole set rather than a selection because of the merge rule above: a form that
shows some options and silently keeps the rest cannot tell you what the queue is.

Per partition, `messages` and `stats` are the same object. Here `pending` **includes**
what is leased (`processing` is a part of it), unlike the list route. It uses the
slowest-cursor rule above, so a single lagging group holds the number up. `completed` is
`total - pending - deadLetter`, and `failed` is always `null` because there is no
per-message failure state. `cursor.totalConsumed` sums the lifetime counters of the
partition's cursors; `batchesConsumed` is always `0`. `lastActivity` is the latest lease
taken on the partition. `oldestMessage` is the stamp of the first message ever written to
the partition, and retention does not move it; `newestMessage` is the stamp of the newest
message, `null` when the partition retains none. Partitions are sorted by name.

A queue that does not exist answers `404` with `{"error":"Queue not found"}`.

## GET /api/v1/resources/queues/:queue/depth

Access level **read-only**. The minimal backlog read for relays and schedulers:
per-partition pending from offsets and cursors only. No payload files, no timestamps and
no dead-letter rows are read, and it is computed per request.

```json
{
  "queue": "orders",
  "group": null,
  "pending": 310,
  "processing": 24,
  "ready": 286,
  "partitionsPending": 4,
  "partitionsReady": 3,
  "conflation": false,
  "effectivePending": 310,
  "effectiveReady": 286,
  "partitions": [
    { "partition": "Default", "pending": 310, "processing": 24, "ready": 286 }
  ]
}
```

Without `group`, `pending` uses the same slowest-cursor rule as the detail route, so the
numbers agree. With `?group=<name>` each partition reports that group's own backlog
against its committed cursor; a group with no cursor on a partition owes the
partition's whole retained range. A queue that does not exist answers `404` with
`{"error":"Queue not found"}`.

`partitionsPending` counts the partitions with anything pending. `processing` is the
part of pending covered by live leases, clamped to `pending`; `ready` is
`pending - processing`, and `partitionsReady` counts partitions whose `ready` value is
non-zero.

`conflation` and `effectivePending` describe [last-value
delivery](/reference/http/pop#conflation). `conflation` is the group's stored delivery
policy (`false` without `?group=`, which addresses no group). `effectivePending`
is `partitionsPending` for a conflating group and `pending` for every other;
`effectiveReady` similarly selects `partitionsReady` or `ready`. The distinction is the one that
decides whether you are looking at an incident:

> For a conflating group, `pending` is **log depth**, the positions still to
> retire, and `effectivePending` is **work depth**, the handler invocations that
> remain.
> A conflating queue at `pending: 4000000, effectivePending: 12` is healthy. The
> same two numbers on a non-conflating group are a page.

## GET /api/v1/resources/queues/:queue/sizes

Access level **read-only**. The retained payload bytes of each partition, keyed by
partition name. It reads one counter per partition, where the detail route also reads
every partition's cursors and files.

```json
{ "queue": "orders", "partitions": { "Default": 24160, "eu-1": 170723 } }
```

A queue that does not exist answers `404` with `{"error":"Queue not found"}`.

## DELETE /api/v1/resources/queues/:queue

Access level **admin**. The delete runs as a sequence of log entries:

1. The first entry removes the queue's name: its configuration, its consumer-group
   registrations, its counters and the index from partition names to partitions. From
   this entry on the name is free, and a push right after it creates a new, empty queue.
2. The same entry starts removing the old partitions' data, and follow-up entries
   finish it, in chunks of up to 1,000 rows: cursors and leases, dead-letter rows, the
   payload index, deduplication rows and counters, then each partition itself.

The call answers after the last chunk has applied. If it runs out of time first, it
answers `503` (code `timeout`), and the leader's retention pass finishes the remaining
chunks.

The response is `200` with a JSON body, never `204`: the SDKs read
`res.deleted === true` and a bodyless response would make them see `null`.

```json
{ "deleted": true, "queue": "orders", "existed": true }
```

Deleting a queue that does not exist is also `200`, with the body made
self-consistent rather than misleading:

```json
{
  "deleted": false,
  "queue": "nope",
  "existed": false,
  "message": "Queue not found, nothing was deleted"
}
```

The status stays `200` because the SDKs use delete-before-create as a cleanup
idiom; a `404` would turn a no-op into a thrown error for them. Check `deleted`,
not the status code.

Message traces are **not** deleted. They keep their tenant and stay readable by name
until they expire. See [Traces](/reference/http/traces).

## Aggregate listings

Three sibling reads, all `read-only`, all computed per request from the same per-queue
figures as `GET /api/v1/resources/queues`, for the caller's tenant only.

| Route | Returns |
| --- | --- |
| `GET /api/v1/resources/overview` | Counts (`queues`, `partitions`, `namespaces`, `tasks`), a `messages` block (`total`, `pending`, `processing`, `completed`, `failed`, `deadLetter`), a `lag` block (`time` and `offset`, each with `avg`, `median`, `min`, `max`), `timestamp` and `statsAge`. |
| `GET /api/v1/resources/namespaces` | `namespaces[]` with `namespace`, `queues`, `partitions`, `messages.total`, `messages.pending`, in name order. |
| `GET /api/v1/resources/tasks` | The same shape on the `task` axis. |

Because they sum the list's figures, `messages.pending` excludes leased messages here
too. In the overview, `failed` is always `0`, and `statsAge` is always `0` because
nothing is cached. The `lag` block is per queue: a queue's time lag is the age in
seconds of the oldest message any of its cursors has not consumed, and its offset lag
is the largest backlog of any one cursor (one partition, one group). `avg` and `max` are
taken over the queues whose lag is above zero; `median` and `min` are always `0`.

The namespaces and tasks listings count only non-empty labels. Because a push derives
the namespace from the first dotted component of the name, an undotted queue created by
a push is listed as a namespace of its own.

## POST /api/v1/partitions/changed

Lists a queue's partitions by **name**, a page at a time, optionally only those written
since an instant, with the offsets a reader needs. It is the discovery half of what
[`POST /api/v1/fetch`](#post-apiv1fetch) is the read half of: each name comes with
`lastOffset` and `logStart`, so a caller can start fetching without a second round
trip. It serves a queue partitioned by entity, where the names are order ids or
customer ids and a per-queue count is not enough.

Like the fetch, it is **not a pop**: no lease, no cursor, no claim, nothing written.
Two callers asking the same question get the same answer and neither disturbs a
consumer group. Its access level is `read-only`.

### Request

```json
{ "entries": [ { "queue": "orders",
                 "since": "2026-09-04T10:00:00.000000Z",
                 "after": "t|1788515700123456|cust-0419",
                 "limit": 1000 } ] }
```

| Field | Required | What it is |
| --- | --- | --- |
| `entries` | yes | At most **1024**; more is a `400` (`{"error":"too many entries"}`), not a truncation. An entry is a *queue*, not a partition, and each one can cost 1000 rows. A missing `entries` is an empty list. |
| `queue` | yes | The queue name. A missing name is looked up as `""`, which is a valid queue name, so it answers like any other name. |
| `since` | no | Absent or `null` enumerates the queue's whole partition set, ordered by name. An ISO 8601 instant returns only partitions written at or after it, ordered by `(lastWriteAt, name)`. It is read to millisecond precision; a value that does not parse is treated as absent. |
| `after` | no | The opaque cursor from a previous answer's `next`, echoed back unmodified. |
| `limit` | no | Partitions for this entry. Default 1000, clamped to 1 to 1000, never rejected. A caller that asks for more learns the real bound from `next` being non-null. |

### The answer

```json
{ "safeTime": "2026-09-04T10:04:57.412331Z",
  "safeTimeDegraded": false,
  "entries": [ { "queue": "orders",
                 "partitions": [ { "name": "cust-0420",
                                   "lastOffset": 1811,
                                   "logStart": 1400,
                                   "lastWriteAt": "2026-09-04T10:04:12.000000Z" } ],
                 "next": null } ] }
```

`lastOffset` is the last offset written, so the high watermark is `lastOffset + 1`.
`logStart` is the oldest offset retention still holds. Timestamps are rendered UTC at
microsecond precision.

`next` is non-null **only when the page filled**, which is the rule to page on: a
short page is the end of the sweep. The cost is one extra empty round trip when
the partition count is an exact multiple of the limit.

**The cursor is opaque and mode-tagged. Do not parse it.** Its shape is the
broker's, and it carries which kind of sweep produced it, so a cursor from an
enumeration sent with a `since` (or the reverse) is answered `BAD_CURSOR` for that
entry rather than paging silently against the wrong column. Restarting quietly
would loop a paging client for ever on its own first page.

Two per-entry errors replace `partitions` and `next`:

| `error` | When |
| --- | --- |
| `UNKNOWN_TOPIC_OR_PARTITION` | The queue does not exist **for this tenant**. Identical to the answer for a queue that exists nowhere, so this route cannot be used to discover another tenant's queue names. |
| `BAD_CURSOR` | The `after` cursor does not parse, or does not belong to the sweep it was sent with. |

**Paging is sound because `lastWriteAt` only moves up.** Every write to a partition
stamps it with a time later than the previous write, so a partition written between two
pages of one sweep moves *forward* past the cursor and is seen a second time on a later
page. Seen twice is free, since the caller re-reads bounds it already had; missed would
be a silent hole in whatever the caller is mirroring.

### `safeTime`

On 2.0, `safeTime` is the answering node's clock when it builds the answer, and
`safeTimeDegraded` is always `false`. Both keys are kept so the answer's shape does not
change. `safeTime` is not derived from the writes in flight: a write stamped shortly
before it can still become visible after the answer, so do not treat a time range just
below `safeTime` as closed. It is answered even for an **empty** `entries` array.

## POST /api/v1/fetch

Access level **read-only**. Reads messages from given offsets, several partitions per
call: the read half of the pair. Like the discovery route it takes no lease, moves no
cursor and claims nothing; no consumer group is involved.

```json
{ "entries": [ { "queue": "orders", "partition": "cust-0420", "offset": 1400, "maxBytes": 1048576 } ],
  "maxWaitMs": 5000,
  "minBytes": 1 }
```

| Field | Required | What it is |
| --- | --- | --- |
| `entries` | yes | At most **1024**; more is a `400` (`{"error":"too many entries"}`). |
| `queue` | yes | The queue name. |
| `partition` | no | The partition name: a string, or a number read as its decimal spelling. Absent means `Default`. |
| `offset` | yes | The first offset to read. A negative offset is a `400` (`{"error":"offset must be non-negative"}`). |
| `maxBytes` | no | Payload bytes for this entry. Default 1 MiB, clamped to 1 byte to 8 MiB. The first record is returned even when it alone is larger. |
| `maxWaitMs` | no | How long to wait for data. Default `0` (answer at once), capped at 30000. |
| `minBytes` | no | With `maxWaitMs`, answer as soon as the entries hold at least this many payload bytes. Default `1`. |

```json
{ "entries": [ { "queue": "orders",
                 "partition": "cust-0420",
                 "records": [ { "offset": 1400,
                                "transactionId": "order-4471",
                                "payload": { "amount": 41 },
                                "ts": "2026-09-04T10:04:12.000000Z" } ],
                 "highWatermark": 1812,
                 "logStartOffset": 1400 } ] }
```

- There is one answer per asked entry, in order, with at most 10,000 records each.
- `highWatermark` is `lastOffset + 1`; `logStartOffset` is the oldest offset retention
  still holds. `ts` is the message's stamp.
- Payloads stored encrypted are decrypted when the broker has the key. A payload that
  is not JSON comes back as a string.
- An entry whose queue does not exist for this tenant carries
  `"error": "UNKNOWN_TOPIC_OR_PARTITION"` with no records and both offsets `0`. A queue
  that exists without that partition answers no records and both offsets `0`, without
  an error.
- An `offset` below `logStartOffset` or above `highWatermark` carries
  `"error": "OFFSET_OUT_OF_RANGE"` with the real offsets, so the caller can reset.
- With `maxWaitMs`, the call returns once the entries hold at least `minBytes` of
  payload (each record counts its payload's JSON length, at least 1), once the wait runs
  out, or once an entry reports an error. A write to one of the partitions it reads
  wakes it.
- A body that is not JSON, or an entry without `queue` or `offset`, is a `400` (code
  `bad_body`).

## Access levels

Access levels are a role *set*, not a ladder. A `WriteOnly` token passes
`/api/v1/push` and is rejected on every route on this page, including the
listings.

| Route | Level |
| --- | --- |
| `POST /api/v1/configure` | read-write |
| `GET /api/v1/resources/queues` | read-only |
| `GET /api/v1/resources/queues/:queue` | read-only |
| `GET /api/v1/resources/queues/:queue/depth` | read-only |
| `GET /api/v1/resources/queues/:queue/sizes` | read-only |
| `DELETE /api/v1/resources/queues/:queue` | admin |
| `GET /api/v1/resources/overview` | read-only |
| `GET /api/v1/resources/namespaces` | read-only |
| `GET /api/v1/resources/tasks` | read-only |
| `POST /api/v1/partitions/changed` | read-only |
| `POST /api/v1/fetch` | read-only |

Every route here resolves a tenant from the request, so with
`QUEEN_TENANCY_HEADER` on they are scoped to the caller's tenant. In a cluster any node
answers them: a follower forwards the request to the leader. The full route table,
generated from the router and the authorization function, is in the
[reference index](/reference).
