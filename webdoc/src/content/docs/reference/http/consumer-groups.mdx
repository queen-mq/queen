Consumption state is one cursor per (partition, consumer group) in the replicated
state: `committed`, the highest offset that group has completed in that partition.
There is no per-message state, so every number on these routes is arithmetic over
cursors and partition offsets rather than a scan of messages.

A pop that carries no `consumerGroup` uses the reserved group name
`__QUEUE_MODE__`, which is why that name shows up in listings on queues where
nobody set a group explicitly. Groups are created implicitly: the first pop of a group
on a queue registers it there, with its subscription (where a partition it has not
touched yet starts) and its delivery policy. Each partition's cursor is created on the
group's first contact with that partition, seeded from the registration.

Reads are `read-only`, except `POST /api/v1/consumer-groups/positions`, which is a
POST and therefore `read-write`. `subscription` and both `seek` routes are
`read-write`. Both `DELETE` routes are **admin**: `route_access_level` maps every
`DELETE` under `/api/v1/consumer-groups/` to admin regardless of what follows. Every
write on this page is one entry in the replicated log. Group, queue and partition names
in these paths are percent-decoded, so encode them as you would any path segment.

## GET /api/v1/consumer-groups

Every group the tenant has, one entry per (group, queue) pair with at least one cursor,
ordered by group, then queue. The body is a bare JSON array.

```json
[
  {
    "name": "invoicer",
    "topics": ["orders"],
    "queueName": "orders",
    "members": 8,
    "partitionCursors": 8,
    "partitionsWithLag": 2,
    "totalLag": 314,
    "maxTimeLag": 42,
    "state": "Stable",
    "storage": "segments",
    "kind": "queen",
    "subscriptionMode": "new",
    "subscriptionTimestamp": "2026-07-30T08:00:00.000000Z",
    "subscriptionCreatedAt": "2026-07-30T08:00:00.000000Z",
    "conflation": false
  }
]
```

Read these fields carefully:

- `members` counts **cursor rows**, not consumer processes. One consumer on a
  32-partition queue reports `members: 32`. `partitionCursors` carries the same
  number under its true name; `members` is kept only for wire compatibility.
- `totalLag` is the sum over partitions of
  `max(lastOffset - max(committed, logStart - 1), 0)`: pure arithmetic, exact, and no
  scan. Messages already removed by retention are not counted as lag.
- `maxTimeLag` is the age in seconds of the oldest message any of the group's cursors
  on that queue has not consumed.
- `state` is derived, not stored: `Lagging` when `maxTimeLag > 300`, otherwise
  `Stable` when the group has ever consumed anything there, otherwise `Dead`.
- `storage` is always `"segments"` and `kind` always `"queen"`.
- `subscriptionMode` (`all`, `new` or `timestamp`), `subscriptionTimestamp` and
  `subscriptionCreatedAt` are the group's registration on this queue. For `all` the
  timestamp is the epoch (`1970-01-01T00:00:00.000000Z`); for `new` it is the
  registration instant. All three are `null` for `__QUEUE_MODE__`, and for a group that
  has cursors but no registration on the queue: one that only used the partition-pinned
  pop without conflation, or whose cursors a seek created.
- `conflation` is the group's stored delivery policy on this queue: `true`
  means [last-value delivery](/reference/http/pop#conflation), where `totalLag`
  and `partitionsWithLag` mean different things. For a conflating group `totalLag`
  is **log lag**, the positions still to retire, most of which will be skipped;
  `partitionsWithLag` is the number of handler runs actually outstanding, and it is
  the figure to alert on.

## GET /api/v1/consumer-groups/lagging

Query: `minLagSeconds` (default **3600**). Returns a bare array of
(group, partition) cursors, queue mode included, whose time lag is greater than the
threshold, largest lag first. The static `lagging` path is matched before the group
route, so a group actually named `lagging` does not shadow it.

```json
[
  {
    "consumer_group": "invoicer",
    "queue_name": "orders",
    "partition_name": "eu-3",
    "partition_id": "0198...",
    "worker_id": "0198...",
    "kind": "queen",
    "offset_lag": 512,
    "time_lag_seconds": 7421,
    "lag_hours": 2.06,
    "oldest_unconsumed_at": "2026-07-30T07:41:02.010Z",
    "last_consumed_at": null
  }
]
```

Keys are snake_case here, unlike the other listings. `time_lag_seconds` is the age of
the oldest message the cursor has not consumed, so a partition whose entire backlog was
removed by retention drops out of the result rather than reporting a huge lag.
`lag_hours` is the same value in hours, rounded to two decimals. `partition_id` is the
partition UUID. `last_consumed_at` is always `null`: the cursor does not record it.

## GET /api/v1/consumer-groups/:group

One group, broken out per queue and partition. The body is an object keyed by
queue name.

```json
{
  "orders": {
    "conflation": false,
    "kind": "queen",
    "partitions": [
      {
        "partition": "eu-1",
        "workerId": "0198...",
        "lastConsumedAt": null,
        "totalConsumed": 91204,
        "offsetLag": 0,
        "timeLagSeconds": 0,
        "leaseActive": false
      }
    ]
  }
}
```

`leaseActive` is true only while the group holds a live lease on the partition, the
one in-flight leased batch. `totalConsumed` is the cursor's lifetime counter, and it
counts **log positions retired**, not handler runs: under
[conflation](/reference/http/pop#conflation) it keeps counting the skipped
positions too, which is what the lag and state derivations want. `conflation`
is the group's stored delivery policy on that queue. `lastConsumedAt` is always `null`.
Partitions are sorted by name.

A group with no cursor anywhere answers `404` with
`{"error":"Consumer group not found"}`.

## POST /api/v1/consumer-groups/positions

Where a group reads, partition by partition. The group travels in the body, not in the
path, because a group name can be any string. Access level `read-write`: the route is a
POST, although it writes nothing.

```json
{ "consumerGroup": "invoicer", "entries": [ { "queue": "orders", "partition": "eu-1" } ] }
```

```json
{
  "consumerGroup": "invoicer",
  "entries": [ { "queue": "orders", "partition": "eu-1", "offset": 91205, "metadata": "" } ]
}
```

- `offset` is the next offset the group reads: the cursor's `committed + 1`. Where the
  group has no position (no cursor, no such partition, no such queue) the entry answers
  `"offset": null` and carries no `metadata`.
- `partition` defaults to `Default`. There is one answer per asked entry, in order, and
  at most 65,536 entries per call.
- Without `entries`, the answer is every position the group holds, on every queue it is
  registered on.
- `metadata` is the string stored with the position. It is empty unless a caller set
  one through the `positions` field of `POST /api/v1/transaction`.
- The read waits until this node has applied everything the cluster had committed when
  it began, so a position acknowledged anywhere in the cluster is what it answers.

A missing or empty `consumerGroup`, an entry without a `queue`, `entries` that is not
an array, or more than 65,536 entries is a `400`.

## POST /api/v1/consumer-groups/:group/subscription

Body: `subscriptionTimestamp` (required, an ISO 8601 instant). A missing value is a
`400` (`subscriptionTimestamp is required`); one that does not parse, the empty string
included, is a `400` (`subscriptionTimestamp is invalid`).

```json
{ "subscriptionTimestamp": "2026-07-30T08:00:00Z" }
```

Response:

```json
{
  "success": true,
  "consumerGroup": "invoicer",
  "newTimestamp": "2026-07-30T08:00:00Z",
  "rowsUpdated": 3
}
```

What this actually changes: the group's registration on **every queue** of the tenant
where it is registered, because the route takes no queue. Each registration becomes
subscription mode `timestamp` at the given instant, all in one log entry. `rowsUpdated`
is the number of queues changed, and `newTimestamp` echoes the value as sent.

<Aside type="caution">
This route does **not** move any existing cursor. It changes where a partition the
group has *not yet* touched gets seeded on first contact. `rowsUpdated: 0` with
`success: true` means the group is registered nowhere (it has never popped), so
nothing was written at all. To reposition a group that is already consuming, use
`seek`.
</Aside>

## Seek

Two routes, one body shape. Send either `toEnd` or `timestamp`:

```json
{ "toEnd": true }
```

```json
{ "timestamp": "2026-07-30T08:00:00Z" }
```

A body with neither, or with a `timestamp` that does not parse, is a `400`
`{"success":false,"error":"Must specify toEnd=true or a timestamp"}`. Both routes treat
an **empty body** as `toEnd: true`, and `toEnd: true` wins when a body sends both.

Cursor placement:

- `toEnd` sets `committed` to the partition's last offset, so the next wanted offset is
  the one after it and the whole existing backlog is skipped.
- `timestamp` sets `committed` to one below the first retained message stamped at or
  after `timestamp` (read to millisecond precision). Messages pushed together in one
  request share one stamp, so the resolution is a push, not a message. If no message is
  that recent, the cursor lands on the last offset (a future-only cursor). A timestamp
  older than what is retained lands on the oldest retained message.

Either way the seek releases any live lease on the partition and resets the
retry and redelivery state for that (partition, group). A partition where the group has
no cursor gets one. Every partition a seek moves is moved in one log entry. When it
applies, each partition the seek left behind its last offset becomes claimable for the
group again, so the group's next pop delivers from the new position.

### POST /api/v1/consumer-groups/:group/queues/:queue/seek

Seeks every partition of the queue.

```json
{
  "success": true,
  "consumerGroup": "invoicer",
  "queueName": "orders",
  "partitionName": null,
  "seekToEnd": true,
  "targetTimestamp": null,
  "partitionsUpdated": 8,
  "updated": true
}
```

A queue that does not exist for this tenant, or has no partitions yet, answers `404`
rather than a successful no-op:

```json
{
  "success": false,
  "error": "Queue not found or has no partitions",
  "consumerGroup": "invoicer",
  "queueName": "nope",
  "partitionsUpdated": 0
}
```

### POST /api/v1/consumer-groups/:group/queues/:queue/partitions/:partition/seek

Seeks one named partition. The response has the same keys as the queue-wide route:

```json
{
  "success": true,
  "consumerGroup": "invoicer",
  "queueName": "orders",
  "partitionName": "eu-1",
  "seekToEnd": false,
  "targetTimestamp": "2026-07-30T08:00:00.000000Z",
  "partitionsUpdated": 1,
  "updated": true
}
```

An unknown partition answers `404` with the same keys as the queue-wide `404` and
`"error": "Partition not found"`.

## DELETE routes

Both are **admin**. Both accept `deleteMetadata` (default `true`; only the value
`false` turns it off), and both answer `200` with a JSON body, not `204`, because the
SDKs read fields off the response. Each is one log entry.

### DELETE /api/v1/consumer-groups/:group

Removes the group's cursors on **every queue** of the tenant and, when
`deleteMetadata` is on, its registration on each queue together with the group's
counters and pending-work index there.

```json
{
  "success": true,
  "consumerGroup": "invoicer",
  "queueName": null,
  "deletedPartitions": 24,
  "metadataDeleted": true,
  "queues": ["orders", "refunds"]
}
```

`deletedPartitions` is the number of cursors removed. `metadataDeleted` echoes the
flag: it is `true` even on a queue where there was no registration to remove. `queues`
lists the queues the call looked at, every queue of the tenant here. A group with
nothing to remove still answers `success: true` with `deletedPartitions: 0`.

### DELETE /api/v1/consumer-groups/:group/queues/:queue

The same operation scoped to one queue.

```json
{
  "success": true,
  "consumerGroup": "invoicer",
  "queueName": "orders",
  "deletedPartitions": 8,
  "metadataDeleted": true,
  "queues": ["orders"]
}
```

<Aside type="note">
With no cursor on a partition, the group's next pop seeds a new one from its
registration: from the oldest retained message for `all`, from the first message
written at or after the registration instant for `new`, and from the first at or after
the subscription timestamp for `timestamp`. With `deleteMetadata` on, the registration
goes too, and the next pop registers the group again from what that pop asks for, or
from `DEFAULT_SUBSCRIPTION_MODE` (default `new`) when it asks for nothing. So a delete
makes a group re-consume from the oldest retained message only when its registration,
kept or new, is `all`; to restart from a point in time, `seek` with a `timestamp`.
There is no separate reset-offsets route: `seek` and `DELETE` are the two mechanisms.

Neither route removes the group's dead letters. Purge them with `DELETE /api/v1/dlq`.
</Aside>

## Access levels

| Route | Level |
| --- | --- |
| `GET /api/v1/consumer-groups` | read-only |
| `GET /api/v1/consumer-groups/lagging` | read-only |
| `GET /api/v1/consumer-groups/:group` | read-only |
| `POST /api/v1/consumer-groups/positions` | read-write |
| `POST /api/v1/consumer-groups/:group/subscription` | read-write |
| `POST /api/v1/consumer-groups/:group/queues/:queue/seek` | read-write |
| `POST /api/v1/consumer-groups/:group/queues/:queue/partitions/:partition/seek` | read-write |
| `DELETE /api/v1/consumer-groups/:group` | admin |
| `DELETE /api/v1/consumer-groups/:group/queues/:queue` | admin |

Every route here is tenant-scoped: a group's cursors and registrations hang off the
tenant's own queues and partitions, so two tenants can run a group called `workers` on
their own queues without seeing each other's cursors. Related pages:
[queues and resources](/reference/http/queues),
[messages and DLQ](/reference/http/messages-dlq).
