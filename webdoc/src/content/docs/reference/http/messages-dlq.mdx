These are inspection routes, not a consumption path. Payloads live in each node's
queue log, so reading one message means walking a partition's retained messages until
the transaction id matches. Plan for them to be used by an operator or a dashboard,
not by a hot loop.

Every per-message route is addressed by **two** path segments,
`:partitionId/:transactionId`. `partitionId` is either the decimal partition id a pop
answer carries (the one an ack sends back), or the partition UUID the listings show
(`partitionId` in `GET /api/v1/messages`, `partitions[].id` in the queue detail). Either
form resolves only among the caller's tenant's partitions.

<Aside type="caution">
There is no single-segment `/api/v1/messages/:transactionId` route. A transaction
id is only unique within a partition, so the broker does not expose one. A request to
that path answers `404`
`{"code":"no_such_route","error":"not found","path":"..."}`.
</Aside>

## GET /api/v1/messages

Browse messages with filters. All filters are optional.

| Parameter | Default | Notes |
| --- | --- | --- |
| `queue` | none | Exact queue name. |
| `partition` | none | Exact partition name. |
| `namespace` | none | Exact namespace. `ns` is not an alias. |
| `task` | none | Exact task. |
| `status` | none | One of `pending`, `processing`, `completed`, `dead_letter`. |
| `from` | `now - 1 hour` | Inclusive of the exact timestamp. |
| `to` | `now` | Truncated to the minute, then `+1 minute`, compared with `<`, so the whole minute you name is included. |
| `limit` | `200` | Clamped to 1 to 1000. |
| `offset` | `0` | |

<Aside type="note">
The default window is **the last hour**. A queue that has been quiet for two hours
returns an empty list even though it holds a large backlog. Pass `from` explicitly
whenever you are not looking at live traffic.
</Aside>

```json
{
  "messages": [
    {
      "id": "0198...",
      "transactionId": "order-4471",
      "txnHash": "9f2c...",
      "partitionId": "0198...",
      "queuePath": "orders/eu-1",
      "queue": "orders",
      "partition": "eu-1",
      "offset": 41901,
      "namespace": "billing",
      "task": "invoice",
      "queuePriority": 0,
      "status": "pending",
      "queueStatus": "pending",
      "busStatus": { "consumedBy": 0, "totalGroups": 2 },
      "traceId": null,
      "producerSub": null,
      "isEncrypted": false,
      "payloadAvailable": true,
      "segment": { "seq": 41856, "frameIdx": 45 },
      "createdAt": "2026-07-30T10:41:02.010Z",
      "leaseExpiresAt": null,
      "data": { "amount": 41 },
      "payload": { "amount": 41 }
    }
  ],
  "total": 1,
  "pagination": { "limit": 200, "offset": 0 },
  "mode": { "hasQueueMode": true, "busGroupsCount": 2, "type": "hybrid" }
}
```

How that body is produced, and what it implies:

- **The listing reads the log itself.** Every retained message whose stamp falls in
  the window can be listed; nothing leaves the listing before retention removes the
  message. Partitions are visited newest write first, each read backwards from its
  tail, and the walk stops once it holds `offset + limit` messages newer than anything
  left to read. Messages come back newest first.
- **`payloadAvailable` is always `true`**: a retained message always has its payload.
  `data` and `payload` are the same value. A payload stored encrypted is decrypted when
  the broker has the key; a payload that is not JSON comes back as a string, an empty
  one as `null`.
- `offset` is the message's offset. `segment.seq` is the offset of the first message of
  the stored batch that holds it, and `segment.frameIdx` its index in that batch. Treat
  both, and `txnHash`, as opaque.
- **`total` is the size of the page, not of the result set.** There is no total count;
  page with `offset` until you get a short page.
- **`status` is derived per message:** `dead_letter` when a dead-letter row exists at
  that offset (for any group); else `completed` when every named consumer group with a
  cursor on the partition has passed it, or, with no named group, when the queue-mode
  cursor has; else `processing` when any cursor on the partition holds a live lease;
  else `pending`. `queueStatus` repeats it.
- `busStatus.totalGroups` counts the named groups with a cursor on the partition, and
  `busStatus.consumedBy` how many of them have passed the message.
- `leaseExpiresAt` is the queue-mode cursor's lease, when it has one.
- `mode.type` is `queue`, `bus`, `hybrid` or `none`, detected from which consumer
  groups have cursors on the partitions the `queue` and `partition` filters select. The
  `namespace` and `task` filters narrow the list but not `mode`.

## GET /api/v1/messages/:partitionId/:transactionId

Resolves one message and returns it with its management detail. The broker walks the
partition's retained messages from the oldest and answers the first whose transaction
id matches, so the cost grows with the partition's retained size. A message removed by
retention, or an address that does not resolve in this tenant, is a `404`
`{"error":"Message not found"}`.

```json
{
  "id": "0198...",
  "transactionId": "order-4471",
  "data": { "amount": 41 },
  "payload": { "amount": 41 },
  "traceId": null,
  "producerSub": "svc-billing",
  "createdAt": "2026-07-30T10:41:02.010000Z",
  "partitionId": "0198...",
  "partition": "eu-1",
  "queue": "orders",
  "queuePath": "orders/eu-1",
  "namespace": "billing",
  "task": "invoice",
  "status": "processing",
  "errorMessage": null,
  "retryCount": 0,
  "isEncrypted": false,
  "queueConfig": { "leaseTime": 300, "retryLimit": 3, "dedupWindowSeconds": 3600 },
  "mode": { "hasQueueMode": true, "busGroupsCount": 1, "type": "hybrid" },
  "consumerGroups": [
    { "name": "__QUEUE_MODE__", "committed": 41899, "consumed": false, "leaseExpiresAt": "2026-07-30T10:46:02.010000Z" },
    { "name": "invoicer", "committed": 41850, "consumed": false, "leaseExpiresAt": null }
  ]
}
```

Details worth knowing:

- `data` and `payload` are the same value. A payload stored encrypted is decrypted
  when the broker has the key; `isEncrypted` reports the flag stored with the message.
- `status` is `dead_letter` when a dead-letter row exists for this address (for any
  group), and otherwise derived from the cursors as in the list above.
- `errorMessage` and `retryCount` come from that dead-letter row. For a live message
  they are `null` and `0`: the broker counts retries per (partition, group), not per
  message.
- `consumerGroups` lists every cursor on the partition, `__QUEUE_MODE__` included.
  `committed` is the group's cursor, and `consumed` is `committed >= offset`.
- `namespace` and `task` are the queue's stored values.
- `queueConfig` is the queue's options object, the one the queue detail route
  returns (abbreviated in the example).

## DELETE /api/v1/messages/:partitionId/:transactionId

Access level `read-write`. This deletes **dead-letter rows**, nothing else: every
group's row for the address, in one log entry. A live message cannot be deleted
individually.

```json
{
  "success": true,
  "partitionId": "0198...",
  "transactionId": "order-4471",
  "deleted": 1
}
```

`deleted` is the number of rows removed. Nothing matched is a `404`, not a `200`
carrying `success: false`. A caller that ignores the body must not read a no-op as a
deletion:

```json
{
  "success": false,
  "partitionId": "0198...",
  "transactionId": "order-4471",
  "error": "Message not found",
  "message": "No dead-letter row for this address. Live messages live in immutable segments and cannot be deleted"
}
```

## POST /api/v1/messages/:partitionId/:transactionId/retry

Access level `read-write`. Replays a dead-lettered message. It works **only** for
dead-lettered addresses; an address with no dead-letter row answers `404`.

The act underneath is a **move**: the broker builds one transaction that pushes the
dead letter's payload as a new message and deletes the dead-letter row, and the leader
writes it as **one entry** in the replicated log. Read it as four guarantees, each one
a property of the move rather than something the caller arranges:

1. **One entry, all or nothing.** The push and the delete apply together or not at
   all, so there is no "replayed but still dead-lettered" state to recover from. A
   second call after a successful move finds no row and answers `404`.
2. **A deterministic transaction id.** The replayed message carries
   `dlq:<dead-letter row id>`, derived from the row rather than minted per attempt. It
   is also what links a replayed message back to the record it came from. When two
   concurrent calls for one row both find it, the second one's push meets the first
   one's `dlq:` id in the destination's dedup window and answers `duplicate` (on a
   destination with `dedupWindowSeconds: 0` there is no such check).
3. **One record per call.** An address can carry one dead-letter row per consumer
   group. This route moves one of them, the one with the lowest row id, which is the
   oldest, and the other groups' rows stay. That is where it differs from
   `DELETE /api/v1/messages/:partitionId/:transactionId`, which deletes every group's
   row for the address. To pick the row, use `POST /api/v1/dlq/:id/replay`.
4. **A foreign partition cannot be replayed.** The lookup reads only the caller's
   tenant's dead-letter rows, so with `QUEEN_TENANCY_HEADER` enabled another tenant's
   address gets exactly the same `404` as an address that does not exist, and no
   payload is touched on the way to that answer.

A dead-letter row holds the message's payload **decrypted** (see
[GET /api/v1/dlq](#get-apiv1dlq)). The move encrypts it again when the **destination**
queue has `encryptionEnabled` and the broker has a key. A row that holds an encrypted
envelope is decrypted first.

```json
{
  "success": true,
  "result": "moved",
  "queue": "orders",
  "partition": "eu-1",
  "consumerGroup": "invoicer",
  "dlqId": "0198...",
  "originalTransactionId": "order-4471",
  "replayedAs": {
    "index": 0,
    "message_id": "0198...",
    "transaction_id": "dlq:0198...",
    "queueName": "orders",
    "status": "queued",
    "offset": 41902
  },
  "dlqRowRemoved": true
}
```

`replayedAs` is shaped like a push result, so the SDK wrappers and `queenctl` parse it;
`offset` is where the message landed. Beside it: `result`, the verdict;
`consumerGroup`, whose record was moved; `dlqId`, the row it was; and
`originalTransactionId`, the id the dead-lettered message carried, which is the only
link between that id and the `dlq:` one.

### The verdicts

| Answer | What happened |
| --- | --- |
| `200` `result: "moved"` | The message was written at `replayedAs.offset` and the dead-letter row is gone. `dlqRowRemoved` is `true`. |
| `200` `result: "duplicate"` | **Nothing was written and nothing was removed.** `dlqRowRemoved` is `false`. |
| `404` `result: "gone"` | No dead-letter row matches: already replayed or purged, a live address, another tenant's, or a malformed `:partitionId`. The body is `{"success":false,"result":"gone","error":"Message not found"}`. |
| `409` | The broker refused the move while planning it. Nothing was written and the row is untouched: `{"success":false,"error":"...","reason":"<code>","dlqRowRemoved":false}`. |
| `503` `no_leader`, `retry` or `timeout` | The cluster could not take the write, with `Retry-After: 1`. After `timeout` the outcome is **not known**: the entry may still commit. Re-read the dead-letter list; if the row is gone, the move happened. |
| `507` `storage_full` | The data disk is past its high-water mark. Nothing was written. |
| `429` `overloaded` | The node's write admission stayed full. Nothing was written; retry after `Retry-After`. |
| `400` | The body is not JSON (code `bad_body`). |

`duplicate` is the one that repays reading twice. It means the destination's dedup
window already holds a message under this replay's transaction id, so the push wrote
nothing. The row is kept anyway, and deliberately: the dedup identity is the
transaction id alone, and `dlq:<row id>` is derivable by anyone who can read the
dead-letter listing, so deleting on that verdict would turn a producer credential into
a way to destroy a dead-letter record without replaying it. `replayedAs.offset` names
where the existing message is, `replayedAs.status` is `duplicate`, and
`replayedAs.message_id` is the all-zero UUID.

Five admin clients wrap this route, spelling it the way their language does:
`retryMessage` in JavaScript and PHP, `RetryMessage` in Go, `retry_message` in
Rust and Python. None of them sends a destination.
`queenctl dlq retry <partitionId> <transactionId>` wraps it too and requires `--yes`,
because it appends a message and removes a record. The Go client sends it with
`WithoutFailoverRetry()`: it is a write, and a blind resend by the transport would hide
a verdict the caller has to read.

## POST /api/v1/dlq/:id/replay

Access level `read-write`. The same move, addressed by the **dead-letter row id**
that `GET /api/v1/dlq` returns in each row's `id`. This is the form the dashboard's
Replay button uses, and the one a redrive wants: a row id names exactly one record, so
a message dead-lettered under two consumer groups loses only the record that was
replayed, with no row-order rule to reason about.

The body is optional. Absent, empty, whitespace or `{}` replays in place. When
it is present it may name a destination:

```bash
curl -sS -X POST \
  http://localhost:6632/api/v1/dlq/0198abcd-0000-4000-8000-00000000cafe/replay \
  -H 'Content-Type: application/json' \
  -d '{"queue":"orders.retry","partition":"eu-2"}'
```

Both fields are optional and independent at the broker: an omitted half keeps the
source row's own value, so `{"queue":"orders.retry"}` moves the message to another
queue and keeps its partition name. Names are trimmed, and a present-but-blank one is a
`400` `{"success":false,"error":"queue and partition overrides must be non-empty"}`, and
a name too long for the store is a `413` (code `name_too_long`). A field that is not a
string is ignored. A destination that does not exist yet is created, queue and
partition, with the implicit defaults a first push uses, under the caller's own tenant.

<Aside type="caution">
Through the multi-tenant proxy the destination is admitted **as a pair or not at
all**: a body that names one half and not the other is refused `400`
`invalid_request` naming the half to add, because the omitted half lives in the
broker's dead-letter row and never reaches the proxy, so neither plan cap could
be answered for the pair that would actually be created. Send both halves, or
neither. Broker-direct, and on a proxy configured to measure rather than enforce,
the independent behaviour above is what you get.
</Aside>

Every verdict matches the retry route's, bodies included: the same `200`, the same
`404` `{"success":false,"result":"gone","error":"Message not found"}`, the same `409`,
`503`, `507` and `429`. A malformed `:id` answers the same `404`.

Three caveats belong to appending to a log rather than to this route, and they
apply to both forms. The message lands at the **tail** of the destination
partition, so it is out of order with respect to its own key, and the offset the
original occupied stays committed: a move is a re-push, not a revival. Its
`createdAt` is stamped at the destination, so the replayed message's lag clock
starts at zero. And it is encrypted for the **destination** queue, which an
override can change: a move out of an encrypted queue into a plaintext one stores
plaintext.

No SDK wraps this route yet. The five retry wrappers and `queenctl dlq retry`
use the address-keyed form above.

## GET /api/v1/dlq

Lists dead-lettered messages. Each row holds its own copy of the payload, so no
message is read from the log.

| Parameter | Default |
| --- | --- |
| `queue` | none |
| `consumerGroup` | none |
| `limit` | `100` (clamped to 1 to 1000) |
| `offset` | `0` |

```json
{
  "messages": [
    {
      "id": "0198...",
      "queue": "orders",
      "partition": "eu-1",
      "partitionId": "0198...",
      "consumerGroup": "invoicer",
      "offset": 41901,
      "messageId": "0198...",
      "transactionId": "order-4471",
      "data": { "amount": 41 },
      "payload": { "amount": 41 },
      "errorMessage": "Test error",
      "retryCount": 3,
      "createdAt": "2026-07-30T10:52:11.400000Z",
      "failedAt": "2026-07-30T10:52:11.400000Z"
    }
  ],
  "total": 1,
  "pagination": { "limit": 100, "offset": 0 }
}
```

- Ordered by `failedAt`, newest first. `total` is the number of rows that match the
  filters, not the length of this page.
- `createdAt` equals `failedAt`: the row records when the message was dead-lettered.
- `offset` and `messageId` are the dead-lettered message's offset and id;
  `partitionId` is the partition UUID.
- `retryCount` is the retry count at dead-letter time.
- `data` and `payload` are the same value. A row that holds an encrypted envelope is
  decrypted when the broker's key opens it and returned as stored otherwise.

<Aside type="caution">
A dead-letter row holds the payload **decrypted**. When a message stored encrypted is
dead-lettered, the broker decrypts it with its key before filing the row, so on an
`encryptionEnabled` queue dead letters are stored in the data directory as plaintext.
</Aside>

Retention never removes dead letters, and neither does deleting a consumer group. They
stay until you delete, replay or bulk-purge them, or the queue is deleted.

## DELETE /api/v1/dlq

Access level **admin**. Bulk-purges dead-letter rows for one exact queue, optionally
narrowed to one exact consumer group:

```bash
curl -sS -X DELETE \
  'http://localhost:6632/api/v1/dlq?queue=orders&consumerGroup=invoicer'
```

`queue` is required and must be non-empty, so an omitted filter can never become a
tenant-wide delete. An omitted `consumerGroup` purges every group for that queue. The
purge reads only the caller's tenant's rows and removes every match in one log entry.

```json
{
  "success": true,
  "deleted": 17,
  "queue": "orders",
  "consumerGroup": "invoicer"
}
```

No matches is a successful, idempotent delete with `deleted: 0`. A missing or empty
`queue` returns `400`
`{"success":false,"error":"queue is required","message":"Bulk DLQ purge requires an exact queue name"}`.

## Ownership gating

Every route on this page reads only the caller's tenant. The address-keyed routes
(`GET`, `DELETE` and `POST .../retry`) resolve `:partitionId` among the tenant's own
partitions, so with `QUEEN_TENANCY_HEADER` enabled a partition belonging to another
tenant gets exactly the same `404` as a partition that does not exist, and no payload
is read on the way to that answer. A distinct `403` would confirm that the partition
exists under some other tenant, so it is deliberately not used.

`POST /api/v1/dlq/:id/replay` looks the row up among the tenant's own dead-letter
rows. Another tenant's row is `gone`, the same `404` as a row that never existed, for
the same reason.

`GET /api/v1/messages`, `GET /api/v1/dlq` and `DELETE /api/v1/dlq` walk only the
tenant's queues and rows.

## Access levels

| Route | Level |
| --- | --- |
| `GET /api/v1/messages` | read-only |
| `GET /api/v1/messages/:partitionId/:transactionId` | read-only |
| `DELETE /api/v1/messages/:partitionId/:transactionId` | read-write |
| `POST /api/v1/messages/:partitionId/:transactionId/retry` | read-write |
| `GET /api/v1/dlq` | read-only |
| `POST /api/v1/dlq/:id/replay` | read-write |
| `DELETE /api/v1/dlq` | admin |

Broker-direct, those are the levels `auth::route_access_level` applies. Through
the multi-tenant proxy both replay routes are **queue admin**, which an API key
gets from `scopes.admin` and a session from the Admin role only, and they answer
the storage and monthly push blocks the way a push does. See
[Endpoints and route classes](/reference/multi-tenant/endpoints).

Related: [consumer groups](/reference/http/consumer-groups) for the cursors these
statuses are computed against, and [traces](/reference/http/traces) for per-message
event history.
