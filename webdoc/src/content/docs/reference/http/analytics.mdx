Nine routes live under `/api/v1/analytics/`. All are `read-only` `GET`s, answered by the state
machine's generic adapter. Most are time series over metric rows that each node writes for
itself: every `METRICS_FLUSH_MS` (default `60000` ms) a collector on every node appends one
worker row, one system row, and one row per queue with activity to `dash.db` in its data
directory. A read gathers the rows of every node over the Raft RPC port, so a new node answers
with empty series until its first flush, about a minute after it starts. A node that does not
answer the gather within 1.5 s is left out of the result.

Each node keeps its worker and system rows for `QUEEN_DASH_NODE_RETENTION_H` hours (default
`168`) and its per-queue rows for `QUEEN_DASH_QUEUE_RETENTION_H` hours (default `24`, at most
`QUEEN_DASH_MAX_QUEUE_ROWS` rows, default `500000`). A window reaching further back than that
comes back empty for the part that is gone.

Seven routes are scoped to the caller's tenant. Two are **cell-wide**: they aggregate across
every tenant on the cell and must not be exposed to a tenant.

| Route | Scope | Source |
| --- | --- | --- |
| `GET /api/v1/analytics/queue-lag` | tenant | per-queue rows of every node |
| `GET /api/v1/analytics/queue-ops` | tenant | per-queue rows of every node |
| `GET /api/v1/analytics/queue-parked-replicas` | tenant | parked-consumer rows of every node |
| `GET /api/v1/analytics/retention` | tenant | the retention steps this node applied |
| `GET /api/v1/analytics/workload` | tenant | per-queue rows of every node, plus the replicated state |
| `GET /api/v1/analytics/dlq-signatures` | tenant | the replicated state (the queue's dead-letter rows) |
| `GET /api/v1/analytics/partition-liveness` | tenant | the replicated state (the queue's partitions) |
| `GET /api/v1/analytics/system-metrics` | **cell-wide** | system rows of every node |
| `GET /api/v1/analytics/worker-metrics` | **cell-wide** | worker rows of every node |

## The bucket rule

Every time-series route here derives its bucket width from the length of the window
you ask for, so a wide range does not return one point per minute per queue:

| Window | Bucket |
| --- | --- |
| up to 60 minutes | 1 minute |
| up to 6 hours | 5 minutes |
| up to 24 hours | 15 minutes |
| up to 7 days | 60 minutes |
| longer | 360 minutes |

Unless stated otherwise, `from` defaults to one hour before now and `to` to now. The envelope
carries `bucketMinutes`; never assume 1-minute points. A 360-minute width still floors each point
to the hour, so a range over seven days reports `bucketMinutes: 360` over hourly buckets.

Gauges and counters are rolled up differently, on purpose. Counters are summed.
`avg_lag_ms` is merged as a pop-weighted average (`SUM(avg × count) / SUM(count)`).
The parked-consumer gauge is summed across nodes within a bucket and averaged
across buckets.

<Aside type="note">
Lag is sampled **at pop**. A bucket with pushes but no pops holds no lag sample, and
these routes emit `null` rather than `0` for it: "unmeasured" stays distinct from
"zero". Render `null` as a gap, not as a reassuring flat line.
</Aside>

A `from` or `to` that does not parse answers `500` with `{"error": ...}` naming the bad
value.

## GET /api/v1/analytics/queue-lag

Tenant-scoped. Filters: `from`, `to`, `queue`. The response is a **bare JSON array**.
There is no envelope, so the bucket width travels with every point.

```json
[
  {
    "queueName": "orders",
    "popCount": 41200,
    "avgLagMs": 18,
    "maxLagMs": 412,
    "bucketMinutes": 1,
    "bucketTime": "2026-07-30T10:41:00Z"
  }
]
```

Ordered newest bucket first, then by queue name. `avgLagMs` and `maxLagMs` are
`null` when the bucket held no pop sample.

## GET /api/v1/analytics/queue-ops

Tenant-scoped. Filters: `from`, `to`, `queue`. The per-queue operations series the
dashboard's queue-operations view renders.

```json
{
  "timeRange": { "from": "2026-07-30T09:44:00.000Z", "to": "2026-07-30T10:44:00.000Z" },
  "bucketMinutes": 1,
  "series": [
    {
      "bucket": "2026-07-30T10:41:00Z",
      "queueName": "orders",
      "pushRequests": 412,
      "pushMessages": 41200,
      "popMessages": 40980,
      "popEmpty": 31,
      "ackRequests": 402,
      "ackSuccess": 40970,
      "ackFailed": 10,
      "transactions": 0,
      "partitionsCreated": 0,
      "partitionsDeleted": 0,
      "partitionCount": null,
      "avgLagMs": 18,
      "maxLagMs": 412,
      "pushPerSecond": 686.67,
      "popPerSecond": 683.0,
      "ackPerSecond": 683.0,
      "emptyPerSecond": 0.52,
      "parkedCount": 12.5
    }
  ],
  "queues": ["orders"]
}
```

The `*PerSecond` fields are the counters divided by the bucket width, computed by the broker so
a client cannot get the division wrong; `parkedCount` is a gauge and is deliberately not
rate-normalised. `avgLagMs` and `maxLagMs` are `null` for a bucket with no pop sample.
`partitionCount` is always `null`: nothing records it. `partitionsCreated` and
`partitionsDeleted` count the partitions created and removed in the bucket, as the log entries
that did it applied. `queues` lists the queue names present in the window, so a chart can build
its legend before the first datapoint arrives. Points are ordered oldest first.

## GET /api/v1/analytics/queue-parked-replicas

Tenant-scoped. Filters: `from`, `to`, `queue`. The same parked-consumer gauge as
`queue-ops`, broken out by node instead of aggregated.

```json
{
  "timeRange": { "from": "2026-07-30T09:44:00.000Z", "to": "2026-07-30T10:44:00.000Z" },
  "bucketMinutes": 1,
  "series": [
    {
      "bucket": "2026-07-30T10:41:00Z",
      "queueName": "orders",
      "hostname": "queen-0",
      "workerId": 0,
      "parkedCount": 12.5
    }
  ],
  "replicas": [ { "hostname": "queen-0", "workerId": 0 } ]
}
```

Buckets line up exactly with `queue-ops`, so the two can share a time axis.
`parkedCount` is a within-bucket average, rounded to two decimals: a node that
parks and wakes long-polls constantly will show fractional values. `hostname` is the node's
name (`QUEEN_SERVER_ID`, else `HOSTNAME`, else `node-<raft node id>`), and `workerId` is always
`0`: one process per node. Rows are written only for a queue that actually had parked pops in
the interval.

## GET /api/v1/analytics/retention

Tenant-scoped. Filters: `from`, `to`, `queue`. How many messages retention released, per
bucket.

```json
{
  "timeRange": { "from": "2026-07-30T09:44:00.000Z", "to": "2026-07-30T10:44:00.000Z" },
  "bucketMinutes": 1,
  "series": [
    {
      "bucket": "2026-07-30T10:41:00Z",
      "retentionMsgs": 40960,
      "completedRetentionMsgs": 0,
      "evictionMsgs": 0,
      "totalMsgs": 40960,
      "eventCount": 5
    }
  ],
  "totals": { "retentionMsgs": 40960, "completedRetentionMsgs": 0, "evictionMsgs": 0, "totalMsgs": 40960, "eventCount": 5 }
}
```

On 2.0 a retention step moves a partition's log start forward, as one applied log entry, and
every node records the steps it applies in a small local journal. `retentionMsgs` counts the
positions a step released, **whichever rule released them**: age (`retentionSeconds`),
consumption by every group (`completedRetentionSeconds`) or `maxWaitTimeSeconds` eviction, see
[queues](/reference/http/queues). `completedRetentionMsgs` and `evictionMsgs` are always `0`,
and `eventCount` counts the steps.

The journal keeps the most recent 4,096 steps per raft group, so on a busy cell the series only
reaches back as far as those steps do. A step whose partition no longer resolves to a queue (the
queue was deleted after the step) cannot be attributed and stays in the result rather than
being dropped, so `totals` can exceed the sum of what the `queue` filter would show.

### Grouping the retention totals

`groupBy` (`namespace`, `task` or `queue`; anything else is a `400` with
`{"error":"bad groupBy"}`) adds a `rows` array next to `series` and `totals`: one entry per
group with `key` (the empty string for queues without a namespace or task), `queues` (the
queues that had at least one retention step in the window) and the same five `totals`
figures for that group, ordered by `totalMsgs` descending. `series` and `totals` are
unchanged. This is what attributes a released message to a queue instead of to the tenant.

## GET /api/v1/analytics/workload

Tenant-scoped. Filters: `from`, `to`, `groupBy`, `namespace`, `task`, `queue`. Who is
doing the work, how much of it, and what is stuck right now, rolled up per namespace or
per task rather than per queue. It is the one route here that answers with a group and
its parts in the same payload.

`groupBy` takes `namespace` (the default), `task` or `queue`. Any other value is a `400`
with `{"error":"bad groupBy"}`; the route does not fall back to the default. The three
name filters are exact matches on the queue's own fields and combine with `AND`. Bucket
widths follow the same rule as the routes above.

The example is trimmed: one row of many, two of its buckets, and the `tenant` block
collapsed. Every row carries the same three blocks.

```json
{
  "timeRange": { "from": "2026-09-08T09:44:00.000Z", "to": "2026-09-09T09:44:00.000Z" },
  "bucketMinutes": 15,
  "groupBy": "namespace",
  "buckets": ["2026-09-08T09:45:00Z", "2026-09-08T10:00:00Z"],
  "rows": [
    {
      "key": "smartchat",
      "queues": 21,
      "window": {
        "pushMessages": 412000, "pushRequests": 4120,
        "popMessages": 409800, "popEmpty": 310,
        "ackRequests": 4020, "ackSuccess": 409700, "ackFailed": 100,
        "transactions": 0, "conflated": 0,
        "partitionsCreated": 0, "partitionsDeleted": 0,
        "parkedAvg": 12.5, "avgLagMs": 18, "maxLagMs": 412
      },
      "series": {
        "push": [41200, null], "pop": [40980, null], "popEmpty": [31, null],
        "ackFailed": [10, null], "parked": [12.5, null],
        "avgLagMs": [18, null], "maxLagMs": [412, null]
      },
      "now": {
        "pending": 1204, "processing": 8, "deadLetter": 0,
        "retainedBytes": 91230144, "partitions": 168,
        "groups": 24, "queuesWithoutGroup": 2, "pendingWithoutGroup": 0,
        "queuesTouched": 19, "queuesActive": 17
      }
    }
  ],
  "tenant": { "queues": 68, "window": {}, "series": {}, "now": {} }
}
```

How the three blocks are built:

- **`window` counters are summed** over every metric row the group's queues wrote inside
  `[from, to]`: `pushMessages`, `pushRequests`, `popMessages`, `popEmpty`, `ackRequests`,
  `ackSuccess`, `ackFailed`, `transactions`, `conflated`, `partitionsCreated` and
  `partitionsDeleted`.
- **`window.avgLagMs` is pop-weighted**, `SUM(avg × pops) / SUM(pops)` over the rows that
  hold a pop sample, and `null` when the group had no pops in the window. `maxLagMs` is
  the maximum over those same rows, and `null` on the same condition. A busy window with
  no pops is unmeasured, not zero.
- **`window.parkedAvg` is a gauge, not a counter.** It is averaged per queue across the
  window first, then summed across the group's queues, so it reads as "parked consumers
  in this group" rather than as a total that grows with the number of buckets.
- **`series` follows the `buckets` axis**, one value per bucket, with `push`, `pop`,
  `popEmpty` and `ackFailed` summed, `parked` averaged per queue and then summed, and
  `avgLagMs` pop-weighted within the bucket. A bucket where the group wrote no row is
  `null` in every series, never `0`. `buckets` runs from the floored `from` to the floored
  `to` whether or not each one has data, so the axis is complete even where the series
  is not.
- **`now` is a snapshot and says nothing about the window.** `pending`, `processing`,
  `deadLetter`, `retainedBytes` and `partitions` are read from the replicated state at the
  time of the request and summed over the group; `pending` includes what is leased.
  `groups`, `queuesWithoutGroup` and `pendingWithoutGroup` count the consumer groups
  registered on each queue (the queue-mode group included): a queue with no consumer group
  is a queue nobody is reading, and its pending messages are counted separately for that
  reason. `queuesTouched` and `queuesActive` are the only two that look at the window,
  counting the group's queues that wrote any row and those that actually pushed or popped.
- **`queues` counts the group, not the traffic**: every queue matching the filters,
  whether or not it was touched in the window.
- `namespace` and `task` appear on a row only when `groupBy` is `queue`. A queue with an
  empty namespace or task groups under `""`, not under `null`.
- **`tenant` ignores the `namespace`, `task` and `queue` filters** and aggregates every
  queue of the tenant, so a row's share is always against the whole tenant and does not
  move when you narrow the filters.

Every number is a JSON number and never a string. `parkedAvg` is rounded to two decimals,
`avgLagMs` is integer milliseconds.

## GET /api/v1/analytics/dlq-signatures

Tenant-scoped. Filters: `queue` (required; missing is a `400` with `{"error":"queue
required"}`), `limit` (default 200, clamped to 1 to 1000). Why the messages of one queue are in
its dead-letter queue, without transferring a single payload: the newest `limit` rows by
`failedAt` are read, their error messages are folded, and the folded texts are counted.

Folding replaces UUIDs and runs of 20 or more hex digits with `<id>`, dates and timestamps with
`<date>`, standalone integers with `<n>`, collapses whitespace and keeps the first 120
characters (an empty message reads `(no message)`), so "connection 3f2a... unresolvable" and
"connection 9c1d... unresolvable" are one signature. `avgBytes` is the average stored payload
length of the sample, measured by the broker; no payload is returned on this route.

```json
{
  "queue": "channel.opsync_flush",
  "rowsNow": 3205,
  "sample": 150,
  "retryCounts": [5],
  "groups": ["channel.opsync_flush.worker"],
  "oldest": "2026-09-02T12:32:01.813Z",
  "newest": "2026-09-02T19:20:05.431Z",
  "avgBytes": 187,
  "signatures": [
    { "text": "flush: resolve connection <id>: syncwire: connection <id> unresolvable", "n": 149, "share": 0.993 }
  ],
  "byDay": [ { "day": "2026-09-02", "n": 150 } ]
}
```

`rowsNow` is the number of the queue's dead-letter rows, so it can exceed `sample`. Signatures
are the top eight by count.

## GET /api/v1/analytics/partition-liveness

Tenant-scoped. Filters: `queue`, `namespace`, `task` (exact matches; an explicit empty
`namespace=` selects the queues without one), `limit` (default 20, clamped to 1 to 200). How
many of a queue's partitions are alive, counted from each partition's last write time in the
replicated state: no partition row crosses the wire, which is the difference from the queue
detail route on a queue with twelve thousand partitions.

```json
{
  "capturedAt": "2026-09-09T09:34:23.098Z",
  "rows": [
    {
      "queue": "smartchat.router.history", "namespace": "smartchat", "task": "core",
      "partitions": 12611, "live1h": 812, "live24h": 7252, "live7d": 12610,
      "created24h": 4823,
      "oldestWriteAt": "2026-09-02T08:41:00.000Z", "newestWriteAt": "2026-09-09T09:34:00.000Z",
      "pending": 0
    }
  ]
}
```

Rows are ordered by `partitions` descending. `pending` is the queue's unconsumed count, leased
messages included (`messages.pending` plus `messages.processing` on
[`/api/v1/status/queues`](/reference/http/status-metrics)). Partitions deleted in a window
are not here: that is `partitionsDeleted` on the workload route.

## GET /api/v1/analytics/system-metrics

**Cell-wide.** Filters: `from`, `to`, `hostname`, `workerId`. Host and process
gauges per node, re-aggregated into the window's buckets: `{timeRange, replicaCount, replicas,
bucketMinutes, pointCount}`, each replica with `hostname`, `port`, `workerId` (always
`"worker-0"`) and a `timeSeries` of `{timestamp, sampleCount, metrics}`. Every numeric leaf is
a `{avg, min, max, last}` object.

Populated blocks: `cpu.user_us` and `cpu.system_us` (percent × 100, so divide by 100
to plot a percentage), `memory.rss_bytes`, and `raft`, the node's log and store at each flush:
`inflight` (entries proposed or committed but not applied), `applied_lag`, `log_bytes`,
`log_files` and `map_used_pct` (how full the store's map is).

<Aside type="note">
Several blocks in this payload are not measurements on 2.0 and are kept for shape
compatibility. `database` (the 1.x connection pool) and `threadpool` are `null` in every
leaf, `memory.virtual_bytes` and `registries.response` read `0`, and every leaf of
`shared_state` is `null`. A chart should draw them as gaps.
</Aside>

## GET /api/v1/analytics/worker-metrics

**Cell-wide.** Filters: `from`, `to`, `queue`, `hostname`, `workerId`. Per-node throughput and
health as a time series.

```json
{
  "timeRange": { "from": "2026-07-30T09:44:00.000Z", "to": "2026-07-30T10:44:00.000Z" },
  "bucketMinutes": 1,
  "pointCount": 60,
  "timeSeries": [],
  "workers": [],
  "queues": [],
  "summary": {}
}
```

Each `timeSeries` point, newest first, carries `timestamp`, the interval deltas
(`pushMessages`, `popMessages`, `ackMessages`, `pushRequests`, `popRequests`,
`ackRequests`, `ackSuccess`, `ackFailed`, `dlqCount`, `dbErrors`), their
`pushPerSecond` / `popPerSecond` / `ackPerSecond` normalisations, the scheduler
("event loop") lag pair `avgEventLoopLagMs` / `maxEventLoopLagMs`, and the pop-lag
triple `avgLagMs` / `maxLagMs` / `lagCount`. `hostname` and `workerId` narrow `timeSeries`
only; `queue` is accepted and ignored.

Some fields carry no measurement on 2.0: `dbConnections`, `avgFreeSlots`, `minFreeSlots`,
`avgJobQueueSize`, `maxJobQueueSize` and `backoffSize` are always `null`, and `dbErrors` is
always `0` (nothing records it). `jobsDone` is the push-request count, so it equals
`pushRequests`. Do not chart them.

`workers` enumerates the nodes seen in the last 5 minutes, so a rolling restart shows the
nodes side by side. `queues` lists the queues in the window by pop count, and `summary` sums
every row the nodes still keep, whatever the window. Each node writes its own rows, so this is
where per-node skew that the cluster totals hide becomes visible.

## Access levels

| Route | Level | Tenant-scoped |
| --- | --- | --- |
| `GET /api/v1/analytics/queue-lag` | read-only | yes |
| `GET /api/v1/analytics/queue-ops` | read-only | yes |
| `GET /api/v1/analytics/queue-parked-replicas` | read-only | yes |
| `GET /api/v1/analytics/retention` | read-only | yes |
| `GET /api/v1/analytics/workload` | read-only | yes |
| `GET /api/v1/analytics/dlq-signatures` | read-only | yes |
| `GET /api/v1/analytics/partition-liveness` | read-only | yes |
| `GET /api/v1/analytics/system-metrics` | read-only | no |
| `GET /api/v1/analytics/worker-metrics` | read-only | no |

`read-only` here is the *route* level, not a tenancy boundary: the two cell-wide
routes will serve one tenant's read-only token the whole cell's numbers.
Restrict them at the proxy or the network. The aggregate status routes are on
[Status, health and metrics](/reference/http/status-metrics).
