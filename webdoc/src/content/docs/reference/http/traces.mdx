A trace is an application-written event attached to a message address. The broker
stores what you post and gives you three ways to read it back; it never writes
traces itself and never interprets the `data` you send. Use them to answer "what
happened to this message, in the words of the workers that handled it"
(retry reasons, external system responses, business checkpoints) for messages whose
payload alone does not explain their fate.

Traces live in the replicated state, keyed by tenant, partition and transaction id,
with an index by name. Recording one is one entry in the replicated log. That key is
why the address route takes the same two-segment address as the message routes.

## POST /api/v1/traces

Access level `read-write`. Required: `transactionId`. A missing or empty
`transactionId` is a `400` (`{"error":"transactionId is required"}`), and a body that is
not JSON is a `400` (code `bad_body`).

```json
{
  "transactionId": "order-4471",
  "partitionId": "0198e0f2-1c44-7b91-9c31-9a4b8f2ad001",
  "consumerGroup": "invoicer",
  "eventType": "retry",
  "data": { "reason": "downstream 503", "attempt": 2 },
  "traceNames": ["payment-failures", "order-4471"]
}
```

| Field | Default | Notes |
| --- | --- | --- |
| `transactionId` | required | Free text; not validated against any message. `transaction_id` is accepted too. |
| `partitionId` | none | The decimal partition id a pop answer carries, or the partition UUID. `partition_id` is accepted too. It must resolve among the caller's partitions (below). Without it the trace has no partition and can be read only by name. |
| `consumerGroup` | `null` | The group the event is attributed to, stored as given. |
| `eventType` | `"event"` | Free text. `type` is accepted too. |
| `data` | `null` | Any JSON value, stored as given. |
| `traceNames` | none | An array of labels. `names` is accepted too. Only its string elements are kept; any other value is ignored. |
| `traceId` | a new UUIDv7 | A UUID to use as the trace's id. |
| `messageId` | `null` | A message UUID stored with the trace. |
| `worker` | `null` | Free text naming the writer. |

Success is `201` with `{"success": true, "traceId": "0198..."}`. The trace is stamped
with the answering node's clock. A trace adds to storage, so it is refused like a push
when the node cannot take it: `507` (code `storage_full`) past the data disk's
high-water mark, and `429` (code `overloaded`) while write admission is full.

<Aside type="caution">
Nothing checks that the message exists. A trace is keyed by the address you send and
stored whether or not a message with that transaction id was ever pushed. A trace
posted for a transaction id that was never pushed is stored and returned by the read
routes exactly like a real one. Traces are evidence you produce, not evidence the
broker corroborates.
</Aside>

A `partitionId` is resolved among the caller's own partitions before anything is
written, because it arrives straight off the wire and a leaked or guessed id would
otherwise let anyone attach records to another tenant's messages. A foreign, unknown or
malformed `partitionId` gets `404` with `{"success": false, "error": "Partition not found"}`
and nothing is written.

## GET /api/v1/traces/:partitionId/:transactionId

All traces for one message address, newest first. Query: `limit` (default `200`,
clamped to 1 to 1000), `offset` (default `0`).

```json
{
  "traces": [
    {
      "traceId": "0198...",
      "trace_id": "0198...",
      "partitionId": "17",
      "partition_id": "17",
      "messageId": null,
      "message_id": null,
      "transactionId": "order-4471",
      "transaction_id": "order-4471",
      "consumerGroup": "invoicer",
      "consumer_group": "invoicer",
      "eventType": "retry",
      "event_type": "retry",
      "data": { "reason": "downstream 503", "attempt": 2 },
      "worker": null,
      "worker_id": null,
      "names": ["payment-failures", "order-4471"],
      "trace_names": ["payment-failures", "order-4471"],
      "createdAt": "2026-07-30T10:52:11.400000Z",
      "created_at": "2026-07-30T10:52:11.400000Z",
      "queue_name": "orders",
      "partition_name": "eu-1",
      "message_payload": null
    }
  ],
  "total": 1,
  "pagination": { "limit": 200, "offset": 0 }
}
```

The body also carries `events`, a copy of `traces`, left out above. Every trace carries
each field under two spellings, camelCase and snake_case, with the same value.
`partitionId` is the decimal partition id, the form pop answers carry; the address
route accepts it or the UUID. `queue_name` and `partition_name` are resolved from the
partition and are `null` once it is gone. `message_payload` is always `null`: use
`GET /api/v1/messages/:partitionId/:transactionId` to fetch the payload. See
[messages and DLQ](/reference/http/messages-dlq). `total` counts every match, not the
page.

An address with no traces returns an empty `traces` list at `200`, and so does a
partition that belongs to another tenant or does not exist: an empty set leaks nothing
about whether the partition exists elsewhere.

## GET /api/v1/traces/by-name/:traceName

Every trace of the caller's tenant carrying one label, newest first, in the same body
as the address route. Query: `limit` (default `200`, clamped to 1 to 1000), `offset`
(default `0`). `total` is the full count of the tenant's matches, not the page length.

This route is name-addressed, so there is no partition to gate on. A trace belongs to
the tenant that recorded it, and only the caller's tenant's traces are counted and
returned. A trace whose partition has been deleted is still returned here, with
`queue_name` and `partition_name` `null`.

## GET /api/v1/traces/names

The index of labels the caller's tenant has used, in name order.

Query: `limit` (default `100`, clamped to 1 to 1000), `offset` (default `0`).

```json
{
  "trace_names": [
    {
      "trace_name": "payment-failures",
      "trace_count": 214,
      "message_count": 173,
      "last_seen": "2026-07-30T10:52:11.400000Z"
    }
  ],
  "total": 4,
  "pagination": { "limit": 100, "offset": 0 }
}
```

`trace_count` counts traces, `message_count` counts distinct message addresses
(partition and transaction id), and `last_seen` is the newest trace's time. `total` is
the number of names. Only the caller's tenant's traces are counted: trace names are
caller-chosen text, so a global index would leak both the names and the activity times
of every other tenant.

## Operational limits

Three properties of trace storage that will surprise you eventually:

- **Traces expire.** The leader's retention pass (every `RETENTION_INTERVAL`
  milliseconds, default 5000) deletes traces older than `QUEEN_RAFT_TRACE_RETENTION_S`
  seconds (default 604800, 7 days). Message retention, the dead-letter purge and queue
  deletes do not touch traces. A tenant purge (`DELETE /api/v1/resources/tenant`)
  deletes the tenant's traces.
- **Deleting a queue leaves its traces behind** until they expire. They keep their
  tenant, so the by-name and names routes still return them; the address route no
  longer can, because the partition id no longer resolves.
- **The read routes walk every stored trace** and filter by tenant, address or name,
  so their cost grows with the node's total trace volume. If you trace at message
  rate, lower `QUEEN_RAFT_TRACE_RETENTION_S` to bound it.

## Access levels

| Route | Level |
| --- | --- |
| `POST /api/v1/traces` | read-write |
| `GET /api/v1/traces/:partitionId/:transactionId` | read-only |
| `GET /api/v1/traces/by-name/:traceName` | read-only |
| `GET /api/v1/traces/names` | read-only |

All four are tenant-scoped. Note the routing shape: `/api/v1/traces/names` is one
segment deep and cannot collide with the two-segment address route, but
`/api/v1/traces/by-name/:traceName` and
`/api/v1/traces/:partitionId/:transactionId` are both two segments deep and the
static `by-name` wins. A partition whose id were literally `by-name` would be
unreachable. Partition ids are numbers or UUIDs, so this is a routing fact rather than
a practical limit.
