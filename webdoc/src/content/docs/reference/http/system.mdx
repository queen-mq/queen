Everything on this page is an operator surface, not part of the client API. No SDK
calls these routes, and a tenant on a shared cell must never reach them.

`route_access_level` maps every path starting with `/api/v1/system/` to **admin**, plus
`/api/v1/stats/refresh` explicitly. That mapping only protects anything when JWT is on.

<Aside type="danger">
With `JWT_ENABLED=false` (the default), the authorization middleware is a
transparent pass-through and every one of these routes is open to anyone who can
reach the port. Several of them change how the whole cluster behaves: the kill switches
pause KV, timer scheduling or the ephemeral queues for every tenant, and the membership
routes decide which nodes vote. If the broker's port is reachable by anything you do not
fully trust, enable JWT or put a proxy in front of it.
</Aside>

None of these routes are tenant-scoped: the switches and the membership belong to the cluster,
not to a tenant. The membership routes go further and refuse a request that names a tenant.

## How the flags are stored

The kill switches below are flags in the replicated state: a `POST` is one entry in the
replicated log, and every node applies it. The request path checks an in-process copy of each
flag. The node that answered the `POST` sets its copy at once (in a cluster that is the leader,
because a follower forwards every `/api/` request to it), and a node reads the stored values when
it starts. A node that becomes leader later keeps the values it read at its start, so after a
leader change, send the flag again. The `GET` routes read the stored values.

An absent stored flag means **on**. That is the difference between a kill switch and a feature
flag, and getting it backwards would mean every fresh cell booting with a feature dead and no row
to explain why.

## The kv and timer kill switches

Access level **admin**, like every route under `/api/v1/system/`.

KV and timers have no boot flag. There is no variable that decides whether those routes exist, for
the same reason there is none for push and for pop, so nothing here is a way to opt into a feature.
What these three switches are is the other instrument entirely: "stop the bleeding, now", for an
incident that a rollout does not resolve.

That is why a paused surface answers **503** with `Retry-After` and never `404`: an operator pulled a
lever, it is temporary, and the client should come back. A `404` on a KV or timer path means the path
is wrong. The switches gate the KV and timer routes only: the `kv` and `timers` riders of
`POST /api/v1/transaction` are not checked against them.

### GET /api/v1/system/kv-timers

```json
{
  "kvEnabled": true,
  "timersScheduleEnabled": true,
  "timersFireEnabled": true,
  "quotaTenants": 0,
  "quotaAgeMs": null,
  "quotaHot": 0
}
```

The three `…Enabled` fields are the switches, and they are what `POST` writes. `quotaTenants`,
`quotaAgeMs` and `quotaHot` are fixed values kept for compatibility.

### POST /api/v1/system/kv-timers

```json
{ "timersSchedule": false }
```

| Field | Effect when `false` |
| --- | --- |
| `kv` | every KV route answers `503`. Nothing already stored is affected |
| `timersSchedule` | a `POST /api/v1/timers` batch that schedules anything answers `503`, whole, cancels in it included. The timers already scheduled still fire, and `DELETE /api/v1/timers/:queue/*timerKey` and the timer reads are never blocked |
| `timersFire` | stored and reported, but nothing reads it on 2.0 (see below) |

Each field is independent and an omitted one is left alone. A body that reset the unmentioned ones
would turn "pause new timers" into "and also stop delivering the ones already promised". The
answer is the same object as the `GET`. A body that is not an object is a `400`
(`{"error":"object required"}`), a field that is not a boolean is a `400` naming it, and a body
with none of the three is a `400`.

<Aside type="caution">
On 2.0, `timersFire: false` does **not** stop timers from firing. The flag is stored and the
`GET` reports it, but the state machine does not consult it when it fires a due timer. To stop
new timers arriving, use `timersSchedule: false`.
</Aside>

Every flip of any of the three writes a single `sweeper` log line on the node that flipped it,
naming the switch and what the operator has just done to the cell. It is on-change only, so a
switch that has been off for an hour does not write an hour of lines.

## The ephemeral kill switch

Same instrument, one switch, for the [ephemeral](/reference/http/ephemeral) route family: a flag
in the replicated state, an absent flag meaning **on**, and a paused surface answering `503` with
`Retry-After` rather than `404`.

### GET /api/v1/system/ephemeral

```json
{ "ephemeralEnabled": true }
```

### POST /api/v1/system/ephemeral

```json
{ "enabled": false }
```

```json
{ "ephemeralEnabled": false, "mirrored": true }
```

With `enabled: false` the six ephemeral verbs (push, pop, ack, reset and the two status reads)
answer `503`. The declaration routes, `POST /api/v1/ephemeral/configure` and
`DELETE /api/v1/ephemeral/queue/:queue`, are not paused. Consumers already parked stay parked
until their own timeout expires, the rings keep their memory until the idle collector reaches
them, and nothing stored durably is affected, because nothing of this class is stored durably
except the declarations. Turning it back on resumes service on rings that are, by then,
whatever the age and bound limits have left in them.

## Raft membership

Five routes change and report which nodes vote in a cluster. They need the openraft replicator
(`QUEEN_RAFT_REPLICATOR=openraft`): a node with the `local` replicator answers them `400` with
code `unsupported`. A request scoped to a tenant (`x-queen-tenant`, with tenancy on) is refused
with `403` and code `forbidden`. Every node answers them: a follower forwards them to the leader, and with no
leader known the answer is the usual `503` with `Retry-After: 1`.

The peer addresses are written into the membership, in the log, when the cluster first boots.
After that, `QUEEN_RAFT_PEERS` only supplies each node's own listen address: editing it does
not change who votes. These routes do.

| Route | Body | Answer |
| --- | --- | --- |
| `GET /api/v1/system/raft/membership` | none | `{"engine":"raft","membership":{...}}` |
| `POST /api/v1/system/raft/membership/learners` | `{"id":4,"raft":"host:port","http":"host:port"}` | `{"engine":"raft","ok":true,"membership":{...}}` |
| `POST /api/v1/system/raft/membership/promote` | `{"ids":[4],"force":false}` | same |
| `PUT /api/v1/system/raft/membership/voters` | `{"voters":[1,2,4],"force":false}` | same |
| `DELETE /api/v1/system/raft/membership/members/:id` | none | same |

`nodeId` is accepted for `id`, a single `id` for `ids` and a single `voter` for `voters`; `force`
can also be sent as `?force=true`. An empty body reads as `{}`.

The `membership` object: `nodeId` (the node that took the view), `source` (`leader`, or
`follower` for a follower's copy of the leader's view, `viewAgeMs` old), `leader`, `term`,
`voters`, `learners`, `joint` (the voter sets that must agree while a change is between its two
steps, else `null`), `membershipIndex`, `membershipCommitted`, `changeInFlight`, `lastLogIndex`,
`committedIndex`, `liveWithinMs`, `promoteMaxLag`, and `members`, each with `nodeId`, `voter`,
`raft`, `http`, `matched`, `lag`, `lastAckMs` and `live`.

A change runs on the leader and is checked before anything is written:

- **One change at a time.** A change still running, a joint configuration, or a membership entry
  not yet committed refuses with `in_flight`. A change another leader made in between refuses
  with `membership_changed` instead of being overwritten.
- **Quorum.** The voters after the change, and the voters before it, must each have a majority
  that acknowledged the leader within `liveWithinMs` (the leader counts as live). Otherwise
  `no_quorum`: a change that leaves the voters unable to commit would stop every write.
- **No empty cluster.** Removing the last voter is refused with `last_voter`.
- **Catch-up.** A learner becomes a voter only once it is within `promoteMaxLag` entries of the
  leader's last one (`QUEEN_RAFT_PROMOTE_MAX_LAG`, default `1000`), else `learner_behind`,
  unless `force`.

Every change is idempotent, so a caller that lost an answer can repeat it: adding a learner that
is already there with the same addresses, promoting a voter, removing a node that is not a member,
or setting the voters they already are, succeeds and writes nothing. A removed voter is dropped
from the membership, not kept as a learner: stop its process, and do not bring it back with its
data under the same id without adding it again. Adding a node is therefore two calls: add it as a
learner, then promote it once its `lag` is small.

`?timeoutMs=` bounds a change (1 ms to 120 s, default 30 s). Past it the answer is `504` with
code `timeout`, and the change may still complete: read the membership before repeating it. A
refused change answers `{"ok":false,"code":"...","error":"..."}`:

| Status | Codes |
| --- | --- |
| `409` | `in_flight`, `no_quorum`, `last_voter`, `learner_behind`, `already_voter`, `address_mismatch`, `membership_changed`, `leader_changed` |
| `400` | `bad_request`, `not_a_learner`, `not_a_member`, `unsupported` |
| `503` | `leader_unreachable`: the leader did not answer |

The read-only views of the cluster, `GET /api/v1/raft/status`, `/members` and `/liveness`, are on
[Status, health and metrics](/reference/http/status-metrics). The cluster walkthroughs are under
[Self-hosting](/deploy/).

## POST /api/v1/system/quota

Grants a tenant an allowance for a feature family and stores it as one entry in the replicated
log. `POST /api/v1/system/quotas` is the same route.

| Field | Meaning |
| --- | --- |
| `tenant` (or `tenantId`) | the tenant granted; defaults to the request's own tenant |
| `kind` | `kv`, `ephemeral` or `streams`; anything else is a `400` |
| `enabled` | default `true` |
| `maxRows`, `maxBytes`, `maxTimers`, `maxTimerHorizonSeconds`, `maxReadsPerSecond`, `maxWritesPerSecond`, `maxQueues`, `maxMessagesPerSecond`, `maxQueries` | the limits, each optional and non-negative; the snake_case spellings are accepted too |

The answer echoes the stored grant: `{"success":true,"tenant":...,"kind":...,"enabled":...}`
followed by every limit field, `null` where it was not sent. A negative limit is a `400`. For
the `kv` and `ephemeral` kinds the node that answered applies the grant at once, and a node reads
the stored grants when it starts. [KV and timers](/deploy/state/) shows the route in use.

## GET /api/v1/system/shared-state

```json
{
  "enabled": true,
  "reason": "raft_state_machine",
  "appliedIndex": 18342,
  "durableIndex": 18340,
  "queues": 12
}
```

`appliedIndex` is the last log entry this node has applied and `durableIndex` the entry its
last durable point covered. `queues` counts the queues of the request's tenant.

## POST /api/v1/stats/refresh

Access level **admin**. It answers `200` and does nothing:

```json
{ "success": true, "refreshed": false, "engine": "raft" }
```

The counters the status and resource routes report are maintained as log entries apply, so
there is nothing to refresh. The route exists because every SDK's admin API calls it.

## Protect the Raft RPC port

In a cluster each node also listens on its Raft RPC port for votes, log appends, snapshots, the
membership calls a follower forwards, and the dashboard's gather of the other nodes' rows. The
listener binds `0.0.0.0` on this node's Raft port unless `QUEEN_RAFT_LISTEN` says otherwise.

With `QUEEN_RAFT_TOKEN` set, every RPC carries it in the `x-queen-raft-token` header and every
node refuses a request without it. Without it, anyone who can reach the port can vote, append
and install snapshots. Set the same token on every node, and keep the port reachable by the
cluster's nodes only.

## No migration routes

There is no `/api/v1/migration/*` surface, and no route backs up or restores a node's data
directory.
