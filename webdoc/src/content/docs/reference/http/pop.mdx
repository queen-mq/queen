A pop claims a **leased batch**: a contiguous span of offsets right after the consumer group's
cursor in one or more partitions, held for a lease duration so no other worker in that group can
take them. It never removes anything. All three routes are `GET`, take their parameters in the
query string, have access level **read-write**, and return the same response shape.

| Route | Scope |
| --- | --- |
| `GET /api/v1/pop/queue/:queue` | one queue; the broker picks which partitions to claim |
| `GET /api/v1/pop/queue/:queue/partition/:partition` | exactly one partition |
| `GET /api/v1/pop` | discovery across every queue matching `namespace` and/or `task` |

## Query parameters

| Parameter | Type | Default | Applies to |
| --- | --- | --- | --- |
| `batch` | integer | `200` | all three |
| `partitions` | integer | `1` | `GET /api/v1/pop/queue/:queue` and discovery |
| `autoAck` | boolean | `false` | all three |
| `wait` | boolean | `false` | the two queue-scoped routes; see [Long polling](#long-polling) |
| `timeout` | integer, ms | `30000` | all three |
| `leaseSeconds` | integer | the queue's `leaseTime`, else `60`; `60` on discovery | all three |
| `consumerGroup` | string | `__QUEUE_MODE__` | all three |
| `subscriptionMode` | string | `new` (`DEFAULT_SUBSCRIPTION_MODE`) | all three |
| `subscriptionFrom` | string | empty | all three |
| `conflation` | boolean | `false` | all three |
| `autopilot` | boolean | `false` | `GET /api/v1/pop/queue/:queue` |
| `namespace` | string | empty | discovery only |
| `task` | string | empty | discovery only |

`batch` is the **total message budget for the call**, shared across every partition the pop
touches, not a per-partition limit. The budget is consumed partition by partition until it runs
out.

`partitions` caps how many partitions one call may claim. It is clamped to 1–64: `0` or a
negative value is read as `1`, and anything above 64 as `64`. It is ignored by the
single-partition route, which by definition claims one.

`timeout` is the long-poll deadline in milliseconds. Its default comes from `DEFAULT_TIMEOUT`,
falling back to `POP_DEFAULT_TIMEOUT_MS`, falling back to `30000`; `DEFAULT_TIMEOUT` wins when
both are set. It only has an effect when `wait=true`. The broker caps a request's deadline at
60000 ms, so a larger `timeout` waits 60 seconds.

`leaseSeconds` overrides the queue's configured lease for this call only. Values of `0` or less
are treated as absent. On the queue-scoped routes the queue's `leaseTime` then applies: **60
seconds** for a queue created implicitly by a push, **300 seconds** for one created through
`/api/v1/configure`. On the discovery route the default is 60 seconds whatever the matched
queues' `leaseTime`; send `leaseSeconds` to change it.

`consumerGroup` omitted means queue mode, which is implemented as the reserved group name
`__QUEUE_MODE__`. Queue mode is an ordinary group with a reserved name: it has its own cursor
like any other, and two consumers that both omit `consumerGroup` share it.

`subscriptionMode` and `subscriptionFrom` **seed a cursor that does not exist yet** and are
ignored for a `(partition, group)` that has already been contacted. `subscriptionMode=all`
starts at the oldest retained message; `new` (the default) skips the backlog stored before the
group's first pop; any other value is read as `all`. `subscriptionFrom` takes `now` or an
ISO-8601 timestamp, and starts at the first message stored at or after it; an unparseable
timestamp is ignored. Queue mode is deliberately excluded from seeding, so a queue-mode pop never
skips backlog even if it carries these parameters. A group's first pop on
`GET /api/v1/pop/queue/:queue` or on the discovery route registers the group with the
subscription that pop carried (the single-partition route registers a group only when it
conflates). From then on that stored subscription, or one registered through the consumer-group
routes, seeds the group's cursor on every partition it reaches, whatever later pops carry.

The discovery route requires at least one of `namespace` and `task`. With neither, it returns
`400` with `{"success":false,"error":"namespace or task is required","messages":[]}` rather than
scanning every queue.

One side effect to know about: a pop on `GET /api/v1/pop/queue/:queue` for a queue that does not
exist **creates the queue**, with the defaults a push would give it (`namespace` and `task`
derived from the dotted name, `leaseTime` 60), and registers the group on it before answering
204. That is deliberate, because a group may subscribe before the first push. It does mean a typo
in a consumer's queue name leaves an empty queue behind rather than nothing. The single-partition
and discovery routes create nothing.

## Conflation

`conflation=true` asks for **last-value delivery**: a pop of a partition returns
only that partition's newest visible message and commits everything below it when
you ack. It is for command-style queues where one partition is one logical key and
only the freshest "recompute X" matters. Under a backlog the handler runs once per
partition instead of once per message, and nothing on disk is touched: retention
still governs storage.

The guarantee it keeps is the one that matters:

> After the last push to a partition, at least one run of that partition's handler
> **starts after that push commits**.

The broker never commits past an offset it did not observe at pop time, so a
message that becomes visible after the claim is still pending afterwards and the
next pop delivers it.

**It is a property of the consumer group, not of the call.** The first pop that
registers the group on the queue persists the flag, and from then on the stored
value wins for every consumer of that group. A later consumer that disagrees does
not flip it: the stored policy is applied, and the response says so (see
[the two conflation keys](#conflation-in-the-response)). Changing a group's policy
means deleting and recreating the group. `/api/v1/configure` cannot set it: it is
a group policy, which is exactly what lets `workers` conflate while `audit` on the
same queue reads everything.

`partitions` defaults to `1`, and a conflating pop yields at most one message per
partition, so for a conflating group it is the partition cap, not `batch`, that
sizes a call. The broker therefore reads `partitions` as `batch` when you leave it
out, capped at **64**. A conflating pop returns at most 64 messages per round trip
whatever `batch` says.

Two combinations are refused with `400` rather than warned about, because the
silent version of each is unfixable in production:

| Refused | Why |
| --- | --- |
| `conflation=true` with no `consumerGroup` | queue mode is a shared cursor with no group identity to hang a delivery policy on |
| `conflation=true` with `autoAck=true` | auto-ack commits at delivery with no lease, so a failed handler loses the tail and the guarantee above degrades to at-most-once |

Composition with `subscriptionMode` is deliberate in both directions: `all` plus
conflation collapses the entire retained history to one message per partition
("rebuild the world once, then stay current"), `new` plus conflation skips the
history in the seed and delivers only live changes.

Retries are unaffected. The retry budget lives on the `(partition, group)` cursor
and is charged only by an explicit `failed` ack, so it survives supersession: a
poison partition under a hot producer still dead-letters on schedule, and the
message filed is the tail of the last attempt.

## Response

`200 OK` when at least one message is delivered:

```json
{
  "success": true,
  "queue": "orders.created",
  "partition": "customer-42",
  "partitionId": "17",
  "leaseId": "0198f2c1-9a7b-7d20-8e31-4c5d6e7f8a90",
  "consumerGroup": "billing",
  "messages": [
    {
      "id": "0198f2c1-4d3a-7c10-9f2b-6a1e5d0c7b83",
      "transactionId": "order-8891-created",
      "traceId": null,
      "data": { "orderId": 8891, "total": 4200 },
      "producerSub": null,
      "createdAt": "2026-07-30T11:02:44.512Z",
      "partitionId": "17",
      "partition": "customer-42",
      "leaseId": "0198f2c1-9a7b-7d20-8e31-4c5d6e7f8a90",
      "consumerGroup": "billing",
      "deliveryAttempt": 1,
      "offset": 8192
    }
  ],
  "partitionsClaimed": 1
}
```

### Top-level fields

| Field | Type | Meaning |
| --- | --- | --- |
| `success` | boolean | always `true` on a 200 |
| `queue` | string | the queue from the path; **empty string** on the discovery route, which spans queues |
| `partition` | string | the name of the **first** claimed partition |
| `partitionId` | string | the id of the **first** claimed partition |
| `leaseId` | string | the lease covering every message in this response; empty string when `autoAck=true` |
| `consumerGroup` | string | the group the pop used, `__QUEUE_MODE__` when you sent none |
| `messages` | array | the delivered messages, in offset order within each partition |
| `partitionsClaimed` | integer | how many partitions this call claimed |
| `conflation` | boolean | present, and always `true`, only when this pop was served under [conflation](#conflation) |
| `conflationConflict` | boolean | present, and always `true`, only when this request declared a conflation policy the group does not have |
| `autopilot` | object | present only when this request sent `autopilot=true` and the broker chose at least one knob for it: `partitions` and `batch` are the values the claim actually used |

A `partitionId` is the partition's numeric id written as a decimal string (`"17"`), not a UUID.
Treat it as opaque and send it back exactly as the pop returned it.

### Autopilot

`autopilot=true` asks the broker to choose the knobs you did **not** send.
`partitions` is the sweep width of one claim, and its right value is a fact about
the broker (how many partitions of this queue currently hold work for your group)
rather than about your consumer. It also moves: a queue's partition count grows,
so a number that was right when it was typed is wrong later.

The choice is **per parameter**. A knob you send is yours and is never
overridden: `autopilot=true&partitions=1` is a manual width of 1 with an
automatic batch. Send neither and both are chosen. Send both and nothing is,
which is exactly the request you would have sent without the flag.

What the node that serves the pop chooses, from the group's own state:

- `partitions`: the group's partitions that are ready now, divided among the group's
  autopilot pops in flight on that node, clamped to 1–64.
- `batch`: the group's measured drain rate (messages acknowledged per second of lease)
  times 200 ms, clamped to 100–1000. A group with no measurement yet starts at 100.
  `QUEEN_RAFT_AUTOPILOT_DRAIN_MS`, `QUEEN_RAFT_AUTOPILOT_BATCH_MIN` and
  `QUEEN_RAFT_AUTOPILOT_BATCH_MAX` move those three numbers.

A pop that omits `autopilot` is served, and answered, as if the parameter did not
exist, which is what every existing consumer relies on. The broker applies the choice only on
`GET /api/v1/pop/queue/:queue`, with or without a `consumerGroup`. The
single-partition and discovery routes accept the parameter and ignore it, since a
pinned pop is one partition by definition and has no width to choose. A conflating
pop ignores it too: it keeps its own meaning for `partitions`, the message budget
rather than a sweep width, so the feature that already owns that dimension keeps it.

### Conflation in the response

Both keys are emitted **only when true**, so the response to a pop that never
mentions conflation carries neither.

`conflation` reports what the broker **applied**, never what the request asked
for, and it rides every conflating response including empty ones. That is
load-bearing: no SDK negotiates a version with the broker, so a client that sends
`conflation=true` to a broker without conflation has the parameter silently ignored and
quietly drains the whole backlog one message at a time. The echo is the only
evidence there is, and because it is present on empty pops the client can raise on
its first round trip, before a single message is handled. Every SDK does exactly
that: requested conflation, no echo, no explanation, and the consume loop stops
with an error saying the broker did not apply conflation.

`conflationConflict` is the explanation that keeps that check from firing on a
disagreement. A group registered without conflation answers a `conflation=true`
consumer with `conflationConflict` and no `conflation` echo: the request was
understood, the stored policy won, the consumer keeps running and warns once. A
reject would take down the already-correct half of a rolling deploy, which is why
this is a warning and not an error.

Because those keys have to reach the client, a response that has anything to say
about conflation is a `200` with a body **even when it delivered nothing**: an
empty conflating pop, and an empty conflicting pop, are both `200`. That is the
steady state of a long-poll consumer on an idle queue, not an edge case.

The top-level `partition` and `partitionId` describe only the first claimed partition. When a
call claims several, they are **not** representative of the batch. Always ack using each
message's own `partitionId`.

### Per-message fields

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string (UUIDv7) | the message id assigned at push |
| `transactionId` | string | the deduplication key, and the address you ack with |
| `traceId` | string or `null` | `null` unless the message was written by a transaction that supplied one |
| `data` | any JSON value | the payload, spliced back verbatim; decrypted transparently if it was encrypted |
| `producerSub` | string or `null` | the `sub` of the JWT that pushed it, when authentication was on |
| `createdAt` | string | the creation time of the **write** that stored this message |
| `partitionId` | string | this message's partition id, the one to ack with |
| `partition` | string | this message's partition name |
| `leaseId` | string | repeated on every message for convenience; empty on `autoAck` |
| `consumerGroup` | string | repeated on every message |
| `deliveryAttempt` | integer | 1-based delivery count for this consumer group's current partition batch; increments when the same batch is redelivered after a nack or lease expiry, and is always `1` with `autoAck` |
| `offset` | integer | the message's absolute zero-based position in its partition |

`deliveryAttempt` belongs to the `(partition, consumerGroup)` claim, not to the stored message.
Every message from the same claimed partition in one response therefore carries the same value;
another partition in that response may carry a different one. Once the group advances to fresh
work, the count resets to `1`.

### What a popped message does not carry

These absences are deliberate and each one has a consequence:

- **No lease expiry timestamp.** You know the lease id, not when it dies. Use `leaseSeconds` (or
  the queue's `leaseTime`) as the budget you plan against, and
  [extend the lease](/reference/http/lease) if you need more.
- **No queue name.** Per message there is no `queue` field; on the queue-scoped routes the
  top-level `queue` covers it, but on the **discovery** route the top-level `queue` is empty, so
  a discovery consumer that needs to know which queue a message came from must map it from
  `partitionId` itself.
- **No headers or metadata envelope.** There is exactly one user-controlled field, `data`.
- **No status or DLQ flag.** `deliveryAttempt` describes redelivery of the current group claim;
  the remaining message state is a cursor per `(partition, group)`, not mutable state stored on
  the message.

`createdAt` is the time the leader stamped on the write that stored the message, not a
per-message clock. Every message one push stored in one partition carries the same value. The
wire value is UTC at millisecond precision with a literal `Z` suffix, so two writes within the
same millisecond can show the same `createdAt`. It orders writes, not messages; ordering inside
a partition is the offset order in which `messages` is returned.

`offset` is informational on the HTTP surface: acknowledgements are still addressed by
`transactionId`, not by an "ack through offset" parameter. It is the message's absolute position
in its partition, so partial and multi-write claims keep the absolute partition position rather
than restarting at zero.

### An empty pop is a 204 with no body

When nothing is delivered, the response is `204 No Content` with **no body at all**. There is
nothing to parse; check the status first. Two different situations produce that same bare 204:

1. Nothing is available for this group. That includes a queue or, on the single-partition route,
   a partition that does not exist, and messages held back by a
   [visibility delay](#visibility-delays).
2. A long poll (`wait=true`) whose `timeout` elapsed.

The one exception is a request that mentioned [conflation](#conflation). Dropping
the body there would drop the echo the client uses to tell a broker that conflates
from one that does not, and it would read the silence as a version mismatch and stop
consuming on an idle queue. So a pop whose answer has anything to say about
conflation keeps its `200` and its body:

- an empty **conflating** pop: `{"messages":[],"conflation":true, ...}`
- an empty **conflicting** pop: `{"messages":[],"conflationConflict":true, ...}`

A pop that fails does not look like an empty one: it answers with an error status and a body.
An error raised by the state machine is `{"error":"…","code":"…"}`.

| Code | When |
| --- | --- |
| `200` | at least one message delivered, or the answer carries a conflation key |
| `204` | nothing delivered (no body) |
| `400` | discovery pop with neither `namespace` nor `task`; `conflation=true` without `consumerGroup` or with `autoAck=true`; a query parameter that fails to deserialize |
| `403` | authentication is on and the token has no `read-write` role |
| `413` | code `name_too_long`: the tenant, queue and the longer of the consumer group and partition names together exceed 447 bytes |
| `503` | code `no_leader`, `retry` or `timeout`, with `Retry-After: 1` |
| `500` | code `internal`: a broker fault, for example a stored payload the node cannot read |

## Leases and concurrency

A non-`autoAck` pop takes a lease on the span `(committed, batch_end]` for the
`(partition, group)` pair, and the lease id is the id the pop minted for itself: every partition
one pop claims shares it. Exactly **one live leased batch exists per `(partition, group)`**.
That is the ordering guarantee, and it is also the concurrency limit: a queue with one partition
cannot be consumed in parallel by one group, no matter how many workers poll it. Parallelism
comes from having more partitions.

Other workers polling a leased partition are not blocked. They skip it and look elsewhere,
which is why a wildcard pop with `partitions=1` and many hot partitions still spreads out
across workers.

When the lease expires without an ack, the batch becomes claimable again and redelivers. Lease
expiry **never** consumes retry budget; only an explicit `failed` ack does. That is at-least-once
delivery: design handlers to tolerate a repeat.

`autoAck=true` is different in kind. The cursor is committed by the same log entry that records
the claim, before the response is written, and the response carries an empty `leaseId`. If the
client dies after that commit and before it processes the batch, those messages are gone:
at-most-once. Use it for throughput on data you can afford to lose, never for work you must not
drop.

## Long polling

With `wait=false` (the default) a pop is a single attempt: it returns whatever is claimable now,
otherwise 204.

With `wait=true` a pop on one of the two queue-scoped routes parks until messages arrive or
`timeout` elapses. The discovery route does not park: with nothing to deliver it answers 204 at
once, whatever `wait` says.

A parked pop waits on the node that serves it. When an entry applies on that node that makes one
of the group's partitions claimable (a push appending to it, or an ack releasing a lease), one
parked pop of that group is woken and claims again. A pop parked on the single-partition route is
woken by any push to its queue. Work that becomes claimable only because time passed, such as an
expired lease or a message crossing its `delayedProcessing` deadline, wakes nobody: a parked pop
finds it on its periodic re-check, every `QUEEN_RAFT_POP_PARK_RECHECK_MS` (default 5000 ms).
With less than `QUEEN_RAFT_POP_SUBMIT_MIN_MS` (default 100 ms) of `timeout` left, a parked pop
does not claim again, so nothing is leased for a caller that is about to give up.

A long poll that times out returns 204, not an error.

## Visibility delays

Two queue options can make a message that is committed still not deliverable:

- `delayedProcessing`: only messages stored at least that many seconds ago are delivered.
- `windowBuffer`: if the partition received anything within that many seconds, the pop delivers
  **nothing** from that partition, so writes can accumulate into fatter batches.

The leader applies both when it plans a claim, so they apply to every pop route. If a pop returns
204 on a queue you wrote to a moment ago, check these before anything else. A parked long poll notices
the end of either delay on its periodic re-check, not at the instant it ends.

`minPopWaitTime` is accepted by `/api/v1/configure` and stored with the queue, but the 2.0 pop
path does not read it: it has no effect on delivery.
