Most of Queen's limits exist to keep one request from costing everyone else: a body cap, a ceiling
on what one log entry may carry, a budget on how much a KV call may read. Few of them are about the
data itself. The broker puts no cap on partitions per queue, on queues per tenant, or on how long a
partition's history may grow: your disk and your memory bound those, and a proxy plan can cap them
per tenant (see [tenants](/manage/tenants/)).

Each limit below comes with the setting that moves it, when there is one, and the file that
applies it. The values are the defaults of server 2.7.0; the full list of settings is on
[configuration](/reference/configuration/).

## Requests

| Limit | Default | Setting | Applied in |
|---|---|---|---|
| Request body | 64 MiB | `QUEEN_MAX_BODY_BYTES` | `server/src/handlers/raft.rs` |
| One planned command (a push to one partition, a KV call, a timers call, a positions list) | 96 MiB | `QUEEN_RAFT_ENTRY_MAX_BYTES` | `server/src/rsm/planner/push.rs` |
| Message `payload` | any JSON value, inside the two limits above | | `server/src/rsm/facade/real.rs` |
| Items per push | 10,000; more is refused 400 `too_many_items` | `QUEEN_PUSH_MAX_ITEMS` | `server/src/rsm/facade/real.rs` |
| An admin command that touches many rows: a DLQ purge, a seek, a group, queue or tenant delete, a streams reset | sent as commands of at most 4,096 rows each; one still over `QUEEN_RAFT_ENTRY_MAX_BYTES` is refused `too_large` | | `server/src/rsm/facade/real/phase2/admin.rs` |
| `transactionId` | 65,535 bytes | | `server/src/rsm/facade/real.rs` |
| Deadline of a push | 30 s, at most 60 s | `POP_DEFAULT_TIMEOUT_MS` | `server/src/handlers/raft.rs` |
| Deadline of an ack, a lease extension or a transaction | 30 s, at most 60 s | `QUEEN_STMT_TIMEOUT_MS` | `server/src/handlers/raft.rs` |

The pushes to one partition travel as one command, so items for one partition that together exceed
the command limit are refused, and those items answer `status: "error"` in the 201 body.

## Memory and connections

| Limit | Default | Setting | Applied in |
|---|---|---|---|
| The node's memory limit, which the guard below compares the process's anonymous memory with | the cgroup's `memory.max`; with neither, the guard is off | `QUEEN_MEMORY_LIMIT_BYTES` | `server/src/memguard.rs` |
| Large reads (message, dead-letter and trace pages, analytics, status, resources and KV listings, consumer groups, stream states, fetch) answer 503 `memory_pressure` | past 80 % of the limit | `QUEEN_MEMGUARD_SOFT_PCT` | same |
| Writes that grow the stored state (push, transaction, stream cycle, KV, timer and trace writes) answer 503 `memory_pressure` too | past 90 % | `QUEEN_MEMGUARD_HARD_PCT` | same |
| Large reads served at once; one that waits 2 s for a slot answers 503 `busy` | 32 | `QUEEN_HEAVY_READS_MAX` | same |
| Open connections on the broker port; past it a new one is closed as it is accepted | 20,000 | `QUEEN_MAX_CONNECTIONS` | `server/src/main.rs` |
| Time to send a request's head, and to send a next request on a kept-alive connection | 120 s | `QUEEN_HTTP_HEADER_READ_TIMEOUT_MS` | same |
| Long polls waiting at once on a node; past it a pop answers empty at once, and the client polls again | 50,000 | `QUEEN_MAX_PARKED_POPS` | `server/src/rsm/consume/wait.rs` |
| Pops and acks a follower has in flight to the leader | 64 MiB | `QUEEN_RAFT_FWD_DRAIN_INFLIGHT_MB` | `server/src/rsm/replicator/raft/forward.rs` |

Pops, acks, renewals, deletes, `/health`, metrics and Raft are never refused by the memory guard,
so a node near its limit can still be drained. The refusals carry `Retry-After`, 1 to 5 s, which
every SDK waits out.

<Why>a broker that runs out of memory loses every client at once, and its data is reloaded into
memory at start. Refusing the requests that would grow it first keeps the node up while the cause
is found.</Why>

## Names

| Name | Rule | Applied in |
|---|---|---|
| Queue, partition, consumer group | No character rules. Tenant + queue + the longer of partition and group: at most 447 bytes. The tenant id is 36 bytes, which leaves 411 for the queue and the longer of the other two. Over it: 413 `name_too_long`. | `server/src/rsm/facade/mod.rs` |
| Partition, when not named | `Default` | `server/src/rsm/facade/real.rs` |
| Consumer group, when not named | `__QUEUE_MODE__` (queue mode) | `server/src/rsm/facade/real.rs` |
| Queue namespace and task, for a queue a push creates | The first and second dot-separated parts of the queue name | `server/src/rsm/planner/timers.rs` |
| KV namespace (`ns`) | `^[a-z0-9][a-z0-9._-]{0,63}$` | `server/src/rsm/planner/kv.rs` |
| KV key | 1 to 512 bytes, no NUL, and tenant + namespace + key within the store's 511-byte key | `server/src/rsm/planner/kv.rs` |
| Position metadata | 4096 bytes | `server/src/rsm/planner/positions.rs` |

A request with a name that breaks these rules is refused 413 `name_too_long` before anything is
written. The broker measures every key the command makes from a name: a `0x00` byte is stored as
two, and a consumer group's counters and the timers' due index add a few bytes to the key they
start from.

<Why>a store key longer than LMDB's 511 bytes fails when the command is applied, on every node, and
again at every restart. Before 2.7.0 one such request stopped the cluster.</Why>

## Queues, leases and retries

A queue created by its first push (or by a timer firing into it) and a queue created with
`POST /api/v1/configure` start with different lease times:

| Option | Created by a push | Created by `configure` | Applied in |
|---|---|---|---|
| `leaseTime` | 60 s | 300 s | `server/src/rsm/planner/timers.rs`, `server/src/rsm/facade/real/phase2.rs` |
| `retryLimit` | 3 | 3 | same |
| `deadLetterQueue` | on | on | same |
| `dedupWindowSeconds` | 3600 | 3600 | same |
| `retentionEnabled` | off | off | same |

A pop's `leaseSeconds` overrides `leaseTime` for that pop, and
`POST /api/v1/lease/:leaseId/extend` extends by `seconds`, 60 by default. `configure` merges by
default: an option you leave out keeps its value, and `null` restores its default. With
`"mode": "replace"`, every option you leave out goes back to its default.

## Dead letters

| Limit | Default | Setting |
|---|---|---|
| Dead letters kept in one queue | 100,000 | `QUEEN_DLQ_MAX_ROWS_PER_QUEUE` |
| Bytes of one queue's dead letters, estimated from its oldest ones | 1 GiB | `QUEEN_DLQ_MAX_BYTES_PER_QUEUE` |
| Age of a dead letter | 14 days | `QUEEN_DLQ_MAX_AGE_S` |

Past any of the three the oldest dead letters go first, at most 1,024 per maintenance pass. `0`
turns a cap off. Applied in `server/src/rsm/maintenance.rs`.

<Why>a dead letter is a full copy of its message, in memory on every node and reloaded at start.
Before 2.7.0 only a delete removed one, so a consumer that failed every message filled the nodes'
memory as fast as it failed.</Why>

## Dedup

| Limit | Default | Setting | Applied in |
|---|---|---|---|
| Dedup window, per queue, checked per partition | 3600 s; `0` turns dedup off; at most 7 days, and a longer window is cut to it, also on a queue configured before | `dedupWindowSeconds` on `configure`, `QUEEN_MAX_DEDUP_WINDOW_S` | `server/src/rsm/planner/push.rs`, `server/src/rsm/facade/real/phase2.rs` |
| How long the hashes behind it are kept | the window, and never less than 900 s | `QUEEN_RAFT_TXN_WINDOW_MIN_S` | `server/src/rsm/maintenance.rs` |
| How long a push keeps its index row in memory | the same time, then the row goes even if the message stays (cluster version 6) | `QUEEN_RAFT_ROWS_WINDOW` | `server/src/rsm/maintenance.rs` |
| A committed command answers a retry of its request id | 60 s | `QUEEN_RAFT_REQUEST_ID_WINDOW_S` | `server/src/rsm/batcher.rs` |

Two items with the same `(queue, partition, transactionId)` in one request store one message,
whatever the window.

## Pop and long-poll

| Parameter | Default | Bound | Applied in |
|---|---|---|---|
| `batch` | 200 | 10,000 messages and 64 MiB of payloads (`QUEEN_POP_MAX_BATCH`, `QUEEN_POP_MAX_BYTES`); always at least one message | `server/src/frames.rs` |
| `partitions` (wildcard pop) | 1 | 1 to 64 | `server/src/handlers/data.rs` |
| `timeout` with `wait=true` | 30,000 ms (`POP_DEFAULT_TIMEOUT_MS`) | 60 s | `server/src/handlers/raft.rs` |

A pop that finds nothing before its timeout answers `204`.

Through the proxy built into the binary, three timers in one process bound a pop with `wait=true`.
The broker waits at most 60 s (300 s for an ephemeral pop) and answers `204`. The proxy waits
`min(timeout, QUEEN_PROXY_LONGPOLL_MAX_MS)` plus `QUEEN_PROXY_LONGPOLL_MARGIN_MS`, 100 s at most by
default, then answers 504 `upstream_timeout`. The edge waits `timeout` plus
`QUEEN_EDGE_LONG_POLL_GRACE_MS`, at most `QUEEN_EDGE_LONG_POLL_MAX_MS` (310 s), then answers 504
`request_timeout`. A durable pop always ends at the broker. An ephemeral pop that asks for more than
100 s ends at the proxy with a 504, unless `QUEEN_PROXY_LONGPOLL_MAX_MS` is raised to `300000`.

## KV

| Limit | `POST /api/v1/kv` and the KV routes | Inside a transaction | Setting |
|---|---|---|---|
| Value | 64 KiB as compact JSON | the same | `QUEEN_KV_MAX_VALUE_BYTES` |
| Operations per call | 256 | 64 | `QUEEN_KV_MAX_OPS_PER_CALL` (routes only) |
| Keys named per call | 1024 | 256 | `QUEEN_KV_MAX_KEYS_PER_CALL` (routes only) |
| `getPrefix` `limit` | 100 by default, at most 1000 | not allowed | |
| Bytes read per call | 4 MiB | 4 MiB | |
| Writes of one key per call | 1 | 1 | |
| Expiry | `ttlSeconds` above 0 or `forever: true`, required on every `put`, `putIfAbsent` and `incr` | the same | |
| `check` | needs cluster format version 5 (503 below it) | the same | |
| Calls per tenant | reads 200/s (burst 400), writes 100/s (burst 200) | writes 10,000/s (burst 20,000), on the same quota | `QUEEN_KV_READ_RATE`, `QUEEN_KV_READ_BURST`, `QUEEN_KV_WRITE_RATE`, `QUEEN_KV_WRITE_BURST`; in a transaction `QUEEN_KV_TXN_WRITE_RATE`, `QUEEN_KV_TXN_WRITE_BURST` |

A call over a tenant's rate answers 429 `rate_limited`, a transaction too, and writes nothing.
The writes of a transaction (a `once()` gate, a `kv` rider) have their own rate because a gate per
step runs at the app's step rate; the Kafka facade's own rows are not counted. A tenant's quota row can set its own rates
and row and byte caps; see [tenants](/manage/tenants/).

## Streams

| Limit | Value |
|---|---|
| Partitions in one `POST /streams/v1/claim` | 1 to 1,000 |
| The lease a claim gives | 30 s, or `lease_seconds` from 1 to 600 |
| Partitions per page of `POST /streams/v1/state/partitions` | 1,000, or `limit` up to 10,000 |
| State rows one `state/partitions` call reads | 100,000, then it stops at the next partition and answers `next` |

Why: a claimed partition waits for its lease to end if the runner that claimed it stops, so the lease
is short; and a query with a large state answers in pages instead of one long read. Applied in
`server/src/rsm/facade/real/phase2.rs`.

| Limit | `POST /streams/v1/cycle` | Setting |
|---|---|---|
| One state value | 16 MiB of JSON. A cycle with a larger one answers 413 `state_too_large` and stores nothing | `QUEEN_STREAMS_MAX_STATE_BYTES` |
| State operations in one cycle | 10,000. More answers 413 `too_many_state_ops` and stores nothing | `QUEEN_STREAMS_MAX_STATE_OPS` |
| One state key | a key that would make a store key over 511 bytes (about 485 bytes of key) answers 400 `state_key_too_long` | |

Why: a window's state is read and written whole on every cycle of its partition, so its size is
paid on every event. Keep large data out of the state: put it in a message or your own storage, and
keep a reference. Applied in `server/src/rsm/facade/real/phase2/streams.rs`.

`QUEEN_STREAMS_STATE_TTL_S` removes the state rows nobody wrote for that many seconds. It is off by
default, because a window may rightly stay open longer than any default would guess.

## Locks

A lock is a KV row in the namespace `queen-locks`, so the KV value, rate and quota limits above
apply to it. The route's own limits are constants in `server/src/locks.rs`.

| Limit | `POST /api/v1/locks` |
|---|---|
| Operations per call | 64, each on a different lock |
| Permits of one semaphore (`limit`) | 1 by default (a lock), at most 1,024 |
| Slots named per call | 4,096 (an `acquire` counts its `limit`, a `get` 1,000) |
| Lock name | 1 to 256 bytes, no control character, no `#` |
| `owner` | at most 256 bytes, no control character |
| Lifetime | `ttlSeconds`, a whole number above 0, required on every `acquire` and `renew`; there is no `forever` |
| Calls per tenant | a call with an `acquire`, `renew` or `release` spends one token of the KV write rate; a call of `get`s alone, one of the read rate |

A waiting `acquire` in the SDKs comes back every 100 ms to 1 s, with jitter, and the handles that
renew in the background do so every third of the lifetime.

## Timers

| Limit | `POST /api/v1/timers` | Inside a transaction | Setting |
|---|---|---|---|
| Horizon (`delayMs`) | 90 days, narrowed by a tenant's quota | 90 days | `QUEEN_TIMERS_MAX_HORIZON_S` |
| Payload, decoded | 1 MiB | 1 MiB | `QUEEN_TIMERS_MAX_PAYLOAD_BYTES` |
| Operations per call | 256 | 256 | `QUEEN_TIMERS_MAX_OPS_PER_CALL` (the route only) |
| Schedules per tenant | share the KV write rate | not counted | `QUEEN_KV_WRITE_RATE` |
| One `(queue, timerKey)` per call | yes | yes | |

The leader fires due timers every 50 ms (`QUEEN_RAFT_TIMER_TICK_MS`), at most 256 timers and 4 MiB
per tick. A fire that fails is retried with a backoff from 1 s to 60 s, and after 5 failed
attempts (`QUEEN_SWEEPER_MAX_ATTEMPTS`; transient failures are not counted) the timer is
dead-lettered into its queue's DLQ.
