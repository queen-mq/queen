This is the contract a Kafka client gets from Queen, in the form you check things against: the
settings the facade reads, what it does with topic configs, the APIs and versions it answers, the
places where it knowingly behaves differently from Apache Kafka, and what each client library needs.
How it all fits together, with a working example, is on [Kafka clients](/integrations/kafka/).

```bash
QUEEN_KAFKA_EMBEDDED=true
QUEEN_KAFKA_ADVERTISED_ADDR=kafka-1.example.internal:9092   # required: what clients dial for this node
```

## Settings

Read once, when the node starts. An empty value counts as unset, and a value that does not parse or
is out of range stops the node with the variable's name, except for `QUEEN_KAFKA_THREADS` and
`QUEEN_KAFKA_SHUTDOWN_GRACE_MS`, which fall back to their defaults.

| Variable | Default | What it does |
|---|---|---|
| `QUEEN_KAFKA_EMBEDDED` | `false` | `true` runs the facade inside the broker. Nothing below is read otherwise. |
| `QUEEN_KAFKA_ADDR` | `0.0.0.0:9092` | The address the Kafka listener binds. |
| `QUEEN_KAFKA_ADVERTISED_ADDR` | none, required | The `host:port` clients dial for this node. A value without a port is refused at boot. |
| `QUEEN_KAFKA_PEERS` | unset | The address the other nodes are advertised at, `1=host:port,2=host:port`, by raft node id. Unset, a node is advertised at the host of its raft address with this node's Kafka port, which is the shape of a StatefulSet (one headless name per pod, one port everywhere). |
| `QUEEN_KAFKA_THREADS` | `min(4, cores / 2)`, at least 1 | Threads of the facade's own runtime. |
| `QUEEN_KAFKA_DEFAULT_PARTITIONS` | `1024` | The width of a topic created without one, 1 to 100,000. |
| `QUEEN_KAFKA_AUTO_CREATE` | `true` | Metadata creates a topic it does not know when the client allows it. |
| `QUEEN_KAFKA_DEDUP_WINDOW_SECONDS` | `900` | The dedup window of a topic the facade creates, and of a topic without one when an idempotent producer first writes to it, 0 to 604,800. A producer retries a batch for at most `delivery.timeout.ms` (2 minutes by default), so a longer window catches no retry. `0` leaves every topic as it is. |
| `QUEEN_KAFKA_GROUP_JOIN_DELAY_MS` | `3000` | How long the first join of an empty group waits for more members (Kafka's `group.initial.rebalance.delay.ms`), 0 to 300,000. |
| `QUEEN_KAFKA_SASL` | unset | `plain` (or `required`) makes every connection log in with SASL/PLAIN before it may send anything but ApiVersions and the SASL handshake ([security](#security)). `off`, or unset: no login. Any other value stops the node. |
| `QUEEN_KAFKA_MAX_CONNECTIONS` | `10000` | Connections served at once, 1 to 1,000,000. Past it a new connection is closed, with a line in the node's log, and the client tries again. |
| `QUEEN_KAFKA_MAX_REQUEST_BYTES` | `104857600` (100 MiB) | The largest request frame, 1 MiB to 1 GiB (Kafka's `socket.request.max.bytes`). A larger one closes the connection. Before a client logs in with SASL a frame is at most 512 KiB. |
| `QUEEN_KAFKA_FRAME_READ_TIMEOUT_MS` | `30000` | How long the rest of a frame may take once its first byte arrived, 100 to 3,600,000. A slower one closes the connection. |
| `QUEEN_KAFKA_IDLE_TIMEOUT_MS` | `600000` | A connection that sends no request for this long is closed (Kafka's `connections.max.idle.ms`), 1,000 to 86,400,000. |
| `QUEEN_KAFKA_INFLIGHT_BYTES` | `268435456` (256 MiB) | The request frames every connection together may hold at once, 1 MiB to 64 GiB. A frame waits in its socket until there is room. |
| `QUEEN_KAFKA_FETCH_MAX_BYTES` | `52428800` (50 MiB) | The most one Fetch answer carries, whatever the request asks (Kafka's `fetch.max.bytes`), 1 KiB to 1 GiB. |
| `QUEEN_KAFKA_METADATA_MAX_PARTITIONS` | `100000` | The partitions one Metadata answer lists, 1 to 10,000,000; the topics past it are answered with an error. One request creates at most 16 topics by itself. |
| `QUEEN_KAFKA_GROUP_MAX_MEMBERS` | `1000` | The members one consumer group may have (Kafka's `group.max.size`), 1 to 1,000,000. |
| `QUEEN_FETCH_TOPIC_WAKE_MS` | `5` | How long a parked fetch that has read nothing waits at least before it answers, empty, because another partition of its topic was written on the node, 0 to 30,000. `0` parks it on its own partitions only. Read by the broker, so `POST /api/v1/fetch` behaves the same. |
| `QUEEN_KAFKA_SHUTDOWN_GRACE_MS` | `5000` | How long a stopping node waits for the facade to close. |

## Topic configs

A topic is a Queen queue. Of the configs a client sends with CreateTopics, two become the queue's
settings, as they did before 2.6; the others are accepted and not applied yet.

| Config | Accepted | What it does |
|---|---|---|
| `retention.ms` | `-1` (default), or 1000 and more | The queue's retention (`retentionSeconds`), rounded down to whole seconds. `-1` keeps every record. Less than a second is refused with `INVALID_CONFIG`, because it would round to nothing. |
| `cleanup.policy` | `delete` (default), `compact`, `compact,delete` | `delete` lets `retention.ms` delete by age. `compact` keeps every record whatever `retention.ms` says, because Queen does not compact and the last value of every key has to stay. `compact,delete` deletes by age and compacts nothing. Anything else is refused with `INVALID_CONFIG`. |
| Anything else | | Accepted, not applied. |

A topic created on first use, by a metadata request, has no configs and keeps every record. The
facade also sets the queue's dedup window to `QUEEN_KAFKA_DEDUP_WINDOW_SECONDS`. The configs are read
at creation only: AlterConfigs and IncrementalAlterConfigs are not offered in 2.7, so change a
topic's retention afterwards through Queen ([queue options](/writing-applications/queues/)),
and DescribeConfigs answers no entries.

## Where it differs from Apache Kafka

- The cluster a client sees is the raft cluster: every voter is a broker and an in-sync replica of
  every partition, and the raft leader leads every partition and coordinates every group and every
  transactional id. Produce, Fetch, ListOffsets and the group and transaction APIs reach the leader;
  another node answers `NOT_LEADER_OR_FOLLOWER` or `NOT_COORDINATOR` and the client asks again.
- A transactional id nobody used for 7 days is forgotten, as Kafka's
  `transactional.id.expiration.ms` does by default: its next InitProducerId starts it again with a
  new producer id. Each id is coordinated on its own, so a slow commit holds back only its producer.
- Inside a transaction, a produce answers offset `-1`, because no offset exists until the commit.
  The transaction's records wait in the leader's memory and its commit writes them, with its
  offsets, as one raft entry. There are no commit markers, so a committed transaction of N records
  advances the log by N and an aborted one by 0, and `read_committed` and `read_uncommitted` read the
  same records. A leader change aborts the transactions that were open on the old leader.
- An idempotent producer's record is deduplicated by Queen's dedup window: its producer id, epoch
  and sequence are its Queen transaction id, so a retry within the window writes nothing. There is
  no per-partition sequence check, so a gap in a producer's sequence is not refused.
- `acks=1` is `acks=all`. `acks=0` gets no answer; an error closes the connection instead.
- CreateTopics refuses names that begin with `__`.
- Every leader epoch is 0. OffsetForLeaderEpoch is not offered, and clients skip truncation detection
  against a broker without it.
- A timestamp lookup (ListOffsets with a time) is answered on the broker's append clock, and the
  records carry the producer's timestamps ([details](/integrations/kafka-frameworks/)).
- Committed offsets are the Queen consumer group's positions and never expire. DeleteGroups
  removes a group with no members and its position on every queue.
- Group membership is held in the leader's memory. When the leader changes, members are told
  `NOT_COORDINATOR` or `UNKNOWN_MEMBER_ID`, rejoin at the new leader and resume from their committed
  offsets, the same sequence as a Kafka coordinator failover.
- A group with no members leaves the leader's memory ten minutes after its last member left.
  ListGroups stops listing it and DescribeGroups answers `Dead`; its committed offsets stay, and a
  member that joins later starts it again at generation 1. Kafka lists an empty group as `Empty`
  until its offsets expire, seven days by default.

### Known issues in 2.6

- Right after a topic is created through another node, the leader can answer
  `UNKNOWN_TOPIC_OR_PARTITION` to ListOffsets and DescribeConfigs for up to a second.
- Metadata auto-creation does not refuse names that begin with `__`, as CreateTopics does, so a
  client that asks for `__consumer_offsets` with auto-creation on creates a queue of that name.

A client running in a container dials the advertised address too, so the node has to advertise one
the container can reach, such as `host.docker.internal:9092`; `localhost` there is the container
itself. A consumer configured for the KIP-848 group protocol (`group.protocol=consumer`) or for
static membership (`group.instance.id`) fails when it joins, with an error from the client.

## Security

There is no TLS listener in 2.6: keep the Kafka port on a private network, or put a TLS-terminating
TCP proxy in front of it. With `QUEEN_KAFKA_SASL=plain`, a client logs in with SASL/PLAIN: the
password is a Queen token, the one an SDK sends as `Authorization: Bearer`, and the username is a
label for the logs. Until a connection has logged in it may only negotiate versions and
authenticate; anything else closes it. Without TLS, SASL puts tokens on the wire in clear.

```properties
bootstrap.servers=kafka-1.example.internal:9092
security.protocol=SASL_PLAINTEXT
sasl.mechanism=PLAIN
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required \
  username="orders-service" password="<a Queen token>";
```

Every call a connection makes into the broker carries the token it logged in with, and the broker
authorizes it as it authorizes the HTTP route of the same operation. A connection that did not log
in carries none: on a broker that checks tokens (`JWT_ENABLED`) its calls are refused, so turn SASL
on there, and on a broker that does not, every password is accepted.

## Ceilings

Compiled in, and listed because each one explains an answer you might otherwise have to guess at.

| Ceiling | Value | What happens past it |
|---|---|---|
| A request frame | `QUEEN_KAFKA_MAX_REQUEST_BYTES` (100 MiB) | The connection closes. |
| One produce request, decompressed | 256 MiB or 2,000,000 records | The partition that crosses it is refused. |
| Topic width | 100,000 partitions | CreateTopics and CreatePartitions answer `INVALID_PARTITIONS`. |
| Session timeout a consumer asks for | 1 second to 1 hour | `INVALID_SESSION_TIMEOUT`. |
| One transaction | 8 MiB, 50,000 records, 1,000 partitions | A produce past the bytes or the records answers `MESSAGE_TOO_LARGE`; a partition past the thousandth answers `INVALID_TXN_STATE`. |
| Every open transaction on the leader, together | 256 MiB | A produce into a transaction answers `MESSAGE_TOO_LARGE` until others end. |
| `transaction.timeout.ms` | 1 hour | `INVALID_TRANSACTION_TIMEOUT`. Kafka's `transaction.max.timeout.ms` is 15 minutes; one hour here because that is what Flink's sink asks for. |
| Topic name | 249 characters of `[a-zA-Z0-9._-]` | `INVALID_TOPIC_EXCEPTION`. |
| Group id | 255 bytes | `INVALID_GROUP_ID`. |
