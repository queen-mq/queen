Queen can encrypt message payloads with AES-256-GCM before they enter the
replicated log, so every node stores them as ciphertext and a copy of a node's
data directory (a stolen volume, a snapshot of the disk) does not yield message
contents. It needs exactly two things true at once: a key on the process and a
flag on the queue. **With only one of the two in place the broker stores
plaintext without raising an error.**

## Enabling it

<Steps>

1. Generate 32 random bytes as **64 hexadecimal characters**, set
   `QUEEN_ENCRYPTION_KEY` to them on every node, and restart. Every node of a
   cluster needs the same key: any node can serve a push or a pop, so a node with
   no key writes plaintext, and a node with another key writes envelopes the others
   cannot read.

   ```bash
   openssl rand -hex 32
   ```

2. Confirm the boot log line on every node. If it is absent, encryption is off
   there: see [the silent failure](#a-bad-key-silently-stores-plaintext).

   ```text
   encryption service initialized (AES-256-GCM)
   ```

3. Flag each queue that should be encrypted, with `encryptionEnabled` in the
   options of `POST /api/v1/configure`:

   ```bash
   curl -s -X POST http://localhost:6632/api/v1/configure -H 'Content-Type: application/json' -d '{"queue":"orders","options":{"encryptionEnabled":true}}'
   ```

</Steps>

`/configure` [merges](/reference/queue-options), so a later call that does not
repeat `encryptionEnabled: true` leaves the flag alone. Two ways to turn it off
remain, and both are explicit: send `encryptionEnabled: false`, or send the whole
configuration with `"mode": "replace"`, where an omitted flag means the default,
which is off.

<Aside type="caution">
A manifest is the case to watch. `queenctl apply -f` sends `"mode": "replace"` because a
declarative source means the whole configuration, so a manifest that does not carry
`encryptionEnabled: true` turns encryption off for that queue and subsequent pushes store
plaintext. Keep the flag in the file, not only in the call that first set it.
</Aside>

The flag is part of the queue's configuration in the replicated store, and every
push reads it there, with no cache in between. A change applies to the pushes
that follow it.

## What gets encrypted

Encryption applies when the key is loaded **and** the queue's flag is true, on
these write paths: `POST /api/v1/push`, `POST /api/v1/transaction`, a timer's
payload, and the dead-letter move behind the two replay routes.

A timer payload is enveloped at **schedule** time rather than at fire, on the
timers route and on a transaction's `timers` rider alike: the fire is planned by
the leader, possibly days later, so a late envelope would leave the payload in
cleartext at rest until then. The consequences of encrypting early are declared on
[timers](/reference/http/timers/#encryption-happens-at-schedule).

The dead-letter move is the one path that reads an envelope as well as writing
one. The broker decrypts the stored snapshot, then asks the same question the push
path asks about the **destination** queue, and envelopes for that answer. So
replaying into a different queue re-encrypts for the destination: a move out of
an encrypted queue into a plaintext one stores plaintext, and the other way round
stores an envelope. When the snapshot cannot be decrypted (a plaintext snapshot,
or an envelope whose key is gone or has changed), the move takes the stored bytes
as the payload.

One case resolves to "no encryption" without an error: a push to a queue that has
no configuration yet, because that push creates the queue with the flag off.

**A stream's sink output is not enveloped.** On a 2.0 broker
`POST /streams/v1/cycle` writes the messages it emits to a sink queue as
plaintext, whatever that queue's `encryptionEnabled` says.

Only message payloads are enveloped. The `transactionId`, trace name, queue and
partition names, offsets, timestamps, `producerSub`, consumer-group cursors, DLQ
metadata and key/value state are stored as they are, so anyone who can read a
node's data directory still sees the shape of your traffic, the names of your
queues, and the identity of your producers. Encrypting the volume itself is the
operator's business, outside Queen.

## The stored envelope

```json
{
  "encrypted": "<base64 ciphertext>",
  "iv": "<base64, 16 bytes>",
  "authTag": "<base64, 16 bytes>"
}
```

Standard base64 with padding, `authTag` in camelCase. The envelope stores all 16
IV bytes but only the **first 12** are fed to the cipher: the earlier
OpenSSL-based implementation never set the GCM IV length, so it used OpenSSL's
default 12-byte nonce, and the format keeps that byte for byte.

## Reading it back

Each stored message carries its own flag saying whether it was stored as an
envelope, and a read decrypts exactly the messages whose flag is set. That is why
a queue whose `encryptionEnabled` has since been turned off still returns readable
messages. The `isEncrypted` field in a message detail response reports that
stored per-message flag.

Three refusals, all of which return the payload **as stored**:

| Refusal | Behaviour |
| --- | --- |
| No key configured | The read serves the envelope JSON itself: a consumer receives `{"encrypted":"…","iv":"…","authTag":"…"}` as its message body. That is the signal that the node serving the read is missing the key |
| Wrong key | GCM tag verification fails and the envelope is served as-is. No error, no log line on the read path |
| Wrong sizes | An IV or tag that is not 16 bytes is rejected without attempting the cipher |

<Aside type="caution">
A decrypt failure is never an error to a consumer: it is a message whose body
happens to be an envelope, so a client fails on the field names, not on a status
code. If you rely on encryption, assert on the decrypted shape in your consumer,
and alert on it.
</Aside>

## A bad key silently stores plaintext

`QUEEN_ENCRYPTION_KEY` is read at boot, and every rejection path *disables
encryption for the whole process and lets the broker start normally*:

| Key value | Outcome | Log |
| --- | --- | --- |
| Unset or empty | Encryption disabled | none |
| Not exactly 64 characters | Encryption disabled | `warn`: `QUEEN_ENCRYPTION_KEY must be 64 hex chars; encryption DISABLED` |
| 64 characters, not all hex | Encryption disabled | `warn`: `QUEEN_ENCRYPTION_KEY is not valid hex; encryption DISABLED` |
| 64 hex characters | Encryption enabled | `info`: `encryption service initialized (AES-256-GCM)` |

With encryption disabled, a queue whose flag is `true` keeps accepting pushes and
stores every payload in plaintext: the push succeeds, the response says `queued`,
and only the boot log shows it. The same design covers a runtime cipher failure:
if the cipher call fails for an individual message, the broker logs
`encryption failed; stored plaintext` with the queue name and stores that message
in plaintext rather than failing the push.

Verify at the deployment level, since the queue's flag alone does not tell you
whether the key loaded:

<Steps>

1. Grep the boot log of every node for `encryption service initialized`. Its
   absence, with a key set, means the key is malformed.

2. Push one message to a flagged queue and read it back with
   `GET /api/v1/messages/:partitionId/:transactionId`: `isEncrypted` must be
   `true`.

3. Make that check part of the deploy, not a one-off. A key arriving from a secret
   store as an empty string, or with a trailing newline, fails the 64-character
   check above.

</Steps>

## Rotation

Rotation is a drain-then-restart operation: drain the affected queues first
(consume to the head, or let retention age the old records out), then restart
every node with the new key at the same moment. Verify the drain with the queue's
own depth, not with elapsed time.

The drain is what makes it safe. One key is loaded per process and decryption
tries only that key, so every message still in the log written under the old key
becomes an undecryptable envelope from the instant the new key is in place.
