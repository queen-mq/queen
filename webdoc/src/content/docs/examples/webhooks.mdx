Every product with an API ends up writing this one. Deliveries to one subscriber have to arrive in
the order the events happened, a subscriber whose endpoint is down must not hold up anybody else,
a failure is retried a bounded number of times, and what never succeeds has to end up somewhere a
person can read it. With one partition per endpoint the first two come from the storage, and the
last two are queue settings, so the sender itself is a function that POSTs and throws. The
program queues three events for three subscribers, one of which answers 500 to everything, and
checks all four properties.

## Run it

```bash
docker run --platform linux/amd64 -d --name queen -p 6632:6632 ghcr.io/queen-mq/queen:latest
npm install queen-mq
node webhooks.mjs     # the JavaScript tab below, saved as webhooks.mjs
```

The failing endpoint's deliveries are the oldest in the queue, and the healthy endpoints were
served while it was still on its first attempt. Each of its events was tried three times, in
order, and then filed with the error that killed it.

## How it works

The application pushes each delivery into the partition of the endpoint it is for, with the event
id as `transactionId`, so an application that retries its own emit does not create a second
delivery. Order per subscriber is then a property of the partition: the sender group holds one
lease per partition, and the next delivery to an endpoint is not handed out while the previous
one is in flight.

<Figure id="guides/webhooks-endpoints" />

The sender is a handler that returns or throws. Returning acknowledges the delivery; throwing
gives it back with the error, which spends one unit of the queue's `retryLimit`, and the broker
hands it out again with `deliveryAttempt` one higher. When the budget is spent, the queue's
`dlqAfterMaxRetries` files the delivery in the dead-letter queue with its last error and the
endpoint's next delivery goes out. The retries live in the broker, so they survive the sender
crashing halfway, which a retry loop inside the handler would not.

`.partitions(1)` keeps one endpoint per pop. After a failed delivery the JavaScript client skips the
endpoint's later deliveries in that pop, because the failure released the endpoint's lease and they
will come back; it still sends the other endpoints' deliveries of the same pop. Older JavaScript
clients skipped the whole rest of the pop, so the other endpoints' deliveries waited for their lease
to run out: without `.partitions(1)` and with the dead endpoint first in the queue, the healthy
endpoints received nothing before the program gave up. `.partitions(1)` avoids that with any
version.

[Deliver webhooks](/guides/webhooks/) goes further into the pattern: re-queueing dead letters once
an endpoint is fixed, skipping the budget for a permanent error, and putting a pause between
attempts.

## Why it is short

Without per-endpoint partitions, a sender has to build the isolation itself: a queue per
subscriber to provision and clean up, or a shared queue plus a table of failing endpoints to skip
and a scheduler to come back to them, and a retry counter stored next to every delivery. Here
each of those is a setting or a side effect of the partition, and the sending code is the HTTP
call.

## Limits

- A failing delivery holds up its own endpoint. Later deliveries to that endpoint wait until
  it succeeds or is dead-lettered. That is the price of order, and other endpoints do not pay it.
- Retries come back immediately. For a pause between attempts, see the
  [guide](/guides/webhooks/).
- Only a failure that is reported spends the budget. A sender that hangs or dies costs
  nothing: the lease expires and the delivery comes back, forever if it kills every sender. Read
  `deliveryAttempt` and dead-letter the delivery yourself past a threshold.
- Delivery to the endpoint is at least once. A sender that dies after the POST and before the
  ack sends it again, so send the event id in a header and let the receiver drop repeats.
