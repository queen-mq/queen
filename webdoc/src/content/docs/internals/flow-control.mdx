Every write on a 2.0 node goes through one serial pipeline: the leader's planner, then the log. When
producers offer more than that pipeline can take, something has to make them slow down, and it has to
happen before their request bodies pile up in memory. Before the budget below existed, an offered
rate above the planner's ceiling queued bodies in RAM until the kernel killed the process.

A node pushes back in three places, from the outside in.

| Where | What it bounds | What the client sees |
| --- | --- | --- |
| The admission budget, at the HTTP edge | bytes of writes in flight, from arrival to reply | a wait, then `429` with `Retry-After` |
| The disk gate | writes while the data directory's disk or the store's map is nearly full | `507` |
| The bounded queues inside | commands waiting for a planning cycle, entries in flight | a wait, bounded by the request's deadline, then `503` |

## The admission budget

`server/src/rsm/admit.rs` keeps one byte budget per process, shared by the HTTP edge and every caller
inside the process.

**Where it is taken.** `POST /api/v1/push` and `POST /api/v1/transaction` carry an admission layer
(`admit_edge` in `server/src/handlers/raft.rs`) that runs inside authentication and tenancy, so an
unauthenticated request never takes budget, and **before the body is read**. It takes permits sized by
the request's `Content-Length`, or 64 KiB when there is none (a chunked body). A push waiting for
room holds only its connection: its bytes stay in the socket, and TCP slows the sender down. Callers
that do not come through that edge (in-process callers, KV writes, timer schedules) are gated in the
facade instead, sized by their raw body or by an estimate of the command; a request the edge already
admitted is not charged twice. On a cluster, the leader gates the prepared commands its followers
send it the same way.

**What it covers.** At the edge, every request to the push and transaction routes. Inside, only
commands that grow storage: pushes, transactions that push, put keys or schedule timers, KV puts and
increments, timer schedules, trace appends. Pops, acks and lease renewals on their own routes never
take permits, so consumption keeps running while producers are held.

**Hold, then 429.** When the budget is spent, a new command **waits** for room, so a producer that
waits for its answers simply slows down. Only if no room frees within the hold is it refused, with
`429` and `Retry-After`. Both are jittered: the hold by plus or minus 25%, `Retry-After` uniformly over
1 to 5 seconds, so requests that queued together are not refused together and do not come back
together. Permits are returned when the reply is ready, not when the body has been read.

| Setting | Default | What it does |
| --- | --- | --- |
| `QUEEN_RAFT_ADMIT_MAX_MB` | 64 | the budget, in megabytes of raw request bytes. `0` turns admission off |
| `QUEEN_RAFT_ADMIT_HOLD_MS` | 15000 | how long a command waits for room before `429`; below the SDKs' 30 s request timeout |

A command larger than the whole budget takes all of it and runs alone. The budget counts raw request
bytes, and a parsed push costs several times its wire size in memory, which is why the budget is
small.

The state is on [`/metrics/prometheus`](/reference/prometheus/) while `QUEEN_RAFT_METRICS` is on (the
default):

| Series | Meaning |
| --- | --- |
| `queen_raft_admit_bytes{kind="cap"}` | the budget |
| `queen_raft_admit_bytes{kind="held"}` | bytes held by admitted commands now |
| `queen_raft_admit_waiting` | commands waiting for room now |
| `queen_raft_admit_total{outcome="waited"}` | commands that had to wait, then got in |
| `queen_raft_admit_total{outcome="refused"}` | commands refused with `429` |

The 1.x admission arbiter, its connection pool and its `QUEEN_ADMISSION_*` knobs do not exist in 2.0.

## The disk gate

A node refuses writes that grow storage once its data directory's filesystem is at least
`QUEEN_RAFT_DISK_HIGH_PCT` used (default 85), and accepts them again only below
`QUEEN_RAFT_DISK_LOW_PCT` (default 80). The same gate closes when the store's LMDB map is 85% full and
reopens below 80%. The check is cached and refreshed at most every `QUEEN_RAFT_DISK_CHECK_MS` (100 ms),
so a burst of writes does not become a burst of `statvfs` calls. A refused write answers `507` with
code `storage_full`, and `queen_raft_storage_full` is `1` while the gate is closed. Pops, acks and
deletes keep working, which is how the disk drains. Size the volume for retention.

## The queues inside

Past admission, a command crosses bounded queues. None of them refuses on its own: a full one makes
the command wait, and the request's deadline bounds the wait.

- **The command channel** between the receivers and the batcher holds
  `QUEEN_RAFT_COMMAND_QUEUE_DEPTH` commands (default 1024). A full channel makes the sender wait.
- **The cycle.** The batcher drains the channel into cycles of at most 4096 commands, an estimated
  4 MiB, or 5 ms of planning, whichever comes first. Every command that is not a plain push (acks,
  pops, renewals, transactions, KV, timers) waits in a priority lane that each cycle drains before any
  push: the work that empties the system goes ahead of the work that fills it.
- **The pipeline.** At most `QUEEN_RAFT_PIPELINE` entries (default 4) are proposed and not yet applied.
  While the pipeline is full, the next cycle waits for the oldest entry to apply.
- **Forwarding from a follower.** A follower keeps at most `QUEEN_RAFT_FWD_INFLIGHT` calls to the
  leader in flight (default 4096), prepared commands and read barriers together; past that a call waits
  for a free slot, up to its deadline.

A command that runs out of deadline anywhere on that path answers `503` with `Retry-After: 1`, as does
every write while no leader is known. Clients retry those; a retried push that reuses its
`transactionId` is deduplicated against whatever did commit.

## Reading the signals

| What you see | What it means |
| --- | --- |
| `queen_raft_admit_waiting` above zero, `refused` flat | producers are being slowed, not refused: the budget is full, so new writes wait for room |
| `queen_raft_admit_total{outcome="refused"}` rising | producers keep sending after the hold; they get `429` and come back after `Retry-After` |
| `queen_raft_storage_full` at `1` | the disk or the store map is past its high mark; writes answer `507` until usage drops below the low mark |
| `503` with `Retry-After: 1` | no leader, a leadership change, or a deadline spent inside the node |

The client-facing contract of each status is on [Errors](/reference/errors/).
