The KV store is part of the replicated state machine. A key lives in the same ordered store as
queues, partitions and cursors, a write to it is an effect in the replicated log, and every node
applies that effect to its own copy. That placement is the point of the feature: the idempotency
marker, the message and the cursor advance of one `POST /api/v1/transaction` are one entry in the
log, so they commit together or not at all. A key/value store standing beside the broker cannot
give that.

<Aside type="note">
Every node serves the KV routes: `POST /api/v1/kv`, the path routes under `/api/v1/kv/:ns/*key`,
and the console's `POST /api/v1/resources/kv/list` and `GET /api/v1/resources/kv/namespaces`. No
boot flag turns the store on or off; the operator's side is on [KV and timers](/deploy/state).
</Aside>

## Where a key lives

Two keyspaces of the ordered store hold the whole feature:

| Keyspace | Key | Value |
| --- | --- | --- |
| `kv` | `(tenant, namespace, key)` | the row: value, version, expiry, created and updated stamps |
| `kv_expiry` | `(expires_at, version)` | the `kv` key of the row, for rows that expire |

The tenant and the namespace are escaped names and the key is the raw tail of the store key, so the
keys of one namespace sort in byte order and a key prefix is a store-key prefix: `getPrefix` and the
console listing are range scans. The tenant comes from the request, never from an op: an op that
carries a `tenant` field is refused (`kv_tenant_not_an_input`).

Like every keyspace, both are held in memory on every node and written to LMDB (under `store/` in
the data directory) as a checkpoint at each durable point. After a crash a node reopens at its last
checkpoint and replays the later entries from its queue logs. A key therefore costs memory on every
node for as long as it exists, which is one reason every write has to declare its expiry.

| Field | What it is |
| --- | --- |
| `value` | The JSON value as compact text. `null` is a value, not an absent key. |
| `version` | Unique across the store and never re-issued. See below. |
| `expires_at` | Absent means forever, and forever is an explicit choice on the wire (`forever: true`), never a default. |
| `created_at`, `updated_at` | Stamped by the planner from the call's instant. |

## One write path

<Steps>

1. **The receiver validates the whole call** before anything is planned: the op names, the
   namespace charset (`^[a-z0-9][a-z0-9._-]{0,63}$`), the key (non-empty, no NUL, at most 512 bytes
   and within the store's own key limit), the value ceiling, the expiry declaration of every write
   (exactly one of `ttlSeconds`, an integer above 0, and `forever: true`), at most one write per key
   per call, and the op and key budgets. A refused call costs no planning and writes nothing.

2. **A call with at least one write becomes one command.** The leader plans it serially, against
   committed state plus the entries still in flight, in the same cycle as every other command. The
   planner is the one point every write passes, so exactly one of several concurrent `putIfAbsent`
   calls on a key wins, an `expect` is compared with the version the previous writer left, and an
   `incr` never loses an update. A write marked `required: true` that loses its precondition aborts
   the whole call, and nothing is logged. A call whose writes all lost a precondition that was not
   required logs nothing either.

3. **The answer waits for apply.** The call is answered once its entry has committed and applied on
   the node that took it.

</Steps>

Every instant in a call is the planner's one stamp: each expiry (the stamp plus `ttlSeconds`), each
`created_at` and each `updated_at`. Apply reads no clock. It writes what the effect carries, so
every node holds the same row.

`incr` adds to the number a live key holds, or to 0 when the key is absent or expired. The
arithmetic is exact decimal while the numbers fit a 128-bit mantissa with at most 38 fractional
digits, and floating point beyond. `min` and `max` refuse an increment that would cross them
(nothing is clamped), and the TTL applies only when the increment creates the row: a live key keeps
its expiry.

## The version is a token

A write's version is the entry's version base plus the write's position in the entry. Versions are
unique across the whole store and never re-issued, so a key that expired and was written again
cannot hand an old holder its version back, and a compare-and-set against a lineage that no longer
exists cannot succeed. They also happen to increase, which nothing may rely on: compare versions
for equality only.

The version of an absent or expired row is 0. That is what lets `expect: 0` mean "must not exist"
without a flag.

## Expiry is judged at read time

A row is live when it has no expiry or its expiry is later than now. A row exactly at its instant
is dead, for readers and for the sweep alike. An expired row is absent from the first read after its
instant whether or not anything has removed it, so the sweep below reclaims memory and is never
needed for a correct answer.

A read uses one instant for the whole call: the node's wall clock, never earlier than the last
instant the state machine applied. A row the planner already judged expired never reads back alive.
A plain `delete` of an expired row removes it and still answers that the key was absent.

## Reads

`get`, `getMany` and `getPrefix` return values; their bytes never enter the log. One call reads at
most 4 MiB of values.

- **In a call that also writes**, apply renders the reads right after the call's own last effect
  and before any later command's. They see the call's own writes and nothing planned after it.
- **In a read-only call**, nothing is planned. The node first waits until it has applied what the
  cluster had committed when the read began, then reads at an entry boundary, so it never sees half
  of another call's writes.
- **`getPrefix`** exists only on `POST /api/v1/kv`; a transaction refuses it. Its `limit` is clamped
  to 1 to 1000, default 100, and its `after` cursor is exclusive. Rows come back in byte order, not
  locale order.
- **The console listing** (`POST /api/v1/resources/kv/list`) pages a namespace the same way. With
  `includeExpired` it also returns rows past their instant that the sweep has not removed yet, each
  marked `expired`. It is not read at an entry boundary: holding one would stall apply for the
  length of the scan. `GET /api/v1/resources/kv/namespaces` counts every row of each namespace,
  expired rows included, since they still occupy it.

## The sweep

The leader removes expired rows with a bounded step it plans itself:

- every `QUEEN_RAFT_KV_SWEEP_MS` (default 1000), one step reads `kv_expiry` from its oldest entry
  and takes the rows whose expiry is at or before the step's instant, up to
  `QUEEN_RAFT_KV_SWEEP_LIMIT` (default 512) deletions. It reads up to twice the limit, so
  candidates that entries in flight have touched do not starve it;
- each candidate is judged again against the row as committed state plus the entries in flight
  see it: a row rewritten since (a different version) or already deleted is skipped;
- the step is planned after the cycle's client commands, so a key a command rewrote in the same
  cycle is not swept;
- its deletions are one command with its own request id, added to the cycle's entry and answered
  by nobody. Every node applies them.

The cost follows the expired rows, never the number of keys. A step does not repeat before its next
tick even when more rows are due, so at the defaults the sweep removes at most 512 expired keys a
second; a higher expiry rate keeps more dead rows in memory, never wrong answers. A value of 0 for
either knob is ignored and the default applies. A step whose read fails is skipped until the next
tick.

## Apply

`KvPut` writes the row and keeps `kv_expiry` exact: it removes the old row's index entry and adds
the new one. `KvDelete` removes the row and its index entry. A delete that finds no row is a
counted no-op, so a replayed entry converges on the same state. Deleting a tenant removes its keys
in the purge entry.

## Transactions

`POST /api/v1/transaction` carries a `kv` array beside its pushes, acks and `timers`, and the whole
bundle is one command and one entry. The transaction's own budgets are smaller (64 ops and 256 keys
per call) and `getPrefix` is refused there. A lost `required` precondition rolls the whole bundle
back: nothing in it is logged. The transaction route goes straight to the state machine: it does
not consult the KV grants, the quotas or the runtime switches, which apply to the KV routes only.

## Ceilings

These are the state machine's own. The HTTP handler checks its own edge limits first, and a call
has to pass both.

| Ceiling | Value |
| --- | --- |
| Ops per call | 256 (64 in a transaction) |
| Keys per call, counting a `getMany` by its keys and a `getPrefix` by its clamped limit | 4096 (256 in a transaction) |
| Key | 512 bytes, or less when the tenant and namespace are long: the whole store key has to fit LMDB's 511-byte limit (`kv_key_too_large`, 413) |
| Value | 65,536 bytes of compact JSON |
| Values read by one call | 4 MiB |
| `getPrefix` limit | 1 to 1000, default 100 |

## Quota

A tenant's KV grant is a replicated row (a `QuotaSet` effect). Enforcement is in process: at boot
every node measures, for each tenant with a KV grant, its live keys, their value bytes and its
timers, and the KV routes charge each call's upper bound against that before it is planned, giving
the charge back when nothing can have been written. A transaction's `kv` array is not charged. The
operator's side is on [KV and timers](/deploy/state).
