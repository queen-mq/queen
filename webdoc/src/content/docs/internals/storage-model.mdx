A message's address in Queen is one number: an offset, gapless and monotone within its partition. A
consumer group's progress in a partition is one integer, the difference between two offsets is a
message count, and whether one message precedes another is a comparison. That did not change in
2.0. What changed is where the bytes live: in the data directory of each node, split between two
stores that apply keeps in step.

- **The queue logs** hold the message payloads, appended once, in the leader's order.
- **The ordered store** holds everything whose shape is a key and a value: queues, groups,
  partitions, cursors, leases, dead letters, the hash lists deduplication and acks resolve through,
  KV, timers, counters, and the recorded outcome of every recent command.

Each node holds a full copy of both, built by applying the same entries. Nothing is shared between
nodes except the entries themselves.

## The data directory

`QUEEN_RAFT_DIR` names it (default `/var/lib/queen/raft`). Put it on a persistent volume: it is the
only copy of this node's state.

| Path | What it holds |
| --- | --- |
| `qlog/` | the queue logs: one directory per log (`q<id>/`) holding rolling files `rNNNNNNNN.qlog` and, beside each sealed file, its index `rNNNNNNNN.qidx`. `q0/` is the system log, for entries that touch no queue. `qlog/SHARDS` records the shared-log count when the directory uses one |
| `store/` | the ordered store: one LMDB environment opened through the `heed` crate |
| `raft/` | the openraft replicator only: `state.json` (the vote and the purge point, replaced atomically) and `committed.json` (the commit point, rewritten in place and never fsynced) |
| `snapshots/`, `snapshot.pending` | a snapshot received from the leader, staged here and swapped in at the next boot |
| `dash.db` | this node's dashboard rows, a checksum-framed journal |
| `local.db` | node-local metrics and retention history, the same journal format |
| `groups/g<N>/` | with `QUEEN_RAFT_GROUPS` above 1, group N's own queue logs, store and raft state (group 0 keeps the top level) |

Two more directories, `log/` and `seg/`, belong to the layout used before the queue logs became the
write-ahead log (`QUEEN_RAFT_QLOG=0`). With the default, apply files no payload into `seg/` and the
writer appends nothing to `log/`; the local replicator still replays a `log/` tail left by an older
build when it opens.

There is no disk spool and no external database. Crash recovery needs nothing but this directory: the
store reopens at its last durable point, and the entries above it replay from the queue logs.

## The queue logs

A queue's messages live once, in the leader's order, in that queue's log. The log **is** the
write-ahead log: there is no second copy of a payload anywhere on the node.

<pre class="mermaid">{`
flowchart LR
  E["entry 812<br/>pushes to orders/p1 and orders/p2"] --> W["log writer"]
  W --> Q7["q7/r00000003.qlog<br/>message record p1, base 120, 3 frames<br/>message record p2, base 44, 1 frame<br/>entry record 812"]
  W -->|"one fsync per touched log"| D[("disk")]
  D --> A["apply entry 812"]
`}</pre>

**Which log.** A queue's log id is an `xxh3` of `(tenant, queue)`. With `QUEEN_QLOG_SHARDS` at its
default of `0`, every queue has its own log. With `QUEEN_QLOG_SHARDS=K` (1 to 4096), every queue's
records go to shared log `queue_id % K` instead, so one write group fsyncs at most `K` logs however
many queues it touches. The count is fixed when a data directory is created and recorded in
`qlog/SHARDS`; a directory keeps its layout, and a different value in the environment only logs a
warning.

**What a record is.** Every record is self-describing and checksummed:

```text
len:u32 | xxh3:u64 | seq:u64 | pid:u64 | base_offset:u64 | count:u32 | created_at:i64 | txn_kind:u8 |
  hashes[16 * count] | payload
```

(A `txn_kind` of 1 adds a transaction envelope before the hashes; the high bit of `txn_kind` marks a
compressed payload.) `len` counts every byte after itself, so a scanner knows where the next record
starts, and the checksum covers every byte after itself, so a torn tail fails it. `seq` is the index
of the entry that wrote the record. A **message record** carries one `Append` effect: `count`
messages of one partition starting at `base_offset`, their 16-byte `transactionId` hashes in frame
order, and the packed frames as the payload. An **entry record** carries the entry itself in its payload-free form.
For each entry the writer puts the whole entry record into the lowest-numbered log the entry touches
and a 61-byte stub into every other touched log (`QUEEN_QLOG_ENTRY_LAYOUT=copies` writes the whole
record into each instead). Entry records are never indexed, so no read path can see them.

**Durability.** The log writer takes a group of pending entries (on the local replicator at most
4096 entries or 4 MiB), writes their records, fsyncs every log the group touched once, and only then
hands the group to apply. The openraft replicator stores its log through the same group write. A
message is durable when its record is fsynced, untorn, in its log. At open, recovery merges the entry
records of every log by `seq` and replays the gapless prefix of complete entries above the store's
durable index; an entry missing a part is the unacknowledged tail of a group whose fsyncs did not all
land, and it is cut from every log. Only the active file can have a torn tail. A damaged record in a
sealed file is corruption and is reported, never truncated.

**Files and the index.** Files roll at `QUEEN_RAFT_SEGMENT_BYTES` (default 64 MiB) and a sealed file
never changes again. The index maps `(pid, base_offset)` to the record's byte offset, length, end
offset, timestamp and count: the active file's index is in RAM, a sealed file's is the `.qidx` beside
it, and either can be rebuilt by scanning the `.qlog`. Byte offsets are node-local: they never appear
in an entry, so two nodes may lay out the same records in different files.

**Compression.** The log writer compresses each message record's payload with zstd at
`QUEEN_RAFT_QLOG_ZSTD_LEVEL` (default 1; `0` turns it off). A payload under 512 bytes, or one that
compresses by less than a tenth, is stored raw. The codec is node-local: the entry in the replicated
log carries the raw frames, and every read decompresses at one decode point.

**Reclaim.** A queue log shrinks only by dropping whole sealed files. On each maintenance tick every
node runs one bounded pass over its own logs: it unlinks sealed files whose message records all sit
below their partition's `txns_start`, and rewrites at most one partly dead file per pass, copying
only its live records forward. A file is never dropped while it holds a record above the store's
durable index (recovery replays from there) or, on openraft, above the purge point (a follower may
still need the entry).
`txns_start` trails the payload retention watermark (see below), so a record outlives its payload
retention by the hash-list window. [Retention internals](/internals/retention) covers the watermarks.

## The frames inside a payload

A message record's payload is the packed frames of the messages that survived deduplication, in
offset order, one frame per message. The frame codec is the one 1.x used (`server/src/frames.rs`),
little-endian:

```text
u32 body_len
body:
  u8   flags                  1 = trace id present, 2 = producer sub present, 4 = encrypted
  u8[16] message_id
  [u8[16] trace_id]           present only when flag 1 is set
  u16  txn_len
  u8[txn_len] transaction_id
  [u16 psub_len | u8[psub_len] producer_sub]   present only when flag 2 is set
  u8[...] payload             the JSON bytes as the client sent them, or their ciphertext
```

The receiver packs one frame per message before it submits the command; the planner concatenates
the survivors' frames into the `Append` blob and never repacks or decompresses them. Reading offset
`O` from a record based at `B` means decoding the payload and taking frame `O - B`.

## The ordered store

The store is one LMDB environment, opened through `heed`. Every keyspace is held in RAM, loaded in
full at open, and LMDB holds its checkpoint, written durably at each **durable point**: every
`QUEEN_RAFT_DURABLE_EVERY_MS` (1000 ms) or `QUEEN_RAFT_DURABLE_EVERY_BYTES` (256 MiB), whichever comes
first. In between, the queue logs are the write-ahead log. After a crash the store reopens exactly at
its last durable point (its `applied_index` included) and the entries above it replay from the queue
logs; apply skips an entry at or below the applied index, which is what makes that replay safe.

LMDB keeps no checksums, so every value carries one (`xxh3` over the keyspace, the key and the value),
verified on every read. A corrupt value stops the node rather than being served.

Keys are byte strings compared with `memcmp`, integers big-endian, names escaped so that a composite
key of two names cannot be confused with another pair. Every scan is therefore a scan in key order.
The message-path keyspaces:

| Keyspace | Key | Value |
| --- | --- | --- |
| `queues` | `(tenant, queue)` | the queue's configuration: lease time, retry limit, DLQ flags, delays, retention, encryption, dedup window |
| `groups` | `(tenant, queue, group)` | the group's registration: subscription mode and instant, conflation policy |
| `partitions` | `pid` | the partition row (below) |
| `partitions_by_key` | `(tenant, queue, partition)` | `pid`: the unique name index |
| `queue_partitions` | `(tenant, queue, pid)` | nothing: the scan index for wildcard pops and administration |
| `cursors` | `(pid, group)` | the cursor row (below) |
| `leases_by_worker` | `(worker, pid, group)` | the lease expiry, walked by lease renewal |
| `pending` | `(tenant, queue, group, pid)` | `ready_at`: partitions with work for a group, the source of the ready rings |
| `txns` | `(pid, base_offset)` | one row per `Append`: end offset, timestamp and the 16-byte hash of every message |
| `dlq`, `dlq_by_pos` | `(tenant, queue, dlq_id)`, `(pid, group, offset)` | dead letters with their payload snapshot, and the index by position |
| `request_ids`, `request_expiry` | `request_id`, `(time, request_id)` | the outcome recorded for each recent command |
| `counters` | `(scope, id, counter)` | counters maintained at apply |
| `meta` | fixed names | the applied index and term, the durable index, the next partition id, the clock floor |

The rest cover the other surfaces: `kv` and `kv_expiry`, `timers` and `timers_due`, `streams_queries`
and `streams_state`, `traces`, `trace_names` and `trace_expiry`, `flags`, `quotas`, `eph_config`,
`garbage` (partitions whose data is still being deleted in chunks), and `dedup` (a per-hash index
written only with `QUEEN_RAFT_DEDUP_INDEX=rows`). Three keyspaces are node-local because they name
this node's files: `seg_loc`, `files` and `partition_files`. Every other keyspace is replicated.

### The partition row

| Field | Meaning |
| --- | --- |
| `uuid` | the partition's UUID, echoed by reads and traces |
| `tenant`, `queue`, `partition` | the names |
| `last_offset` | the highest offset appended, `-1` when empty. The next base offset is `last_offset + 1` |
| `log_start` | the retention watermark: no offset below it is served any more |
| `txns_start` | the hash-list watermark: every `txns` row below it is gone. It trails `log_start` |
| `oldest_live_at` | the timestamp of the oldest live append, unset when the partition holds nothing |
| `last_write_at`, `last_created_at` | the last write, and the floor for the next append's timestamp |
| `created_at` | creation time |

A partition's id (`pid`) is a small integer from one counter in `meta`, assigned by the planner and
never reused. On the wire, `partitionId` in pop responses and acks is this number in decimal; read
and admin routes accept it or the partition's UUID.

### The cursor row

One row per `(pid, group)`. Queue-mode consumers use the group name `__QUEUE_MODE__`.

| Field | Meaning |
| --- | --- |
| `committed` | the cursor: the last acked offset, `-1` when nothing is acked. The next wanted offset is `committed + 1` |
| `batch_end` | the inclusive end of the leased batch; unset when there is no lease |
| `worker` | the lease holder, returned to the client as `leaseId` |
| `lease_expires_at`, `lease_acquired_at` | the lease window |
| `batch_retry_count` | the retry budget spent, charged only by an explicit `failed` ack |
| `attempt_offset`, `attempt_count` | redelivery telemetry: the first offset of the delivered batch and how many times that same start was delivered |
| `delivered` | the distinct hashes the leased batch delivered, which the ack fast path compares against ([Ack internals](/internals/ack-internals)) |
| `lease_conflated` | whether the lease was a conflating one |
| `total_consumed` | a lifetime counter |
| `metadata` | the opaque string recorded with a position set through a transaction's `positions` rider; empty otherwise |
| `created_at` | when the row was first written |

A leased batch is the span `(committed, batch_end]`. One row holds at most one lease, so exactly one
leased batch is in flight per `(partition, group)`, and one group cannot consume a single partition in
parallel. Parallelism comes from partitions.

## How a message is found

<pre class="mermaid">{`
flowchart LR
  N["tenant, queue, partition"] -->|"partitions_by_key"| P["pid"]
  P -->|"cursors"| C["wanted = committed + 1"]
  P -->|"txns rows"| S["the append covering wanted"]
  S -->|"queue id, log id"| L["qlog index: pid, base_offset"]
  L --> R["record, decompressed"]
  R --> F["frame wanted - base_offset"]
`}</pre>

The planner decides *which* offsets a pop takes without touching a payload: it rebuilds a partition's
append boundaries (base, end, timestamp) from the replicated `txns` rows plus the appends still in
flight, and never reads a byte position. The claim travels in the outcome as `(pid, start, end)`. The
node that answers then reads the payloads from its own queue log: the log id from the queue's id and
the shard count, the record from the index lookup of `(pid, offset)`, the frames from the decompressed
payload. [Life of a pop](/internals/life-of-a-pop) has the whole path.

## The invariants

1. **Offsets are gapless and allocated in plan order.** The planner allocates a push's offsets from
   `last_offset + 1`, and apply refuses an `Append` whose `base_offset` is not the partition's next
   offset: such an entry means the planner planned against different state, and the node stops
   rather than paper over it.
2. **Timestamps are strictly monotone per partition.** An append is stamped
   `max(now, last_created_at + 1 µs)` by the planner. Time-based retention, subscription seeding and
   the `delayedProcessing` filter are all forward walks because of this.
3. **Two watermarks, one order.** `txns_start <= log_start <= last_offset + 1`. Payloads below
   `log_start` are no longer served; hash lists survive down to `txns_start`, so a duplicate check or
   an ack by `transactionId` still resolves in the gap between them.
4. **Retention removes a prefix.** A cursor can sit below `log_start` after retention; the next claim
   then starts at the first retained offset. A gap is not an error and not a stall.
5. **Positions never replicate.** Which file and which byte offset a record landed at is this node's
   business. Entries carry effects, never positions, which is what lets a snapshot install onto a node
   whose files are laid out differently.

## What this model does not have

- **No global order.** Order is per partition. Two messages in different partitions of one queue
  have no defined relative order.
- **No per-message pending state.** Progress is a cursor: acking offset `N` completes every earlier
  unacked offset of that partition for that group. The one per-message record is the dead letter: a
  message that exhausts its retries is filed individually and the cursor moves past exactly that
  offset, so one poison message cannot pin an ordered lane.
- **No reordering.** A partition is first in, first out in log order. Nothing can jump the queue.
