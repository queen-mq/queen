An ack is a cursor commit. There is no per-message state to flip, so acking offset `N` implicitly
completes every earlier unacked offset in that partition for that group. The wire, though, does not
carry offsets. It carries `transactionId`, because that is the identifier a client holds. Turning one
into the other is the work this page describes, along with the fast path that skips it.

The wire contract, documented field by field on [the ack reference page](/reference/http/ack/):

```text
POST /api/v1/ack        {transactionId, partitionId, status, consumerGroup?, leaseId?, error?}
POST /api/v1/ack/batch  {consumerGroup?, acknowledgments:[{transactionId, partitionId, status, leaseId?, error?}]}
```

Both answer `200` with a **top-level array**, one element per ack in request order:
`{index, transactionId, success, error, leaseReleased, dlq, noop}`. In 2.0 `partitionId` is the
partition's numeric id in decimal, as the pop that delivered the message reported it.

## The receiver: resolve, group, snapshot

`ack_impl` in `server/src/rsm/facade/real.rs` does everything that needs only this node's state:

- it resolves each `partitionId` to a partition row. An id that does not parse, that names no
  partition, or that names a partition of another tenant fails that item (`success: false`) without
  touching anything else;
- it groups the items by `(partition, leaseId)` into **targets**;
- it hashes each `transactionId` with `xxh3_128`;
- for every item acked `failed` or `dlq` on a partition whose cursor holds a lease, it reads the
  message's frame from this node's queue log (payload, message id, transaction id) as a
  **snapshot**, so that a dead letter can be filed in the same entry as the cursor move without the
  planner ever reading a payload.

The whole request becomes one `Ack` command, and the batcher plans it like any other.

## The fast path: the delivered set

A leasing pop records on the cursor row the distinct hashes of the messages it delivered. For each
target, the planner first checks the common case: every item is `completed`, the acked hashes exactly
equal that delivered set, and the `leaseId` is the lease holder. When all three hold, the ack is one
cursor move to `batch_end` with no hash resolution: the lease is released, and the attempt and retry
counters reset.

Because the delivered set lives on the cursor row, it is replicated state. The fast path does not
depend on which node served the pop or on a map in memory, and a leader change does not lose it. A
lease renewal keeps it.

## Resolution: transactionId to offset

Every other case resolves each hash through the dedup authority, the `txns` rows: one row per
`Append`, holding the 16-byte hash of each of its messages in frame order, so hash `k` of the row
based at `B` is offset `B + k`. These rows are written for every append whether deduplication is on
or off, which is why acks resolve on a queue with `dedupWindowSeconds: 0`.

The planner (`ack_target` in `server/src/rsm/planner/ack.rs`) validates the lease **only when a
non-empty `leaseId` was supplied**: a wrong worker or an expired lease rejects every item of that
target. A lease-less ack falls through and still advances the cursor.

For each item it computes:

- `eff`, the lowest occurrence of the hash inside the ackable span
  `[max(committed + 1, txns_start), batch_end]` (to the partition's tail when no lease is held). Taking
  the lowest in-span occurrence means a re-push that sits below the cursor never shadows the copy the
  client is acking;
- `below`, whether an occurrence sits at or below the cursor.

The **head signal** is the lowest `eff` among the items acked `failed`, `dlq` or `retry`, ties broken
`dlq` over `failed` over `retry`. The new cursor is the highest offset acked `completed` that lies
**below** the head signal.

### The two honesty guarantees

**An explicit signal is never skipped.** The cursor stops below the lowest `failed`, `dlq` or `retry`
in the call, even when a later position in the same call was acked `completed`. That lowest signal
decides the action; the completed positions above it are redelivered. An at-least-once duplicate is
acceptable, a lost nack is not. Only positions the client did not mention at all are completed
implicitly.

**An ack that can no longer have an effect says so.**

| Item | What the client is told |
| --- | --- |
| acked `completed`, resolves only at or below the cursor | `success: true, noop: true`: a harmless repeat |
| acked `failed`, `dlq` or `retry`, resolves only at or below the cursor | `success: false`, "transaction is unresolvable, already committed, or acknowledgment is stale" |
| resolves nowhere (never pushed here, or its hash list already pruned) | `success: false`, the same message; the cursor does not move for it |
| its lease was wrong or expired | `success: false`, "invalid or expired lease" |

An unresolvable item leaves its position unacked, so the message is redelivered rather than lost.

### The branches

The signal branches apply to a leased batch.

| Signal | Retry budget | Effect |
| --- | --- | --- |
| `dlq` | bypassed | advance over the completed prefix, file the dead letter, advance past it, release the lease, reset the counters |
| `failed` | budget remains | advance over the prefix, release the lease, charge `batch_retry_count` once; the batch redelivers |
| `failed` | exhausted, DLQ enabled | advance over the prefix, file the dead letter, advance past it, release the lease, reset the counters |
| `failed` | exhausted, DLQ disabled | **drop the poison**: the cursor advances past it, the lease is released, the counter resets |
| `retry` | untouched | advance over the prefix and release the lease: a retry that costs no budget |
| all `completed`, reaching `batch_end` | reset | advance, release the lease, reset the attempt and retry counters |
| all `completed`, short of `batch_end` | untouched | advance and keep the lease, so the rest of the batch can still be acked |

The retry limit is the queue's `retryLimit` (3 on a queue a push created), and dead-lettering is on
when either `deadLetterQueue` or `dlqAfterMaxRetries` is true. Both default to true, so an
unconfigured queue dead-letters. The client-facing shape of that budget is
[leases, retries and the DLQ](/use/model/).

`batch_retry_count` is charged **only** by an explicit `failed`. A lease expiry never spends it; it
only raises `attempt_count`, which [the pop path](/internals/life-of-a-pop/) keeps as telemetry.

A conflating lease delivered one frame, at `batch_end`, standing in for the whole leased span, so a
clean ack of it moves the cursor to `batch_end` directly and retires the skipped positions with it.

## The dead letter, in the same entry

When a `dlq` signal or an exhausted `failed` files a dead letter, the same entry carries both the
`DlqInsert` effect and the cursor move. The row holds the receiver's snapshot of the frame (payload,
message id, transaction id), the error text from the ack (or "Retries exhausted"), and the retry count
as it stood. It is keyed `(tenant, queue, dead letter id)`, with a second index by
`(partition, group, offset)`.

The dead letter is a snapshot, not a pointer, so it outlives the retention that removes its source
message, and partition cleanup refuses to delete a partition that still holds one. Nothing removes a
dead letter on a timer.

<Aside type="note">
Replay is a **move**, and it is one transaction entry: a push of the stored payload with a fresh
message id and the derived transaction id `dlq:<dead letter id>`, plus the deletion of the dead
letter row. Two routes take it: `POST /api/v1/messages/:partitionId/:transactionId/retry` by message
address, and `POST /api/v1/dlq/:id/replay` by dead letter id; either body may name another `queue` or
`partition` as the destination. If the destination already holds that derived transaction id inside
its dedup window, the push is a `duplicate`, nothing is appended, and the row stays. The message lands
at the tail of the partition, and the offset the original occupied stays committed. While maintenance
mode is on, a replay answers `503`. The routes are on
[Messages and the dead-letter queue](/reference/http/messages-dlq/).
</Aside>

## Lease renewal

[`POST /api/v1/lease/:leaseId/extend`](/reference/http/lease/) plans a `Renew` command that extends
**every live lease held by that worker** on the requesting tenant's partitions (a multi-partition pop
shares one worker id). A renewal never shortens a lease: each new expiry is the later of the current
one and `now + seconds`. The answer reports the **earliest** of the renewed expiries, since that is
the deadline the caller has to beat next:
`{leaseId, success, renewed, newExpiresAt, expiresAt, lease_expires_at}`, with `success: false` when
nothing was renewed. A lease on another tenant's partition is simply not renewed, so a leaked lease
id is indistinguishable from an expired one. Renewal keeps the delivered set, so the fast path still
applies to the eventual ack.

## Acks inside a transaction

[`POST /api/v1/transaction`](/reference/http/transaction/) bundles pushes and acks, plus the optional
KV, timer and position riders, into **one** command, planned into **one** entry, so it applies whole or
not at all. A lease-less ack in the bundle takes the lease id the request names (in `requiredLeases`
or on its other acks) when all of those name the same one.

Every failure rolls the whole bundle back and writes nothing: a pushed message that is a duplicate
(`QDUP`), an acked item the cursor does not honour (a wrong or expired lease, an already acked or
unresolvable position: `QTXN`), a lost `required` KV precondition. The answer is still HTTP `200`,
with `success: false`. Here an unresolvable ack aborts the bundle instead of redelivering, because
the pushes that ride along must not commit on their own.

The transaction is atomic, but it is not exactly-once end to end. A lost response plus a client retry
still duplicates unless the `transactionId` is deterministic and the retry lands inside the
deduplication window.
