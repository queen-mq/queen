A push is not written by the request that carries it. The request is turned into commands, one per
partition, and the leader's batcher plans every command that arrived during a cycle into one entry
of the replicated log. The HTTP answer comes back only when that entry has been written, fsynced,
committed and applied on the node that took the request.
[`POST /api/v1/push`](/reference/http/push/) is the route contract: the body, the per-item statuses,
the deduplication rules. This page is what happens behind it.

## 1. The edge: admission before the body

The push route carries an admission layer (`admit_edge` in `server/src/handlers/raft.rs`) that runs
after authentication and tenant resolution and before the body is read. It takes permits from one
process-wide byte budget, sized by the request's `Content-Length` (64 KiB for a request without
one). A push that has to wait for room holds only its connection: its bytes stay in the socket and
TCP slows the sender. If no room frees within the hold, the answer is `429` with a `Retry-After`
between 1 and 5 seconds. The permits are returned when the reply is ready.
[Flow control](/internals/flow-control) has the budget, the hold and the disk gate that answers
`507`.

## 2. The receiver: parse, bound, dedup inside the request, group

The receiver is `push_impl` in `server/src/rsm/facade/real.rs`. An empty `items` array answers `201`
with `[]` at once. A `transactionId` longer than 65,535 bytes rejects the request before anything is
submitted. For each item the receiver:

- mints a UUIDv7 message id;
- resolves the transaction id: the client's `transactionId` if present, otherwise the minted
  message id as a string, so every message has one;
- resolves the partition, defaulting to `Default`;
- checks the name budget: the tenant, the queue and the partition together may take at most 447
  bytes (LMDB's 511-byte key limit minus a reserve for the rest of the key), else the request fails
  with `413`;
- **deduplicates inside the request**, keyed on `(queue, partition, transactionId)`. The first
  occurrence leads; a repeat produces no frame and inherits the leader's final verdict, message id
  and offset when the response is rendered, so if the leader turns out to duplicate something
  already stored, the repeat reports the original too;
- hashes the transaction id with `xxh3_128` (16 bytes);
- encrypts the payload when the queue is configured for encryption;
- packs one frame per message: flags, message id, transaction id, the producer subject taken from
  validated authentication (never from the body), and the payload.

The surviving items are grouped by `(queue, partition)`, and each group becomes one push command. A
request that names three partitions is three commands. They are submitted together and the response
waits for all of them, but they are separate commands: they can land in different entries, and a
push request is not atomic across partitions. Use
[`POST /api/v1/transaction`](/reference/http/transaction/) when several writes must commit together.

## 3. The cycle: many commands, one entry

On the leader, the batcher (`server/src/rsm/batcher.rs`) drains the bounded command channel
(`QUEEN_RAFT_COMMAND_QUEUE_DEPTH`, 1024 commands) into a cycle. A cycle is cut at 4096 commands, at
an estimated 4 MiB, or after 5 ms of planning, and the rest waits for the next one. Every command
that is not a plain push (acks, pops, renewals, transactions, KV, timers) waits in a priority lane
that each cycle drains before any push, so consumption does not wait behind a burst of writes. Each
command's request id is looked up first: a command already planned and committed is answered from
its recorded outcome and never planned twice. That lookup is what makes a follower's retry of a
forwarded command safe after a lost answer or a leader change.

Nothing waits on a timer. While up to 4 entries are in flight (`QUEEN_RAFT_PIPELINE`), the commands
that arrive join the next cycle, so an entry carries one command at low load and many under load.
Batching is emergent, not configured.

## 4. The planner: probe, then allocate

`plan_push` (`server/src/rsm/planner/push.rs`) plans one command, reading committed state through a
store read transaction plus an **overlay** of every entry still in flight and every command planned
earlier in the same cycle. The overlay is how the second push to a partition in one cycle sees the
first one's offsets and hashes before either has applied.

1. **Resolve the queue.** A queue that does not exist yet is created by this push: a `QueueUpsert`
   effect with the implicit defaults (lease 60 s, retry limit 3, dead-lettering on, dedup window
   3600 s).
2. **Resolve the partition.** A partition that does not exist yet gets a `PartitionCreate` effect
   and the next partition id from the one counter in `meta`.
3. **Probe for duplicates**, only on an existing partition and only when the queue's
   `dedupWindowSeconds` is above 0. Each item's hash is looked up in the committed hash lists and in
   the overlay; an occurrence counts when it was appended inside the window. A duplicate keeps the
   **original** occurrence's offset and contributes nothing to the append.
   [Deduplication](/internals/dedup) has the details.
4. **Allocate.** The survivors get one gapless run of offsets starting at the partition's
   `last_offset + 1`, and one timestamp, `max(now, last_created_at + 1 µs)`, so timestamps are
   strictly monotone per partition.
5. **Build the `Append` effect**: the survivors' frames concatenated as they were packed, never
   repacked, and their 16-byte hashes in frame order.

A push whose every item is a duplicate emits no effect: it is answered at once and never logged. A
command whose planned size exceeds `QUEEN_RAFT_ENTRY_MAX_BYTES` (96 MiB) is refused, and its items
come back with status `error`.

The planner stamps `now` for the whole cycle; apply has no clock. Every time and every id the entry
needs is decided here and carried in the effects.

## 5. The log: written and fsynced before anything applies it

The batcher proposes the entry through the replicator. With the local replicator, the writer thread
takes every pending entry into one group (at most 4096 entries or 4 MiB), writes each `Append`'s
payload as a message record into its queue's log and the entry's payload-free record into the logs
the entry touches, and fsyncs each touched log once. Only then does the group go to apply. With
`QUEEN_QLOG_SHARDS=K`, queues share `K` logs, so a group fsyncs at most `K` files however many queues
it touches. The log writer also compresses each payload (zstd level `QUEEN_RAFT_QLOG_ZSTD_LEVEL`,
default 1); on the node that plans the command, the receiver starts that compression early, while
the command waits for its cycle.

With the openraft replicator the leader appends the entry through the same group write, followers
append it the same way, and the entry commits once a majority of voters hold it.

## 6. Apply

The apply thread executes the entry's effects in order, on every node. For an `Append` it checks that
`base_offset` is the partition's next offset (a mismatch stops the node: the planner and this node
disagree about the log), records the hash list as one `txns` row, moves the partition's
`last_offset`, `last_write_at` and `oldest_live_at`, bumps the counters at partition, queue and tenant
scope, and updates the `pending` rows that make the partition a candidate for each subscribed group.
The payload itself is not copied: it is already in the queue log. Apply then wakes parked pops: one
per group whose partition became claimable.

## 7. The answer

When the entry has applied on this node, the batcher answers each command from its recorded outcome,
and the receiver renders one result per input item, in input order:
`{index, message_id, transaction_id, queueName, status, offset}`.

- `queued` carries the message's offset.
- `duplicate` carries the **original** message's offset and message id. The id is read back from the
  original's frame in this node's queue log.
- `error` marks the items of a command the planner refused.

The broker never answers `buffered`: there is no spool. When a write cannot be taken (no leader, an
election, a lost quorum, a planning deadline), the whole request fails with `503` and
`Retry-After: 1`, sometimes with a `leader` hint, and the client retries.

On a follower of a cluster (with `QUEEN_RAFT_CLIENT_OFFLOAD`, the default), steps 1 and 2 run on the
follower, the prepared commands go to the leader over the Raft RPC listener, and the follower waits
until it has applied the entry's index before it renders the same answer from its own state. The
leader applies its own admission budget to those commands.

## Failure modes worth predicting

| What happens | What the client sees | What is stored |
| --- | --- | --- |
| Duplicate inside one request body | later items report `duplicate` with the first item's message id and offset | one copy |
| Duplicate of an earlier push, inside the window | `duplicate` with the original's message id and offset | nothing new; an all-duplicate command is not even logged |
| The byte budget stays full for the whole hold | `429`, `Retry-After` 1 to 5 s | nothing |
| The node that takes the request is in push maintenance mode | `503` with `{"success":false,"error":"maintenance"}` | nothing |
| The data directory's filesystem at `QUEEN_RAFT_DISK_HIGH_PCT` (85%) | `507` | nothing |
| Tenant, queue and partition names over 447 bytes | `413` | nothing |
| A body over `QUEEN_MAX_BODY_BYTES` (64 MiB) | `413` | nothing |
| A planned command over `QUEEN_RAFT_ENTRY_MAX_BYTES` | that command's items report `error` | nothing for that partition |
| No leader, or leadership lost while the entry was in flight | `503`, `Retry-After: 1` | the entry may or may not have committed. A retry that reuses the same `transactionId` inside the dedup window is answered `duplicate` for whatever did commit |

That last row is the reason to always send a `transactionId`. Without one, the minted message id is
the transaction id, a retry mints a new one, and a push that committed before its answer was lost is
stored twice.

## Why one entry per cycle is the interesting part

The cost of a write group is mostly its fsyncs, one per touched queue log, not its bytes. The lever
is messages per fsync, and the design pulls it twice without a timer: the batcher folds every command
that arrived during the previous cycle into one entry, and the log writer folds every entry pending
when its last fsync finished into one group. A client that pushes
larger batches makes each `Append` bigger; many clients pushing at once make each entry and each
group bigger. Neither needs a server-side batch size, and there is none.
