This page follows one push, one pop, one ack and one transaction through a node, from the HTTP
edge to the answer. Read it when you need to know what a status code means, or how far a write
had got when you were answered. The parts it names are on [architecture](/internals/).

## Push

```sh
curl -X POST localhost:6632/api/v1/push -H 'content-type: application/json' -d '{
  "items": [{"queue": "orders", "partition": "customer-42",
             "transactionId": "order-1001", "payload": {"total": 30}}]}'
```

1. **Edge.** The request takes admission permits sized by its `Content-Length` before its body is
   read. When the budget (`QUEEN_RAFT_ADMIT_MAX_MB`, at least 128 MiB) is spent the request waits,
   holding only its connection, for up to `QUEEN_RAFT_ADMIT_HOLD_MS` (15000), then gets
   `429 overloaded` with a `Retry-After` of 1–5 s. A node above `QUEEN_RAFT_DISK_HIGH_PCT` (85)
   answers `507 storage_full`. A name too long for a store key answers `413`.
2. **Receiver.** The node mints a request id and a deadline, gives each item a message id, hashes
   its `transactionId` (the message id when there is none), packs one frame per message, and
   encrypts the payload if the queue is encrypted. A follower sends only this prepared command to
   the leader, over `QUEEN_RAFT_FWD_STREAMS` (4) streams, with its own share of admission there.
3. **Planner.** A retry under the same request id within `QUEEN_RAFT_REQUEST_ID_WINDOW_S` (60)
   gets the recorded outcome. The first push that names a queue or a partition creates it in the
   same entry.
4. **Dedup.** For an existing partition, a bloom filter answers "certainly new" or "maybe". A
   "maybe" is checked exactly against the committed hash lists and the entries in flight, inside
   the queue's dedup window. A duplicate gets the original offset and adds nothing; the survivors
   get one gapless run of offsets.
5. **Log.** Each payload goes into its queue's log file, an entry record into every log the entry
   touches, then one fsync per touched log. Each follower does the same before it acknowledges.
6. **Answer.** `201` when the entry commits (`QUEEN_RAFT_ANSWER_AT_COMMIT`, on by default): on one
   node once the fsync returns, in a cluster once a majority has fsynced it. A push with a duplicate
   item waits for local apply, because its answer carries the original message id from the log.
   Every node then applies the entry and wakes the long polls waiting on the partition.

## Pop

```sh
curl 'localhost:6632/api/v1/pop/queue/orders?consumerGroup=billing&batch=10&wait=true&timeout=30000'
```

1. **Engine.** The pop goes to the consumption engine on the leader (a follower forwards it). The
   engine serves only while its node leads and has heard from a quorum within
   `QUEEN_CONSUME_LEADER_LEASE_MS` (400); otherwise the caller takes the pop to the new leader.
2. **Claim.** The engine takes the group's claimable partitions, oldest first. A partition becomes
   claimable when apply reports an append to it, or when a lease on it is released, expires, or a
   delay ends. Each claimed partition gets a lease for the queue's `leaseTime`. The engine stops
   claiming a margin before the caller's deadline (250 ms at most, a quarter of the time left at
   most), so it never leases messages nobody can receive.
3. **Nothing to claim.** With `wait=true` the pop is held on the leader until a partition of the
   group becomes claimable or the deadline comes (`204`).
4. **Durability.** A lease is a change to the group's cursor row. Every
   `QUEEN_CONSUME_CHECKPOINT_MS` (5) the engine logs the changed rows as a checkpoint, and the pop
   is answered only once the checkpoint holding its lease has committed. `QUEEN_CONSUME_FAST=1`
   answers before that, and a leader change can then lose the lease.
5. **Payloads.** The node that answers reads the messages from its own queue logs once it has
   applied up to the leader's index. A follower that cannot catch up before the deadline hands the
   leases back at once.

## Ack

```sh
curl -X POST localhost:6632/api/v1/ack -H 'content-type: application/json' -d '{
  "transactionId": "order-1001", "partitionId": "17", "leaseId": "<from the pop>",
  "consumerGroup": "billing", "status": "completed"}'
```

1. **Lease check.** The engine checks a `leaseId` against the live lease: same holder, not
   expired. An ack without a `leaseId` is not checked and still advances the cursor.
2. **Cursor.** The acked hashes are resolved inside the leased batch and the cursor moves. A
   `failed` status charges the retry budget, and past it the message goes to the DLQ in the same
   checkpoint as the cursor row.
3. **Answer.** As for a pop: once the checkpoint holding the new cursor row has committed.
4. **Repeat.** An ack sent again after it released its lease (its reply was lost) is answered as
   the first one was, on any leader: the released lease is kept in the cursor row.

## Transaction

```sh
curl -X POST localhost:6632/api/v1/transaction -H 'content-type: application/json' -d '{
  "operations": [
    {"type": "ack", "transactionId": "order-1001", "partitionId": "17",
     "consumerGroup": "billing", "leaseId": "<from the pop>", "status": "completed"},
    {"type": "push", "items": [{"queue": "receipts", "partition": "customer-42",
     "transactionId": "receipt-1001", "payload": {"total": 30}}]}],
  "kv": [{"op": "put", "ns": "orders", "key": "1001",
          "value": {"status": "paid"}, "ttlSeconds": 2592000}]}'
```

1. **Receiver.** The body is validated (`kv` and `timers` are top-level arrays, not operations)
   and the pushes are packed like a push. A body of the wrong shape is a `400`.
2. **Acks, on the leader.** Before planning, the engine validates every ack on shadow copies of
   the cursors. An ack whose lease is expired or another worker's, or whose message is already
   acked, rolls the whole transaction back (`rejected_ack`). Otherwise the engine reserves those
   partitions (no pop, ack, expiry or checkpoint touches them until the entry lands, or for
   `QUEEN_CONSUME_TXN_TTL_MS`, 30000, at most) and hands the planner the cursor rows to write.
3. **Planner.** Pushes, then positions, then KV, then timers, then the engine's rows. A duplicate
   push rolls the whole transaction back (`duplicate`), and so does a lost KV `required`
   precondition (`kv_precondition`). A rollback restores the planner's view: nothing is logged.
4. **One entry.** Everything goes into one entry, written into every queue log it touches. Crash
   recovery replays it only if every copy is present (see [storage](/internals/storage/)).
5. **Answer.** After the entry applies on the answering node, so KV results are read at the
   entry's position: `200` with `success: true`. A rollback is also `200`, with `success: false`
   and a `reason`.

## After a leader change

The receiving node retries a command under the same request id, against the new leader, until
its deadline. That is safe for everything the planner logs (pushes, transactions, KV, timers): if
the entry committed, the new leader returns the recorded outcome; if not, it plans the command.

Acks and nacks are served from the engine's memory and leave no request-id record. If the leader
loses its lead while the checkpoint carrying an ack is on its way, or a forwarded ack is lost after
it went out, the answer is **`503 outcome_unknown`: the ack may or may not have applied.** Send the
same ack again: if it applied, the repeat is answered as a success. A transaction is not
repeat-safe through its acks (a retry finds them settled and rolls back), so give its pushes a
deterministic `transactionId`: a retry of a committed transaction then rolls back as a duplicate
and the first commit stands.

A graceful stop of the leader waits up to `HAND_OFF_DRAIN` (500 ms) for the acks it already
answered to commit before it hands leadership over. A new leader takes over only after applying
an entry of its own term, and loads leases from the committed cursor rows: a leased batch is not
redelivered before its lease expires.

## When you are answered

| Command | Leader answers | Follower answers |
|---|---|---|
| Push, no duplicate | when the entry commits | when it learns the entry committed in the leader's term |
| Push with a duplicate | after the entry applies locally | after it applies the entry |
| Pop | after the lease's checkpoint commits | after it applies up to the leader's index |
| Ack, nack, renew | after the cursor row's checkpoint commits | when the leader's answer arrives |
| Transaction, KV | after the entry applies locally | after it applies the entry |

## Limits

- **Delivery is at-least-once.** A lease that expires before the ack lands puts the batch back.
- **`503 outcome_unknown` and `503 timeout` do not say whether the change applied.** Make retries
  harmless with `transactionId` and `once`. See [dedup](/concepts/dedup/).
- **Lease exclusivity across a leader change** needs node clocks within
  `QUEEN_RAFT_MAX_CLOCK_SKEW_MS` (500 ms).
- **Transactions are one call.** There is no BEGIN and COMMIT across requests. See
  [transactions](/concepts/transactions/).
