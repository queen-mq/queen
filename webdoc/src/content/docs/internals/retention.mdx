Retention has two halves. The leader decides what is dead and writes that decision into the
replicated log: watermark moves, partition deletes, trace expiry. Every node applies those effects
to its own state. Then each node, on its own, reclaims the queue-log files the watermarks made dead.
The decision is replicated; the file work is not, because each node's files have their own
boundaries.

Nothing is deleted message by message. A partition's retained messages are one contiguous range of
offsets, retention cuts the head of that range, and the unit it cuts is one append: the messages one
write added to the partition.

## The pass

The leader's batcher sets a maintenance pass due every `RETENTION_INTERVAL` milliseconds (default
5000). The pass is planned on the leader's planning thread from committed state, inside an ordinary
cycle, and its effects go into that cycle's entry as one command with its own request id, answered
by nobody: they commit, apply and replay like a client write. A pass that knows more work remains
runs again in the next cycle instead of waiting for the tick. A follower plans nothing; on a
follower the tick only starts the file reclaim described below.

One pass, in order:

<Steps>

1. **Unfinished deletions.** Every partition still in the `garbage` set (a queue, consumer group or
   tenant delete whose data has not all been removed yet) gets one bounded `DeleteChunk`. The resume
   point is kept in state, so a chunk replayed after a crash never sweeps a range twice.

2. **Queues.** For each queue the pass computes the cutoffs below, then visits up to
   `QUEEN_RAFT_RETENTION_VISIT` partitions of that queue (default 8192), starting where the previous
   pass stopped and wrapping, so a queue with more partitions is covered over several passes. A
   visited partition gets at most one effect: a `Watermark` when its watermarks move, otherwise a
   `PartitionDelete` when it is dead.

3. **Traces.** When the oldest trace is older than `QUEEN_RAFT_TRACE_RETENTION_S` (default 604800,
   seven days), one `TraceExpire` drops every trace created before that cutoff.

</Steps>

`RETENTION_BATCH_SIZE` (default 1000) bounds a pass: at most that many watermark, partition-delete
and deletion-chunk effects, a deletion chunk of at most that many rows, and a watermark moved past at
most that many appends of one partition. A value of 0 is ignored.

## The cutoffs

Per queue, from its configuration and the pass's one instant:

| Rule | Applies when | Cutoff |
| --- | --- | --- |
| Retention | `retentionEnabled` and `retentionSeconds` above 0 | now minus `retentionSeconds` |
| Completed retention | `retentionEnabled` and `completedRetentionSeconds` above 0 | now minus `completedRetentionSeconds`, never past what every consumer group has acknowledged |
| Max wait | `maxWaitTimeSeconds` above 0, whatever `retentionEnabled` says | now minus `maxWaitTimeSeconds` |
| Hash window | always | now minus the largest of `dedupWindowSeconds`, `completedRetentionSeconds` and `QUEEN_RAFT_TXN_WINDOW_MIN_S` (default 900) |

A rule that does not apply contributes nothing. A queue for which none of the first three applies
keeps its messages forever.

## Two watermarks

Each partition has two watermarks, and they only move forward:

- `log_start` is the first offset whose message is still retained. Offsets below it are gone, and
  the queue's `total` counts from it.
- `txns_start` is the first offset whose hash list is still kept. The hash lists are what duplicate
  detection and acks by transaction id read, and they outlive the messages: `txns_start` is never
  above `log_start`, so inside the hash window a duplicate push is still recognised and an ack by
  transaction id still resolves after the message itself is gone.

For each visited partition the pass reads its append records from `txns_start`, oldest first (one
record per append, carrying its first and last offset and its creation time), and computes:

- **Retention and max wait**: `log_start` moves past every append older than the cutoff, in order,
  and stops at the first one that is not. Consumption plays no part. Max wait therefore deletes
  unconsumed messages for every consumer group, leased ones included, and dead-letters nothing: its
  purpose is to bound how long data may sit.
- **Completed retention**: the same walk with its own cutoff, but it also stops at the first append
  that holds an offset some consumer group has not acknowledged (above the lowest committed offset
  among the partition's cursors). A partition with no cursor gets nothing from this rule, so an
  unconsumed backlog is never removed by it.
- The new `log_start` is the furthest any rule reached. It always lands on an append boundary: an
  append that is partly unconsumed stays whole.
- **Hash window**: `txns_start` moves past the appends older than the hash window, never past the
  new `log_start`.

If either watermark moved, the partition gets one `Watermark` effect. Apply refuses one that moves a
watermark back or puts `txns_start` above `log_start`, releases the messages below `log_start` (the
queue's `retainedBytes` goes down with them), drops the hash lists below `txns_start`, and records
the move in the node's `local.db`, which the Retention chart and `GET /api/v1/analytics/retention`
read ([Counters, rates and lag](/internals/stats)).

## Quiet empty partitions

A partition whose watermarks did not move is checked for cleanup when
`QUEEN_PARTITION_CLEANUP_ENABLED` is on (the default; `0`, `false`, `off` or `no` turns it off),
against a window of `PARTITION_CLEANUP_DAYS` (default 30; a value of 0 is ignored). It is dead when
all of these hold:

- it was created, and last written, before the window;
- it retains no message (`log_start` is past its last offset);
- no dead letter is filed against it;
- no consumer group holds a live lease on it, or created its cursor, took a lease or had one expire
  inside the window;
- no streams state is kept for it.

A dead partition gets a `PartitionDelete`. The batcher drops that effect when a push in the same
cycle, or in an entry still in flight, touched the partition, and a later pass judges it again.
Apply removes the partition and everything keyed by it: cursors, leases, pending rows, hash lists,
counters and its claims on queue-log files.

## Reclaiming the disk

A watermark frees nothing on disk by itself. A message's bytes and its hash list are one record in
its queue's log files (`qlog/` in the data directory), so a record is dead only once `txns_start` has
passed it, or once its partition no longer exists. Each node reclaims its own files:

- Each maintenance tick starts one reclaim pass, unless the previous one is still running, on the
  leader and on every follower alike. `QUEEN_QLOG_RECLAIM` set to `0`, `false`, `off` or `no` turns
  it off, and then the disk only grows.
- Only sealed files are candidates, and only those whose records are all at or below the node's
  recovery floor (its last durable point): a file recovery may still need is never touched. The
  active file is never touched either; the queue-log writer seals an active file whose data is older
  than `QUEEN_QLOG_SEAL_AGE_S` (default 600, `0` never), so a queue that went quiet does not keep
  its last file forever.
- A file with no live message is unlinked. A file mixing live and dead messages is rewritten with
  only its live records once enough of it is dead: at the first dead message in a per-queue log, at
  half of its message bytes in a shared log (`QUEEN_QLOG_SHARDS` above 0).
  `QUEEN_QLOG_COMPACT_MIN_DEAD_PCT` (0 to 100) overrides both.
- One pass examines at most 256 sealed files, rewrites at most one, and stops after 200 ms. The next
  tick continues where it stopped.

The passes log under the `rsm` target: a pass that took 20 ms or more, the files a pass reclaimed,
and a failed pass, which is retried at the next tick.

Three consequences for sizing the data volume:

- a message stays on disk until its retention rule and the hash window have both passed it, and then
  until the file around it is reclaimed;
- a queue with no retention rule never frees its files: `txns_start` cannot pass `log_start`;
- a shared log mixes queues, so one queue's long retention can keep another queue's dead bytes on
  disk until half of the file is dead.

When the data directory's filesystem reaches `QUEEN_RAFT_DISK_HIGH_PCT` used (default 85), writes are
refused with `507` until it is back under `QUEEN_RAFT_DISK_LOW_PCT` (default 80).

## What retention does not touch

- **Dead letters.** No pass removes them, and a partition holding one is never cleaned up. They
  leave through an explicit call ([dead-letter routes](/reference/http/messages-dlq/)).
- **KV keys and timers.** Each has its own mechanism: the [KV expiry sweep](/internals/kv) and the
  [timer fire](/internals/timers).
- **Queues.** Deleting a queue is an explicit call. Its name is removed, and reusable, at once; its
  partitions go in bounded chunks that later passes resume.

## Configuring it

Retention is opt-in per queue: `retentionEnabled` plus a positive window, or `maxWaitTimeSeconds` on
its own. Every key, with the value the code applies when you omit it, is on
[Queue options](/reference/queue-options/), and the operator's view is
[Operations](/deploy/operations/). `POST /api/v1/configure` merges by default, so an edit that omits
`retentionEnabled` leaves it as it is; `"mode": "replace"` resets every option the body does not name
to its default.

Partition cleanup is the one rule that is not per queue: `PARTITION_CLEANUP_DAYS` and
`QUEEN_PARTITION_CLEANUP_ENABLED` are broker-wide. A queue that keeps its data forever is unaffected
in practice, because a partition that retains a message is never dead.
