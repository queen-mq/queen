Open a Queen database with `psql` today and you find the log engine, the shared management tables,
and nothing else. That was not true until **2026-07-30**, and this page is the record of what was
there, why it lingered, and what finally removed it.

Two storage engines shaped this schema before the current one:

- **The rows engine**: one row per message in `queen.messages`, coordination in
  `queen.partition_consumers`. Its DDL and procedures were files `001`–`018`.
- **The `seg_*` engine**: the first segment-based engine, which folded its cursor columns onto the
  rows engine's coordination table. Gone since the log engine landed, and actively dropped from any
  database at every boot by `040`.

The current engine is the **log engine**, files `040`–`051`.

## What was removed, and when

The rows engine went in two steps, both on 2026-07-30.

**Its message plane**, meaning push, the four generations of pop, ack, transaction, lease renewal, the
pending probe, the two `partition_lookup` maintainers and `streams_cycle_v1`. A call-graph closure
over `server/src` and the surviving SQL found **zero callers** for all sixteen functions; the only
references left in the tree were comments. Eleven files and 4,662 lines went, and
`049_drop_rows_message_plane.sql` removes the functions from databases that had already applied them.

**Its tables and its remaining branches.** `queen.messages`, `queen.partitions`,
`queen.partition_consumers`, `queen.dead_letter_queue`, `queen.messages_consumed` and
`queen.partition_lookup` are dropped by `050_drop_rows_tables.sql`, and every surviving procedure was
rewritten to stop referencing them. That was 49 references across 13 files: 6 unreachable
`storage = 'rows'` branches, 36 joins over tables that were permanently empty, and **6 genuine
defects** where the empty-or-phantom table changed a number somebody read.

<Aside type="note">
Dropping the tables was safe because this broker has no importer and no in-place upgrade: a
deployment starts from a clean database, so they were empty by construction. See
[Compatibility](/reference/compatibility). If you point this build at a database that did carry
rows-engine data, take a dump first: the boot apply removes it.
</Aside>

### The six defects the rows tables were still causing

Five of them traced back to one line: `configure_queue_v1` inserted a `Default` row into
`queen.partitions` on every `/configure`, for a partition the engine never used. It was the only
writer that table had.

| Surface | Reported | Truth |
| --- | --- | --- |
| `GET /resources/namespaces` and `/resources/tasks`, field `partitions` | the count of `/configure`-created rows, so **0** for any queue created by push | the live log-partition count |
| `queue_lag_metrics.partitions_created`, plotted as "Partitions Created" | one event per `/configure` call | partitions actually allocated by push |
| `queue_lag_metrics.partitions_deleted` | never moved | partitions reclaimed by the retention cleanup |
| `/configure` response, `partitionId` | a uuid resolving to nothing | `null`, because partitions are created by the first push |
| `queen_dlq_depth` (Prometheus) | **no sample at all**, because it read the empty rows DLQ | the live `queen.log_dlq` depth |

The last one is the one to remember: DLQ alerting could never fire, while `GET /api/v1/dlq` listed
the same rows correctly the whole time.

## Tables the log engine uses

Everything in `schema.sql` today is either the log engine's or genuinely shared: `queen.queues` (the
configuration row), `consumer_groups_metadata`, `consumer_watermarks`, `stats`, `stats_history`,
`retention_history`, `message_traces`, `message_trace_names`, `system_state`, `system_metrics`, the
worker-metrics tables and `queue_lag_metrics`. Do not assume that anything defined there is retired: after this
change, nothing is.

Three of them keep a `partition_id` column that now carries a **`queen.log_partitions` id with no
foreign key**: `stats`, `retention_history` and `message_traces`. The constraints were dropped
because a log partition never had a row in the rows table, and they stay dropped because each of
those rows must be able to outlive its partition: a retention audit row is written by the very step
that deletes the partition.

## Why `queen.stats` reports engine "segments"

Because `queen.queues.storage` holds the literal value `'segments'` for every log queue, and that is a
**public compatibility value**, not a description of the engine.

The chain is:

1. `POST /api/v1/configure` accepts and returns `storage: "segments"`. That is part of the wire
   contract and did not change when the engine did.
2. The first push creates the `queen.queues` configuration row with `storage = 'segments'`.
3. Two admin readers still join on `storage = 'segments'`, not to select an engine (there is only
   one) but as a queue-existence guard. See the header of `047_log_admin.sql`.
4. `log_refresh_all_stats_v1` selects the queues to refresh with `WHERE q.storage = 'segments'` and
   labels its summary `engine: "segments"` with a `segPartitions` count, so the label stays aligned
   with the column value. `stats.rs` prints that summary verbatim.

So "segments" in a stats row, a summary line, or a `/configure` response means "the non-rows engine".
Read it as a discriminator, not as a version. The tables it actually reads are `log_partitions`,
`log_consumers`, `log_segments` and `log_dlq`.

## What the boot-time apply drops

`040_log_drop_legacy.sql` is a teardown file that runs on every boot, forever, and is a no-op when
there is nothing to drop. Everything in it is catalogue-driven or `IF EXISTS`.

**Every `seg_*` function.** A `DO` block collects `DROP FUNCTION IF EXISTS queen.<name>(<args>)
CASCADE` for every `pg_proc` entry in schema `queen` whose name matches `seg\_%` with
`prokind = 'f'`, reconstructing signatures with `pg_get_function_identity_arguments` so overloads each
get their own drop. The statements are collected into an array *before* any of them runs, so the
catalogue scan never iterates over rows it is concurrently invalidating; `CASCADE` may take dependent
functions out mid-loop, and `IF EXISTS` makes the already-cascaded drops harmless. It is dynamic rather
than a hardcoded list because the legacy roster changed across builds and a fixed list would silently
miss stragglers.

**Every `seg_*` table.** Explicitly `queen.seg_dedup`, `seg_dlq`, `seg_segments`, `seg_partitions`,
`seg_queues` and `seg_migration_progress`, then a dynamic `pg_class` sweep for any other `seg_%`
ordinary or partitioned table, all `CASCADE`. No data is preserved: the log engine was a greenfield
replacement with no migration.

**Nine columns from `queen.partition_consumers`.** The `seg_*` engine grafted its cursor onto the rows
engine's coordination table. That table is itself gone as of `050`, so on any database this build has
booted the block is a permanent no-op. It is guarded on the table existing and stays only for a
database coming straight from the `seg_*` era, where the columns are dropped with
`DROP COLUMN IF EXISTS`, taking their dependent indexes and constraints with them:

```text
next_seq, next_off, batch_end_seq, batch_end_off, batch_positions,
attempt_seq, attempt_off, attempt_count, total_consumed
```

The whole block is wrapped in a `to_regclass` guard so the file survives even a database where
`partition_consumers` itself is absent.

Three other constraint drops happen in the `04x` files, for the same underlying reason. Log-engine
rows have no counterpart in the rows-engine tables the foreign keys pointed at:

| Dropped | File | Why |
| --- | --- | --- |
| `log_queues_name_key` | `041` | superseded by the composite unique index on `(tenant_id, name)` |
| `retention_history_partition_id_fkey` | `045` | pointed at `queen.partitions`, where no log partition had a row. Its cascade is replaced by an age purge |
| `message_traces_partition_id_fkey` and `message_traces_message_id_fkey` | `047` | same reason; otherwise tracing a log message failed |
| `stats_partition_id_fkey` | `050` | same reason, on the last surviving table that still pointed at `queen.partitions` |

## The migrate subcommand

`queen migrate ...` still exists as a CLI entry point and is a **stub**. It logs that migration is
not supported on the log engine and exits non-zero **without opening a database connection**. The
rows-to-segments migration it used to run was built on SQL that was deleted with the `seg_*` engine.

There is no rows-to-log migration on this tree. The log engine boots its own schema.

## What to do with any of this

Nothing, in normal operation. One rule survives the cleanup:

- **When reading the database, start from the `log_*` tables.** They are the only place the engine
  keeps data. Everything else you find is shared infrastructure (configuration, stats, metrics,
  traces) rather than an artefact of a retired engine. There are no longer any of those.
