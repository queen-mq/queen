Deduplication in Queen is exact: no sampling, and no "best effort" qualifier. Within a partition and
within the queue's window, a `transactionId` that has already been stored writes nothing and comes
back with `status: "duplicate"`, the original message's id and the original's offset. Probabilistic
structures appear only where they make an exact answer arrive faster, never where they could change
it.

It is on by default. A queue created by a push or by `/configure` gets `dedupWindowSeconds: 3600`, and
only an explicit `0` turns it off.

## Two layers, one authority

| Layer | Where | Scope | Authority? |
| --- | --- | --- | --- |
| 1 | the receiver | one request body, keyed on `(queue, partition, transactionId)` | first wins inside the request |
| 2 | the planner, on the leader | the partition's window: committed hash lists plus every entry still in flight | **yes** |

Layer 1 exists so the planner is never handed two frames with the same hash in one command. The first
occurrence leads and a repeat becomes a follower that produces no frame. When the response is
rendered, a follower inherits its leader's final result: if the leader itself turns out to be a
duplicate of something already stored, the follower reports the original's id and offset too.

Layer 2 is the verdict, computed in `plan_push` (`server/src/rsm/planner/push.rs`) before any offset is
allocated.

## The probe: before allocation, in one planner

For each item of a push command, and only when the partition already exists and the queue's
`dedupWindowSeconds` is above 0, the planner looks for an earlier occurrence of the item's 16-byte
hash (`xxh3_128` of the `transactionId`) whose timestamp is at or after `now - dedupWindowSeconds`.
It looks in two places:

- **the committed hash lists**: the `txns` rows, one per `Append`, each holding the hash of every
  message it appended in frame order;
- **the overlay**: the appends of every entry still in flight and of every command planned earlier in
  the same cycle.

If it finds one, the item is a duplicate and keeps the **lowest** matching offset, which is the
original. Only the survivors get offsets and go into the `Append`.

Read it as four claims:

1. **One planner decides.** Only the leader plans, one cycle at a time, and each plan's effects are
   folded into the overlay before the next command is planned. Two pushes of one `transactionId`, in
   the same cycle or while the first one's entry is still in flight, cannot both survive: the second
   one sees the first in the overlay. That is the whole race argument; there is no lock.
2. **A duplicate writes nothing.** A duplicate adds no frame, moves no offset and records no hash. A
   push whose every item is a duplicate emits no effect at all: it is answered at once and never
   logged.
3. **The lowest offset is the original.** One hash can match several occurrences (for example after
   data was pushed while deduplication was off), and the answer carries the first.
4. **A brand-new partition has nothing to probe.** A partition created by this push has no earlier
   occurrence, so the probe is skipped.

Apply records the hash list of every append, whatever the window: `dedupWindowSeconds: 0` skips the
probe, not the write, because an ack by `transactionId` resolves through the same rows
([Ack internals](/internals/ack-internals)).

On a leadership change the new leader starts planning only after it has applied an entry of its own
term, so it plans over every committed append. Its bloom front (below) is reset at that moment.

## The front: skipping the committed read

Almost every pushed message carries a new `transactionId`, so almost every committed read would come
back empty. The planner keeps a **front** in memory (`DedupFront` in `server/src/rsm/dedup.rs`): per
partition, a ring of generational bloom filters at 16 bits per hash. For a hash it answers either
"certainly not in the committed window: skip the read" or "maybe: read". A "maybe" names the offset
bands of the generations that matched, and the committed read becomes a bounded scan of those `txns`
rows. The front never answers "duplicate", and the overlay is always checked whatever it says.

It stays sound because a bloom filter has no false negatives and the front covers every committed
append:

- A partition this leader created is born covered: its committed window is empty.
- A partition that existed before (after a restart, or a new leader) is seeded on first touch from its
  committed `txns` rows plus the appends in flight. If that is too many hashes, the partition falls
  back to always reading.
- Every later append is planned by the same leader, and the planner adds each survivor's hash at plan
  time, before it commits. A hash added for an entry that never commits costs one extra read, never a
  missed duplicate.
- A generation is dropped only when every hash in it is older than the window.

`QUEEN_RAFT_DEDUP_FRONT` (on by default) is the switch; off, every probe reads the committed rows,
with the same verdicts. `QUEEN_RAFT_DEDUP_FRONT_MB` (default 512) caps the front's memory: a
partition that would grow it past the cap falls back to always reading. The front costs about 2 bytes
per in-window message.

## How long a hash lives

Each partition keeps two watermarks. `log_start` is the payload retention watermark. `txns_start`,
below which the hash lists are pruned, trails it: the leader's maintenance step prunes a hash list
only once it is older than the largest of the queue's `dedupWindowSeconds`, its
`completedRetentionSeconds`, and `QUEEN_RAFT_TXN_WINDOW_MIN_S` (default 900 s). The queue-log records
follow the same watermark, so while a hash can still match, the original's frame can still be read,
and the duplicate's answer carries the original message id read back from this node's queue log.

A `transactionId` pushed again after the window has passed is accepted as new, even if its hash list
has not been pruned yet: the probe only counts occurrences inside the window.

## Nothing to coordinate between nodes

Every push, on every node, is planned by the one leader, and every node applies the same entries and
holds the same `txns` rows. A follower serving its own client sends the prepared push to the leader
and renders the leader's verdict. No node keeps a deduplication cache of its own that could disagree.

## The edges

| Situation | Result |
| --- | --- |
| Same `transactionId` twice in one request body | the second item is `duplicate` and carries the first's message id and offset |
| Same `transactionId` in a later request, inside the window | `duplicate` with the original's message id and offset; nothing written |
| `transactionId` pushed again after the window | accepted as new |
| Same `transactionId` in a *different* partition | accepted: deduplication is per partition |
| `dedupWindowSeconds: 0` | no probe; the hash list is still written, so acks still resolve |
| `/configure` called without `dedupWindowSeconds` | the window is **kept**, because `/configure` merges; it is reset to 3600 only on a create or under `"mode": "replace"` |
| Duplicate inside `POST /api/v1/transaction` | the whole transaction rolls back (`QDUP`), HTTP `200` with `success: false` |
| A client retry that reuses its `transactionId` after a lost answer | `duplicate` for whatever did commit |

## A timer's fire is probed like a push

A [timer](/use/timers) carries a transaction id fixed when it was scheduled. On 2.0 its fire is
planned through the same push planner, so the fired message is probed against the destination
partition's dedup window like any push. If that transaction id is already there, the timer is done:
it is deleted and nothing is appended. The fire and the timer's deletion are effects of one entry, so
they apply together or not at all.
