A node keeps three things on its own disk. The queue log files hold every message, and they are
also the write-ahead log: a message is written once, in its queue's log, and that write is the one
that makes it durable. The store holds everything else (queues, partitions, cursors, dedup rows,
KV, timers) in RAM, and checkpoints it to an LMDB file four times a second; no write waits for the
checkpoint. Since 2.0.1 (cluster version 4), message traces live in a second LMDB file of their
own, `traces/` in the data directory, read from disk and never loaded into RAM.

This page covers when a write is durable, what a restart replays, the damage that makes a node
refuse to boot, and how disk space comes back.

## The data directory

```text
$QUEEN_RAFT_DIR                    default /var/lib/queen/raft
  store/data.mdb                   the store checkpoint (LMDB)
  traces/data.mdb                  message traces (LMDB, read from disk; 2.0.1 and later)
  qlog/
    LANES  SHARDS                  the log layout, fixed when the directory is created
    q0/                            the system log: entries that touch no queue
    q<queue id>/r00000001.qlog     a queue's log files, rolling
                r00000001.qidx     the index of a sealed file
                r00000001.qhsh     the hash sidecar of a sealed file, for the boot refill (2.6)
                dirx-<a>-<b>.qdx   which of the sealed files a to b holds a partition's offsets
  raft/                            openraft only: vote, commit point, purge point, membership,
                                   and what the node keeps for a standby (link_holds.json) and
                                   for an away member (member_holds.json, 2.6)
  snapshots/                       a snapshot received from the leader, staged for the next boot
  link.seed                        on a standby's first node: the record of the seed it took
  local.db  dash.db                node-local metrics and dashboard rows (not replicated)
  groups/g1/ ...                   the same layout for each extra raft group (QUEEN_RAFT_GROUPS)
```

A data directory belongs to the replicator that created it: the local replicator refuses a
directory openraft wrote, and the reverse.

## The queue logs are the write-ahead log

We built it this way to write each message once. An earlier design kept the payloads in a
consensus log and copied them into segment files as entries applied, so every message reached the
disk twice. With the queue logs as the log, the bytes that make a message durable are the bytes a
pop reads back.

Each queue has its own log directory by default. A record starts with its length and an xxh3
checksum, and each covers every byte after itself, so a file describes itself: a scanner always
knows where the next record starts, and a record torn by a crash fails its checksum. A message
record holds one append, the messages of one push for one partition after dedup: the partition id,
the first offset, the count, the timestamp, the 16-byte hash of each `transactionId`, and the
payloads.

An entry of the log can touch many queues, and each touched log has to be able to prove, after a
crash, that it holds its part of the entry. So the writer puts a payload-free entry record into
every log the entry touches: the whole record in the lowest one, and a 61-byte stub that names it
in the others. Before the stub layout every touched log got the whole record. With 1,000 queues of
one partition each at 5,000 messages a second on one local node, the copies came to about 14,900
bytes of queue log per message, and the stubs brought it to 236
(`benchmark-queen/2026-09-25-qlog-entry-stubs`, runs `q1000-r5k-copies-np-1` and
`q1000-r5k-stub-np-1`, no preallocation).

From cluster version 7 (2.4.0) an entry record also leaves out the `transactionId` hashes of the
appends whose message records are written with it, in the same log and the same write: those
records already hold them, 16 bytes a message. A read puts them back from the message records and
checks the rebuilt record against its own checksum, so a reader gets the entry that was written,
byte for byte. `QUEEN_QLOG_ENTRY_HASHES=keep` writes them whole, as before.

A payload of at least 512 bytes is stored zstd-compressed at `QUEEN_RAFT_QLOG_ZSTD_LEVEL`
(default 1; `0` turns it off), unless that saves less than a tenth. Compression is node-local: the
replicated entry stays raw, two nodes may store the same record differently, and each payload read
decompresses at one point.

The active file rolls at `QUEEN_RAFT_SEGMENT_BYTES` (64 MiB). A sealed file is immutable and gets a
`.qidx` index beside it, while the active file's index lives in RAM; a stale or missing `.qidx` is
rebuilt by scanning its file. A roll writes and opens that index before it changes anything in
memory: one that fails (no file descriptor, a write error) leaves the file active, with every
message in it still found, and the next roll seals it whole. Both indexes carry append timestamps and offset ranges, so message
browsing can seek a historical window and select its page before reading payloads. Only appends
containing a selected message need to be read and decompressed, once per append for that page.

A log that retains a lot has many sealed files, and an index per file does not say which file
holds a given partition's offset. Each log therefore keeps a directory beside its files
(`dirx-<first>-<last>.qdx`): for a range of sealed files, one sorted entry per partition per file,
"offsets `a` to `b` of this partition are in file `f`". A read of a message outside the active
file asks the directory for the file and then that file's own `.qidx` for the record, so it costs
a few lookups whatever the log retains, where it used to ask the sealed files one by one. The
node's maintenance builds a directory file for every 16 sealed files that have none and merges 8
of a size into one, with sequential I/O only and never on the log writer, and hands a file to the
disk 8 MB at a time while it writes it, so the raft log's sync never waits behind a whole merge; the files it has not
covered yet are asked directly. A directory file is derived data: one that is missing or damaged
is removed at boot and built again from the `.qidx` files (`QUEEN_QLOG_DIRX=0` stops building
them).

`QUEEN_QLOG_SHARDS=K`, set before the directory is created, maps every queue onto K shared logs
(`queue id % K`), so one write fsyncs at most K files however many queues it spans. That is the
layout for many small queues: with one log per queue, a group that touches 10,000
single-partition queues fsyncs 10,000 files.

## When a write is durable

For each group of entries the writer puts the payload records into their queues' logs, the entry
records into every log the entries touch, and then fsyncs each touched log once (`fdatasync` on
Linux). Only then does the entry go to apply. In a cluster every follower does the same before it
acknowledges the append, and the entry commits once a majority has.

**A write is durable when its entry is fsynced in the queue logs of a majority of voters, or on a
single node, in its own.**

<Figure id="internals/storage-write" />

The store is not on that path. Its keyspaces live in RAM, loaded whole at boot. Every
`QUEEN_RAFT_DURABLE_EVERY_MS` (250) or `QUEEN_RAFT_DURABLE_EVERY_BYTES` (256 MiB), a checkpoint
writes the rows that changed into `store/data.mdb`, commits and syncs it, and records the applied
index in the same transaction. That checkpoint bounds what a restart replays. No answer ever waits
for it, which is why a store write costs a push nothing.

From cluster version 7 a push's index row goes into the checkpoint without the hashes of its
`transactionId`s. The queue log keeps the push's message record, which holds them, for as long as
the row exists (a record is reclaimed only below `txns_start`, and rows start at or above it), so
a boot puts them back from the queue logs before it replays anything, and logs `txns rows
refilled from the queue logs` with the count. A row of a 100-message push is then 28 bytes instead
of about 1.6 KB: on one node at 300,000 messages a second, the checkpoint's index table went from
616 to 11 MB (`benchmark-queen/2026-10-15-bytes-per-msg`). `QUEEN_RAFT_CHECKPOINT_TXNS=whole`
keeps the hashes in the checkpoint.

From 2.6 that refill reads no payload from a sealed file. A thread of its own writes, beside each
sealed file, a hash sidecar (`.qhsh`): every record's header and the hashes it carries, about 16
bytes per message, written in 8 MiB steps it waits for so the log's own syncs never queue behind
it. The boot refills the rows from the sidecars, checked by their checksums and record by record
against the file's index, and reads the file itself only where a sidecar is missing or does not
match, building it again afterwards. On 254 GB of queue logs a restart's refill went from 171 to 201
s to 20 s (2026-10-21). `QUEEN_QLOG_HASH_SIDECARS=0` turns the sidecars off.

## Crash recovery

1. The store reopens exactly at its last checkpoint.
2. Each queue log cuts a torn tail from its active file.
3. From cluster version 7, the index rows take back from the queue logs the hashes the checkpoint
   left out, before anything is replayed or read. A row whose record reclaim removed after that
   checkpoint keeps none: the watermark that removed it is above the checkpoint, so the replay
   removes the row again.
4. Recovery merges the entry records of every log by index and replays, from the entry after the
   checkpoint's index, the gapless run of complete entries. The first missing or incomplete entry and everything
   after it is cut from every log: that group's fsyncs did not all land, so it was never
   acknowledged.
5. Apply skips any entry at or below the store's applied index, so replaying twice changes nothing.

An entry that touches three queues is written into three logs and records that it has three
copies, and **it replays only if every copy is present and identical** (the present-in-all rule,
`planner/txn.rs`). This is where transactions get their atomicity on disk. A transaction torn by a
crash is cut from every log and leaves no gap in the offsets, because its offsets were never
applied.

In a cluster a restarted node then catches up from the leader, whose log is kept for it: for a
member that is away, from the entry it had, up to `QUEEN_RAFT_MEMBER_HOLD_S` (6 hours) while the
leader's volume stays below `QUEEN_RAFT_MEMBER_HOLD_DISK_PCT` (2.6), and for one that is connected
but behind, `QUEEN_RAFT_PURGE_HOLD_S` (600). A node the leader has purged past, or a new one,
receives a snapshot instead: the leader's store checkpoint, its trace file and its queue log files
with their indexes. The leader first asks the node where its log stands and sends only the queue
log files above that point, a delta; the whole state goes to a node with no log or older than 2.6,
and nothing to a node that does not answer. The node stages it under `snapshots/`, exits, and swaps
it in at the next boot, never while it serves. A boot opens the sealed files' indexes without
reading them whole and checks them in the background, so it no longer reads every index before it
serves. The first node of a
[standby cluster](/operate/standby/) takes the same snapshot from a node of its source, once, and
one for each raft group when the clusters run several. That
node keeps its log from the snapshot's position on from the moment it is asked, and the source's
other nodes from wherever the standby has got to once it reads, as they do for a follower that is
behind.

## Refused at boot

A node does not guess its way around damage. It refuses to start when:

- a sealed queue-log file holds a record that fails its checksum (sealed files were fsynced before
  the roll, so this is corruption, not a torn tail);
- a damaged record in the active file is followed by a verified record the store already counts as
  durable;
- the queue logs end before the last record the store recorded as durable;
- the copies of one entry disagree across logs;
- a store value fails its checksum. Every value carries an xxh3 over its keyspace, key and bytes,
  and the load at boot verifies every row, the key order and the row counts.

At runtime, a corrupt value that a checkpoint or the scrub meets ends the process. The scrub walks
the whole store every `QUEEN_STORE_SCRUB_EVERY_S` (21600) at `QUEEN_STORE_SCRUB_ROWS_PER_S` (2000),
to find damage on one node before a restart finds it on several. A cluster member that refuses to
boot is restored by wiping its data directory, so it rejoins from a peer. See
[cluster](/operate/cluster/).

## Retention and reclaim

Retention is decided once, on the leader, and executed on every node, like every other change.

1. **Decide.** A scanner on the leader walks every partition at `QUEEN_RAFT_RETENTION_SCAN_PER_S`
   (50,000), at most one round per `RETENTION_INTERVAL` (5000 ms). A store it could walk in a
   fraction of that interval is walked over the whole of it, in 100 steps, so that its
   watermarks do not all reach the planner in the same instant. The planner checks each proposal
   against the current state and logs three watermarks per partition: `log_start`, below which the
   payloads are gone; `rows_start`, below which the store holds no index row; and `txns_start`,
   the lower of the two, below which a record has neither and its file can be reclaimed. A push's
   index row (its offsets, its timestamp and the hashes of its `transactionId`s) is kept for the
   queue's dedup window, and never less than `QUEEN_RAFT_TXN_WINDOW_MIN_S` (900 s). That is
   independent of the message and of the retention that keeps it (`retentionSeconds`,
   `completedRetentionSeconds`): the row of a message retention already took stays for the rest
   of that time, so dedup outlives the payload, and the row of a message that is still retained
   goes at the end of it, so memory does not grow with what a queue retains.
   The messages left without a row are served from the queue log's own index: a consumer that
   far behind reads its positions from disk, as it reads its payloads. One watermark moves at
   most `RETENTION_BATCH_SIZE` (1000) pushes of a partition, and a partition that has more due is
   judged again at once. A partition with no write for `PARTITION_CLEANUP_DAYS` (30), no retained
   message, no dead letter and no live lease is deleted.

   Rows leave ahead of their messages only where the cluster is at version 6 (every node runs
   a release that reads it; the version rises by itself and does not go back) and
   `QUEEN_RAFT_ROWS_WINDOW` is on. Below it a row lives exactly as long as its message, as
   before.
2. **Reclaim.** Each node frees its own files below `txns_start`, one sealed file at a time. A file
   with no live record is unlinked. A partly live file is rewritten with only its live records; the
   copy is made without holding the log's lock (a sealed file is immutable) and swapped in under
   it, so appends do not wait for it. A per-queue log file is rewritten on its first dead message,
   a shared log file once half its message bytes are dead; `QUEEN_QLOG_COMPACT_MIN_DEAD_PCT`
   overrides both.

Reclaim never touches the active file, nor a file holding a record above the last store checkpoint
or, in a cluster, above the raft purge point. One pass examines at most 256 files, spends at most
200 ms and rewrites at most one file. An active file that holds data older than
`QUEEN_QLOG_SEAL_AGE_S` (600) is sealed so that reclaim can reach it, when that is worth a file:
reclaim found a dead message in it (it looks at 32 partitions of an aged active file a pass), or
it holds an eighth of a full file. Age alone seals nothing, so a queue without retention gets a
new file every 64 MiB and no other. A queue's log with nothing left
in it is closed and its directory removed: renamed to `q<id>.dead` first and deleted after, so a
stop in between leaves a retired directory, which the next start sweeps, and never a log with no
file in it, which a start refuses.

## Limits

Disk is freed by whole files: a partition's bytes go when its file dies or is rewritten, and a
watermark that moves frees nothing by itself. RAM holds the whole store, since partitions,
cursors, KV keys and request ids are loaded at boot on every node, so memory grows with them.
Messages are not in that list: a push costs a row in RAM (about 200 bytes, measured on 2.1.0)
for the queue's dedup window, 15 minutes at least, and nothing after it, so memory follows the
push rate times that window and not the retention. Until the cluster is at version 6 the row
stays as long as the message. A sealed log file's `.qidx` is memory-mapped, unless it fits one
page (about 80 records): then it is read into memory and takes no mapping. Linux allows a
process 65,530 mappings by default (`vm.max_map_count`), which is about 4 TB of log per node at
64 MiB per file; `queen_raft_qlog_index_maps` shows the mapped indexes against that limit and
the node warns in its log past 70% of it. Past the limit the kernel refuses a mapping and the
index is held in memory instead (megabytes for a full file, counted in the same series), so
raise the limit, or `QUEEN_RAFT_SEGMENT_BYTES`, before a node gets there.
Traces are the exception: the trace file is page cache, a trace costs its row on disk and no RAM,
and expiry (`QUEEN_RAFT_TRACE_RETENTION_S`, 7 days) deletes at most 512 of them per step.
Replication protects against losing a minority of disks; losing a majority for good can lose
acknowledged writes. A data directory does not move between replicators, and `QUEEN_QLOG_SHARDS`
and `QUEEN_QLOG_LANES` take effect only on a new directory.
