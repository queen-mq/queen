No number on a 2.0 node comes from a refresh loop. There are three sources, and knowing which one
a figure comes from predicts how it behaves.

| Source | Kept by | Answers |
| --- | --- | --- |
| Counters | apply, on every node, in the replicated store | retained bytes and dead letters |
| Read-time figures | the node answering, from its partition and cursor rows at the moment of the read | total, pending, processing, completed, lag |
| Node rows | each node, in its own `dash.db` and `local.db` | throughput per minute, delivery lag, CPU and memory, retention history |

## POST /api/v1/stats/refresh

The route answers `200` with `{"success":true,"refreshed":false,"engine":"raft"}` and changes
nothing. Counters are updated when entries apply and everything else is computed when it is read,
so there is nothing to refresh. The route stays because every SDK's admin API calls it.

## Counters kept by apply

The `counters` keyspace holds one 64-bit integer per `(scope, id, counter)`. The scopes are
partition, queue, tenant and (queue, consumer group); the counters are pushed, pending (per group),
completed, failed, dead letters, retained bytes, consumed, and the instants of the last push and the
last pop. Each effect updates the rows it concerns as it applies (an append also adds to `pending`
once per subscribed group), and the updates of one store transaction are folded into one write per
key at commit. They are replicated state: every node holds the same values after the same entry, and
nothing recomputes them.

Two of them feed the API today. `retainedBytes` (the queue list, the queue detail and the sizes
view) adds the frame length of every retained message and goes down when retention moves
`log_start` past it; it is also the number a storage quota reads. `deadLetter` is the dead-letter
count.

## Queue figures are computed when read

The queue list, the queue detail, the overview and the status views compute their message figures
from the partition rows and the cursors, per request, on the node that answers:

```text
per partition, then summed per queue:
  total      = last_offset - log_start + 1
  pending    = last_offset - max(committed, log_start - 1)     (floored at 0)
  processing = sum over live leases of (batch_end - committed), capped at pending
  completed  = total - pending - deadLetter                    (floored at 0)
```

`committed` is the lowest cursor among the queue's named consumer groups on that partition, else the
queue-mode cursor, else -1 (nothing consumed). `deadLetter` and `retainedBytes` are the counters
above. The queue detail reports `pending` with the leased span included, beside `processing`; the
queue list and the overview report `pending` net of `processing`, the part nobody has leased.

What follows from that:

- **A figure is exact at the instant of the read.** It does not lag an interval; the overview's
  `statsAge` is always 0.
- **`total` counts retained messages.** It shrinks when retention moves `log_start`, and a message
  retention removed is neither pending nor completed.
- **`completed` is a residual**, not a count of acknowledgements.
- **The list, the overview and the status views walk every partition of every queue of the
  tenant.** Freshness is paid for per request, in proportion to the partitions.
- **Some fields are constant.** The overview reports `failed` as 0, and the `median` and `min` of its
  lag as 0. The queue detail reports `failed` as null and `cursor.batchesConsumed` as 0.

## Lag

Lag is computed per `(partition, consumer group)` cursor, at read time:

- **offset lag** is that cursor's `pending`, as above;
- **time lag** is the age of the oldest message the cursor has not consumed: now minus the creation
  time of the record holding `committed + 1`, or of the first record after it when retention has
  already removed that offset, rounded to the nearest second. It comes from the queue log's in-memory
  index, without reading a payload, and is absent for a cursor that is caught up.

The overview's `lag` block takes, per queue, the largest time lag and the largest offset lag over
its cursors; `max` is the largest over the queues and `avg` the mean over the queues that lag.
`GET /api/v1/consumer-groups/lagging` lists the cursors whose time lag exceeds `minLagSeconds`
(default 3600), largest first.

There is a second lag, measured differently. Delivery lag is the age of a message at the moment a
pop hands it out; it is measured on the pop path and lands in the node rows below. Time lag is the
age of a backlog and exists with no consumer running; delivery lag exists only while messages are
being delivered.

## Node rows in dash.db

One collector thread per process wakes every `METRICS_FLUSH_MS` (default 60000; a value below 1000
is ignored) and records what this node did since its previous flush:

| Row | One per | Carries |
| --- | --- | --- |
| worker | flush | push, pop and ack requests and messages, transactions, messages moved to the dead-letter queue, local store commit failures, event-loop lag, delivery lag |
| system | flush | CPU, resident memory, and a raft family: entries in flight, apply lag in entries, log bytes and files, store map use |
| queue | queue and minute with any activity | pops, empty pops, pushes, transactions, acks, delivery lag, the minute's average of parked long-polls, conflated positions |
| parked | queue and minute with a parked long-poll | this node's parked long-polls |

The rows are journaled to `dash.db` in the data directory, one per process, shared by every raft
group of the node. A torn tail is cut on reopen, and losing the unflushed tail loses a graph point,
never queue state. Worker and system rows are kept `QUEEN_DASH_NODE_RETENTION_H` hours (default
168), queue and parked rows `QUEEN_DASH_QUEUE_RETENTION_H` hours (default 24), and queue and parked
rows are also capped at `QUEEN_DASH_MAX_QUEUE_ROWS` each (default 500000).

A dashboard or analytics read gathers the rows of every node over the raft port and merges the
queue rows of one minute: counters add, delivery lag is averaged weighted by its count, the maximum
is the largest, parked long-polls add. A node that does not answer is missing from the result, and
`GET /api/v1/status` names it in `nodesMissing`. A node is named by `QUEEN_SERVER_ID`, else
`HOSTNAME`, else `node-` and its raft node id.

## Retention and partition churn in local.db

Apply records two more histories in the node's `local.db`: every watermark move (the last 4096 are
kept) and the partitions created and deleted per queue and minute (kept 24 hours). Because apply
records them, every node holds the same rows, and a read serves them from the answering node alone.
A retention row records how far `log_start` and `txns_start` moved, not which rule moved them, so
the Retention chart's completed-retention and eviction series stay at 0.

## Prometheus

`/metrics/prometheus` serves this process's own counters plus the state machine's families. The
families are listed in the [Prometheus reference](/reference/prometheus/).
