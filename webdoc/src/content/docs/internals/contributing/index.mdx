Queen is one repository with one Rust binary in it. The binary is the broker, and it links the
multi-tenant proxy and the Kafka facade as libraries; a Vue dashboard is compiled into it; six client
SDKs, a Dockerised test matrix and this site sit beside it. The broker keeps its state in a data
directory, so there is no database to install to build it, test it or run it. What makes the build
order matter is that the dashboard and the version string are baked into the binary at compile
time.

| Path | What it is |
| --- | --- |
| `server/` | The broker. Crate `queen-engine`, import path `queen`, binary `queen`: axum 0.7 and tokio over the state machine in `src/rsm/` (LMDB through `heed`, Raft through `openraft`). Default features `server` (the HTTP broker, the dashboard, the proxy) and `kafka` (the Kafka facade). |
| `server/webapp/dist/` | The built dashboard the binary embeds. Ignored by git except `index.html` and two favicons, so a clean clone compiles but serves a dashboard without its assets until `app/` is built. |
| `server/server.json` | Name and version. The single source of the version string. |
| `proxy/` | The multi-tenant gateway: a library (`queen_proxy`) the broker links and runs in-process when `QUEEN_PROXY_EMBEDDED=true`. |
| `proxy/console/` | The operator console SPA. Unlike the dashboard, its `dist/` **is** committed; the proxy library embeds it. |
| `protocols/queen-kafka/` | The Kafka wire facade, linked by the `kafka` feature and run in-process when `QUEEN_KAFKA_EMBEDDED=true`. |
| `app/` | Vue 3 + Vite dashboard. Builds into `server/webapp/dist`. |
| `clients/` | Six client SDKs: JavaScript (npm `queen-mq`), Python (PyPI `queen-mq`), Go, Rust (crates.io `queen-mq`), PHP/Laravel (Packagist `queen-mq/php-client`) and a header-only C++ client. Also `queenctl`, the operator CLI. |
| `crates/queen-protocol/` | The canonical wire types, shared by the Rust client and the broker's embedded library API. The broker's HTTP parsers and hand-rendered responses do not use them. |
| `test/` | The Docker Compose test matrix. One entry point, `run.sh`. |
| `webdoc/` | This site. |
| `benchmark-queen/` | Archived benchmark sessions, their loaders and their raw output. |
| `Dockerfile` | The published image. |
| `go.work` | Go workspace joining `client-cli` and `client-go`. |

## The build order

The dashboard is embedded by `server/src/handlers/static_files.rs`:

```rust
#[derive(RustEmbed)]
#[folder = "webapp/dist"]
struct Assets;
```

`app/vite.config.js` sets `outDir` to `../server/webapp/dist`, so building the dashboard is what fills
that folder. The proxy embeds the same directory through `proxy/src/webapp.rs`
(`#[folder = "../server/webapp/dist"]`) rather than keeping a second copy, so one dashboard build
serves both. The binary serves the dashboard from those embedded bytes; there is no runtime static
directory.

<Steps>

1. Build the dashboard once. From `app/`:

   ```bash
   npm ci
   ```

   ```bash
   npm run build
   ```

2. Build the broker. From `server/`:

   ```bash
   cargo build --release
   ```

   The binary lands at `server/target/release/queen`. The proxy and the Kafka facade are compiled
   into it: there is no second binary to build.

</Steps>

`server/build.rs` reads `server/server.json` and exports its `version` as `QUEEN_VERSION`, which is
what `/health` and `queenctl ping` report, so a version bump is a rebuild.

A `debug` build reads the embedded assets from disk, so a dashboard change appears after
`npm run build` alone. A `--release` build does not: it needs the Rust rebuild. The console works
the same way: its bundle is committed under `proxy/console/dist`, and `npm run build` in
`proxy/console/` rewrites it.

## Running a broker

<Steps>

1. Run it with a data directory. From `server/`:

   ```bash
   QUEEN_RAFT_DIR=./queen-data cargo run --release
   ```

   The node creates the directory, opens its store and queue logs as a single node (the local
   replicator: no network, no consensus), and binds `PORT` (default 6632). Delete the directory to
   start from empty.

2. Confirm.

   ```bash
   curl -s http://localhost:6632/health
   ```

   It answers `200` with `"status":"healthy"` and `"engine":"raft"` once the node is ready, and `503`
   with `"status":"settling"` until then.

</Steps>

A three-node cluster is on [High availability](/deploy/ha).

For work on authentication, tenancy, quotas or 429s, run the same binary with the embedded proxy in
front: `QUEEN_PROXY_EMBEDDED=true` turns it on, and `QUEEN_PROXY_PORT=6711` gives it a port of its
own while `6632` keeps serving the broker router directly. The proxy keeps its tenants, clusters,
users and keys in the broker's own KV and is configured by the `QUEEN_PROXY_*` variables
([The proxy](/deploy/proxy/)). It starts in shadow mode, computing and logging its limit decisions
without applying them; `QUEEN_PROXY_ENFORCE=true` makes them real, which is what the 429 checks need.

The dashboard's own dev server (`npm run dev` in `app/`) listens on 4000 and proxies `/api`, `/auth`,
`/health` and `/metrics` to `http://localhost:6711`: the proxy, not the broker, because auth and
tenancy are what the app has to behave correctly against. `QUEEN_DEV_UPSTREAM=http://localhost:6632`
points it at the broker directly.

## Container builds

The root `Dockerfile` builds the published image from a clean clone: it builds the dashboard and
the console itself, then the broker and `queenctl`. Its build context is the repository root,
because the broker takes the proxy, the Kafka facade and `queen-protocol` by relative path.
`test/run.sh` builds the same image as `queen:test`.

## Go modules

`clients/client-go` and `clients/client-cli` are separate Go modules, and `go.work` at the
repository root joins them so a change to the client is immediately visible to the CLI without
publishing. End users are unaffected: `go install` ignores `go.work` and resolves through the
public proxy using the versions pinned in `client-cli/go.mod`. The CLI's own test suite needs
that workspace, which is why the `cli` runner image is built with it.

## Conventions

- **English in committed material.** Source comments, documentation and commit messages.
  Several benchmark session notes under `benchmark-queen/` are in Italian; they are working
  records, not published documentation.
- **One logical change per pull request**, with the component in the title (`server:`,
  `queen_proxy:`, `client-py:`).
- **Run the matrix for what you touched.** See [Testing](/internals/contributing/testing).
- **Regenerate the derived documentation** when you change the router, the configuration, the
  metrics, the proxy's route classifier or a published snippet. See
  [The documentation site](/internals/contributing/docs).
- **Do not add a dependency that needs cmake or a system OpenSSL.** The broker and the proxy are
  deliberately `rustls` + `ring` only; `server/Cargo.toml` records the reasoning at each
  dependency. This is why there is no `reqwest` and why JWKS fetching is a small in-tree HTTPS
  client (`server/src/httpget.rs`).
