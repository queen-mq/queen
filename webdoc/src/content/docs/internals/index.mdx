A Queen node is one process. The raft leader turns each batch of client commands into one log
entry of effects, a majority of nodes makes it durable, and every node applies it to its own copy
of the state. Read this page to know which part of the process does what before you read
[life of a step](/internals/life-of-a-step/) or [storage](/internals/storage/).

## The parts of a node

| Part | Runs on | What it does | Code |
|---|---|---|---|
| HTTP edge | every node | Mints a 16-byte request id and a deadline per command, parses the body, mints message ids, hashes each `transactionId` (xxh3-128), packs one frame per message. | `handlers/raft.rs`, `rsm/facade/real.rs` |
| Intake | leader | Sends pops, acks, nacks and renews to the consumption engine, has the engine validate a transaction's acks, and sends everything else to the planner's channel. | `rsm/facade/intake.rs` |
| Planner | leader | Plans each command against committed state plus the entries still in flight, builds one entry per cycle, proposes it. | `rsm/batcher.rs`, `rsm/planner/` |
| Raft log | every node | Orders and replicates entries; in a cluster, openraft decides who leads and what is committed. The log is the queue log files. | `rsm/replicator/` |
| Apply | every node | Executes committed entries in index order. The only writer of the store. | `rsm/apply.rs` |
| Store | every node | Queues, partitions, cursors, dedup rows, KV, timers, request ids, counters. In RAM, checkpointed to LMDB. | `rsm/store/` |
| Consumption engine | leader | Serves claims, leases and acks from memory and logs the changed cursor rows as checkpoints. | `rsm/consume/` |

The same process can also run the Kafka wire facade (`QUEEN_KAFKA_EMBEDDED=true`) and the
multi-tenant proxy (`QUEEN_PROXY_EMBEDDED=true`). Both call the broker's own HTTP router in
process, so a Kafka produce is a push like any other.

### Planner and lanes

A planning cycle drains the command channel up to `QUEEN_RAFT_BATCH_MAX_CMDS` (4096) commands or
`QUEEN_RAFT_BATCH_MAX_BYTES` (4 MiB), looks up each request id (a retry under the same id gets the
recorded outcome), plans, and builds one entry. Up to `QUEEN_RAFT_PIPELINE` (8) entries are in
flight at once. The planner stamps the time and mints every id, so an entry carries effects
(absolute values), never commands.

A **lane** is a planning thread that owns the partitions whose id modulo `QUEEN_LANES` (default 8)
equals its number. Lanes plan the commands that touch only their own existing partitions (pushes,
single-lane transactions, consumption checkpoints) in parallel. A control step then plans the
rest on one thread: queue and group changes, new partitions, KV, timers, commands that span lanes.
The result is still one entry, and it applies exactly as if one thread had planned it.

### Raft log and apply

There is one log per raft group. A single node runs the local replicator
(`QUEEN_RAFT_REPLICATOR=local`, the default): the same files, no network. A cluster runs openraft
(`QUEEN_RAFT_REPLICATOR=openraft` with `QUEEN_RAFT_PEERS`). The leader streams entries to each
follower over one long-lived connection with several appends in flight, and an entry commits once
a majority has written and fsynced it.

Apply is a pure function of committed state and the entry: no clock, no environment, no
randomness, no hash-map order (`server/clippy.toml` makes those calls a compile error in
`rsm/apply.rs`, `rsm/state/` and `rsm/store/`). Two nodes that apply the same entries hold the same
replicated state. An effect kind a node cannot decode stops that node; it is never skipped.
Partition-keyed effects run on `QUEEN_RAFT_APPLY_SHARDS` (4) threads, with the same result as one
thread.

### Consumption engine

Pops, acks and leases never go through the planner. The engine on the leader holds each consumer
group's cursors and leases in memory, loaded lazily from the committed cursor rows. It serves only
while its node leads and has heard from a quorum within `QUEEN_CONSUME_LEADER_LEASE_MS` (400 ms).
Every `QUEEN_CONSUME_CHECKPOINT_MS` (5 ms) it logs the rows that changed, and it releases an answer
only once the checkpoint holding its change has committed.

### Followers

Every node applies every committed entry, so a follower holds a full copy of its raft groups.
With `QUEEN_RAFT_CLIENT_OFFLOAD` (on by default in a cluster) a follower serves its own clients: it
prepares the command, forwards only the prepared command to the leader, and renders the answer
from its own state once it has applied the entry. A KV or position read on a follower first asks
the leader for its read index and waits until it has applied that far.

## One tenant, one leader

**A tenant lives in exactly one raft group, and one leader orders every write of that group.**
Placement is `QUEEN_TENANT_GROUPS=tenant=group,...`, else a hash of the tenant name over
`QUEEN_RAFT_GROUPS` (default 1, at most 64):

```sh
QUEEN_RAFT_GROUPS=3
QUEEN_TENANT_GROUPS=acme=2
```

Every command, a transaction included, carries one tenant, so it touches one group. One leader
plans it into one entry. That is the whole transaction protocol: no coordinator, no two-phase
commit, no transaction markers in the partitions, no isolation level for readers to choose. An
entry is applied whole or not at all.

The price is that one tenant's writes do not scale out: they pass through one planner and one log.
You scale out with more raft groups (with as many groups as nodes, group `g` prefers node
`g mod n` as leader, so every node leads one) and with more clusters. See
[tenants](/operate/tenants/).

## Limits

- **Adding nodes adds copies, not write throughput for one tenant.**
- **A tenant's group is fixed while it has data.** There is no migration yet; pin a large tenant
  with `QUEEN_TENANT_GROUPS` before it writes.
- **`QUEEN_RAFT_GROUPS` above 1 needs `QUEEN_RAFT_CLIENT_OFFLOAD` on**, and every node of a cluster
  must use the same value.
- **The store is loaded into RAM in full at boot.** Each node's memory grows with partitions,
  cursors and KV keys of the groups it holds.
- **A new leader serves no pops or acks** for one checkpoint interval plus
  `QUEEN_RAFT_MAX_CLOCK_SKEW_MS` (500 ms) after it takes over.
