Queen 2.0 is one Rust binary (crate `queen`, binary `queen`) and one data directory. There is no
external database. Every message, offset, cursor, lease and queue configuration a node knows is in
the directory named by `QUEEN_RAFT_DIR` (default `/var/lib/queen/raft`), and the code that owns it
is the replicated state machine in `server/src/rsm/`.

That state machine has one rule, and every page in this section leans on it. One leader turns
client commands into log entries of **effects**: deterministic state changes such as "append these
frames to partition 7 at offset 120" or "write this cursor row". Every node applies the committed
entries, in index order, to its own full copy of the state. Committed state is changed only by
apply, and apply reads no clock, no environment and no randomness: every time and every id it needs
was stamped by the planner and travels inside the effect. Two nodes that apply the same entries
therefore hold the same replicated state.

The one deliberate exception is the [ephemeral queue class](/use/ephemeral/): its messages live in
process memory by contract and never enter the log. Only its configuration is replicated state.

Read the [concept pages](/use) first if you want to know what Queen promises. This section explains
how a node keeps those promises.

## One request, top to bottom

<pre class="mermaid">{`
flowchart TB
  H["HTTP router<br/>PORT, default 6632"] --> R["receiver<br/>parse, validate, pack frames"]
  R -->|"typed command"| B["batcher and planner, on the leader<br/>one entry per cycle"]
  B -->|"propose"| L["replicator<br/>local or openraft"]
  L -->|"write, one fsync per touched log"| Q[("queue logs")]
  L -->|"committed entries, in order"| A["apply thread<br/>the only writer of committed state"]
  A --> S[("ordered store, LMDB")]
  A -->|"applied at index"| B
  B -->|"outcome"| R
  R --> H
`}</pre>

1. **The router** (`build_raft_router` in `server/src/handlers/raft.rs`). The message path (push,
   the three pops, ack, transaction, lease renewal), KV, timers, the ephemeral verbs and the raft
   membership routes have typed handlers. The other `/api/` and `/streams/` routes go through one
   generic adapter over the same state machine (`server/src/rsm/facade/real/phase2.rs`), and
   anything else is the dashboard SPA compiled into the binary. The router serves `PORT`, unless the embedded [proxy](/deploy/proxy) takes that port
   (`QUEEN_PROXY_EMBEDDED=true` without `QUEEN_PROXY_PORT`). JWT validation (`JWT_ENABLED`, off by
   default) and tenant resolution (`QUEEN_TENANCY_HEADER`, off by default) run as middleware before
   any handler.
2. **The receiver** (`server/src/rsm/facade/real.rs`). It does the work that needs no shared state:
   parse the body, bound the name lengths, mint message ids (UUIDv7), hash every `transactionId`
   with `xxh3_128`, encrypt payloads for queues configured for it, pack one frame per message, and
   build a typed command. It never plans and never writes committed state.
3. **Admission.** A push or a transaction takes a byte budget sized by its `Content-Length` before
   its body is read, and a node whose disk is full refuses writes that grow storage. See
   [Flow control](/internals/flow-control).
4. **The batcher and the planner** (`server/src/rsm/batcher.rs`, `server/src/rsm/planner/`), on the
   leader only. Each cycle drains the command channel, plans every command against committed state
   plus an overlay of the entries still in flight, and builds one entry out of all of them. Planning
   runs on one dedicated thread, `queen-planner`. Up to 4 entries are in flight at once
   (`QUEEN_RAFT_PIPELINE`).
5. **The replicator** (`server/src/rsm/replicator/`). `local`, the default, is a single node with no
   consensus protocol. `openraft` runs the Raft protocol and is required for a cluster. Both write
   an entry into the queue logs, with one fsync per log it touches, before anything applies it;
   openraft also needs a majority of voters to hold it before it counts as committed. A data
   directory belongs to the replicator that created it: each one refuses a directory the other
   wrote.
6. **Apply** (`server/src/rsm/apply.rs`). One thread per node executes committed entries in index
   order against the ordered store. When the entry that carries a command has applied on this node,
   the batcher answers the receiver, which renders the HTTP response from the recorded outcome. A
   pop reads its payload bytes from this node's own queue logs at that point.

An answered write is therefore fsynced in the queue logs and applied on the node that answered, and
in a cluster it is also on a majority of voters. [Life of a push](/internals/life-of-a-push) and
[Life of a pop](/internals/life-of-a-pop) walk the two main paths step by step.

## Any node serves clients

In a cluster (`QUEEN_RAFT_REPLICATOR=openraft` with `QUEEN_RAFT_PEERS`; see
[High availability](/deploy/ha/)) only the leader plans. A follower still serves its own clients
(`QUEEN_RAFT_CLIENT_OFFLOAD`, on by default). It parses and prepares the command exactly as the
leader would, and sends only the prepared command to the leader over the Raft RPC listener, carrying
the cluster token. The leader plans it with everything else and answers with the log index its entry
landed at. The follower waits until it has applied that index itself, then renders the answer from
its own state. A pop therefore reads its payloads from the follower's own queue logs, and a client
reads its own writes on whichever node it talks to. A prepared command keeps its request id across
retries, so a lost answer followed by a retry never plans the command twice.

Reads that must observe every acknowledged write (a KV read, a queue's depth or configuration, the
empty answer of a pop that does not wait) take a **read barrier** first: the node obtains the
leader's read index (the leader confirms it still leads) and waits until it has applied that far.
On a single node the barrier costs nothing.

With `QUEEN_RAFT_CLIENT_OFFLOAD` off, a follower instead relays every `/api/` and `/streams/`
request to the leader over HTTP, except the `/api/v1/raft/` routes, which describe the node that
was asked. With no leader known the answer is `503` with `Retry-After: 1`, and the client retries.

## What lives where

| What | Where | Replicated | How it survives a restart |
| --- | --- | --- | --- |
| Message payloads (packed frames) | queue logs, `qlog/` | yes, as entries; file boundaries and byte positions are node-local | fsynced before apply; recovery replays the entries above the store's last durable point |
| Queues, groups, partitions, cursors, leases, dead letters, dedup hash lists, KV, timers, counters, recorded outcomes | ordered store, `store/` (LMDB through the `heed` crate) | yes | every keyspace is held in RAM and LMDB holds its checkpoint, written at each durable point |
| Ready rings, visibility and lease deadlines | RAM | derived | rebuilt from the `pending` and `leases_by_worker` keyspaces at open and when a node becomes leader |
| The dedup front (bloom filters) | planner RAM | no | rebuilt on first touch; it can skip a read, never change a verdict |
| Parked long-polls | RAM, one gate per (tenant, queue, group) | no | a parked request ends with the process |
| Vote, purge point, commit point | `raft/` (openraft only) | no | written by the replicator |
| Dashboard rows and node-local metrics | `dash.db`, `local.db` | no | losing the unflushed tail loses a graph point, never queue state |

[The storage model](/internals/storage-model) has the files, the keyspaces and the invariants.

## Background work

Periodic work is planned the way client commands are: on its tick, the leader's batcher plans a
step and proposes the result as an ordinary entry, and every node applies it. Only work on a node's
own files runs locally.

| Step | Cadence | Runs on | What it does |
| --- | --- | --- | --- |
| Timer fire | `QUEEN_RAFT_TIMER_TICK_MS`, 50 ms | the leader, as entries | fires due timers through the push planner ([Timer internals](/internals/timers)) |
| KV expiry | `QUEEN_RAFT_KV_SWEEP_MS`, 1000 ms | the leader, as entries | deletes expired keys; a read already treats an expired key as absent ([KV internals](/internals/kv)) |
| Maintenance | `RETENTION_INTERVAL`, 5000 ms | the leader, as entries | moves retention watermarks, deletes empty partitions idle past `PARTITION_CLEANUP_DAYS`, expires traces, resumes interrupted deletes ([Retention internals](/internals/retention)) |
| Request-id expiry | 10 s | the leader, as entries | retires recorded outcomes older than `QUEEN_RAFT_REQUEST_ID_WINDOW_S` (60 s) |
| Queue-log reclaim | on the maintenance tick | every node, locally | unlinks sealed queue-log files that hold only dead records, and rewrites partly dead ones |
| Durable point | `QUEEN_RAFT_DURABLE_EVERY_MS` (1000 ms) or `QUEEN_RAFT_DURABLE_EVERY_BYTES` (256 MiB) | every node, locally | checkpoints the store; crash recovery replays from here |

Counters (messages pushed, bytes retained, and the rest the dashboard reads) are updated by apply as
each entry applies, so `POST /api/v1/stats/refresh` has nothing to recompute and answers
`{"success":true,"refreshed":false,"engine":"raft"}`. See [Counters, rates and lag](/internals/stats).
