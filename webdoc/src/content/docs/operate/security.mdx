Out of the box a node authenticates nobody: its HTTP port is plain HTTP and every route answers
any caller. Turn on one of two front doors, broker JWT for services that hold tokens or the
built-in proxy for API keys and humans, keep the raft port on a private network, and encrypt the
queues whose payloads must not sit on disk in clear.

## What listens where

| Port | Set by | Serves | Protected by |
|---|---|---|---|
| `6632` | `PORT`, `QUEEN_BIND_ADDR` (`0.0.0.0`) | The HTTP API, the dashboard, `/health`, metrics | Broker JWT, off by default. Plain HTTP, no CORS |
| `7400` by convention | the raft address in `QUEEN_RAFT_PEERS`, `QUEEN_RAFT_LISTEN` | Votes, log entries, snapshots, the commands followers send the leader | `QUEEN_RAFT_TOKEN`. Plain HTTP |
| raft port + N | `QUEEN_RAFT_GROUPS` | Raft group N | The same token |
| `QUEEN_PROXY_PORT` | e.g. `6711` | The proxy: keys, sessions, console, `/api/cp/*` | API keys and sessions; TLS with `QUEEN_TLS_CERT` / `QUEEN_TLS_KEY` |
| `9092` | `QUEEN_KAFKA_ADDR` | The Kafka facade (`QUEEN_KAFKA_EMBEDDED=true`) | `QUEEN_KAFKA_SASL=plain`; TLS with `QUEEN_KAFKA_TLS_CERT` / `QUEEN_KAFKA_TLS_KEY` |

`QUEEN_BIND_ADDR=127.0.0.1` keeps port 6632 on the host, which is wrong in Kubernetes, where
probes and Services arrive on the pod IP. Port 6632 never faces the internet without one of the
front doors below.

## Broker JWT

```bash
JWT_ENABLED=true
JWT_ALGORITHM=RS256                 # HS256, HS384, HS512, RS256, RS384, RS512, EdDSA, auto
JWT_JWKS_URL=https://idp.example.com/.well-known/jwks.json   # or JWT_PUBLIC_KEY (PEM), or JWT_SECRET for HS*
JWT_ISSUER=https://idp.example.com/
JWT_AUDIENCE=queen
```

```bash
curl -s http://queen:6632/api/v1/resources/queues -H "authorization: Bearer $TOKEN"
```

A token's roles come from the `role` claim (a string) or the `roles` claim (an array):
`JWT_ROLES_CLAIM`, `JWT_ROLES_ARRAY_CLAIM`. JWKS keys are fetched at boot, cached by `kid` and
refreshed every hour (`JWT_JWKS_REFRESH_INTERVAL`, seconds) and on an unknown `kid`; `exp`, `nbf`
and `iat` are checked with 30 s of skew (`JWT_CLOCK_SKEW`). Auth on with no usable key material
stops the boot. The `config: auth` boot line states the mode, secrets masked.

Each route has an access level, and the token's roles decide which levels it passes. Write-only is
not below read-write: it is a produce-only role that cannot read.

| Level | Routes | Passes with role |
|---|---|---|
| public | `/health`, `/metrics`, `/metrics/prometheus`, the dashboard shell, `/auth/me`, `/auth/login` | none needed |
| read-only | `GET` listings, status, messages, consumer groups, DLQ, traces, KV and timer reads | `read-only`, `read-write`, `admin` |
| write-only | `POST /api/v1/push`, `POST /api/v1/timers`, the ephemeral push | `write-only`, `read-write`, `admin` |
| read-write | everything else: pop, ack, transaction, KV writes, configure | `read-write`, `admin` |
| admin | `/api/v1/system/*` (raft membership, kill switches), queue, group and DLQ deletes | `admin` |

The role names are settings too (`JWT_ROLE_ADMIN`, `JWT_ROLE_READ_WRITE`, `JWT_ROLE_READ_ONLY`,
`JWT_ROLE_WRITE_ONLY`). Each route's level is in the [HTTP reference](/reference/http/).

## API keys and humans

The proxy built into the binary (`QUEEN_PROXY_EMBEDDED=true`) is the second front door: API keys
bound to one tenant, human sessions with per-cluster roles, plan quotas, and TLS on its own
listener. Its port is the one to expose. See [tenants, API keys and quotas](/operate/tenants/).

The broker also has a raw tenant mode, `QUEEN_TENANCY_HEADER=1`, which scopes every request by an
`x-queen-tenant` header it never validates. **It refuses to boot unless `QUEEN_KV_TRUSTED_PROXY=1`
states that something in front sets that header and strips the client's.** The built-in proxy needs
neither: it hands requests to the broker in-process.

## TLS

The broker port does not terminate TLS. Two listeners do:

- **The proxy's**, with `QUEEN_TLS_CERT` and `QUEEN_TLS_KEY` (PEM paths, HTTP/1.1). Both or neither:
  one alone fails the boot.
- **The Kafka facade's**, with `QUEEN_KAFKA_TLS_CERT` and `QUEEN_KAFKA_TLS_KEY`.

Otherwise terminate TLS at your ingress or load balancer and keep the hop to the node on a private
network.

## The raft token

Every Raft RPC carries `QUEEN_RAFT_TOKEN` in `x-queen-raft-token`, and the receiver checks it from
the headers, in constant time, before it reads the body: a wrong token is a `401` and costs nothing.
Nodes also present it to each other on the HTTP port for broker-to-broker calls, and the proxy
strips it from client requests.

```bash
QUEEN_RAFT_TOKEN="$(openssl rand -hex 32)"    # the same value on every node
```

Unset, anything that reaches the raft port can vote, append entries and submit commands. Set, it
still travels in clear, so bind the raft port to a private network and allow it only from the
other nodes. Rotating it is a rolling restart: nodes with the new token form the quorum once a
majority has restarted.

## Payload encryption at rest

```bash
QUEEN_ENCRYPTION_KEY="$(openssl rand -hex 32)"    # 64 hex characters, the same on every node
```

```bash
curl -s -X POST http://localhost:6632/api/v1/configure -H 'content-type: application/json' \
  -d '{"queue":"payments","options":{"encryptionEnabled":true}}'
```

Payloads of a queue with `encryptionEnabled` are stored AES-256-GCM encrypted, pushes from
transactions and timers into it included, and decrypted when read. Queue, partition and KV key
names, and KV values, are stored in clear. Check the boot line
`encryption service initialized (AES-256-GCM)`: **with no key, or a key that is not 64 hex
characters, the node logs a warning and stores flagged queues in plaintext.**

## The data directory

`QUEEN_RAFT_DIR` holds everything a node knows: payloads (in clear unless encrypted), KV, timers,
consumer offsets and, with the proxy, its users and API-key hashes. Treat the volume and every
snapshot of it like a credential.

## Limits

- **Off by default.** With `JWT_ENABLED=false` and no proxy, anyone who reaches port 6632 can read,
  write, delete queues and change the raft membership.
- **`/metrics/prometheus` is public on port 6632** and names every tenant's queues; on the proxy's
  port it needs `x-queen-cp-token`.
- **A token without `exp` is accepted.** Issue tokens that expire.
- **Changing `QUEEN_ENCRYPTION_KEY` makes encrypted payloads unreadable**, and consumers then
  receive the ciphertext envelope as data with no error. Keep the key; restoring it restores the
  plaintext.
- **No TLS between nodes.** The raft port and the HTTP port between nodes are plaintext.

## Reporting a vulnerability

Report it privately through GitHub's private vulnerability reporting on the
`queen-mq/queen` repository, as `SECURITY.md` describes, not in a public issue.
