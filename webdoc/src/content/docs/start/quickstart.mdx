Docker, curl, jq and five minutes. You run one node, push a message, consume it, and then commit
a whole step (the ack, the next event and a state change) as one transaction.

<Steps>

1. **Run a node.** One container, no database. The volume keeps the node's data directory
   (`QUEEN_RAFT_DIR`, default `/var/lib/queen/raft`) when the container is replaced.

   ```bash
   docker run -d --name queen -p 6632:6632 -v queen-data:/var/lib/queen/raft ghcr.io/queen-mq/queen:latest
   curl -s http://localhost:6632/health
   ```

   The answer carries `"status":"healthy"` and a `raft` object with `"role":"leader"`: a single
   node leads its own raft group. No answer means the node is still starting; `docker logs queen`
   says why if it stays that way. The dashboard is on the same port, at `http://localhost:6632`.

2. **Push a message.** Nothing is created first: the queue `orders` and the partition
   `customer-123` come into existence with this push. `transactionId` is your idempotency key.

   ```bash
   Q=http://localhost:6632
   curl -s -X POST $Q/api/v1/push -H 'content-type: application/json' -d '{
     "items": [{ "queue": "orders", "partition": "customer-123",
                 "transactionId": "order-8891-created",
                 "payload": { "orderId": 8891, "total": 42 } }]
   }'
   ```

   The answer has one entry per item, with `"status":"queued"` and the message's `offset` in its
   partition. Run the same command again: it answers `"status":"duplicate"` with the first
   message's id, and writes nothing.

3. **Pop it and ack it.** A pop takes a lease: the message is yours until you ack it or the lease
   expires. With no `consumerGroup`, the pop reads through the queue's own cursor, which starts at
   the beginning.

   ```bash
   POP=$(curl -s "$Q/api/v1/pop/queue/orders?batch=1&wait=true&timeout=5000")
   echo "$POP" | jq '.messages[0] | {transactionId, partition, data}'

   curl -s -X POST $Q/api/v1/ack -H 'content-type: application/json' -d "$(echo "$POP" | jq '{
     transactionId: .messages[0].transactionId,
     partitionId:   .messages[0].partitionId,
     leaseId:       .leaseId,
     status:        "completed" }')"
   ```

   The ack answers `[{ "success": true, ... }]`. A refused ack also answers HTTP 200, with
   `"success": false` on the item, so read the flag. An empty pop is a `204` with no body.

4. **Commit one step.** Push a second order, pop it, and handle it the way a service would: ack
   the order, push a receipt and record the order's state, in one `POST /api/v1/transaction`.
   `kv` sits at the top level of the body, beside `operations`, and every KV write declares its
   lifetime (`ttlSeconds`, or `forever: true`).

   ```bash
   curl -s -X POST $Q/api/v1/push -H 'content-type: application/json' -d '{
     "items": [{ "queue": "orders", "partition": "customer-123",
                 "transactionId": "order-8892-created",
                 "payload": { "orderId": 8892, "total": 42 } }]
   }'
   POP=$(curl -s "$Q/api/v1/pop/queue/orders?batch=1&wait=true&timeout=5000")

   curl -s -X POST $Q/api/v1/transaction -H 'content-type: application/json' -d "$(echo "$POP" | jq '{
     operations: [
       { type: "ack", transactionId: .messages[0].transactionId,
         partitionId: .messages[0].partitionId, leaseId: .leaseId, status: "completed" },
       { type: "push", items: [{ queue: "receipts", partition: "customer-123",
         transactionId: "receipt-8892", payload: { orderId: 8892 } }] }
     ],
     kv: [{ op: "put", ns: "orders", key: "order-8892",
            value: { status: "paid" }, ttlSeconds: 2592000 }]
   }')" | jq '.success'
   ```

   `true` means the ack, the receipt and the state were written as one entry. Check each:

   ```bash
   curl -s $Q/api/v1/kv/orders/order-8892 | jq '.value'                      # {"status":"paid"}
   curl -s "$Q/api/v1/pop/queue/receipts?batch=1" | jq '.messages[0].data'   # {"orderId":8892}
   curl -s -o /dev/null -w '%{http_code}\n' "$Q/api/v1/pop/queue/orders"     # 204: nothing left
   ```

   **If any part is refused, nothing is written.** Commit the next order with the receipt's
   `transactionId` still `receipt-8892` and the answer is `"success": false` with
   `"reason": "duplicate"`: the ack and the KV write roll back with the push. An expired lease
   does the same, with `"reason": "rejected_ack"`.

5. **The same step in JavaScript.** Install the SDK with `npm install queen-mq` (Node.js 24 or
   later).

   ```js
   import { Queen } from 'queen-mq'

   const queen = new Queen({ url: 'http://localhost:6632' })

   await queen.queue('orders').partition('customer-123')
     .push([{ transactionId: 'order-8893-created', data: { orderId: 8893, total: 42 } }])

   const [message] = await queen.queue('orders').batch(1).wait(true).pop()

   await queen.transaction()
     .ack(message)
     .queue('receipts').partition('customer-123')
       .push([{ transactionId: 'receipt-8893', data: { orderId: 8893 } }])
     .kv.put('orders', 'order-8893', { status: 'paid' }, { ttl: '30d' })
     .commit()

   await queen.close()
   ```

   `commit()` throws when the broker refuses the transaction, so the line after it runs only if
   all three were written. `ack(message)` sends the lease the pop returned. This pop named no
   consumer group; when yours does, pass it to the ack as well:
   `.ack(message, 'completed', { consumerGroup: 'billing' })`.

</Steps>

<Aside type="caution">
A node refuses writes that grow storage once its disk is 85% full (`QUEEN_RAFT_DISK_HIGH_PCT`):
the push answers `507` with `"code":"storage_full"`. Under Docker Desktop, that is the disk of
Docker's virtual machine.
</Aside>
