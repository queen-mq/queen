Queen speaks JSON over HTTP, on port `6632`, so every client is a thin layer over the same
routes, and curl is a complete client. What an SDK adds is the part that is tedious to write by
hand: consume loops that ack and nack for you, lease renewal, push buffering, retries with
failover across the nodes of a cluster, and builders for transactions, KV and timers. Pick the one
for your language. The tutorials in `examples/tutorials/` use these same packages, one program
per language, and check themselves against a live broker.

## Install and connect

<Tabs>
<TabItem label="JavaScript">

```bash
npm install queen-mq
```

```js
import { Queen } from 'queen-mq'

const queen = new Queen({ url: 'http://localhost:6632' })
// ...
await queen.close()
```

Node.js 24 or later. With `urls: [...]` instead of `url`, the client sends each consumer's pops to
the node that a consistent hash of its queue, partition and group picks (the default `affinity`
strategy; `round-robin` and `session` are the others), and fails over to another node on a network
error or a 5xx.
[README](https://github.com/queen-mq/queen/tree/master/clients/client-js)

</TabItem>
<TabItem label="Python">

```bash
pip install queen-mq
```

```python
from queen import Queen

async def main():
    queen = Queen(url="http://localhost:6632")
    # ... every call is awaited
    await queen.close()
```

Python 3.9 or later. The client is asyncio from end to end, and `url` is a keyword argument.
[README](https://github.com/queen-mq/queen/tree/master/clients/client-py)

</TabItem>
<TabItem label="Go">

```bash
go get github.com/smartpricing/queen/clients/client-go/v2
```

```go
import queen "github.com/smartpricing/queen/clients/client-go/v2"

client, err := queen.New("http://localhost:6632")
if err != nil {
	return err

defer client.Close(context.Background())
```

Go 1.24 or later. `queen.New` also takes a slice of URLs or a `ClientConfig`. The repository
lives at `github.com/queen-mq/queen`, but the module path still carries the organization it
started in, so import it exactly as written above.
[README](https://github.com/queen-mq/queen/tree/master/clients/client-go)

cargo add queen-mq serde_json

Rust 1.86 or later, on tokio. `connect` checks the configuration and opens no socket; the first

<TabItem label="C++">

The client is one header, `clients/client-cpp/queen_client.hpp`, used from a checkout of the
repository: it includes the thread pool in `clients/server/include/` by a relative path, and
`clients/server/vendor/` carries the nlohmann/json it needs. You install cpp-httplib 0.27.0 or later and OpenSSL
(`brew install cpp-httplib openssl` on macOS).

```cpp
#include "queen_client.hpp"

queen::QueenClient client("http://localhost:6632");
// ...
client.close();
```

```bash
g++ -std=c++17 -O2 -pthread \
    -I clients/client-cpp -I clients/server/vendor \
    -I /opt/homebrew/include -I "$(brew --prefix openssl)/include" \
    app.cpp -o app \
    -L "$(brew --prefix openssl)/lib" -lssl -lcrypto -lpthread
```

C++17 or later. Link OpenSSL even over plain HTTP: the header turns on cpp-httplib's TLS support
itself. Fluent consumers can enable dashboard observations with
`.supervision(queen::SupervisionConfig{"billing-production"})` before `.consume(...)`;
they are off by default. The README describes worker counts, handler progress and publication
timings. These observations do not restart or scale application processes.
[README](https://github.com/queen-mq/queen/tree/master/clients/client-cpp)

The JavaScript client is 2.0.4 and the Python, Go, Rust and C++ clients are 2.0.3; the PHP client
has its own version line. All of them talk to any 2.0 broker (the broker is at 2.0.3). The Go
client's module path ends in `/v2`, as Go requires for a major version above 1.

## curl is a client

Every SDK call is one of the broker's routes, so anything that can send an HTTP request can push,
pop, ack, commit a transaction, and read and write KV and timers, with nothing to install:

```bash
curl -s -X POST http://localhost:6632/api/v1/push -H 'content-type: application/json' \
  -d '{"items":[{"queue":"orders","partition":"customer-123","payload":{"orderId":8891}}]}'
```

The [quickstart](/start/quickstart/) runs a whole step this way, with curl and jq, and the
[HTTP reference](/reference/http/) lists every route. `queenctl`, the operator CLI (status, tail,
push, replay, lag, dead letters), ships inside the Docker image (`docker exec queen queenctl
status`) and as release binaries for Linux, macOS and Windows. See [queenctl](/reference/queenctl/).

## Consumer supervision

All six SDKs offer optional consumer observations through the authenticated KV API.
Reporting is off by default. Enable it before executing the consume loop:

| Client | Opt-in API | Observed lifetime |
| --- | --- | --- |
| JavaScript | `.supervision({ group: 'billing-production' })` | One awaited `consume()` execution. |
| Python | `.supervision({"group": "billing-production"})` | One awaited `consume()` execution. |
| Go | `Supervision(&queen.SupervisionConfig{Group: "billing-production"})` | One `Consume(...).Execute(...)` execution. |
| Rust | `.supervision(Some(SupervisionConfig::new("billing-production")))` | One awaited `consume()` or `consume_batch()` execution. |
| C++ | `.supervision(queen::SupervisionConfig{"billing-production"})` | One blocking `consume()` call. |
| PHP | `->supervision(['group' => 'billing-production'])` | One fluent `consume()->execute()` execution, separate from the Laravel process supervisor. |
| queenctl | `tail --supervision-group billing-production` | One tail command invocation. |

Each execution gets a new instance ID and fresh counters, including repeated calls on the
same client, builder, queue or host. The publication group collects instances; it does not
merge them or change the consumer group. Message and idle limits end an instance normally
and publish `stopped` with zero running workers. Several stopped cards for one host can
therefore describe finished short calls while an outer scheduler is still running.

JavaScript, Python, Go, Rust, C++ and queenctl publish at 10-second intervals with a
30-second heartbeat timeout and 60-second TTL. PHP publishes cooperatively when the loop
regains control, with heartbeat timeout `max(30, ceil(poll_timeout_ms / 1000) + 15)` seconds
(capped at 86400) and a TTL of at least twice that. Its default 30-second poll gives a
45-second heartbeat timeout and 90-second TTL. Long synchronous work can delay PHP
publication. Expired observations can remain visible until the broker sweeps them.

Use one persistent consume execution for persistent consumer observations, or `tail --follow`
without stopping limits for the CLI. If the application owns worker slots that rotate through
short calls, [publish its scheduler status](/reference/supervisor-status/#reporting-an-application-owned-scheduler)
with one ID for its lifetime and leave per-call supervision off. The fluent APIs do not offer
a shared reporter or instance-ID override. Preserve limits used for queue fairness and the
combined concurrency budget. [Consuming](/concepts/consuming/#optional-sdk-consumer-supervision)
explains the lifetime; the [status contract](/reference/supervisor-status/) defines the wire format.

## The broker inside a Rust program

A Rust program can run the broker in its own process, as the library `queen::Broker`. Every call
goes through the same handler functions the HTTP router dispatches to, so behaviour and defaults are
the broker's, and the data lives in a directory on local disk that you name.

2.0 is not on crates.io yet (the `queen-engine` published there is 1.3, which ran on PostgreSQL),
so depend on the repository, pinned to the 2.0.0 commit:

```toml
[dependencies]
queen-engine = { git = "https://github.com/queen-mq/queen", rev = "86562c25d", default-features = false }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
serde_json = "1"
```

The crate imports as `queen` and needs Rust 1.88. `default-features = false` leaves out what only
the standalone binary needs: the HTTP listener, the dashboard, the embedded proxy and the Kafka
facade. Start it on a data directory:

The embedded broker is one node and one tenant. It exposes push, pop, ack, lease renewal,
transactions, queue configuration, the dead-letter queue and ephemeral queues. KV and timers are
reachable only inside a transaction, so there is no standalone KV read or timer listing, and
consumer-group administration, queue listings, traces and streams are not exposed. A panic in one
of the broker's core threads (planner, log writer, apply, checkpoint, raft) aborts the process, and
the next start replays from the data directory; any other panic, your own included, unwinds as
usual. Never open one data directory from two brokers at once.
