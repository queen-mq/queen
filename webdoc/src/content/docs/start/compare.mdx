Two questions separate these systems: how you get order per entity when there are millions of
entities, and what one commit covers when a service handles an event. Queen's answers are a
partition per entity, created by its first message, and one transaction that writes the ack, the
KV state, the next events and the timers as one entry. Each section says where the other system
is better.

## Kafka

A topic has a fixed number of partitions, chosen when you create it. The producer hashes each
record's key onto one of them, so an entity shares its partition with every other entity that
hashes there, and a slow one delays the rest. Adding partitions later moves keys to other
partitions.

A Kafka transaction makes writes to several partitions and the consumer's offsets atomic: read,
process, write. Kafka Streams keeps its state inside that boundary by writing it to changelog
topics. State in a database is outside it, and Kafka has no delayed delivery.

**Where Kafka is better:** the ecosystem (Connect and its connectors, Streams, schema tooling),
log compaction, and CPU per message, which was lower than Queen's in every shape of the
cross-broker runs (those runs measured Queen 1.x). Queen's [Kafka facade](/guides/kafka/) lets
existing clients connect; it does not bring that ecosystem.

## RabbitMQ

Producers publish to exchanges, and bindings route each message into queues. A queue delivers in
order, but competing consumers on one queue do not process in order. Per-entity order needs a
queue per entity, or a consistent-hash exchange over a fixed set of queues, each with a single
active consumer.

AMQP 0-9-1 transactions make a batch of publishes and acks on one channel atomic. State in your
database is outside them.

**Where RabbitMQ is better:** routing. Exchanges, bindings, topic patterns and header matching
have no Queen equivalent: the producer names the queue and the partition. RabbitMQ also speaks
more protocols (AMQP, MQTT, STOMP); Queen speaks HTTP and the Kafka wire protocol.

## Amazon SQS

FIFO queues keep order within a message group ID, and while a group has messages in flight, SQS
delivers no others from it. This is the closest idea to a Queen partition: a group needs no
declaration and there is no count to choose. Deduplication uses a deduplication ID inside a fixed
five-minute interval.

There is no transaction. Deleting the input, sending the output and writing state are separate
calls. One queue serves one set of consumers: fan-out goes through SNS or a queue per subscriber,
and a deleted message cannot be read again.

**Where SQS is better:** there is no server to run, patch or back up.

## Temporal and Restate

Both are durable execution engines. You write the workflow as code; they record each step in a
history (Temporal) or a journal (Restate), and on recovery they replay your code against that
record. Per-entity order comes from addressing one workflow, or one Restate virtual object, by
the entity's key: Restate runs one exclusive handler at a time per key. What commits is a step of
your code, so the code follows the SDK's rules for replay, such as deterministic workflow code in
Temporal.

Queen keeps the state machine as data instead: the partition is its input, KV is its state, and
one transaction is one transition. Any language that speaks HTTP can be the worker, and nothing
replays your code. See [one state machine per entity](/guides/state-machines/).

**Where Temporal and Restate are better:** authoring long workflows as code. Loops, branches,
waits of days and compensation read as one function.

## PostgreSQL and a transactional outbox

This is the stack Queen replaces, and the one Queen 1.x was built on. A service writes its state
and an outbox row in one database transaction. A relay (a poller, or change data capture)
publishes the outbox rows to a broker. Consumers keep an idempotency table so a redelivery is
harmless, and a jobs table or a scheduler handles time. Per-entity order holds if the outbox
carries a sequence per entity and the relay and the broker keep it.

The database transaction covers the state and the outbox row. The publish, the consumer's ack and
the consumer's own state write are separate commits: the idempotency table and the reconciliation
code exist to stitch them together.

**Where PostgreSQL is better:** your state is relational. SQL, joins, constraints and ad hoc
queries, with the backups and tooling you already run. Queen's [KV](/concepts/kv/) reads by key or
by prefix.

## Summary

| | Per-entity order from | Partitions to choose | One commit covers | You run |
|---|---|---|---|---|
| **Queen** | a partition per entity, created by its first message | none | the ack, KV state, pushes and timers, as one entry | one binary: one node, or a cluster of three or five |
| **Kafka** | the record key, hashed onto a partition | a fixed count per topic, chosen up front | records across partitions, and consumer offsets | Kafka brokers |
| **RabbitMQ** | a queue per entity, or a hash onto a fixed set of queues | the queues you declare | publishes and acks on one channel | RabbitMQ nodes |
| **SQS FIFO** | the message group ID | none | no transactions | nothing: a managed service |
| **Temporal, Restate** | one workflow or virtual object per entity key | none | a step of your code, recorded for replay | their server (Temporal also needs a database) |
| **PostgreSQL + outbox** | a sequence per entity, kept by the relay | none | the state and the outbox row; publish and ack commit separately | the database, a relay and a broker |

This page carries no benchmark numbers: the cross-broker runs measured Queen 1.x, whose storage
was PostgreSQL. The 2.0 numbers and their conditions are in [benchmarks](/benchmarks/).

## Limits

- **No routing.** No exchanges, bindings, topic patterns or header matching.
- **Delivery is at-least-once.** Effects inside Queen are exactly-once through
  [transactions](/concepts/transactions/) and [`transactionId` dedup](/concepts/dedup/); a call
  your worker makes to another system is outside any commit.
- **A transaction is one call, inside one tenant.** There is no interactive BEGIN and COMMIT.
- **One leader orders every write of a raft group.** A hot partition is sequential by design.

The full list is in [limits](/reference/limits/).
