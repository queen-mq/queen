**A message queue is the smallest thing Queen MQ does.**

It's a transactional event broker. Every customer, order or conversation gets its own ordered
partition, created by the first message that names it. No partition count to choose. The ack, the
state change, the next events and the timer commit as one entry. Nothing happens halfway.

## A step, in code

Here is what a worker in the `billing` consumer group does with one payment event, the `message`
it took from the queue. It takes the event, marks the order paid, sends the customer a receipt and
asks for a reminder tomorrow:

```js
await queen.transaction()
  .ack(message, 'completed', { consumerGroup: 'billing' })                   // the event is done
  .kv.put('orders', `order-${orderId}`, { status: 'paid' }, { ttl: '30d' })  // state
  .queue('receipts').partition(customerId)
    .push([{ transactionId: `receipt-${orderId}`, data: receipt }])          // the next event, once
  .timer('reminders').key(`order-${orderId}`).delay('24h')
    .payload({ orderId }).schedule()                                         // what comes later
  .commit()
```

In most stacks those lines would reach four systems. The ack goes to the broker, the status to a
database, the receipt to an outbox table that a relay publishes later, the reminder to a scheduler,
and an idempotency table makes sure a retry doesn't send a second receipt. Each of them commits on
its own, so a crash between two commits leaves the step half done, and somebody writes the code
that finds those halves and repairs them.

In Queen the step is one call, `POST /api/v1/transaction`, and the broker writes it as one entry of
its log. All of it is there, or none of it is. If the worker was too slow and its lease ran out, the
ack is refused and the rest of the call is refused with it, so a worker that lost its message can
never write over the one that has it now. If the step committed and only the answer got lost, the
retry carries the same receipt id, the broker finds that receipt already stored and refuses the
whole call, and nothing is written twice. The outbox, the idempotency table, the cron job and the
reconciler were all there to keep separate commits consistent, and with one commit there is nothing
left for them to do. See [transactions](/concepts/transactions/).

## One partition per entity

The payment event above came from a partition, and so did every earlier event of the same order.
Most brokers order messages per shard: you choose a number of partitions when you create a topic,
your keys are hashed onto them, and every entity shares its shard with whoever else hashed there.
A slow customer holds up the customers behind it, and changing the count later moves keys around.

In Queen the partition is the entity. You name it when you push (`partition('customer-42')`), and the
first push creates it, in the same log entry as the message. There is no count to choose and
nothing to provision. Order holds inside the partition, and a consumer group works on one batch of
a partition at a time, so a slow customer delays nobody but itself. A partition costs the broker a
few rows of state, which is why millions of them are an ordinary number.
See [partitions](/concepts/partitions/).

Put the two ideas together and every entity becomes a small state machine. Its partition is the
input, in order; its KV entry is the state; each transaction is one transition, and a timer is a
transition that time triggers. The workers keep nothing between events, so you run as many as you
need and restart any of them at any time. See
[one state machine per entity](/guides/state-machines/).

## What you run

Queen is one Rust binary. A node keeps everything in a log on its own disk, with no database,
ZooKeeper or sidecar beside it. For availability you run three or five nodes as a raft cluster:
every entry is written to a majority of them before you get an answer, any node takes any request
(a follower forwards writes to the leader), and the cluster keeps serving while a majority is up.

Releases before 2.0.0 (2026-10-03) kept their data in PostgreSQL. 2.0 replaced it with this log,
and a 2.0 node does not read a 1.x database: see the [changelog](/reference/changelog/).

We keep each tenant inside one raft group, and that is what lets a transaction be a single log
entry, with no coordinator and no two-phase commit. The price is that one leader orders all of a
tenant's writes. A cluster can run several raft groups (`QUEEN_RAFT_GROUPS`), each with its own
leader, so tenants spread their load over the nodes. See [cluster](/operate/cluster/).

You talk to it in JSON over HTTP, so curl is a complete client, or through the SDKs for JavaScript,
Python, Go, Rust, C++ and PHP, the last with a [Laravel queue driver](/guides/laravel/). Existing Kafka producers and
consumers can connect, unchanged, to a Kafka wire-protocol facade that runs inside the same process
once you turn it on, PostgreSQL tables stream in and out through built-in connectors, and an S3
sink writes queues to a bucket. The binary serves the dashboard and Prometheus metrics too, and, when you
enable them, checks JWTs, encrypts payloads at rest and runs a proxy for API keys and per-tenant
limits. For traffic that should never touch a disk, such as typing indicators, ephemeral queues
keep their messages in memory. See [clients](/start/clients/), [Kafka](/guides/kafka/), [PostgreSQL](/guides/postgres/) and
[S3](/guides/s3/).

## Numbers

On three 16-vCPU nodes, with every write fsynced on two of them before its answer, 2.0.0-beta.2
pushed and consumed 1,000,000 messages a second through one queue at every partition count we
tried, from 200 to ten million, with an end-to-end p99 between 103 and 163 ms. An exactly-once step
of 10 messages committed in 3 ms at the median, and one raft group topped out between 7,000 and
9,000 such transactions a second (2026-10-01, with Kafka, Redpanda and Pulsar measured on the same
machines). The latest full Jepsen campaign, on the code of 2.1.0, ran 153 tests under kill -9,
partitions, pauses, clock jumps and power loss: 152 were valid, and the other, judged invalid on
test nodes whose clocks had drifted apart, was valid when it ran again
([Jepsen](/benchmarks/jepsen/)). Every number, with its conditions and
the places where other systems did better, is on [benchmarks](/benchmarks/), and what the
guarantees cover is on [guarantees](/concepts/guarantees/).

## Limits

- Delivery is at-least-once. Effects inside Queen are exactly-once, through transactions and
  `transactionId` dedup, and a call your worker makes to another system is outside any commit.
- A hot partition is sequential, by design. Parallelism comes from having many partitions with
  work.
- A transaction is one call, inside one tenant. There is no interactive BEGIN and COMMIT.
- One leader orders every write of a raft group, so one tenant's write rate is what one leader can
  plan. You scale out with more raft groups and more clusters.
- There is no routing: no exchanges, bindings or header matching. The producer names the queue and
  the partition.
- Ephemeral queues lose what a node held when it crashes, because their contents are not in the
  log.

When one of these rules Queen out, [when not to use Queen MQ](/start/when-not-to-use/) names what
to use instead.
