**High-performance transactional messaging for applications that need an ordered stream per
entity.**

Queen is a message broker written in Rust. Each node is one binary that keeps its state in a
replicated log on its own disk, with no external database. Its defining abstraction is one logical
ordered partition per application entity, a customer, an account, a conversation, a device, a
workflow, a session or a job, created by the first push that names it and never provisioned in
advance.

## The problem

Most brokers give you ordering per *shard*. Your requirement is ordering per *entity*: this
customer's events processed in order, this conversation's messages not overtaking each other,
this account's transactions settling in sequence.

Bridging the two is where the pain lives. Hash your entities onto a fixed partition count and the
ones that collide block each other, so a slow customer stalls every customer sharing its shard.
Give each entity its own queue instead and broker-side objects grow with your customer list.

Queen removes the bridge: **the entity is the partition.**

## One entity, one ordered partition

You choose the partition key. It is your ordering boundary, not an infrastructure sizing
decision: `customer_id`, `account_id`, `conversation_id`, `device_id`, `workflow_id`.

<pre class="mermaid">{`
flowchart LR
  A["customer A"] --> A1["A1 → A2 → A3"]
  B["customer B"] --> B1["B1 → B2"]
  C["customer C"] --> C1["C1 → C2 → C3"]
  A1 --> AX["strict FIFO within the lane"]
  B1 --> BX["B is not held up by A"]
  C1 --> CX["C is not held up by A or B"]
`}</pre>

The push creates the queue, the lane and the message. Nothing is preallocated, nothing is
assigned, nothing rebalances when a consumer restarts.

<Render file="snippets/js-push" />

The `transactionId` is optional and is the idempotency key: give it your own and a retry of the
same push, inside the queue's deduplication window, writes nothing the second time.

Consumers choose how they read: which partition, how many at once, batch size, consumer group,
lease time.

<Render file="snippets/js-consume" />

Two things this does not mean. **A single hot partition stays sequential, by design**, because
one leased batch exists per partition and consumer group: parallelism comes from many active
partitions, not from splitting one, so add lanes rather than workers. And **do not pick a key
because it has high cardinality**: pick the boundary your application genuinely requires. A
partition per message is not a supported shape.

The whole of it, in one page: [the model](/use/model).

## Transactional processing

The second reason Queen exists. One [`POST /api/v1/transaction`](/reference/http/transaction)
bundles acknowledgements, pushes, key/value writes and timer operations into one entry of the
replicated log, and an entry applies whole or not at all.

<Render file="snippets/js-transaction" />

The bundle is N to M: one call may acknowledge batches leased from any number of partitions,
queues and consumer groups, and push to any number of queues and partitions, which is what makes
a fan-in stage possible. This is what replaces transactional outbox tables, a separate store for
idempotency markers, and the reconciliation code that exists only because the broker's commit and
the application store's commit were two different commits.

<Aside type="caution">
Atomicity covers broker state, not the network. If the response is lost you do not know whether
it committed, and a blind retry duplicates the pushes unless your transaction ids are
deterministic and the retry lands inside the deduplication window. Queen does not make an
external HTTP call exactly-once, and no broker can. The one case that *is* exactly-once end to
end is when the effect is itself state in this broker, written through the
[key/value rider](/use/kv): marker, effect, output and cursor advance become a single commit.
</Aside>

## The mental model

```text
Application entity        the thing whose order matters
    ▼  Partition key      your ordering boundary, chosen by you
    ▼  Ordered stream     one lane, created on demand, strict FIFO
    ▼  Transaction        ack + state + output in one log entry
    ▼  Replicated log     one leader orders it, every node applies it
    ▼  Node               one binary, a full copy on its own disk
    ▼  Cell               one deployment, one failure domain
    ▼  Region             where a cell physically lives
```

The top half is your application's shape. The bottom half is infrastructure. Queen's central bet
is that these two halves should scale independently of each other.

## What has been measured

Every figure on this site names the run that produced it, and a figure without an archived
artifact recording its configuration does not get published. The runs published so far measured
Queen 1.x, whose storage was PostgreSQL; 2.0 replaced that storage with the replicated log, so
those figures describe the 1.x engine and not this one. They are kept, with their conditions, under
[Benchmarks](/benchmarks). Read [method and rig](/benchmarks/method) before quoting any number:
single-shape runs say nothing about your throughput, latency, sizing, disk, retention capacity or
partition distribution, which follow from your workload, payloads and hardware.

## Application scale is not infrastructure scale

This is the principle the rest of the architecture follows from.

In most brokers the two are welded together: a per-entity ordering guarantee means a per-entity
infrastructure object, either a topic partition with its own files and replicas or a live
server-side queue. Doubling your customers means doubling something an operator has to think
about.

In Queen a partition is an entry in the node's ordered store and a range of offsets in its queue's
log. It is not a file, a process or a replica set of its own. **Millions of logical entity streams
do not require millions of infrastructure objects.**

## Three kinds of scale

Three axes, frequently confused, not interchangeable. Confusing them is the most common way to
mis-size a deployment.

| Axis | What it scales | What it does not |
| --- | --- | --- |
| **Partitions** | Application cardinality. Add entities freely: nothing is provisioned, no process is created, no rebalance runs | Make one hot lane parallel |
| **Nodes** | Availability. Three voters survive one failure, five survive two, and any node serves any client | Write throughput: every write goes through one leader and lands on every voter |
| **Cells** | The deployment. Capacity grows by adding cells, not by growing one system | Solve cross-region replication or global ordering |

Inside one cell, `QUEEN_RAFT_GROUPS` runs several independent raft groups per process, each with
its own leader and log, and places each tenant in one of them, so a cell with many tenants spreads
its writes over several leaders ([High availability](/deploy/ha#several-raft-groups-per-process)).

## Inside a cell

A cell is one Queen node or a raft cluster of them, optionally with the proxy switched on in the
same process. It is at once the scaling boundary, the failure boundary and the unit of upgrade and
operational ownership. Cells do not coordinate with each other to process messages.

<pre class="mermaid">{`
flowchart LR
  C["clients<br/>six SDKs, queenctl, curl, Kafka clients"] -->|HTTP| N1["Queen node<br/>leader"]
  C -->|HTTP| N2["Queen node<br/>follower"]
  N2 -.->|forwards writes| N1
  N1 -->|replicated log| N2
  N1 -->|replicated log| N3["Queen node<br/>follower"]
  N1 --- D1[("local disk")]
  N2 --- D2[("local disk")]
  N3 --- D3[("local disk")]
`}</pre>

**The log is the durable source of truth, and every node holds a full copy of it.** Messages,
offsets, leases, deduplication state, queue configuration, dead letters, key/value state and timers
are all state the log produces. One leader orders every write into it; a write is answered once a
majority of the voters have it on disk; every node applies the same entries in the same order. That
is why deduplication and leases stay exact across nodes, and why a client can talk to any node: a
follower forwards writes to the leader and holds reads until it has applied what was committed when
they began.

**The failure domain is the majority.** A cluster of three keeps serving through the loss of one
node, a cluster of five through two, and a leader that stops gracefully hands leadership over
before it drains. Losing a majority stops writes until it is back ([high availability](/deploy/ha)).
A single node is its own failure domain.

## Many tenants, one cell

The proxy is the tenant-facing boundary, and it runs inside the broker process when
`QUEEN_PROXY_EMBEDDED=true`. Queen core stays focused on messaging, and everything a shared broker
has no business holding lives in the proxy: per-cluster API keys and human logins, plan limits on
rate, size and count, and usage metering. Its own state lives in the same replicated log, under a
system tenant.

Isolation is split across both halves on purpose. The broker scopes queue identity natively as
`(tenant, name)` on every read and write, so two tenants both owning a queue called `orders` own
different queues. The proxy is what makes the tenant identity driving that scoping trustworthy.
Neither half is sufficient alone ([isolation](/reference/multi-tenant/isolation)).

A **cluster** is the tenant-visible Queen: one hostname, one plan, one namespace. A **cell** is
the physical deployment it runs on. A cluster lives on exactly one cell and never spans two.

## What is in the box

- **Messaging**: ordered FIFO partitions created on demand, consumer groups with one cursor per
  partition, leases with explicit ack, nack, retry and dlq, [replay and seek](/use/model#replay),
  retry budgets and a real [dead-letter queue](/reference/http/messages-dlq), long-poll
  consumption, retention by age and by completion.
- **Exactly-once building blocks**: [deduplication at push](/internals/dedup) keyed on your
  transaction id, exact rather than probabilistic, so a duplicate writes nothing; transactional
  `ack + kv + push + timers` in one commit.
- **State and time**: [`queen.kv`](/use/kv) with optimistic locking and an expiry on every write,
  [timers](/use/timers) that stay cancellable until they fire, delayed delivery, window-buffer
  debounce, and [conflation](/reference/http/pop#conflation) for last-value delivery.
- **Stream processing**: an [operator chain](/use/streams) that runs in your process with state in
  the same broker. Four window types, event time with watermarks, per-message gating, and one
  cycle that commits state, sink pushes and the ack together.
- **Ephemeral queues**: an [in-memory class](/use/ephemeral) with no disk in the path, for
  request/reply, signalling and cache invalidation.
- **Operations**: one binary serving HTTP on port 6632, six SDKs plus
  [`queenctl`](/reference/queenctl), a [dashboard](/deploy/dashboard) in the same binary on the
  same port, [Prometheus metrics](/reference/prometheus), [JWT auth](/reference/security/jwt),
  payload encryption and a raft cluster for failover.
- **The Kafka wire protocol**, in the same process and off until you switch it on. The facade
  advertises 32 Kafka API keys, so an unmodified Kafka producer or consumer reaches Queen by
  changing `bootstrap.servers` and nothing else. The contract is [reference/kafka](/reference/kafka),
  running it is [deploy/kafka](/deploy/kafka).

## When something else is the better tool

These systems made different tradeoffs, and some of those tradeoffs are better than Queen's for
workloads that need them.

- **The Kafka ecosystem, past the wire protocol.** The protocol itself is spoken by the
  [facade](/reference/kafka), but there is no log compaction and a transaction lives in one facade
  process, so Kafka Streams, Connect's exactly-once source, the Schema Registry's compacted topic,
  and Flink and Spark's two-phase writers all stay out, and the literature about brokers, replicas
  and log directories does not apply.
- **A single ordered stream that must itself scale horizontally.** One lane is sequential. If your
  ordering boundary is everything, Queen's core idea does nothing for you.
- **Storage that scales beyond one machine's disk**, or a system that replicates itself across
  regions. Every voter holds a full copy of the state, so retention is bounded by one node's disk.
- **Rich content-based routing.** No exchanges, no bindings, no header matching. That is
  RabbitMQ's strength.
- **No server to operate at all.** That is Amazon SQS.

In one sentence: distributed logs make *infrastructure partitions* the fundamental scaling
abstraction, and Queen makes *application entities* the fundamental ordering abstraction and
*cells* the infrastructure scaling boundary. The side-by-side is
[the comparison](/start/compare).
