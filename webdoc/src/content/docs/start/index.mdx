**A message queue is the smallest thing Queen MQ does.**

It's a transactional event broker. Every customer, order or conversation gets its own ordered
partition, created by the first message that names it. No partition count to choose. The ack, the
state change, the next events and the timer commit as one entry. Nothing happens halfway.

## One step, one commit

When a service handles an event, it does five things. In most stacks they live in four systems,
and each one commits on its own:

| The service | Usually lives in | In Queen |
|---|---|---|
| takes the event and acks it | the broker | [consumer groups and leases](/concepts/consuming/) |
| changes state | a database | [KV](/concepts/kv/) |
| emits the next events | an outbox table, then the broker | [push](/concepts/partitions/) |
| schedules what comes later | cron or a scheduler | [timers](/concepts/timers/) |
| makes a retry harmless | an idempotency table | [`transactionId` and `once`](/concepts/dedup/) |

Queen keeps all five in one replicated log. One call writes them as one entry:

```js
await queen.transaction()
  .ack(message)                                                    // the event is done
  .kv.put('orders', orderId, { status: 'paid' }, { ttl: '30d' })   // state
  .queue('receipts').partition(customerId)
    .push([{ transactionId: `receipt-${orderId}`, data: receipt }]) // the next event, once
  .timer('reminders').key(orderId).delay('24h')
    .payload({ orderId }).schedule()                               // what comes later
  .commit()
```

If the lease has expired, if this receipt was already pushed by an earlier try, or if any part is
refused, nothing in the call is written: a retry of a step that committed writes nothing twice. The outbox table, the idempotency table, the cron job and the reconciler
that exist only to stitch four commits together are not needed. See
[transactions](/concepts/transactions/).

## One partition per entity

Most brokers order messages per shard: a fixed number of partitions, chosen up front, with your
entities hashed onto them. Entities that share a shard wait for each other.

In Queen the partition is the entity. You name it on push (`customer-123`), and it exists from
that message on. Order holds inside it, and a slow entity delays only itself. See
[partitions](/concepts/partitions/).

Together, these two ideas let you run every entity as a small state machine: its partition is the
input, its KV entry is the state, and each transaction is one transition. Workers stay stateless.
See [one state machine per entity](/guides/state-machines/).

## What runs it

- **One binary.** A node keeps its state in a log on its own disk. No database, no ZooKeeper, no
  sidecars.
- **One node, or a cluster of three or five.** Raft replicates every entry, and the cluster keeps
  serving while a majority is up. See [cluster](/operate/cluster/).
- **Tenants in raft groups.** Each tenant lives in exactly one raft group, so a transaction is one
  entry with no coordinator and no two-phase commit. See [architecture](/internals/).
- **Any client.** HTTP (curl is enough), six SDKs, and Kafka clients through the built-in Kafka
  wire protocol. See [clients](/start/clients/) and [Kafka](/guides/kafka/).
- **Built in:** dashboard, Prometheus metrics, API keys, JWT, quotas, payload encryption.

## Numbers

Three nodes, 16 vCPU each, every write replicated:

- **1,000,000 msg/s** pushed and consumed, one queue, 500,000 partitions, e2e p99 ~270 ms.
- **10,000,000 partitions** in one queue at ~910,000 msg/s (60 s run, e2e p99 4.7 s).
- **Jepsen-tested:** no acked message lost through kill -9, partitions, clock jumps and power loss.

These runs measure push, pop and ack, not transactions. Conditions and sources:
[benchmarks](/benchmarks/) and [guarantees](/concepts/guarantees/).

## Limits

- **Delivery is at-least-once.** Exactly-once holds for effects inside Queen (transactions,
  dedup), not for a call your worker makes to another system.
- **A hot partition is sequential by design.** Parallelism comes from many partitions, not from
  splitting one.
- **Transactions are one call**, inside one tenant. There is no interactive BEGIN and COMMIT.
- **One leader orders every write of a raft group.** You scale out with more raft groups and more
  clusters, not by spreading one tenant's writes.
- **No routing.** There are no exchanges, bindings or header matching: the producer names the
  queue and the partition.
