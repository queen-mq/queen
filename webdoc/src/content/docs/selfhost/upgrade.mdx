Queen is **always-virgin**: an upgrade is the new version against a fresh
database plus a traffic cutover, and pointing a new build at an old database
is unsupported; [what happens at boot](#what-happens-at-boot) explains why.
Same-version restarts and replacements are routine and coordination-free.

## Restarting and replacing replicas (same version)

<Steps>

1. **Start the replacement broker** with the same configuration.

2. **Wait for a real health check**: 200 from `GET /health` means the
   [database is reachable](/selfhost/probes-restarts#what-health-tests);
   process liveness proves nothing.

   ```bash
   curl -sf http://new-broker:6632/health
   ```

3. **Take the old broker out of the load balancer, then SIGTERM.** Shutdown
   drains in-flight requests; acks park until their commit resolves, so a
   drain-time completion committed or errored, never vanished.

4. **Check the shutdown log.** A spool warning with a pending count means
   events on a [node-local](/selfhost/durability#the-limits) volume, replayed
   only by a broker on the same `FILE_BUFFER_DIR`.

5. **Repeat** per replica.

</Steps>

Startup [replays the spool](/selfhost/durability#startup-recovery) **before**
the listener binds: big spool, slow start; a dead database does not block boot
indefinitely.

### In-flight leases

Leases are rows in `queen.log_consumers`, not memory: a restart neither touches
nor releases them. The leased span stays invisible to its group until
`lease_expires_at` passes, then the whole span redelivers from the unchanged
cursor.
[Probes and restarts](/selfhost/probes-restarts#what-happens-to-in-flight-leases)
walks the sequence and why redelivery charges the attempt count but never the
retry budget.

Restart-specific: a client can still ack a live lease to any replica (the
in-memory fast path dies with the process; the ack resolves through the SQL
hash sidecar, one extra lookup). Lease time is the recovery window: size
`leaseTime` above normal processing, below an acceptable redelivery delay.

<Aside type="note">
`autoAck=true` pops commit inside the pop transaction: nothing to redeliver, and a message in flight to the client when the broker stopped is lost. At-most-once, as requested.
</Aside>

## Upgrading a deployment: fresh database + cutover

<Steps>

1. **Stop producing** to the old deployment.

2. **Let consumers drain it** to empty: acked work commits, expired leases
   redeliver.

3. **Stand up the new version against a fresh database** (a fresh name on the
   same server counts); it creates its own schema at first boot. Never point
   it at the old database.

4. **Repoint producers and consumers.** The first push creates its queues and
   partitions, no provisioning step; re-apply any `/configure` options,
   configuration lives in the old database.

</Steps>

Cannot drain? Copy at the application level: read the backlog through the old
API and push it to the new deployment with a deterministic `transactionId` per
message, so a retried copy loop cannot duplicate.

### Rollback

The cutover reversed: keep the old deployment and database (producers stopped,
consumers drained) until you trust the new one; rollback is repointing
clients. Deleting the old database closes the route; messages pushed meanwhile
need the copy loop in reverse.

## What happens at boot

`schema::apply` runs before anything else touches the database:

1. Hold a **session** advisory lock, `pg_advisory_lock(778120010)`, released
   on every exit path; the apply serialises cluster-wide, so concurrent
   restarts cannot race the DDL.
2. Execute `sql/schema.sql`, then each `sql/procedures/*.sql` in lexical order
   (23 files, 24 batches). All statements are idempotent (`CREATE OR REPLACE`,
   `IF NOT EXISTS`): every-boot re-apply is safe.
3. **Fail the process** on any DDL error, naming the file: a broker never
   serves against a schema it could not bring to shape.

Each function and table is defined exactly once, by one file; the lexical order
is load-bearing (table files `001_log_schema`, `002_streams_schema` before the
SQL-language bodies that resolve them at creation; trigger attachment
`020_log_partition_counters` after both).

An empty database gets the full schema; a same-version database is verified and
re-asserted (per-table storage and autovacuum parameters re-applied every boot,
so no drift). A different version's database is left as found: the
always-virgin contract (no migration files, no version table, no upgrade
ALTERs; `CREATE TABLE` declares the final shape once). `CREATE OR REPLACE` also
means **the last broker to boot decides which procedure version every
connected broker runs**.

<Aside type="note">
`QUEEN_APPLY_SCHEMA=0` skips all of the above, making this version's DDL your responsibility before first boot, see [PostgreSQL](/selfhost/postgres); everything else on this page still applies.
</Aside>

## Coming from 0.16

The previous broker was C++ on a different storage engine; 1.0 is not an
update of it, and moving is the cutover above, carrying no data.
`queen migrate` logs that migration is unsupported on the log engine and exits
1 without opening a database connection. This engine's data is `queen.queues`
plus five log tables (`log_partitions`, `log_segments`, `log_txns`,
`log_consumers`, `log_dlq`); none of the old broker's tables are created or
read, and nothing on disk needs converting: the old broker's state was also in
PostgreSQL.

## Confirming which version you are running

```bash
curl -s http://localhost:6632/health
```

`server/server.json` is the source of truth: `build.rs` embeds it into the
binary, `build.sh` uses it as the image tag, and `/health` and
`queenctl version` report it. The boot `listening` line carries the same
version plus the resolved engine settings.
