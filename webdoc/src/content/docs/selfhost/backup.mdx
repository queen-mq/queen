Backing up Queen is a PostgreSQL operation. The broker is stateless: everything
it persists lives in the two schemas `queen` and `queen_streams`, plus the
[node-local push spool](/selfhost/durability), which no database backup can
capture. Dump both schemas in custom format, so the restore can be parallel and
selective:

```bash
pg_dump -Fc -n queen -n queen_streams -f queen-2026-07-30.dump "postgresql://user@host:5432/queen"
```

Check what you captured before you trust it:

```bash
pg_restore -l queen-2026-07-30.dump
```

Restore into an empty database, with every broker instance stopped:

```bash
createdb -h host -U postgres queen_restored
pg_restore --no-owner --no-privileges -d "postgresql://postgres@host:5432/queen_restored" queen-2026-07-30.dump
```

<Aside type="danger">
**Do not restore into a database a broker is still connected to: stop every
instance first, including ones you forgot were behind the load balancer.** A
restore under live pushes and acks rewrites cursor rows underneath them and
leaves the deployment incoherent, not rolled back.
</Aside>

## Why the commands look like that

**Both `-n` flags matter.** Omitting `queen_streams` is the most common mistake:
it holds every registered streaming query and all per-key operator state, and the
loss is silent, because the broker boots happily and recreates an empty schema.

**A dump can be taken against a running broker.** `pg_dump` works from a single
transaction snapshot, so the result is internally consistent.

**Dump the data, not the shape.** The broker re-applies its full DDL at every
boot under an advisory lock, every statement idempotent, so a schema-only dump is
redundant for recovery. No table lives in `public` and no extension is required:
the schema needs `CREATE SCHEMA` and nothing else.

**`--no-owner --no-privileges` are deliberate.** The boot-time schema applier
re-issues the `GRANT` statements the broker needs, so you do not reproduce the
source cluster's roles; start a broker against the restored database with
`QUEEN_APPLY_SCHEMA` at its default of true and the idempotent re-apply verifies
the schema and re-asserts the per-table parameters.

**Restore into the same broker version that produced the dump.** The deployment
model is always-virgin: boot DDL only creates, never reshapes, so an
older-version schema is the unsupported "database built by a different version"
case. Moving data across versions is a cutover, not a restore; see
[Upgrades](/selfhost/upgrade).

<Aside type="note">
The published image ships the PostgreSQL 18 client tools, so every command here
runs from inside the broker container; the slim broker-only image built from
`server/Dockerfile` does not carry them, so with that build run them from a
client image or the database host, matching the client's major version to the
server's or newer. The remaining `migrate` subcommand only reports that offline
migration is unsupported and exits non-zero.
</Aside>

## What a restore does to consumers

A restore rolls the entire consumption state back to the dump instant. The
consequences are mechanical:

| State | After the restore |
| --- | --- |
| Cursors | Back to their dump-time `committed` offsets, so every message acked since the dump is redelivered. Duplicate volume is proportional to the dump's age: an hour-old dump means an hour of reprocessing. Consumers must be idempotent for this to be a recovery rather than an incident. |
| Leases | A lease is columns on the consumer row (`worker_id`, `batch_end`, `lease_expires_at`), not a session. Restored timestamps are in the past, the lease predicate treats the row as free, and the next pop re-leases from `committed`. One edge: a fast restore can capture a still-future `lease_expires_at`, and that (partition, group) is invisible to pops until it passes; the wait is bounded by the queue's lease time. |
| Deduplication | `queen.log_txns`, the hash sidecar the push path probes, is in the dump, so producers replaying pre-dump messages are still deduplicated inside the window. Hashes written after the dump are gone, so a retry of one of those pushes is accepted as new. Plan for duplicate delivery and, for post-dump traffic, duplicate storage. |
| Retry budgets and dead letters | `batch_retry_count` returns to its dump value, so an exhausted batch gets its budget back. `queen.log_dlq` rows written after the dump are gone. |
| Maintenance flags | Both live in `queen.system_state` and are read at boot. A dump taken during a maintenance window restores with push maintenance **on**, so every push goes to the spool and nothing reaches PostgreSQL: check `GET /api/v1/system/maintenance` immediately after any restore. |
| The push spool | Not in the dump: buffered pushes are [node-local files](/selfhost/durability) under `FILE_BUFFER_DIR`, so drain the spools before rebuilding a deployment. |
| Metrics and stats | Recover on their own: `queen.stats` is recomputed within one reconciler interval and the metrics tables refill from the collectors. A data-only restore that skips `queen.system_metrics`, `queen.worker_metrics` and `queen.queue_lag_metrics` is a legitimate way to shrink a large dump. |

## Cloning a deployment

The same two-schema dump builds a staging copy from production.

<Steps>

1. Dump both schemas from the source, as above.

2. Restore into a fresh database on the target cluster with `--no-owner
   --no-privileges`.

3. Start one broker against it and read the `config: postgres` boot line to
   confirm it is talking to the clone, not to production.

4. **Do not leave `QUEEN_MESH_PEERS` pointing at the source deployment**: a clone
   that joins the original mesh can affect production, up to
   [flipping its maintenance mode](/selfhost/ha#the-mesh-port-must-be-firewalled).

5. The restored cursors are production's cursors. To replay history in the
   clone, seek the groups back with
   `POST /api/v1/consumer-groups/:group/queues/:queue/seek` rather than editing
   rows by hand.

</Steps>

A clone is a separate database, so the advisory locks gating retention and the
stats reconciler are separate too: the clone sweeps its own data and cannot
interfere with the source's maintenance.

## Physical backups

A base backup plus WAL archiving, or your provider's snapshot and point-in-time
recovery, works without caveats: it covers both schemas by construction, which
removes the "forgot `queen_streams`" failure mode, and it is the right choice
once a logical dump stops finishing in a sensible window. Recovering to a point
in time rolls cursors back to that point with exactly the redelivery
consequences above, and the spool stays outside the picture either way.
