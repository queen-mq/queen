Every broker serves a dashboard on its own port, with nothing to deploy: the
built single-page application is compiled into the binary with `rust_embed` from
`server/webapp/dist` and read out of the executable at request time.

```bash
open http://localhost:6632/
```

The bundle is fixed at build time: no `QUEEN_STATIC_DIR`, no runtime
static-directory override, a volume mounted at the container changes nothing,
and a different dashboard means rebuilding the binary. `queen_proxy` embeds the
same `server/webapp/dist`, so a proxy and the broker behind it serve the
identical bundle.

## How it is served

The dashboard is the router's **fallback**, registered after every real route,
so it can never shadow an API path. It resolves in three steps:

1. A path under `/api/` or `/auth/` (or exactly `/api` or `/auth`), or any
   method other than `GET` or `HEAD`, gets a JSON 404:
   `{"error":"Not Found","code":"no_such_route"}`. Without this step a call to a
   nonexistent endpoint came back `200 text/html`, which every JSON client read
   as success; a phantom endpoint now fails loudly.
2. A path matching an embedded asset returns that asset, content type guessed
   from its extension.
3. Anything else returns `index.html`, so client-side routes like
   `/queues/orders` survive a hard reload. A binary built without the bundle
   returns a plain `404 Not Found` here.

Assets are served with a content type and nothing else: no `Cache-Control`, no
`ETag`, no compression negotiation. If the dashboard is on a hot path, put a
reverse proxy or CDN in front and let it add caching.

## Who the dashboard thinks you are

The dashboard boots by calling `GET /auth/me` and derives every permission from
that one payload: it never guesses a role from a response code and never sniffs
which binary is serving it. Whoever serves the bundle answers `/auth/me`, and
that is the whole difference between the deployments:

| Deployment | `/auth/me` answers with | What that means |
| --- | --- | --- |
| Behind `queen_proxy` | the proxy's cookie-authenticated session | real users, per-cluster roles, an operator flag and a login page; the broker never sees these paths |
| Broker-direct, auth off (`JWT_ENABLED=false`, the default) | a fixed *standalone* identity: one synthetic cluster `local`, the `admin` role on it, the operator capability live, `standalone: true` | every view including System works. The `standalone` flag is the one thing the shell reads to hide the session controls: no cluster selector (nothing to switch to), no sign-out (no session to end). Nothing is granted: with auth off the API was already open to anyone reaching the port, and the boot log says so. The dashboard adds visibility, not privilege |
| Broker-direct, auth on (`JWT_ENABLED=true`) | `401 {"code":"auth_required"}`: the app sends no bearer token, and the broker holds no user accounts or browser sessions | the login redirect lands on `/auth/login`, where the broker serves a static page saying exactly that: use the proxy, or run with auth off. The page is terminal, so there is no redirect loop |

`POST /auth/logout` exists as a no-op (`{"ok":true}`) so a hand-typed call gets
an answer instead of a JSON 404. All three routes are `public` in the
authorization table; `/auth/me` enforces the auth state itself.

Every view is tenant-scoped except one, and the exception is labelled on screen.

| View | Path | What it reads |
| --- | --- | --- |
| Dashboard | `/` | the resource overview, namespaces and tasks: the tenant's totals and key rates |
| Queue Operations | `/operations` | per-queue throughput, lag and consumer health |
| Queues | `/queues` | the queue list, with per-queue detail and delete |
| Queue Detail | `/queues/:queueName` | one queue's configuration and current status |
| Consumer Groups | `/consumers` | groups, their lag, the lagging list, subscription changes, seek and delete |
| Messages | `/messages` | message listing and single-message inspection, plus delete |
| Traces | `/traces` | trace names that actually exist, and the timeline for one |
| Analytics | `/analytics` | per-queue status over time, queue lag and queue ops time series, retention volume |
| Dead Letter | `/dlq` | the dead-letter listing, with purge |
| System | `/system` | **cell-level**: host CPU and memory, worker metrics, PostgreSQL internals, the disk spool, the maintenance switch |

Three properties to know before reading a number off this UI:

**The System view is not about your tenant.** Host resources, PostgreSQL
internals and the file-buffer state cover the whole cell, every tenant on it;
the view says so on screen, and behind a proxy it answers only for an operator
principal. Reading a cell figure as a tenant figure is the specific mistake the
shell is built to prevent.

**The dead-letter view inspects and purges, with no replay control.** An earlier
version had a retry button posting to a path the broker did not route; the
request fell through to the static fallback and reported success while doing
nothing, so the control was removed rather than left lying.

<Screenshot

**An unknown is not a zero.** Panels carry explicit loading, error and
last-updated state, a failed call renders as a failure instead of a confident
`0`, and refresh is one shared ticker, so what you see across a page is one
moment.

## Rebuilding it

The source is `app/`: Vue 3, Vite, Tailwind, Chart.js, Node 22 or newer. Run the
first two steps from `app/` and the last from `server/`.

<Steps>

1. Install dependencies.

   ```bash
   npm install
   ```

2. Build. The output goes straight to `server/webapp/dist`, the one artifact
   both Rust binaries embed.

   ```bash
   npm run build
   ```

3. Rebuild whichever binary serves it, because the bytes are baked in.

   ```bash
   cargo build --release
   ```

</Steps>

<Aside type="caution">
**A source change ships only after both the `npm run build` and the `cargo
build`.** Debug builds of `rust_embed` read from disk, so locally the npm build
alone usually appears to be enough; release builds are not, and that difference
is a reliable way to ship a stale dashboard.
</Aside>

For iterating on the UI, `npm run dev` serves it on port 4000 and proxies
`/api`, `/auth`, `/health` and `/metrics` to a `queen_proxy` development cell on
port 6711. `QUEEN_DEV_UPSTREAM=http://localhost:6632` points it straight at a
broker instead: standalone mode, with its fixed operator identity (no sessions,
no tenancy, no role checks, no rate limiting). Default to the proxy upstream
unless standalone behaviour is what is being worked on, because the proxy side
is where a permission or a 429 can prove the UI wrong. `QUEEN_APP_BASE` sets the
router and asset base if the bundle is mounted under a path prefix.
