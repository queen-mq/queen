PostgreSQL is not a dependency of Queen; it is Queen's storage engine. Messages,
offsets, the dedup index, queue configuration and the DLQ are ordinary tables,
and every queue semantic runs in stored procedures inside the database. Sizing
PostgreSQL *is* sizing Queen, and the broker's connection must behave like a
real session, not a pooled statement channel.

## Set it up

**PostgreSQL 15 or newer, no extensions.** The simplest correct setup is a
dedicated database owned by a dedicated role:

```sql
CREATE ROLE queen LOGIN PASSWORD 'change-me';
```

```sql
CREATE DATABASE queen OWNER queen;
```

Point the `PG_*` variables at it; the broker applies its schema at boot. The 15
floor is one unique index declared `NULLS NOT DISTINCT` (on
`queen.consumer_groups_metadata`, whose discovery rows carry NULLs that must
still collide); 14 fails there, the rest of the DDL needs only 13. Harness and
rigs run `postgres:16`; there is no `CREATE EXTENSION` anywhere in
`server/sql/`.

## Privileges

To apply its schema the broker needs `CREATE` on the database (two
`CREATE SCHEMA IF NOT EXISTS`), ownership of what it creates (the DDL sets
`fillfactor`, per-table autovacuum, `ALTER COLUMN blob SET STORAGE EXTERNAL`),
and `GRANT` capability (`002_streams_schema.sql` issues grants, below). The
owner-role setup above provides all three.

### Running as a low-privilege role

If policy forbids DDL from an application role, set `QUEEN_APPLY_SCHEMA=0`: the
broker logs `apply skipped (QUEEN_APPLY_SCHEMA=0)` and connects straight to
serving. The schema is compiled into the binary, so pre-apply the exact source
text: `server/sql/schema.sql`, then `server/sql/procedures/` in lexical order,
which is [load-bearing](/selfhost/upgrade#what-happens-at-boot);
`server/src/schema.rs` holds the authoritative ordered list of 23 files. The
serving role needs `USAGE` on both schemas, DML on their tables, and advisory
locks (any role has them); new functions are `EXECUTE`-granted to `PUBLIC` by
default.

<Aside type="caution">
With `QUEEN_APPLY_SCHEMA=0` **you own matching the schema to the binary**: SQL
that expects a missing object fails at runtime, not at boot; the DDL is
always-virgin, it only creates. See [Upgrades](/selfhost/upgrade).
</Aside>

### `queen_streams` is granted to PUBLIC

`002_streams_schema.sql` ends with three grants:

```sql
GRANT USAGE ON SCHEMA queen_streams TO PUBLIC;
```

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON queen_streams.queries TO PUBLIC;
```

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON queen_streams.state TO PUBLIC;
```

Every role that can log into the database can read and write stream queries and
all stream state; nothing purges `queen_streams.state`, rows go away only on
re-register with reset, or drop. Plan around that if the database is shared.

## A direct connection is required

The broker must keep the same PostgreSQL backend for the life of a pooled
connection; a pooler in transaction or statement mode breaks it:

| Mechanism | What breaks behind a transaction- or statement-mode pooler |
| --- | --- |
| **Session-scoped advisory locks** | The boot-time schema apply holds `pg_advisory_lock(778120010)` across the whole DDL (`schema.sql` plus 23 procedure files, as 24 batches); the maintenance cycle holds `pg_advisory_lock(737001)` across many autocommitting step calls, which is how exactly one replica sweeps per cycle. Both locks live on a *session*: a pooler that hands the next statement to a different backend breaks the schema serialisation and the retention leader election. |
| **Server-side prepared statements** | The hot paths use `prepare_cached` (33 distinct statements), parsed and planned once per connection. Transaction-mode pooling invalidates the cache on every checkout, and every push, pop and ack pays a parse and plan. |

Session-mode pooling, a connection multiplexer rather than a statement
multiplexer, is transparent; give each broker its own backends.

## Connection pool sizing

`DB_POOL_SIZE` (default **160**) is the ceiling on concurrent PostgreSQL work
for one broker; the arithmetic is per cluster:

```text
replicas × DB_POOL_SIZE + superuser_reserved_connections + your own tooling ≤ max_connections
```

Three brokers at the default want 480 connections; a stock PostgreSQL allows
100. The mismatch answers `500` with `{"error":"pool"}` long before anything
looks like a query problem. The rig runs `max_connections=600` with
`DB_POOL_SIZE=300`; the harness `DB_POOL_SIZE=32`.

Also count: the retention cycle and the stats reconciler each hold one pooled
connection for a whole cycle, and a statement-timeout cancellation travels on
its own short-lived connection, briefly exceeding `DB_POOL_SIZE` under a
timeout storm.

## Statement timeout

`QUEEN_STMT_TIMEOUT_MS` (default 30000) is **broker-side**; the broker never
sets PostgreSQL's `statement_timeout`. On elapse it drops the broker-side
future, fires a best-effort cancellation on a fresh connection (the backend
otherwise keeps running and holding its locks), and **quarantines the pooled
connection**: closed and removed, never handed to the next caller.

For a hard server-side ceiling too, set `statement_timeout` on the broker's role
*above* `QUEEN_STMT_TIMEOUT_MS` so the broker's path runs first; a
PostgreSQL-side cancellation arrives as an ordinary statement error and returns
as a 500.

## Server settings that matter for this workload

The workload is append-heavy: a segment insert plus an allocator-row update per
push, a consumer-row update per pop and ack, and, with retention on, a matching
delete rate.

| Setting | Why it matters here |
| --- | --- |
| `max_connections` | See the sizing arithmetic above. This is the setting most likely to be wrong. |
| `shared_buffers` | The hot working set is the allocator and consumer rows plus the newest segments. Those rows are tiny and updated constantly; keeping them resident is what keeps the row-lock hold times short. |
| `synchronous_commit` | Every push is a commit. `on` is the durable choice and what the published runs used. Turning it `off` trades durability for commit rate; nothing in the broker compensates for the lost commits. |
| `commit_delay` / `commit_siblings` | Group commit. Because pushes arrive concurrently and are already coalesced broker-side, a small `commit_delay` lets one fsync carry more transactions. The benchmark rig used `commit_delay=200`, `commit_siblings=5`. |
| `max_wal_size`, `min_wal_size`, `checkpoint_timeout`, `checkpoint_completion_target` | A high sustained write rate will checkpoint constantly at stock settings. The benchmark rig used `max_wal_size=96GB`, `checkpoint_timeout=15min`, `checkpoint_completion_target=0.9`. |
| `wal_compression` | Segment blobs are already zstd-compressed by the broker, but the surrounding WAL traffic still benefits. |
| `autovacuum_naptime`, `autovacuum_max_workers`, `autovacuum_vacuum_cost_limit`, `autovacuum_vacuum_cost_delay` | The four tables the broker updates in place churn far faster than their live row counts suggest. The schema sets per-table parameters (below), but the cluster-level naptime and worker budget still gate how often those passes actually happen. |
| `effective_io_concurrency`, `random_page_cost` | Relevant on NVMe: the pop path reads segments by primary key, and a pessimistic `random_page_cost` pushes the planner off it. |

<Aside type="note">
Command-line settings outrank `ALTER SYSTEM`: a container started with
`-c synchronous_commit=on` cannot be changed by `ALTER SYSTEM` plus a reload;
check `pg_settings.source` when a setting refuses to change.
</Aside>

### The broker sets its own per-table parameters

The DDL re-applies these at every boot; they are why the tables look
over-vacuumed in `pg_stat_user_tables`.

| Table | Parameters | Reason |
| --- | --- | --- |
| `queen.log_partitions` | `fillfactor=70`, threshold-based autovacuum (`scale_factor=0`, `threshold=500`), `vacuum_truncate=off` | One allocator `UPDATE` lands on one row per push. Dead tuples dwarf the live row count between passes. |
| `queen.log_consumers` | `fillfactor=50`, same threshold-based autovacuum, `vacuum_truncate=off` | Every pop and every ack updates its row. |
| `queen.log_segments` | `blob` set to `STORAGE EXTERNAL`, insert-scale-factor autovacuum on both the heap and its TOAST table | The blob is already zstd-compressed, so TOAST compression would burn CPU for nothing. There are no secondary indexes: the primary key *is* the pop path. |
| `queen.log_txns` | insert-scale-factor autovacuum | Append-heavy at segment rate. |

**Do not re-enable `vacuum_truncate`** on the two small tables: heap truncation
takes an `ACCESS EXCLUSIVE` lock, freezing every push and pop to reclaim nothing
on tables holding roughly one row per partition and consumer group; diagnosed
off from a live run.

## What lives in the database

| Schema | Contents |
| --- | --- |
| `queen` | The five log-engine tables (`log_partitions`, `log_segments`, `log_txns`, `log_consumers`, `log_dlq`); `queen.queues`, the single table that is both queue identity and queue configuration (`log_partitions.queue_id` is a foreign key to it); traces, statistics and metrics tables. |
| `queen_streams` | The two stream tables above. |

That is the entire state: backup is `pg_dump`, restore `pg_restore`. The one
artefact outside a dump is the [node-local disk spool](/selfhost/durability);
its pending pushes are in no dump until they drain.
