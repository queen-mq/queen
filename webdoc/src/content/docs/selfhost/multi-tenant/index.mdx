The broker and the gateway in front of it are both Apache-2.0, so anyone can stand
up the same multi-tenant service in-house: for internal teams, for customers, or
for a product built on top. This section is the design of `proxy/`, read out of the
code, not a description of a commercial offering.

The whole service is one broker flag, one gateway process, and two SQL calls:

```bash
# the cell broker: native tenant scoping plus JWT, reachable only by the proxy
JWT_ENABLED=true JWT_ALGORITHM=HS256 JWT_SECRET="$CELL_JWT_SECRET" QUEEN_TENANCY_HEADER=true ./bin/queen

# the gateway in front of it
docker run -d --name queen-proxy -p 6711:6711 -e PXDB_HOST=10.0.3.20 -e PXDB_PASSWORD=change-me -e QUEEN_PROXY_JWT_SECRET="$SESSION_SECRET" -v queen-proxy-spool:/app/spool ghcr.io/queen-mq/queen-proxy:latest
```

```sql
-- register the cell, then onboard a tenant with a cluster, an admin and an API key
INSERT INTO queen_proxy.cells (slug, region, base_url, class, cell_secret)
VALUES ('eu1-shared-a', 'eu1', 'http://10.0.3.11:6632', 'shared', :'cell_secret');

SELECT queen_proxy.bootstrap_tenant(
  'acme', 'Acme Inc', 'acme-prod', 'free',
  (SELECT id FROM queen_proxy.cells WHERE slug = 'eu1-shared-a'),
  'ops@acme.example', 'initial-password', 'default');
```

[Deploying queen_proxy](/selfhost/multi-tenant/proxy) walks the first two commands,
including how `$CELL_SECRET` is minted;
[Tenants, clusters and cells](/selfhost/multi-tenant/tenants) walks the SQL.

## Three nouns

| Term | What it is | Where it lives |
| --- | --- | --- |
| **Tenant** | The organisation. Owns users and clusters, carries a lifecycle status, is what a bill would be addressed to | `queen_proxy.tenants` |
| **Cluster** | The tenant-visible Queen: one hostname, one plan, one set of quotas, one queue namespace | `queen_proxy.clusters` |
| **Cell** | One physical stack (a broker, its PostgreSQL, and a proxy) on one failure domain | `queen_proxy.cells` |

Users belong to a tenant; permissions are granted per cluster
(`queen_proxy.cluster_roles`), so one person can be admin on one cluster and a
viewer on another. A tenant may own many clusters (production, staging, one per
region), each a separate namespace and quota bundle.

## Cluster to cell

<pre class="mermaid">{`
flowchart LR
  T1["tenant acme"] --> C1["cluster acme-prod"]
  T1 --> C2["cluster acme-staging"]
  T2["tenant globex"] --> C3["cluster globex"]
  C1 --> S1["cell eu1-shared-a<br/>one proxy, one broker, one PostgreSQL"]
  C2 --> S1
  C3 --> S2["cell eu1-ded-7<br/>one proxy, one broker, one PostgreSQL<br/>dedicated: nothing else on it"]
`}</pre>

A cluster names a single cell and never spans two: **N:1 on shared cells, 1:1 on
dedicated ones**. The pairing is a placement decision made by whoever runs the
fleet, with no database constraint behind it;
[placement is manual today](/selfhost/multi-tenant/tenants#placement-is-manual-and-draining-does-not-exist).

Each cluster carries a `broker_tenant_uuid`, generated at creation. That UUID, not
the tenant id, is what the proxy injects upstream as `x-queen-tenant`, and it is
what scopes queue identity inside the broker.

## One cluster lives on exactly one cell

This is the structural decision the enforcement model rests on: a cluster's
traffic can only arrive at the one proxy that fronts its cell, so every limit is
plain in-process state, exact by construction.

| Limit | Why it is exact |
| --- | --- |
| Rate limits | Request and message token buckets, sharded 16 ways by cluster id. No Redis, no gossip, no coordination latency |
| Parked-consumer slots | An RAII guard held across the upstream await; a per-cluster atomic plus a cell-wide one |
| Queue and partition caps | The proxy remembers every `(queue, partition)` pair it admitted, so the common case is a set lookup |
| Usage | Aggregated locally and flushed per minute, never counted twice and reconciled |

The counters are process-local, so a proxy restart resets them;
[Quotas and rate limits](/selfhost/multi-tenant/quotas) covers how each one refills
and re-blocks. **Running two proxies in front of one cell breaks the exactness: one
proxy per cell is the assumption the code is written against.**

## Routing is a DNS label

The proxy resolves the cluster from the **first label of the `Host` header**:

```text
Host: acme-prod.eu1.example.com       →  slug "acme-prod"
Host: Acme-Prod.eu1.example.com:6711  →  slug "acme-prod"

clusters.slug ~ ^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$   (globally unique)
```

The label is lowercased and a numeric port stripped; the slug is validated as the
DNS label it literally is. A label matching no cluster answers `421` with
`{"code":"cluster_unknown"}`: the request reached the wrong endpoint, not a missing
thing. The dashboard is the one hostname shared by every cluster, so it names its
cluster with the explicit `x-queen-act-cluster` header instead, honoured for a
human session and refused for an API key;
[Credentials and authorization](/selfhost/multi-tenant/auth) has the matrix.

## What a request goes through

The order is load-bearing, and it is the order in the gateway:

<Steps>

1. **Resolve the cluster** from `Host`, or from `x-queen-act-cluster` when a
   session named one. A miss is `421`.

2. **Status gate.** Suspended or deleting is `403 cluster_suspended`; produce on a
   push-blocked cluster is `403` with the code naming the cause.

3. **Classify the route, gate features.** An unknown API-shaped path is `404`; a
   plan without the feature is `403 feature_gated`.

4. **Authenticate and authorize.** An API key resolves to a cluster and scopes; a
   session resolves to a per-cluster role.

5. **Limits.** The request bucket always; for produce the size caps, admission and
   message bucket; for a long-poll pop a parked slot held across the upstream call.

6. **Forward.** Rebuild the URI on the cell's base URL, swap the client's
   `Authorization` for the cell secret, inject `x-queen-tenant` and a request id.

7. **Meter the response** from the per-item statuses it actually returned.

</Steps>

## What the proxy is not

- **Not a control plane.** Every mutation of tenants, clusters, users, keys, plans
  and roles is a SQL function in the `queen_proxy` schema; no HTTP endpoint
  creates a tenant.
- **Not a billing console.** It has a cluster console (usage, keys, members) and
  nothing about invoices or payment.
- **Not a second broker.** It parses request bodies to count and cap them and
  never rewrites one.
- **Not an isolation layer bolted onto an open broker.** The broker scopes tenants
  natively; the proxy makes the header that drives it trustworthy.
  [Isolation](/selfhost/multi-tenant/isolation) draws the line precisely.

## The pieces

| File in `proxy/` | Responsibility |
| --- | --- |
| `src/main.rs` | Listener, optional TLS, the background pumps, graceful shutdown |
| `src/cache.rs` | Host → cluster and API-key-hash → cluster, with `LISTEN` invalidation |
| `src/gateway.rs` | The request pipeline above |
| `src/routes.rs` | Route classification: the enforcement spec |
| `src/auth.rs` | Credential verification, JWT mint and verify, the authorization matrix |
| `src/limits.rs` | Token buckets, parked-slot gauges, push-block flags |
| `src/registry.rs` | Queue/partition admission and the per-cell inventory reconciler |
| `src/meter.rs` | Usage aggregation, the daily roll-up, the monthly quota chain |
| `src/spool.rs` | Disk spool for usage rows when the proxy database is unreachable |
| `src/console.rs` | Cluster console API and its embedded SPA |
| `src/oauth.rs` | Local login, Google and GitHub, session cookies |
| `migrations/` | The `queen_proxy` schema and its control-plane SQL functions |
