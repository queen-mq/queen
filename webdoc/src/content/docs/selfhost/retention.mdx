Retention is **opt-in per queue**: a fresh queue keeps everything forever, no
amount of consuming changes that, and until you enable it the only thing the
maintenance loop touches is the deduplication hash sidecar. The default is
deliberate, because losing data quietly is worse than filling a disk visibly.

A seven-day hard cap with one day of consumed history:

```bash
curl -s -X POST http://localhost:6632/api/v1/configure -H 'Content-Type: application/json' -d '{"queue":"orders","options":{"retentionEnabled":true,"retentionSeconds":604800,"completedRetentionSeconds":86400}}'
```

**`/configure` is a [full replace](/reference/queue-options), so a later call
that sets one unrelated option and omits these keys silently turns retention
back off.** Always send the queue's complete option set; the full field list is
in [queue options](/reference/queue-options).

## The two rules

| Rule | Deletes | Boundary |
| --- | --- | --- |
| `retentionSeconds` | segments older than the cutoff **regardless of consumption state**. This is the one rule that can lose messages nobody ever read | `now() - retentionSeconds` |
| `completedRetentionSeconds` | only data that has been consumed. A partition with **no** consumer rows has consumed nothing, so this rule contributes nothing there and old-but-unread segments survive; and one stalled consumer group pins the whole partition's history for every group | capped at `MIN(committed) + 1` across every consumer group on the partition: the slowest group's next wanted offset |
| Granularity (both rules) | **whole segment rows**, and only ones lying entirely below the boundary: a boundary mid-segment leaves the covering segment in place, consumed head included | disk is reclaimed in segment-sized steps, so heavy producer batching means lumpier steps and an on-disk footprint that lags the logical window |

Both rules require `retentionEnabled` to be true *and* the corresponding window
to be positive. A queue with `retentionEnabled: true` and no windows set is
swept by nothing.

## The cadence

| Property | How it works |
| --- | --- |
| Cycle | every `RETENTION_INTERVAL` ms (default **5000**, not the five minutes an older generation of this system used) |
| Leader | session advisory lock `737001` elects one sweeper per cycle, so replicas never double-delete; released on every exit path |
| Transactions | **none wrapping**: every step autocommits and holds exactly one `queen.log_partitions` row lock (the push allocator's serializer) for at most `RETENTION_BATCH_SIZE` rows (default 1000), so pushes interleave with the sweep and steps cannot deadlock against multi-partition writers |
| Rate | scales with `RETENTION_PARALLELISM` (default **1**, clamped to 16) and nothing else: workers pull partitions off a shared cursor, each holding one maintenance-lane admission slot, so raise `QUEEN_ADMISSION_SHARE_MAINT` along with it. A larger `RETENTION_BATCH_SIZE` is not an alternative: step cost is per row, so a bigger batch absorbs no more rows per second and only lengthens the row lock the push allocator waits on |

The full walk through the loop is in
[Retention internals](/internals/retention). The phases per cycle:

| Phase | Applies to | Cutoff |
| --- | --- | --- |
| Retention | partitions of queues with at least one enabled rule | `retentionSeconds` and `completedRetentionSeconds` |
| Hash-sidecar purge | **every** log partition, always | `GREATEST(dedupWindowSeconds, completedRetentionSeconds, 900s)` |
| Age eviction | queues with `maxWaitTimeSeconds > 0` | `maxWaitTimeSeconds` |

The middle phase is why the loop touches every partition even with retention off
everywhere: `queen.log_txns` is written for every push whether deduplication is
on or not, because ack resolution depends on it, and its 900-second floor means
a hash is never dropped while a plausible late ack could still need it. A hash
that outlives the window resolves as unknown on ack, which counts as *not*
acked: redelivery over loss, the engine's standing bias.

## maxWaitTimeSeconds deletes unconsumed data, for every group, including leased batches

**This option deletes whole segments older than `now() - maxWaitTimeSeconds` for
every consumer group, in-flight leases included, regardless of
`retentionEnabled`.** The stored procedure calls it data loss by design. It does
not dead-letter, records nothing against a consumer group, and tells no client;
a cursor left below the new watermark resumes at the next offset that still
exists. Use it only where a stale message is worthless (a live price tick, a
presence update); an age limit *with* an audit trail is not this option. Details
in [queue options](/reference/queue-options#maxwaittimeseconds).

## The metrics purge

The fourth phase of every cycle trims the observability tables on
`METRICS_RETENTION_DAYS` (default **90**): one stored procedure ages out
`queen.worker_metrics`, `queen.queue_lag_metrics`, `queen.queue_parked_replica`
and `queen.retention_history`, and a batched delete trims
`queen.system_metrics` in `RETENTION_BATCH_SIZE` chunks. A failure here is
logged and swallowed: it cannot poison the segment deletes, which have already
committed statement by statement.

## Two growth surfaces nothing reclaims

<Aside type="danger">
**Retention never touches `queen.log_dlq`: dead letters accumulate forever,
payload included**, and the only removal is
`DELETE /api/v1/messages/:partitionId/:transactionId`.
</Aside>

The second is stream state: `queen_streams.state` holds one row per (query,
partition, key), nothing purges it, and it is dropped only when an application
resets its query, so a high-cardinality key space in a streaming query is
permanent storage. The `queen_streams` tables are also granted to `PUBLIC`, so
anything holding a broker database credential can read and write them.

Partitions are the one thing in this family that *is* reclaimed: a
`queen.log_partitions` row is deleted once empty and idle for
`PARTITION_CLEANUP_DAYS` (30), on a batched phase that runs at most once a
minute and stays serial under `RETENTION_PARALLELISM`. "Empty" excludes
dead-letter rows and streaming state, so a DLQ row pins its partition in place
too. `QUEEN_PARTITION_CLEANUP_ENABLED=false` restores the older keep-forever
behaviour; mechanics in
[Retention internals](/internals/retention#empty-partition-cleanup).

## Watching disk growth

The `retention` target logs a line only when a cycle actually deleted something:

```text
INFO retention  swept queues=12 segments_deleted=340 txns_purged=340 max_wait_evicted=0 partitions_deleted=0 metrics_purge=… elapsed_ms=47
```

An idle cycle is DEBUG, so silence at `info` means "nothing to delete", the
thing to be suspicious about on a growing deployment; large `segments_deleted`
with a growing `elapsed_ms` means the sweep is running behind ingest.

Then measure the tables. `GET /api/v1/analytics/postgres-stats` returns
per-table total, table and index sizes, but only for the **`queen`** schema and
only the 20 largest relations; `queen_streams` growth does not appear there, so
query it yourself:

```sql
SELECT pg_size_pretty(pg_total_relation_size('queen_streams.state'));
```

The four relations that dominate a busy deployment are `queen.log_segments` (and
its TOAST table, holding the compressed payloads), `queen.log_txns`,
`queen.log_dlq`, and `queen.system_metrics` if the metrics purge has been
disabled by a very large `METRICS_RETENTION_DAYS`.

`GET /api/v1/analytics/retention` aggregates `queen.retention_history` (the
audit row each deleting step writes) into a time series of eviction volume per
rule; its `messagesDeleted` figures are frame counts, not segment-row counts,
and the table itself ages out on the metrics window.

<Aside type="note">
The boot-time schema applies measured autovacuum settings to the hot tables,
including `vacuum_truncate = off` on `queen.log_partitions` and
`queen.log_consumers` (heap truncation takes an `ACCESS EXCLUSIVE` lock that
stalls every push and pop while reclaiming nothing): do not override them
per-table without re-reading the schema comments.
</Aside>
