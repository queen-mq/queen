When PostgreSQL is unreachable a push does not have to fail: it lands in an
on-disk spool, comes back `buffered`, and replays when the database returns.
Check the spool at any time:

```bash
curl -s http://localhost:6632/api/v1/status/buffers
```

The reply carries a live database ping plus the in-process gauges, present even
when the database-backed part of a Prometheus scrape is missing:

| Surface | What it tells you |
| --- | --- |
| `queen_file_buffer_db_healthy` | 0 while the broker believes PostgreSQL is unreachable |
| `queen_file_buffer_pending` | events written and not yet replayed |
| `queen_file_buffer_failed` | spool *write* failures: accepted-then-lost work |
| `GET /api/v1/system/maintenance` | adds `bufferedMessages` plus a `bufferStats` block: finalized-file count and bytes on disk |
| The log | enter/leave transitions once each on the `spool` target; `spool_pending` and `spool_healthy` in the periodic `sizes` block |

## What the spool is

An append-only directory of event files:

| Property | Value |
| --- | --- |
| Location | `FILE_BUFFER_DIR`, default `/var/lib/queen/buffers` |
| Record | a little-endian `u32` length + a JSON body: queue, partition, resolved tenant, original `transactionId`, authenticated producer subject, an `encrypted` flag, the payload verbatim |
| Files | active `*.tmp`, finalized drainable `*.buf`; names embed a 13-digit epoch-millisecond stamp and an 8-digit sequence, so a lexical sort is FIFO order |
| Rotation | after `FILE_BUFFER_EVENTS_PER_FILE` events (10000 by default) |
| Fallback | a directory that cannot be created logs a `spool` warning and falls back to a per-user temporary directory |
| Production | set `FILE_BUFFER_DIR` explicitly and confirm it in the `config: file_buffer` boot line |

<Aside type="caution">
Records are buffered appends under a mutex, **no per-event fsync**: a crash or
power loss can lose the tail of the active file. The reader stops at the first
incomplete record, so the cost is that truncated tail, not the whole file: a
small crash window traded for a push path that never blocks on disk.
</Aside>

## How a push becomes buffered

<pre class="mermaid">{`
flowchart TB
  P["POST /api/v1/push"] --> MM{"maintenance mode"}
  MM -->|"off"| T{"push transaction"}
  MM -->|"on"| SP{"append to the spool<br/>FILE_BUFFER_DIR"}
  T -->|"committed"| Q["status: queued"]
  T -->|"PostgreSQL unreachable"| SP
  SP -->|"write ok"| BUF["status: buffered"]
  SP -->|"write fails"| FA["status: failed, the item is lost"]
  BUF --> DR["drain cycle every 100 ms,<br/>oldest .buf file first"]
  DR --> RP["replay keeps the original transactionId"]
  RP --> DUP["stored, or duplicate if it already committed"]
`}</pre>

The first is failure: a push whose transaction failed (connection error,
statement timeout, pool exhaustion) is counted as a database error and spooled.
A successful spool write relabels it `buffered`; a failed one makes it `failed`,
genuinely lost. In-request duplicates inherit its status. The response is still
`201`: **the per-item `status` field is the contract**.

```json
[
  {"messageId":"0198…","transactionId":"order-4471","queue":"orders","status":"buffered"},
  {"messageId":"0198…","transactionId":"order-4472","queue":"orders","status":"failed"}
]
```

The other is [maintenance mode](#maintenance-mode-is-the-deliberate-diversion),
below. The spool covers pushes only: `POST /api/v1/transaction` is
all-or-nothing against PostgreSQL and fails during an outage; pops and acks
error, safely: an unacked lease redelivers.

## Replay, and why it is idempotent

Each cycle finalizes the active file and replays `.buf` files oldest first; no
file ever becomes one giant transaction.

| Knob | Role |
| --- | --- |
| `FILE_BUFFER_FLUSH_MS` (100 ms) | drain cadence |
| Files per cycle | up to 10 while the database looks healthy, 1 while it does not |
| `FILE_BUFFER_MAX_BATCH` (100 events) | one multi-segment transaction per batch, grouped by (tenant, queue, partition) |

Idempotence comes from deduplication, not bookkeeping: replay keeps each event's
original `transactionId`, mints fresh message ids, and declines to vouch for the
in-memory dedup cache, so the SQL probe checks the full window. An
already-committed batch comes back `status: "duplicate"` and writes nothing.

<Aside type="caution">
The guarantee is exactly as wide as the deduplication window. With
`dedupWindowSeconds: 0` replay is **not** idempotent: a partially committed
drain attempt duplicates. And the hash sidecar is purged at
`GREATEST(dedupWindowSeconds, completedRetentionSeconds, 900s)`, so a longer
outage can outlive the evidence a replay needs.
</Aside>

## Failure handling inside the drain

Drain errors are classified; the two kinds need opposite responses.

| Class | What counts | Response |
| --- | --- | --- |
| **Transient** | a connection-level failure with no SQLSTATE; `40001` (serialization failure), `40P01` (deadlock); SQLSTATE classes `08`, `53`, `57`, `58` | The file stays exactly where it is, the broker marks the database unhealthy, and the cycle stops so the head of the FIFO retries next tick. After 10 consecutive failures a circuit breaker holds the loop off for 5 seconds. Good spool is never discarded during an outage. |
| **Permanent** | any other server-side SQL error (bad data, a constraint, a custom `RAISE`); a spool file that cannot be read | The same data would fail every retry and block everything behind it. After 5 attempts on the same head file (each logged as `ERROR` on `spool` with `attempt` and `max_attempts`) it moves to `<FILE_BUFFER_DIR>/failed/` and the cycle carries on. If the rename fails the file is deleted: data that can never be stored must not freeze the queue behind it. |

**A non-empty `failed/` directory is an alert.** Drain listings filter on
`.buf`/`.tmp` and do not recurse: nothing picks those files up, and those
messages were accepted and will never be stored.

## Startup recovery

Before the listener binds, the broker finalizes any `.tmp` left by a crash and
replays every `.buf` in FIFO order, bounded at one hour; past the cap, or on a
file failure (which also marks the database unhealthy), the rest goes to the
background drain. A large spool means a slow start, and a spool is recovered
only by a process booting with the same `FILE_BUFFER_DIR`: see
[Probes and restarts](/selfhost/probes-restarts).

## Maintenance mode is the deliberate diversion

```bash
curl -s -X POST http://localhost:6632/api/v1/system/maintenance -H 'Content-Type: application/json' -d '{"enabled": true}'
```

This diverts **every** push to the spool before it touches PostgreSQL and pauses
the drain: the tool for a planned failover, `VACUUM FULL` or version upgrade,
when producers must keep succeeding while writes are impossible. Items come back
`buffered` with `201`; a failed spool write makes the response `500`. Disabling
force-finalizes the active file and resumes the drain, which replays everything.

What it does not do:

- **Pause consumers**: pop maintenance is a separate flag,
  `POST /api/v1/system/maintenance/pop`; pops keep serving stored messages.
- **Divert transactions**: `POST /api/v1/transaction` still writes straight to
  PostgreSQL and fails if it is down.
- **Scope to a tenant**: both flags are cell-wide.

The flag is mirrored into `queen.system_state` (it **survives a restart**) and
broadcast to peers. Left on by accident it grows an unbounded spool:
`queen_maintenance_mode_enabled` is worth an alert.

## The limits

The spool is node-local, unreplicated, and unencrypted beyond what the queue
already asked for: losing the node loses its spool.

- A spool is drained only by the instance that wrote it; behind a load balancer,
  buffered messages scatter across whichever instances accepted them.
- Give `FILE_BUFFER_DIR` storage that outlives the container and keep the pod on
  that node; an ephemeral filesystem takes the spool with it.
- A queue with `encryptionEnabled` spools the stored AES-256-GCM envelope,
  still flagged encrypted on replay; every other payload is plaintext JSON on
  disk. A malformed `QUEEN_ENCRYPTION_KEY` that
  [silently disabled encryption at boot](/selfhost/security/encryption#a-bad-key-silently-stores-plaintext)
  leaves plaintext for flagged queues too.
- **No size cap, no maximum age**: a long outage grows the spool until the
  filesystem fills, spool writes fail, and pushes report `failed`. Monitor free
  space alongside `queen_file_buffer_pending`.
