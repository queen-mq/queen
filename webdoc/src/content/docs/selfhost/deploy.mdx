Two ways to get a broker: run the published container, or build the binary. Both
end at one process holding a connection pool to PostgreSQL, schema and dashboard
inside. The broker applies its schema at every boot; the only ordering
requirement is a reachable PostgreSQL, otherwise boot fails loudly rather than
starting half-working.

## Run the published image

The image is `ghcr.io/queen-mq/queen`: runtime `ubuntu:24.04`, workdir `/app`,
command `./bin/queen`.

<Steps>

1. **Give the broker a network and a PostgreSQL.** Any reachable PostgreSQL
   works; harness and rigs use `postgres:16`.

   ```bash
   docker network create queen
   ```

   ```bash
   docker run -d --name queen-pg --network queen -e POSTGRES_PASSWORD=postgres postgres:16
   ```

2. **Start the broker.** `PG_USER` and `PG_DATABASE` default to `postgres`; a
   minimal run needs only host, port and password.

   ```bash
   docker run -d --name queen --network queen -p 6632:6632 -e PG_HOST=queen-pg -e PG_PORT=5432 -e PG_PASSWORD=postgres ghcr.io/queen-mq/queen:latest
   ```

3. **Give the disk spool a real home.** The
   [node-local spool](/selfhost/durability) at `FILE_BUFFER_DIR` (default
   `/var/lib/queen/buffers`) is replayed only from the same directory, so mount
   it.

   ```bash
   docker run -d --name queen --network queen -p 6632:6632 -e PG_HOST=queen-pg -e PG_PASSWORD=postgres -v queen-spool:/var/lib/queen/buffers ghcr.io/queen-mq/queen:latest
   ```

</Steps>

### The environment variables that matter

A deployment sets variables from this list; the full table is generated in the
[configuration reference](/reference/config/).

| Variable | Default | Why you would set it |
| --- | --- | --- |
| `PG_HOST` | `localhost` | Always, in a container. |
| `PG_PORT` | `5432` | Non-standard port or a pooler's port. |
| `PG_USER` | `postgres` | A dedicated role. |
| `PG_PASSWORD` | `postgres` | Always. |
| `PG_DATABASE` | `postgres` | A dedicated database. Resolves `PG_DATABASE`, then the legacy `PG_DB`, then `postgres`. |
| `DB_POOL_SIZE` | `160` | Must fit inside `max_connections` across **all** replicas: see [pool sizing](/selfhost/postgres#connection-pool-sizing). |
| `PORT` | `6632` | A different HTTP port. |
| `QUEEN_APPLY_SCHEMA` | `true` | Set `0` to run as a low-privilege role against a pre-applied schema. |
| `FILE_BUFFER_DIR` | `/var/lib/queen/buffers` | Point it at a writable, persistent path. |
| `QUEEN_STMT_TIMEOUT_MS` | `30000` | Bound how long a single statement may run before the broker abandons and cancels it. |
| `PG_USE_SSL` | `false` | A managed PostgreSQL that requires TLS. |
| `JWT_ENABLED` | `false` | Turn authentication on. Off means every route is open. |
| `QUEEN_MESH_PEERS` | unset | Running more than one replica. |
| `QUEEN_SYNC_SECRET` | unset | Always, when the mesh is on. |
| `LOG_LEVEL` | `info` | Accepts full `EnvFilter` syntax, e.g. `info,queen::pop=debug`. `RUST_LOG` overrides it. |

<Aside type="caution">
Booleans are strict: `true/false`, `1/0`, `yes/no`, `on/off`, case-insensitive;
unset or empty means the default; **anything else is a fatal boot error**. See
[Configuration](/selfhost/configuration).
</Aside>

### Ports

| Port | Protocol | Exposed by the image | Purpose |
| --- | --- | --- | --- |
| 6632 | HTTP | Yes (`EXPOSE 6632`) | The API and the dashboard. `PORT` changes it. |
| 6633 | Framed TCP | No | The inter-replica mesh. `QUEEN_MESH_PORT` changes it ([legacy alias](/selfhost/configuration#names-with-a-history)). |

A single broker with no peers never binds the mesh port, so the image does not
publish it; replicas need it reachable between them and
[from nowhere else](/selfhost/ha#the-mesh-port-must-be-firewalled).

### What else is inside the image

```bash
docker exec -it queen queenctl status
```

| Extra | Why it is there |
| --- | --- |
| `queenctl` at `/usr/local/bin/queenctl`, a static Go binary from `clients/client-cli` | The operator CLI. `QUEEN_SERVER=http://localhost:6632` is pre-set, so the command above needs no flags. |
| PostgreSQL 18 client tools from PGDG: `psql`, `pg_dump`, `pg_restore` | The whole state is in PostgreSQL, so backup and restore travel with the image. |
| `/app/webapp/dist`, the dashboard bytes the binary already embeds | Inspection only: the binary does **not** read them, and [`QUEEN_STATIC_DIR` configures nothing](/selfhost/configuration). |

## Build from source

The root `Dockerfile` builds four stages (Vue dashboard, Rust broker,
`queenctl`, runtime); BuildKit is required for the cache mounts:

```bash
DOCKER_BUILDKIT=1 docker build -t queen-mq .
```

`build.sh` is the publish path for both images:

```bash
./build.sh all --push --multiarch --latest
```

It defaults to `ghcr.io/queen-mq` (`--registry` / `$QUEEN_REGISTRY`): `queen`
from the root `Dockerfile`, `queen-proxy` from `proxy/Dockerfile`. `--multiarch`
implies `--push` and needs a `docker-container` buildx builder, checked up
front; without it the image is host-architecture, loaded locally.
`server/server.json` is the single source of truth for the broker's tag,
`/health` and `queenctl version` (`build.rs` embeds it as `QUEEN_VERSION`,
`build.sh` passes it as `QUEENCTL_VERSION`); the proxy tags from
`proxy/Cargo.toml`.

The binary alone:

```bash
cargo build --release --manifest-path server/Cargo.toml
```

The result is `server/target/release/queen`. Two build-time couplings:

<Aside type="caution">
**The dashboard is a compile-time dependency.**
`server/src/handlers/static_files.rs` embeds `webapp/dist` with `rust_embed` and
hard-errors when the folder is missing; `app/vite.config.js` writes exactly
there, so build the frontend first:

```bash
npm --prefix app ci
```

```bash
npm --prefix app run build
```
</Aside>

<Aside type="caution">
**The SQL is compiled in.** `server/src/schema.rs` embeds `sql/schema.sql` and
the 23 procedure files with `include_str!`: editing a `.sql` file changes
nothing until you rebuild; a running broker keeps applying the old text at every
boot.
</Aside>

`server/Dockerfile` builds a broker-only image (`debian:bookworm-slim`): the
binary, `PORT=6632`, no `queenctl`, no client tools.

## Verify it actually works

`/health` proves the broker can reach PostgreSQL, not that a message can be
stored and delivered. Run all four steps; the last catches a broker that accepts
writes but cannot serve them.

<Steps>

1. **Health.** A 200 means broker *and* PostgreSQL both work: the handler runs a
   [real database query](/selfhost/probes-restarts#what-health-tests), not a
   static answer.

   ```bash
   curl -s http://localhost:6632/health
   ```

   ```json
   {"status":"healthy","database":"connected","engine":"segments-rust","version":"1.0.0"}
   ```

   Unreachable PostgreSQL yields HTTP 503 and
   `{"status":"unhealthy","database":"disconnected",…}`.

2. **Read the boot log.** The broker prints what it actually resolved, secrets
   masked: `applied schema.sql + procedures` on the `schema` target, one
   `config:` block per subsystem, then `listening`. A setting that seems ignored
   shows here [as the broker understood it](/selfhost/configuration).

   ```bash
   docker logs queen 2>&1 | grep -E 'schema|config:|listening'
   ```

3. **Push a message.** The first push that names a queue and a partition creates
   them.

   ```bash
   curl -s -X POST http://localhost:6632/api/v1/push -H 'Content-Type: application/json' -d '{"items":[{"queue":"deploy-check","partition":"p1","payload":{"hello":"world"}}]}'
   ```

   One result per item; `status: queued` means stored.

4. **Pop it, and pop again.** `autoAck=true` commits the consumer cursor inside
   the pop transaction, so the second call proves the cursor advanced.

   ```bash
   curl -s 'http://localhost:6632/api/v1/pop/queue/deploy-check?batch=10&autoAck=true'
   ```

   ```bash
   curl -si 'http://localhost:6632/api/v1/pop/queue/deploy-check?batch=10&autoAck=true'
   ```

   The second call must answer **`HTTP/1.1 204 No Content`** with no body: this
   broker's 204 never carries one (a content-length on an elided body poisoned
   Node and undici connections).

</Steps>

If step 4 keeps returning the same message, the ack path is broken. A 204 on
the *first* call may be pop maintenance: a paused pop path answers the same
bodiless 204; `GET /api/v1/system/maintenance/pop` reports the flag.

<Aside type="note">
With auth off the dashboard boots into a standalone operator identity; with
`JWT_ENABLED=true` it is deliberately unavailable broker-direct and
`/auth/login` explains why. See [the dashboard page](/selfhost/dashboard).
</Aside>

## Compose, for a two-broker stack

The harness's `test/compose/docker-compose.ha.yml` works as-is: one PostgreSQL,
two brokers with distinct `QUEEN_SERVER_ID`, one shared `QUEEN_SYNC_SECRET`,
`QUEEN_MESH_PEERS` pointing at each other, and a separate `FILE_BUFFER_DIR` per
broker, load-bearing: the [spool is node-local](/selfhost/durability) and must
never be shared.
