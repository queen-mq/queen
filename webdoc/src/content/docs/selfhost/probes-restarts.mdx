The broker is one stateless process; all durable state is in PostgreSQL except
the node-local push spool, the exception that makes probe configuration matter.

## What /health tests

```bash
curl -s http://localhost:6632/health
```

```json
{"status":"healthy","database":"connected","engine":"segments-rust","version":"1.0.0"}
```

`GET /health` takes a pooled connection and runs a trivial query; it answers
503 with `"status":"unhealthy","database":"disconnected"` when the pool cannot
hand out a connection or the query fails. A **dependency** check, not a process
check: the readiness question, and the wrong liveness question. The route is
`public` and the auth middleware short-circuits before token lookup:
`JWT_ENABLED` does not close it.

## The liveness-probe trap

<Aside type="danger">
Wiring `/health` to a Kubernetes liveness probe defeats the disk spool it
exists to complement: during a PostgreSQL outage the broker is *working as
designed*, returning 503 while accepting pushes into the spool, and the probe
reads that 503 as a dead container and kills the pod, in a loop, for the whole
outage.
</Aside>

The damage compounds: each kill discards in-flight requests, so pushes that
would have spooled are refused at the socket, and nothing drains while the
container restarts. A spool on the container filesystem
[is destroyed outright](/selfhost/durability#the-limits): a survivable outage
becomes data loss.

Use `/health` for **readiness**: an instance that cannot reach PostgreSQL
should leave the load balancer. For **liveness**, probe the process: a TCP
connect on `PORT` is the honest test (the listener exists only while the
process lives; a panic aborts instead of limping), and the
[Kubernetes manifest](/selfhost/kubernetes) has both stanzas.
[`GET /status`](/reference/http/status-metrics) skips the database but is
read-only access, not public: under JWT it needs a token, awkward for a probe.

## SIGTERM drains, background loops do not

On SIGTERM (or Ctrl-C) the broker logs

```text
INFO shutdown  signal received, draining in-flight requests
```

then stops accepting, waits for in-flight requests, reports the spool depth
and exits:

```text
WARN  shutdown  spool has undrained events at shutdown pending=<n>
INFO  shutdown  shutdown complete
```

A parked long-poll pop is an in-flight request, open until its own deadline
(`POP_DEFAULT_TIMEOUT_MS`, default 30000 ms; `DEFAULT_TIMEOUT` takes
precedence), so shutdown can take that long even idle: size the termination
grace period above your largest pop timeout, or the orchestrator SIGKILLs a
correct shutdown. Parked pops release their pooled connection *before*
parking, holding a slot only while querying.

The background loops (retention, stats, metrics, spool drain) are detached
tasks and stop with the runtime: **the spool is not flushed on the way out**.
`pending=<n>` means events on disk, replayed only by a process starting with
the same `FILE_BUFFER_DIR`: drain the spool before permanently retiring the
volume.

## What happens to in-flight leases

Nothing is handed back: consumption state is one cursor per (partition,
consumer group), `queen.log_consumers.committed`. A pop leases
`(committed, batch_end]` by writing `worker_id`, `batch_end`,
`lease_acquired_at`, `lease_expires_at` onto that row. A lease is a row, not a
session: no release-on-disconnect path exists anywhere in the engine.

<Steps>

1. The instance dies; the request fails; nothing was acked, so `committed` is
   unchanged.

2. Until `lease_expires_at` passes, the lease predicate filters that
   (partition, group) out of every pop: the batch is invisible, lag grows.

3. On expiry, the next pop re-leases from the same `committed`: the whole span
   redelivers, to whoever asks first, on any instance.

</Steps>

Lease time is your restart recovery window: a 300-second lease stalls its
partitions up to 300 seconds; shorter redelivers faster, too short redelivers
work still in progress. Tune that, not the restart.

Expiry redelivery does not consume the retry budget: `attempt_count`
increments on a re-lease from the same start offset (redelivery telemetry);
`batch_retry_count` is charged **only** by an explicit `failed` ack, so a
restart cannot push a message toward the DLQ.

`autoAck=true` pops commit inside the pop transaction, no lease: a restart
cannot redeliver them, and anything the client had not processed is gone, the
at-most-once trade you asked for.

## Rolling restarts

Every boot re-applies the embedded schema
[under a session advisory lock](/selfhost/upgrade#what-happens-at-boot):
concurrent boots serialise, re-application is idempotent, a DDL error fails the
boot (`FATAL: schema apply failed`, exit 1) rather than serving a half-applied
schema. Three things to get right:

- **Drain before terminating**: readiness out of the balancer, SIGTERM, the
  grace period. A SIGKILL mid-request is survivable (unacked batches
  redeliver) but strands the spool.
- **Restart one instance at a time when spools may be non-empty**:
  [startup recovery](/selfhost/durability#startup-recovery) replays the spool
  *before* the listener binds, so start time grows with the spool.
- **Keep `FILE_BUFFER_DIR` on storage that outlives the container**: the spool
  only counts if the next process on the node can see it.

Pre-applying the DDL with a privileged role? Set `QUEEN_APPLY_SCHEMA=0`: boot
logs `apply skipped`, touches no catalog, and the definitions serving requests
are the ones you applied.
