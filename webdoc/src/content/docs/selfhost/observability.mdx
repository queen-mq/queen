A broker publishes what it is doing through exactly three surfaces: structured
logs on stdout, `GET /metrics` (a small JSON object), and
`GET /metrics/prometheus` (exposition text). The logs carry rates, latencies and
cache sizes that Prometheus does not; Prometheus carries database-backed cluster
totals that the logs do not.

```bash
curl -s http://localhost:6632/metrics/prometheus   # exposition text, the scrape target
curl -s http://localhost:6632/metrics              # JSON, for a quick check by hand
```

<Aside type="danger">
**Per-queue Prometheus series sum across tenants, and broker authentication does
not apply to the endpoint: `/metrics/prometheus` is a cell-wide operator
surface, never one to expose to a tenant.** See
[the Prometheus reference](/reference/prometheus#per-queue-series-are-not-tenant-scoped).
</Aside>

## Log verbosity and format

Verbosity resolves as `RUST_LOG`, then `LOG_LEVEL`, then `info`, an empty or
whitespace-only value treated as unset. Both accept full `EnvFilter` syntax, so
per-subsystem control works without raising the global level:

```bash
LOG_LEVEL=info,queen::pop=debug
```

An unparseable filter directive does not fail the boot; it silently falls back
to `info`. `QUEEN_LOG_JSON=1` emits one JSON object per line, fields flattened
to the top level: the mode for a log shipper. In text mode ANSI colour is off
unconditionally, since these logs are read through container and journal
drivers. The subscriber is installed before configuration loads, so even a
fatal boot error is a timestamped structured line. Every line has the same
shape, with a broker-generated timestamp and a `target` naming the subsystem:

```text
<RFC3339 UTC>  <LEVEL>  <target>  <message>  key=value …
```

| Target | What it reports |
| --- | --- |
| `boot` | the effective configuration, the listener, fatal boot aborts |
| `rates`, `sizes` | the periodic aggregate blocks described below |
| `spool` | the on-disk push spool: drain loop, buffered mode, quarantine |
| `retention` | the maintenance cycle: swept counts, cycle errors |
| `stats` | the `queen.stats` reconciler |
| `metrics` | the per-minute metrics collector |
| `fusion`, `ack-fusion`, `ack-reg`, `dedup`, `hotlist` | engine internals, mostly at DEBUG |
| `pool` | connection-pool saturation |
| `auth` | JWT and JWKS state |
| `mesh`, `reconcile` | multi-instance coordination |
| `push`, `txn`, `db`, `encryption`, `streams`, `schema` | path-specific warnings |
| `shutdown` | signal received, undrained spool, shutdown complete |
| `panic` | a task panicked; the process is about to abort |
| `migrate` | the retired `migrate` subcommand refusing to run |

At boot the broker emits one `boot` line per subsystem (`config: server`,
`postgres`, `auth`, `sync`, `engine`, `flow`, `jobs`, `file_buffer`, `security`,
`logging`) with the value it actually resolved for each knob, secrets masked.
Numeric environment variables are parsed leniently (an unparseable number
silently becomes the default), so this block is the only reliable confirmation
of what the process understood; read it before believing a manifest.

## The rates block

One task emits a `rates` line with `scope="global"` every `QUEEN_LOG_RATES_MS`
(default 10000 ms, floored at 1000), from state already collected, so it costs
nothing per request; rates are deltas over the window, not lifetime averages.

| Field | Meaning |
| --- | --- |
| `push_s`, `pop_s`, `ack_s` | messages pushed / popped / acked per second |
| `txn_s` | transaction requests per second |
| `p50_push_ms`, `p99_push_ms`, `p99_pop_ms`, `p99_ack_ms` | percentiles over a bounded in-process ring of recent batch round trips |
| `ack_hit_pct` | share of acks resolved by the in-memory ack registry instead of the SQL hash path, over this window |
| `pop_empty_pct` | share of pop requests in this window that returned nothing |
| `parked` | long-poll pops currently parked, summed over queues |
| `pool` | connections the pool has created, over its configured maximum |
| `pool_waiting` | requests queueing for a connection. Non-zero is backpressure |
| `adm_budget`, `adm_mode` | the admission budget in force, and whether the train sensor is live (`normal`) or degraded (`nosync`) |
| `adm_lanes` | per lane `inflight/cap w<waiters>`. Waiters with an idle pool means admission is the constraint |
| `buffered` | `true` while pushes are being spooled to disk instead of PostgreSQL |

Up to `QUEEN_LOG_TOPN_QUEUES` (default 10) `queue rates` lines follow, ranked by
push + pop + ack, each carrying `tenant`, `queue`, `push_s`, `pop_s`, `ack_s`, a
window-weighted `lag_ms` and a `hot=shown/total` counter. A queue with no
activity in the window is omitted, so absence means idle, not missing.

## The sizes block

The same task emits one `sizes` line per interval: whether the broker's caches
live inside their budgets.

| Field | Meaning |
| --- | --- |
| `dedup` | `resident/capMB(percent)` of the deduplication hash cache, against `QUEEN_DEDUP_CACHE_MB` |
| `dedup_suppressed` | partitions currently excluded from that cache under byte-budget pressure |
| `ack_reg` | ack-registry occupancy as `entries/MB` |
| `hotlist` | `rings/ready/wheel` counts of the wildcard candidate hot list |
| `spool_pending` | push events written to disk and not yet replayed |
| `spool_healthy` | the spool's view of PostgreSQL reachability |
| `pool`, `pool_waiting` | as in the rates block |
| `rss_gb` | resident set size |

A rising `dedup_suppressed` is a sizing signal, not a correctness one:
deduplication stays exact because the SQL probe is authoritative, but a
suppressed partition pays a full-window database probe per push, and the fix is
a larger `QUEEN_DEDUP_CACHE_MB` or fewer hot partitions. `rss_gb` and
`queen_process_resident_memory_bytes` both read `/proc/self/statm`, so a
non-Linux host reports 0.

Two lines fire on transition, not on schedule. Entering spooled mode is
`WARN spool "entering buffered mode (degraded durability)"` with the pending
count, and recovery is `INFO spool "DB recovered"`: the most important
durability lines the broker emits, once per transition. Pool saturation is
`WARN pool "connection pool saturated"` with `waiting`, `size` and `max`, at
most once per 10 s.

## Anti-flood sampling

No line is emitted per message or per request: every hot-path and
background-loop diagnostic goes through one wall-clock window gate admitting one
emit per interval process-wide (a compare-and-swap picks the winner), with
`suppressed=N` counting occurrences swallowed since the previous emit.

| Window | Applies to |
| --- | --- |
| 10 s | hot-path and drain diagnostics: encryption failures, spool open and drain failures, fusion and ack-fusion errors, pool acquisition failures, the periodic fusion and dedup summaries |
| 30 s | retention and stats cycle errors |
| 60 s | metrics-collector insert errors, JWKS refresh failures |

So `suppressed=0` on a warning means it happened once, a large count means a
storm, and a sustained outage produces roughly one line per window per
subsystem: do not size an alert on log volume. The counterpart is the panic
hook: release builds
[abort on any panic](/selfhost/configuration#what-kills-the-boot), and the hook
emits `ERROR panic` with source location and thread name first, so a
crash-looping container always leaves a reason behind.

## GET /metrics is JSON, not Prometheus

Scraping `/metrics` with Prometheus fails to parse: it is a small JSON object
inherited from an older server, with several structural placeholders.

| | Fields |
| --- | --- |
| Real | `uptime`, `requests.total` (push + pop + ack requests for this process), `messages.total`, `database.poolSize`, `database.idleConnections`, `memory.rss` |
| Always zero | `requests.rate`, `messages.rate`, `database.waitingRequests`, every `memory` field except `rss`, both `cpu` fields |

Use it by hand, not for a dashboard: `pool_waiting` is the number you actually
want, and this endpoint reports it as zero.

## GET /metrics/prometheus

Three properties decide how you read the exposition; the full family list, label
sets and assembly order are in the
[Prometheus reference](/reference/prometheus/).

| Property | Consequence |
| --- | --- |
| The database block is **best-effort**: if the read fails, those families are absent from the scrape and it still returns 200 | an alert on the *absence* of `queen_cluster_*` detects a database problem; an alert on a non-200 response does not |
| `queen_process_*` is per-instance and resets on restart; `queen_cluster_*` is a lifetime total read out of PostgreSQL, identical on every instance | aggregate `queen_cluster_*` with `max`, never `sum` |
| Per-queue series are minute buckets flushed every `METRICS_FLUSH_MS` (60 s) and read within a five-minute window | a value can be one flush stale, and a quiet queue drops out after about five minutes instead of reporting zero; `queen_queue_metrics_age_seconds` tells "no traffic" from "stale bucket" |

## What to alert on

Durability first: the top four rows are in-process gauges, always present.

| Signal | Reading |
| --- | --- |
| `queen_file_buffer_db_healthy == 0` | the broker is spooling pushes to disk. Page on it |
| `queen_file_buffer_pending` not returning to 0 after the database recovers | the drain is stuck; check the `spool` target for permanent drain failures |
| `queen_file_buffer_failed > 0` | a spool *write* failed: those pushes were reported `failed` to the client and are gone. The only counter here that represents accepted-then-lost work; it should be zero forever |
| `queen_maintenance_mode_enabled == 1` when nobody enabled it | a peer flipped it, or it survived a restart in `queen.system_state` |
| `rate(queen_cluster_db_errors_total)` above zero | statement errors, statement timeouts and pool acquisition failures on the data paths; spooled pushes are counted *before* being relabelled `buffered`, so the spool cannot hide them |
| `queen_db_pool_idle` pinned at 0 | pool exhaustion; corroborate with the `pool` WARN in the log |
| `queen_event_loop_lag_avg_milliseconds` sustained growth | a 100 ms ticker measuring its own overshoot: the runtime or the host is starved |
| `queen_queue_pop_lag_milliseconds{stat="max"}` per queue | read together with `queen_queue_metrics_age_seconds`, so a stale bucket is not read as recovery |
| `rate(queen_cluster_dlq_total)` and `queen_dlq_depth` | the rate is the incident signal (dead-letter transitions); the depth, with `queen_dlq_depth_by_queue`, only falls when someone deletes dead letters, so it is the hygiene signal |
| log: `target=panic` at any level | the process is about to abort |
| log: `target=encryption` reporting `encryption DISABLED` | [flagged queues then store plaintext](/selfhost/security/encryption#a-bad-key-silently-stores-plaintext) |
| log: `target=retention` `"cycle error"` | the sweep is failing |
| log: `target=shutdown` `"spool has undrained events at shutdown"` | buffered pushes are sitting on a node that just stopped |

The last four rows have no metric at all, which is why they are log rules. Do
not alert on `/health` returning 503 as "the broker is broken": that endpoint
does a real database round trip, and treating it as a liveness signal falls
into [the liveness-probe trap](/selfhost/probes-restarts#the-liveness-probe-trap).
