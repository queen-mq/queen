Run one to three identical brokers against **one** PostgreSQL, load balancer in
front. Brokers hold no authoritative state (messages, offsets, dedup, queue
configuration, leases, DLQ: all PostgreSQL): nothing to replicate, no quorum,
no serving leader, no split-brain. Replicas cover a broker process dying, a
rolling restart, one node's network, not losing PostgreSQL: that is
PostgreSQL tooling's job.

## Configuration for a pair

Condensed from `test/compose/docker-compose.ha.yml`, whose harness version adds
a runner asserting the mesh is up.

```yaml
services:
  pg:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: postgres
  queen-a:
    image: ghcr.io/queen-mq/queen:latest
    environment:
      PG_HOST: pg                       # same database for both brokers
      PG_USER: postgres
      PG_PASSWORD: postgres
      PG_DATABASE: postgres
      PORT: "6632"
      QUEEN_SERVER_ID: queen-a          # distinct per broker
      QUEEN_MESH_PORT: "6633"
      QUEEN_MESH_PEERS: "queen-b:6633"  # points at the other broker
      QUEEN_SYNC_SECRET: "change-me"    # byte-identical on every broker
      FILE_BUFFER_DIR: /var/lib/queen/buffers   # spool: own volume per broker
    volumes: ["spool-a:/var/lib/queen/buffers"]
  queen-b:
    image: ghcr.io/queen-mq/queen:latest
    environment:
      PG_HOST: pg
      PG_USER: postgres
      PG_PASSWORD: postgres
      PG_DATABASE: postgres
      PORT: "6632"
      QUEEN_SERVER_ID: queen-b
      QUEEN_MESH_PORT: "6633"
      QUEEN_MESH_PEERS: "queen-a:6633"
      QUEEN_SYNC_SECRET: "change-me"
      FILE_BUFFER_DIR: /var/lib/queen/buffers
    volumes: ["spool-b:/var/lib/queen/buffers"]
volumes:
  spool-a:
  spool-b:
```

**The [disk spool is node-local](/selfhost/durability#the-limits) and must never
be shared**: each broker drains its own files, and two brokers on one volume
fight over them.

`QUEEN_SYNC_ENABLED` defaults to `true`; the mesh starts only with at least one
peer configured, so a single stock broker binds nothing and keeps the
in-process long-poll waker. A busy mesh port logs `TCP mesh bind failed` and
serving continues on the local waker.

Three replicas is the designed ceiling: full-mesh connections grow
quadratically, and `replicas × DB_POOL_SIZE`
[must fit `max_connections`](/selfhost/postgres#connection-pool-sizing); past
three the bottleneck is almost always PostgreSQL.

## The shape

<pre class="mermaid">{`
flowchart TB
  CL["clients"] --> LB["load balancer"]
  LB --> A["broker-a"]
  LB --> B["broker-b"]
  LB --> C["broker-c"]
  A -. "mesh hints" .- B
  B -.- C
  A -.- C
  A --> PG["PostgreSQL<br/>messages, offsets, leases, dedup, queue config"]
  B --> PG
  C --> PG
`}</pre>

A dropped frame costs a parked pop some latency, nothing else. Every replica
serves every route, no session affinity, no partition ownership: leases are
rows in `queen.log_consumers`, so a pop from `broker-a` can be acked to
`broker-c`.

## What the mesh is

Framed TCP: `u32` big-endian length, one type byte, a JSON payload. No sequence
numbers or per-frame signature (TCP orders; the mesh tolerates loss), and
lengths above 16 MiB are rejected before allocation. Topology, framing, frame
set: [Mesh internals](/internals/mesh/). The `QUEEN_UDP_*`
[alias names](/selfhost/configuration#names-with-a-history) are legacy; the
wire is TCP.

## What the mesh carries

Hints, all best-effort:

| Hint | Effect on the receiving replica |
| --- | --- |
| **Pop wakes** (`MESSAGE_AVAILABLE`, and a batched form) | A push that committed on A wakes a long-poll pop parked on B immediately, instead of B waiting out its backoff. Also records the partition so the woken pop can target it. |
| **Hot-list dirty hints** (batched) | Marks the peer's in-memory wildcard-pop candidate set for a (queue, partition) that went from empty to pending. Coalesced: sent on the transition, not per message. An item may name a consumer group, which scopes the mark to that group's candidate ring; a hint from a backward seek does, a hint from a push does not. |
| **Maintenance flips** | `MAINTENANCE_MODE_SET` and `POP_MAINTENANCE_MODE_SET` flip the receiving replica's flags, and keep its spool drain lifecycle in step. |
| **Queue-config invalidation** | `QUEUE_CONFIG_SET` / `QUEUE_CONFIG_DELETE` drop the peer's cached lease time and encryption flag for that queue. The **value** is not sent, only the instruction to forget. |
| **`HELLO` + `HEARTBEAT`** | `HELLO` at connection setup, then a heartbeat every `QUEEN_SYNC_HEARTBEAT_MS` (default 1000): the periodic write that detects a dead peer when no hints are flowing. |

## What the mesh does not carry

| Never on the mesh | Where it actually lives |
| --- | --- |
| **Messages** | No payload ever crosses it. |
| **Offsets, acknowledgements, leases** | All rows in `queen.log_consumers`. |
| **Deduplication state** | Enforced in SQL under the partition row lock, which is why it is exact across every replica without coordination. |
| **Queue configuration values** | Only invalidations cross; a replica re-reads the configuration from PostgreSQL lazily. |
| **Cluster membership as authority** | Peer liveness feeds logging and the stats surface. Nothing routes on it, and a replica that believes every peer is dead serves normally. |
| **Leader election** | Done with PostgreSQL advisory locks. |

### Loss is designed in, not tolerated grudgingly

Each peer has a bounded send queue: full or down, the frame is **dropped** and
a counter bumped; the send path never blocks. On reconnect, frames queued
meanwhile are discarded *before* the peer is marked connected: stale wakes are
pointless, a stale maintenance state is actively wrong (depths and backoff:
[Mesh internals](/internals/mesh/)). A lost frame costs latency, not
correctness: every accelerated channel has a periodic floor re-reading the
database.

| Mechanism | Cadence | Heals |
| --- | --- | --- |
| Periodic reconcile | `QUEEN_CACHE_REFRESH_INTERVAL_MS`, default 60000 ms | Re-reads both maintenance flags from `queen.system_state` (the database is the truth) and clears the per-queue lease and encryption caches, so a lost config invalidation heals within one interval. Runs unconditionally, on a single broker too: reconverging on the database is useful even without peers. |
| Pop long-poll backoff | Up to `POP_WAIT_MAX_INTERVAL_MS`, default 1000 ms | A parked pop re-queries on its own schedule regardless of wakes, so a dropped wake costs at most one interval of latency. |
| Hot-list reseed floor | `QUEEN_HOTLIST_RESEED_MS`, default 30000 ms | Rebuilds a candidate ring from PostgreSQL even when it is non-empty, recovering a partition dropped by a missed mark or a dropped hint. Bounded to the partitions written in the last `QUEEN_HOTLIST_RESEED_WINDOW_MS`, which covers every case a **push** can create, and so every dropped push hint. |
| Hot-list repair markers | `QUEEN_CACHE_REFRESH_INTERVAL_MS`, default 60000 ms | The two operations that make old partitions pending without writing anything, a backward seek and a consumer-group delete, are invisible to the bounded walk above. Each writes a row into `queen.hotlist_repairs` in its own transaction, and every broker reads that table on the reconcile pass and repairs the rings named there. This is the floor under the mesh hint the operation also sends, and it is why a dropped hint on a seek no longer costs a replay a full-walk interval. |
| Hot-list full reseed | `QUEEN_HOTLIST_RESEED_FULL_MS`, default 300000 ms | The same walk over every partition of the queue. This is the one that recovers pendingness no write explains and no marker announces: a ring entry cleared in error, a claim stranded by a dropped pop, a stale lease park. |

## Leader-gated background jobs

Two of the three cadenced background writers are advisory-lock gated, so
exactly one replica works per cycle; one that cannot take the lock skips the
cycle. No persistent leader, no election protocol.

| Job | Cadence | Gate |
| --- | --- | --- |
| Retention and eviction sweep | `RETENTION_INTERVAL`, default 5000 ms | Session lock `737001`, taken with `pg_try_advisory_lock` and released on every exit path. Held across a whole cycle of autocommitting steps, which is one of the two reasons the broker needs a [direct PostgreSQL connection](/selfhost/postgres). |
| Statistics reconciler | `STATS_INTERVAL_MS`, default 10000 ms | Transaction lock `737002`, so it releases with the cycle's commit. Distinct from the retention lock so the two never block each other. |
| System and worker metrics collector | `METRICS_FLUSH_MS`, default 60000 ms | **Not gated.** Every replica records its own rows, keyed by host and worker; the dashboard aggregates across replicas. |

## The mesh port must be firewalled

Not advice. A requirement.

The `HELLO` handshake is `{server_id, nonce, mac}` with
`mac = HMAC-SHA256(secret, nonce)`, verified in constant time before any further
frame is accepted. That is the entire authentication story, and it has three
properties an operator has to plan around:

1. **The handshake is replayable.** The nonce is generated by the dialer and the
   listener never tracks nonces it has already seen. A captured `HELLO` can be
   replayed verbatim to open a new accepted connection, without knowing
   `QUEEN_SYNC_SECRET`.
2. **Post-handshake frames are unauthenticated JSON.** There is no per-frame MAC.
   Once a connection is accepted, every frame in the set is honoured.
3. **The frame set includes `MAINTENANCE_MODE_SET`.** Maintenance mode diverts
   pushes to the disk spool; pop maintenance mode makes every pop answer empty.
   Anyone who can complete a handshake (by replay) can flip both on a replica.

Inbound connections are receive-only: the broker never writes back on an accepted
connection. An attacker therefore needs no reply channel at all, only the ability
to connect and send.

<Aside type="danger">
Bind the mesh to a private network and allow the mesh port **only** from the other
brokers' addresses. Concretely: a `NetworkPolicy` selecting the broker pods, a
security-group rule limited to the broker instances, or a Docker network the
brokers share with nothing else. Never publish the mesh port on a host interface
that is reachable from a client network, and never expose it to the internet.
</Aside>

Setting `QUEEN_SYNC_SECRET` is still worth doing: an empty secret is *open mode*,
where any well-formed `HELLO` is accepted from anyone, so the secret raises the
bar from "connect" to "capture one handshake". It does not replace the firewall.
The boot `config: sync` block reports `auth` as `hmac` or `off`, and the mesh
start line does the same.

## What HA does not buy you

**Replicas do not parallelise a single partition.** One in-flight leased batch
exists per (partition, consumer group); scaling consumption means more
partitions.

**Replicas do not add PostgreSQL capacity.** Every push is a commit, every pop
and ack a row update, in the shared database; when throughput plateaus, look at
PostgreSQL, not at another broker.
