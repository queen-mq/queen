For building applications, QueenMQ is the better choice: services that handle events per customer, order or conversation, microservices that hand work to each other, and steps that have to commit whole. The one exception is a firehose of millions of messages a second on up to some thousands of partitions, where Kafka and Pulsar are ahead.

| You are building | Use |
| --- | --- |
| Services that handle events per customer, order, device or conversation | QueenMQ |
| Microservices that hand work to each other: jobs, fan-out, retries, delayed work | QueenMQ |
| Steps that must commit whole: the ack, the state, the next events and the timer | QueenMQ |
| A firehose: millions of messages a second through up to some thousands of partitions, where every millisecond matters | Kafka or Pulsar |

## The firehose

One leader orders all of a queue's writes, and more nodes do not raise that. On three 24-vCPU nodes with local NVMe, one queue of 1,000 partitions carried 3,000,000 messages a second at a p99 of 15 ms, 5,000,000 at 87 ms, and not 5,500,000, with every write on two disks before its answer. On the same machines Kafka carried about 8,000,000 on one topic at a p99 near 12 ms, answering from memory before any fsync. Kafka's lead ends as partitions multiply: at 10,000 it used twice QueenMQ's CPU, and it did not carry 50,000. The runs are in [QueenMQ vs Kafka, Pulsar and Redpanda](/benchmarks/queen-vs-kafka/).

Transactions have the same kind of ceiling: one leader plans a tenant's transactions, near 12,900 a second of ten messages each on 16-vCPU machines. More raft groups raise it for a deployment, not for one tenant. If one tenant needs more, with nothing but messages in the commit, use Pulsar.

<Why>one leader per tenant is what makes a transaction one log entry, with no coordinator. That is the trade: a ceiling per tenant, for steps that cannot come apart.</Why>

## Cases that look like another tool's, and the QueenMQ answer

These cases are often sent to another system. Each has an answer inside QueenMQ.

- **You route messages by their content.** QueenMQ has no exchanges, bindings or topic patterns: the producer names the queue and the partition. Route with a step: a consumer reads each message, picks the queue, and pushes and acks in one [transaction](/reference/transaction/), so the push and the ack commit together.
- **You need only the latest value per key, as with Kafka's compaction.** A consumer group with conflation gets only the newest message of each partition ([last value](/patterns/last-value/)), and KV keeps the latest value per key for reads. Nothing is deleted: retention decides what stays. QueenMQ accepts `cleanup.policy=compact` from Kafka clients and keeps every record. See [Kafka frameworks](/integrations/kafka-frameworks/).
- **The step needs SQL to decide.** KV reads by key or by prefix, with no joins. Read what the decision needs from your database, then commit the step in QueenMQ: the ack, the state and the next events. For records you search, the [PostgreSQL sink](/integrations/postgres/) writes a queue into a table, so the table follows the queue.
- **A step needs many reads and decisions.** A QueenMQ transaction is one call; there is no interactive BEGIN and COMMIT. Read first, decide in the worker, then commit with a condition on each value the decision used (`expect`, `check`). If any of them moved, nothing commits and the step runs again.
- **You want long workflows.** The partition is the workflow's input, KV its state, each step one transaction, and a timer each wait, up to 90 days by default (`QUEEN_TIMERS_MAX_HORIZON_S`). See [workflows](/patterns/workflows/).

## Limits you design around

Three limits are part of how QueenMQ works. Each has an answer inside QueenMQ.

- **A partition is sequential.** One entity's events are handled one step at a time, in order. Parallelism comes from many partitions with work; an entity too busy for one worker is split into finer partitions (an order's lines instead of the order).
- **Delivery is at least once.** Effects inside QueenMQ are exactly once through transactions and deduplication. A call to another system needs that system's own idempotency key. No broker removes that.
- **Ephemeral queues are not durable.** A node that crashes loses what it held. Use them for request and reply, and a regular queue for anything that must survive a crash.
