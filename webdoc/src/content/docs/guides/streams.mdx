A stream is an operator chain (map, filter, window, aggregate, sink) that runs inside your
process and reads a queue the way a consumer group does. The window state lives in Queen, and each
cycle commits the source ack, the state change and the sink push as one entry, so a crash
mid-cycle neither loses an event nor counts it twice. There is no stream cluster, changelog topic
or state store to run.

## A windowed total per customer

```js
import { Queen, Stream } from 'queen-mq'

const url = 'http://localhost:6632'
const queen = new Queen({ url })

const handle = await Stream
  .from(queen.queue('sales'))                       // partitioned by customer
  .filter((m) => m.data.amount > 0)
  .windowTumbling({ seconds: 60 })
  .aggregate({ count: () => 1, sum: (s) => s.amount })
  .to(queen.queue('sales-per-minute'))
  .run({ queryId: 'sales-per-minute', url })

// later: await handle.stop()
```

- **The partition is the key.** Window state is kept per source partition, so with one partition
  per customer each customer gets its own windows. The sink pushes into a partition of the same
  name unless `.to(q, { partition })` says otherwise.
- **`queryId` is the query's identity.** Its state is keyed by it, so a restart with the same id
  resumes the same windows. Registering a different chain under the same id is refused unless you
  pass `reset: true`, which drops the state.
- **The runner is a consumer group**, `streams.<queryId>` by default. It leases up to
  `maxPartitions` partitions (4) and `batchSize` messages (200) per cycle, so several processes
  running the same query share the partitions.
- **Extractors see the payload.** `aggregate` and `reduce` receive the message payload, or what a
  `map` before the window returned (`s.amount`); `filter`, `map` and `eventTime` receive the
  message (`m.data.amount`). A missing field aggregates to zero, without an error.

## Windows

| Operator | Window | Closes |
|---|---|---|
| `windowTumbling({ seconds })` | fixed, non-overlapping | at window end + `gracePeriod` |
| `windowSliding({ size, slide })` | overlapping, hops every `slide` s | at each window's end + grace |
| `windowSession({ gap })` | per key, extends while events arrive within `gap` s | after `gap` s of silence |
| `windowCron({ every })` | aligned to `second`, `minute`, `hour`, `day` or `week` (UTC) | at the boundary + grace |

By default a window runs on processing time, the `createdAt` Queen stamped on each message. A
window on a partition that has gone quiet is closed by the idle flush (`idleFlushMs`, 5000 by
default for tumbling and sliding), which commits the state delete and the sink push as one entry
with no source ack.

Pass `eventTime` to window on a time inside the event instead:

```js
.windowTumbling({
  seconds: 60,
  eventTime: (m) => m.data.eventTs,   // Date, epoch ms or ISO string
  allowedLateness: 30,                // seconds behind the newest event still accepted
  onLate: 'drop',                     // or 'include'
})
```

Each partition keeps a watermark: the newest event time seen, minus `allowedLateness`. A window
closes when the watermark passes its end plus grace, and an event older than the watermark is
dropped (or, with `include`, added to a window that may already have been emitted, which emits it
again). The watermark is stored with the window state, so it survives a restart.

## What one cycle commits

The runner pops a batch per partition, runs the chain, and posts the result to
`POST /streams/v1/cycle`. The broker turns it into one transaction: a positional ack of the source
batch, the state upserts and deletes, and the sink pushes. All of it applies or none of it does.
If the commit fails, the lease expires and the batch is redelivered to the same chain with the
same state.

`.foreach(fn)` is the other terminal: it runs `fn` and acks only after `fn` resolves, so its
effect is at-least-once. Write to a sink queue instead when the effect must happen once. `.gate()`
makes an allow or deny decision per message with per-key state (a token-bucket rate limiter), and
cannot be combined with a window in the same stream.

## Limits

- **Streams are not part of the Jepsen pass.** The cycle route and the runners are covered by the
  server and client test suites, not by fault injection. See [guarantees](/concepts/guarantees/).
- **One window and one reducer per stream.** Chain two streams through a queue for more stages.
- **Re-keying costs contention.** `.keyBy()` with a key that is not the partition lets workers
  holding different partitions write the same state key. Push to a queue partitioned by the new
  key and aggregate there instead.
- **Event-time idle flush follows the watermark, not the clock.** On a partition that stops
  receiving events, the last event-time window stays open until a newer event arrives.
- **`windowCron` takes `every`, not cron syntax.**
- **No published run measures stream throughput.** The [benchmarks](/benchmarks/) measure push,
  pop and ack.
