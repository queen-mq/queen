A consumer that charges cards will see some orders twice: a lease expires, a node restarts, an
operator replays the queue. Make the second delivery harmless by writing a marker in the same
transaction as the ack, so an order is charged-and-acked or neither. This gives exactly-once
effects inside Queen; the charge itself is a call to another system, and the last section says
what that leaves open.

## The problem

The usual worker keeps its "already charged" flag in a second system: charge, write the flag to
the database, ack the broker. The flag and the ack commit separately, so they can disagree, and
nothing stops a worker whose lease has expired from writing its flag after another worker took the
message. Anything else the step emits (a receipt, a ledger event) has the same gap.

## The fix

Keep the marker in KV and commit it with the ack:

```js
await queen.queue('orders')
  .group('charger')
  .subscriptionMode('all')
  .autoAck(false)
  .each()
  .consume(async (msg) => {
    const key = `charge:${msg.data.orderId}`
    const marker = await queen.kv.get('charges', key)
    if (marker.found) {                               // a redelivery: already charged
      await queen.ack(msg, 'completed', { group: msg.consumerGroup })
      return
    }

    const chargeId = await chargeCard(msg.data)       // the external effect

    try {
      const res = await queen.transaction()
        .kv.putIfAbsent('charges', key, { chargeId }, { ttl: '30d', required: true })
        .ack(msg, 'completed', { consumerGroup: msg.consumerGroup })
        .commit()
      if (res.success === false) {                    // kv_precondition: another delivery won
        await queen.ack(msg, 'completed', { group: msg.consumerGroup })
      }
    } catch (err) {
      if (err.reason === 'rejected_ack') return       // lease lost: nothing was written
      await queen.ack(msg, 'failed', { group: msg.consumerGroup, error: err.message })
    }
  })
```

Three things make it hold:

- **Marker and ack in one transaction.** The marker exists exactly when the order is acked. A
  worker that dies before the commit leaves no marker, and the redelivery runs the handler again.
- **`required: true` makes `putIfAbsent` a gate.** Without it a lost race is only a verdict in the
  results, and the ack still commits. With it, the whole transaction rolls back and `commit()`
  returns `success: false, reason: 'kv_precondition'` with HTTP 200. It is returned, not thrown,
  because it is the normal outcome of a duplicate. The gate covers what the read cannot: two
  deliveries of one order in flight at once (two messages for the same order, or two groups). Only
  one of them commits its marker and anything else in its transaction.
- **The lease is the fence.** If the worker's lease expired while it was charging, the ack is
  refused and the marker write is refused with it: `commit()` throws with `reason:
  'rejected_ack'`. A compare-and-set cannot do this, because a version that still matches succeeds
  for a worker that no longer owns the message.

`once` is the same gate under a shorter name: `.once('charges', key, { ttl: '30d', value: {
chargeId } })` is `putIfAbsent` with `required: true`. Over HTTP, put the pop's `leaseId` on the
ack operation, as the curl program below does. The SDKs send it for you. **An ack without a lease
id is not fenced.** See [transactions](/concepts/transactions/) and [dedup](/concepts/dedup/).

## Limits

- **The charge itself can still happen twice.** Three windows remain, all between the provider's
  answer and the commit: the worker dies; its lease expires during the call (the commit is then
  refused and the next worker charges again); or two deliveries of one order are in flight at
  once. The marker narrows a double charge to those windows; it does not close them. Keep
  `leaseTime` well above the provider's timeout, and pass the order id as the provider's
  idempotency key so a second charge for the same order is refused there.
- **Do the work that can fail before the charge.** Validation, lookups and anything else that can
  throw should run first, so a failure leaves no external effect behind.
- **A marker lives as long as its TTL.** An expired marker is absent, so its TTL must outlast any
  redelivery or replay you will run. Markers are KV rows: deleting the queue does not delete them.
- **Delivery stays at-least-once.** Exactly-once holds for what the transaction writes. The
  transaction and the dedup are Jepsen-tested; see [guarantees](/concepts/guarantees/) for the
  conditions.
