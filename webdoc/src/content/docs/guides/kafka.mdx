Your Kafka producers, consumers and admin tools can use Queen as they are: change
`bootstrap.servers` and nothing else. A topic is a Queen queue and a consumer group is a Queen
consumer group, so Kafka clients and Queen clients read and write the same streams, and you can move
an application over one service at a time.

## Try it

```bash
docker run -d --name queen -p 6632:6632 -p 9092:9092 \
  -v queen-data:/var/lib/queen/raft \
  -e QUEEN_KAFKA_EMBEDDED=true \
  -e QUEEN_KAFKA_ADVERTISED_ADDR=localhost:9092 \
  ghcr.io/queen-mq/queen:2.5.0
```

`QUEEN_KAFKA_EMBEDDED=true` starts the Kafka listener inside the broker, on port 9092.
`QUEEN_KAFKA_ADVERTISED_ADDR` is the address Kafka clients come back to after their first request,
so it has to be one they can reach. It has no default, and a node started without it refuses to
boot and tells you why.

Send three keyed records with [kcat](https://github.com/edenhill/kcat) and read them back:

```bash
printf 'customer-123:{"orderId":8891,"total":42}\ncustomer-456:{"orderId":8892,"total":17}\ncustomer-123:{"orderId":8893,"total":5}\n' \
  | kcat -P -b localhost:9092 -t orders -K:
kcat -C -b localhost:9092 -t orders -o beginning -e -q -f '%t [%p] offset %o  key=%k  %s\n'
```

```text
orders [307] offset 0  key=customer-123  {"orderId":8891,"total":42}
orders [307] offset 1  key=customer-123  {"orderId":8893,"total":5}
orders [400] offset 0  key=customer-456  {"orderId":8892,"total":17}
```

Nobody created `orders`. kcat's first metadata request did: the queue came into existence 1,024
partitions wide, kcat hashed each key onto one of them, and both orders of `customer-123` landed in
partition 307 in the order they were sent. Queen's HTTP API reads the same records:

```bash
curl -s 'localhost:6632/api/v1/pop/queue/orders?batch=10' | jq -c '.partition, .messages[].data'
```

```text
"307"
{"k":"Y3VzdG9tZXItMTIz","t":1790948151426,"v":"eyJvcmRlcklkIjo4ODkxLCJ0b3RhbCI6NDJ9"}
{"k":"Y3VzdG9tZXItMTIz","t":1790948151427,"v":"eyJvcmRlcklkIjo4ODkzLCJ0b3RhbCI6NX0="}
```

The partition is the Kafka partition and the offsets are the Kafka offsets. Each record is one
message. Its payload carries the key (`k`) and the value (`v`) in base64, because a Kafka key or
value is bytes and a Queen payload is JSON, then the producer's timestamp (`t`) and, when there are
any, the headers (`h`).

Consumer groups are shared the same way. Run a group consumer, and stop it with Ctrl-C once it has
printed the three records:

```bash
kcat -b localhost:9092 -G billing -o beginning -q -f 'billing [%p] offset %o key=%k\n' orders
```

```text
billing [400] offset 0 key=customer-456
billing [307] offset 0 key=customer-123
billing [307] offset 1 key=customer-123
```

```bash
curl -s localhost:6632/api/v1/consumer-groups \
  | jq -c '.[] | select(.name == "billing") | {name, queueName, partitionCursors, totalLag}'
```

```text
{"name":"billing","queueName":"orders","partitionCursors":2,"totalLag":0}
```

`billing` is a Queen consumer group now. Its commits are the group's positions, its lag is in the
dashboard beside every other group, and a Queen consumer that joins it starts where the Kafka
consumer stopped. Push one more order over HTTP and pop it as `billing`:

```bash
curl -s -X POST localhost:6632/api/v1/push -H 'content-type: application/json' \
  -d '{"items":[{"queue":"orders","partition":"307","payload":{"orderId":8894,"total":99}}]}' > /dev/null
curl -s 'localhost:6632/api/v1/pop/queue/orders/partition/307?consumerGroup=billing&batch=10' \
  | jq -c '.messages[] | {offset, data}'
```

```text
{"offset":2,"data":{"orderId":8894,"total":99}}
```

And a Kafka consumer reads what a Queen client pushed as a record with no key, whose value is the
JSON document:

```bash
kcat -C -b localhost:9092 -t orders -p 307 -o 2 -c 1 -q -f 'offset %o key=%k value=%s\n'
```

```text
offset 2 key= value={"orderId":8894,"total":99}
```

## How it works

The facade runs inside the broker process on threads of its own (`QUEEN_KAFKA_THREADS`,
`min(4, cores / 2)` by default) and keeps nothing of its own that outlives a connection or a
leader's term. It is a translation layer: a produce request becomes one ordered push and a fetch one
read at an offset, both through the state machine's own record path in memory, with no HTTP request
and no JSON body, and every other call (commits, topic widths, time lookups, transactions) is one of
the broker's routes handed to its router in-process. Routing, authorization, tenancy and admission
are the ones every HTTP client meets.
We kept Kafka on Queen's one pipeline on purpose: a record is a Queen message from the moment it is
written, so replication, retention, the dashboard and native consumers all apply to it, and there is
no second storage path to keep in step with the first.

<Figure id="guides/kafka-pipeline" />

The Kafka cluster a client sees is the raft cluster. Every node runs the facade and is a broker,
every voter is a replica in sync of every partition, and the raft leader leads every partition and
coordinates every group and transaction. Produce, Fetch, ListOffsets and the group and transaction
calls are served by the leader; another node answers `NOT_LEADER_OR_FOLLOWER` or
`NOT_COORDINATOR`, and the client refreshes its metadata and goes to the leader.

`acks=1` and `acks=all` take the same path: a produce is answered when its push is committed to the
raft log, which on a cluster means a majority of the voters have it. `acks=0` writes the same way
and sends nothing back. A connection reads its next request once the push before it is in the raft
log, without waiting for it to commit, so the batches of one connection land in the order they were
sent, which is what an idempotent producer counts on.

Topics created through Kafka get a dedup window of 900 seconds (`QUEEN_KAFKA_DEDUP_WINDOW_SECONDS`),
which is what makes the idempotent producer work ([below](#idempotent-producers)). A queue that
already existed keeps its own settings, except that a queue with no window gets this one when an
idempotent producer first writes to it.

## How Kafka maps onto Queen

| Kafka | Queen |
|---|---|
| Topic | A queue of the same name, created by CreateTopics or by the first metadata request that names it |
| Partition `n` | The partition named `"n"` |
| Partition count | The topic's width: what CreateTopics declared, else `QUEEN_KAFKA_DEFAULT_PARTITIONS` (1,024), or more if more partitions exist |
| Record | One message: key, value, headers and timestamp in a JSON envelope |
| Offset | The partition's offset, assigned by the raft leader |
| Consumer group | The Queen consumer group of the same name |
| Committed offset | The group's position on that partition |
| `acks=1`, `acks=all` | One path: answered once the push is committed to the raft log |
| Replication factor | The number of raft voters; every voter holds every partition |
| `retention.ms` | The queue's retention, in whole seconds, set when the topic is created |
| `cleanup.policy=compact` | Retention off: every record is kept |
| Other topic configs | Accepted, not applied yet |
| Idempotent producer | Queen's dedup window: a record's producer id, epoch and sequence are its transaction id |
| Transaction | Held in the raft leader's memory, committed with its offsets as one raft entry |

### Partitions and width

A Kafka client spreads keys by hashing them modulo the partition count, so a topic needs a fixed
width. A Queen queue has none: a partition is a name that exists from its first message. The facade
keeps a width per topic and advertises the larger of that width and the partitions that exist. The
width is what CreateTopics asked for, so `kafka-topics.sh --create --partitions 8` makes an
eight-partition topic, and `QUEEN_KAFKA_DEFAULT_PARTITIONS` for a topic created on first use. A
topic never narrows, because a smaller count would send existing keys to other partitions, and
CreatePartitions widens a topic created through Kafka. CreateTopics writes the width before it
creates the queue, so on a cluster every node reports the declared width from its first answer
about a new topic. Kafka Connect, which reads the partitions of the topics it has just created
straight back from metadata, depends on exactly that.

The default is wide because partitions are cheap here: until something is written to it, a
partition costs the broker a key and a counter, and a wide topic leaves a consumer group room to
grow. Width has one real cost, the metadata answer, which lists every partition at about 50 bytes
each, so one topic is capped at 100,000 partitions.

Queen partitions whose names are not numbers, such as `customer-123`, count toward the width, but a
Kafka client cannot address them. A produce through Kafka always creates numbered partitions, so
this matters only for queues that Kafka and Queen clients share.

### Consumer groups and committed offsets

Groups use Kafka's classic protocol (JoinGroup, SyncGroup and heartbeats), and the assignment is
computed by the client, so range, round-robin, sticky, cooperative-sticky and the Kafka Streams
assignor all work. The first member of a new group waits three seconds for others before the first
assignment (`QUEEN_KAFKA_GROUP_JOIN_DELAY_MS`, Kafka's `group.initial.rebalance.delay.ms`). The
raft leader coordinates every group and holds its membership in memory: when the leader changes,
members are told `NOT_COORDINATOR` or `UNKNOWN_MEMBER_ID`, rejoin at the new leader and resume from
their committed offsets. A group with no members leaves that memory ten minutes after its last
member left, so `kafka-consumer-groups.sh --list` stops showing it; its committed offsets stay.

A committed offset is the group's position on the partition. That is why `billing` showed up in
`/api/v1/consumer-groups` with its lag, and why a Queen consumer of `billing` resumed at offset 2.
Kafka consumers read with fetch requests and take no leases, so Queen's redelivery, retry budget and
dead-letter queue do not apply to them; a Kafka consumer handles its own failures, as it does on
Kafka. Both kinds of consumer share a group's position, but not its work. A Kafka commit sets the
position the way a seek does, so hand a group from one kind of consumer to the other, and do not run
both at once.

Committed offsets never expire. Kafka drops the offsets of a group that has been empty for seven
days (`offsets.retention.minutes`), and a consumer that comes back after that starts over from
`auto.offset.reset` without a word; here a group keeps its position until you delete it.
`kafka-consumer-groups.sh --delete` does that, and since a Kafka group is a Queen group, deleting
one with no members deletes the Queen consumer group of that name, with its position on every
queue. `--delete-offsets` is not offered in 2.6.

A Kafka consumer takes no lease, so the broker learns that a group is alive from the facade. While a
group's members heartbeat, the facade writes the group's presence to the key-value store every 15
seconds, and at once when a rebalance completes or the last member leaves.
`/api/v1/consumer-groups` reports such a group as `kind: "kafka"`, with `liveMembers`, `lastSeenAt`
and `inactiveSeconds`. When the group leaves the leader's memory, its presence row is deleted and it
is reported like any group nobody reads for: `Dead`, or `Lagging` while it is more than five
minutes behind. The dashboard counts a live Kafka group as a reader of its topic, and a topic
the facade created is not flagged for having no reader, since Kafka clients never read in queue
mode.

### Idempotent producers

Java clients since 3.0 and franz-go turn idempotence on by default, so a producer with no settings
at all is an idempotent one. Each of its records goes to Queen with a transaction id made of the
producer's id, epoch and sequence number (`k<producer id>.<epoch>.<sequence>`). A batch sent again
after a lost answer repeats those ids exactly, so within the topic's dedup window it writes nothing
and is answered with the offsets it got the first time.

That window is Queen's own, in the raft log like every other dedup entry, so it survives a node
restart and a leader change, where Kafka keeps producer state in its log for the same reason. The
facade sets it to 900 seconds on the topics it creates, and on a topic with none when an idempotent
producer first writes to it (`QUEEN_KAFKA_DEDUP_WINDOW_SECONDS`): a producer retries a batch for at
most `delivery.timeout.ms`, two minutes by default, so a longer window would catch nothing more.

There is no sequence check per partition: a batch that leaves a gap in a producer's sequence is
written, where Kafka refuses it with `OUT_OF_ORDER_SEQUENCE_NUMBER`. Order within one connection is
kept by the ordered push above, and a producer sends one partition's batches on one connection.

### Transactions

A transactional producer needs no extra settings, and `sendOffsetsToTransaction` in a
consume-transform-produce loop works too, on one node and on a cluster. A transaction of three
records behaves like this: each produce inside it is answered with offset -1, the topic's end offset
does not move while the transaction is open, the commit moves it by exactly three, and an aborted
transaction leaves it where it was.

The records wait in the memory of the raft leader, which is every partition's leader and the
transaction coordinator, so the producer's records, its offsets and its commit all reach it.
`commitTransaction()` writes them, together with the consumer offsets the transaction carries, as
one Queen transaction: one raft entry, so the records and the offsets land together or not at all.
`abortTransaction()` throws them away. No uncommitted record ever enters the log, which is why
`read_committed` costs nothing here and why a committed transaction of N records advances the log by
N, where Kafka adds a commit marker. Each `transactional.id` has a row in Queen's key-value store with
its producer id and epoch: a newer producer with the same id fences the older one, and the fenced
producer's commit writes nothing.

Because a transaction lives in memory until it commits, it has limits Kafka does not: 8 MiB, 50,000
records and 1,000 partitions per transaction, 256 MiB across the open transactions of the leader,
and a timeout of at most an hour (the [reference](/reference/kafka/#ceilings) has the answers past
each). A leader change loses the transactions that were open on the old leader: the new leader finds
them marked open and lets them only abort (`INVALID_TXN_STATE` to anything else), and their records
are never written.

### Compaction and retention

`retention.ms` on a topic created through Kafka becomes the queue's retention, rounded down to
whole seconds; `-1`, the default, keeps records forever, and so does a topic created on first use.
`cleanup.policy=compact` is accepted, and Queen keeps every record of such a topic: retention is off
whatever `retention.ms` says, so the last value of every key is always in the log, next to every
earlier one. A reader that replays a compacted topic, a Kafka Streams changelog or Kafka Connect's
config topic, rebuilds the same state from the whole log as from a compacted one. It reads more, and
the topic grows until real compaction exists; tombstones are kept like any other record.
`compact,delete` keeps the retention and compacts nothing. The other topic configs are accepted and
not applied yet, and a topic's configs are read when it is created: change its retention later
through Queen ([queue options](/concepts/partitions/#queue-options)). What
[Kafka Streams, Connect and Flink](/guides/kafka-frameworks/) ask for is on a page of its own.

## Run it on a cluster

Every node of a raft cluster runs the facade, and together they are one Kafka cluster with no
setting of its own: the voters are the brokers, and the raft leader leads every partition and
coordinates every group. Each node advertises itself at its own `QUEEN_KAFKA_ADVERTISED_ADDR`, and
the others at the host of their raft address with the same Kafka port, which is the shape of a
StatefulSet. When that is not how clients reach the nodes, `QUEEN_KAFKA_PEERS` gives every node's
address by raft node id. For the three-node Compose file in `deploy/compose/three-node/`
([Run a cluster](/operate/cluster/)), whose ports are published on the host, this override sits next
to `compose.yaml` in the same folder:

```yaml title="compose.kafka.yaml"
# docker compose -f compose.yaml -f compose.kafka.yaml up -d
x-kafka: &kafka
  QUEEN_KAFKA_EMBEDDED: "true"
  QUEEN_KAFKA_PEERS: "1=127.0.0.1:16092,2=127.0.0.1:26092,3=127.0.0.1:36092"

services:
  queen-1:
    environment:
      <<: *kafka
      QUEEN_KAFKA_ADVERTISED_ADDR: 127.0.0.1:16092
    ports: ["127.0.0.1:16092:9092"]
  queen-2:
    environment:
      <<: *kafka
      QUEEN_KAFKA_ADVERTISED_ADDR: 127.0.0.1:26092
    ports: ["127.0.0.1:26092:9092"]
  queen-3:
    environment:
      <<: *kafka
      QUEEN_KAFKA_ADVERTISED_ADDR: 127.0.0.1:36092
    ports: ["127.0.0.1:36092:9092"]
```

The addresses say `127.0.0.1` because the ports are published on that address only, and some
systems (macOS among them) try `localhost` as `::1` first. Ask any node what the cluster looks like,
with `kcat -L -b 127.0.0.1:26092 -t orders`: it lists the three brokers, names the raft leader as the
controller and as the leader of every partition of `orders`, and every broker as a replica in sync.
A client sends its produce, its fetches and its group calls to the leader; when the leader changes,
they are answered `NOT_LEADER_OR_FOLLOWER` or `NOT_COORDINATOR`, read the new metadata and follow.

Do not put the nodes behind one load-balanced address. A client reconnects to the address it is
given for each broker, so if every node advertises one address, a client sent to the leader lands on
another node, is told to go to the leader, and loops. A load balancer is fine in
`bootstrap.servers`, which a client uses once.

## Performance

We measured the 2.6 facade against 2.5.0's on 2026-10-20 on the benchmark rig: three 24-vCPU nodes
with local NVMe and three load machines running franz-go with 1 KB records, lz4, and 4 producers
and 4 consumers each, into one topic of 100 partitions. At 500,000 msg/s both carried the rate,
2.6 with a produce p99 of 14 ms and records reaching their consumers at 15 ms p99. At 700,000 2.6
added about 3 ms of produce latency; neither build carried 850,000 with this client, and at
1,000,000 2.6 pushed 30% less than 2.5.0. The difference is where produce goes: 2.6 takes it on the
raft leader only, where 2.5.0's followers relayed theirs and spread the Kafka protocol work over the
three nodes. The earlier matrix, measured on the first facade, is on
[Kafka clients](/benchmarks/kafka-clients/) in the benchmarks.

## Limits

- Fetch stops at version 6, before fetch sessions (KIP-227), so a consumer names all of its
  partitions in every fetch. At hundreds of partitions that costs nothing; at 100,000 it is most of
  the gap to Queen's own clients.
- Records are stored decoded, one message each, and fetch answers carry them in uncompressed
  batches. A producer's compression saves bandwidth into the broker only, and librdkafka-based
  producers do not compress zstd at all here (librdkafka waits for Fetch version 10).
- No KIP-848 groups and no static membership: keep `group.protocol=classic` (the default of every
  Kafka 4.x client) and leave `group.instance.id` unset, or the consumer fails when it joins.
- No DeleteRecords, so `kafka-delete-records.sh` fails and Kafka Streams cannot purge its
  repartition topics.
- Of a topic's configs only `retention.ms` and `cleanup.policy` are applied, at creation, and
  AlterConfigs, IncrementalAlterConfigs, OffsetDelete, DescribeLogDirs and the ACL calls are not
  offered in 2.6
  ([reference](/reference/kafka/#apis-and-versions)).
- No TLS listener: keep the Kafka port on a private network, or terminate TLS in front of it.
- A partition that retention has emptied and that nobody has written to for 30 days
  (`PARTITION_CLEANUP_DAYS`) is removed, and the next record written to it starts again at offset 0.
- Right after a topic is created through another node, the leader can answer ListOffsets for it
  with `UNKNOWN_TOPIC_OR_PARTITION` for up to a second.
- The facade's own tests run in CI; the client suites under `protocols/queen-kafka/compat/` are run
  by hand, last on 2026-10-20. The Jepsen campaign behind [guarantees](/concepts/guarantees/) used
  the HTTP API and did not cover the facade.
