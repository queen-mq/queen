Consuming a message does not remove it: a segment stays until retention deletes it, and a
consumer group's progress is one number per partition. Replay is moving that number.
**Subscription modes** decide where a group starts on first contact; **seek** moves an
existing cursor, forwards or backwards, at any time. A replay into a fresh group is one pop:

## Where a new consumer group starts

A pop carries two optional parameters:

| Parameter | Values | Effect on a cursor being created |
| --- | --- | --- |
| `subscriptionMode` | `new` (default), `all` | `all` delivers the whole retained backlog; `new` skips it. A pop with no `consumerGroup` is always `all`. |
| `subscriptionFrom` | `now`, an ISO 8601 timestamp | `now` behaves like `new`; a timestamp starts at that point in the log. |

**Seeding happens only on the first contact between a consumer group and a partition.** Once
the `(partition, group)` row exists, its cursor is never re-seeded: passing
`subscriptionMode=new` to a group that has already consumed changes nothing, and neither
does removing it. Moving an existing cursor is what seek is for.

What each mode writes:

- `all`: just below the oldest retained offset.
- `new` or `subscriptionFrom=now`: the partition's current last offset, so only messages
  pushed after this moment are delivered.
- A timestamp: just below the first segment whose commit time is at or after it; if nothing
  that recent exists yet, the current last offset, a future-only cursor.

An unparsable timestamp is treated as registration-time `new` rather than failing the pop.

## Seek

Two routes, per queue and per partition:

```http
POST /api/v1/consumer-groups/:group/queues/:queue/seek
```

```http
POST /api/v1/consumer-groups/:group/queues/:queue/partitions/:partition/seek
```

The body is either `{"toEnd": true}` or `{"timestamp": "2026-07-30T00:00:00Z"}`. A body
with neither is rejected with `Must specify toEnd=true or a timestamp`, unparsable JSON with
a `bad body` error. The per-partition route accepts an **empty** body as `toEnd: true`; the
per-queue route does not. From the SDKs the same call is one admin method, here rewinding a
group by an hour:

<Render file="snippets/js-seek" />

The per-queue form applies to every partition and answers `partitionsUpdated`; a missing or
partitionless queue reports `Queue not found or has no partitions` rather than a successful
no-op, so a misdirected seek does not look like it worked. The per-partition form answers
`updated: true`, or a not-found error.

Every seek, on every partition it touches:

- sets `committed` to the resolved position;
- releases any live lease (an in-flight batch is abandoned, not acked);
- resets the retry budget and redelivery counters;
- creates the `(partition, group)` row if the group never popped that partition;
- clears the empty-scan watermark so cold partitions are re-examined.

Replay begins on the next poll: the candidate set re-seeds immediately, with no periodic
rescan to wait for. A seek touches exactly one consumer group; that independence is the
point of keeping messages after consumption.

## A timestamp seek is segment-granular

A segment is one row holding many packed frames, with one commit timestamp for the whole
row. A timestamp seek walks segments, not messages: the cursor is set to `base_offset - 1`
of the first segment whose commit time is at or after your timestamp.

<pre class="mermaid">{`
flowchart LR
  S1["segment base 0<br/>created 10:00"] --> S2["segment base 100<br/>created 10:05"] --> S3["segment base 200<br/>created 10:10"]
  T["seek to 10:05"] -->|"first commit time at or after it"| S2
  S2 -->|"base_offset - 1"| C["committed = 99<br/>next poll starts at 100"]
  OLD["cursor was 250"] -.->|"moves backward"| C
`}</pre>

The walk compares your timestamp against one stamp per segment, so the cursor can only land
on segment boundaries: you will receive some messages committed slightly *before* your
timestamp, bounded by one segment's frame count. Never treat a timestamp seek as an exact
cut: seek a little early and filter in the consumer. The `subscriptionFrom` timestamp mode
uses the same walk.

Timestamps work as positions because `created_at` is stamped under the same partition row
lock that allocates offsets: per partition it is monotone in offset, so one forward walk
finds the boundary. Across partitions there is no such relationship; a queue seek positions
each partition independently, and no global instant cuts all partitions at the same point
([Guarantees](/use/concepts/guarantees)).

## The durable subscription record

The first time a group pops a queue, the broker durably records its subscription (mode and
registration timestamp) and seeds the cursor of **every** partition in one set-based
statement. The record matters for a partition created *later*: on first contact the broker
seeds from the stored subscription rather than the partition's last offset, so a partition
that appears after the group subscribed does not silently skip its own backlog.

A pop with no `consumerGroup` uses the internal queue-mode cursor, which always registers
as `all`: subscription modes are ignored there, and a queue-mode pop never skips a backlog.

## Changing the stored subscription

```http
POST /api/v1/consumer-groups/:group/subscription
```

Body: `{"subscriptionTimestamp": "2026-07-30T00:00:00Z"}`. The field is required; omitting
it is a `400`. This is narrower than it looks: it updates the stored timestamp for **every**
queue the group has a record for (there is no queue filter), it clears the group's
empty-scan watermarks so caught-up partitions become visible to the next poll again, and it
does **not** move any existing cursor. It changes where *future* first contacts start. For
an actual replay, use seek.

## The floor: you can only replay what is retained

Every walk starts at the partition's retention watermark. A timestamp older than the oldest
retained segment resolves to that oldest segment, with no error telling you the earlier
data was deleted; data that retention has deleted cannot be replayed by any means, so the
retained window *is* the replay window; and a cursor left below the watermark resumes at the
next offset that still exists, because the pop scan tolerates the gap. Which window you get
is on [Retention](/use/concepts/retention).

## Practical recipes

- **Reprocess the last hour for one group.** Seek that group's queue one hour back. Other
  groups keep their positions.
- **Skip a backlog you no longer care about.** Seek the queue with `{"toEnd": true}`.
- **Bring up a new consumer that must not see history.** Pop with `subscriptionMode=new` on
  first contact, cheaper than seeking afterwards.
- **Re-run a pipeline from scratch.** A *new* consumer group name with
  `subscriptionMode=all` reads the whole retained log without disturbing the existing group.
- **Give up on a stuck batch.** A seek releases the lease, so it also abandons an in-flight
  claim without waiting for its expiry.
