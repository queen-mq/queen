A pop that is not auto-acknowledged removes nothing: it takes a **lease** on a span of
offsets, a claim that expires. Until an ack releases it, or it expires on its own, no other
consumer in the same group can take that partition. Three routes drive the lifecycle:

```http
POST /api/v1/ack                     # status completed, retry, failed or dlq
POST /api/v1/lease/:leaseId/extend   # give a slow batch more time
GET  /api/v1/dlq                     # read what was dead-lettered
```

## What to reach for

- Can succeed later: ack `retry`. No budget charge, immediate redelivery.
- Broke: ack `failed` with an `error`. The budget decides redelivery or dead-letter.
- Never again: ack `dlq`. Straight to the dead-letter queue.
- Needs more time: extend the lease, or raise `leaseTime`. Expiry is not a retry mechanism:
  it redelivers the whole span, forever, without escalating.

Cursor arithmetic: [Acknowledgement is an offset commit](/use/concepts/ack).

## What a lease is

A pop reads forward from `committed + 1` up to the batch budget and writes onto the
`(partition, consumer group)` row: `worker_id` (the lease id), `lease_expires_at`
(`now + leaseSeconds`) and `batch_end`, the inclusive last offset delivered. The leased
span is `(committed, batch_end]`; the cursor moves only when you ack, so if nothing acks,
the span is simply claimed by someone else later.

`leaseId` is broker-minted, never client-supplied, one id for all partitions of a
multi-partition pop. An auto-acked pop takes no lease: it commits the cursor in the reading
transaction and reports an empty `leaseId`
([`autoAck`, and what it costs](/use/concepts/consuming#autoack-and-what-it-costs)).

The claim skips live leases, so there is **exactly one leased batch per
`(partition, consumer group)`**: parallelism comes from partitions, fan-out from groups
([Consuming](/use/concepts/consuming#one-leased-batch-per-partition-group)).

## Effective lease time

Precedence: `?leaseSeconds=N` on the pop when `N > 0`, then the queue's stored `lease_time`,
then 60 seconds. The stored value depends on how the queue came into existence:

| How the queue was created | Effective `leaseTime` |
| --- | --- |
| Implicitly, by the first push | **60 seconds** (the queue row's own default) |
| By an explicit `/configure` that omits `leaseTime` | **300 seconds** (the configure default) |
| By an explicit `/configure` with `leaseTime` set | Whatever you set |

An unconfigured queue redelivers a stalled batch after a minute; after one `/configure`
call, five. The broker caches per queue and invalidates on `/configure`, so a change applies
on the next pop. **`/configure` is a [full replace](/reference/queue-options): any omitted
option, `leaseTime` and `retryLimit` included, resets to its default.**

## Extending a lease

```http
POST /api/v1/lease/:leaseId/extend
```

The body is `{"seconds": 60}`; an empty body means 60. The call renews **every live lease
held by that lease id** and never shortens one. The response is always HTTP `200`:

```json
{
  "leaseId": "0191…",
  "success": true,
  "renewed": 2,
  "newExpiresAt": "2026-07-30T12:34:56.000000Z",
  "expiresAt": "2026-07-30T12:34:56.000000Z",
  "lease_expires_at": "2026-07-30T12:34:56.000000Z"
}
```

`renewed` counts the rows touched; `success` is `renewed > 0`, so an expired lease reports
`success: false`. Expiry is final, there is no reclaim. The three timestamp keys carry the
same value (the earliest expiry across the renewed rows) under the names different clients
look for. The JavaScript consumer can auto-renew: off by default, per consumer.

## When a lease expires

There is no timer and no sweeper: the next pop for that partition and group finds the lease
dead, claims the row, and delivers **from `committed + 1` again**, the entire un-acked
span, messages your handler finished but did not ack included.

Expiry never charges the retry budget and never dead-letters: a slow consumer is not a
failing consumer, and a message that always outlives its lease redelivers forever.
Redelivery increments `attempt_count`, telemetry only.

An explicit nack redelivers **immediately**: the release promotes the partition back into
the broker's candidate set and wakes parked long-polls. Nothing spaces out attempts, so if
you need a gap, wait inside your handler before nacking.

## The retry budget

One counter per `(partition, consumer group)`, not per message: `batch_retry_count`,
against the queue's `retryLimit` (default 3). An ack whose lowest explicit signal is
`failed` charges one while budget remains: the lease releases, the cursor keeps the
completed prefix, the failed message and everything after it redeliver. `retry` and lease
expiry charge nothing. A completed batch resets the counter, as does a dead-letter filing.

So "three retries" means three `failed` acks against that lane before the head message
dead-letters, and a partition failing on different messages spends the same shared budget.

<pre class="mermaid">{`

  W --> L: pop claims the span
  L --> C: ack completed
  L --> W: ack retry, budget untouched

  L --> D: ack dlq, or failed with no budget left
  L --> X: failed with no budget left, dead-lettering off
`}</pre>

Three arrows come straight back, and only one moves the budget; the loop through expiry has
no exit.

## Transition to the dead-letter queue

A `failed` ack with no budget left, or an ack with status `dlq` (which bypasses what
remains), dead-letters the head un-acked message. Two halves, because only the broker can
decompress a segment: SQL advances the cursor over the completed prefix, keeps the lease
and reports the poison offset; the broker snapshots id, transaction id and payload into a
`queen.log_dlq` row, advances past the poison message, resets retry state and releases the
lease. The items report `dlq: true` with your `error`, falling back to `Retries exhausted`.

**Dead-lettering is on when `deadLetterQueue` or `dlqAfterMaxRetries` is true (both default
true); with both false, an exhausted `failed` drops the message: cursor advanced, payload
gone.** Choose that data loss deliberately.

<Aside type="caution">
If retention has already deleted the segment covering the poison message, the broker cannot
snapshot it and the items come back with `dlq rejected`. The cursor does not advance. A
dead-letter path only works inside the retained window. See
[Retention](/use/concepts/retention).
</Aside>

## Reading the dead-letter queue

```http
GET /api/v1/dlq
```

The handler reads exactly four query parameters: `queue`, `consumerGroup`, `limit` (default
100) and `offset` (default 0). The date and partition filters some SDK builders send are
silently ignored: filter client-side. `total` counts *this page*, not the whole queue, so
paginate until a short page comes back.

| Entry field | Notes |
| --- | --- |
| `id`, `transactionId`, `partitionId`, `queue`, `partition`, `consumerGroup` | Identity of the filed message |
| `errorMessage`, `retryCount` | The recorded error, and the budget consumed at filing |
| `data` | The payload snapshot, stored verbatim; on an encryption-enabled queue it is the envelope, decrypted by the broker on read |
| `createdAt`, `failedAt` | Always equal: one frame's enqueue time is not recoverable from a packed segment, so the dead-letter time is reported for both |
| `producerSub` | Always `null`; not tracked on the snapshot |

## Getting a message out of the dead-letter queue

Two routes, both addressed by `(partitionId, transactionId)`:

```http
POST /api/v1/messages/:partitionId/:transactionId/retry
```

Re-pushes the stored snapshot to its original queue and partition, then deletes the
dead-letter row. The replay gets a **fresh transaction id**: reusing the original would be
suppressed as a duplicate. The row is removed only after the push is accepted: a failed
push leaves the message dead-lettered, and a failed cleanup delete after a successful push
answers `replayed: true`, `dlqRowRemoved: false`, the message in both places.

```http
DELETE /api/v1/messages/:partitionId/:transactionId
```

Deletes the dead-letter row and nothing else. Live messages sit in immutable segments and
cannot be deleted, so any address without a dead-letter row is a `404`.

Reprocessing is one message at a time, and each replay mints a new id: replaying twice
produces two messages. There is no bulk replay, purge or scheduled purge: rows survive
retention and leave only through these routes or queue deletion. The SDK helpers
`clearQueue()` and `moveMessageToDLQ()` call routes the broker does not register and always
return `404`. An unattended dead-letter queue grows without bound.
