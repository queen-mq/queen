Queen is a queue with two halves, and knowing which half you are looking at explains most of
its behaviour. **The Kafka half is the log**: a queue is split into partitions, each message
gets a monotone integer offset inside its partition, and a consumer group owns one cursor per
partition, so groups read the same data independently and can be moved backwards. **The
RabbitMQ half is the work queue**: a consumer claims a batch under a lease, reports each
message as completed, failed, retried or dead-lettered, and a message that exhausts its retry
budget is copied into a real dead-letter table.

Where the halves would contradict, the log wins. Progress is a cursor, not per-message rows,
and a message's state is the arithmetic between its offset and that cursor: done at or below
it, in flight inside the leased span, waiting above it.

```text
push  ->  queue "orders"
            partition "cust-42"    offsets:   0   1   2   3   4   5
                                   segments: [ 0 .. 2 ][ 3 .. 5 ]

          group "billing"   committed = 2   ->  next wanted = 3
          group "audit"     committed = -1  ->  next wanted = 0
```

A push to `orders` / `cust-42` locks the partition row, allocates the next offsets, and
writes one segment; `created_at` is stamped under the lock, so it is monotone per partition,
which retention and timestamp seeks rely on. A pop by `billing` claims from `committed + 1`
under a lease; `audit` is a different row, unaffected. Acking offset 5 as `completed` sets
`committed = 5`: offsets 3 and 4 are done too, acked or not, because the cursor is the only
record of progress. If the consumer dies, the lease expires and the next pop re-delivers
from offset 3.

One queue, one ordered lane per entity, one independent cursor per lane per group: both
groups read the same messages at their own positions, nothing is copied, and neither holds
the other up.

## The vocabulary

| Term | What it is |
| --- | --- |
| **Queue** | A named container with a configuration. Created implicitly by the first push to it, or explicitly with `POST /api/v1/configure`. |
| **Partition** | An ordered lane inside a queue, created the first time you push to its name. The default name is `Default`. One row in `queen.log_partitions`. |
| **Offset** | A per-partition `BIGINT`, allocated monotonically under that partition's row lock. It is not global, not a timestamp, and not comparable across partitions. |
| **Segment** | One row in `queen.log_segments` holding many messages as length-prefixed frames, packed and zstd-compressed, covering an inclusive offset range. It is the unit of storage, of retention, and of a timestamp seek. |
| **Consumer group** | A named reader of a queue. Each group has its own cursor per partition. Omitting a group puts you in the implicit group `__QUEUE_MODE__`. |
| **Cursor** (`committed`) | The last acked offset for one (partition, group), in `queen.log_consumers`. Everything at or below it is done; the next message the group wants is `committed + 1`. |
| **Lease** | A claim on the span `(committed, batch_end]` for one (partition, group), carrying a worker id (the `leaseId` you echo back on an ack) and an expiry. |
| **Ack** | An offset commit that moves `committed`. On the wire it is addressed by `transactionId` plus `partitionId`, not by offset. |
| **`transactionId`** | The idempotency key of a push, and the address of a message in an ack. You supply it; if you omit it the broker uses the message id it minted. |
| **Namespace and task** | Two labels on a queue. They are what a discovery pop and the namespace/task listings match on. |
| **DLQ** | `queen.log_dlq`, a real table. A message whose retry budget runs out on a DLQ-enabled queue is copied there with its payload and the failure reason. |

There is no per-message row anywhere in that list: consumption state for a whole partition
is one row per group holding one integer, so ten thousand partitions cost ten thousand rows,
not files or processes.

## The five invariants

1. **Order is per partition, in commit order.** At most one write per partition is in flight
   at a time, so offset order equals commit order; there is no
   [global ordering](/use/concepts/guarantees) across partitions.
2. **One in-flight leased batch per (partition, group).** A second consumer in the same group
   gets nothing from a leased partition until the lease is acked or expires, so
   [parallelism inside a group](/use/concepts/consuming) is bounded by the number of
   partitions, not workers.
3. **An ack is an offset commit.** Acking message N completes every earlier unacked message
   in that partition for that group; mixed outcomes clamp the cursor below the lowest failure
   signal. See [Ack semantics](/use/concepts/ack).
4. **Deduplication is exact, per partition, and windowed.** A repeated `transactionId` inside
   `dedupWindowSeconds` (default 3600, enabled) writes nothing and returns
   `status: "duplicate"`. See [Producing](/use/concepts/producing).
5. **Delivery is at-least-once.** A leased pop plus an explicit ack can redeliver but cannot
   lose; `autoAck=true` commits inside the pop and is
   [at-most-once](/use/concepts/consuming#autoack-and-what-it-costs).

## Where the model draws its boundaries

<Aside type="caution">
These are design decisions, not configuration options.
</Aside>

- **No global ordering.** Total order is per partition; a correctness argument spanning
  partitions cannot rest on it.
- **No priority queueing.** A partition is drained from its cursor forward.
- **No per-message delivery rows.** Offset against cursor and leased span is the whole story;
  nothing per-message exists to clean up or disagree with it.
- **No client-side assignment or rebalancing.** No partition assignments, no membership
  protocol: a restart is cheap, a dead consumer is recovered by lease expiry, and you cannot
  pin a worker to a partition through the broker.
- **No bulk DLQ requeue.** One address at a time is deleted or replayed, and a replay
  re-pushes the stored payload under a fresh `transactionId`. See
  [Leases, retries and the DLQ](/use/concepts/leases-retries-dlq).
