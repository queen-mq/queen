A queue is a named container with a configuration. A partition is an ordered lane inside it.
Neither is declared before use: a push to a queue and partition that do not exist creates
both, in the transaction that stores the message.

```bash
curl -s -X POST http://localhost:6632/api/v1/push \
  -H 'Content-Type: application/json' \
  -d '{
    "items": [
      { "queue": "orders", "partition": "cust-42", "payload": { "id": 1 } },
      { "queue": "orders", "payload": { "id": 2 } }
    ]
  }'
```

One request, one new queue, two new partitions: `cust-42` and `Default`, the name used when
`partition` is omitted.

## A queue is created in one of three ways

- **A push**, as above, provisions the queue's `queen.queues` configuration row and the
  partition named in the request.
- **`POST /api/v1/configure`** creates the queue if missing, rewrites it if not, and creates
  no partitions.
- **A queue-scoped pop** on a missing name creates the configuration row with column
  defaults, so a group can subscribe before the first push. The flip side: a typoed consumer
  queue name creates an empty queue.

One default differs: the lease-time column default is 60, while `/configure` writes an
explicit 300 when `leaseTime` is omitted:

| Queue created by | `leaseTime` in effect |
| --- | --- |
| A push or a pop | 60 seconds |
| `/configure` with no `leaseTime` | 300 seconds |

**`/configure` is a [full replace](/reference/queue-options), not a patch: every omitted
option, `namespace` and `task` included, resets to its default.**

## Partitions are created on first push

Partition names are opaque strings; identity is the pair (queue, name). No preallocation, no
fixed count to pick up front: partition by the entity whose order you care about (a customer,
a device, a document) and let the set grow.

A lane empty and untouched for `PARTITION_CLEANUP_DAYS` (30 by default) is reclaimed by
maintenance; one still holding segments, dead-letter rows, streaming state or a live lease is
never deleted, whatever its age. A later push recreates the lane under a new id, starting
from offset 0.

## What a partition costs

| Per partition | Per (partition, consumer group) |
| --- | --- |
| One row in `queen.log_partitions` (the offset allocator, the retention watermarks, and `last_write_at`) | One row in `queen.log_consumers` (the cursor, the current lease, the retry counter) |

Messages are packed into segment rows, many per row, so a thousand partitions of ten
messages each costs far less than ten thousand message rows. Two details show up as
behaviour:

- **`last_write_at` is quantised to one real update per second.** A wildcard pop finds
  recently written partitions through it, so candidate selection tolerates staleness and
  searches with two minutes of slack.
- **Cursor rows are bulk-seeded on first contact.** The first wildcard or discovery pop of a
  (queue, group) [creates a `log_consumers` row for every partition](/use/concepts/replay) in
  one statement: 10,000 partitions, 10,000 rows, once.

## How many partitions is reasonable

Thousands per queue are ordinary: the [ordered-pipeline benchmark](/benchmarks/ordered-pipeline)
verified 88,503,408 messages over 1000 partitions at 25,000 events/s with 0 duplicates, 0
gaps and 0 order violations.

What bounds the useful count is discovery, not storage. A wildcard pop never scans the whole
set: it takes a capped candidate list (at most 256 names from the broker-side ring, 512 from
the SQL fallback), candidates are recently written partitions in random order so consumers
spread out, and an empty-ring re-poll short-circuits in memory while a bounded correctness
re-walk runs every 30 s. Exact clamps and ring mechanics:
[the life of a pop](/internals/life-of-a-pop).

Tens of thousands of partitions work; a partition per message does not: each still costs a
row, paid on cold discovery and in the per-group cursor rows above.

## Namespaces and tasks

A queue carries two optional labels, `namespace` and `task`, so a consumer can ask for work
without naming a queue:

```text
GET /api/v1/pop?namespace=orders&consumerGroup=billing
GET /api/v1/pop?task=email
```

A discovery pop resolves every queue whose configuration row matches the labels and
wildcard-pops across their partitions in one call; a request with neither label is a `400`.

<pre class="mermaid">{`
flowchart LR
  POP["discovery pop<br/>namespace=orders"] --> Q1
  POP --> Q2

  Q1["queue orders.email<br/>namespace orders, task email"] --> P1["partition Default<br/>offsets 0,1,2"]
  Q1 --> P2["partition cust-42<br/>offsets 0,1"]
  Q2["queue orders.invoice<br/>namespace orders, task invoice"] --> P3["partition Default<br/>offsets 0,1,2,3"]
  Q3["queue orders.audit<br/>namespace empty, task empty"] --> P4["partition Default"]
`}</pre>

The labels select queues, they do not contain them: the unlabelled queue is reachable by
name but invisible to discovery. They are set in two ways, and the interaction is the
sharpest edge here:

- **A push derives them from a dotted queue name**: `orders.email` gives namespace `orders`,
  task `email`; no dot gives the whole name as namespace and an empty task.
- **`/configure` sets them explicitly**; being a full replace, omitting them writes empty
  strings.

<Aside type="caution">
A queue created by `/configure` with no `namespace` or `task` (what the SDK `create()`
helpers do unless you call `.namespace()` / `.task()`) has both labels empty: discovery
never matches it and the listings omit it. `/configure` on a queue whose labels came from a
dotted push name also wipes them.
</Aside>

## Listing what exists

| Route | Returns |
| --- | --- |
| `GET /api/v1/resources/queues` | Every queue, each enriched with a live partition count and segment/message counts |
| `GET /api/v1/resources/queues/:queue` | One queue's detail, plus its segment and message counts; `404` if it does not exist |
| `GET /api/v1/resources/namespaces` | Namespaces with queue, partition and message rollups |
| `GET /api/v1/resources/tasks` | The same rollup keyed by task |
| `GET /api/v1/resources/overview` | System-wide counters |

Three caveats about those numbers:

- The queue list **accepts `namespace` and `task` query parameters and does not apply them**;
  filter client-side.
- `messages.total` in the queue list is the **retained** frame count, acked or not;
  `pending` and `processing` come from the periodically refreshed statistics table and lag.
- The namespace and task listings count partitions from a catalog the log engine does not
  write: a push-created queue reports **0 partitions** there. The queue list overlays the
  live count and is exact.

## Deleting a queue

`DELETE /api/v1/resources/queues/:queue` requires admin access and removes the queue's
partitions, segments, deduplication sidecar, consumer cursors, and dead-letter rows.
Retention never touches DLQ rows, so deleting the queue (or deleting/replaying one address)
is the only way they go away.

Delete is idempotent and always answers `200` (the SDKs use delete-then-create as cleanup):
`deleted` is `true` only when a queue was actually removed, otherwise `false` with
`Queue not found, nothing was deleted`.
