Queen promises order per partition, PostgreSQL durability, at-least-once delivery on leased
pops, and exact push deduplication inside a window. Here is the deduplication promise doing
its job, the second push writing nothing:

Every promise, with its boundary:

| Property | Guarantee | Boundary |
| --- | --- | --- |
| Ordering | Total order per partition, in commit order | None across partitions; none by priority |
| Durability | PostgreSQL commit | `buffered` means broker disk, not the database |
| Delivery (leased) | At-least-once | Duplicates on expiry, nacks and restarts |
| Delivery (`autoAck`) | At-most-once | Loss on a lost response or a crash |
| Push deduplication | Exact, per partition, inside the window | Hash identity; off when the window is 0 |
| Consumption | Not exactly-once | Ack is an offset commit, not a receipt |

The consumption rows are on [Acknowledgement is an offset commit](/use/concepts/ack) and
[Transactions](/use/concepts/transactions).

## Ordering

**Order is per partition, in commit order.** Offsets are single monotone integers allocated
under the partition's row lock and fixed at commit, so they have no gaps in steady state and
commit timestamps increase with offset, the invariant behind time-based retention and
timestamp seeks. See [Replay and subscription modes](/use/concepts/replay).

Not promised: global ordering (a timestamp is not a consistent cut across a queue),
priority ordering (nothing reorders a partition), and cross-partition atomic visibility (a
multi-partition push commits at once, but each partition's consumers see it when they
poll).

Within a group, the one-lease rule adds serialisation: one leased batch per partition per
group. A nack rewinds to the failed message and redelivers everything after it, so parallel
handlers inside one partition trade order for throughput.

Measured end to end: a four-stage pipeline verified 88,503,408 messages with **0
duplicates, 0 gaps and 0 order violations**
([the ordered pipeline benchmark](/benchmarks/ordered-pipeline)).

## Durability

Durability is PostgreSQL's. The broker holds no committed state: a push is durable when its
transaction commits, and survives a broker restart because the broker was never where it
lived. **HTTP 201 on a push does not mean "in PostgreSQL"**. Read the per-item `status`:

| `status` | Meaning |
| --- | --- |
| `queued` | Committed to PostgreSQL. Durable. |
| `duplicate` | Not written; an identical transaction id already exists in the window. The response carries the original message id. |
| `buffered` | **Not in PostgreSQL.** The database write failed and the payload was written to the broker's local disk spool for later replay. |
| `failed` | Neither stored nor spooled. Lost unless you retry. |

`buffered` payloads replay oldest-first with their transaction ids preserved once the
database is back ([mechanics](/selfhost/durability)). That is one broker's disk, not your
replicated database: on an ephemeral disk, `buffered` is a warning. An ack is durable the
same way: the cursor moves when the transaction commits and the item returns
`success: true`; anything else means it did not move.

Sustained evidence: a 24-hour soak moved 86,369,975,300 messages at roughly 1,000,000 per
second per side with explicit acknowledgement, 0 restarts and flat broker memory
([Throughput 24h 1M](/benchmarks/soak-24h)).

## Delivery

Two modes, chosen per pop. **Leased pops (`autoAck=false`) are at-least-once**: the cursor
moves only on ack, and a dead consumer's lease expires and redelivers the whole span.
Nothing is lost; some things arrive twice. The default, and the right choice for work that
matters.

**Server-side auto-ack (`autoAck=true`) is at-most-once**: the pop commits the cursor in the
transaction that reads the messages and returns no lease, so a crash before processing or a
lost response loses those messages
([`autoAck`, and what it costs](/use/concepts/consuming#autoack-and-what-it-costs)). The
SDKs' client-side auto-ack is different: a real ack after your handler returns (a nack if it
throws), still at-least-once.

## Deduplication is exact inside its window

On by default with a 3600-second window (`dedupWindowSeconds`), per partition, keyed on your
`transactionId`. A duplicate writes **nothing at all** and returns `status: "duplicate"`
with the original message's id. The verdict is a SQL probe of a 128-bit hash sidecar under
the same row lock that allocates offsets, so no concurrent push can slip past it and no
probabilistic filter or cache decides ([Deduplication internals](/internals/dedup)).
First-wins also holds within a single push or fused batch: a repeated id stores once, the
repeats report `duplicate`.

The bounds:

- **Per partition.** The same transaction id in two partitions is two messages.
- **Window-bounded.** Outside the window, or after the sidecar row is purged
  ([its own retention](/use/concepts/retention#the-ack-window-is-separate)), a repeat is a
  new message.
- **Identity is the hash.** Two ids colliding in 128 bits would be one message; the
  probability is negligible.
- **Off means off.** `dedupWindowSeconds: 0` removes the probe; mind that `/configure`
  resets an omitted window back to 3600.

Deduplication guards the *push* side. It does not make consumption exactly-once.

## Where duplicates still come from

All of these are normal operation: lease expiry and nacks (the cursor clamps at the lowest
explicit failure, so everything after it comes back, ones acked `completed` in the same call
included), a broker restart or lost ack (the lease expires normally), an ack outside the
hash window (reported `unresolvable`, the message redelivers rather than being dropped), a
transaction retried after a lost response without deterministic ids, and a dead-letter
replay (deliberately a fresh transaction id).

Two levers make them harmless: idempotent handlers keyed on the message's `transactionId`,
which survives redelivery unchanged, and deterministic transaction ids on pushes so retries
collapse inside the window.

## What each failure looks like

### A broker crash

- Uncommitted in-flight pushes got no response: retry them. Deterministic ids make the retry
  accepted or reported `duplicate`.
- Leases are not released early; redelivery waits up to the queue's lease time.
- Undrained spool files replay when that broker restarts. A broker that never comes back
  takes its spool with it.
- Other brokers keep serving; there is no leader election on the delivery path.

A clean stop differs only in degree: `SIGTERM` drains in-flight requests, but held leases
still wait out their expiry ([restarts](/selfhost/probes-restarts)).

### A database failover or outage

- Pushes spool to disk and report `buffered` under HTTP `201`; replay starts when
  connections return.
- Pops and acks fail outright. No cursor moves, nothing is lost, leases expire meanwhile.
- `GET /health` does a real database round-trip and returns `503`: a readiness signal,
  [never a liveness probe](/selfhost/probes-restarts#the-liveness-probe-trap).
- What survives is exactly what PostgreSQL confirmed committed. Queen adds nothing on top of
  your replication configuration and cannot compensate for one that acknowledges writes it
  can lose.

### A client crash

- Leased-but-unacked messages redeliver in full, including ones the handler finished but
  had not acked: this is what makes idempotent handlers mandatory.
- Messages acked before the crash stay acked; the cursor is durable.
- With server-side `autoAck=true`, everything in the last response is lost.
- **A crash charges nothing against the retry budget, so a crash-looping consumer
  redelivers forever without ever dead-lettering.** Watch redelivery counts, not just the
  dead-letter queue.
