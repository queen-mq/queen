One route, `POST /api/v1/transaction`, bundles pushes and acks into a single PostgreSQL
transaction: everything in the call commits together or nothing does. The pattern it exists
for is the pipeline handoff, an ack of the input and a push of the output that cannot come
apart:

<Render file="snippets/js-transaction" />

There is no window in which the output exists without the input being consumed, or the
reverse. No ordering of two separate calls gives you that property.

Chained across stages, no hop can lose work or emit an orphan: the commit that records the
consumption is the commit that records the production, and a failed attempt rolls back both
halves. The duplicate risk that remains is a client retry after a lost response. See
[the limit](#the-limit-this-is-not-end-to-end-exactly-once).

## The shape of a call

```http
POST /api/v1/transaction
```

```json
{
  "operations": [
    { "type": "ack", "transactionId": "in-42", "partitionId": "8f1c…", "status": "completed" },
    { "type": "push", "queue": "orders.shipped", "partition": "eu", "payload": { "id": 42 } }
  ],
  "requiredLeases": ["0191…"]
}
```

Only `push` and `ack` operations exist. Anything else fails the request with `400` and
`segments transaction supports only push and ack operations`, before any work is attempted.
A `push` carries one message inline or an `items` array (`queue`, optional `partition`
defaulting to `Default`, `payload` or `data`, optional `transactionId` and `traceId`); an
`ack` takes `transactionId`, `partitionId`, optional `status` defaulting to `completed`,
`consumerGroup` and `leaseId`, with exactly the meanings on
[Acknowledgement is an offset commit](/use/concepts/ack).

## What rolls a transaction back

The stored procedure raises on every failure path, and a raise takes down every other
operation in the call, pushes that already ran included:

- **A duplicate push.** On a deduplication-enabled queue, a `transactionId` already inside
  the window raises `QDUP`. A plain push reports `status: "duplicate"` and carries on;
  all-or-nothing leaves no such option. With deduplication off there is no probe, and the
  message stores again.
- **A rejected ack.** An invalid or expired lease, a position beyond the leased batch, or a
  missing consumer row.
- **An ack for an unknown transaction id**, checked *before* the procedure runs against the
  partition's hash sidecar:
  `QTXN ack references unknown transactionId; transaction rolled back`, database untouched.
  Otherwise the pushes would commit while the bogus ack quietly moved nothing.
- **An unresolvable partition or queue name**, on either kind of operation.

A rolled-back transaction leaves cursors, offsets and segments exactly as they were.

## Reading the response

The route answers HTTP `200` **even when the transaction failed**:

```json
{
  "transactionId": "0191…",
  "success": false,
  "error": "QDUP duplicate messages in queue \"orders.shipped\" partition \"eu\"; transaction rolled back",
  "results": []
}
```

On success, `results` is one entry per operation, in request order: pushes carry
`transactionId`, `messageId`, `queueName` and `duplicate: true` when an item repeated an
earlier one; acks carry `transactionId` and `dlq`.

<Aside type="caution">
`success` is in the body, not the status line. The JavaScript transaction builder raises on
`success: false` for you; a raw HTTP caller must read the field. `transactionId` at the top
level is a per-call identifier minted by the broker. It is not one of your message ids.
</Aside>

Two facts about the ack entries: they always read as successful when the transaction
commits, because the per-item honesty of the plain ack routes (`noop`, `already committed`,
`unresolvable`) is not surfaced here, so an ack below the cursor commits and moves nothing;
if you need that signal, ack outside a transaction. And a `transactionId` repeated among the
*pushes* of one call is first-wins within the call, the later item echoing the first item's
`messageId` with `duplicate: true`, no raise; only the duplicate-against-history case above
raises.

## Leases inside a transaction

An ack still proves it owns the lease, resolved per `(partition, consumer group)` in this
order: a `leaseId` on the operation, then the current holder read from the consumer row,
then the single unambiguous entry in `requiredLeases`. A request with no lease information
anywhere skips the ownership check and still advances the cursor, mirroring the plain ack
route. A lease id that has since expired is different: validated, rejected, rolled back.

## Ordering and locks inside the call

Pushes execute in request order; acks in ascending `(partition, consumer group)` order,
regardless of how you listed them. Every multi-partition writer takes partition locks in
ascending partition id before consumer-row locks, so concurrent transactions cannot
deadlock against each other, a plain push, or retention. Bundle freely across partitions
and queues; the `results` array is stamped back to your operation indices, not execution
order.

## The limit: this is not end-to-end exactly-once

Atomicity covers the broker's state, not the network. A lost response (timeout, dropped
connection, client crash after the commit) leaves the client not knowing whether the
transaction committed, and a blind retry can duplicate the pushed messages.

The fix is a deterministic `transactionId` on each pushed item, derived from the input (for
example its transaction id plus a stage name), and a deduplication window longer than your
retry horizon. Then a retry either commits normally, because the first attempt never did, or
is rejected with `QDUP` and **nothing is written twice**: the error means "already applied",
provided your ids really are deterministic and the window really covered the gap. Both
conditions are yours to guarantee; outside the window a repeat is accepted as a new message.
The JavaScript transaction builder sends only `queue`, `partition` and `payload` per item,
so to set a deterministic id inside a transaction, call the HTTP route directly.

What "exact" means for deduplication is on [Guarantees](/use/concepts/guarantees).

## When not to use it

A transaction is one database transaction: it holds locks for its duration and commits
once. A stage that only pushes gets the same durability from a plain batched push, cheaper.
Reach for `/api/v1/transaction` when the coupling matters: a push that must not survive a
failed ack, or the reverse.
