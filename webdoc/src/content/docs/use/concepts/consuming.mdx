Consuming is a pop that claims a batch under a lease, followed by acks that move the group's
cursor past what you finished. A pop is a plain `GET`: no subscribe call, no broker-assigned
partitions, no membership to join.

The cursor stands still throughout: the pop wrote a claim, not a commit, and the lease is
the clock under your handler.

## Consumer groups

A consumer group is a name with one cursor per partition, so groups read the same messages
independently at their own pace; the rows appear on the group's first pop.

Omitting `consumerGroup` puts you in the implicit group `__QUEUE_MODE__`, the
competing-consumers shape: those consumers share one set of cursors, and a message is
delivered to exactly one of them.

<Aside type="note">
A pop with no `consumerGroup` always reads from the start of the retained log: `subscriptionMode=new` is deliberately ignored for `__QUEUE_MODE__`.
</Aside>

## Three shapes of pop

| Route | Shape |
| --- | --- |
| `GET /api/v1/pop/queue/:queue` | The **wildcard pop**, the normal one: claims from any partitions of one queue |
| `GET /api/v1/pop/queue/:queue/partition/:partition` | The **targeted pop**: exactly one named partition, no candidate selection, the cheapest call. Use it when a worker owns a lane by construction. It seeds only the partition it names, so its subscription behaviour differs (below) |
| `GET /api/v1/pop?namespace=&task=` | The **discovery pop**: every queue whose labels match; at least one of `namespace` or `task` is required, else `400`. The response can mix queues, so its top-level `queue` field is empty; ack using each message's own `partitionId` |

Wildcard candidate selection is approximate on purpose: the broker claims from partitions
that probably have work and are not leased, and a stale candidate yields nothing because
cursor and lease are re-verified under the partition row lock.

## Parameters

| Parameter | Default | Meaning |
| --- | --- | --- |
| `batch` | `200` | Maximum messages to return. A budget, not a promise; claimed partitions share it. |
| `partitions` | `1` | Maximum partitions one wildcard or discovery pop may claim from. |
| `consumerGroup` | `__QUEUE_MODE__` | The reading group. |
| `autoAck` | `false` | Commit the cursor inside the pop transaction instead of taking a lease. |
| `wait` | `false` | Long-poll instead of returning immediately when there is nothing to deliver. |
| `timeout` | `30000` ms | How long `wait=true` may block. The broker default comes from `DEFAULT_TIMEOUT`, falling back to `POP_DEFAULT_TIMEOUT_MS`, then 30000. |
| `leaseSeconds` | queue's `leaseTime` | Per-request lease override. A positive value wins over the queue configuration; the fallback when a queue has none is 60 seconds. |
| `subscriptionMode` | `new` | `all` or `new`. Only consulted on a group's first contact. The broker default comes from `DEFAULT_SUBSCRIPTION_MODE`; a pop with no `consumerGroup` is always `all`. |
| `subscriptionFrom` | empty | `now`, or an ISO 8601 timestamp. Only consulted on a group's first contact. |

The SDKs layer their own defaults on top: the JavaScript `pop()` and `consume()` both
default to a batch of 1, and `consume()` sets `wait=true`.

## What comes back

A pop that delivered something returns `200` with:

```json
{
  "success": true,
  "queue": "orders",
  "partition": "cust-42",
  "partitionId": "0198e4c1-...",
  "leaseId": "0198e4c2-...",
  "consumerGroup": "billing",
  "messages": [
    {
      "id": "0198e4c0-...",
      "transactionId": "order-91-created",
      "traceId": null,
      "data": { "orderId": 91, "total": 4200 },
      "producerSub": null,
      "createdAt": "2026-07-30T09:12:44.881Z",
      "partitionId": "0198e4c1-...",
      "partition": "cust-42",
      "leaseId": "0198e4c2-...",
      "consumerGroup": "billing"
    }
  ],
  "partitionsClaimed": 1
}
```

- **Top-level `partition` and `partitionId` are the first claimed partition's**; ack with
  the `partitionId` on the individual message.
- **`createdAt` is the segment's commit timestamp**, shared to the microsecond by messages
  written in one push.

A pop that delivered nothing returns **`204` with no body at all**, also the answer during
pop maintenance mode: treat it as "no messages". The missing body is
[deliberate](/use/errors#the-envelope).

## Long-poll

With `wait=true` a pop that finds nothing parks, releasing its PostgreSQL connection first,
and waits on the queue's wake gate: a push wakes it, and with the default candidate ring
wakes coalesce onto a 5 ms tick, so a hot queue costs a bounded number of wake-ups per
second. With no push it re-checks on an exponential backoff (a wake resets it) and gives up
at `timeout` with the bodiless `204`.

An idle consumer with a 30-second timeout issues about two requests a minute and is woken in
milliseconds when work arrives.

## Subscription modes are decided once

A group's starting position is chosen on its **first contact with the queue** and stored
durably: the first wildcard or discovery pop writes the subscription record and seeds every
partition's cursor in one statement.

| Mode | Where the cursor starts |
| --- | --- |
| `all` (default) | The oldest retained offset: the whole backlog is delivered |
| `new`, or `subscriptionFrom=now` | The partition's current end: the entire existing backlog is skipped |
| `subscriptionFrom=<ISO timestamp>` | Just before the first segment written at or after that timestamp; if nothing is that recent, the current end |

<Aside type="caution">
`subscriptionMode` on later pops has no effect, the stored record wins: to move a group, use the seek routes (`POST /api/v1/consumer-groups/:group/queues/:queue/seek`) or a new group name.
</Aside>

Two consequences: a partition created later is
[seeded from the stored subscription](/use/concepts/replay), so a `new` group receives
everything ever pushed to it; and a targeted pop registers no subscription and seeds only
the partition it names, so if you mix pop shapes for one group, the first to run decides. Timestamp modes land on a segment boundary: replay is
[segment-granular](/use/concepts/replay#a-timestamp-seek-is-segment-granular).

## One leased batch per (partition, group)

The limit to design around: coordination state is one row per (partition, group), with one
`batch_end` and one `worker_id`, so:

- A claimed partition is held until its batch is acked or the lease expires; a same-group
  second consumer is skipped past it, without blocking.
- **Parallelism inside a group is bounded by the number of partitions**, not workers: twenty
  workers on a single-partition queue is one worker's throughput and nineteen idle pollers.
- Different groups never interfere: different rows.

<pre class="mermaid">{`
flowchart LR
  W1["worker 1"] --> R1["row (p1, billing)<br/>leased"]
  W2["worker 2"] --> R2["row (p2, billing)<br/>leased"]
  W3["worker 3"] -.->|"leased, skipped"| R1
  W3 -.->|"leased, skipped"| R2
  W4["worker in group analytics"] --> R3["row (p1, analytics)<br/>leased"]
`}</pre>

Worker 3 just finds nothing free and polls again. For more concurrency, add partitions; with
no natural key you are choosing between ordering and parallelism, and the lane count is
yours.

An expired lease needs no reaper: the next pop ignores it and re-delivers from the cursor
forward, and expiry does **not** consume the retry budget, only an explicit `failed` ack
does. To hold a batch longer, [extend the lease](/use/concepts/leases-retries-dlq)
(`POST /api/v1/lease/:leaseId/extend`).

## `autoAck`, and what it costs

`autoAck=true` makes the pop commit the cursor in the same transaction that reads the
messages: no lease, an empty `leaseId`, nothing to ack.

That is **at-most-once**: the cursor has already moved when the response is written, so a
crash mid-batch or a response lost in the network loses those messages permanently. Use it
where loss is cheaper than duplicate work (metrics, sampled telemetry, cache warming), never
for work you would have to reconcile.

## Delaying visibility

Three queue options, all off by default, change what a pop is allowed to see.

| Option | Effect |
| --- | --- |
| `delayedProcessing` | Seconds a message must age before it becomes visible. Always enforced in SQL, so it applies to every pop shape. |
| `windowBuffer` | Holds a partition back while it is still being written to, trading delivery latency for fatter batches. With the default candidate ring the hold is timed in the broker, ending at the earlier of the window elapsing and the batch filling. |
| `minPopWaitTime` | Milliseconds a **non-empty** but under-full pop may wait for more messages before claiming, so one commit carries more work. Applies only to a pop that asked to block with a `batch` above 1, is clamped to 60000, is bounded by that pop's own deadline, and never delays a pop on an empty queue. |

## After the pop

An ack is an offset commit: acking one message finishes everything before it in that
partition for that group. [Acknowledgement is an offset commit](/use/concepts/ack) covers
statuses, clamping, and the reports for acks below the cursor.
