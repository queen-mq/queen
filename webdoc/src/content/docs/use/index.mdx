The surface you write against is small: push a message, pop it, acknowledge it, and a transaction
that bundles pushes and acks into one PostgreSQL commit. Every application in this section is
those four in a different arrangement.

<Render file="snippets/js-push" />

The queue and the partition are created by the push that names them, so there is nothing to
provision first. [The model](/use/model) is one page: queue, partition, offset, consumer group,
cursor, lease, ack.

Two rules shape everything built on top. An acknowledgement is a commit of a position, not a
receipt for one message, so acking the last message of a batch completes the batch. And a
consumer group holds at most one leased batch per partition, so parallelism comes from partitions,
not from more consumers on one.

Everything is HTTP over a small JSON API, so curl is a client and the SDKs are convenience over
it. Clients hold no coordination state: a worker that restarts does not stall its peers.

What people build with it:

- **Producer and consumer.** One queue, one group, an ack when the work is done:
  [the loop](/use/examples/#producer-and-consumer).
- **Fan-out.** Two groups over one queue, each reading every message, at one copy of the data:
  [fan-out](/use/examples/#fan-out-to-two-groups).
- **Deduplicated ingest.** A deterministic `transactionId`, and the repeat refused by the broker:
  [deduplication](/use/examples/#deduplicated-ingest).
- **Transactional pipeline.** Ack the input and push the next stage in one commit:
  [the pipeline](/use/examples/#transactional-pipeline).
- **Replay.** Move a group's cursor back to a timestamp, or point a new group at history:
  [replay](/use/examples/#replay).
- **Windowed aggregation.** Tumbling, sliding, session and cron windows, with the accumulator in
  the same PostgreSQL: [streams](/use/streams).

Pick a client, write the loop, read [errors](/reference/errors/) before it meets traffic.
