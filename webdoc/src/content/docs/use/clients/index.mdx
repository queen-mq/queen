Every SDK speaks the same HTTP API, so the choice is about ergonomics and completeness, not
about capability. All six wrap the same six calls (push, pop, ack, transaction, lease
renewal, DLQ query) behind a fluent builder with the same method names transliterated into
each language's conventions. The differences are in coverage: the admin surface,
client-side buffering, lease renewal inside the consume loop, and how each one behaves when
a proxy answers `429` or `403`.

If your language is not here, the HTTP API is the SDK. The whole message plane is eight
routes and one header. See the [HTTP quickstart](/use/clients/http).

The SDKs ship at the broker's version, and the HTTP API is the stable compatibility surface.
[Versions and compatibility](/reference/compatibility) states what that covers.

`crates/queen-protocol`, and the broker's own test suite round-trips its request parsers and

a client. Every other SDK re-describes the wire by hand.

## Same grammar, six spellings

Every SDK builds a request the same way: name the queue, narrow it, then act.

<Tabs>

<TabItem label="JavaScript">

```js
await client.queue('orders').partition('acct-42').push([{ data: { id: 1 } }])
```

</TabItem>

<TabItem label="Python">

```python
await client.queue("orders").partition("acct-42").push([{"data": {"id": 1}}])
```

</TabItem>

<TabItem label="Go">

```go
_, err := client.Queue("orders").Partition("acct-42").Push(payload).Execute(ctx)
```

</TabItem>

<TabItem label="Rust">

```rust
queen.queue("orders").partition("acct-42").push(json!({ "id": 1 })).await?;
```

</TabItem>

<TabItem label="PHP">

```php
$client->queue('orders')->partition('acct-42')->push([['data' => ['id' => 1]]])->execute();
```

</TabItem>

<TabItem label="C++">

```cpp
client.queue("orders").partition("acct-42").push({{{"data", {{"id", 1}}}}});
```

</TabItem>

</Tabs>

Two rules hold in all of them, with one exception. `data` (or `payload`) is unwrapped as the
message body; an item with neither key is sent as the body itself. Rust is the exception:
`push` takes the body directly, because there is no untyped item object to unwrap. And a
`transactionId` you do not supply is minted client-side as a UUIDv7 everywhere, which means it
is unique per call and therefore non-idempotent. Supply your own if you want the dedup window
to protect a retry.

## Where the SDKs diverge

These are per-SDK behaviours to check when you move between languages.

**`pop()` long-polls everywhere except Go.** JavaScript, Python, PHP and C++ all initialise
the builder's wait flag from their *consume* defaults, which is `true`, so a bare `pop()`
issues a 30-second long poll. Go's `Pop()` leaves the flag unset and falls back to
`PopDefaults.Wait`, which is `false`, so it returns immediately with whatever is available.
Call `.Wait(true).TimeoutMillis(...)` in Go, or `.wait(false)` elsewhere, rather than
relying on the default.

**A failed pop is silent in three SDKs.** JavaScript, Python and C++ catch every exception
inside `pop()`, including an exhausted `429` budget and a terminal `403`, and return an
empty list. An empty result therefore does not mean an empty queue. PHP's `pop()`, Go's
`Pop()` and Rust's `pop()` propagate the error instead. If you need to distinguish, use the
consume loop, which logs the status code and treats `403` as fatal.

**Only Rust reads the consumer group off the message.** Everywhere else the group is a separate
argument to `ack()`, so forgetting it acks the wrong cursor silently. A Rust `Message` carries
the group that claimed it and the ack uses that, which also means a batch ack spanning two
groups is refused client-side rather than half-applied.

**The handler signature is not the same everywhere.** JavaScript and PHP pass the array of
popped messages unless you call `.each()`. Python passes a *single* message when `batch` is 1
and one message came back, and the list otherwise. Go picks the shape from the method:
`Consume` takes one message, `ConsumeBatch` takes a slice. C++ always hands the handler a
`json` value: the array, or one message under `.each()`. Rust picks the shape from the method,
like Go: `consume` takes one message, `consume_batch` takes the batch. Details are on each
SDK's page.

**Only four consumers abandon a batch after a negative ack.** Because an ack is an offset
commit, a nack clamps the group's cursor at the failed message, so every later message in that
popped batch is coming back. Under `.each()` the JavaScript, Python, Go and Rust consumers stop
and drop the rest of the batch; the PHP and C++ consumers keep going and ack messages that will
be redelivered anyway, producing duplicate work and rejected acks. Make those handlers
idempotent, or fail the whole batch.

**Client-side buffering suppresses the server's verdict.** With a buffer configured, `push`
returns a local acknowledgement immediately and the messages flush later on a count or time
trigger. You never see the per-item `queued` / `duplicate` status for a buffered push, and the
buffer lives in process memory: a crash between the call and the flush loses the messages.
Every SDK's `close()` flushes first, so run it. The JavaScript, Python and PHP consumers hook
signals to do that for you; Go, Rust and C++ leave it to you.

**`limit` under concurrency counts per worker, except in Rust.** JavaScript, Python and Go
track the limit inside each worker, so `concurrency(4).limit(10)` processes up to forty
messages. Rust shares one counter across workers and stops at ten.

## Verified against the source

Each of these was checked against the current client sources and the broker's router. The
full stories live on the SDK pages; this is the map of where they bite.

| Quirk | The short version |
| --- | --- |
| `renew()` expiry field | The broker writes the new expiry under all three historical key names, so every SDK finds it. Renewal always answers HTTP 200: check `success`, not the status |
| `clearQueue()`, `moveMessageToDLQ()` | Present in four SDK admin surfaces, routed nowhere on the broker: they 404. The operations that exist are `retryMessage()` (a DLQ replay with a new identity) and `deleteMessage()` |
| `traceId` | Survives only the transaction path; a plain push silently drops it and the message pops back with `traceId: null` |
| C++ surface | Message plane, transactions and DLQ query only: no admin class, and `renew_lease(true, ms)` is accepted but not acted on, so renew on your own timer |
| C++ signals | `SIGINT` exits without flushing buffers: call `close()` from your own handler |
| Go pop fields | Per-message `Queue`, `RetryCount` and `ErrorMessage` are never populated from a pop |
| Python logging | Prints to stdout unconditionally; no injectable logger |
| DLQ query | The broker reads only `queue`, `consumerGroup`, `limit`, `offset`; other filters are dropped, and `total` is the page size, so page with `offset` until a short page |

## Authentication and rate limits

All six SDKs authenticate with one header, `Authorization: Bearer <token>`. There is no
API-key header and no query-string token. Set it as `bearerToken` (JavaScript, PHP),
`bearer_token` (Python), `BearerToken` (Go), `Config::bearer_token` (Rust) or
`ClientConfig::bearer_token` (C++). The broker
also accepts a bare token with no `Bearer ` prefix, but the SDKs always send the prefix. In C++
the token only takes effect through the vector-of-URLs constructor; the single-URL constructor
ignores `ClientConfig` entirely.

The `429` and `403` handling exists because of the multi-tenant proxy, not the broker. All
six implement the same policy: a `429` is retried in place with exponential backoff,
`Retry-After` wins, and it never triggers failover; a `403` is terminal and stops the
consume loop. The budgets, the jitter and the error codes are in
[HTTP errors and retries](/reference/errors).

<Aside type="caution">
Access levels are a role *set*, not a ladder. A `WriteOnly` token passes `POST /api/v1/push`
and is rejected on every read and consume route, so a producer credential cannot be reused
for a consumer. See [Reference](/reference) for the level of every route.
</Aside>
