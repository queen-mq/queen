Every SDK speaks the same HTTP API, so the choice is about ergonomics and completeness, not
about capability. All six wrap the same six calls (push, pop, ack, transaction, lease
renewal, DLQ query) behind a fluent builder with the same method names transliterated into
each language's conventions. The differences are in what got finished: the admin surface,
client-side buffering, lease renewal inside the consume loop, and how each one behaves when
a proxy answers `429` or `403`.

If your language is not here, the HTTP API is the SDK. The whole message plane is eight
routes and one header. See [Using Queen over HTTP](/use/clients/http).

The runtime floors are read from `package.json` (`engines.node`), the PEP 585 annotations in

The last row is the one structural difference. The Rust client and the broker both depend on
`crates/queen-protocol`, and the broker's own test suite round-trips its request parsers and
its rendered responses through those types. A renamed field fails a test rather than reaching
a client. Every other SDK re-describes the wire by hand, which is where most of the gaps below
came from.

## Same grammar, six spellings

Every SDK builds a request the same way: name the queue, narrow it, then act.

<Tabs>

<TabItem label="JavaScript">

```js
await client.queue('orders').partition('acct-42').push([{ data: { id: 1 } }])
```

</TabItem>

<TabItem label="Python">

```python
await client.queue("orders").partition("acct-42").push([{"data": {"id": 1}}])
```

</TabItem>

<TabItem label="Go">

```go
_, err := client.Queue("orders").Partition("acct-42").Push(payload).Execute(ctx)
```

</TabItem>

<TabItem label="Rust">

```rust
queen.queue("orders").partition("acct-42").push(json!({ "id": 1 })).await?;
```

</TabItem>

<TabItem label="PHP">

```php
$client->queue('orders')->partition('acct-42')->push([['data' => ['id' => 1]]])->execute();
```

</TabItem>

<TabItem label="C++">

```cpp
client.queue("orders").partition("acct-42").push({{{"data", {{"id", 1}}}}});
```

</TabItem>

</Tabs>

Two rules hold in all of them, with one exception. `data` (or `payload`) is unwrapped as the
message body; an item with neither key is sent as the body itself. Rust is the exception:
`push` takes the body directly, because there is no untyped item object to unwrap. And a
`transactionId` you do not supply is minted client-side as a UUIDv7 everywhere, which means it
is unique per call and therefore non-idempotent. Supply your own if you want the dedup window
to protect a retry.

## Where the SDKs diverge

These are behaviours you cannot infer from one SDK by reading another.

**`pop()` long-polls everywhere except Go.** (Rust long-polls too.) JavaScript, Python, PHP and C++ all initialise
the builder's wait flag from their *consume* defaults, which is `true`, so a bare `pop()`
issues a 30-second long poll. Go's `Pop()` leaves the flag unset and falls back to
`PopDefaults.Wait`, which is `false`, so it returns immediately with whatever is available.
Call `.Wait(true).TimeoutMillis(...)` in Go, or `.wait(false)` elsewhere, rather than
relying on the default.

**A failed pop is silent in three SDKs.** JavaScript, Python and C++ catch every exception
inside `pop()`, including an exhausted `429` budget and a terminal `403`, and return an
empty list. An empty result therefore does not mean an empty queue. PHP's `pop()`, Go's
`Pop()` and Rust's `pop()` propagate the error instead. If you need to distinguish, use the
consume loop, which logs the status code and treats `403` as fatal.

**Only Rust reads the consumer group off the message.** Everywhere else the group is a separate
argument to `ack()`, so forgetting it acks the wrong cursor silently. A Rust `Message` carries
the group that claimed it and the ack uses that, which also means a batch ack spanning two
groups is refused client-side rather than half-applied.

**The handler signature is not the same everywhere.** JavaScript and PHP pass the array of
popped messages unless you call `.each()`. Python passes a *single* message when `batch` is 1
and one message came back, and the list otherwise. Go picks the shape from the method:
`Consume` takes one message, `ConsumeBatch` takes a slice. C++ always hands the handler a
`json` value: the array, or one message under `.each()`. Rust picks the shape from the method,
like Go: `consume` takes one message, `consume_batch` takes the batch. Details are on each
SDK's page.

**Only four consumers abandon a batch after a negative ack.** Because an ack is an offset
commit, a nack clamps the group's cursor at the failed message, so every later message in that
popped batch is coming back. Under `.each()` the JavaScript, Python, Go and Rust consumers stop
and drop the rest of the batch; the PHP and C++ consumers keep going and ack messages that will
be redelivered anyway, producing duplicate work and rejected acks. Make those handlers
idempotent, or fail the whole batch.

**Client-side buffering suppresses the server's verdict.** With a buffer configured, `push`
returns a local acknowledgement immediately and the messages flush later on a count or time
trigger. You never see the per-item `queued` / `duplicate` status for a buffered push, and the
buffer lives in process memory: a crash between the call and the flush loses the messages.
Every SDK's `close()` flushes first, so run it. The JavaScript, Python and PHP consumers hook
signals to do that for you; Go, Rust and C++ leave it to you. Rust can do it behind the
`signals` cargo feature, which still installs nothing on its own: it gives you a future that
resolves on the signal, so the flush sits where you want it in your shutdown sequence.

**`limit` under concurrency counts per worker, except in Rust.** JavaScript, Python and Go
track the limit inside each worker, so `concurrency(4).limit(10)` processes up to forty
messages. Rust shares one counter across workers and stops at ten.

## Verified gaps

Every item below was checked against the current source and the broker's router. They are
listed here so a green call does not mislead you.

- **`renew()` does report the new expiry, under three names.** This used to be a gap: the
  stored procedure returns `{"renewed":N,"expiresAt":"..."}` while the SDKs read `newExpiresAt`
  or `lease_expires_at`. The broker now writes the same value under all three keys
  (`server/src/handlers/data.rs`, the `for key in ["newExpiresAt", "expiresAt",
  "lease_expires_at"]` loop), so whichever one your SDK looks for is populated. Renewal is
  still best-effort and always answers HTTP 200, so check `success` rather than the status
  code.
- **Two admin methods target routes the broker does not register.** `clearQueue()` (`DELETE
  /api/v1/queues/:queue/clear`) and `moveMessageToDLQ()` (`POST
  /api/v1/messages/:partitionId/:transactionId/dlq`) exist in the JavaScript, Python, Go and
  PHP admin surfaces, but neither path appears in `server/src/main.rs`. They return a 404.
  `retryMessage()` and `deleteMessage()` are real. The Rust client does not expose either one,
  for that reason. Note also that `retryMessage()` is a dead-letter *replay*: it re-pushes the
  DLQ snapshot and drops the DLQ row, and errors on a message that is not in the DLQ.
- **`traceId` on a plain push is discarded.** The JavaScript, Python and Go clients forward a
  `traceId` with `POST /api/v1/push`, and their pages say so, but the broker's push path has
  nowhere to put it: `PushItem` in `server/src/handlers/data.rs` declares no such field, and
  neither the staged frame nor `fusion::OwnedFrame` carries one. Serde drops the unknown key
  and the message pops back with `"traceId": null`. It is honoured on the transaction path,
  where `txn_add_push` reads it, so push inside a transaction when a trace id has to survive.
  The Rust client omits the field on plain pushes rather than offering one that does nothing.
- **C++ has no admin surface at all.** `queen_client.hpp` defines no `Admin` class: no
  overview, queue listing, status, analytics, traces-by-name, maintenance mode or consumer
  group calls. Only the message plane, transactions and the DLQ query are reachable.
- **C++ accepts `renew_lease(true, ms)` and does nothing with it.** The value is carried into
  `ConsumeOptions`, and the consume worker's renewal site is a `// TODO`. Long-running C++
  handlers must call `client.renew(messages)` on their own timer or lose the lease.
- **Go's per-message `Queue`, `RetryCount` and `ErrorMessage` stay empty after a pop.** The
  broker's pop response carries `queue` once at the top level and emits no `retryCount` or
  `errorMessage` per message (`server/src/handlers/data.rs`), so those struct fields are
  never populated from a pop.
- **The Python client prints to stdout unconditionally.** `close()`, a failed `pop()`, a
  failed trace and a failed lease renewal all `print(...)` regardless of
  `QUEEN_CLIENT_LOG`. There is no injectable logger, unlike JavaScript.
- **C++ signal handling is not safe to rely on.** The `SIGINT` handler calls `exit(0)`
  without flushing buffers and the `SIGTERM` handler only prints. Call `close()` from your
  own handler.
- **The DLQ builders send filters the broker ignores.** `GET /api/v1/dlq` reads only `queue`,
  `consumerGroup`, `limit` and `offset` (`server/src/handlers/messages.rs`). Every SDK except
  Rust also sends `partition`, `from` and `to`, which are dropped; the Rust builder exposes only
  the four that work. The response has no `total` either
  (it carries `messages` plus a `pagination` object), so the `total` field the SDKs expose is
  always zero or undefined.

## Authentication and rate limits

All six SDKs authenticate with one header, `Authorization: Bearer <token>`. There is no
API-key header and no query-string token. Set it as `bearerToken` (JavaScript, PHP),
`bearer_token` (Python), `BearerToken` (Go), `Config::bearer_token` (Rust) or
`ClientConfig::bearer_token` (C++). The broker
also accepts a bare token with no `Bearer ` prefix, but the SDKs always send the prefix. In C++
the token only takes effect through the vector-of-URLs constructor; the single-URL constructor
ignores `ClientConfig` entirely.

The `429` and `403` handling exists because of the multi-tenant proxy, not the broker. All
six implement the same policy: a `429` is retried in place against the same backend with
exponential backoff (base 500 ms, cap 30 s, ±20 % jitter) and `Retry-After` wins when the
server sends one. An ordinary request gets ten attempts; a long-poll pop retries
unboundedly, because its outer loop is already an indefinite wait. Setting the maximum
explicitly applies it to both kinds. A `429` never triggers failover to another backend: it
is a quota signal, not a health signal. A `403` is terminal: `cluster_suspended`,
`storage_quota_exceeded`, `feature_gated` and `forbidden` cannot resolve themselves, so the
consume loop stops and surfaces the error rather than retrying.

<Aside type="caution">
Access levels are a role *set*, not a ladder. A `WriteOnly` token passes `POST /api/v1/push`
and is rejected on every read and consume route, so a producer credential cannot be reused
for a consumer. See [Reference](/reference) for the level of every route.
</Aside>

## Versions

At the 1.0.0 release the client SDKs are version-aligned with the broker. Pin the SDK to the
broker's major version; the wire contract shown throughout these pages is the 1.0.0 one.
