Queen has no binary protocol and no wire framing. Every SDK is a wrapper over JSON-over-HTTP,
so anything that can make an HTTP request is a first-class client. The whole message plane is
eight routes:

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/push` | Append messages |
| `GET` | `/api/v1/pop/queue/:queue` | Lease a batch from a queue |
| `GET` | `/api/v1/pop/queue/:queue/partition/:partition` | Lease a batch from one partition |
| `GET` | `/api/v1/pop` | Lease across a namespace or task |
| `POST` | `/api/v1/ack` | Commit or fail one message |
| `POST` | `/api/v1/ack/batch` | Commit or fail many |
| `POST` | `/api/v1/transaction` | Push and ack atomically |
| `POST` | `/api/v1/lease/:leaseId/extend` | Extend a lease |

Everything else (queue configuration, DLQ, traces, status, analytics, consumer groups) is in
[Reference](/reference) with its access level. These routes are the stable compatibility
surface Queen commits to; [Versions and compatibility](/reference/compatibility) states what
that covers.

## A complete walkthrough

<Steps>

1. Check the broker is up. `/health` round-trips the database, so a `200` means PostgreSQL is
   reachable too.

   ```bash
   curl -s http://localhost:6632/health
   ```

2. Push two messages into one partition. Queue and partition are created on first push: there
   is no declaration step.

   ```bash
   curl -s -X POST http://localhost:6632/api/v1/push -H 'Content-Type: application/json' -d '{"items":[{"queue":"demo","partition":"acct-42","transactionId":"evt-1","payload":{"n":1}},{"queue":"demo","partition":"acct-42","transactionId":"evt-2","payload":{"n":2}}]}'
   ```

3. Push `evt-1` again. It comes back `duplicate` with the original `message_id`; nothing is
   written.

   ```bash
   curl -s -X POST http://localhost:6632/api/v1/push -H 'Content-Type: application/json' -d '{"items":[{"queue":"demo","partition":"acct-42","transactionId":"evt-1","payload":{"n":1}}]}'
   ```

4. Lease both for the `billing` group, long-polling up to five seconds. Keep the `leaseId`
   and each message's `partitionId`.

   ```bash
   curl -s 'http://localhost:6632/api/v1/pop/queue/demo?consumerGroup=billing&batch=10&wait=true&timeout=5000'
   ```

5. Acknowledge both. An ack is an offset commit, so acking `evt-2` alone would also complete
   `evt-1`: send both when you have processed both.

   ```bash
   curl -s -X POST http://localhost:6632/api/v1/ack/batch -H 'Content-Type: application/json' -d '{"consumerGroup":"billing","acknowledgments":[{"transactionId":"evt-1","partitionId":"<partitionId>","leaseId":"<leaseId>","status":"completed"},{"transactionId":"evt-2","partitionId":"<partitionId>","leaseId":"<leaseId>","status":"completed"}]}'
   ```

6. Pop again. The cursor is past both messages, so this is `204` with an empty body, which
   `-i` makes visible.

   ```bash
   curl -si 'http://localhost:6632/api/v1/pop/queue/demo?consumerGroup=billing&batch=10'
   ```

7. Pop as a different group. `analytics` gets its own cursor on first contact and sees both
   messages again.

   ```bash
   curl -s 'http://localhost:6632/api/v1/pop/queue/demo?consumerGroup=analytics&batch=10'
   ```

</Steps>

## Conventions

**Base URL.** `http://host:6632` by default (`PORT`). The broker has no TLS listener and no
CORS layer: terminate HTTPS in front of it, and a browser cannot call it directly across
origins.

**Content type.** `Content-Type: application/json` on every request with a body. Responses
are `application/json` (`/metrics` included, a JSON snapshot) except `/metrics/prometheus`,
`text/plain; version=0.0.4`.

**Authentication.** One header, `Authorization: Bearer <token>`; a bare token with no prefix
works too. With JWT auth on, the token's roles decide which routes you may call; access
levels are generated into [Reference](/reference).

<Aside type="caution">
Access levels are a role **set**, not a ladder: a `write-only` token is rejected on every read and consume route, and an admin token is not automatically a superset.
</Aside>

**Errors.** Any failure is `{"error":"..."}`; a malformed body is `400` with the parser's
message. At a multi-tenant proxy a `429` adds `code`
`rate_limited` or `quota_exceeded` plus `Retry-After` in seconds, and a `403` adds `code`
`cluster_suspended`, `storage_quota_exceeded`, `feature_gated` or `forbidden`. Branch on
`code`, not on the message text.

**The bodiless 204.** An empty pop answers `204 No Content` with no body at all. Treat it as
"no messages" and never parse it; the missing body is [deliberate](/use/errors#the-envelope).

Management responses are often stored-procedure JSON passed through verbatim: the shapes are
the SQL's, not a hand-written DTO's.

## Push

`POST /api/v1/push`

```json
{
  "items": [
    {
      "queue": "orders",
      "partition": "acct-42",
      "transactionId": "order-1-created",
      "payload": { "id": 1, "total": 1999 }
    }
  ]
}
```

`queue` and `payload` are required per item; `partition` defaults to `Default`. A missing
`transactionId` is minted as a UUIDv7, which makes the push non-idempotent: supply a
deterministic one to make a retry safe inside the dedup window.

The response is `201 Created` and a top-level array, one entry per item in request order.
Note the mixed casing: `message_id` and `transaction_id` against `queueName`.

```json
[
  {
    "index": 0,
    "message_id": "0197f2b1-...",
    "transaction_id": "order-1-created",
    "queueName": "orders",
    "status": "queued"
  }
]
```

| `status` | Meaning |
| --- | --- |
| `queued` | Appended and committed. |
| `duplicate` | The `(queue, partition, transactionId)` already exists inside the dedup window. Nothing was written; `message_id` is the **original** message's id. |
| `buffered` | The database write failed and the message went to the broker's disk spool for replay. |
| `failed` | The database write failed and the spool write failed too. This message is lost. |

<Aside type="caution">
**`201` does not mean "stored in PostgreSQL".** A `buffered` item is on the broker's disk awaiting replay, and a `failed` item is gone: check every item's `status`. Dedup on the preserved `transactionId` is what makes the replay idempotent.
</Aside>

Duplicates are also collapsed within one request: the first `(queue, partition,
transactionId)` wins, the rest come back `duplicate` with the winner's `message_id`. An empty
`items` array is `201` with `[]`.

## Pop

`GET /api/v1/pop/queue/:queue`, or `.../partition/:partition` to pin one lane, or
`/api/v1/pop?namespace=…&task=…` to lease across every matching queue (one of the two
required, otherwise `400`).

| Query parameter | Default | Effect |
| --- | --- | --- |
| `batch` | 200 | Maximum messages returned. |
| `partitions` | 1 | Claim up to N partitions in one call. `batch` becomes the global cap across all of them, and every claimed partition shares one `leaseId`. |
| `wait` | false | Long-poll: park the request until a message arrives or the timeout expires. |
| `timeout` | 30000 ms | Long-poll window in **milliseconds**. The server-side default comes from `DEFAULT_TIMEOUT`, then `POP_DEFAULT_TIMEOUT_MS`, then 30000. |
| `consumerGroup` | queue mode | The group whose cursor advances. |
| `autoAck` | false | Commit the cursor inside the pop transaction. At-most-once. |
| `leaseSeconds` | queue's `leaseTime` | Per-request lease override, in seconds. No SDK exposes this. |
| `subscriptionMode` | `new` | `all` or `new`, applied **only** when this `(partition, group)` cursor is created. The broker default comes from `DEFAULT_SUBSCRIPTION_MODE`. A pop with no `consumerGroup` always uses `all`. |
| `subscriptionFrom` | none | `now` or an ISO timestamp, same first-contact-only rule. |

A successful pop is `200`; an empty pop is `204` with no body:

```json
{
  "success": true,
  "queue": "orders",
  "partition": "acct-42",
  "partitionId": "0197f2b0-...",
  "leaseId": "0197f2b2-...",
  "consumerGroup": "billing",
  "messages": [
    {
      "id": "0197f2b1-...",
      "transactionId": "order-1-created",
      "traceId": null,
      "data": { "id": 1, "total": 1999 },
      "producerSub": null,
      "createdAt": "2026-07-30T09:12:44.031Z",
      "partitionId": "0197f2b0-...",
      "partition": "acct-42",
      "leaseId": "0197f2b2-...",
      "consumerGroup": "billing"
    }
  ]
}
```

| Detail | Behaviour |
| --- | --- |
| Top-level `partition` / `partitionId` | The **first claimed partition's**. With `partitions>1`, read each message's own `partitionId`. |
| `leaseId` | One per pop, shared by all messages even across partitions. One extend call renews the whole claim. |
| `producerSub` | The authenticated producer's JWT `sub`, stamped by the broker at push time; a client cannot set it, which is what prevents impersonation. `null` when JWT auth is off. |
| `createdAt` | The *segment's* timestamp: every message written by one push call shares it. |
| Missing fields | No per-message `queue`, `retryCount` or `errorMessage` on a pop; those appear on DLQ rows. |
| Claim exclusivity | Exactly one in-flight leased batch per `(partition, group)`, so one group cannot drain a single-partition queue in parallel, no matter how many workers poll it. |

## Acknowledge

`POST /api/v1/ack`

```json
{
  "transactionId": "order-1-created",
  "partitionId": "0197f2b0-...",
  "leaseId": "0197f2b2-...",
  "status": "completed",
  "consumerGroup": "billing",
  "error": null
}
```

`POST /api/v1/ack/batch`

```json
{
  "consumerGroup": "billing",
  "acknowledgments": [
    { "transactionId": "order-1-created", "partitionId": "0197f2b0-...", "leaseId": "0197f2b2-...", "status": "completed" },
    { "transactionId": "order-2-created", "partitionId": "0197f2b0-...", "leaseId": "0197f2b2-...", "status": "dlq", "error": "unparseable payload" }
  ]
}
```

`partitionId` is required: a `transactionId` is not unique across partitions. `consumerGroup`
defaults to `__QUEUE_MODE__`, the internal name for queue mode. `error` is recorded on the DLQ
row if this nack exhausts the retry budget.

`status` is normalised server-side: `completed`, `success`, `acked`, `ok` and absent all mean
`completed`; `retry` and `dlq` mean themselves; **anything else at all means `failed`**. A
typo does not error: it nacks.

Both routes answer `200` with an array in request order, whatever the outcome:

```json
[
  { "index": 0, "transactionId": "order-1-created", "success": true, "error": null,
    "leaseReleased": true, "dlq": false, "noop": false }
]
```

<Aside type="caution">
A rejected ack is **HTTP 200 with `success: false`** on its item: the status code tells you nothing. Check every item's `success`, and the array length against the acks you sent.
</Aside>

`noop: true` means the ack changed nothing: it landed below the cursor or outside the
transaction-hash window. An ack you cannot resolve is not an ack that worked.

### Ack is an offset commit

There is no per-message delivery state, only one cursor per `(partition, consumer group)`.
Acking message N completes every earlier unacked message in that partition for that group.
Two consequences:

- **Acking out of order silently completes the gap.** Ack offset 10 with 7, 8, 9 unacked and
  they are done too.
- **A negative ack clamps the cursor** at the lowest signal in the call (`dlq` beats `failed`
  beats `retry` at one offset; none is skipped by a later `completed`). Everything after the
  failed message in that batch will be redelivered: do not keep processing it.

## Extend a lease

`POST /api/v1/lease/:leaseId/extend`

```json
{ "seconds": 60 }
```

An empty body defaults to 60 seconds. The response is always `200`, because renewal is
best-effort:

```json
{ "renewed": 2, "expiresAt": "2026-07-30T09:14:44.031Z" }
```

`renewed` counts the `(partition, group)` lease rows touched (one per claimed partition);
`expiresAt` is the **earliest** deadline across them: schedule the next renewal from it.
`{"renewed":0,"expiresAt":null}` means the lease is unknown, expired, or not yours.
The full response repeats the expiry under
[three equivalent keys](/use/concepts/leases-retries-dlq#extending-a-lease).

## Transactions

`POST /api/v1/transaction` bundles pushes and acks into a single PostgreSQL transaction, all
or nothing:

```json
{
  "operations": [
    { "type": "push", "items": [ { "queue": "stage-2", "partition": "acct-42", "payload": { "value": 2 } } ] },
    { "type": "ack", "transactionId": "order-1-created", "partitionId": "0197f2b0-...", "status": "completed", "consumerGroup": "billing" }
  ],
  "requiredLeases": ["0197f2b2-..."]
}
```

`requiredLeases` makes the commit fail if any of those leases expired in the meantime: a
stale worker cannot ack a batch someone else now owns. This is atomic,
[not end-to-end exactly-once](/use/concepts/transactions#the-limit-this-is-not-end-to-end-exactly-once):
a retry after a lost response duplicates the pushes unless their `transactionId`s are
deterministic and still inside the dedup window.

## Writing your own client

The behaviours the six SDKs implement, in the order they matter:

| Rule | Detail |
| --- | --- |
| Send `Authorization: Bearer` and nothing else | No API-key header, no query-string token. |
| Treat `204` as "no messages" | Never parse its body. |
| Read per-item statuses | A push `201` and an ack `200` both carry per-item verdicts that can disagree with the status code. Check the array length against what you sent. |
| Back off on `429`, in place | Honour `Retry-After` (seconds); otherwise exponential backoff from 500 ms capped at 30 s, with jitter. Ten attempts for an ordinary request, unbounded for a long-poll pop. Never fail over on a `429`: it is a quota signal, not a health signal. |
| Stop on `403` | `cluster_suspended`, `storage_quota_exceeded`, `feature_gated` and `forbidden` cannot resolve themselves. |
| Give the long poll client-side slack | The SDKs set their HTTP timeout to `timeout + 5000` ms so the server-side timeout fires first and the socket is reused. |
| Never send `autoAck` when you intend to ack yourself | `autoAck=true` [commits the cursor inside the pop transaction](/use/concepts/consuming#autoack-and-what-it-costs); a crash after the response is a lost message. |
| Abandon the rest of a batch after a negative ack | The cursor clamped at the failed message; everything after it is coming back. |
| Pin a lane to a backend if you run several brokers | The SDKs hash `queue:partition:consumerGroup` (or `namespace:task:consumerGroup`) onto a ring so a lane's long-poll wake-ups stay local. |
| Set a generous idle connection pool | Language defaults are often 2 per host, which forces a handshake per request under concurrency. |
