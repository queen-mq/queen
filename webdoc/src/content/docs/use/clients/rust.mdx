The Rust client is `async` on tokio, with a builder chain that executes when you `await` it.
It requires Rust 1.75 and speaks `reqwest` with rustls: no OpenSSL on the host, no cmake in
the build. It is the only SDK sharing its wire types with the broker, through
`crates/queen-protocol`: a field that drifts on either side fails the broker's own round-trip
tests instead of reaching a client.

## Install

```toml
[dependencies]
queen-mq = "1.0.0"
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
serde_json = "1"
```

## Construct

```rust
use queen_mq::{Config, Queen};

let queen = Queen::connect(Config::new("http://localhost:6632"))?;
```

`Queen` is cheap to clone: every clone shares one connection pool, one load balancer and one
set of push buffers, so build it once and pass clones around. `connect` validates the
configuration and the TLS setup but opens no socket; a bad URL, an unusable bearer token or a
`Host` smuggled through `headers` fails here rather than on the first call.

Several brokers, with failover and consistent-hash affinity:

```rust
let queen = Queen::connect(
    Config::urls(["http://broker-a:6632", "http://broker-b:6632"])
)?;
```

## Push

<Render file="snippets/rust-push" />

`push` takes anything `serde::Serialize`; `push_many` an iterator of them; `push_items`
fully-formed `PushItem` values for when the transaction id matters.
The result is the broker's array in request order, each entry carrying `status`: `Queued`,
`Duplicate`, `Error`, `Buffered` or `Failed`.

A `transaction_id` you do not supply is minted client-side as a UUIDv7, unique per call and
thus not idempotent. Supply your own when you want the dedup window to protect a retry:

<Render file="snippets/rust-push-dedup" />

<Aside type="note">
`PushItem` has no `traceId`: the broker's push path has nowhere to store one, so a trace id sent with a push pops back as `null`, and this client omits the option rather than offer one that does nothing. Inside a transaction it does work, through `TxnPushItem::trace_id`.
</Aside>

### Buffering

```rust
use queen_mq::BufferOptions;
use std::time::Duration;

let orders = queen.queue("orders").buffer(BufferOptions {
    message_count: 100,
    time: Duration::from_millis(1000),
});
orders.push(serde_json::json!({ "id": 1 })).await?;
```

A buffered `push` returns an empty result: nothing has been sent yet, so no per-item verdict
exists. The buffer lives in process memory: a crash before the flush loses those messages,
and `Queen::close` flushes before returning, so run it.

## Pop

<Render file="snippets/rust-pop" />

`pop` returns `Err` when the call fails, the one place this client deliberately diverges from
JavaScript, Python and C++: those catch everything inside `pop` and return an empty list, so
an exhausted `429` budget or a terminal `403` looks like an empty queue there. An empty claim
is still `Ok` with nothing in it, and so is a claim refused because pop maintenance is on.

`pop_auto_ack` takes the broker-side flag instead, committing the cursor at delivery with no
lease: [at-most-once delivery](/use/concepts/consuming#autoack-and-what-it-costs), where a
crash mid-handler loses that batch.

## Consume

<Render file="snippets/rust-consume" />

The handler's return settles the message: `Ok` acks, `Err` nacks, and the error's `Display`
becomes the DLQ reason if the nack exhausts the retry budget; the error type only has to be
printable.

`consume` hands the handler one message at a time; `consume_batch` hands it the whole claimed
batch and settles it with a single ack, one round-trip cheaper for vectorised work.

Because an ack is an offset commit, a nack clamps the group's cursor at the failed message and
the rest of that batch is coming back; the per-message loop therefore abandons it rather than
acking messages the broker will reject.

Stop a consumer with a `Cancel`:

```rust
use queen_mq::Cancel;

let cancel = Cancel::new();
let stopper = cancel.clone();
tokio::spawn(async move {
    tokio::signal::ctrl_c().await.ok();
    stopper.cancel();
});

queen.queue("orders").group("billing").cancel(cancel)
    .consume(|msg| async move { Ok::<_, std::convert::Infallible>(()) })
    .await?;
```

A cancel takes effect between messages, never mid-handler: no claim is left in limbo.

<Aside type="note">
`limit` counts across all workers: with `concurrency(4).limit(10)` this client stops after ten messages in total, where the JavaScript and Python consumers apply the limit per worker and process up to forty.
</Aside>

## Ack

```rust
queen.ack(&msg).await?;
queen.nack(&msg, "could not reach the payment provider").await?;
queen.ack_with(&msg, queen_mq::AckStatus::Dlq, Some("poison".into())).await?;
queen.ack_all(&msgs).await?;
```

The consumer group and the lease come from the message itself, so a forgotten group cannot
ack the wrong cursor. `ack_all` sends one request; the batch endpoint
carries a single consumer group, so mixing groups in one call is refused client-side rather
than half-applied.

A rejected ack arrives as HTTP 200 with `success: false` on the item: check the returned
`AckResult`, not the absence of an error. `noop: true` means the cursor was already past that
message, a harmless duplicate commit.

## Transactions

<Render file="snippets/rust-transaction" />

Acking through the transaction builder also collects the messages' lease ids into
`requiredLeases`, so a lease that expired mid-handler rolls everything back instead of
pushing stage two for work somebody else has re-claimed.

A rolled-back transaction comes back as HTTP 200 with `success: false`. This client surfaces
that as an `Err`: a caller who ignored it would believe in a handoff that did not happen.

## Streams

<Render file="snippets/rust-stream" />

Tumbling, sliding, session and wall-clock windows; event time with watermarks and a late-event
policy; `reduce` and the named aggregates; `key_by`; `gate`; and `to` or `foreach` terminals.
See [Streams](/use/streams) for the model, and
[the Rust reference](/reference/sdk/rust) for every method.

The chain's `config_hash` is computed byte-identically to the JavaScript, Go and Python SDKs,
so the same query redeploys in a different language without tripping the changed-chain guard.

## Errors

`queen_mq::Error` carries the HTTP status and the proxy's machine-readable `code` when there
was one; branch on those, not on the prose message:

```rust
match queen.queue("orders").push(payload).await {
    Ok(results) => { /* ... */ }
    Err(e) if e.is_rate_limited() => { /* the 429 budget ran out */ }
    Err(e) if e.is_terminal_refusal() => { /* 403: suspended, gated, out of quota */ }
    Err(e) if e.is_retryable() => { /* 5xx, timeout, transport fault */ }
    Err(e) => return Err(e),
}
```

## Configuration

```rust
use std::time::Duration;
use queen_mq::{Config, Strategy};

let config = Config::new("http://localhost:6632")
    .timeout(Duration::from_secs(30))
    .retry_attempts(3)
    .strategy(Strategy::Affinity)
    .bearer_token(std::env::var("QUEEN_TOKEN")?);
```

Defaults match the other SDKs: 30 s timeout, three attempts on `5xx` and transport faults
with exponential backoff, affinity with 128 virtual nodes per backend, failover on, failed
backends held out of the pool for five seconds.

Behind a `queen_proxy` deployment, `host_header` advertises one Host while dialling another
address, the way `curl --resolve` does:

```rust
let config = Config::new("http://cell.eu1.queenmq.cloud")
    .bearer_token(token)
    .host_header("acme.eu1.queenmq.cloud")?;
```

**A `Host` set through `headers` is rejected at construction: a wrong Host at a proxy with a
default cluster lands traffic in another tenant's data.**

## Shutdown

```rust
queen.close().await?;
```

`close` flushes every buffer. Signal handling is opt-in behind the `signals` feature and
installs nothing on its own: `shutdown_on_signal` resolves when `SIGINT` or `SIGTERM`
arrives, and the caller decides where it belongs in the shutdown sequence. Every other SDK
except Go registers process-wide handlers by default, right for a script and wrong for a
service.

## Not offered

`clearQueue()` and `moveMessageToDLQ()`, which other SDKs expose, call
[routes the broker does not register](/use/concepts/leases-retries-dlq#getting-a-message-out-of-the-dead-letter-queue),
so this client omits them: drop a queue with `queen.queue(name).delete()` or seek the group
past its backlog; dead-letter by acking with `AckStatus::Dlq`.

`retry_message` is a dead-letter replay rather than a generic retry: it re-pushes the DLQ
snapshot, drops the DLQ row, and errors on a message not in the DLQ.
