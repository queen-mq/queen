Horizon and Queen both run ordinary Laravel jobs and both supervise their workers, but on different
queue backends: Horizon on Redis, Queen on its own broker. This page compares the two whole stacks
for a team that runs Horizon today. Every measured row links to the run behind it, and
[How Queen runs Laravel jobs](/use/laravel/concepts) defines the terms.

## Choose Horizon when

- Redis is the intended queue backend and the team already operates it well.
- Silenced jobs, job lists, batches in the dashboard, or Slack and SMS routes are required.
- Several masters must run without a broker to coordinate through.
- A native release artifact, or a supervisor that runs on Unix only, is unacceptable.
- Jobs of very different lengths must share one queue, and a short job must never wait behind a long
  one.
- The application does not need Queen's partitions, replay, timers or transactions.
- The load is low and steady, and backend CPU matters more than latency: there the Raft broker spends
  more CPU per job than Redis.

## Evaluate Queen when

- Queen is already the desired queue backend.
- The memory of the master or of the workers matters.
- Workers run as Kubernetes pods that should scale with the backlog.
- Bursts must get workers within seconds, not within several cooldowns.
- Jobs are short, and each worker should complete more of them at the same durability.
- Throughput must keep growing with the worker count: on the benchmark server, Horizon stayed near
  1,100 jobs/s from 32 to 64 workers, while Queen went from 2,753 to 4,395.
- Long jobs must never run twice at once, however long they take.
- Per-entity order, consumer groups, replay or atomic ACK-and-push help the workload.
- The team can qualify its own jobs under at-least-once delivery and the current preview gates.

If Queen fits, follow the [Horizon migration runbook](/use/laravel/migrate-from-horizon). If a
Horizon-only feature above is a hard requirement, stay on Horizon until Queen has a tested
replacement, rather than recreating it in application code by accident.

## Where Queen has an advantage

### More jobs per worker at the same durability

On a dedicated Linux server, 32 Queen workers on the Raft broker, which fsyncs every acknowledged
write, completed **2,753 jobs/s** of 10 ms jobs, against **1,124** for Horizon on Redis with
`appendfsync always`. Relaxing Redis did not close the gap: **1,247** with `everysec` and **1,313**
with `appendfsync no`, while Raft kept fsyncing. With 64 workers, Horizon stayed near 1,100 jobs/s and
Queen reached **4,395**. Each Horizon job cost about 33 Redis commands, against 1.3 Queen requests.
Every Queen pop and ACK waits for an fsync, so Queen keeps those waits off the worker's path: the ACK
of a job travels while the next job runs ([`ack_async`](/use/laravel#asynchronous-acknowledgements)),
and the pop for the next batch travels while the last job of the current one runs
([`pop_ahead`](/use/laravel#pop-the-next-batch-ahead)).

### Lower latency at a steady rate

With jobs dispatched one at a time at 500 jobs/s and 16 workers, 95% of jobs completed within 227 ms
of their dispatch with Horizon and within 23 ms with Queen. Over a 15-minute soak at 400 jobs/s, the
p95 was 249 against 22 ms. Horizon's producer could not send 500 jobs/s, because each dispatch also
writes Horizon's monitoring records. An earlier run with 8 workers on Docker Desktop found the same
direction with smaller margins, and equal speed for CPU-bound jobs of about 20 ms, where the job
itself dominates
([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-a-linux-server-2026-10-01)).

### Long jobs without a long `retry_after`

Laravel's Redis queue gives a job back to the queue `retry_after` seconds after a worker took it, even
while that worker still runs it, so a Horizon job must end before `retry_after`. With
[lease renewal](/use/laravel/concepts#lease-renewal-and-fencing), Queen renews the lease of a running
job, and stops the worker before the lease ends when it cannot renew. A job with a longer `$timeout`
of its own can then run past `retry_after` without a second attempt beside it, and `retry_after` only
sets how soon the jobs of a crashed worker run again. In a fault test, a prefetched job ended 32.1 s after it was queued, past
its 30 s lease, on its first attempt
([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-raft-2026-10-01)).

### A smaller control plane

The Rust master does not keep a Laravel application resident after configuration. In the final
diagnostic campaign, its median proportional set size was **2.9 MiB**, against **65.0 MiB** for the
Horizon orchestrator and 35.1 MiB for the Queen PHP master. That is a control-plane result, not a
whole-stack one: Queen still needs its broker and storage.

### Smaller workers

Horizon, like Laravel's own `queue:work`, boots the framework once per worker. Queen's
[prefork workers](/use/laravel/supervisors#prefork-workers) boot it once per master and fork every
worker from it, so the workers share the framework and the opcache copy-on-write. Eight workers after
600 jobs used 336 MiB when each booted Laravel and 85 MiB when forked, with opcache on. These figures
were taken 15 seconds after the burst: a worker that runs for hours writes to more of the shared
pages, so the saving shrinks with time.

On the Linux server, with the master renewing leases instead of a helper process per worker, 64
workers used 183 MiB against 1,892 MiB for Horizon. A Horizon worker held 28 MiB of private memory, a
forked Queen worker 1.4 MiB; the rest was shared with the process it was forked from. The Horizon
workers ran with PHP's default `opcache.enable_cli=0`, the Queen workers with `opcache.enable_cli=1`.
The benchmark job is tiny: a real application's workers keep more private memory, so expect a smaller
ratio.

### Faster reaction to bursts

Horizon reads its queue sizes every `balanceCooldown`, three seconds by default, and moves
`balanceMaxShift` workers per check. A Queen supervisor polls at the same cadence by default. With
[`event_driven`](/use/laravel/supervisors#event-driven-scaling), the broker wakes it when jobs arrive,
and with `fast_scale_up` each step closes half of the gap to the target, once a second while the pool
climbs. On the Linux server, a burst of 30,000 jobs with autoscaling from 1 to 64 workers was done
after 9.5 s with Queen, which reached 64 workers after 8.2 s, and after 37.0 s with Horizon, whose
producer sent jobs too slowly for it to need more than 34.

### Built for Kubernetes replicas

[Coordinated replicas](/use/laravel/supervisors#several-replicas) split the target of every pool
through the broker's key/value store, so a supervisor Deployment scales with its replica count or an
HPA. The [Prometheus endpoint](/use/laravel/monitoring#prometheus-and-kubernetes-autoscaling) gives
KEDA the backlog to scale on, and the dashboard lists every pod and warns about masters that share a
queue without coordinating. [Scale Laravel queues on Kubernetes](/use/laravel/kubernetes) puts the
pieces together.

### Metrics without a snapshot command

The workers record per-job-class metrics, monitored tags and the data for long-wait alerts into the
broker, so the numbers cover every host and need no scheduled snapshot. A long-wait alert reads the
age of the oldest waiting job instead of estimating it. See [Monitoring and alerts](/use/laravel/monitoring).

### Queen queue semantics

Choosing Queen also chooses capabilities below the supervisor:

- one FIFO partition per ordering key, created by the first push;
- consumer groups and replay over one stored copy;
- delayed jobs backed by Queen timers;
- a broker DLQ snapshot synchronized with Laravel's failed-job index;
- atomic acknowledgement plus push or timer operations;
- several broker endpoints, and a separate read token for the supervisor's depth calls.

These are advantages only when the application needs them. A team that already operates Redis and
does not need Queen's model may value Horizon's smaller topology more.

### One configuration, two engines, fenced controls

PHP and Rust consume the same resolved configuration and publish the same versioned status and
control protocol. A deployment can validate behavior with the readable PHP engine, then move to Rust
without changing pool definitions or dashboard commands. Configuration, status and telemetry have
explicit size limits, controls carry the exact generation that they target, and unsafe ownership of
the state directory fails closed instead of creating a second control namespace.

## Where Horizon has an advantage

### Less backend CPU at a low, steady rate

At 500 jobs/s with one job per dispatch, the Raft broker used 0.87 ms of CPU per job against 0.49 for
Redis, and 0.97 against 0.54 in the 15-minute soak. Each job is then its own Raft entry, and about half
of the broker's CPU goes to handing work between its threads. Under load the order reverses: 0.23
against 0.37 ms per job with 32 workers. The application side was cheaper with Queen on the Linux
server, 0.91 against 1.83 ms per job under load, with the PHP client's cURL transport; on Docker
Desktop, with the older Guzzle transport, the Queen workers used more. When CPU is the scarce
resource, measure your own jobs first
([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-a-linux-server-2026-10-01)).

### No wait behind a long job

On Redis, any free worker takes the next job, so a long job delays no other job. On Queen, a job waits
until the job ahead of it in its stripe has ended: a ten-minute job holds back the jobs that hashed to
its stripe for up to ten minutes, even while other workers are idle. Give long jobs a queue of their
own ([queues and stripes](/use/laravel/concepts#queues-and-stripes)).

### Product maturity and familiarity

Horizon has an established Laravel installation path, a long operating history and one familiar
Redis-backed surface, and `horizon:clear` empties a queue. Queen's Laravel supervisor is still a
preview, with more decisions about the broker, its storage and the state directory, and no atomic
queue clear yet.

### A richer Laravel-specific dashboard

Horizon still has silenced jobs, lists of recent, pending and completed jobs, batches, Slack and SMS
notification routes and per-supervisor controls. Queen's panel covers process health, safe master
controls, per-job-class metrics over up to a day, monitored tags, failed-job details with a
one-click retry, the jobs waiting and running in each queue, a tuning page and a per-queue chart from
the broker's counters. Its controls apply to a whole master; job lists, global backlog analytics and
DLQ operations live in the separate broker dashboard; and forgetting, flushing and pruning failed jobs
stay with Laravel's commands.

### Multi-host supervisors

Horizon keeps live master and supervisor records in its
[Redis repository](https://github.com/laravel/horizon/blob/5.x/src/Repositories/RedisMasterSupervisorRepository.php).
Queen's filesystem lock prevents a second local owner only; it does not elect one leader across hosts.
With [coordination](/use/laravel/supervisors#several-replicas), several masters register in the
broker's key/value store and each runs a share of every pool's target. Without it, a Queen deployment
must run one master for an application and consumer group, with no rolling-surge overlap.

### Fewer release artifacts

Horizon installs as a Composer package and still relies on an outer process monitor. Queen PHP does
the same. Queen Rust adds a native artifact, a platform matrix, an installer and a coordinated
Composer and native release. The installer is explicit and checks every step, but it remains another
deployment step.

## Capability comparison

Both stacks run Laravel workers under a supervisor, on different backends:

| Stack | Queue backend | Control plane | Worker process |
| --- | --- | --- | --- |
| Horizon | Redis | Horizon PHP master and supervisors | `artisan horizon:work` |
| Queen PHP | Queen broker and its storage | Laravel/PHP master | `artisan queue:work queen` |
| Queen Rust | Queen broker and its storage | Rust master after one temporary Artisan config load | `artisan queue:work queen` |

The fair comparison is therefore **Horizon plus Redis** against **Queen's Laravel driver,
supervisor, broker and storage**. Horizon facts below follow the current
[official Laravel Horizon documentation](https://laravel.com/docs/horizon). Queen facts follow the
implementation and tests named in this page's frontmatter.

| Area | Horizon | Queen Laravel |
| --- | --- | --- |
| Laravel jobs | Standard dispatch, middleware, retry, backoff and failures | Same Laravel application surface |
| Queue backend | Redis only; the official docs state Redis Cluster is not supported | Queen broker with its durable storage as source of truth |
| Dynamic balancing | `auto`, with `size` or `time` strategy | `auto`, with independent `size` or `time` implementation |
| Per-queue minimum | `minProcesses` applies to every queue | `min_processes_per_queue` |
| Reaction to new jobs | Reads the queue sizes every `balanceCooldown`, three seconds by default | The same polling, or `event_driven`: the broker wakes the master when jobs arrive |
| Scale-up rate | `balanceMaxShift` workers per cooldown | The same, or `fast_scale_up`: half of the gap per cycle, every second with `event_driven` |
| Fixed allocation | `simple` | `simple` |
| Ordered queue priority | `balance=false` | `balance=off` |
| Long jobs | `retry_after` must exceed the job | Lease renewal, with fencing before the lease ends |
| Master runtime | PHP with Laravel/Horizon loaded | PHP reference engine or optimized Rust engine |
| Worker memory | Every worker boots Laravel | The same, or prefork: workers forked from one booted Laravel share it copy-on-write |
| Crash-loop control | Process restart behavior managed by Horizon and the outer monitor | Capped restart backoff plus an open/one-probe circuit breaker in both engines, for short-lived crashes only: a worker that Laravel killed after a job timeout, that stopped at `--memory` after a job, or that ran for `stable_after` restarts at once |
| Multiple master hosts | Master records and supervisor state are shared through Horizon's Redis repository | Opt-in coordination: replicas share each pool's target through the broker's key/value store; otherwise one master per application and consumer group |
| Dashboard | Mature Horizon dashboard over its Redis state | Supervisor panel listing every host or pod, Jobs and Tags pages, plus a separate global Queen broker dashboard |
| Job metrics | Per-job and per-queue graphs from the scheduled `horizon:snapshot` | Live per-job-class throughput, failures and runtime over one hour to one day, from every worker; per-queue completed and failed chart from the broker's counters |
| Job tags and silencing | Automatic and `tags()` tags, monitored tags and silenced jobs | Automatic and `tags()` tags and monitored tags; no silencing |
| Long-wait notifications | Mail, Slack and SMS routes; the wait is estimated from backlog and runtime | `queen:check-waits`: the broker's age of the oldest waiting job per consumer group, a `LongWaitDetected` event and mail |
| Autoscaler metrics | Not built in | Prometheus endpoint for Kubernetes HPA and KEDA |
| Per-supervisor controls | Pause, continue and status for individual supervisors | Controls currently apply to the complete local master |
| Failed jobs | Horizon commands and dashboard integration | Laravel commands remain authoritative; Queen synchronizes a DLQ snapshot and shows paged metadata, plus the exception and a one-click retry on a detail page per job |
| Clear a queue | `horizon:clear` and `queue:clear` | `queue:clear` is not supported: the command fails, and the jobs still run |
| Native binary | Not needed | Rust engine requires an explicit version-pinned installation |

Matching names do not imply identical algorithms. Capacity limits can be configured to the same
values, but queue depth, runtime estimation, cooldown and process lifecycle come from different
implementations.

## Reliability boundary

On one Linux server, the three engines went through 15 failures, two replica scenarios, a 45-minute
mixed soak and 32 Laravel queue features; the two tables below summarize them. Earlier, the
qualification and the Raft campaign killed workers during user code, and a prefetched batch outlived
its 30 s lease while the master renewed it, with no duplicate effect. That verifies the tested
at-least-once paths.

It does not verify exactly-once external effects. A process can perform an external side effect and
die before its acknowledgement becomes durable in any of the three systems. Jobs still need an
idempotency strategy.

Queen's remaining pre-GA gates include a 24-hour Laravel soak, network and storage faults, the same
failure lanes on PostgreSQL storage and a Raft cluster, broader scaling and partition matrices, and
native release verification.

## What happens when something fails

The same Laravel application ran through each failure on Horizon, the Queen PHP supervisor and the
Queen Rust supervisor, on one Linux server, with Queen's production-like settings. Pass means that
every job completed once, or failed once into `failed_jobs`, and that no two attempts of one job ran
at the same time.

| Failure | Horizon | Queen PHP | Queen Rust |
| --- | --- | --- | --- |
| A job throws until `tries` runs out | Pass | Pass | Pass |
| A job throws once, then succeeds | Pass | Pass | Pass |
| A job calls `release()` or `fail()` | Pass | Pass | Pass |
| A job runs past its `timeout` | Pass | Pass | Pass |
| A job takes its worker over `--memory` | Pass | Pass | Pass |
| A job exceeds PHP's `memory_limit` | Pass | Pass | Pass |
| SIGKILL on a worker during a job | Pass | Pass | Pass |
| SIGKILL on the master | Pass | Pass | Pass |
| A deploy during jobs shorter than the grace | Pass | Pass | Pass |
| A deploy during jobs longer than the grace | Pass | Pass | Pass |
| A deploy during the second of two long jobs on one worker | Pass | Pass | Pass |
| The backend restarts | 2 of 300 jobs ran twice | Pass | Pass |
| The backend freezes for 5 s | Pass | Pass | Pass |
| The backend freezes for 45 s, past the lease | Pass | Pass | Pass |
| `dispatch()` while the backend is down | Pass: it throws | Pass: it throws | Pass: it throws |
| Two masters, one killed | Pass | Pass | Pass |
| Two masters, restarted one after the other | Pass | Pass | Pass |
| 45 minutes of mixed jobs, with a worker killed every 10 minutes and a deploy | Pass | Pass | Pass |

A fourth profile, the Rust engine with prefetch 4, `ack_async` and `pop_ahead`, passed every lane
except one: a job that crashes its worker also charged an attempt to the jobs prefetched with it.
The worker's lease renewer, the Rust master or the PHP helper, now hands those jobs back after a
worker crash, and that lane passed in a rerun on both engines
([prefetch](/use/laravel/concepts#prefetch-ack_async-and-pop_ahead)). The first run of these lanes
found three defects in the Queen PHP client and supervisors, fixed in this release; the
[benchmark page](/benchmarks/laravel-supervisors#failures-replicas-a-soak-and-laravel-features-2026-10-02)
has every lane, the defects and the data.

## Laravel queue features

Each feature ran with the same application on the three engines and was checked against the
behaviour that the Laravel documentation states.

| Area | Features checked | Horizon | Queen PHP | Queen Rust |
| --- | --- | --- | --- | --- |
| Delays and retries | `delay()`, a `DateTimeInterface` delay, `backoff` arrays, `retryUntil()`, `release()` with a delay, `maxExceptions`, `failOnTimeout`, `ThrottlesExceptions` | Pass | Pass | Pass |
| Uniqueness and limits | `ShouldBeUnique`, `ShouldBeUniqueUntilProcessing`, `WithoutOverlapping`, `RateLimited`, `Skip` | Pass | Pass | Pass |
| Chains and batches | chains, a failing chain's `catch`, batches with `then`, `catch` and `finally`, `allowFailures()`, `cancel()`, `queue:retry-batch` | Pass | Pass | Pass |
| Other queued work | queued listeners, queued notifications, queued closures with `catch`, `ShouldBeEncrypted`, `$deleteWhenMissingModels`, a job that forks | Pass | Pass | Pass |
| Transactions and events | `afterCommit`, `Queue::before`, `Queue::after` and `Queue::failing` | Pass | Pass | Pass |
| Commands | `queue:retry`, `queue:forget`, `queue:flush`, `queue:prune-failed`, `queue:monitor`, `Queue::size()` | Pass | Pass | Pass |
| Clearing a queue | `queue:clear` | Clears it | Not supported: the command fails, and the jobs still run | Not supported |

The Rust engine with prefetch 4, `ack_async` and `pop_ahead` passed all 32 features as well.
Laravel's Redis queue stores due times in whole seconds, so on Horizon a retry can start up to a
second early or late: for `backoff` `[1, 3]`, Horizon's retries came after 1.81 and 4.03 s, Queen's
after 1.02 and 3.05 s.
