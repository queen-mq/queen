## Start here

Queen replaces two parts of a Horizon setup: Redis, where the jobs wait, and Horizon's master, which
runs the workers. Your job classes stay as they are.

<Chart

Each line below names the measurement behind it:

- **More jobs per worker at the same durability.** On a dedicated Linux server, with every write
  fsynced on both sides, 32 workers completed 2,753 jobs/s of 10 ms jobs against 1,124 for Horizon,
  and 64 workers 4,395 against 1,090
  ([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-a-linux-server-2026-10-01)).
- **Lower latency at a steady rate.** On the same server, with 16 workers and 500 jobs/s asked, 95%
  of jobs completed within 23 ms of their dispatch, against 227 ms for Horizon, whose producer
  reached 440 jobs/s
  ([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-a-linux-server-2026-10-01)).
- **Smaller workers.** With 64 workers forked from one booted Laravel, the application container used
  183 MiB against 1,892 MiB for Horizon
  ([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-a-linux-server-2026-10-01)).
- **Long jobs on a short `retry_after`.** The lease of a running job is renewed, and a worker that
  cannot renew it is stopped before the lease ends. In a fault test, a prefetched job ended 32.1 s
  after it was queued, past its 30 s lease, on its first attempt
  ([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-raft-2026-10-01)).
- **Workers within seconds of a burst.** Woken by the broker, one supervisor with `fast_scale_up`
  reached 20 workers 5.6 s after a burst, against 13.9 s when it polled every 3 s; Horizon was not
  part of that run
  ([benchmark](/benchmarks/laravel-supervisors#event-driven-scaling)).

These results are diagnostic: each comes from one host, and the protocol was written by the Queen
team. Horizon keeps advantages too, such as less broker CPU at a low, steady rate and a more complete
dashboard.

## The connection and the supervisor

Queen can play two separate roles in a Laravel application:

1. The `queen` queue connection stores Laravel jobs in Queen instead of Redis or a database table.
2. The optional Queen supervisor starts, stops and balances ordinary `queue:work queen` processes.

You can use the queue connection with your existing process manager and add the supervisor later.
Your jobs still implement Laravel's normal `ShouldQueue` contract and keep their middleware, retry,
backoff and failed-job events.

<Aside type="caution">
The Laravel supervisor and dashboard are currently preview features. The queue driver is usable on
its own, but the production supervisor qualification is not complete on every target. Start with the
safe settings on this page and read [Production checks](/use/laravel/supervisors#production-checks)
before replacing Horizon.
</Aside>

## Before you start

You need PHP 8.3 or newer, a Laravel application and a reachable Queen broker. If Queen is not
running yet, [start the local Compose stack](/deploy/compose) first.

The queue driver itself does not require the process-control extensions. The Queen supervisors are
Unix-only today and add `pcntl` and `posix` requirements.

## Install the queue connection

<Steps>

1. **Install the Composer package.**

   ```bash
   composer require queen-mq/php-client
   ```

2. **Publish the configuration.**

   ```bash
   php artisan vendor:publish --tag=queen-config
   ```

   Package discovery registers the service provider, the `Queen` facade and a `queen` queue
   connection. You do not need to add that connection to `config/queue.php` unless you want to
   override it explicitly.

3. **Point Laravel at Queen.**

   ```dotenv
   QUEUE_CONNECTION=queen
   QUEEN_URL=http://127.0.0.1:6632
   QUEEN_QUEUE=default
   QUEEN_CONSUMER_GROUP=laravel
   QUEEN_RETRY_AFTER=90
   QUEEN_PREFETCH=1
   QUEEN_ACK_BATCH=1
   ```

   Add `QUEEN_BEARER_TOKEN` when the broker requires authentication. Keep secrets outside source
   control. Give each logical application and environment a stable consumer-group name: two
   applications sharing one group intentionally share one cursor and split the work. A group does
   not separate applications, though: two groups on one queue each receive every job, so give each
   application and environment its own queue names or its own broker as well.

4. **Dispatch an existing job.** Nothing changes at the call site.

   ```php
   use App\Jobs\GenerateInvoice;

   GenerateInvoice::dispatch($invoiceId);
   ```

5. **Run one worker.**

   ```bash
   php artisan queue:work queen --queue=default --timeout=60 --tries=3
   ```

   `QUEEN_RETRY_AFTER` is the lease duration. It must be longer than the worker timeout and the
   longest job runtime. Stop this first worker with the same signal you use for any Laravel worker.

</Steps>

At this point the integration works without either Queen supervisor. Keep your current systemd,
Kubernetes, Supervisor or platform process definition if all you need is a fixed worker count.

## Start with the safe delivery profile

The default `prefetch=1` and `ack_batch=1` preserve one synchronous acknowledgement boundary per
job. Use this profile while validating a migration and whenever every job, including safety margin,
fits inside `retry_after`.

Values above one reduce broker round trips, but they widen the at-least-once redelivery window. A
Laravel worker may also pause while it still owns a prefetched tail. The Queen connector therefore
rejects `prefetch > 1` unless lease renewal is enabled, whether workers are started by Queen or by
another process manager.

```dotenv
QUEEN_PREFETCH=4
QUEEN_ACK_BATCH=1
QUEEN_LEASE_RENEWAL=true
```

Enable lease renewal even with `prefetch=1` when the longest runtime cannot be bounded safely.
Renewal extends the active lease and fences the worker if renewal can no longer finish safely. Under
the [Rust supervisor on Linux](/use/laravel/supervisors#lease-renewal-in-the-master), the master
renews the leases of all its workers. Elsewhere, lease renewal starts a small PHP helper beside each
worker, and an exact-PID `SIGCHLD` watchdog kills the owning worker if that helper disappears while
a lease is active. This Unix CLI path requires PCNTL/POSIX support, and application code must not
replace Queen's signal handler. Renewal cannot make external side effects exactly once, so jobs
must remain idempotent.

### Asynchronous acknowledgements

With `ack_async`, a worker sends the acknowledgement of a completed job and starts the next job at
once. The broker commits the acknowledgement while the next job runs, and the worker reads the
answer when that job ends or before its next pop.

```dotenv
QUEEN_ACK_ASYNC=true
```

The cost is a later failure report. When the broker refuses an acknowledgement, the job after it
has already run on the same lease. The worker reports the refusal through Laravel's exception
handler, abandons the lease and discards the rest of its prefetched jobs, and the refused job is
delivered again after its lease expires. Delivery stays at-least-once. `ack_async` requires
`ack_batch=1`, because a batch already defers its acknowledgements.

With `prefetch=1` and without `pop_ahead`, the worker must read the answer before its next pop,
so `ack_async` gains little there. The gain is the broker's write latency per job. On the Raft broker, which fsyncs every acknowledged
write, eight workers with 10 ms jobs and prefetch 4 went from 453 to 566 jobs/s with `ack_async`, and
to 643 with `pop_ahead` too ([benchmark](/benchmarks/laravel-supervisors#horizon-against-queen-on-raft-2026-10-01)).

### Pop the next batch ahead

With `pop_ahead`, a worker that starts the last job of its local batch also sends the pop for the
next batch. The broker leases that batch while the job runs, and the worker takes it in when the
job ends, so the next job starts without a round trip.

```dotenv
QUEEN_LEASE_RENEWAL=true
QUEEN_POP_AHEAD=true
```

The batch is leased one job earlier than without the option, so it needs `lease_renewal` like any
prefetched job. The worker tracks the new lease as soon as the job ends, before it can pause. A
worker does not pop ahead after a job that took more than a third of `retry_after`, and when a job
still leaves too little of the new lease to renew it safely, the worker returns the batch to the
queue at once. A worker that serves a comma-separated queue list never pops ahead, because its
next job may come from another queue. A worker pops ahead only after a full batch: a batch that
came back short shows that the queue was nearly empty, so a pop sent ahead would most likely come
back empty too. Under a light load the worker then sends one pop per job, not two: at 500 jobs/s on
the benchmark server that took 12% off the broker's CPU and 8% off the workers', with no change under
a backlog. A pop sent ahead never waits for new jobs, so an idle queue behaves as before.

## What changes from another Laravel connection

| Area | What stays the same | What changes with Queen |
| --- | --- | --- |
| Job code | `ShouldQueue`, `dispatch()`, middleware, timeout, tries and backoff | Storage and delivery use Queen leases and consumer groups |
| Delays | Laravel delayed dispatch and positive backoff | Queen timers store the delay |
| Failures | Laravel's failed-job commands remain the command index | Queen also retains a synchronized DLQ snapshot by default |
| Ordering | Laravel queue names | Implement `QueenPartitionable` when one entity needs its own FIFO lane |
| Delivery | At-least-once | A lease expiry or worker crash can redeliver a job |
| Clearing | Connection-specific | Queen does not yet provide one atomic clear across ready jobs, live leases and Laravel timers |

## Choose how workers are managed

| Choice | Use it when | Master process |
| --- | --- | --- |
| Existing process manager | You want a fixed number of `queue:work` processes | Whatever you already operate |
| Queen PHP | You want Horizon-like local pools with no native artifact | Laravel remains loaded in one PHP master |
| Queen Rust | You want the smallest control plane and crash-loop circuit breaking | Rust, after one temporary Artisan configuration load |

The PHP and Rust engines read the same configuration and publish the same state protocol. Either
engine can also publish it to the broker for a dashboard served by other hosts. Begin with
[Worker supervisors](/use/laravel/supervisors), then enable the
[Laravel dashboard](/use/laravel/dashboard) only after authentication is in place.

Both engines offer the same opt-in features beyond Horizon's pools, each off by default:

| Feature | What it does | Measured |
| --- | --- | --- |
| [Coordinated replicas](/use/laravel/supervisors#several-replicas) | Several pods or hosts on one queue share one worker target | Two pods held the target at every sample, instead of up to twice it |
| [Prefork workers](/use/laravel/supervisors#prefork-workers) | Laravel boots once per master; workers are forked from it and share its memory | 8 workers after 600 jobs: 85 MiB instead of 336 MiB |
| [Event-driven scaling](/use/laravel/supervisors#event-driven-scaling) | The broker wakes the master when jobs arrive, instead of the next poll | 20 workers after a burst in 5.6 s instead of 13.9 s |
| [Per-queue minimum and fast scale-up](/use/laravel/supervisors#dedicated-and-balancing-workers) | Every queue keeps a warm worker; a burst closes half the gap each cycle | |
| [Monitoring and alerts](/use/laravel/monitoring) | Job metrics per class, monitored tags, long-wait alerts, a Prometheus endpoint for KEDA | |

The measurements come from one host; the [benchmark page](/benchmarks/laravel-supervisors) has the
method. [Scale Laravel queues on Kubernetes](/use/laravel/kubernetes) puts the features together
for pods that follow the backlog.
