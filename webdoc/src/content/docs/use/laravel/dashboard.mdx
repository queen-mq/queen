The Laravel panel answers one question: **what is this application's Queen supervisor doing?** It
reads the private supervisor state already written by the PHP or Rust engine on this host. When
supervisors run on other hosts or pods, it can also read the copy each engine
[publishes to the broker](#a-supervisor-on-another-host). It does not poll queue depth again and it
is not a replacement for Queen's global broker dashboard.

The route is absent by default.

## Enable it locally

```dotenv
QUEEN_DASHBOARD_ENABLED=true
QUEEN_DASHBOARD_PATH=queen
QUEEN_DASHBOARD_REFRESH_SECONDS=5
QUEEN_DASHBOARD_FAILED_JOBS_LIMIT=50
```

Open `/queen`. Local and testing environments may use the built-in local allowance while
`queen.dashboard.allow_local` is true.

Each sidebar section is its own page, so a reload or a shared link lands on the same view:

| Page | Path |
| --- | --- |
| Overview | `/queen` |
| Workload | `/queen/workload` |
| Supervisors | `/queen/supervisors` |
| Failed jobs | `/queen/failed-jobs` |
| Configuration | `/queen/configuration` |

Each page refreshes every `QUEEN_DASHBOARD_REFRESH_SECONDS` in place: a small packaged script
fetches the page again and swaps only the header and the main region, so scroll position and the
sidebar stay put. **Pause auto-refresh** in the header stops it; the choice is kept in the browser's
local storage. Refreshing waits while the tab is hidden, while text is selected or while focus is on
a control that would be replaced, and stops with a notice when the response is no longer the panel,
for example after the session expired. Without JavaScript the pages still work: a `<noscript>` meta
refresh reloads the current page whole.

To test the production authorization path locally, disable that allowance:

```dotenv
QUEEN_DASHBOARD_ALLOW_LOCAL=false
```

Changing the route path, domain, enabled flag or middleware after Laravel has cached routes or
configuration requires rebuilding both caches:

```bash
php artisan config:clear
php artisan route:clear
php artisan config:cache
php artisan route:cache
```

## Authorize production access

Enabling the route is not enough in production. Queen denies access until the application defines
the `viewQueenDashboard` Gate ability. Attach application authentication before that Gate runs:

```php
// config/queen.php
'dashboard' => [
    'enabled' => env('QUEEN_DASHBOARD_ENABLED', false),
    'path' => env('QUEEN_DASHBOARD_PATH', 'queen'),
    'middleware' => ['web', 'auth'],
],
```

```php
use Illuminate\Support\Facades\Gate;

Gate::define('viewQueenDashboard', function ($user): bool {
    return $user !== null && $user->canOperateQueues();
});
```

The package always retains Laravel's `web` middleware, even if it is omitted from the configured
list. This preserves sessions and CSRF protection for state-changing controls. Put the route behind
the same network and identity controls as any other production administration surface.

<Aside type="danger">
Do not define a production Gate that simply returns `true` unless another trusted layer has already
authenticated and authorized the request. The same Gate protects the HTML page, JSON status and
control actions.
</Aside>

## What the panel shows

- master engine, host, PID, state, generation and live/stale heartbeat of each supervisor instance;
- whether that status is local or published by a supervisor on another host;
- a warning when more than one running master autoscales the same queue and consumer group without
  coordinating, and each coordinated pool's share of its replicas;
- pools, queues, worker counts and workers currently draining;
- last queue depth already sampled by the supervisor;
- [jobs completed, failed and dispatched](#jobs-processed) per queue over the last hour, six hours,
  day or week, from the broker's own counters;
- on the **Jobs** page, [throughput, failures and runtime per job class](/use/laravel/monitoring#jobs-per-class)
  from every worker of every host;
- on the **Tags** page, [monitored tags](/use/laravel/monitoring#monitored-tags) and the recent jobs
  carrying them;
- restart and circuit state;
- a safe allowlist of worker settings;
- paged metadata from supported Laravel database or file failed-job stores, and the reason each
  job failed.

The read model never returns broker endpoints, bearer tokens, custom headers, job payloads or raw
backend errors. Exception text appears only on the [detail page](#why-a-job-failed) of a failed job.
Unsupported or unavailable failed stores are shown as unavailable instead of falling back to an
unbounded read.

## What the panel controls

The three controls apply to the complete local master:

| Control | Effect |
| --- | --- |
| Pause | Drain current workers and start no replacements |
| Continue | Resume reconciliation and start workers as needed |
| Terminate | Drain, stop the master and let the outer process monitor restart it if configured |

Each form carries the exact supervisor `instance_id`. An old page cannot pause or terminate a
replacement generation. Queen also refuses a second pending command instead of overwriting the
first one.

| HTTP result | Meaning |
| --- | --- |
| `404` | Dashboard disabled at runtime or route not registered |
| `403` | The `viewQueenDashboard` Gate denied authorization |
| `419` | CSRF token absent or expired |
| `409` | Supervisor replaced, stale, unavailable, on another host, or already has a pending command |
| `303` | Command accepted, followed by a redirect back to the panel |

Authentication middleware runs before Queen's Gate. An unauthenticated request can therefore
redirect or return `401`, depending on the application's guard and request format.

Control TTL and heartbeat timeout are values published by the active supervisor generation. A
newly deployed Laravel configuration cannot silently reinterpret an old master's liveness or run an
expired command. Restart the supervisor to activate timing changes.

## Jobs processed

The Workload page charts how many jobs completed and failed per time bucket, like Horizon's
throughput view. It reads the counters the broker already keeps for every queue, through
[`GET /api/v1/analytics/queue-ops`](/reference/http/analytics), so it adds no write to the job
path and needs no setting.

| Figure | Broker counter | For Laravel jobs |
| --- | --- | --- |
| Completed | `ackSuccess` | jobs acknowledged as completed |
| Failed | `ackFailed` | jobs moved to the dead-letter queue, plus rejected acknowledgements |
| Dispatched | `pushMessages` | jobs pushed to the queue |

A job that Laravel releases for another attempt is a broker transaction, not an acknowledgement,
so a retried attempt is not counted as completed. The counters are per queue: every consumer
group that acknowledges the queue adds to them.

The **1h**, **6h**, **24h** and **7d** links set the window, which also sets the bucket width the
broker uses: 1 minute for an hour, 5 minutes for six hours, 15 minutes for a day and 60 minutes for
a week. The selected window stays in the page address (`?range=24h`) and in the automatic
refresh. Times are shown in UTC. A table below the chart gives the totals per queue.

Only the Workload page reads the counters. It sends one request per configured queue, in
parallel, with the supervisor's `read_bearer_token` when one is set and a timeout of at most five
seconds, and caches the result for 15 seconds in Laravel's default cache store. A queue whose
counters cannot be read is marked unavailable without hiding the others.

## Failed jobs and the broker dashboard

Laravel remains the command index for Laravel jobs:

```bash
php artisan queue:failed
php artisan queue:retry <id>
php artisan queue:forget <id>
php artisan queue:prune-failed
```

The Queen panel displays failed-job metadata but does not provide web actions for retry, forget,
flush or prune. When failed-job synchronization is enabled, those Laravel commands also coordinate
the matching Queen DLQ snapshot.

The failed-jobs page shows `QUEEN_DASHBOARD_FAILED_JOBS_LIMIT` jobs, newest first, with **Older**
and **Newest** links. The pages use a keyset cursor instead of an offset: on a database store each
page is one `id < ?` range read on the primary key, with one extra row to learn whether an older page
exists, and never a `COUNT(*)`. A table with millions of failed jobs therefore costs the same per
page as a table with ten, and the total shows as a lower bound (`51+`) when more rows exist. A file
store is read whole, within the 4 MiB bound the panel always applies to it, and its pages are
positions: a new failure or a retry while you read an older page shifts that page by one row.

### Why a job failed

Each row of the failed-jobs page ends with an arrow and opens that job in a drawer beside the
list; **Open as page** shows the same detail at `/queen/failed-jobs/{id}`, which is also where the
row leads without JavaScript. Automatic refresh pauses while the drawer is open. The detail shows
the job class, the queue and connection, the maximum tries and timeout read from the payload, the
exception class and message in red under **Why it failed**, the stack trace, and the `queue:retry`
command for that job. Each of the last three has a **Copy** button; where the browser offers no
clipboard access, for example on a plain `http://` origin, the button copies through a selection
instead. The payload itself is never displayed. Paths under the application root are shown relative
to it, and the page does not refresh itself. The exception and the payload are read from the
store cut to 1 MiB, in SQL on a database store, so a row of many megabytes costs no more memory
than that. The page does not show an attempt count: Laravel's payload counter is only kept current
by the Redis driver, so it would read `0` for a job that used every try.
The exception message can contain application data, so the page sits behind the same
`viewQueenDashboard` Gate as the rest of the panel.

Use the [broker dashboard](/deploy/dashboard) for global queue analytics and DLQ operations. The
two dashboards intentionally cover different scopes:

| Laravel supervisor panel | Queen broker dashboard |
| --- | --- |
| One local application master | Queues and consumer groups visible to the broker |
| Worker processes and restart state | Backlog, partitions, lag, messages and system metrics |
| Laravel failed-job metadata | Queen DLQ records |
| Pause, continue and terminate the local master | Broker and queue administration |

## A supervisor on another host

The panel reads one local `state_directory`. When the dashboard is served by other processes than
the supervisor, for example Kubernetes web pods beside a dedicated worker pod, that directory is
empty and the supervisor shows as unavailable. Either engine can close that gap by also publishing
its status document to the broker's [key/value store](/use/kv):

```dotenv
QUEEN_SUPERVISOR_REMOTE_STATUS=true
QUEEN_SUPERVISOR_REMOTE_STATUS_KEY=orders-production
```

Set both variables on every supervisor host and on every web host, so the publishers and the reader
address the same key. Use one key per application and environment that share a broker. Every
supervisor instance publishes into its own slot under that key, named by its `instance_id`, so
several hosts or pods never overwrite each other.

| Variable | Default | Meaning |
| --- | --- | --- |
| `QUEEN_SUPERVISOR_REMOTE_STATUS` | `false` | Publish the status document |
| `QUEEN_SUPERVISOR_REMOTE_STATUS_KEY` | none | Key the documents are published under, required when enabled |
| `QUEEN_SUPERVISOR_REMOTE_STATUS_CONNECTION` | `queen` | Laravel queue connection whose broker and credentials are used |
| `QUEEN_SUPERVISOR_REMOTE_STATUS_NAMESPACE` | `queen-supervisor` | Key/value namespace |
| `QUEEN_SUPERVISOR_REMOTE_STATUS_INTERVAL` | `poll_interval` | Seconds between publishes; a state change publishes at once |
| `QUEEN_SUPERVISOR_REMOTE_STATUS_TTL` | twice `heartbeat_timeout`, at least 300 | Expiry of the published copy |

The Supervisors page shows one card per instance: a live local supervisor first, then every
published one, live before stale, each with its host name, PID and last heartbeat. The overview,
the header and the notices sum workers, draining processes and the process budget over the live
instances, and report ready or healthy only when every live instance is. A stopping or stopped
master is not live, so the old pod of a rollout stays listed as stale until its copy expires and
never counts in those totals. A local supervisor keeps its controls; every published instance is
**read-only**: pause, continue and terminate stay with `php artisan queen:supervisor` on its own
host, and a control POST for it answers `409`. Liveness comes from the published heartbeat alone,
because a web host cannot check another supervisor's owner lock. Keep `heartbeat_timeout` and the
supervisors' clocks sane: a copy older than the heartbeat timeout shows as stale, and an expired
one disappears.

When more than one running instance autoscales the same queue for the same consumer group without
coordinating, the panel warns: each master sizes its workers from the whole backlog, so together they
can exceed `max_processes`. [Coordinated replicas](/use/laravel/supervisors#several-replicas) share
one target and are not reported, and each of their pools shows its share of the replicas. Fixed
pools do not follow the backlog and are not reported either.

What travels is the same document as `status.json` without its legacy pool map. It is split across
`<key>/<instance_id>/head` and `<key>/<instance_id>/chunk/NNNN`, written in one batch transaction,
so it never depends on the 64 KiB key/value value ceiling. The panel lists every slot with
`getPrefix` and decodes each one from a single page, which is one snapshot; a slot a page cuts
through is read whole on the next page. Chunks left over by an earlier, larger write are recognized
by their write id and expire with their TTL, like the slots of instances that are gone. A document
at `<key>/head`, the single slot of releases before per-instance slots, is still read, so web hosts
can be upgraded before their supervisors. The connection is resolved without `read_bearer_token`,
because publishing is a key/value write.

Publishing is best effort. The resolver adds one request timeout per broker endpoint to the
heartbeat budget, a failure is reported once per failure streak, and a broker outage shows the
supervisor as stale without ever stopping supervision. The Rust engine publishes from supervisor
0.2.0, and into its own instance slot from 0.3.0: `queen:supervisor-config --for-engine` hands it
the setting with its write credential, and it publishes after every status write, throttled to the interval and forced on
every state change, exactly like the PHP engine.

## Metrics for scrapers

The same state is available to Prometheus, and through it to Kubernetes autoscalers, at
`/queen/metrics` with its own bearer token and no session. See
[Prometheus and Kubernetes autoscaling](/use/laravel/monitoring#prometheus-and-kubernetes-autoscaling).

## Behind a load balancer

Without remote status, the panel is not a multi-host aggregator. Route the administrative endpoint
to the host that owns the supervisor, or use a sticky dedicated admin endpoint. A GET on host A
followed by a control POST on host B intentionally fails the instance fence.

The view loads no fonts or assets from a CDN and contains no inline scripts, style blocks or style
attributes. The package serves its content-hashed stylesheet and refresh script from the dashboard
routes, without a `vendor:publish` or frontend build step. Both links include Subresource
Integrity. Content Security Policy allows scripts, styles and `fetch` only from the same origin and
explicitly rejects inline style attributes. Dynamic responses use `no-store`, while successful
asset responses use an immutable one-year private browser cache with intermediary transformations
disabled to preserve the integrity digest.
Error responses are never cached. Responses also carry frame denial, MIME-sniffing denial and a
no-referrer policy.

### Web servers that serve every asset statically

Some web server configurations answer every `*.css` or `*.js` request from the public directory and
never reach PHP, for example an nginx or Caddy rule for static assets. The asset routes then return
the web server's `404`: the panel renders unstyled and falls back to whole-page refreshes. Publish
the assets instead, as Horizon does with its own:

```bash
php artisan vendor:publish --tag=queen-assets --force
```

The copies land in `public/vendor/queen/dashboard.css` and `public/vendor/queen/dashboard.js`. The
panel links to each, with the content version as a query string and the same integrity digest,
only while it is byte-identical to the packaged file. A missing or stale copy, for example after an
upgrade without republishing, falls back to the route, so publishing can never serve the wrong
styles. The file is also tagged
`laravel-assets`, which the default Laravel `post-update-cmd` republishes on every
`composer update`. In container builds, run the publish command next to the other asset steps.
