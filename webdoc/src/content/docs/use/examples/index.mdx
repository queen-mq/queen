The examples in this section are not transcriptions. Where a page shows a flow that a client test already covers, the code block on the page is the exact text of a region inside that test file, extracted at documentation build time; nobody retypes it, so it cannot drift into being subtly wrong while still looking plausible.   .queue('orders')

## How a snippet gets onto a page

The marker matcher is comment-flavour agnostic (`//`, `#` and `--` all work). `webdoc/scripts/gen-snippets.mjs` walks the four client test trees, the C++ client directory and `examples/full` (the [complete runnable programs](/full-examples)), strips the common leading indentation, and writes one partial per region under `src/content/partials/snippets/`, headed by the file it came from and the suite that runs it. Regenerate everything with one command:

```bash
pnpm --dir webdoc gen
```

Three properties of the extractor matter when you read a snippet:

- **Ids are globally unique.** Two regions with the same id anywhere is a hard error, so an id always names one place in the source.
- **Unbalanced markers fail loudly.** An unclosed region, or a `docs:end` without a start, aborts the generator.
- **Removing a marker removes the partial.** The output directory is rewritten from scratch on every run, and `gen.mjs --check` compares instead of writing and exits non-zero on any difference, so a page that renders a deleted region fails the build rather than publishing stale code.

## What running the suites proves

`test/run.sh` builds the broker image and one runner image per language, then runs each suite against a real broker and a real PostgreSQL in an isolated Docker Compose project, on three topologies: `single`, `ha` (a two-broker mesh pair) and `tenanted` (native tenant scoping on while the client suites send no tenant header). The tenanted lane must produce results identical to `single`, and the run fails on any divergence. Run one suite on its own:

```bash
test/run.sh --suite js
```

A green suite means the code in each marked block executed against a broker process talking to PostgreSQL over HTTP, the assertions around it in the same test function passed, and the same code passed again with tenant scoping enabled.

## What the claim does not cover

Be precise about the limits, because a "verified" badge invites over-reading.

- **A snippet is a fragment, not a test.** The assertions that make the test meaningful usually sit outside the marked region; `js-push-dedup` is unusual in carrying its expected statuses as a trailing comment.
- **Region boundaries are a human choice.** Setup the call depends on is frequently just above the `docs:start`; read the source file when a snippet looks like it works in isolation.
- **Green means green in that harness.** The suites run the broker's default configuration on a throwaway database, not your queue configuration, your load, or the proxy.
- **Extraction reads the working tree**, not a published package tag.
- **Only the fenced block is extracted.** The prose around it is hand-written; where a page states a broker rule, its `sourceOfTruth` frontmatter names the file the rule was read out of. Hand-written code on these pages is labelled as such.

<Aside type="caution">
A snippet proves that a call is accepted, never that a design is correct for your workload: ordering, retry and deduplication semantics are properties of the broker, not of the example.
</Aside>
