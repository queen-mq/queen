The broker crate has a library target: `Broker::start` boots the same engine the standalone binary runs, inside your Rust process, on a data directory you give it. There is no database to reach. Every operation on the handle invokes the same handler functions the HTTP router dispatches to, so behaviour, defaults and edge cases are the broker's by construction, minus one network hop and one deployment unit.

<Aside type="note">
The embedded API is published as **beta**: the HTTP API remains the stable compatibility surface, and [versions and compatibility](/reference/compatibility) states both contracts.
</Aside>

## Install

```toml
[dependencies]
queen-engine = { version = "2.0.0-alpha.4", default-features = false }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
serde_json = "1"
```

The package is named `queen-engine` (the bare crates.io name `queen` belongs to an unrelated crate) and imports as `queen`; it needs Rust 1.88. This page describes the 2.0 line, which is in alpha: pin the exact version you tested, as `server/Cargo.toml` states it. A 1.x version of the crate is the PostgreSQL engine and has no `raft` builder. `default-features = false` skips the `server` feature, which exists for the repository's own binary: the axum serve stack, the embedded dashboard and the tracing subscriber stay out of your build. Built with default features, the broker serves the API but not a working dashboard: that bundle is a build product of the repository and the Docker image. `queen-mq` is the HTTP client; this crate is the broker itself.

## Start

The code on this page runs inside an async function and assumes:

```rust
use queen::{Broker, BrokerConfig};
use queen::protocol as qp;
```

<Render file="snippets/embedded-start" />

`BrokerConfig::new().raft(dir)` names the data directory, and `start` opens it, creating it on first use, recovers what it holds, and starts the engine on your tokio runtime. It returns once the broker can serve. There is no schema to apply, no connection pool to size and no spool to recover: everything the broker keeps lives in that directory, so put it on a persistent disk, and give every `Broker` a directory of its own.

`Broker` is cheap to clone and every clone shares the same engine. Call `shutdown()` on the way out.

## Produce and consume

<Render file="snippets/embedded-push" />

Requests and responses are the [queen-protocol](/use/rust-client/) types, re-exported as `queen::protocol` (the `qp` alias above). Push results carry per-item outcomes (`queued`, `duplicate` or `error`) in request order. Popping through the same handle claims a lease exactly as over HTTP:

```rust
// Illustrative, not extracted from a test.
let params = qp::PopParams {
    batch: Some(10),
    consumer_group: Some("workers".into()),
    subscription_mode: Some(qp::SubscriptionMode::All),
    ..Default::default()
};
let popped = broker.pop("orders", &params).await?;
for m in &popped.messages {
    broker.ack(&qp::AckRequest {
        transaction_id: m.transaction_id.clone(),
        partition_id: m.partition_id.clone(),
        status: qp::AckStatus::Completed,
        consumer_group: Some(m.consumer_group.clone()),
        lease_id: Some(m.lease_id.clone()),
        error: None,
    }).await?;
}
```

With `wait: Some(true)` a pop parks directly on the broker's in-process waker and is woken by a concurrent push, replacing the HTTP long-poll choreography. An empty claim returns an empty response, never an error.

## Transactions

The broker's atomic handoff works unchanged: ack the input and push the next stage in one entry of the broker's log, guarded by the input's lease.

<Render file="snippets/embedded-transaction" />

A rollback (an expired required lease, a duplicate push) comes back as `success: false` with the broker's message in `error` and its code in `reason`, exactly as over HTTP.

## The disk gate

Writes are refused with `507` once the filesystem of the data directory is 85% used, and accepted again below 80%. `raft_disk_pct(high, low)` sets both, as do `QUEEN_RAFT_DISK_HIGH_PCT` and `QUEEN_RAFT_DISK_LOW_PCT`. Size the disk for the retention you configure. Defaults and the other builder methods are in the [Engine API reference](/reference/engine).

## What it puts in your process

The engine plans, writes its log, applies and checkpoints on threads of its own; the driver that feeds them, and that fires timers and runs retention, is a task on your tokio runtime. The library never installs a tracing subscriber, so install your own to see the broker's logs.

A panic on one of the engine's core threads (the planner, the log writer, apply, the checkpoint) aborts your process: `start` installs a panic hook for that, chained to yours, and the next start recovers from the data directory. Every other panic, your own included, unwinds as usual.

## Not offered

[Ephemeral queues](/use/ephemeral) are exposed: the six verbs and the two status reads run against the same in-process engine, taking and returning plain JSON values rather than typed protocol structs. Consumer-group administration (list, seek, delete), durable queue listings, traces, the streams runner endpoints and the key/value and timer routes are not exposed in the beta surface. Tenancy and JWT auth do not apply in-process: the embedded broker is single-tenant, trusts its caller, and logs a warning if their env knobs are set.

The full surface, argument by argument: [Engine API reference](/reference/engine).
