Windowed aggregation over a queue, expressed as an operator chain, with the accumulator state stored in the same PostgreSQL the broker uses. The operators run in your process; the broker contributes three endpoints, and the important one commits your state changes, your output messages and your source ack in one transaction. A stream is a process holding a partition lease, not a service to deploy.

## A complete query

<Tabs>

<TabItem label="JavaScript">

```js
// Illustrative, not extracted from a test.
import { Queen, Stream } from 'queen-mq'

const url = 'http://localhost:6632'
const queen = new Queen({ url })

const perMinute = Stream
  .from(queen.queue('orders'))
  .filter(msg => msg.data.amount > 0)
  .windowTumbling({ seconds: 60, gracePeriod: 5 })
  .aggregate({ count: () => 1, sum: m => m.amount })
  .map((agg, ctx) => ({ partition: ctx.partition, ...agg }))
  .to(queen.queue('orders.per_minute'))

const handle = await perMinute.run({ queryId: 'orders.per_minute', url })
// handle.metrics() reports counters; stop() drains in-flight cycles.

// Each closed window is one ordinary message on the sink queue.
const emits = await queen.queue('orders.per_minute')
  .group('reporting')
  .subscriptionMode('all')
  .batch(10)
  .pop()
await queen.ack(emits, true, { group: 'reporting' })

await handle.stop()
```

</TabItem>

Each closed window becomes one ordinary message on the sink queue, one per window and key: the payload is the value that left the chain (here `{ partition, count, sum }`), the partition name is the source's unless the sink overrides it. There is no separate results API: anything that can consume a queue reads it. What each callback receives:

| Callback | Receives |
| --- | --- |
| `filter`, `keyBy`, pre-window `map` | The source message, payload under `msg.data` |
| `aggregate` extractors, `reduce` | The value being aggregated: the payload, or whatever an upstream `map` returned |
| Post-window `map` | The aggregate plus a `ctx` carrying `partition`, `key`, `windowStart`, `windowEnd`, `windowKey` |

## The operator set

The chain is immutable (every combinator returns a new stream) and `run` finalises it. A sink (`to` or `foreach`) must be last; the builder rejects a chain where it is not. The same operators exist in four languages:

| Stage | JavaScript | Python | Go | Rust |
| --- | --- | --- | --- | --- |
| Stateless | `map`, `filter`, `flatMap` | `map`, `filter`, `flat_map` | `Map`, `Filter`, `FlatMap` | `map`, `filter`, `flat_map` |
| Keying | `keyBy` | `key_by` | `KeyBy` | `key_by` |
| Windows | `windowTumbling`, `windowSliding`, `windowSession`, `windowCron` | `window_tumbling`, `window_sliding`, `window_session`, `window_cron` | `WindowTumbling`, `WindowSliding`, `WindowSession`, `WindowCron` | `window_tumbling`, `window_sliding`, `window_session`, `window_cron` |
| Folding | `reduce`, `aggregate` | `reduce`, `aggregate` | `Reduce`, `Aggregate` | `reduce`, `aggregate_count`, `aggregate_sum`, `aggregate_min`, `aggregate_max`, `aggregate_avg` |
| Flow control | `gate` | `gate` | `Gate` | `gate` |
| Terminal | `to`, `foreach` | `to`, `foreach` | `To`, `Foreach` | `to`, `to_partitioned`, `foreach` |

Rust names each aggregate field with its own call (`aggregate_count("count").aggregate_sum("sum", ...)`) because typed extractors have different signatures; it builds the same single aggregate and fingerprints identically.

<Aside type="note">
The `config_hash` is computed identically in all four SDKs (`sha256` over each operator's kind and structural configuration, user closures excluded), so a query can be redeployed in another language without tripping the mismatch guard; the Rust implementation is pinned with test vectors from the JavaScript one.
</Aside>

## The three endpoints behind it

| Route | Access | Purpose |
| --- | --- | --- |
| `POST /streams/v1/queries` | read-write | Idempotent query registration. Returns the canonical `query_id` used by every later call. |
| `POST /streams/v1/state/get` | read | Read state rows for one `(query_id, partition_id)`, by explicit keys, key prefix, or ripeness. |
| `POST /streams/v1/cycle` | read-write | Commit one cycle: state operations, sink pushes and the source ack, atomically. |

### Registration and the config hash

`run` posts the query name, its source and sink queues, and the `config_hash`. A name already registered with a different hash refuses with **HTTP 409**: rerun the same chain with `reset: true` (Rust: `.reset(true)` on `RunOptions`), which deletes the query's state rows before re-registering, because old accumulators and a new reducer shape do not mix. Registration is otherwise idempotent: restarts and multiple workers re-resolve the same `query_id`.

### The cycle

<Steps>

1. **Pop a batch** from the source under consumer group `streams.<queryId>` (overridable); an ordinary leased pop, whose response carries the lease id the cycle's ack presents.

2. **Read state** for the partition, if the chain is stateful.

3. **Run your operators** in your process and decide which windows close.

4. **Commit** one `POST /streams/v1/cycle`: state upserts and deletes, sink messages, source ack.

</Steps>

The commit is one PostgreSQL transaction: the ack advances the source cursor, and sink pushes take an ordinary push's allocator path (pre-packed into segments), so sink messages get offsets, deduplication and ordering like any other message.

`release_lease` in the cycle body defaults to `true`: ack the whole leased batch. A `gate` operator passes `false`: the cursor advances by exactly the messages allowed and the lease is **retained** on the un-acked tail, so denied messages and their successors redeliver in their original order, with no side queue.

An idle-flush timer commits emit-only cycles (no source ack) that close ripe windows on a quiet partition, every 5000 ms per window operator by default. `idleFlushMs: 0` disables it; a window on a silent partition then never closes.

## Windows

All four kinds take `gracePeriod` and `idleFlushMs`, plus `eventTime`, `allowedLateness` and `onLate` to switch from processing time to event time.

| Kind | Builder call | Semantics |
| --- | --- | --- |
| Tumbling | `windowTumbling({ seconds: 60 })` | Fixed non-overlapping buckets, `floor(time / seconds)`. One state row per key per window. |
| Sliding | `windowSliding({ size: 3600, slide: 60 })` | Overlapping windows of `size` hopping every `slide`; `size` must be an integer multiple of `slide`, enforced at construction. Each event writes `size / slide` state rows per key (here 60), the cost to budget at high key cardinality. |
| Session | `windowSession({ gap: 1800 })` | Per-key activity window: extends as long as events for that key keep arriving within `gap` seconds of each other. |
| Cron | `windowCron({ every: 'day' })` | Wall-clock-aligned tumbling; `every` is `second`, `minute`, `hour`, `day` or `week`. Day and week boundaries are UTC. Full cron expressions are rejected at construction. |

### Processing time and event time

Without an `eventTime` extractor, bucketing uses `createdAt`, the broker-stamped commit time of the message's segment. With one, bucketing uses its return value (a `Date`, epoch milliseconds or an ISO string) and the runtime keeps a per-partition watermark. An event older than `watermark - allowedLateness` is late: `onLate: 'drop'` (the default) discards it, `'include'` accumulates it best-effort (an already-flushed window is recreated and emits a second time when it closes again), anything else throws.

| Mode | A window closes when |
| --- | --- |
| Processing time | `windowEnd + gracePeriod` is at or before the latest time seen |
| Event time | The partition watermark passes the same point |
| Idle flush | Wall clock passes the same point on a quiet partition |

## Keys, partitions and isolation

The state primary key is `(query_id, partition_id, key)`, and that shape is the isolation mechanism: **partition leases are exclusive**, so one worker holds a partition at a time, so every write to one `(query, partition)`'s state rows comes from one writer, with no cross-worker locking. Stateful operators key on the source `partition_id` by default; `keyBy` overrides it, its callback returning the state key used downstream, `keyBy(msg => msg.data.userId)` for one session per user.

<Aside type="caution">
A `keyBy` key that does not line up with the partition lets workers on different partitions write the same logical key, which is contention on shared state rows: repartition instead, by pushing to an intermediate queue partitioned by that key and running the stateful stage there.
</Aside>

Workers of one query divide the source partitions exactly as consumers in one group do; parallelism is the partition count.

## Where the state lives

Two tables in their own schema, `queen_streams`, applied at boot like every other procedure file:

| Table | Contents |
| --- | --- |
| `queen_streams.queries` | One row per registered query: `name`, `source_queue`, `sink_queue`, `config_hash`. |
| `queen_streams.state` | `(query_id, partition_id, key) -> value` JSONB, with `updated_at`. Cascades on query delete. |

**State is reclaimed only by dropping the query or re-registering with `reset: true`**; retention never touches it. Closed windows delete their own rows, so bounded key cardinality reaches a steady state and unbounded cardinality grows until you intervene ([watching it](/selfhost/retention)). **The schema is granted to `PUBLIC`**: database access is stream access ([details](/selfhost/postgres)).

Read state over HTTP when debugging:

```http
POST /streams/v1/state/get
Content-Type: application/json

{"query_id": "…", "partition_id": "…", "key_prefix": "tumb:60"}
```

Rows are `key`, `value`, `updated_at`; accumulators live under a composite key of operator tag, window key and user key, joined by a unit-separator byte.

## What is guaranteed, and what is not

| Property | Mechanism |
| --- | --- |
| The cycle is atomic | State, sink pushes and the source ack commit together or not at all. A crash mid-cycle leaves the cursor in place, the lease expires, the batch redelivers. |
| A lost response cannot double-consume or double-emit | The sink push happens before the ack inside the transaction, and the ack aborts on an invalid or expired lease, so a retried cycle finds the lease gone and its sink write rolls back with it. |
| `foreach` is at-least-once | The source is acked only after your function resolves, so a crash during it redelivers and the side effect may already have happened. An effect that must not repeat belongs on a sink queue with a dedicated consumer. |
| A cycle nack spends no pop-path retry budget | An `ack.ok = false` cycle releases the lease and leaves the cursor untouched for a full redelivery; retry policy is the runtime's business, not the broker's. |
| The body is the signal, not the status code | `cycle` answers 200 even for a failed cycle; the SDKs raise on `success: false`. A 500 from it is an infrastructure error, safe to retry because the call is one transaction. `state/get` answers 400 when the procedure reports failure and 500 on an embedded error. Full contract: [errors](/use/errors). |

## Operational notes

- The three `/streams/v1/*` routes are **not tenant-scoped**, so a proxy deployment plan-gates streams on a dedicated cell. Route classes are in the [reference](/reference).
- `run` requires an explicit broker URL: the runtime builds its own HTTP client for the `/streams/v1/*` calls, with its own retry policy ([errors](/use/errors)).
- Sink emits and source acks land in per-queue and broker-wide metrics, on the same throughput charts as any producer and consumer.
