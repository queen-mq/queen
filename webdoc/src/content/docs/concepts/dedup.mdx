Every message carries a `transactionId`. A second push of the same id to the same partition,
inside the queue's dedup window, writes nothing and answers with the original message. Use it to
make a retried push harmless, and use `once` to make a whole step harmless.

## `transactionId` is the idempotency key

<Render file="snippets/js-push-dedup" />

Over HTTP the retry answers HTTP 201 with `status: "duplicate"`, the original `message_id` and
the original `offset`. Nothing is appended.

- **Exact, not probabilistic.** The leader checks the partition's index of ids when it plans the
  push, in the same step that assigns offsets.
- **Scoped to one partition.** The same id in another partition, or another queue, is a new
  message.
- **The window** is the queue's `dedupWindowSeconds`: 3,600 s by default, `0` turns dedup off.
- **Across failover.** The index is replicated state, so a new leader answers a retry the same
  way, with the original offset. This is [Jepsen-tested](/concepts/guarantees/).
- **Within one request,** a repeated queue, partition and id is stored once; the repeats answer
  `duplicate`.
- **Without an id,** the broker uses the message id, which is new on every push, so nothing is
  deduplicated. The JS SDK mints a UUIDv7 when you pass none, with the same effect.

## Choose deterministic ids

Derive the id from the work, never from the attempt: an upstream event id, a primary key plus a
version (`order-9137-v3`), or the input's id in a pipeline (`invoice-${message.transactionId}`).
**A fresh UUID per attempt deduplicates nothing.**

## A duplicate inside a transaction rolls back everything

When a push inside a [transaction](/concepts/transactions/) is a duplicate, the whole transaction
rolls back with `reason: "duplicate"`: the ack, the KV writes and the timers are not written
either. That is what makes a retried transaction safe: if the first attempt committed, a retry
with the same push ids finds them and writes nothing.

## `once`: a step at most once

A redelivered event carries the same `transactionId` but runs your step again. `once` writes a
marker in the step's transaction and refuses the whole transaction when the marker exists:

```js
const res = await queen.transaction()
  .ack(message, 'completed', { consumerGroup: 'mailer' })
  .queue('emails').push([{ data: mail }])
  .once('welcome', userId, { ttl: '7d' })
  .commit()
if (res.success === false) await queen.ack(message, true, { group: 'mailer' })  // already done
```

`once(ns, key, opts)` is a KV `putIfAbsent` with `required: true`. A lost gate answers HTTP 200
with `reason: "kv_precondition"`, and the JS SDK returns it from `commit()`. The ack rolled back
too, which is why the example acks on its own. Outside a transaction,
`queen.kv.once(ns, key, { ttl })` returns `{ won }`.

A transaction checks its pushes before its KV ops. If it also pushes with a deterministic id, a
repeat rolls back with `duplicate` first, and the JS SDK throws that one. Handle both, or let
`once` be the only gate, as above.

| You want | Use |
|---|---|
| a retried push not to store twice | a deterministic `transactionId` |
| a redelivered event not to run its step twice | `once` in the step's transaction |
| an external call not to run twice | an idempotency key the other system honours |

## Limits

- **The window is bounded.** Outside `dedupWindowSeconds`, the same id is a new message.
- **Dedup is per partition.** Pick the same partition for every retry of the same message.
- **A `once` marker lives until its TTL.** After it, a redelivery runs the step again: make the
  TTL longer than any redelivery can arrive.
- **Dedup does not cover a side effect outside Queen.** See [exactly-once](/guides/exactly-once/).
- **`transactionId` is at most 65,535 bytes.**
