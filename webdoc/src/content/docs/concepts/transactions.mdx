A transaction is one call that writes one step: it acks what the worker took, pushes the next
events, writes KV state and schedules or cancels timers, as a single entry of the replicated log.
Either every part applies or none does. Use it whenever a worker's output must not come apart
from its input.

## One call, one entry

```js
await queen.queue('orders').group('billing').autoAck(false).each()
  .consume(async (message) => {
    const id = String(message.data.orderId)
    const res = await queen.transaction()
      .ack(message, 'completed', { consumerGroup: 'billing' })              // progress
      .kv.put('orders', id, { status: 'paid' }, { ttl: '30d' })              // state
      .queue('receipts').partition(message.data.customerId)
        .push([{ data: { orderId: id } }])                                    // events
      .timer('reminders').key(id).delay('24h').payload({ orderId: id }).schedule() // time
      .once('payments', message.data.paymentId, { ttl: '30d' })              // identity
      .commit()
    if (res.success === false) await queen.ack(message, true, { group: 'billing' })
  })
```

The same call over HTTP is `POST /api/v1/transaction` with `operations` (acks and pushes) and
the top-level arrays `kv` and `timers`; [the model](/concepts/) shows a full body and
[the reference](/reference/transaction/) every field. A commit answers HTTP 200 with
`success: true` and one result per operation, KV op and timer op; a rollback answers HTTP 200
with `success: false`, a `reason` and an empty `results`.

## What can go in

| Part | Where | What it can hold |
|---|---|---|
| Acks | `operations`, `type: "ack"` | Messages leased from any partitions, queues and consumer groups of the tenant. Each names `transactionId`, `partitionId`, `consumerGroup` (default `__QUEUE_MODE__`) and its `leaseId`. |
| Pushes | `operations`, `type: "push"` | Messages to any queues and partitions. A queue or partition that does not exist is created, as by a push. |
| KV | `kv` | `put`, `putIfAbsent`, `delete`, `incr`, `get`, `getMany`. No `getPrefix`. See [KV](/concepts/kv/). |
| Timers | `timers` | `schedule` (an upsert) and `cancel`. See [timers](/concepts/timers/). |

Name the consumer group on every ack (`{ consumerGroup }` in the JS SDK): without it the ack
goes to `__QUEUE_MODE__`, not to the group that popped the message. The entry is crash-atomic
across every queue log it touches: after a crash, recovery replays it only when every copy is
present, so a transaction is never partly visible.

## The lease is the fence

When an ack carries the `leaseId` of the pop that delivered the message, the lease fences the
whole call. **If that lease expired or another worker holds the partition now, the ack is refused
and the whole transaction rolls back, KV write and timer included** (`reason: "rejected_ack"`).
A compare-and-swap cannot give you this: an `expect` on a version that still matches succeeds
even from a worker that no longer owns the message.

The lease must travel with the ack. Over HTTP, put `leaseId` on each ack operation. An ack
without its own `leaseId` takes the lease in `requiredLeases` only when the call names exactly
one lease; otherwise it is not lease-checked and still moves the cursor. The JS SDK sends each
message's `leaseId` in `requiredLeases`, so its acks are fenced when they come from one pop.

## `once`: the gate

`.once(ns, key, { ttl })` is a `putIfAbsent` with `required: true`. When the marker already
exists, the transaction rolls back and answers `success: false`,
`reason: "kv_precondition"`, `kvReason: "exists"` and the `failedIndex` of the gate. The JS SDK
returns that verdict from `commit()` instead of throwing, because a second event for the same key
(a payment provider retrying its webhook, say) is the expected case, not an error. Key the gate on
the business fact (`paymentId`), not on the message: a message that committed is already acked.
The ack rolled back with the rest, so ack the message on its own, as the example above does, or
it comes back.

## Why a transaction rolls back

| `reason` | Cause | JS `commit()` |
|---|---|---|
| `kv_precondition` | A KV op with `required: true` lost its precondition (`once` found its marker, an `expect` missed). | returns the verdict |
| `duplicate` | A pushed `transactionId` is already in its partition's dedup window. | throws, `error.reason` |
| `rejected_ack` | An ack's lease expired or moved, or the message was already acked. | throws |
| `reserved` | Another transaction or a checkpoint holds that cursor at this moment. Retry. | throws |
| `bad_request` | A malformed operation. Some shapes answer HTTP 400 instead. | throws |

These are the common reasons; [errors](/reference/errors/) lists every code. A rolled-back
transaction writes nothing and leaves nothing visible. A 503 (`outcome_unknown`,
`timeout`, `no_leader`) is not a rollback: the outcome is not known yet, and the answer carries
`Retry-After`.

## One tenant, one raft group

A transaction carries the tenant of its request, and each tenant lives in exactly one raft group
(`QUEEN_RAFT_GROUPS`, placed by a hash of the tenant or by `QUEEN_TENANT_GROUPS`). So every
transaction is one entry in one log: no coordinator, no two-phase commit. It cannot span tenants.

## Where exactly-once stops

- **A lost response.** Send the same call again. If the first one committed, a retry that
  carries the same acks or the same push `transactionId`s is refused (`rejected_ack` or
  `duplicate`) and writes nothing. If it did not commit, the retry commits, or, once the lease
  has expired, the message is redelivered and the next attempt commits. Deterministic push
  `transactionId`s make both cases safe: see [dedup](/concepts/dedup/).
- **External calls.** An HTTP call to a payment provider is outside the commit. Give the provider
  an idempotency key derived from the message. See [exactly-once](/guides/exactly-once/).

`transactionRollback`, `kvTransactionGateBlocksTheSecondDelivery` and `timerRidesTheTransaction`
in `clients/client-js/test-v2/` run these behaviours against a live broker.

## Limits

- **Single call, not interactive.** There is no BEGIN, read, decide, COMMIT. A `get` inside a
  transaction is answered after the commit, so it cannot be a condition: use `expect` with
  `required: true`.
- **One tenant per transaction.**
- **KV inside a transaction:** at most 64 ops and 256 keys, one write per key, no `getPrefix`.
- **One timer op per queue and `timerKey`** per call.
- **Size:** one body is at most 64 MiB (`QUEEN_MAX_BODY_BYTES`), one planned entry at most 96 MiB
  (`QUEEN_RAFT_ENTRY_MAX_BYTES`).
- **No published run measures transaction throughput.** The [benchmarks](/benchmarks/) measure
  push, pop and ack.
