A stream reads a queue and writes its results to another. The partition is the key, so each customer gets its own windows. Streams are in the JavaScript, Python, Go and Rust clients; PHP and C++ have none, and a stream reads any queue, whoever pushes to it. Like a new group it starts at the tail: push a few more orders and a result arrives a minute later.

<SdkCode id="stream" />

A stream reads its queue as a consumer group (`streams.<queryId>`) and keeps its state, the open windows, in the broker. Each time it closes windows, it writes the new state, pushes the results and acks the messages they came from in one transaction.

<Fig id="stream-cycle" caption="One cycle of a stream is one transaction." />

<Why>counting, summing and grouping events over time is a job most systems hand to a separate stream processor, with its own cluster and its own idea of what was processed. Here it runs in a normal process, its state lives next to the data, and one commit keeps the results and the inputs in step: a crash can neither lose a result nor count an event twice.</Why>

## Four kinds of window

| Window | Example | What it is, and when to use it |
| --- | --- | --- |
| `windowTumbling` | `seconds: 60` | Fixed windows, one after the other. Revenue per minute. |
| `windowSliding` | `size: 600, slide: 60` | Overlapping windows: the last 10 minutes, every minute. Each event counts in several windows, so it keeps more state. |
| `windowSession` | `gap: 1800` | One window per burst of activity, closed after a quiet gap. A visit, a conversation. |
| `windowCron` | `every: 'hour'` | Windows aligned to the clock (`second`, `minute`, `hour`, `day`, `week`). Hourly and daily reports. |

## When it happened, or when it arrived

By default a window holds the events that arrived during it. Give `eventTime` a function that reads the time from the message, and windows hold the events that happened during it instead. It gets the whole message, so the event's own fields are under `data`; the aggregate's functions get the event itself. Go and Rust want the time as epoch milliseconds.

<SdkCode id="stream-hourly" />

`allowedLateness` says how far behind the newest event an event may be and still count. A later one is dropped, or with `onLate: 'include'` it opens a fresh window, so the window is sent a second time with only the late events. `gracePeriod` keeps a window open a little after its end, and `idleFlushMs` (5 seconds) closes the windows of partitions that went quiet. `subscriptionMode: 'all'` makes a new stream read what the queue already holds.

<Why>events arrive late and out of order: a phone that was offline, a batch upload, a retry. An hourly report should count a sale in the hour it happened, not in the hour its message got through.</Why>

## Shaping the data

- `map(fn)` changes each message, `filter(fn)` drops the ones you do not want, and `flatMap(fn)` turns one message into several values.
- `aggregate({ ... })` folds a window into named numbers. The name decides the fold: `count`, `sum`, `min`, `max` and `avg`; any other name adds up. `reduce(fn, initial)` is the general form, for anything else.
- `keyBy(fn)` groups by something other than the partition (per page instead of per user). Several workers can then write the same key, which slows them down; when that matters, push to a queue partitioned by the new key first, and stream from it.

<Why>most stream jobs are the same few steps: drop noise, reshape, group, fold. Having them as building blocks keeps a stream to a few readable lines.</Why>

## Two ways to end a stream

`.to(queue)` pushes each result to another queue, in the same commit as the state and the acks, into the partition of the same name unless you pass `{ partition }`. `.foreach(fn)` calls your function for each result, and acks only after it returns: a crash in the middle calls it again.

<Why>a result that stays inside Queen can be exactly once. A call to the outside world (an email, an API) cannot, so `foreach` makes it at least once and says so. For an external effect that must happen once, send the result to a queue and let a worker do it with an idempotency key.</Why>

## Rate limits with a gate

`gate(fn)` decides, message by message, whether a message may go on now, with state kept per partition. Two ready-made gates are included: `tokenBucketGate` and `slidingWindowGate`. Rust has no ready-made gates yet, so its code writes the same token bucket as a function, with the same state.

<SdkCode id="stream-gate" />

A message the gate refuses stops its partition there: it and the ones after it are delivered again, in order, when the lease runs out.

<Why>an SMS provider, a partner API or a rate-limited email service accepts only so many calls a second. A gate per customer keeps you inside those limits without losing order and without a queue of your own for the waiting messages.</Why>

## Running a stream

`run()` takes the stream's `queryId`, its identity: its state is stored under it, so a process restarted with the same id carries on with the same windows, and several processes with the same id share the partitions between them. `batchSize` (200) and `maxPartitions` (4) size each cycle, and `stop()` on the handle `run()` returns stops it cleanly.

<Why>a stream is a long-running worker like any other: it has to survive restarts, scale out, and stop during a deploy without losing its place.</Why>

A window on a partition that goes quiet still closes on time. The client keeps the time each open window ends, and at that time leases the quiet partition from the broker (`POST /streams/v1/claim`, broker 2.7) and closes the window under that lease, on the broker's clock. A partition someone else holds, or one with messages still waiting, is not leased: the window then closes in that cycle. So a window closes once, even with several processes on one `queryId`, and a process that starts asks the broker which partitions hold state (`POST /streams/v1/state/partitions`), so windows left open by a restart or a scale-down close too. On an older broker a client closes only the windows of partitions its own process read in the last five minutes. Event-time windows close on their watermark, as before.

<Why>a session per visit or per trace ends with silence, not with a message. If closing it waited for the next message, a deploy or a crash would leave it open for good, and its result would never be sent.</Why>
