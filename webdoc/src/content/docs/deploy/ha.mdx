A cluster is three or five nodes running the same binary, each with a data directory of its own.
One of them leads: it orders every write into a single replicated log, and every node applies that
log, entry by entry and in the same order, to its own full copy of the state. There is no shared
storage and no external coordinator. The consensus protocol is Raft, from the `openraft` crate,
and its log is the broker's own queue logs rather than a second write-ahead log.

What that buys, precisely:

- **A node dying, a rolling restart, one node's network.** The remaining majority keeps serving.
  Three voters tolerate one failure and five tolerate two. Voter counts are odd on purpose: four
  voters need three for a majority and so tolerate one failure, the same as three.
- **No acknowledged write lost to a single failure.** An entry is written to the queue logs and
  fsynced once on each node before that node reports it; the leader counts it committed when a
  majority has reported it; the client is answered only after that.
- **Losing a majority stops writes.** Two of three voters gone means no leader can be elected,
  and every node answers `503` until a majority is back. That is the price of never having two
  leaders; the way out when the majority is gone for good is
  [below](#when-a-majority-is-gone-for-good).

The one deliberate exception is the [ephemeral](/use/ephemeral) queue class, whose contents live in
one node's memory and are not replicated, by contract.

## Three nodes

Every node takes the environment of a single node plus four variables:

```bash
QUEEN_RAFT_DIR=/var/lib/queen/raft
QUEEN_RAFT_REPLICATOR=openraft
QUEEN_RAFT_NODE_ID=1          # 2 and 3 on the other two
QUEEN_RAFT_PEERS=1=queen-1:7400/queen-1:6632,2=queen-2:7400/queen-2:6632,3=queen-3:7400/queen-3:6632
QUEEN_RAFT_TOKEN=...          # openssl rand -hex 32, the same on every node
```

- `QUEEN_RAFT_REPLICATOR=openraft` selects the replicator that talks to peers. A single node runs
  the local replicator by default, and the broker refuses a peer list without this setting.
- `QUEEN_RAFT_NODE_ID` is a number from 1, distinct per node. On Kubernetes it can be `ordinal`,
  which reads the trailing number of `HOSTNAME` and adds one, so pod `queen-0` is node 1.
- `QUEEN_RAFT_PEERS` lists every voter of the initial membership, this node included, as
  `id=raft_address/http_address`. The raft address is where peers send votes and log entries; the
  HTTP address is where a follower forwards a client's write. The node binds its raft listener on
  `0.0.0.0` at the port of its own raft address, unless `QUEEN_RAFT_LISTEN` names another address.
- `QUEEN_RAFT_TOKEN` is the shared secret every raft request carries, in the
  `x-queen-raft-token` header. Leave it unset and anything that can reach the raft port can vote
  and append. Set it, and keep the port on a private network anyway
  ([Security](/deploy/security#the-raft-port)).

Start all three. They find each other, elect a leader and serve. A complete, runnable version is
[Docker Compose](/deploy/compose); the StatefulSet version is [Kubernetes](/deploy/kubernetes).

One `/health` answers `"role":"leader"` and the others `"role":"follower"`. Point clients at all of
them behind a load balancer or a Service, with no affinity: a write that reaches a follower is
forwarded to the leader, and a read waits until the node that took it has applied everything the
cluster had committed when the read began, so a client never reads behind a write it was already
answered for.

## How long a failover takes

The leader sends a heartbeat every 100 ms, and a follower that hears nothing for its election
timeout, a random value between 1 and 2 s, stands for election. Both are settings,
`QUEEN_RAFT_HEARTBEAT_MS` and `QUEEN_RAFT_ELECTION_MS` (the minimum; the maximum is twice it), and
the defaults are deliberately not tighter: a leader whose disk stalls on one slow fsync should not
be deposed for it.

A write in flight when the leader dies is not answered by the dead leader. The client sees an error
or a timeout and retries; a retry of a push with the same `transactionId`, inside the queue's
deduplication window (3600 s unless configured otherwise), finds the original if it was committed
and writes nothing twice.

A planned stop costs less than a crash. On SIGTERM a node that leads first hands leadership to a
caught-up voter and only then drains its listener as a follower, so a rolling restart costs one
leadership transfer rather than an election timeout. Restart one node at a time and wait for it to
answer `/health` with `200` before the next.

## The membership is in the log

The peer list is read at the very first boot, to initialise the cluster. From then on the
membership is an entry in the replicated log, and it wins over whatever `QUEEN_RAFT_PEERS` says: the
variable only tells a node its own listen address. Changing a peer's address, or adding a fifth
line to the variable, changes nothing on a running cluster.

Membership changes go through the operator routes. Every node answers them and a follower forwards
the change to the leader, which refuses any change that would leave the cluster without a quorum.
They are under `/api/v1/system/`, so with authentication on they need the admin level, and a
request scoped to a tenant is refused.

| Route | Body | Does |
| --- | --- | --- |
| `GET /api/v1/system/raft/membership` | none | The current voters and learners |
| `POST /api/v1/system/raft/membership/learners` | `{"id", "raft", "http"}` | Adds a node as a learner: it receives the log and does not vote |
| `POST /api/v1/system/raft/membership/promote` | `{"ids": [...]}` | Makes caught-up learners voters |
| `PUT /api/v1/system/raft/membership/voters` | `{"voters": [...]}` | Sets the voter set |
| `DELETE /api/v1/system/raft/membership/members/:id` | none | Removes a member |

`?timeoutMs=` bounds a change, 30 s by default; past it the answer is `504` and the change may still
complete. A refused change answers `409` with a stable `code`, for example `no_quorum`,
`last_voter` or `learner_behind`. The read-only views `GET /api/v1/raft/status`,
`GET /api/v1/raft/members` and `GET /api/v1/raft/liveness` say what each node sees.

## Replacing a node

A node that lost its disk comes back as a new, empty member, and a removed voter comes back under
its old id only with its data directory wiped. The cycle, from any node that is still up:

<Steps>

1. **Remove the lost member,** if the membership still lists it.

   ```bash
   curl -s -X DELETE http://queen-1:6632/api/v1/system/raft/membership/members/3
   ```

2. **Start the replacement empty, with `QUEEN_RAFT_JOIN=true`.** A fresh node with that setting
   never initialises a cluster of its own and answers `503` until the leader adds it. Without the
   setting, a fresh node still asks its peers first and joins when one of them already holds
   cluster state. Its `QUEEN_RAFT_PEERS` must still list its own entry.

3. **Add it as a learner.** It receives the log, or a snapshot, and does not vote.

   ```bash
   curl -s -X POST http://queen-1:6632/api/v1/system/raft/membership/learners \
     -H 'Content-Type: application/json' -d '{"id":3,"raft":"queen-3:7400","http":"queen-3:6632"}'
   ```

4. **Promote it once it has caught up.** Before that the promotion is refused with `409
   learner_behind`.

   ```bash
   curl -s -X POST http://queen-1:6632/api/v1/system/raft/membership/promote \
     -H 'Content-Type: application/json' -d '{"ids":[3]}'
   ```

</Steps>

A follower that was away for longer than the leader keeps the log for it (`QUEEN_RAFT_PURGE_HOLD_S`,
600 s by default) receives a snapshot instead of the missing entries. A node that has to load a
snapshot exits with code 75 and loads it on the next start, so leave the restart to its supervisor
and keep its volume.

## When a majority is gone for good

If a majority of the voters lost their disks and will never come back, Raft cannot elect a leader
on its own. `QUEEN_RAFT_FORCE_RECOVER=<this node's id>` on the one survivor makes it, at boot, the
only voter of its cluster: it commits everything its own log holds and serves alone, and new nodes
then join it as learners.

It is unsafe by design and should be the last resort. Whatever the lost members had committed and
the survivor had not is gone, and those writes were acknowledged to clients. The lost members must
never come back with their old data, because two of them could still form a majority of the old
voter set and elect a second leader: wipe them, or give their replacements new data directories.
The setting refuses to run unless it names the node it is set on.

## Several raft groups per process

One leader orders every write of a cluster, so one cluster's write rate is what one leader can
plan and one set of disks can sync. `QUEEN_RAFT_GROUPS`, default 1 and at most 64, runs several
independent raft groups in each process instead, each a whole state machine with its own log,
leader and data directory. A tenant lives in exactly one group, chosen by a stable hash of its name
or pinned with `QUEEN_TENANT_GROUPS=tenant=group,...` before it first writes. Group `g` uses the
raft port plus `g`, and prefers a different node as its leader, so with as many groups as nodes
every node leads one group. Every node must use the same value, and a group scales and fails over
on its own. It helps only when the load is spread over several tenants.
