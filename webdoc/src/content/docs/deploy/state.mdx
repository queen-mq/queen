[KV state](/use/kv) and [timers](/use/timers) are part of the engine. There is no environment variable
that turns them on, for the same reason there is none for push and for pop: every cell running this
binary serves both surfaces, on every route, from the first boot. This page is what the operator of
such a cell needs.

## There is no gate. There is a kill switch, and it is a different instrument

Two things are easy to confuse and are opposites. A **gate** is turned on to try something out: it is
read once at boot, it decides whether a surface exists at all, changing it is a rollout, and different
cells may legitimately answer differently. Queen has no gate for KV or timers, and the boot flags that
used to be one, `QUEEN_KV_ENABLED` and `QUEEN_TIMERS_ENABLED`, no longer exist. Setting them does
nothing.

A **kill switch** is turned off to stop something that is already running and is hurting. It is read on
every call, the surface exists either way, the flip takes effect now, and it is expected to be flipped
back. The [ephemeral switch](/reference/http/system#the-ephemeral-kill-switch) is the same class, and
both wear the same shape: an in-process atomic on the hot path, and an entry in the replicated log that
keeps the setting across restarts.

<Aside type="caution">
This changes how a release lands. There is no step where the binary is in production with the surfaces
dark: from the moment it is deployed, KV and timers are live on every cell, and the rollout question is
not "which cells have it on" but "is the cell's quota configuration right before the binary arrives".
Grants and limits are what stage a tenant onto the feature, and they are writes to the broker's state
rather than restarts.
</Aside>

## Three rungs, and each answers differently

A refused call is told the outermost reason, because that is the one the caller can act on.

| Rung | Set by | Answer |
| --- | --- | --- |
| 1. An operator paused it | `POST /api/v1/system/kv-timers` | **503** with `Retry-After` |
| 2. The tenant is granted it | `POST /api/v1/system/quota` with `"kind":"kv"` | **403** `feature_gated` |
| 3. The tenant is inside its quota | the same grant's limits, against the measurement | **403** `kv_quota_exceeded` or `timers_quota_exceeded` |

Nothing on this ladder answers `404`. A `404` from a KV or timer route means the path is wrong, not
that the surface is missing, and a client that treats it as "this cell does not offer the feature" is
reading a typo as a deployment mode.

The ladder guards the KV and timer routes. In 2.0 `POST /api/v1/transaction` does not consult it: the
`kv` and `timers` arrays of a transaction are applied whatever the switches, the grants and the quotas
say, so a tenant that must be stopped completely has to be stopped at the proxy.

<Aside type="caution">
Two surfaces sit outside rung 1 deliberately. A **timer cancel** is never blocked, and neither is a
**timer peek or list**. The fire never switches itself off, so a tenant that cannot cancel keeps
producing messages it cannot stop, and a peek that answered `503` would stop a caller finding out
whether a timer it can no longer cancel is still pending.
</Aside>

Reads and deletes are also never blocked by rung 3. A tenant that is over quota has to be able to get
back under it.

### The runtime switches

Three keys, independent, and an omitted field in the body is left alone: pausing new timers at three in
the morning must not also stop delivering the ones already promised.

```bash
curl -s http://localhost:6632/api/v1/system/kv-timers

curl -s -X POST http://localhost:6632/api/v1/system/kv-timers \
  -H 'Content-Type: application/json' \
  -d '{"timersSchedule":false}'
```

| Key | Field | What pausing it does |
| --- | --- | --- |
| `kv_enabled` | `kv` | Every KV route answers `503`, and nothing already stored is affected |
| `timers_schedule_enabled` | `timersSchedule` | No new timers are accepted on the timer routes. Existing ones still fire, and cancels are never blocked |
| `timers_fire_enabled` | `timersFire` | Stored and reported, and not read by the fire in 2.0: timers keep firing |

An absent setting means **on**. That is the difference between a kill switch and a feature flag: the
other way round, a fresh cell would boot with the feature dead and nothing to explain why.

The flip is written through the replicated log, so every node stores it and it survives a restart. It
takes effect at once on the node that served the request; the other nodes of a cluster apply the stored
value when they restart. Until that changes, send the same request to every node.

<Aside type="danger">
In 2.0 there is no runtime switch that holds the timer fire. The fire runs on the leader, on its own
cadence (`QUEEN_RAFT_TIMER_TICK_MS`, 50 ms), and does not read `timersFire`: a timer that comes due
still fires. The one way to stop it is `QUEEN_RAFT_TIMER_TICK_MS=0` on every node, which takes a
restart. Nothing is lost while it is off (`deliverAt` is a floor), but promised messages are not
arriving.
</Aside>

## Grants and limits

With tenancy on (`QUEEN_TENANCY_HEADER=1`, or the embedded proxy in front), a tenant without a KV grant
is denied: `QUEEN_KV_REQUIRE_GRANT` derives from the tenancy flag, so a `403 feature_gated` means the
grant is missing rather than the feature being broken. With tenancy off, the surfaces work without
configuring anything.

A grant is one call per tenant, and its limits are part of it:

```bash
curl -s -X POST http://localhost:6632/api/v1/system/quota \
  -H 'Content-Type: application/json' \
  -d '{"tenant":"<broker tenant id>","kind":"kv","enabled":true,"maxRows":100000,"maxBytes":104857600,"maxTimers":10000}'
```

The route is under `/api/v1/system/`, so it takes the admin level with authentication on, and the proxy
never forwards it for a tenant. `enabled: false` and an absent grant are different answers: the first is
a tenant somebody restricted, the second a tenant nobody authorised.

## The limits every call meets at the edge

`POST /api/v1/kv` is the endpoint whose call rate is decided by **your customer's end users** rather
than by message volume. Every other route has a natural limiter upstream of it; here the limiter is
somebody else's web traffic. So every KV call is checked before it reaches the state machine:

- **A per-tenant token bucket in the broker**, answering `429` with `Retry-After`. In the broker and not
  only in the proxy, because a self-hosted cell without a proxy is a real deployment and a defence that
  exists only in the proxy is not a defence of the product. Defaults are 200 reads a second with a burst
  of 400 and 100 writes a second with a burst of 200 (`QUEEN_KV_READ_RATE`, `QUEEN_KV_READ_BURST`,
  `QUEEN_KV_WRITE_RATE`, `QUEEN_KV_WRITE_BURST`).
- **Ceilings on one call**: at most 256 operations (`QUEEN_KV_MAX_OPS_PER_CALL`), at most 1024 keys
  counted across them, a prefix read counting as its limit (`QUEEN_KV_MAX_KEYS_PER_CALL`), and at most
  65536 bytes per serialized value (`QUEEN_KV_MAX_VALUE_BYTES`), answered `413`.
- **The disk gate**, shared with every write: a KV write that adds a value is refused with `507` once
  the node's data directory is full past `QUEEN_RAFT_DISK_HIGH_PCT` ([Operations](/deploy/operations#the-disk-gate)).

KV writes that ride **inside** a push or an ack travel with that transaction, and the transaction is one
entry in the replicated log: the KV write and the messages commit together or not at all.

## What switching a surface off does

Stopping a surface is a runtime decision, it is safe, and it is not silent.

| What you switch off | What happens |
| --- | --- |
| `timersSchedule`, with timers pending | New timers are refused. The pending ones still fire and cancels still work, because nothing that was already promised is affected by refusing to promise more |
| `timersFire`, with timers pending | Nothing, in 2.0: the flag is stored and the fire does not read it |
| `kv`, with live keys | Every KV route answers `503`. The keys stay, and a transaction's `kv` array is still applied |

## Billing a shared cell

A timer fires from inside the broker and never crosses the proxy, so it is the one way in the product to
produce a message the gateway's meter cannot see. The only point where it can be billed is the promise:
the `schedule` operation. Today the proxy meters `POST /api/v1/timers` as a request and nothing more, so
the message a timer will deliver is not counted anywhere. Whoever owns the price list for a shared cell
should know that before timers are sold on it.
