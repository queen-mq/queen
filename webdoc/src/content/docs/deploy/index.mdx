A Queen deployment is one process per node and a directory on that node's disk. The broker is a
single Rust binary that serves HTTP on port 6632 and keeps its state in `QUEEN_RAFT_DIR`, default
`/var/lib/queen/raft`: the queue logs that hold the payloads, an embedded ordered store for
everything the broker looks up, and, in a cluster, the raft state. There is no external database,
no coordination service and no sidecar.

There are two shapes, and the difference is what a failure costs:

- **One node.** Every write is fsynced to the node's disk before it is answered, and a restart
  resumes from the directory. The node is the failure domain: while it is down nothing is served,
  and losing its disk loses the data.
- **A cluster of three or five voters.** One leader orders every write into a replicated log, a
  write is answered once a majority of the voters have it on disk, and every node applies the log
  to its own full copy of the state. Three voters keep serving through one failure, five through
  two. Any node serves any client: a write that reaches a follower is forwarded to the leader.

The rest ships inside the same binary and stays off until you switch it on:

- the proxy, `QUEEN_PROXY_EMBEDDED=true`: API keys, tenants, plan quotas, metering and human
  logins, with its own state in the broker's replicated key/value store
- the Kafka facade, `QUEEN_KAFKA_EMBEDDED=true`: Kafka clients connect to the broker directly

The dashboard is always on, served on the broker port, and `queenctl` travels in the image.

A complete single-node deployment, ready to verify:

```bash
docker run -d --name queen -p 6632:6632 -v queen-data:/var/lib/queen/raft ghcr.io/queen-mq/queen:latest
curl -s http://localhost:6632/health
```

`/health` answers `200` with `"status":"healthy"` and `"engine":"raft"` once the node knows a
leader, which on a single node is at once. Its `raft` object carries the node's `role` (`leader`,
`follower`, `candidate` or `learner`), the `term` and the `applied` and `commit` indexes. Without a
leader it answers `503` with `"status":"settling"`, which is an election in progress or a cluster
that has lost its majority, and never a reason to restart the process.

The volume is not optional in anything you keep. Without it the data directory lives in the
container's own filesystem and goes with the container.

## The variables of the first day

`QUEEN_RAFT_DIR` is the data directory, and the one thing to mount. `PORT` moves the HTTP listener
off 6632.

`QUEEN_RAFT_DISK_HIGH_PCT`, default 85, is the disk gate: once the filesystem holding the data
directory is that full, writes are refused with `507` until it is back under
`QUEEN_RAFT_DISK_LOW_PCT`, default 80. Size the volume for the retention you configure, since
nothing is deleted until [retention](/deploy/operations#retention) deletes it.

A cluster adds four variables per node, `QUEEN_RAFT_REPLICATOR=openraft`, `QUEEN_RAFT_NODE_ID`,
`QUEEN_RAFT_PEERS` and `QUEEN_RAFT_TOKEN`, which [High availability](/deploy/ha) walks through.

Booleans are strict everywhere: `true/false`, `1/0`, `yes/no`, `on/off`, case-insensitive. Anything
else is a fatal boot error rather than a guess, and every boot prints the configuration the broker
actually resolved, secrets masked.

`JWT_ENABLED` is `false` by default, which means every route is served to every caller,
`/api/v1/system/*` included. The broker port has no TLS of its own. Turn authentication on, or put
the embedded proxy in front, before the port reaches a routable address
([Security](/deploy/security)).

Every variable the broker reads, with the default the code applies, is in
[the configuration reference](/reference/config).
