Every other page in this section deploys one part. This one is the whole thing in a single file,
against the published image, so there is something to run before there is something to decide:
three nodes forming one cluster, each running the proxy in the same process.

<Aside type="caution">
This is a complete topology, not a hardened deployment. There is no TLS, the broker port is open to
anyone who can reach it, and all three nodes share one machine, so it survives a process dying and
not the machine. What to change before it faces anything real is in [Security](/deploy/security).
</Aside>

## Four secrets, first

They have to exist before the nodes start, because all four are node environment. Generate them
once into `.env` beside the Compose file:

```bash
cat > .env <<EOF
RAFT_TOKEN=$(openssl rand -hex 32)
SESSION_SECRET=$(openssl rand -hex 32)
CP_TOKEN=$(openssl rand -hex 32)
BOOTSTRAP_KEY=qk_live_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')
EOF
```

`RAFT_TOKEN` authenticates the raft traffic between the nodes and has to be byte-identical on all
three. `SESSION_SECRET` signs the proxy's human sessions, on every node, so changing it logs every
human out. `CP_TOKEN` guards the proxy's control plane and its metrics. `BOOTSTRAP_KEY` becomes the
first API key: the proxy treats a bearer token as an API key only when it starts with `qk_`.

## The file

```yaml title="docker-compose.yml"
x-queen-env: &queen-env
  QUEEN_RAFT_DIR: /var/lib/queen/raft
  QUEEN_RAFT_REPLICATOR: openraft
  QUEEN_RAFT_PEERS: "1=queen-1:7400/queen-1:6632,2=queen-2:7400/queen-2:6632,3=queen-3:7400/queen-3:6632"
  QUEEN_RAFT_TOKEN: ${RAFT_TOKEN:?set RAFT_TOKEN}
  QUEEN_PROXY_EMBEDDED: "true"
  QUEEN_PROXY_PORT: "6711"
  QUEEN_PROXY_JWT_SECRET: ${SESSION_SECRET:?set SESSION_SECRET}
  QUEEN_PROXY_CP_TOKEN: ${CP_TOKEN:?set CP_TOKEN}
  QUEEN_PROXY_SPOOL_DIR: /var/lib/queen/raft/proxy-spool
  QUEEN_PROXY_BOOTSTRAP_TENANT: acme
  QUEEN_PROXY_BOOTSTRAP_EMAIL: ops@acme.example
  QUEEN_PROXY_BOOTSTRAP_API_KEY: ${BOOTSTRAP_KEY:?set BOOTSTRAP_KEY}

services:
  queen-1:
    image: ghcr.io/queen-mq/queen:latest
    restart: on-failure
    environment:
      <<: *queen-env
      QUEEN_RAFT_NODE_ID: "1"
    volumes: ["data-1:/var/lib/queen/raft"]
    ports: ["6632:6632", "6711:6711"]

  queen-2:
    image: ghcr.io/queen-mq/queen:latest
    restart: on-failure
    environment:
      <<: *queen-env
      QUEEN_RAFT_NODE_ID: "2"
    volumes: ["data-2:/var/lib/queen/raft"]
    ports: ["6642:6632", "6721:6711"]

  queen-3:
    image: ghcr.io/queen-mq/queen:latest
    restart: on-failure
    environment:
      <<: *queen-env
      QUEEN_RAFT_NODE_ID: "3"
    volumes: ["data-3:/var/lib/queen/raft"]
    ports: ["6652:6632", "6731:6711"]

volumes:
  data-1:
  data-2:
  data-3:
```

Four things in there are load-bearing. Each node has a distinct `QUEEN_RAFT_NODE_ID` and its
**own** data volume, because each one keeps a full copy of the state and a shared directory is
corruption. `QUEEN_RAFT_PEERS` is the same string on all three and names every node, itself
included. `QUEEN_PROXY_PORT` gives the proxy a port of its own, which leaves 6632 as the broker's
internal port: no key needed there, so it belongs to trusted clients, probes and scrapers only. And
`${VAR:?}` fails the `up` with a readable message instead of starting a node with an empty secret.

```bash
docker compose up -d
```

The three nodes find each other and elect a leader within a few seconds:

```bash
curl -s http://localhost:6632/health; echo
curl -s http://localhost:6642/health; echo
curl -s http://localhost:6652/health; echo
```

Each answers `"status":"healthy"` with `"engine":"raft"`; one reports `"role":"leader"` and the
other two `"role":"follower"`. A node that has not seen a leader yet answers `503` with
`"status":"settling"`: ask again.

## The bootstrap tenant

`QUEEN_PROXY_BOOTSTRAP_TENANT` did at the first boot what used to take a database session: it
created the tenant `acme`, a cluster with the same slug on the `dev` plan, an admin user for
`QUEEN_PROXY_BOOTSTRAP_EMAIL`, and an API key whose plaintext is `BOOTSTRAP_KEY`, with all four
scopes. Every node runs the same bootstrap, and it is idempotent, so restarts and the other two
nodes change nothing. The proxy's state lives in the broker's replicated key/value store, so all
three nodes see the same tenants and keys.

More tenants, clusters and keys go through the control plane on the same port, guarded by
`CP_TOKEN`; [Multi-tenant](/deploy/multi-tenant) is the long version.

## Through the front door

Two things get a request routed: the key as a bearer token, and a `Host` whose **first DNS label**
is the cluster slug. Locally that host is a header rather than a name that resolves.

```bash
set -a; . ./.env; set +a

curl -s -X POST http://localhost:6711/api/v1/push \
  -H "Host: acme.local.test" -H "Authorization: Bearer $BOOTSTRAP_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"queue":"orders","partition":"customer-42","payload":{"hello":"world"}}]}'
```

Pop it through another node's front door, which proves both the replication and the forwarding:

```bash
curl -s "http://localhost:6721/api/v1/pop/queue/orders?batch=1&wait=true&consumerGroup=demo&subscriptionMode=all" \
  -H "Host: acme.local.test" -H "Authorization: Bearer $BOOTSTRAP_KEY"
```

Drop the key and the proxy answers `401`; send a `Host` whose first label names no cluster and it
answers `421`.

The proxy hands each cluster its own broker tenant, so the queue `orders` pushed through 6711 is not
the queue `orders` a client sees on 6632, which serves the broker's default tenant. That separation
is the point of a multi-tenant front door. A single-tenant deployment that wants both ports to
see the same queues sets `QUEEN_PROXY_TENANT_HEADER=false`, which makes the proxy stop setting a
tenant of its own ([Proxy](/deploy/proxy)).

## What this stack does and does not survive

Stop any one node, the leader included, and the other two elect a leader among themselves and keep
serving on their own ports:

```bash
docker compose stop queen-1
curl -s -X POST http://localhost:6721/api/v1/push \
  -H "Host: acme.local.test" -H "Authorization: Bearer $BOOTSTRAP_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"queue":"orders","partition":"customer-42","payload":{"n":2}}]}'
docker compose start queen-1
```

The restarted node catches up from the others. Stop two, and the one left answers `503` until a
second one is back: two of three is the majority, and without it no write is taken. Nothing here
spreads load across the three: a client dials one port. Put a load balancer, or a Kubernetes
Service, in front of the three front doors for that ([Kubernetes](/deploy/kubernetes)).

What it does not survive is the machine, because all three volumes are on it. That is the whole
reason a real cluster puts each node on its own host: [High availability](/deploy/ha).

## Clean up

```bash
docker compose down -v
```
