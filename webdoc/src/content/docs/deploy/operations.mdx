Every node keeps its whole state in its data directory, and the cluster keeps it in step. What an
operator watches is whether a leader is known, how full the disk is, and whether the followers are
keeping up. Retention is off until you turn it on. A version change within 2.0 is a rolling restart.

## What to watch

`/health` is the first signal. `200` with `"status":"healthy"` means the node knows a leader and
can take writes; `503` with `"status":"settling"` means it does not, which is an election in
progress or a cluster that has lost its majority. Alert on it staying there, not on one answer, and
never restart a node for it ([the probes](/deploy/kubernetes#the-probes)).

The scrape target is `GET /metrics/prometheus`. The raft families are the ones specific to 2.0:

| Family | What it tells you |
| --- | --- |
| `queen_raft_storage_full` | The disk and store-map admission gate: whether writes are being refused |
| `queen_raft_index` | The node's raft and state-machine indexes |
| `queen_raft_inflight` | Entries committed or proposed but not yet applied |
| `queen_raft_log_storage` | Queue-log files and bytes on this node |
| `queen_raft_admit_waiting` | Commands waiting for admission room right now |

The endpoint sits outside broker authentication, and its per-queue series sum across tenants, so it
is an operator surface, never a tenant one. Behind the embedded proxy's port it answers only with
the control-plane token. The full family list is in [Prometheus](/reference/prometheus).

On a cluster, `GET /api/v1/system/raft/membership` answers, from any node, who leads, the term, and
for each member whether the leader hears from it (`live`) and how many log entries it trails
(`lag`). A member that stays behind is a disk or a network to look at before it is a second failure.

## The disk gate

Nothing is deleted until retention deletes it, so a node's disk fills at the rate the workload
writes. Once the filesystem holding the data directory is `QUEEN_RAFT_DISK_HIGH_PCT` full, default
85%, the node refuses every command that grows storage with `507` and a `storage_full` code, and
accepts them again once usage is under `QUEEN_RAFT_DISK_LOW_PCT`, default 80%. The same gate closes
at 85% of the embedded store's map and reopens under 80%. What grows storage is a push, a
transaction that pushes, writes a KV value or schedules a timer, and a trace; pops and acks keep
working, so consumers can drain while retention catches up. Size the volume for the retention you
configure, with the headroom the gap between logical deletion and reclaimed space needs (below).

## Retention

A queue keeps everything forever, and consuming deletes nothing. Turning retention on is one call:

```bash
curl -s -X POST http://localhost:6632/api/v1/configure \
  -H 'Content-Type: application/json' \
  -d '{"queue":"orders","options":{"retentionEnabled":true,"retentionSeconds":604800,"completedRetentionSeconds":86400}}'
```

`retentionSeconds` deletes on age alone, read or not. `completedRetentionSeconds` never passes the
slowest consumer group's cursor, so one abandoned group pins the history for every other.
`/configure` merges, so a later call that omits these keys leaves retention exactly as it is; the
two ways to turn it back off are both explicit: send `retentionEnabled: false`, or send the whole
configuration with `"mode": "replace"`, which is what `queenctl apply -f` does. A `null` value is
refused with `400` rather than read as "restore the default". See
[queue options](/reference/queue-options).

The leader plans retention every `RETENTION_INTERVAL` ms, default 5000, as ordinary entries of the
replicated log, so every node deletes the same messages. One pass is bounded by
`RETENTION_BATCH_SIZE` rows, default 1000, and visits a bounded window of each queue's partitions,
resuming where the last pass stopped, so a queue with very many partitions is swept over several
passes.

Deleting a message and getting its disk space back are two steps. The space comes back when a whole
queue-log file holds nothing live any more, and each node reclaims its own files. A message's
record is also kept at least as long as the queue's deduplication window and completed retention,
and never less than 900 s (`QUEEN_RAFT_TXN_WINDOW_MIN_S`), because the deduplication index needs
it. So disk usage trails deletion, and the disk gate is where that difference shows.

Two things retention never touches: dead letters, which leave one at a time through
`DELETE /api/v1/messages/:partitionId/:transactionId` or in bulk through `DELETE /api/v1/dlq`, and
streaming state. A partition with no messages left, no dead letters and no live lease, last written
more than `PARTITION_CLEANUP_DAYS` ago (30 by default), is removed, unless
`QUEEN_PARTITION_CLEANUP_ENABLED=false`. The loop step by step is in
[retention internals](/internals/retention).

## Replication is not a backup

Three voters hold three copies, and every one of them applies the same entries. That covers a lost
disk or a lost node. It does not cover a mistake: a queue deleted, a retention window set too short
or a bad replay is replicated to every voter like any other write. Queen 2.0 has no backup command.
The data directory of a stopped node is the whole of what it restarts from; anything beyond that,
such as snapshots of the volumes, is the storage layer's business, and the application-level
defence is the one it always was: consumers that can reprocess, and producers that can replay with
deterministic `transactionId`s.

## Upgrades

Restarts and replacements of the same version need no coordination. Restart one node at a time and
wait for it to answer `/health` with `200` before the next. On SIGTERM a leader first hands its
leadership to a caught-up voter, then drains its in-flight requests; a leased batch nobody acked
redelivers once its lease expires.

A version change within 2.0 is the same rolling restart, as long as the new build reads the data
directory the old one wrote. When it cannot, because the on-disk format changed or because you want
a different `QUEEN_QLOG_SHARDS` (fixed when a directory is created), the move is a fresh start:
stop every node, point all of them at new, empty directories, and start them together. Never start
one empty node into the running cluster for this: it would be sent the old data back. The old
directory stays untouched, so rolling back is the old image with the old directory. Messages in the
old directory do not carry over.

From 1.x, which stored everything in PostgreSQL, there is no in-place upgrade either: 2.0 does not
read a 1.x database.

<Steps>

1. **Start the 2.0 deployment** beside the old one.

2. **Re-apply your `/configure` options** on it: they lived in the old database.

3. **Move producers** to the new address.

4. **Let consumers drain the old deployment** to empty, then move them.

</Steps>

If you cannot drain, copy at the application level, reading the backlog through the old API and
pushing it with a deterministic `transactionId` per message so a retried copy loop cannot duplicate.

Watch `/health` and the disk, turn retention on before the disk decides for you, keep three voters
on three machines, and remember that three copies of a mistake are still a mistake.
