Three voters, a headless Service so they can find each other by name, a client Service carrying
the HTTP port, and a disruption budget. The manifest below is the deployment in full: apply it with
`-n queen`. Every value in it that is not obvious is explained underneath.

```bash
kubectl -n queen create secret generic queen-raft \
  --from-literal=QUEEN_RAFT_TOKEN="$(openssl rand -hex 32)"
```

`QUEEN_RAFT_TOKEN` is the secret every raft request between the pods carries, and it has to be the
same on all three. Without it, anything in the cluster that can reach port 7400 can vote and append.

```yaml

          image: ghcr.io/queen-mq/queen:latest
```

The peer names are short because the pods resolve them inside their own namespace. In another
namespace, or with a different StatefulSet name, the list changes accordingly: it is
`id=<pod>.<headless service>:<raft port>/<pod>.<headless service>:<http port>` for every pod, and
the same string on all of them.

## The probes

`/health` answers `503` with `"status":"settling"` while the node knows no leader, which is an
election or a cluster that has lost its majority. That makes it the readiness answer: a node with
no leader should leave the Service endpoints, since it cannot take a write. Wire it to the
liveness probe and an election, or a network partition that costs the majority, becomes a restart
loop on every pod at once, which is the one thing that cannot help.

Liveness and startup are a TCP connect on the HTTP port. The broker binds its listeners only after
the store and the replicator have opened, so an open port means the boot finished, and the startup
probe above allows 30 minutes for it: a node that replays a long tail of its log after a crash is
slow to open, not stuck.

Readiness does not mean caught up. A follower answers `200` as soon as it knows a leader, even while
it is still receiving the entries it missed. `minReadySeconds: 30` gives a rolling update some
catch-up time before it moves to the next pod. The disruption budget does not wait for that, so a
node drain can take a second voter while the first is still behind, and commits then stall until it
catches up.

## Why a StatefulSet

- Every pod needs a stable name in `QUEEN_RAFT_PEERS` and a stable volume for its data directory,
  and `QUEEN_RAFT_NODE_ID=ordinal` derives the node id from the pod name. That is what a
  StatefulSet behind a headless Service hands out.
- `podManagementPolicy: Parallel` and `publishNotReadyAddresses: true` go together. Without both,
  a full restart deadlocks: no pod is ready without a leader, and no leader can be elected until
  the peers' names resolve.

## The fields that are not obvious

- `replicas` is 3 or 5, and it is fixed at the first boot: the membership is stored in the log, so
  scaling the StatefulSet does not add a voter. Adding and removing voters on a running cluster
  goes through the membership API ([High availability](/deploy/ha#the-membership-is-in-the-log)).
  So do the release name, the namespace and the two ports, because they are inside the peer
  addresses the log recorded. Changing any of them on a live cluster means starting over with new
  volumes.
- `terminationGracePeriodSeconds` must exceed your longest long-poll pop, 30 seconds by default,
  because a parked pop is an in-flight request that SIGTERM drains, and on top of that a leader
  first hands its leadership to a caught-up voter.
- No CPU limit. The raft heartbeat and the commit path are latency-sensitive, and CFS throttling
  turns a burst into scheduler latency at exactly the moment a follower is waiting for a heartbeat.
  Memory has no such caveat: request equals limit.
- Hard anti-affinity puts each voter on its own node, because two voters on one machine turn one
  machine's failure into the loss of a majority. Spread over zones where you have them.
- The disk gate refuses writes with `507` once the volume is 85% full
  (`QUEEN_RAFT_DISK_HIGH_PCT`) and resumes below 80% (`QUEEN_RAFT_DISK_LOW_PCT`). Size the claim for
  retention, not for throughput.
- Nothing but the other pods belongs on port 7400: keep it off the client Service and close it with
  a NetworkPolicy ([the raft port](/deploy/security#the-raft-port)).
- A pod that exits with code 75 is a follower that fell too far behind and will load a snapshot on
  its next start. The kubelet restarts it in place, and the volume stays.

## Verify

```bash
kubectl -n queen rollout status statefulset/queen
kubectl -n queen port-forward svc/queen 6632:6632 &
curl -s http://localhost:6632/api/v1/system/raft/membership
```

The answer names the `leader` and the `term`, and lists the three voters, each with whether the
leader hears from it (`live`) and how many log entries it is behind (`lag`). Every variable above, and the ones
left at their defaults, is in [configuration](/reference/config).
