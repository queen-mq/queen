The proxy inside the broker binary is what turns one Queen into something you can hand to other
people: for internal teams, for customers, or under a product of your own. Both halves are
Apache-2.0, so the multi-tenant service is yours to run.

The broker already scopes queues by tenant on its own
([broker-native tenancy](/reference/multi-tenant/broker-tenancy)). What the proxy adds is the
reason to trust the tenant: it spends the client's credential, drops any tenant header the client
sent, and hands the request to the broker in-process with the tenant it resolved. Around that it
holds what a shared broker has no place holding: per-cluster API keys and human logins
([credentials](/reference/multi-tenant/auth)), plan limits on rate, size and count
([quotas](/reference/multi-tenant/quotas)), a route classifier that forwards nothing it cannot
name ([endpoints](/reference/multi-tenant/endpoints)), and usage counted from the per-item
statuses the broker actually returned ([metering](/reference/multi-tenant/metering)).

## The shape

Three nouns carry the model:

- **Tenant**: the organisation. Owns users and clusters.
- **Cluster**: the tenant-visible Queen. One hostname, one plan, one queue namespace, backed by a
  broker tenant of its own.
- **Cell**: one physical Queen deployment, a single node or one raft cluster of nodes, on one
  failure domain.

A cluster lives on exactly one cell and never spans two. The proxy's own state, tenants, clusters,
users, roles, API-key hashes, plans and usage, is stored in the cell's replicated key/value store
under a system tenant, so it has the same durability as the messages and every node sees it.

Routing is a DNS label. The proxy reads the cluster slug from the first label of the `Host`
header, so `acme-prod.eu1.example.com` is the cluster `acme-prod`, and one wildcard record covers
every cluster on the cell. The exception is a hostname listed in `QUEEN_PROXY_SHARED_HOSTS`: one
URL fronting many clusters, where the credential does the routing instead
([Proxy](/deploy/proxy#routing)).

## Bring up a cell

<Steps>

1. **Generate the secrets.** `QUEEN_PROXY_JWT_SECRET` signs human sessions and `QUEEN_PROXY_CP_TOKEN`
   guards the control plane. Every node gets the same values.

   ```bash
   SESSION_SECRET=$(openssl rand -hex 32)
   CP_TOKEN=$(openssl rand -hex 32)
   ```

2. **Run the nodes with the proxy on.** On one node:

   ```bash
   QUEEN_RAFT_DIR=/var/lib/queen/raft \
   QUEEN_PROXY_EMBEDDED=true \
   QUEEN_PROXY_PORT=6711 \
   QUEEN_PROXY_JWT_SECRET="$SESSION_SECRET" \
   QUEEN_PROXY_CP_TOKEN="$CP_TOKEN" \
   QUEEN_PROXY_SPOOL_DIR=/var/lib/queen/raft/proxy-spool \
   ./bin/queen
   ```

   A cluster adds its raft variables to each node ([High availability](/deploy/ha)); a complete
   three-node file is [Docker Compose](/deploy/compose). With `QUEEN_PROXY_PORT` set, port 6711 is
   the front door and 6632 the internal broker port, which must stay on a network only you reach.
   Leave `QUEEN_PROXY_PORT` out and the proxy takes 6632 itself, with no unauthenticated port at
   all.

3. **Point a wildcard DNS record at the front door,** so every cluster slug on this cell resolves to
   it.

</Steps>

## Onboard a tenant

One call makes the tenant, the cluster, the admin user and the first API key, in one write: either
all of it exists afterwards or none of it does.

```bash
curl -s -X POST http://127.0.0.1:6711/api/cp/bootstrap \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d '{"tenant_slug":"acme","tenant_name":"Acme Inc","cluster_slug":"acme-prod","plan":"free","admin_email":"ops@acme.example","password":"initial-password","key_name":"default"}'
```

It returns `tenant_id`, `cluster_id`, `user_id`, `api_key`, `password_set` and `can_login`. The key
is plaintext, shown exactly once, and only its sha256 hash is stored; a re-run on the same slugs
returns the existing ids with a null key. `cluster_slug` defaults to the tenant slug and `plan` to
`free`. Leave `password` out for an admin who signs in only through Google or GitHub; `can_login`
is false when the admin has neither a password nor a linked identity, which is legal for API-key-only
onboarding and a silent lockout otherwise.

For the first tenant of a cell, the same thing can come from the environment instead, at every
boot and idempotently: `QUEEN_PROXY_BOOTSTRAP_TENANT` and its companions
([the bootstrap tenant](/deploy/proxy#the-bootstrap-tenant)).

That key is everything a client needs. Same routes, same SDKs, same wire format as a bare broker,
with the hostname doing the routing:

```bash
curl -s -X POST https://acme-prod.eu1.example.com/api/v1/push \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"queue":"orders","partition":"cust-42","payload":{"hello":"world"}}]}'
```

The plan named in that call decides the numbers: requests and messages a second, queues,
partitions per queue, parked long polls, payload and batch size, retained bytes and retention
window. Four plans are seeded, `free`, `dev`, `pro` and `dedicated-s`, and a single cluster is
raised above its plan with an override rather than a forked plan
([the data model](/reference/multi-tenant/tenants)):

```bash
curl -s -X PUT http://127.0.0.1:6711/api/cp/clusters/$CLUSTER_ID/overrides \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d '{"max_queues": 500}'
```

The override keys are the plan's own limit names (`max_req_per_sec`, `max_msgs_per_sec`,
`max_queues`, `max_partitions_per_queue`, `max_payload_bytes`, `max_retained_bytes` and the rest). A
key left out inherits the plan's value, a number replaces it, and `null` makes that one limit
unlimited. A body of `null` clears the whole override.

## More keys

A second API key, for a service that should be revocable on its own, is issued from its hash, so
the plaintext never reaches the proxy or its logs. Generate the key, keep it, and send only the
sha256:

```bash
KEY=qk_live_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')
HASH=$(printf '%s' "$KEY" | shasum -a 256 | cut -d' ' -f1)
curl -s -X POST http://127.0.0.1:6711/api/cp/keys \
  -H "x-queen-cp-token: $CP_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"cluster_id\":\"$CLUSTER_ID\",\"name\":\"ingest-worker\",\"key_hash\":\"$HASH\",\"scopes\":[\"produce\"]}"
```

The scopes are `produce`, `consume`, `read` and `admin`, and a key needs at least one. The answer
carries the key's id, which is what `DELETE /api/cp/keys/:id` revokes.

## Human logins

API keys are for programs. People sign in to the dashboard, and the proxy speaks OAuth for that:
Google and GitHub, plus local bcrypt passwords. Google needs two variables, on every node:

```bash
GOOGLE_CLIENT_ID=...apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=...
GOOGLE_ALLOWED_DOMAINS=acme.example,acme.io   # optional, comma separated
```

The authorised redirect URI is `<public base>/auth/google/callback`, and the base is
`QUEEN_PROXY_PUBLIC_URL` when it is set, otherwise the request's `Host` and `X-Forwarded-Proto`.

What happens when someone arrives is worth knowing exactly, because two of the three outcomes are
refusals:

- The identity is already linked to a user: they are logged in.
- No link, but the **verified** email matches a user: the identity is linked to that user.
- Neither: the login is **denied**, unless `QUEEN_PROXY_AUTOPROVISION=true`, in which case a user
  is created with the role in `QUEEN_PROXY_DEFAULT_ROLE`, `viewer` by default.

Further users and their per-cluster roles are managed in the dashboard's Users view by an operator
([Dashboard](/deploy/dashboard)).

## Turn enforcement on

`QUEEN_PROXY_ENFORCE` defaults to `false`, and that is shadow mode: every rate and quota
decision is computed, logged and metered, and the request proceeds anyway. Size caps and the
two push-block quotas are hard regardless of the flag
([quotas](/reference/multi-tenant/quotas)). Watch a real workload through it, then set it to
`true` on every node.

Rate limits are counted per node: behind a load balancer spreading over three nodes, a cluster can
reach up to three times its plan's rate before every node refuses it
([Proxy](/deploy/proxy#limits-are-per-process)).

One cell, one proxy per node over one replicated state, one control-plane call per tenant, and a
`429` contract the SDKs already honour.
