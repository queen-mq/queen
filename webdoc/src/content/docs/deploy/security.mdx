The broker is one process with one plaintext HTTP listener. It binds `PORT` on `QUEEN_BIND_ADDR`,
which defaults to `0.0.0.0` and so answers on every interface, serves the HTTP API and the
dashboard from that single port, and authenticates nobody until you turn JWT on. That listener has
no TLS and no CORS layer. A cluster opens a second listener, the raft port, for its peers.

Because the broker port has no TLS, the bind address is one of the few controls the binary itself
gives you there. `QUEEN_BIND_ADDR=127.0.0.1` makes it reachable only through something on the same
host. It is the wrong setting in Kubernetes, where the kubelet's probes and the Service both arrive
on the pod IP.

Generate the secrets, keep them, and boot with everything the broker implements turned on:

```bash
JWT_SECRET="$(openssl rand -hex 32)"
QUEEN_ENCRYPTION_KEY="$(openssl rand -hex 32)"
echo "$JWT_SECRET" "$QUEEN_ENCRYPTION_KEY"   # both are needed again later
```

```bash
JWT_ENABLED=true JWT_ALGORITHM=HS256 JWT_SECRET="$JWT_SECRET" \
  QUEEN_ENCRYPTION_KEY="$QUEEN_ENCRYPTION_KEY" \
  QUEEN_RAFT_DIR=/var/lib/queen/raft \
  ./bin/queen
```

The boundaries, and who defends each one:

- HTTP API and dashboard, on `PORT`: optional JWT per route, plaintext, with TLS terminated by the
  [embedded proxy](/deploy/proxy) or by whatever else you put in front, and network policy yours.
- The raft port between cluster nodes: a shared token, plaintext, so the network is yours and not
  optional.
- Payloads at rest in the data directory: optional AES-256-GCM on flagged queues, with key
  management yours.
- The data directory itself: everything the node knows, on a disk you own.
- `x-queen-tenant`, where native tenancy is on: checked for shape and never for authority, so the
  gateway that sets it is yours.

<Aside type="danger">
The last of those is the one boundary the broker refuses to let you leave undeclared.
**`QUEEN_TENANCY_HEADER=1` exits 1 unless `QUEEN_KV_TRUSTED_PROXY=1` is set with it**, with no
exception and nothing to switch off instead.

The reason is that [key/value state](/use/kv) is addressable purely by name. For queues a forged
header is bad and bounded: a caller still has to name a queue, and an ack carries a lease id the
broker minted and a caller cannot guess. In the KV there is no such id, so the only gate is the
tenant, and the tenant is the header, which makes a forged one a read and a write of another
tenant's state knowing only its name. Choosing the header mode is itself the assertion that
something in front sets it and strips the client's, and `QUEEN_KV_TRUSTED_PROXY=1` is where you
write that assertion down. If you cannot make it, do not run with the header. The embedded proxy
does not need it: it hands requests to the broker in-process, with the tenant it resolved from the
credential.
</Aside>

One more surface has no switch on the broker port: `/metrics/prometheus` is public there, broker
authentication cannot protect it, and its per-queue series carry no tenant label, so keep that port
off any network a customer can reach ([Prometheus metrics](/reference/prometheus)).

## The front door is in the same binary

The proxy runs inside the broker process with `QUEEN_PROXY_EMBEDDED=true`, and it is the component
the boundaries above assume. It authenticates two credential kinds, an opaque cluster API key and a
human session, classifies every broker path against a fail-closed table that forwards nothing it
cannot name, and hands the request to the broker in-process with the tenant it resolved from the
credential. An `x-queen-tenant` sent by the client is dropped, not honoured.

It serves TLS itself: set `QUEEN_TLS_CERT` and `QUEEN_TLS_KEY`, both PEM paths, and its listener
speaks HTTPS; set neither and it serves plaintext. Setting exactly one is a boot failure, not a
downgrade. On the proxy's port, `/metrics` and `/metrics/prometheus` answer only with the
control-plane token (`x-queen-cp-token`, the value of `QUEEN_PROXY_CP_TOKEN`) and `404` without it,
and `/api/cp/*` answers `404` altogether when no token is configured.

Where the proxy listens decides what else is exposed. Without `QUEEN_PROXY_PORT`, the proxy fronts
`PORT` and the broker router has no socket of its own: every request goes through a credential.
With `QUEEN_PROXY_PORT` set to another port, the proxy serves that one and `PORT` stays the plain
broker, with its own JWT and tenancy settings: an internal port for clients inside the network,
probes and scrapers, which must not face the internet. The variables are in
[Proxy](/deploy/proxy); the classification table is in
[endpoints a tenant can reach](/reference/multi-tenant/endpoints).

## Authentication

`JWT_ENABLED` is `false` by default, and off means open: every route answers anything that can open
a TCP connection, `DELETE /api/v1/resources/queues/:queue`, `POST /api/v1/system/kv-timers` and
the raft membership routes included, and the dashboard boots as a full admin. The boot log states
the mode in one line, so read it instead of assuming.

Turned on, each route carries an access level and each token carries roles. `/health`, the metrics
endpoints, the dashboard shell and the identity routes stay public whatever you do. The algorithms,
JWKS rotation, boot-time validation and the five access levels, which are a set and not a ladder,
are in [broker authentication](/reference/security/jwt).

## The raft port

The nodes of a cluster talk to each other over plain HTTP on the raft port: votes, log entries,
snapshots, the writes a follower forwards to the leader, membership changes and the dashboard's
cross-node reads. Every request carries `QUEEN_RAFT_TOKEN` in the `x-queen-raft-token` header, and
the receiving node checks it from the headers before it reads the body, so a wrong token costs the
sender a `401` and the receiver nothing. Bodies are capped, a vote far below a log append.

Leave the token unset and the port accepts anyone: whoever can connect can vote in elections,
append entries and push commands into the cluster. With it set, whoever can read the traffic can
read the token, because the port has no TLS. Bind it to a private network, allow it only from the
other nodes' addresses, and keep it off every Service a client uses. Generate the token with
`openssl rand -hex 32` and give every node the same value.

## Payload encryption at rest

Encryption needs two things true at once: `QUEEN_ENCRYPTION_KEY` on the process and
`encryptionEnabled` on the queue. With only one of them the broker stores plaintext and raises no
error, so confirm the `encryption service initialized (AES-256-GCM)` line at boot before trusting
the flag. Every node of a cluster needs the same key, since every node stores every payload. It is
the one control that still holds when someone walks off with a copy of a data directory
([payload encryption at rest](/reference/security/encryption)).

## The data directory

Everything a node knows is in `QUEEN_RAFT_DIR`: the payloads (plaintext unless the queue is
encrypted), the key/value store, timers, consumer offsets, and, with the embedded proxy, its
tenants, users and API-key hashes. Treat the volume, and any copy of it, with the care you give the
credentials: it is not a cache.

JWT on or the proxy in front, TLS on the proxy port, a raft port only the nodes can reach, a key on
the queues that need one, and volumes you would not hand out.
