The proxy is a front door built into the broker. It does two jobs, and most deployments want only
one of them.

As a **front door**, it terminates human identity: the dashboard login, Google or GitHub, and
per-cluster roles. The broker has no concept of a user, so this is where one lives.

As a **multi-tenant edge**, it also spends API keys, sets the tenant, enforces plan quotas and
meters usage. That is [multi-tenant](/deploy/multi-tenant); this page is how to run it either way.

## Turning it on

```bash
QUEEN_PROXY_EMBEDDED=true
QUEEN_PROXY_JWT_SECRET=...     # openssl rand -hex 32, the same on every node
```

That is the whole switch. The proxy starts inside the broker process, keeps its tables in the
broker's replicated key/value store under a system tenant of its own, and reaches the broker
in-process, without a socket in between. There is no second service to deploy and no database to
give it, and on a cluster every node runs the same proxy over the same replicated state, so a key
issued through one node works on all of them.

`QUEEN_PROXY_JWT_SECRET` signs human sessions with HS256; `QUEEN_PROXY_JWT_ED25519_PEM`, an
Ed25519 private key in PEM, does the same with EdDSA. Every node has to hold the same material,
because a session minted by one node is presented to another. Leave both out and the proxy still
starts, since an API-key-only front door is a supported shape: it warns at boot, and the console
login answers `503` instead of issuing a session. Material that is supplied and does not load is a
boot failure.

## Two port layouts

Where the proxy listens decides what the broker port is.

| `QUEEN_PROXY_PORT` | The proxy serves | `PORT` serves |
| --- | --- | --- |
| unset, or equal to `PORT` | `PORT` | nothing else: the broker router has no socket, so every request needs a key or a session |
| another port, for example `6711` | that port | the broker router directly, with its own JWT and tenancy settings: an internal port for trusted clients, probes and scrapers |

The second layout is the one to use when in-cluster consumers should keep dialling 6632 with no
credential while humans and external clients come through 6711. Port 6632 then must never be
exposed beyond the network you trust. On the proxy's port, `/health` passes straight through to the broker
for probes, and `/metrics` and `/metrics/prometheus` answer only with the control-plane token.

## State and the spool

Nothing the proxy knows lives outside the data directory. Tenants, clusters, users, roles, API-key
hashes, plans and the usage rollup are rows in the replicated key/value store, written through the
same log as every other write, so they survive a node and follow the cluster's quorum.

The one local path is the meter's spool, where usage that could not be written yet is parked:
`QUEEN_PROXY_SPOOL_DIR`, default `./queen-proxy-spool`, relative to the working directory. Put it on
the data volume, for example `/var/lib/queen/raft/proxy-spool`: on a read-only root filesystem the
default is not writable, and losing the spool loses usage rather than traffic.

## The bootstrap tenant

A fresh cell has no tenants, and a proxy with no tenants routes nothing. The first one can come from
the environment:

| Variable | Default | What it does |
| --- | --- | --- |
| `QUEEN_PROXY_BOOTSTRAP_TENANT` | unset | Tenant slug. The cluster gets the same slug. Unset: no bootstrap |
| `QUEEN_PROXY_BOOTSTRAP_EMAIL` | `admin@localhost` | The admin user |
| `QUEEN_PROXY_BOOTSTRAP_PASSWORD` | unset | The admin's password. Unset: the admin signs in through OAuth, or not at all |
| `QUEEN_PROXY_BOOTSTRAP_PLAN` | `dev` | The cluster's plan code |
| `QUEEN_PROXY_BOOTSTRAP_API_KEY` | unset | A plaintext API key to issue on that cluster, with all four scopes |

The bootstrap runs at every boot, on every node, and is idempotent: a restart or a second node
changes nothing. The key must start with `qk_`, because the proxy treats a bearer token as an API
key only with that prefix. Generate one with
`qk_live_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')` and keep it in a secret.

## The control plane

Everything after the bootstrap goes through `/api/cp/*` on the proxy's port, guarded by
`QUEEN_PROXY_CP_TOKEN` in the `x-queen-cp-token` header. With no token configured the whole surface
answers `404`, as if it did not exist.

| Route | Does |
| --- | --- |
| `POST /api/cp/bootstrap` | A tenant, its cluster, an admin and a first API key, in one call |
| `POST /api/cp/tenants` | A tenant |
| `POST /api/cp/clusters` | A cluster, creating its tenant if needed |
| `GET /api/cp/clusters/:slug` | A cluster's ids |
| `PUT /api/cp/clusters/:id/overrides` | Limits above or below the plan for one cluster (`null` clears them) |
| `PUT /api/cp/clusters/:id/status` | The cluster's status |
| `GET /api/cp/clusters/:id/usage` | The last hour of metered minutes |
| `POST /api/cp/keys` | An API key, from its sha256 hash: the plaintext never reaches the proxy |
| `DELETE /api/cp/keys/:id` | Revokes a key |

The walkthrough is [multi-tenant](/deploy/multi-tenant).

## Routing

A request's cluster is the **first DNS label of the `Host` header**, matched against a cluster slug,
so `acme-prod.example.com` acts on the cluster `acme-prod` and one wildcard record covers the rest.
A port-forward therefore needs the header spelled out, or the request has no cluster:

```bash
curl -H "Host: acme-prod.example.com" -H "Authorization: Bearer $KEY" http://127.0.0.1:6711/api/v1/resources/queues
```

`QUEEN_PROXY_SHARED_HOSTS` lists full hostnames that front several clusters at once: on a listed
host the label names nothing, and the credential does the routing. An API key acts on the cluster
it was issued on; a human session names its cluster with `x-queen-act-cluster`. Configuring any
shared host changes what the whole listener tells strangers: an unauthenticated caller gets `401`
where an unknown host used to answer `421`, so that the wildcard record is not a directory of
cluster slugs ([credentials](/reference/multi-tenant/auth)).

`QUEEN_PROXY_DEFAULT_CLUSTER` is a different feature: it maps every unresolvable `Host` to one
cluster. That is harmless while exactly one cluster exists and a cross-cluster misroute the moment
there are two, so it is only for a cell that will only ever hold one.

## The single-tenant front door

The common case is not the multi-tenant one: one team, one cluster, workloads inside the network
and humans on the console. Run the proxy on its own port, keep the workloads on `PORT` with no
credential, and set `QUEEN_PROXY_TENANT_HEADER=false`. The proxy then stops setting a tenant of its
own, still drops any `x-queen-tenant` a client sends, and console and API-key traffic land in the
broker's default tenant, the same one the workloads on `PORT` use. Without it the bootstrap cluster
gets a broker tenant of its own, and the console shows none of the queues the workloads created.
That setting is right for a single-tenant cell and wrong for a multi-tenant one.

## TLS

The proxy's listener serves TLS itself when `QUEEN_TLS_CERT` and `QUEEN_TLS_KEY`, both paths to PEM
files, are set. The two are both or neither: setting exactly one is a boot failure, not a
downgrade, so a half-configured listener never quietly answers in the clear. With neither, the
listener is plaintext and TLS belongs to whatever is in front of it. The broker port behind it has
no TLS in either case.

## Limits are per process

Rate limits and the parked long-poll gauges are counted in the process, with no shared store: a
cluster's traffic is limited by each node's proxy on what that node sees. Behind a load balancer
spreading over three nodes, a cluster can therefore reach up to three times its plan's rate before
every node refuses it.

`QUEEN_PROXY_ENFORCE` defaults to `false`, which is shadow mode: every rate and quota decision is
computed, logged and metered, and the request proceeds anyway. Size caps and the two push-block
quotas are hard regardless ([quotas](/reference/multi-tenant/quotas)).

## Other variables

| Variable | Default | What it does |
| --- | --- | --- |
| `QUEEN_PROXY_PUBLIC_URL` | unset | The public base URL, used for OAuth redirects and the session audience |
| `QUEEN_PROXY_COOKIE_DOMAIN` | unset | The session cookie's domain |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | unset | Google login; `GOOGLE_ALLOWED_DOMAINS` restricts it |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | unset | GitHub login |
| `QUEEN_PROXY_AUTOPROVISION` | `false` | Create a user on a first OAuth login, with `QUEEN_PROXY_DEFAULT_ROLE` (`viewer`) |
| `QUEEN_PROXY_OPERATOR_ENABLED` | `false` | Lets live operators open cell-wide routes |
| `QUEEN_EDGE_TRUSTED_PROXIES` | unset | Load balancer ranges whose forwarded client address the edge believes |
| `QUEEN_PROXY_UPSTREAM_TIMEOUT_MS` | `35000` | Ceiling on one broker call that is not a long-poll pop |
| `QUEEN_PROXY_LONGPOLL_MAX_MS` | `90000` | Clamp on the wait a client may ask for on `wait=true` |
| `QUEEN_PROXY_LONGPOLL_MARGIN_MS` | `10000` | Added on top of that clamped wait, so the broker's wait expires first |
| `QUEEN_PROXY_STALE_GRACE_MS` | `600000` | How long a last known-good cluster row may be served when the store does not answer |

<Aside type="danger">
`QUEEN_PROXY_DEV_INSECURE=true` does not weaken authentication, it removes it: every request
becomes an API-key principal with all four scopes before any credential is read. Never set it
anywhere a network can reach.
</Aside>

## Registering the OAuth redirect

Register `<public url>/auth/google/callback` with Google. The path matters: `/api` is the proxy's
own prefix, so a redirect under it is rejected before it reaches the OAuth handler rather than
logging anyone in. With `QUEEN_PROXY_PUBLIC_URL` unset, the proxy rebuilds the base from the
request's `Host` and `X-Forwarded-Proto`.
