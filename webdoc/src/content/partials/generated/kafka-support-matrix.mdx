The facade advertises **26 Kafka APIs**. Every row is read out of `protocols/queen-kafka/src/versions.rs` when the site is built: the table the ApiVersions answer is made from, and the one every incoming request is checked against.

| API | Versions | Where the window ends, and why |
| --- | --- | --- |
| `AddOffsetsToTxn` | v0–v3 | v3 answers everything v4 does. v4 exists for KIP-890's transaction protocol 2, in which clients stop sending this request. |
| `AddPartitionsToTxn` | v0–v3 | Ceiling: v4 is a different request, KIP-890's broker-to-broker verification, which no client sends. |
| `ApiVersions` | v0–v3 | Ceiling: one below the schema, on purpose. v3 is what clients negotiate with a Kafka 3.x broker, and a client that opens at v4 (Java 4.x does) is answered with this window and retries at v3, as the protocol specifies. |
| `CreatePartitions` | v0–v3 | The whole window. An increase raises the width of a topic, and the next Metadata reports it; a decrease or an equal count is refused with Kafka's own sentences, and so is a manual replica assignment. |
| `CreateTopics` | v2–v6 | Ceiling: v7 returns a topic id, which the facade does not mint. A partition count of -1 (v4) takes the default width, and v5 answers the width and the replication factor (the number of raft voters) with no configs: a topic's configs are accepted and not applied yet. |
| `DeleteGroups` | v0–v2 | The whole schema; v2 only changes the encoding. Deleting a group with no members deletes the Queen consumer group of that name, with its position on every queue. |
| `DeleteTopics` | v1–v5 | Ceiling: v6 accepts a topic id in place of a name. v5 adds `error_message`, which says in words that there is no such queue. |
| `DescribeConfigs` | v1–v4 | Up to the schema's v4. A topic's configs are accepted when it is created and not applied yet, so a describe answers no entries rather than values nothing enforces; an unknown topic answers UNKNOWN_TOPIC_OR_PARTITION. |
| `DescribeGroups` | v0–v3 | Ceiling: v4 carries `group_instance_id`. v3's authorized operations are answered with Kafka's own 'omitted' value, because there is no ACL model. |
| `EndTxn` | v0–v3 | Ceiling: v5 returns a new producer epoch from inside EndTxn (KIP-890's transaction protocol 2), which the facade does not do. A commit writes the transaction's records and offsets in one raft entry; an abort drops them, so no uncommitted record ever enters the log. |
| `Fetch` | v4–v6 | Ceiling: v7 introduces fetch sessions (KIP-227), state a broker keeps per connection. The facade keeps none, so a request names every partition it wants every time. The raft leader serves it, because a follower can be behind offsets a consumer already read. One side effect: librdkafka compresses zstd only for brokers at Fetch v10 or later, so librdkafka-based producers send their zstd batches uncompressed here. |
| `FindCoordinator` | v0–v3 | Ceiling: v4 is the batched form, for clusters where groups live on different brokers. Here the raft leader coordinates every group and every transactional id, and every answer names it. |
| `Heartbeat` | v0–v2 | Ceiling: v3 carries `group_instance_id`. |
| `InitProducerId` | v0–v4 | Ceiling: v5 exists for KIP-890's transaction protocol 2, which the facade does not run. v3 matters: it is KIP-360's epoch bump, which lets a Java producer recover from a gap in its sequence instead of failing. A transactional id keeps its producer id across restarts, at the next epoch, from the raft leader. |
| `JoinGroup` | v0–v4 | Ceiling: v5 carries `group_instance_id`, and static membership is not supported. A member that joins without an id is given one in the same answer, with no MEMBER_ID_REQUIRED round trip. |
| `LeaveGroup` | v0–v2 | Ceiling: v3 carries `group_instance_id` and lets one request remove several members. |
| `ListGroups` | v0–v4 | Ceiling: v5 adds `group_type`, which tells classic groups from KIP-848 ones, and KIP-848 is not supported. v4's state filter (`--state`) is honoured. |
| `ListOffsets` | v1–v5 | Ceiling: v7 adds MAX_TIMESTAMP, a question about the records' own timestamps, which the broker does not read. Up to v5 there are three questions (earliest, latest, a concrete time) and the raft leader answers all three; a time is looked up on the broker's append clock. |
| `Metadata` | v0–v9 | Ceiling: v10 adds topic ids, and the facade has no registry to resolve a topic by id. v9 is already the flexible encoding and carries every field a client reads. Every raft voter is listed as a broker and as an in-sync replica of every partition, and the raft leader as the leader of them all. |
| `OffsetCommit` | v2–v6 | Ceiling: v7 carries `group_instance_id`, and static membership is not supported. Floor: v0 and v1 are the ZooKeeper-era offset store. |
| `OffsetFetch` | v1–v7 | Ceiling: v8 asks about several groups in one request and changes the response shape. v7's `require_stable` costs nothing: a transaction's offsets are written at its commit, in the same raft entry as its records, so every offset returned is already stable. |
| `Produce` | v3–v9 | Floor: v3 is the first version that carries RecordBatch v2, the format every client of the last decade sends. Ceiling: v10 adds a leader-change hint, and v13 names topics by id. Records go to the raft leader, which leads every partition; another node answers NOT_LEADER_OR_FOLLOWER and the client refreshes its metadata. |
| `SaslAuthenticate` | v0–v1 | Ceiling: v2 only changes the encoding. v1's `session_lifetime_ms` is answered 0, so no client re-authenticates on a timer. |
| `SaslHandshake` | v1 | v1 only: the handshake is followed by SaslAuthenticate requests, the framed flow current clients use. PLAIN is the one mechanism, and its password is a Queen token. |
| `SyncGroup` | v0–v2 | Ceiling: v3 carries `group_instance_id`. |
| `TxnOffsetCommit` | v0–v3 | v3 has to be in the window: kafka-clients refuses to build this request below v3 when group metadata is set, which every consume-transform-produce loop does. Ceiling: KIP-890's transaction protocol 2. |

### Not offered

A client that sends one of these gets no answer: the connection closes, which is what Apache Kafka does with a request it cannot parse (the node logs the key at debug level). A client that read the ApiVersions answer never sends one.

| API | What a client wants it for | Why it is not here |
| --- | --- | --- |
| `ConsumerGroupHeartbeat` | The KIP-848 consumer group protocol (`group.protocol=consumer`). | Not supported. Groups use the classic protocol, which every Kafka 4.x client still uses by default; a client set to `consumer` fails at once with an error that names `group.protocol=classic`. |
| `DeleteRecords` | Truncating a partition below an offset: `kafka-delete-records.sh`, the clear-messages buttons of kafka-ui and AKHQ, and Kafka Streams purging its repartition topics. | Queen has no trim to an offset yet: a partition's start moves by retention and when the queue is deleted. Answering would report a low watermark that did not move. Delete and recreate the topic instead. |
| `OffsetForLeaderEpoch` | Detecting log truncation after a leader change. | Clients check ApiVersions first and skip that validation for a broker without the key. Raft never truncates an acknowledged entry. |
| `DescribeAcls` | Listing ACLs (`kafka-acls.sh --list`). | There is no ACL model: authorization is Queen's, on the token. |
| `CreateAcls` | Creating ACLs. | Same reason. |
| `DeleteAcls` | Deleting ACLs. | Same reason. |
| `AlterConfigs` | Replacing a topic's configuration (the deprecated full-replacement form). | A topic's configs are accepted when it is created and not applied yet, so a change would report a setting that nothing enforces. |
| `IncrementalAlterConfigs` | Changing a topic's configuration (`kafka-configs.sh --alter`). | Same reason. |
| `DescribeLogDirs` | Log directories and the bytes each partition holds (`kafka-log-dirs.sh`). Some topic creators also wait on it until every replica has its log. | Not offered yet. A tool that needs it reports the broker as too old; to wait for a new topic, read Metadata (leaders and in-sync replicas) instead. |
| `OffsetDelete` | Deleting a group's committed offsets for some partitions (`kafka-consumer-groups.sh --delete-offsets`). | Not offered yet: a group's positions go with the group (DeleteGroups). |
| `CreateDelegationToken` | A broker-signed token derived from a SCRAM login. | The facade mints no credentials: the password of a SASL/PLAIN login is a Queen token, checked by Queen. |
| `RenewDelegationToken` | Extending a delegation token. | Same reason. |
| `ExpireDelegationToken` | Revoking a delegation token. | Same reason. |
| `DescribeDelegationToken` | Listing a principal's delegation tokens. | Same reason. |
| `ElectLeaders` | Moving a partition's leadership to its preferred replica (`kafka-leader-election.sh`). | Every partition is led by the raft leader, which raft elects on its own. |
| `AlterPartitionReassignments` | Moving replicas between brokers (`kafka-reassign-partitions.sh`, Cruise Control). | Every raft voter holds every partition, so there is nothing to move. |
| `ListPartitionReassignments` | Reassignments in flight. | Same reason. |
| `DescribeClientQuotas` | Produce and fetch quotas per user and client id. | Queen's limits are per tenant; Kafka's quota entities have nothing to map onto. |
| `AlterClientQuotas` | Changing those quotas. | The same mapping problem, and it would let a client raise its own tenant's limit. |
| `DescribeUserScramCredentials` | Listing SCRAM users. | SASL here is PLAIN, checked against Queen, and the facade keeps no user store. |
| `AlterUserScramCredentials` | Creating or rotating a SCRAM credential. | Supporting SCRAM would make the facade a credential store, with secrets of its own at rest. |
| `DescribeQuorum` | KRaft's metadata quorum (`kafka-metadata-quorum.sh`). | Queen's raft group is not a KRaft quorum. Its state is in `GET /health` and `GET /api/v1/raft/status`. |
| `DescribeCluster` | Cluster id, controller and brokers in one call. | Answerable, and left out because the Java and librdkafka admin clients build `describeCluster()` from a Metadata request, which works. |
| `DescribeProducers` | Producer state per partition (`kafka-transactions.sh find-hanging`). | An idempotent producer keeps no state here: each record's producer id, epoch and sequence become its Queen transaction id, and Queen's dedup window drops a retry. |
| `DescribeTransactions` | One transaction's state. | An open transaction's records wait in the raft leader's memory until its commit; there is no transaction log to describe. |
| `ListTransactions` | Transactions in flight. | Same reason. |
