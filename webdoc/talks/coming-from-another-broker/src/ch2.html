2.1 · Today, on Kafka

One offset per partition. A failure blocks it, or breaks order.

// KafkaJS: you commit a position, not an answer
const c = kafka.consumer({ groupId: 'confirm' })
await c.subscribe({ topics: ['bookings'] })
await c.run({
  autoCommit: false,
  eachMessage: async (m) => {
    await confirm(m.message) // throw: blocks
    const n = BigInt(m.message.offset) + 1n
    await c.commitOffsets([{ topic: m.topic,
      partition: m.partition, offset: `${n}` }])
  },
})
Elsewhere
RabbitMQ
An ack per message, and dead letters after a delivery limit (quorum queues). The order across consumers is not kept.
SQS
A visibility timeout per message, a lease, and a redrive to a DLQ after maxReceiveCount. In a FIFO queue a failing message holds its group, as in QueenMQ.

2.2 · QueenMQ

Every message gets a lease and an answer.

await queen.queue('bookings')
  .group('confirm')
  .each()
  .consume(async (msg) => {
    await confirm(msg.data)  // throw = failed
  })  // return = completed
  • A pop leases the message to one worker for leaseTime (30 s). A worker that dies: the lease runs out, another worker gets it, and no retry is spent.
  • A throw is a failed answer: the message comes back after retryDelay (5 s), and only its booking waits.
  • After retryLimit failures (5), it goes to the dead-letter queue with its error, and the booking moves on.
  • Every group gets every message and its workers compete, as in Kafka. Two more answers: retry (no retry spent) and dlq (now).

2.3 · QueenMQ

Fewer round trips, the same order.

await queen.queue('bookings')
  .group('confirm')
  .batch(100)        // messages per pop
  .partitions(10)    // bookings per pop
  .concurrency(4)    // handlers at once
  .renewLease(true, 10000)
  .each()
  .consume(confirm)
  • .partitions(N): one pop drains up to N bookings, each one still in order.
  • Leave batch and partitions out, and the broker sizes every pop (autopilot).
  • .renewLease(true, 10000) keeps the lease while a long handler runs.
  • .partition('booking-9137') pops one booking only.

2.4 · QueenMQ

The history stays. A seek moves a group.

// a new group can start in the past
await queen.queue('bookings')
  .group('audit')
  .subscriptionFrom('2026-11-10T10:00:00Z')
  .consume(audit)

// a group that exists moves with a seek
await queen.admin.seekConsumerGroup(
  'confirm', 'bookings',
  { timestamp: '2026-11-10T10:00:00Z' })
// { toEnd: true }: skip all it has not read
  • An answer moves the group's cursor. The message stays until retention removes it.
Trap

A new group starts at the end (new), like auto.offset.reset=latest. .subscriptionMode('all') reads the history; .subscriptionFrom(time) starts at a time.
