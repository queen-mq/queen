4.1 · Today, on Kafka

Kafka delivers now. "Later" is another system.

  • Kafka has no delay per message.
  • Teams add a table of due reminders and a cron job that scans it every minute.
  • Or one delay topic per duration, with consumers that wait until each message is due.
  • Moving or cancelling a reminder means finding it again.
Elsewhere
RabbitMQ
A message TTL plus a dead-letter exchange, or the delayed-message plugin, which keeps delayed messages on one node.
SQS
DelaySeconds, up to 15 minutes per message.

4.2 · QueenMQ

A timer is a message for later.

// booking-9137 is created
await queen.timer('payment-reminders')
  .key('booking-9137')
  .partition('booking-9137')
  .delay('15m')
  .payload({ id: 'booking-9137' })
  .schedule()          // 'scheduled'

// the guest paid
await queen.timer('payment-reminders')
  .key('booking-9137').cancel()
  • Named by its queue and key. The same key scheduled again moves it.
  • It fires as a real message, through the log: never early, a little late (checked every 50 ms).
  • With the booking's partition, it arrives in order with the booking's events.

4.3 · QueenMQ

Schedule it in the step that wants it.

// the booking step
await queen.transaction()
  .ack(msg, 'completed',
    { consumerGroup: 'bookings' })
  .timer('payment-reminders').key(id)
  .partition(id).delay('15m')
  .payload({ id }).schedule()
  .commit()

// the payment step
await queen.transaction()
  .ack(pay, 'completed',
    { consumerGroup: 'payments' })
  .kv.put('bookings', id, { status: 'paid' },
    { ttl: '30d' })
  .timer('payment-reminders').key(id).cancel()
  .commit()
Trap

absent on a cancel may mean the timer already fired: the reminder's handler checks the booking first.

4.4 · QueenMQ

The same wait for every message: two queue options.

await queen.queue('room-updates')
  .config({
    leaseTime: 30,
    retryLimit: 5,
    retryDelay: 5000,
    dedupWindowSeconds: 86400,
    retentionEnabled: true,
    retentionSeconds: 604800,
    delayedProcessing: 300, // 5 min each
    windowBuffer: 3,        // bursts
  })
  .create()
  • delayedProcessing: every new message waits that many seconds after its push.
  • windowBuffer: a burst waits that long, then is handed over as one batch. A delay per message is a timer.
