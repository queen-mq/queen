8.1 · Today, on Kafka

Debezium, Connect, Kafka: three systems to move a row.

  • Change data capture is Debezium, running on a Kafka Connect cluster, writing to Kafka.
  • Back into a table: a JDBC sink connector, or a consumer you write.
  • Each one has its own configuration, its own offsets and its own ways to fail.
Elsewhere

Debezium Server, a process of its own, writes changes to RabbitMQ, Kinesis, Pub/Sub and others.

8.2 · QueenMQ

A table becomes a queue, in commit order.

PUT /api/v1/connectors/bookings-src
{
  "kind": "source",
  "connection": {
    "host": "pg", "database": "app",
    "user": "queen", "password": "…" },
  "source": { "tables": [
    { "table": "public.bookings",
      "queue": "bookings" } ] }
}
  • Each committed change is a message, in the partition named after the row's key. One Postgres transaction is one QueenMQ transaction.
  • The WAL position commits with the messages: after a crash, nothing is sent twice.
  • Needs PostgreSQL 17+, wal_level=logical, and QUEEN_ENCRYPTION_KEY on the broker.

8.3 · QueenMQ

A queue becomes a table, exactly once.

PUT /api/v1/connectors/bookings-report
{
  "kind": "sink",
  "connection": { … },
  "sink": { "queue": "bookings",
            "table": "public.bookings_report",
            "mode": "upsert" }
}
appendeach message is a new row
upsertinsert, or update the row with its key, with the columns it names
cdca source event, applied: insert, update, delete
sqlyour statement, with parameters from the message

8.4 · QueenMQ

Four things to know before you turn it on.

The slot keeps WAL

A replication slot keeps WAL while the source is down, and can fill the database's disk. Set max_slot_wal_keep_size, and alert on queen_pg_source_slot_lag_bytes.

Every table needs a key

A primary key, or a unique index as replica identity. A table without one is refused.

A refused row

A message Postgres refuses (a constraint, a wrong type) is tried a few times, then dead-lettered with the database's error. Its partition goes on.

Key = partition

In upsert and cdc mode, keep the table's key aligned with the partition. Order holds inside a partition: two partitions writing one row would race.
