7.1 · Today, on Kafka

What happened to booking-9137? Ask three topics.

  • Each topic is its own log with its own offsets. There is no order across topics.
  • Finding one booking means reading every partition of every topic, or exporting to a search index first.
  • Stream processing is Kafka Streams: Java only, state in RocksDB and changelog topics, repartition topics to join by key.
Elsewhere
RabbitMQ, SQS
A message is gone once it is acked: no history to ask (RabbitMQ Streams aside).
Pulsar
History is kept; stream processing is Pulsar Functions or Flink.

7.2 · QueenMQ

One log of everything, in commit order.

// what happened to one booking, in the last day
for await (const e of queen.feed({
  partitions: ['booking-9137'],
  since: '1d', follow: false,
})) {
  console.log(e.position, e.queue, e.data)
}

// live: every Italian booking from now on
queen.feed({ queues: ['bookings'],
  where: [['data.country', '=', 'IT']] })
  • One position across all queues. Nothing is leased or acked: every group still gets its messages.
  • Followers serve it, not the leader. where is checked by the broker.

7.3 · QueenMQ

Join two queues by booking.

await Stream
  .fromFeed(queen,
    { queues: ['bookings', 'payments'] })
  .join({
    sides: { booking: 'bookings',
             paid: 'payments' },
    within: '1h',
    select: (got, id) => ({ id,
      amount: got.paid.data.amount }),
    onTimeout: (got, missing, id) =>
      ({ id, missing }),
  })
  .to(queen.queue('paid-bookings'))
  .run({ queryId: 'paid-bookings' })
  • The key is the partition: booking-9137 in bookings meets booking-9137 in payments, in either order.
  • The position commits with the outputs. After a restart the open joins come back from a snapshot, and nothing is sent twice.

7.4 · QueenMQ

A booking, then its payment within 15 minutes.

Stream.fromFeed(queen,
    { queues: ['bookings', 'payments'] })
  .pattern({
    key: (m) => m.partition,
    start: (m) => m.queue === 'bookings',
    then: (m) => m.queue === 'payments',
    within: '15m',
    onMatch: (b) => ({ paid: b.partition }),
    onTimeout: (b) => ({ remind: b.partition }),
  })
  .to(queen.queue('payment-followups'))
  .run({ queryId: 'payment-followups' })
  • Chapter 4's reminder, as a stream: a booking, then its payment, or a reminder. .joinTable adds the latest row of a table queue to each message.
  • Windows run on the log's clock: a quiet feed still closes them on time.

7.5 · QueenMQ

Read a stream's state live, from any process.

await Stream
  .fromFeed(queen, { queues: ['availability'] })
  .windowTumbling({ seconds: 60 })
  .aggregate({ count: () => 1 })
  .name('perMinute')
  .run({ queryId: 'per-minute', shards: 4 })

// anywhere else
const { found, value } = await Stream
  .view(queen, 'per-minute')
  .get('perMinute', 'hotel-7')
  • shards: 4: four processes, each with its partitions, its position and its lock.
  • Event time: a step can order messages by a time inside them (eventTime, allowedLateness).
