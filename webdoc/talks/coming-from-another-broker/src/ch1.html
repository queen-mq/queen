One booking =
one partition

In Kafka a partition is a shard you size up front. In QueenMQ it is the thing you work on: one booking, one customer, one conversation.

  1. 1.1Kafka today: bookings share partitions
  2. 1.2QueenMQ: configure, then a partition per booking

1.1 · Today, on Kafka

A fixed number of partitions. Bookings share them.

  • You pick the partition count when you create the topic.
  • The key is hashed: hash(key) % 4. Here booking-9137 and booking-4410 land in partition 2.
  • One consumer works a partition, in order. A slow message holds up every booking behind it.
  • Add partitions later, and keys move to other partitions.
Elsewhere
RabbitMQ
Competing consumers on one queue lose the order per key. Keeping it takes a queue per key, or a consistent-hash exchange with one consumer per queue.
SQS FIFO
Message groups keep the order per group: the closest thing to a QueenMQ partition.

1.2 · QueenMQ

Configure once. Then every booking is a partition.

// once, before the first push: name every option
await queen.queue('bookings').config({
  leaseTime: 30, retryLimit: 5, retryDelay: 5000,
  dedupWindowSeconds: 86400,
  retentionEnabled: true,
  retentionSeconds: 604800,
}).create()

// then: one partition per booking
await queen.queue('bookings')
  .partition('booking-9137')
  .push([{ data: { event: 'created' } }])
  • Configure first, every option named: a queue a push creates gets a 60 s lease and no retention.
  • Then the first push to a booking creates its partition: no count to pick. Order holds inside it; workers take any partition with work.

1.3 · QueenMQ

A retry is not a second booking.

await queen.queue('bookings')
  .partition('booking-9137')
  .push([{
    transactionId: 'booking-9137-created',
    data: { event: 'created' }
  }])
  • The same transactionId in the same partition, within dedupWindowSeconds (3600 s by default, 7 days at most), writes nothing.
  • Build the id from the work, never from a fresh UUID.
  • Kafka's idempotent producer covers its own retries in one session. An app that retries after a crash writes the event again.
