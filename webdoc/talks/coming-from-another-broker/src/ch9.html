Three systems
we run on QueenMQ

Not a booking we made up: a guest chat, a channel manager and a tracing service, as they run today. Names are simplified; the flows are real.

  2. 9.2A channel manager: one door in, one door out, a gate

In production · a guest chat

One conversation, one partition, one commit per step.

Usespartition = chat · ack + push in one transaction · a group per client · DLQ · windowBuffer · ephemeral request/reply · KV, lock, timer

LessonCarry one id through every step. A hop that drops it can only be followed by guesswork.

In production · a channel manager and Gate

One door in, one door out, and a gate to the travel sites.

Usespartition by state · ack + push + KV in one transaction · conflation · timers · ephemeral request/reply · Gate: kv.incr as the rate limit

LessonA message is a key, not a payload. A partition whose messages carried every past version kept growing.

In production · a tracing service

Tracing on QueenMQ and object storage, nothing else.

Usespartition = trace id · dedup by event key · a session-window stream · an archiver group · reads by offset · KV

LessonKeep big bodies out of window state: very large traces held whole in a window pushed the brokers past their memory. Since 2.7.0 QueenMQ reads state without copying it.
