3.1 · Today, on Kafka

Three systems, and no commit across them.

  • Confirming a booking: update Postgres, produce to emails, commit the offset.
  • A crash between two of them leaves the step half done.
  • Kafka transactions cover Kafka's writes and offsets, not your database.
  • The usual fix: an outbox table, a relay to read it, an idempotency table. More systems.
Elsewhere
RabbitMQ
Publisher confirms, and channel transactions that cover its own publishes and acks. Never your database.
SQS
Send and delete are separate calls: nothing commits them together.

3.2 · QueenMQ

The ack, the state, the next event: one commit.

.consume(async (msg) => {
  const id = msg.partition   // booking-9137
  await queen.transaction()
    .ack(msg, 'completed',
      { consumerGroup: 'confirm' })
    .kv.put('bookings', id,
      { status: 'confirmed' }, { ttl: '30d' })
    .queue('emails').partition(id)
    .push([{ transactionId: `mail-${id}`,
      data: { id } }])
    .commit()
})
  • One call, one log entry: all of it commits, or none.
  • A call to the outside (a payment, an email provider) is not in the commit: give it an idempotency key from the message.

3.3 · QueenMQ

The state lives next to the messages.

const id = 'booking-9137'
const b = await queen.kv.get('bookings', id)
// { found, value, version: 3 }

const r = await queen.kv.put('bookings', id,
  { status: 'checked-in' },
  { ttl: '30d', expect: b.version })
r.applied  // false if someone wrote since

await queen.kv.incr('quota', 'hotel-7', 1,
  { max: 500, ttl: '1d' })
  • Every write names its lifetime: a ttl, or forever.
  • Every write raises the version. expect makes a write depend on it.
  • A write that did not apply answers applied: false and the current value. It is not an error.
  • KV has no queries: records you search stay in your database.
