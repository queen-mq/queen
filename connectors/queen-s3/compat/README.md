# queen-s3 compat — the reader lane

PLAN_S3_SINK.md §9's compat lane, on the model of
[`protocols/queen-kafka/compat/`](../../../protocols/queen-kafka/compat): real
readers against real objects with nothing faked in between.

The Kafka lane asks "which clients can talk to the facade". This one asks the
mirror question about the other end of the connector: **which lake readers read
what the sink writes, and with which incantation.** The answer is
[MATRIX.md](MATRIX.md), and it is generated by a run — never written by hand.

## Run it

```bash
connectors/queen-s3/compat/run.sh                 # everything, rewrites MATRIX.md
connectors/queen-s3/compat/run.sh duckdb spark    # a subset
connectors/queen-s3/compat/run.sh --keep          # leave the sample lake behind
connectors/queen-s3/compat/run.sh --samples DIR   # reuse a lake instead of building one
```

Needs `docker`, `cargo` and `python3`. Exit status is non-zero if any cell came
back `fail`; an `unsupported` is a documented fact about a reader and a
`not-run` is an admission, and neither fails the lane. Everything it starts is
`--rm` and named `queen-s3-compat-*`; the sample lake is a `mktemp -d` that is
deleted unless you pass `--keep`. The one thing left behind on purpose is the
shared reader image, which is a cache: `docker rmi queen-s3-compat-python`.

## What it does

1. **Builds a sample lake with the sink's own writers.**
   `cargo run --example gen_samples -- <dir>` (source:
   [`../examples/gen_samples.rs`](../examples/gen_samples.rs)) builds `Record`s,
   hands them to `writer::factory` and puts the bytes at the key
   `layout::data_key` names — the same two functions the driver calls. It writes
   the SAME 5 000 records into five prefixes, one per (format, compression) the
   sink can emit:

   ```
   <dir>/jsonl-zstd/queue=orders/dt=2026-09-04/hour=10/w-0000001842-…-….jsonl.zst
   <dir>/jsonl-gzip/…   <dir>/jsonl-none/…   <dir>/parquet-zstd/…   <dir>/parquet-snappy/…
   <dir>/expected.json
   ```

   Two queues, three partitions each, two aligned hour windows,
   `Layout::Merged`. The partition names are awkward on purpose: `cust 42/eu`
   has a space and a slash, `région-eu` is not ASCII. 14 records have a JSON
   `null` payload. Offsets are dense from 0 within each partition and span both
   windows, so a reader that loses a window loses a contiguous run and every
   check fails at once.

   The **queue name is not in any row**: it is only the `queue=<esc>` key of the
   path (plan §6.3, §6.4). Two queues are in the lake precisely so that a reader
   has to get it back from the layout to be judged at all — through partition
   discovery (DuckDB, Spark, ClickHouse, PyArrow, pandas, Polars over a Parquet
   prefix root) or by being pointed at one queue's prefix (the three dataframe
   libraries on JSONL, where none of them discovers a thing).

2. **Runs each reader in `readers/` against it**, with the lake mounted
   read-only. Each `readers/<name>.sh <samples-dir>` is self-contained and can
   be run on its own; it prints machine-readable `VERDICT` / `NOTE` JSON lines.
   Most drive a container that runs the check inside it; `clickhouse.sh` drives
   `clickhouse-local` from the host per query, because that image has no Python
   and the check has to be the same code for every reader
   ([`readers/_common.py`](readers/_common.py)).

3. **Renders [MATRIX.md](MATRIX.md)** from the verdict lines
   ([`render_matrix.py`](render_matrix.py)).

## What `ok` asserts

A cell is `ok` only if the reader was **exact**, not merely able to open the
files. Against `expected.json`, for every queue:

- the record count, and the count per partition;
- the number of NULL payloads — a reader that turns JSON `null` into `""` is
  wrong in a way no count catches;
- the sha256 of the `partition|offset` list **in the order the reader's own
  `ORDER BY partition, offset` returned it**, so the ordering is under test and
  not just the contents. On a digest mismatch the check re-sorts client-side and
  says which of the two failed: content, or the engine's string collation;
- plan §7's entity-history query: one awkward partition's first records in
  offset order, with `type`, `amount`, `customer.name`, `note` and the exact
  microsecond `ts` decoded out of the payload.

## What it does NOT assert

- **Nothing about S3.** The lake is a directory. Bucket semantics, SigV4,
  multipart and the versitygw path are the crate's own tests and `test/run.sh`'s
  `s3sink` suite, not this lane.
- **Nothing about the sink's protocol**: no broker, no windows, no commits, no
  exactly-once. This lane starts from bytes on a disk.
- **Nothing about the `per-partition` layout.** Every prefix here is
  `Layout::Merged`, so no partition name ever reaches an object KEY and the key
  escaping of `layout::escape` is not exercised — only the awkward names as
  column VALUES are. Both queue names are plain, so `queue=` never has to be
  unescaped either.
- **Nothing about scale.** 5 000 records and four objects per prefix. Row-group
  pruning is exercised (row groups of 500 rows), a 128 MB object is not.
- **Not a version pin.** The Python readers install the current release of each
  library and PRINT the version they got; MATRIX.md records what was measured on
  the day. The Spark and ClickHouse images are the only pinned ones
  (`QUEEN_S3_SPARK_IMAGE`, `QUEEN_S3_CH_IMAGE`), because which Spark you run
  decides which Hadoop codecs you get, and that is half of what that row
  measures.

## Joining CI

Not yet, and on the same rule as the Kafka lane: when it is boring. It pulls
three container images (one of them a JVM), and the dataframe row installs from
PyPI on every image build, so it is a nightly at best.
