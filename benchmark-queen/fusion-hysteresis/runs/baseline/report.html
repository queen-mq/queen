Queen fusion engine — hysteresis sweep

up-sweep down-sweep — if the two trace different paths, that's real hysteresis from the self-clocked group commit.
How to read it. PG cost ≈ commits/s × fixed fsync cost + rows/s × per-row cost + maintenance. At low offered rate each push is its own commit (msgs/commit ≈ 1) so the fixed fsync dominates and PG cost per message is high. As load rises the fusion engine batches (msgs/commit climbs, commits/s & fsync/s plateau) and cost per message falls. Absolute PG cores usually keep rising; a genuine dip there near the knee would be the non-monotonic effect worth a screenshot. The cliff shows up in the last chart, where achieved peels away from offered.

Fusion ratio — msgs / commit

THE curve: Δn_tup_ins / Δxact_commit. Should climb from ~1 toward preferred/max_batch as load rises.

Commits / s

Rises with load then plateaus once batching kicks in. The plateau = fusion engaged.

WAL fsync / s

pg_stat_wal.wal_sync rate. Flattening while msgs/s keeps rising = the fsync cost is being amortized.

PG cores (absolute)

Mean PG container CPU. Usually monotone up — but watch for a DIP near the knee (the non-monotonic effect).

PG cost per message — cores per Mmsg/s

PG cores ÷ (msgs/s). The amortization curve: should fall steeply then bottom out.
