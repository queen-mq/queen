## The 27/27 FAIL verdict is NOT message loss

467 of 954 010 messages (0.049%) reported missing, and goload classified it as
real LOSS ("consumers were idle at the cutoff"). It is not:

* the gaps are at sequence **1, 2, 3** — the FIRST messages of each tenant, not
  the last, so it is a startup race and not a drain tail;
* undelivered backlog measured directly from the watermarks is **0** —
  `last_offset == committed` on every partition, so nothing is stuck;
* `log_segments` = **954 010** = exactly `sentOk` — every message persisted;
* 0 duplicates, 0 extra, 0 cross-tenant.

Cause: `DEFAULT_SUBSCRIPTION_MODE` defaults to `new` (server/src/config.rs:1268),
documented as "the group starts at the tail". goload never sends
`subscriptionMode` and starts producers and consumers together, so the first
messages per tenant land before the group registers and the group starts PAST
them. Working as designed; the harness races it.

**goload's "real LOSS, not a tail" heuristic is unsound at high cardinality.**
It infers completeness from consumers being idle, but a consumer sampling
`pop-partitions=10` of 5 000 partitions is idle whenever its 10 are empty. Here
the conclusion was wrong for a different reason (mode=new), but the heuristic
would also mislabel genuine un-swept backlog. Do not trust the verdict line
alone — check watermark backlog and firstMissing position.

For the soak: set `DEFAULT_SUBSCRIPTION_MODE=all` on both brokers so a startup
artifact does not mask real loss for days. Existing groups are immune to the
setting and groups are created once at t=0 against an empty backlog, so there
is no replay risk.

# Soak attempt 1 (06:23-06:57 UTC) — VOID: Postgres was sized for half the box

The first soak launch degraded steadily after the partition ramp completed:
worst e2e p99 went 200 ms (808k partitions) -> 416 ms -> 971 ms over ~10
minutes, with all 27 queues over the 200 ms SLO. Throughput never faltered
(1 060 msg/s sustained, zero shed, zero loss, `pool_waiting` 0, ready_age 5 ms)
— the degradation was entirely in delivery latency.

**It is not a valid capacity measurement.** `soak-cell.sh` hardcoded
`MEM_GB=8` and derived Postgres memory from that constant, but the soak box has
15.6 GiB: `shared_buffers` was 2 GB and `effective_cache_size` 5 GB on a machine
that should carry twice that. The curve describes that misconfiguration, not
Queen.

Alice caught it from the DO CPU/load graph: a load spike to 35 at 08:45-08:47
local (06:45-06:47 UTC) while CPU only moved 82% -> 88% — processes blocked,
not computing. The Postgres log named the cause exactly:

```
06:38:19  checkpoint starting: time
06:45:55  automatic vacuum of queen.log_partitions      <- 827k rows
06:45:56  automatic analyze of queen.log_partitions
06:51:49  checkpoint complete: wrote 107344 buffers (40.9%), 126 WAL recycled
```

The first checkpoint after the ramp flushed 40.9% of shared_buffers while
autovacuum hit `log_partitions` in the same window. Creating 827 000 partitions
and 1.7M segments dirties an enormous number of pages and they all come due at
once — any cell that onboards tenants in bulk will hit this shape.

## What changed for attempt 2

Sizing is now derived from the box (`free -m`), never a constant.

| setting | was | now | why |
|---|---:|---:|---|
| `shared_buffers` | 2 GB | 3 997 MB | 25% of actual RAM |
| `effective_cache_size` | 5 GB | 11 193 MB | ~70% |
| `maintenance_work_mem` | 512 MB | 1 GB | vacuum on million-row tables |
| `autovacuum_work_mem` | — | 1 GB | dedicated, not shared with DDL |
| `max_connections` | 500 | 700 | **latent bug**: 2 brokers x DB_POOL_SIZE=300 = 600 > 500 |
| `autovacuum_vacuum_cost_limit` | 200 (default) | 3 000 | default throttles vacuum to a trickle against 1 060 msg/s of churn |
| `checkpoint_timeout` / `max_wal_size` | 15 min / 16 GB | 30 min / 32 GB | spread the write wall over 27 min, not 13.5 |
| `wal_compression` | off | pglz | cuts WAL volume feeding the checkpoint |
| `jit` | on (PG18 default) | off | pure overhead on 2-3 ms OLTP statements |
| `work_mem` | 12 MB | 16 MB | |
| `bgwriter` | default | delay 10ms, lru_maxpages 1000 | writes dirty pages before the checkpoint has to |

`synchronous_commit=on` and `fsync=on` are unchanged — durability is the product
claim and must not be traded for a benchmark number.

## The one finding worth re-testing from the void run

`log_hotlist_reseed_v1` went 58.6 ms -> 428.8 ms (7.3x) while segments grew
954k -> 1.71M (1.8x) — superlinear in SEGMENT count, and 5% of database time.
`log_queue_stats_all_v1` 338 -> 635 ms and `log_refresh_all_stats_v1`
1 391 -> 3 145 ms over the same interval. These scale with segments rather than
memory, so if they are real they will reproduce on the tuned rig at the same
segment counts. That is the check that matters, because segments grow unchecked
until retention starts trimming — a full day away for free, three for dev,
seven for pro.

# Attempt 2 (from 06:57 UTC) — the cliff is the hot-list FULL reseed walk

## Postgres sizing was not the cause

Matched state, both runs at 827 000 partitions and within 0.04% on segments
(1 088 289 vs 1 087 855):

| | attempt 1 (2 GB shared_buffers) | attempt 2 (4 GB, fully tuned) |
|---|---:|---:|
| worst e2e p99 | 199.7 ms | 195.6 ms |

Doubling shared_buffers, quadrupling effective_cache_size, `jit=off`,
`wal_compression`, 6x the autovacuum cost limit and a 30-minute checkpoint moved
matched-state latency by 2%. The tuning was still right — `max_connections` 500
against a 600-connection demand was a live bug — but it is not what governs this
cell's latency.

## What does: Theta(partitions) per ring, on a fixed cadence

`log_hotlist_reseed_v1`, windowed cost against segment count:

| segments | ms/call | calls per 120 s | DB time in the window | cores |
|---:|---:|---:|---:|---:|
| 1 311 664 | 234 | 5 | 1.2 s | 0.01 |
| 1 440 136 | **1 133** | **135** | **153.0 s** | **1.27** |

A 10% growth in segments made each call 4.8x slower AND fired it 27x more often.
The frequency jump is the full-walk cycle landing: the broker runs two reseeds,

* windowed every `QUEEN_HOTLIST_RESEED_MS` (30 s) — Theta(partitions WRITTEN in
  the window), cheap;
* a FULL walk every `QUEEN_HOTLIST_RESEED_FULL_MS` (300 s) — **Theta(partitions
  in the queue), PER RING**.

229 rings (one per tenant-queue) span 827 000 partitions, so the full walk
re-scans every partition in the cell every 5 minutes, and its cost grows with
segments. Add `log_queue_stats_all_v1` (~0.67 cores) and roughly **2 of 8 cores
go to maintenance that scales with CARDINALITY, not with traffic**.

Settings in force (all defaults): `hotlist_reseed_full_ms=300000`,
`hotlist_reseed_ms=30000`, `hotlist_reseed_window_ms=120000` (derived),
`hotlist_shards=8`, `hotlist_window_batch=100`, `hotlist_idle_sweep_ms=300000`.

`QUEEN_HOTLIST_RESEED_FULL_MS` is the lever, and config.rs is explicit that it is
not free: the full walk is the repair path for a wrongly-cleared ring entry, an
INFLIGHT stranded by a dropped pop future, a WHEEL park left by a lost
promote-on-ack, a mesh hint dropped past the coalescing bound, and a backward
seek on a peer. Raising 5 min -> 30 min means each of those hides 6x longer.
That is a product decision, not a benchmark tweak.

## The plan-table consequence

Segments accumulate at ~65k/min and NOTHING trims them until completed-retention
expires: 1 day free, 3 days dev, 7 days pro. That is ~94M segments before the
first trim. This cell hits its cliff at ~1.4M.

So at 35 full-quota tenants the binding constraint on a shared cell is RETENTION
LENGTH, not CPU and not memory. The 1d/3d/7d retentions are far beyond what a
shared cell survives at saturation. The open-ended soak will give the number
that matters: how many hours the cell stays inside the 200 ms SLO.

# Attempt 3 (from 08:09 UTC) — hot-list fix VERIFIED, the wall is gone

Broker rebuilt from the working tree as `queen:soak` (build-broker.sh); the fix
routes the full walk through `log_hotlist_reseed_window_v1` with `p_cutoff`
pinned to '-infinity'. Everything else identical to attempt 2 — same tuned
Postgres, same 35 full-quota tenants, same 1 060 msg/s, same client flags — so
the delta is attributable to the hot-list change alone. Both runs start from an
empty database, so equal elapsed time means equal ramp state.

## Root cause (from 004_log_pop.sql's new header)

The broker calls the reseed through `prepare_cached`. After five executions
Postgres may switch to a GENERIC plan in which every parameter is unknown —
including `p_limit`, which the planner then assumes keeps 10% of rows. That
makes an ordered walk of `log_partitions_pkey`, with the queue applied as a join
filter AFTERWARDS, look 10x cheaper than the bitmap on the queue's own index. At
run time `p_limit` is 10 000 — above every queue — so the walk never stops early
and every page reads EVERY PARTITION IN THE CELL.

Measured by the fix's author on this soak's shape (229 queues, 827k partitions):
851k buffers / 303 ms per ring against 20k / ~10 ms for the custom plan, and
identical for a 500-partition queue — which is why free-tier queues were as slow
as pro ones in every reading. The windowed statement orders by its index's own
leading columns and resolves the queue by scalar subquery, so the bad plan is
not available to it.

This is exactly the Theta(partitions in the CELL) behaviour the soak measured,
and it explains why cost tracked TOTAL stored data rather than per-queue size.

`spstrend.sh` grepped `log_hotlist_reseed_v1`, which the fix makes dead code, so
it silently recorded zeros — a sampler that reads a statement name must be
re-pointed whenever the code stops calling it. Now tracks
`log_hotlist_reseed_window_v1`.

cores, measured this morning and untouched by this fix. It has no interval knob.
With the reseed noise gone it is now the largest remaining maintenance consumer,
and it is the next thing to look at.

# Attempt 4 (from 11:11 UTC) — queue-stats fix VERIFIED flat

Broker rebuilt from the working tree with BOTH fixes (hot-list full walk +
queue-stats). `log_queue_stats_all_v1` now reads a maintained counter instead of
counting segments:

```sql
LEFT JOIN queen.stats st ON st.stat_type = 'queue' AND st.queue_id = q.id
COALESCE(MAX(st.segment_count), 0)
```

No segment scan at all — the cost becomes Theta(queues + partitions).

A cheaper Theta(segments) query still degrades over a multi-day soak; only
Theta(partitions) stops. Partition count is pinned at 827 000 after the ramp

a list endpoint, but the dashboard's segment column is now eventually
consistent — worth knowing before someone files it as a bug.

# Pop autopilot, first live A/B (20:16 UTC) — GOOD CPU, BAD TAIL

Rolled onto the running cell WITHOUT wiping Postgres: brokers swapped one at a
time (passive first — which also exercised a mixed old/new fleet serving the
same cell, the compat path nothing else tests), then the loader restarted with
both knobs unset. Same PG, same 35M segments, same 827k partitions, same 35
full-quota tenants — a within-subjects comparison, not two separate runs.

Harness note: `goload` REJECTED `-pop-batch 0` (`if *pushBatch <= 0 || *popBatch
<= 0`), so it could not express "unset". The SDK needed nothing — `Batch(0)` is
documented as identical to never calling it (`batchSet := s.Batch > 0`), and
`Partitions()` was already skipped at <= 1. One-line harness fix; `-pop-batch 0
-pop-partitions 1` now drives a fully autopilot pop.

## Result

| | baseline (W=10, B=100) | autopilot (W->1, B=200) |
|---|---:|---:|
| e2e p50 | 13.5 ms | 15 ms |
| **e2e p99** | **112 ms** | **380 ms** |
| throughput | 1 060 msg/s | 1 060 msg/s |
| cell CPU | ~78% | ~65% |

**A 3.4x worse tail for ~17% CPU.** Against a 200 ms p99 product promise that is
the wrong side of the trade: 380 ms breaches the SLO in the QUIET phase, worse
than the baseline's checkpoint-window peak (~220 ms). p50 is essentially
unchanged, so the body of the distribution is fine and only the tail collapsed.

## Diagnosis: the error term cannot see the harm

The controller widens on `ready_age` alone. `ready_age` measures how long a RING
ENTRY waited before being claimed — not how long a MESSAGE waited in a partition
nobody visited. So it stays pinned at 5 ms while the tail starves, the controller
reads that as "1 is enough", and stops widening.

Corroborating: `cands_visit=1.1` (genuinely ~1 partition per pop),
`pop_empty_pct=0.0` (no wasted sweeps), hot-list ready depth oscillating
`28 -> 4 -> 1`. When a burst makes 28 partitions ready, W=1 drains them one pop
at a time. The median message never notices because most of the time only 1-4
are ready — exactly the p50-flat / p99-inflated shape measured.

**Suggested fix:** the controller already computes a smoothed ready count but
uses it as a CAP. Make it a widening DRIVER too: if `ready_count` persistently
exceeds `W`, widen regardless of `ready_age`. Small change to the feedback loop,
not a redesign.

## Note on method

Shadow mode would have reported that the controller WANTED W=1. Only running it
closed-loop showed that W=1 starves the tail — the open-loop divergence log
cannot surface a harm the controller's own error term is blind to. Alice's call
to skip shadow was the right one.

The divergence log did work as designed, catching the old client mid-roll:
`explicit partitions=10, controller would choose 1 — diagnostic only`.
